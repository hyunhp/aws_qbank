G: ## AI, ML, deep learning and generative AI are nested
Think of the terms as circles inside each other, not as separate products.
- **Artificial intelligence (AI)** is the widest field: any technique that lets software perform tasks that normally need human judgment. It includes hand-written rule engines as well as learned models.
- **Machine learning (ML)** is a subset of AI where the system learns patterns from data instead of being given explicit rules. A churn model trained on past customers is ML.
- **Deep learning** is a subset of ML that uses multi-layer neural networks, which is what made image, speech and language tasks practical.
- **Generative AI (GenAI)** is built on deep learning, usually very large pre-trained foundation models, and creates new content such as text, images or code.
## Why it matters to an executive
"We already have AI" says nothing about which capability you have. A rules-based FAQ bot is AI but cannot learn; a forecasting model is ML but cannot draft a contract. Each inner circle adds capabilities the outer one does not guarantee.
W: ML inside AI, GenAI inside ML: machine learning is one way of building AI, and generative AI is a deep-learning branch of ML, so "having AI" does not mean you already have ML or GenAI capabilities.
X: A=Three unrelated technologies: they are not independent; each is a subset of the previous one, and GenAI models are trained with ML techniques.
B=ML as rules-only: learning from data instead of hand-coded rules is the defining feature of machine learning, so this reverses the definition.
C=GenAI broader than AI: the nesting runs the other way. GenAI is a narrow, recent part of AI, and ML is not a type of GenAI.
T: AI ⊃ ML ⊃ deep learning ⊃ generative AI; owning an outer circle does not give you the inner capabilities.

G: ## Three shapes of data
AI readiness starts with knowing what shape your data is in, because the shape decides how much work it takes before a model can use it.
- **Structured** data fits a fixed schema of rows and columns, such as an orders table with `order_id`, `customer_id`, `amount`, `order_date`. It is easy to query with SQL and feed to classic ML.
- **Semi-structured** data carries its own tags or keys but no rigid table schema. JSON, XML and log events are typical: `{"event":"click","page":"/cart","ts":"2026-09-01T10:00:00Z"}`. Fields can vary between records.
- **Unstructured** data has no predefined data model: audio recordings, images, scanned PDFs, free-text emails and video. Most enterprise knowledge lives here.
## Example
A support call recording must first be transcribed (for example with Amazon Transcribe) and a scanned contract must be run through text extraction (for example Amazon Textract) before most analytics or ML can use the content.
W: Orders structured, JSON semi-structured, audio and scans unstructured: the database has a fixed schema, JSON events are self-describing key-value records, and recordings and scanned images have no internal schema at all.
X: A=Orders unstructured, recordings structured: this swaps the categories. A relational order table is the textbook example of structured data, and raw audio has no rows or fields.
B=JSON structured, orders and recordings semi-structured: JSON has keys but no fixed table schema, which makes it semi-structured; orders are fully structured and audio is unstructured.
D=All structured because digital: being stored as a file does not give data a schema. The classification describes how the content is organized, not whether it is digital.
T: Fixed schema → structured; self-describing tags like JSON → semi-structured; audio, images and scans → unstructured.

G: ## Garbage in, garbage out
A supervised ML model learns the relationship between input features and a target from its training records. It has no way to know which records are wrong, so it learns the errors as if they were real patterns.
## How bad data hurts a churn model
- Churn is usually defined from fields such as the subscription end date. If 30 percent of those dates are missing or mistyped, many customers are labeled "churned" or "active" incorrectly.
- The model then learns from contradictory examples, and its predictions in production are only as good as those labels.
- More rows do not fix this: five years of data with systematic label errors just teaches the error more confidently.
## Data quality dimensions
Common checks are completeness (no missing values), accuracy (values match reality), consistency (same format everywhere), timeliness and validity. Fixing quality usually means profiling the data, correcting or dropping bad records, and adding validation at the point of entry.
W: Data quality drives model quality: missing and wrong end dates corrupt the churn labels the model learns from, so performance drops no matter how many years of records were used.
X: B=Training data stops mattering after deployment: the deployed model is a direct product of its training data; errors learned during training remain in every prediction until the model is retrained on corrected data.
C=Architecture matters more than data: a more sophisticated algorithm trained on mislabeled data still learns the wrong patterns. The audit points at the data, not the model design.
D=Bigger datasets outweigh quality problems: volume helps with random noise, but a 30 percent systematic error in the target field biases the model regardless of dataset size.
T: A model cannot be better than the data it learned from; fix data quality before adding more data or a fancier model.

G: ## What training a model means
Model training is the process where an algorithm looks at historical examples and adjusts its internal parameters so that its outputs match the known outcomes. A demand model trained on 2022-2023 sales learns how price, season, promotions and product type related to units sold in that period.
## Why the forecast broke
The model only knows the patterns present in its training data. New product lines did not exist in 2022-2023, and they may also change how customers buy existing products. The real world has moved away from what the model learned, which is called **data drift** or **concept drift**.
- Symptom: accuracy falls after a business change, even though nothing in the model changed.
- Fix: collect recent data that includes the new products, retrain, validate against a hold-out period, and redeploy.
- Prevention: monitor forecast error over time and retrain on a schedule or when error crosses a threshold.
W: Training is learning from past data, so retrain: the model's knowledge is frozen at 2022-2023, and retraining with recent sales that include the new product lines lets it learn the current patterns.
X: A=Writing fixed business rules: hand-written rules are not how ML models are trained, and adding rules for each new product abandons the learning approach instead of updating it.
B=Deploying to a bigger server: deployment makes a trained model available for predictions; more compute changes speed and capacity, not what the model has learned.
D=Relabel only the old products: labeling prepares training examples, but the problem is that the new products are missing from the data, so relabeling old products does not help.
T: A model knows only the period it was trained on; when the business changes, retrain on recent data rather than scaling or patching it.

Several ISO and ISO/IEC standards look similar by name but cover different management systems or topics.
- **ISO/IEC 42001** (published 2023) specifies requirements for an **AI management system (AIMS)**: AI policy, roles and accountability, AI risk and impact assessment, controls across the AI lifecycle, and continual improvement. Organizations can be certified against it.

- **ISO 9001** specifies a quality management system for consistent products and services.
- **ISO/IEC 23053** is a framework that describes the components and functions of AI systems that use machine learning. It is descriptive guidance, not a management system standard.
## How they fit together
Many organizations run 42001 alongside 27001, reusing the same harmonized management system structure (clauses for context, leadership, planning, support, operation, performance evaluation and improvement), because AI governance and information security overlap but are not the same.

G: ## What ISO/IEC 23053 is
ISO/IEC 23053 (published 2022) is titled "Framework for Artificial Intelligence (AI) Systems Using Machine Learning (ML)". It gives a common vocabulary and reference model for how an ML-based AI system is put together.
- It describes components such as data acquisition and preparation, model training, the trained model, evaluation, and deployment and operation.

It is not a certification of model quality, it does not tell you which provider to use, and it is not a governance policy. Requirements for an organizational AI management system are in ISO/IEC 42001, and each organization still writes its own AI policy.

D=Certifies models are bias-free: no ISO standard certifies that a model has no bias, and 23053 is not a certification scheme for individual models.

G: ## Why unstructured data costs more to make AI-ready
Structured records already have named fields, so a model or a SQL query can use them almost directly. Unstructured content such as PDFs, emails and scans has the knowledge buried in free text or images, so it must be processed first.
## Typical preparation steps
- **Extraction**: turn scans and PDFs into text and fields, for example with Amazon Textract (OCR plus forms and tables).
- **Cleaning and enrichment**: remove boilerplate, detect language, redact PII, add metadata such as document type and date.
- **Chunking and indexing**: split text into passages, create vector embeddings and store them in an index (for example Amazon OpenSearch Service or Amazon Bedrock Knowledge Bases) so a GenAI assistant can retrieve them.
- **Governance**: track ownership, access rights and freshness, because documents change and permissions differ by team.
## The tradeoff
Unstructured data often holds the highest-value knowledge, and modern GenAI can use it, but leaders should budget time and money for this pipeline before expecting good answers.
W: Extra processing such as extraction and indexing: unstructured content is usable by AI, but it usually needs text extraction, cleaning, chunking and indexing first, which is the planning tradeoff.
X: A=Structured data needs more preprocessing: the opposite is normally true; tables with defined fields need far less work than scanned documents and free text.
B=Unstructured data cannot be used by AI: document understanding, speech recognition and GenAI with retrieval all work on unstructured data after proper preparation.
C=AI structures it automatically at no cost: models can extract information at inference time, but extraction, indexing, access control and quality checks still need investment and ongoing maintenance.
T: Unstructured data is valuable and usable, but it needs an extraction and indexing pipeline, so plan for that effort instead of assuming it is free or impossible.

G: ## Scripted bot versus AI agent
- A **scripted bot** matches keywords or intents to pre-written answers. It is cheap, predictable and easy to audit, but it cannot reason across steps or take actions.
- An **AI agent** uses a foundation model to plan steps and call tools or APIs. In one conversation it can look up an order in the order system, decide a refund is due, call the billing API, and hand off to a human with a summary.

- Guardrails and policies: which actions are allowed, refund limits, when human approval is required.
- Security: least-privilege access for each tool the agent calls, and logging of every action.
- Quality: monitoring for wrong actions or hallucinated answers, and clear escalation paths.

The organization still owns the policies and controls.
W: More capability, more governance: the agent can complete multi-step tasks that include real transactions, so it needs guardrails, access control, human escalation rules and monitoring that a static FAQ bot does not.
X: A=Functionally identical: a keyword bot can only return canned text, while the agent can look up data and execute refunds, so the capabilities are very different.
C=Always cheaper with no oversight: agents add model usage, integration and monitoring costs, and actions like refunds require ongoing oversight rather than none.
D=Scripted bot can already issue refunds: keyword matching returns pre-written responses; calling a billing system would need new integration and decision logic the bot does not have.
T: Moving from a scripted bot to an agent buys multi-step automation and action-taking, paid for with stronger governance and oversight.

G: ## Explainability in regulated decisions
When a lender declines a credit application, rules in many jurisdictions require it to tell the applicant and regulators the principal reasons, such as high debt-to-income ratio or short credit history. That means the lender must know which inputs drove each decision.

G: ## Models degrade after launch
A model is trained on a snapshot of the world. After deployment, the world keeps changing:
- **Data drift**: the input data shifts, for example new stores, new suppliers or a change in customer mix.
- **Concept drift**: the relationship between inputs and outcomes changes, for example a promotion strategy or economic shift changes how demand responds to price.
- **Data pipeline issues**: an upstream system changes a field format or stops sending a feed.
None of these trigger an error message. The model keeps producing forecasts that look normal while getting steadily worse.
## What monitoring and human review provide
- Tracking forecast error against actual sales and alerting when it crosses a threshold.
- Checking input distributions against the training baseline (for example with Amazon SageMaker Model Monitor).
- Human reviewers who notice when forecasts no longer match business reality and can trigger retraining.
Six good months prove the model worked under those six months of conditions, not that it will keep working.
W: Drift goes unnoticed: without monitoring and review, a gradual decline caused by changing data or business conditions would only be discovered after it causes stockouts or overstock.
X: A=Dashboards only matter during training: monitoring is most important after deployment, when real-world data can diverge from the training data.
C=Removing monitoring improves accuracy: monitoring observes predictions; it does not change them, so removing it cannot make the model more accurate.
D=Validated performance is guaranteed forever: validation shows performance on data available at the time; drift means performance can and usually does change later.
T: A successful pilot is not permanent proof; keep monitoring and human review so drift is caught before it hurts the business.

G: ## What prompt engineering is
A foundation model's answer depends heavily on the text it receives. Prompt engineering is designing that input so the model understands the task, without changing the model itself.
Common elements of a strong prompt:
- **Role**: "You are an HR policy assistant for a European company."
- **Context**: the relevant policy excerpt or background the model needs.
- **Task and constraints**: "Answer in under 100 words and cite the policy section."
- **Output format**: "Return a short answer followed by a bullet list of next steps."
- **Examples**: one or two sample questions with ideal answers.
## Why the business likes it
Prompt changes are fast, cheap and reversible. There is no training data to prepare, no compute for training, and no new model to host, so teams can iterate in hours and roll out improvements through shared prompt templates.
W: Prompt engineering without retraining: adding role, context, format and examples to the input improves answers immediately while the underlying model stays unchanged, so there is no training cost or delay.
X: A=Data labeling: labeling tags data for supervised training; the pilot changed the text sent to the model, not any dataset.
B=Fine-tuning per user: fine-tuning changes model weights through a training job on a dataset; it is not done per request, and the pilot did not retrain anything.
D=Pre-training from scratch: pre-training builds a foundation model on massive data at very high cost; the pilot used an existing model and only improved its inputs.
T: Better instructions, context, format and examples in the prompt improve results quickly and cheaply because the model is not retrained.

G: ## Zero-shot, one-shot and few-shot prompting
These names describe how many worked examples you put into the prompt.
- **Zero-shot**: only an instruction. "Write a tagline for our new running shoe in a playful tone."
- **One-shot**: the instruction plus one example of the desired output.
- **Few-shot**: the instruction plus several examples (typically 2 to 5), so the model can infer the pattern: length, tone, punctuation, structure.
## Example
A few-shot prompt might list three past taglines such as "Coffee that keeps up with you." and "Your desk, finally organized.", then say "Now write three taglines for our new backpack in the same style."
The model copies the rhythm and format of the examples far more reliably than it follows a description like "punchy and friendly". This happens only in the prompt: the model's weights do not change, and the examples must be sent with every request.
W: Few-shot prompting: supplying several example taglines inside the prompt shows the model the exact tone and format to imitate, without any training.
X: A=Fine-tuning: fine-tuning trains the model on a labeled dataset and changes its weights; the team only placed examples in the prompt.
C=Retrieval-augmented generation: RAG retrieves relevant documents from a knowledge source at query time to ground facts; the team hand-wrote style examples, not retrieved knowledge.
D=Zero-shot prompting: zero-shot means giving only instructions with no examples, which is what the team moved away from.
T: Examples inside the prompt = few-shot; instructions only = zero-shot; changing weights = fine-tuning; retrieving documents = RAG.

@ Q000151 explain
G: ## Tokens and the context window
Foundation models read and write text as **tokens**, pieces of words. In English one token is roughly three quarters of a word. Each model has a **context window**, the maximum number of tokens it can process in one request, counting the prompt and the response together.
A 300-page contract can easily exceed the window of many models, so the request is rejected.
## Chunking pattern (map-reduce summarization)
1. Split the document into chunks that fit comfortably in the window, for example by section or every 10 pages, with a small overlap so sentences are not cut in half.
2. Summarize each chunk separately ("map"), asking for key obligations, dates and risks.
3. Combine the chunk summaries and summarize them again ("reduce") into the final summary.
This also lets chunks be processed in parallel. An alternative is choosing a model with a larger context window, but cost and quality over very long inputs still need checking.
W: Chunk, summarize, combine: splitting the contract into pieces that fit the context window, summarizing each and then merging the summaries respects the token limit while still covering the whole document.
X: A=More few-shot examples: examples add tokens to the prompt, making an oversized request even larger and the error worse.
B=Ignore the error: the context window applies to every request type, including summarization; the model cannot process input it has rejected.
C=Switch to rule-based automation: fixed rules cannot produce meaningful summaries of legal text; the limit is solved by changing how input is fed to the model.
T: When input exceeds the context window, split it into chunks, process each, and combine the results; adding more text only makes it worse.

G: ## Three ways to adapt a foundation model
- **Prompt engineering** changes the instructions and examples in each request. It is fast but must be repeated every time and is limited by the context window.
- **Retrieval-augmented generation (RAG)** fetches relevant documents at query time and puts them into the prompt. It is best for giving the model current or proprietary facts.
- **Fine-tuning** continues training the model on your own labeled examples, updating its weights. What it learns becomes part of the model's default behavior.
## Style versus knowledge
Writing style, tone and domain vocabulary are patterns that appear in every answer, whatever the topic. Training on thousands of the firm's past documents (for example prompt-completion pairs in its formal style) teaches the model to write that way by default, without resending style examples each time. Amazon Bedrock supports fine-tuning for selected models and hosts the resulting custom model.
Facts that change frequently are still better served by RAG, and many solutions combine the two.
W: Fine-tuning: training on thousands of the firm's documents builds the formal style and terminology into the model's weights, so it appears consistently across any topic without long prompts.
X: A=Retrieval-augmented generation: RAG supplies relevant facts per request; it does not reliably change the model's writing style, especially when the retrieved topic changes.
B=Single instruction sentence: one sentence rarely captures a complex house style, and the claim that style cannot be taught through examples is false, since examples and fine-tuning both teach style.
D=Larger context window: a bigger window only allows more input tokens; it does not change how the model writes.
T: Durable style and vocabulary → fine-tuning; fresh or proprietary facts → RAG; quick behavior tweaks → prompt engineering.

G: ## What a hallucination is
A foundation model predicts plausible next tokens. When it lacks information or the request is unclear, it can produce fluent text that is wrong or invented, such as a fake statistic or a citation that does not exist. This is called a hallucination.
## Prompt practices that reduce it
- **Clear, single task**: say exactly what is wanted.
- **Relevant context**: include the facts or source passages the answer should be based on (this is also what RAG automates).
- **Explicit constraints**: "Answer only from the context below. If the answer is not in the context, reply 'I don't know'."
- **Format and scope limits**: ask for a short answer with a quote of the supporting sentence.
## Example
Weak: "Tell me about our refund policy."
Better: "Using only the policy text below, state the refund window in days and quote the sentence that supports it. If it is not stated, say so."
Prompting lowers the risk but does not remove it; high-stakes uses still need grounding checks and human review.
W: Clear instructions, context and constraints: telling the model exactly what to do, giving it the facts to use and allowing it to say it does not know leaves less room to invent answers.
X: A=Many unrelated questions in one prompt: mixing tasks splits the model's attention and makes it easier to miss or blur details, increasing errors.
B=Longest possible response: forcing length pushes the model to add content beyond what it knows, which is where fabricated details tend to appear.
D=Vague, open-ended prompt: without context or constraints the model fills gaps with plausible guesses, which is the main cause of hallucinations.
T: Specific instructions, grounding context and permission to say "I don't know" reduce hallucinations; vague, overloaded or padded prompts increase them.

G: ## Build, buy or partner
Sourcing AI capability is a tradeoff between speed, control, cost and required skills.
- **Build**: full control and differentiation, but needs data scientists, time and ongoing maintenance.
- **Buy**: a ready-made solution, for example from AWS Marketplace, where vendors offer SaaS products, ML model packages and algorithms. Fastest, and needs little in-house ML skill.
- **Partner**: a consultancy or ISV builds or runs it with you.
## Managing lock-in when you buy
Buying is not the same as being locked in. Before signing, check:
- Contract length and exit terms, including renewal and termination notice.
- Whether your data, labels and outputs can be exported in standard formats.
- APIs and integration points, so another product could replace it later.
- Pricing model (usage-based versus long commitments) and any exclusivity clauses.
AWS Marketplace purchases are billed through the AWS account, and many listings offer flexible or private-offer terms that can be negotiated.

G: ## From vendor proof of concept to production
A proof of concept (PoC) shows an idea works on a limited scope. Production needs reliability, security, scale and a clear operating model, and when a third-party vendor built the PoC, ownership questions come up too.
## Key transition areas
- **Data portability**: training data, labels, model artifacts and outputs must be in formats you can move and use on AWS.
- **Integration**: connect to production systems (identity, data pipelines, applications) with proper security and monitoring.
- **Retraining**: decide who retrains the model, on what data and how often, and whether the vendor's approach can be reproduced.
- **Phased cutover**: run the new system in parallel or with a subset of users first, compare results, and keep a rollback path before fully switching.
- **Knowledge transfer**: documentation and handover from the vendor so the team can operate the system.
## Example
A company might run the production system in shadow mode for a month, comparing its outputs with the PoC, then move 10 percent of traffic, then all traffic.

B=Rebuild from scratch ignoring the PoC: discarding the lessons learned wastes the pilot's investment and reintroduces risks the PoC already solved.
C=End the vendor contract on launch day: cutting support at the riskiest moment removes help for issues and knowledge transfer; an overlap period is safer.
E=Adopt the vendor's proprietary format permanently: this creates lasting lock-in and makes future migration or retraining harder, the opposite of portability.
T: Move a vendor PoC to production with portable data, planned integration and retraining, and a phased cutover with overlap, not abrupt or dependency-creating shortcuts.

G: ## Matching pricing models to usage patterns
AI workloads can be paid for in different ways, and the best choice depends on how predictable the usage is.
- **On-demand (pay per use)**: no commitment, pay per request, token or second of compute. Best when volume is unpredictable or spiky, because you do not pay for idle capacity.
- **Commitments**: Savings Plans (for example, Savings Plans that cover SageMaker AI usage) or reserved capacity such as Amazon Bedrock Provisioned Throughput give lower rates or guaranteed capacity in exchange for committing to usage over a term. Best when volume is steady and forecastable.
- **Batch options**: scheduled jobs can often use cheaper batch modes; for example, Amazon Bedrock batch inference is priced lower than on-demand inference for supported models (approximately 50 percent lower), and SageMaker batch transform runs only while the job executes.
## Applying it
Initiative X has unpredictable real-time demand, so committing to fixed capacity risks paying for unused capacity or being short at peaks. Initiative Y runs on a known schedule, so its usage can be forecast and committed to at a discount.
W: On-demand for X, commitments for Y: unpredictable real-time traffic fits pay-per-use pricing, while predictable scheduled batch work can safely use commitments or batch discounts.
X: B=Ignore cost in selection: when business impact is similar, running cost is a key differentiator and belongs in the decision alongside feasibility.
C=Identical cost profiles: the same service can cost very differently depending on real-time versus batch usage, volume and pricing model.
D=Batch is never cost-effective: batch processing is often the cheapest way to run AI because it avoids always-on capacity and can use discounted batch pricing.
T: Unpredictable demand → on-demand pricing; predictable, scheduled demand → commitments or batch discounts.

G: ## The value-versus-effort matrix
A two-by-two matrix is a common way to prioritize AI initiatives.
- **High value, low effort: quick wins.** Do these first to show results.
- **High value, high effort: strategic or long-term bets.** Worth pursuing, but they need planning, funding and groundwork first.
- **Low value, low effort: fill-ins.** Do them when there is spare capacity.
- **Low value, high effort: avoid or deprioritize.**
## Why data quality moves an item to high effort
Poor data quality means the initiative cannot succeed until data is cleaned, integrated and governed, which may require new pipelines, data ownership and validation. That work is effort, but it also benefits other future AI projects.
## Example
A company might approve the data foundation work this year, run a limited pilot once the data meets quality thresholds, then scale. The initiative is kept on the roadmap, not dropped and not rushed.
W: Long-term bet with foundational investment: high value makes it worth pursuing, but high complexity and poor data mean it needs data and platform groundwork before implementation.
X: A=Same priority as low-value, low-effort: that quadrant holds minor fill-ins; this initiative's high value puts it in a different category despite its effort.
C=Permanently removed: high-value initiatives are not discarded just because they are hard; they are sequenced after the prerequisites are in place.
D=Quick win implemented immediately: quick wins are low effort; very high complexity and poor data quality mean immediate implementation would likely fail.
T: High value plus high effort = strategic long-term bet: invest in foundations such as data quality first, rather than rushing it or dropping it.

G: ## Pilot success does not equal production readiness
A sandbox pilot proves the chatbot can answer typical questions for a small group. Production adds conditions the pilot never faced.
- **Scalability**: many concurrent users, peak traffic, service quotas and response times.
- **Cost**: usage-based costs such as model tokens grow with volume, so the pilot's spend does not predict production spend.
- **Monitoring**: answer quality, escalation rate, customer satisfaction, latency and errors need dashboards and alerts.
- **Governance**: guardrails for harmful or off-topic content, PII handling, audit logs, clear ownership and a process for updates.
- **Data variety**: real customers ask more varied and unexpected questions than a pilot set, so accuracy must be re-validated.
## Example
A pilot handling 200 chats per week may cost little; 50,000 chats per week multiplies token spend and exposes rare question types. Services such as Amazon Bedrock Guardrails and Amazon CloudWatch help, but the plan must be revisited before scaling.
W: Reassess scalability, cost, monitoring and governance: full production changes volume, cost, risk and user variety, so each must be re-planned rather than assumed from the sandbox.
X: A=Pilot accuracy will hold automatically: production traffic is larger and more varied than the pilot sample, so accuracy must be re-validated at scale.
B=Skip stakeholder communication: a production rollout affects customers, support staff and compliance teams, so communication becomes more important, not less.
D=Reuse the pilot budget unchanged: usage-based costs grow with volume, and production also adds monitoring, support and governance costs.
T: Scaling a pilot means re-planning capacity, cost, monitoring and governance for production conditions, not assuming sandbox results carry over.
