G: ## Models learn from the examples they have seen
A machine learning model finds patterns in its training data and applies them to new inputs. A demand-forecasting model learns things like seasonality, promotions and trends for each product from past sales.
- When a new input looks like the training data, predictions are usually reasonable.
- When it does not, the model is **extrapolating**: it has to guess with patterns learned from other things, and accuracy drops sharply.
## The "cold start" problem
A product line launched last month has only a few weeks of sales and none of the seasonal history the model relies on. This is often called a cold-start problem, and it appears in forecasting and in recommendations alike.
Common remedies include using data from similar products as a proxy, adding product attributes as features, blending the forecast with expert judgment for new items, and retraining as history builds up.

D=Train on fewer years: cutting history would remove seasonal patterns for existing products and still leave zero examples of the new line, so it would not fix this miss.
T: A model is only as reliable as the examples behind it; for a brand-new product with no history, weak predictions are expected, not a malfunction.

G: ## Precision and recall in plain terms
When a model flags items (fraud, spam, defects), two questions matter:
- **Recall**: of all the real fraud, how much did the model catch? Model X catches 95% of fraud, so its recall is high.
- **Precision**: of everything the model flagged, how much was really fraud? Model X also flags many legitimate transactions, so its precision is low.
## They trade off against each other
Most models output a score, and a threshold decides what gets flagged. A low threshold catches more fraud (higher recall) but blocks more good customers (lower precision). A high threshold does the reverse.
- Example: out of 1,000 flags, if 900 are legitimate customers, precision is only 10% even if recall is excellent.
The right balance is a business decision. If the board's priority is fewer wrongly blocked cards, precision matters most; if fraud losses were the priority, recall would.
W: X favors recall, Y favors precision: Model X catches more fraud but blocks many good customers, while Model Y's few false alarms mean fewer blocked cards, which matches the board's stated top concern, at the cost of missing more fraud.
X: B=Terms reversed: catching more of the actual fraud is recall, not precision, and having fewer false alarms is precision, so this framing swaps the two definitions.
C=Y is overfitting: overfitting means strong results on training data but weak results on new data; flagging fewer transactions reflects a different threshold or trade-off, not overfitting.
D=Same accuracy, decide on cost: nothing in the scenario says the accuracies match, and overall accuracy hides the very trade-off the board cares about, since fraud is rare and a model can look accurate while blocking many good customers.
T: Recall is how much of the real problem you catch; precision is how often a flag is right. Match the metric to the business harm you most want to avoid.

G: ## Training versus inference
An ML model has two main stages:
- **Training** builds the model by learning from data. It is compute-heavy and happens up front or periodically. With a foundation model on Amazon Bedrock, the provider has already done this.
- **Inference** is the trained model answering real requests: every chatbot question, summary or classification is one inference call.

Inference cost is paid every time the model is used, so it grows with traffic.
- On Amazon Bedrock on-demand pricing, text models are billed per input and output token. More users, longer prompts and longer answers all raise the bill.
- Example: 10,000 conversations a day, each averaging 2,000 tokens, is 20 million tokens a day, and doubling users roughly doubles that.
Options such as provisioned throughput, batch inference, prompt caching or smaller models change the shape of the cost, but it remains an ongoing operating expense.
W: Model answering real requests: inference is the production stage where the model serves users, so its cost scales with the number and size of requests and must be budgeted as a recurring expense.
X: B=Evaluation step: evaluation measures model quality against test data and runs when models or prompts change; it does not serve live users and is not what "at inference" means.
C=One-time training run: that describes training, not inference; and even training is rarely a single fixed event, while inference cost continues for as long as people use the chatbot.
D=Data labeling phase: labeling prepares examples for training before a model is built; it has nothing to do with the model producing answers after launch.
T: Training builds the model once or periodically; inference runs on every request, so its cost rises with usage.

G: ## Hallucination
A foundation model generates text by predicting likely next words. It does not look facts up by default, so it can produce fluent, confident content that is simply false. This is called **hallucination**.
- A made-up "Section 7.4 remote work stipend" is a classic example: plausible wording, no source.
- Risk grows when employees trust the tool and stop checking.
## Grounding with retrieval
Retrieval-augmented generation (RAG) fetches relevant passages from the real handbook for each question and tells the model to answer from them.
- Amazon Bedrock Knowledge Bases can store the handbook, retrieve passages and return citations.
- Amazon Bedrock Guardrails offers contextual grounding checks that can block answers not supported by the retrieved text.
- Instructing the model to say "I don't know" when the handbook lacks an answer also helps.
These reduce hallucination; they do not remove it completely, so users should still be able to check sources.
W: Plausible but false content, reduce with grounding: the model invented a section that sounds real, and grounding answers in retrieved handbook text (with citations) sharply reduces this risk.
X: A=Add Section 7.4 to the handbook: the handbook is correct and the model made the section up; rewriting policy to match an AI mistake is backwards.

D=Model was hacked: nothing suggests a breach; fabricated content is normal model behavior, and rotating passwords would not stop the model from inventing answers.
T: Confident but invented answers are hallucinations; ground the model in retrieved source documents rather than expecting size or policy changes to fix it.

- **Fine-tuning** continues training a model on your examples, changing its weights. The knowledge is baked in as of the training date, and updating it means training again.

G: ## Inference parameters
When a model generates text, it picks each next token from a probability distribution. Inference parameters shape that choice without retraining the model.
- **Temperature** controls randomness. Low values (near 0) make the model choose the most likely words, giving consistent, predictable output. Higher values let less likely words through, giving more varied, creative output.
- **Top P** and **Top K** also limit how many candidate words are considered.
- **Maximum tokens** caps the length of the response.
## One setting, two needs
- Legal drafting wants the same clause wording each time: use a low temperature.
- Ad copy benefits from fresh variations: use a higher temperature.
Both observations are explained by where temperature is set for each team's use.
W: Temperature: it controls how random the generated output is, so a setting that is too high explains inconsistent legal wording, and raising it is exactly how marketing gets more variety.
X: B=Maximum tokens for factuality: maximum tokens only limits how long a response can be; it does not make answers more factual or better sourced, nor does it change wording variety.
C=Embedding size for speed: embeddings are numeric vectors used for search and similarity; their dimension does not control how varied generated text is or how fast replies arrive.
D=Context window for concurrent users: the context window is how many tokens the model can consider in one request; concurrency and throughput are governed by service quotas and capacity, not the context window.
T: Temperature trades consistency for variety: set it low for precise, repeatable text and higher for creative output.

G: ## Overfitting and generalization
The goal of training is a model that **generalizes**: it performs well on new data it has never seen, not just on the examples it learned from.
- **Overfitting**: the model fits the training data too closely, including noise and quirks, so it scores very high on training data but much lower on new data.
- **Underfitting**: the model is too simple to capture the patterns, so it scores poorly on training data and new data alike.
## Reading the numbers
99% on training data and 64% on new customer data is a large gap, the classic overfitting signature. It is like a student who memorized last year's exam answers and fails a new exam.
Typical fixes include evaluating on a held-out test set during development, using more varied training data, simplifying the model and applying regularization or early stopping.
W: Overfitting: the model memorized specifics of its training data instead of learning general patterns, which is exactly why it scores 99% on what it has seen and only 64% on new customers.
X: A=99% proves correctness: a high training score says nothing about performance on unseen data; blaming the new data's labels ignores the obvious train-versus-new gap.
C=Underfitting: an underfit model does poorly even on training data, so a 99% training score rules it out.
D=New data always worse: new data is not inherently lower quality, and a well-generalized model scores similarly on training and new data; a drop this large points to the model, not to the data.
T: A big gap between training and new-data performance means overfitting; only results on unseen data show whether a model generalizes.

G: ## Activity metrics versus outcome metrics
- **Activity (output) metrics** count what was done: articles generated, prompts written, users logged in. They show the tool is being used.
- **Outcome metrics** measure what changed for the business: qualified leads, conversions, revenue, cost per acquisition. They show whether the use created value.
A CFO cares about outcomes because they connect to money.
## Making the outcome credible
Compare against a baseline, such as leads per month from content before the tool, and attribute results to the AI-assisted content where possible, for example with tracked links or campaign tags.
- Example: "Leads from blog content rose from 300 to 420 per month after we introduced the tool" is a value statement; "we wrote 4,000 articles" is not.
W: Change in qualified leads or conversions versus baseline: it connects the generated content to a business result the CFO can value, and the baseline shows how much actually changed.
X: A=Employees who logged in: logins measure adoption, which is useful for rollout tracking but says nothing about whether the content created value.
B=Prompts written each week: prompt counts measure effort and usage, not results; more prompts could even mean the tool is harder to use.
C=Average word count versus hand-written articles: longer articles are not better or more profitable ones; word count says nothing about impact on leads or sales.
T: Report outcome metrics against a baseline, not activity counts, to show an AI tool's business value.

G: ## Separating the tool's effect from everything else
Win rates can rise for many reasons at once: seasonality, a new product, market conditions, pricing changes. To credit the AI assistant, the evaluation must hold those other factors constant.
- A **control group** is a comparable set of reps who do not use the assistant during the same period.
- Both groups experience the same season, market and products, so the difference between them is attributable to the assistant.
## Making it fair
Assign reps randomly, or match groups on territory, experience and past win rate. Measure the same outcome (win rate) the same way for both groups.
- Example: users win 31% of deals, the control group wins 28% in the same quarter, so about 3 points come from the assistant and the rest of the 9% rise is from other factors.
W: Concurrent comparison group: reps with and without the assistant over the same period face the same seasonal upturn, so the difference between them isolates the assistant's effect.
X: A=Count proposals and assume wins: drafted proposals are activity, and assuming each produced a win is an unsupported assumption that ignores the seasonal upturn entirely.
C=Ask reps if it helped: self-reported opinions are subjective and biased, especially from users of a new tool, and do not measure actual win rates.
D=Compare with five years ago: many things changed in five years (market, products, team, pricing), so the difference cannot be attributed to the assistant.
T: To prove causation, compare users with a similar non-user group over the same period so shared factors like seasonality cancel out.

G: ## Avoiding lock-in when models change fast
New foundation models appear often, and today's best choice may not be best next year. Flexibility comes from design, not from avoiding models.
- **Common API across models**: Amazon Bedrock provides models from several providers through one set of APIs, such as the `Converse` API. Switching models can be mostly a configuration change instead of a rewrite.
- **Portable prompts**: keep prompts in version control and avoid relying on one model's quirks.
- **Portable evaluations**: keep a test set of real questions with expected answers, and run any candidate model against it. Amazon Bedrock model evaluation can help compare models.
## Example
A team builds a summarizer on one model. When a cheaper, better model is released, it runs the same evaluation set, sees equal quality at lower cost and switches with a configuration change.
W: Multi-model platform plus portable prompts and evaluations: applications stay decoupled from any single provider, so the company can adopt better models quickly while continuing to deliver now.
X: B=Five-year exclusive contract: exclusivity deepens lock-in exactly when models are improving fastest, trading flexibility for a discount.
C=A different provider per application: scattering workloads adds integration, security and operations overhead and still ties each application to one provider, so it does not make switching easier.
D=Avoid foundation models entirely: waiting for consolidation gives up value and learning now, and may never end, so it fails the "without slowing delivery" requirement.
T: Preserve flexibility by building on a common multi-model API with portable prompts and evaluations, not by exclusive deals or waiting.
