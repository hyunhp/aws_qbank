G: ## Why agents need guardrails around actions
An AI agent does more than answer questions: it calls tools and APIs that change real records, such as rebooking a seat or issuing a voucher worth real money. A wrong answer in a chat is embarrassing; a wrong action costs money and is hard to undo.
Two classic controls reduce that risk:
- **Least privilege**: the agent gets only the tools and actions its job needs. A rebooking agent might call `searchFlights`, `rebookPassenger` and `issueVoucher`, but not refunds, crew scheduling or loyalty-point transfers.
- **Limits plus human-in-the-loop**: hard caps on risky values, with escalation to a person above a threshold. Example: vouchers up to 200 dollars are issued automatically; anything larger waits for an agent supervisor to approve.
Logging every action gives an audit trail, so mistakes can be found, traced and reversed.
W: C=Least privilege with full logging: restricting the agent to the specific systems and actions it needs shrinks what can go wrong, and an action log makes every change reviewable and reversible.
E=Voucher limits with approval threshold: a hard cap bounds the cost of any single error, and human approval for larger amounts puts judgment where the financial risk is highest.
X: A=Disable logging: without logs nobody can detect or undo a costly mistake; privacy is protected by access controls and data redaction, not by removing the audit trail.
B=Access to every system: broad permissions widen the blast radius, so one bad decision could touch payments, schedules or records unrelated to rebooking.
D=Agent picks voucher amounts from mood: letting the model set payouts from perceived emotion is unpredictable, easy to manipulate by angry-sounding customers and inconsistent between passengers.
T: Limit what an agent can touch, cap what it can spend and log what it does; broad access with no limits or logs turns a small error into a costly one.

G: ## Garbage in, garbage out
A forecasting model learns from historical data. If each plant records inventory differently, the same number means different things, and the model learns noise.
Example: Plant A counts pallets, Plant B counts individual units, and Plant C records stock only at month end. A value of `500` could be 500 pallets, 500 units or a figure that is weeks old.
The fix is a data foundation, not a smarter model:
- **Common data definitions**: one agreed meaning for "on-hand inventory", the unit of measure and the recording time.
- **A shared, governed data platform**: every plant feeds the same pipelines, with validation checks, ownership and a catalog, so the model gets consistent inputs.
Once inputs are consistent, even a simple model often forecasts better than a sophisticated one fed inconsistent data.
W: B=Common definitions on a shared governed platform: standardizing what each field means and how every plant submits it removes the root cause, so forecasts are built on comparable data.
X: A=More powerful model to guess meanings: a bigger model cannot reliably infer whether a number is pallets or units; guessing adds hidden errors instead of fixing the source data.
C=More dashboards: showing unreliable forecasts in more places spreads the problem without improving the inputs.
D=New AI vendor: the weakness is inconsistent data, which any vendor's algorithm would inherit.
T: When forecasts are unreliable because inputs are inconsistent, invest in data standards and a governed platform before changing the model or the vendor.

G: ## Scaling a pilot safely
A successful pilot proves the idea works in one setting. Other departments have different data, workflows, risks and users, so success does not automatically transfer.
A **phased rollout** reduces risk:
- Pick a few additional departments with different characteristics.
- Define success metrics up front, for example time saved per task, error rate and user satisfaction.
- Measure, fix issues (prompts, data access, training, guardrails) and then expand again.
Example: after a pilot in marketing, the company adds finance and HR next quarter. HR reveals a need for stricter handling of personal data, which is fixed before the tool reaches all 20 departments.
Each wave is small enough that problems are contained, and the one-year deadline is still reachable.
W: B=Phased expansion with measurement: growing in stages lets the team measure value and catch department-specific problems while the impact is small, then refine before a broad rollout.
X: A=Everyone on the same day: a big-bang launch exposes the whole company to any unknown issue at once and overwhelms support and training capacity.
C=Keep it in the pilot department forever: avoiding expansion wastes proven value and fails leadership's goal; risk is managed by staged rollout, not by stopping.
D=Rebuild for each department: rebuilding from scratch multiplies cost and time and throws away what the pilot proved; most needs are met by configuration and adjustments.
T: Scale a successful pilot in measured phases, not all at once, not never and not by rebuilding everything.

G: ## From proof of concept to production
A proof of concept answers "can this work?" Production asks "will it keep working, every day, when things go wrong?" The gap is operational practice, often called MLOps or LLMOps:
- **Monitoring**: track latency, errors, usage and quality, and alert when they drift.
- **Versioning**: know which model, prompt and data version is running.
- **Rollback**: return quickly to the last good version after a bad change.
- **Continuity plan**: define what users do during an outage, such as a manual fallback process.
Example: a model's accuracy slowly drops because customer behavior changes. With monitoring, the team sees the drift in days; without it, users discover the failure weeks later.
On AWS, services such as Amazon CloudWatch provide metrics, logs and alarms that support this monitoring.

X: B=More expensive model: the failure was operational; a pricier model still fails silently without monitoring or an outage plan.
C=Formal launch event: executive visibility at launch does not keep a system running or detect problems afterward.
D=Larger test dataset: passing tests never guarantees production success because real data and conditions change; more test data does not replace monitoring.
T: A proof of concept becomes a production system only with monitoring, versioning, rollback and continuity planning, not with a bigger model or more tests.

G: ## Elastic capacity for spiky AI demand
On-premises capacity is fixed: you buy servers for a planned peak, and they sit idle when demand is low. AI inference demand is often spiky, for example a retail assistant that gets ten times normal traffic during a holiday sale.
Cloud services change the economics:
- **Elasticity**: capacity scales out during spikes and back in afterward, for example through auto scaling on inference endpoints or serverless model access.
- **Pay per use**: you pay for what you consume, so idle capacity is not a sunk cost.
- **Managed options**: services such as Amazon Bedrock provide foundation model inference without managing GPUs, and Amazon SageMaker AI endpoints can scale with traffic.
A hybrid approach is common: keep steady or data-sensitive workloads on premises and move suitable, bursty inference to the cloud.

G: ## Features, labels and algorithms
In supervised machine learning a dataset has:
- **Features**: input variables the model uses to make a prediction, such as last season's purchases, age band, region or recent website visits.

Rule-based fraud systems and classifiers trained on labeled fraud cases are good at catching patterns seen before. Fraudsters adapt, so new tactics can slip through.
**Anomaly detection** takes a different approach: it learns what normal behavior looks like and flags what deviates from it, without needing labeled examples of the new fraud.

G: ## What a context window is
A large language model reads and writes text as **tokens**, small chunks of text. In English a token averages roughly three-quarters of a word, so 200,000 tokens is on the order of 150,000 words.
The **context window** is the maximum number of tokens the model can consider in a single request: the instructions, any documents, the conversation history and the model's own output all share it.
Business meaning:
- A large window lets the model work with long inputs at once, such as a full contract plus a question about it, or a long support conversation.
- Larger inputs typically cost more per request, because pricing is usually per token, and can increase response time.
- A large window does not mean the model remembers anything between separate requests, and it is unrelated to how many users can be served.
W: D=Amount of text considered at once: the context window is how much input and output the model can handle in one request, such as a long document plus a question.
X: A=200,000 simultaneous users: concurrency depends on service quotas and infrastructure, not on the context window.
B=Fixed monthly cost of 200,000 dollars: the number is a token count, not a price; usage-based pricing charges per token processed.
C=Trained on 200,000 documents: the context window describes a per-request input limit, not the size of the training data.
T: A context window is the amount of text a model can consider in one request, not a user count, price or training-data size.

A foundation model on its own answers from general training data and may confidently invent details, which is a problem for HR policy. Two techniques together keep it on approved content:

G: ## Accuracy on imbalanced data
**Accuracy** is the share of all predictions that are correct. When one outcome dominates, accuracy can look good while the model misses what matters.
Here 95% of deliveries are on time. A "model" that always predicts on time is right 95% of the time and catches zero delays. The 90% model is below that trivial baseline, which is a warning sign.
Better questions for leadership:
- **Recall**: of the deliveries that were actually late, what share did the model flag?
- **Precision**: of the deliveries the model flagged as late, what share really were late?
- A **confusion matrix** shows true and false positives and negatives, so the trade-off is visible.
Example: 1,000 deliveries, 50 late. If the model flags 20 of them correctly, recall is 40%, even if overall accuracy looks high.
W: A=Always-on-time baseline scores 95%: with 95% on-time deliveries, accuracy mostly measures the easy majority, so leaders must look at how many delays are actually caught using recall and precision.

G: ## Starting fast with a foundation model and retrieval
A **foundation model** is a large pre-trained model that already understands and generates language. Instead of training a model, you give it the right information at question time.

G: ## Why specific prompts get better results
A model can only use the context it is given. "Write an email about our sale" leaves it guessing about the audience, offer, tone and length, so it produces a generic average.
Effective prompts usually include:
- **Audience**: for example, loyalty members who bought outdoor gear last year.
- **Specifics**: 30% off tents and backpacks, 3 days only, code `CAMP30`.
- **Tone and format**: friendly and energetic, under 120 words, one call to action.
- **An example** of a past email that performed well, so the model can match style and structure. Adding examples is called few-shot prompting.
Iterating on the prompt and comparing outputs is fast and cheap, so it is usually the first step before considering heavier options such as fine-tuning.
W: C=Audience, offer, tone, length and an example: these details give the model the context it was missing, and the example shows the desired style, which directly improves relevance.
X: A=Repeat the request: repeating a vague prompt adds no information, so the output stays generic.
B=Remove all details: less context makes the output even more generic and less aligned with the actual sale.
D=Capital letters: formatting the output in capitals does not make content more relevant and tends to look like spam.
T: Relevance comes from giving the model specific context and examples, not from repetition, fewer details or formatting tricks.

G: ## Two ways to adapt a foundation model
- **Prompt engineering** changes what you send to the model: instructions, context, examples and output format. The model itself is unchanged. It is fast and cheap to iterate; a new prompt can be tested in minutes.
- **Fine-tuning** changes the model's weights by training it further on your own labeled examples, such as thousands of prompt and ideal-response pairs. It needs curated data, training compute and evaluation, and the result is a custom model version that must be hosted and maintained.
Example: an insurer first improves claim summaries with a better prompt and a few examples. Only if a consistent style or domain behavior still cannot be reached does it fine-tune on 5,000 approved summaries.
Amazon Bedrock supports both: prompts with any model, and fine-tuning for supported models.
W: B=Input change versus weight change: prompt engineering adjusts the input and iterates quickly, while fine-tuning modifies the model's weights and requires training data and a training process.
X: A=Same technique, different names: one leaves the model unchanged and the other creates a new trained model version, so they differ in cost, speed and data needs.
C=Prompting needs thousands of examples, fine-tuning none: this is reversed; prompts can use zero or a few examples, while fine-tuning needs a labeled training dataset.
D=Prompting retrains, fine-tuning rewords: this is also reversed; prompting never changes weights, and fine-tuning is the technique that trains the model.
T: Prompt engineering changes the input and iterates fast; fine-tuning changes the model's weights and needs data and training.
