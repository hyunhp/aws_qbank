@ AIF-C01 D4 T4.2 applied definition
S: A compliance officer says, "We are transparent about this model, but we cannot yet explain it." Which statement best captures the difference between transparency and explainability?
A: Transparency covers openly sharing how the model was built, what data trained it and what it is for, while explainability covers showing why the model produced a particular output.
B: Transparency covers showing which input features drove one specific prediction, while explainability covers publishing the model's training data sources and intended uses.
C: Transparency applies only to open-source models that publish their weights, while explainability applies only to proprietary models that hide their internals from users.
D: Transparency means the model always returns the same answer for the same input, while explainability means the model returns answers within a guaranteed response time.
K: A
G: ## Two related but different ideas
Responsible AI asks builders to be open about an AI system in two ways.
- **Transparency** is openness about the system as a whole: how it was designed, what data it was trained on, what it is meant to do, how well it performs and where it should not be used. It is usually delivered through documentation and disclosure.
- **Explainability** is the ability to describe why a model produced a specific output, or how it behaves in general, in terms a person can follow. It is usually delivered through techniques such as feature attributions.
## Why the officer's sentence makes sense
A team can publish a complete description of its data, purpose and limits (transparent) and still be unable to say why one applicant was declined (not explainable). The two support each other, but one does not guarantee the other.
W: Transparency is openness about how the system was built and what it is for, and explainability is the ability to say why a given output came out. The officer's team has the first (documentation) but not the second (reasons for individual outputs).
X: B=Swapped definitions: this reverses the terms. Feature attribution for a single prediction is a form of explainability, and publishing data sources and intended uses is a form of transparency.
C=Open source versus proprietary: both ideas apply to any model. An open-weight model can still be hard to explain, and a proprietary model can still come with strong documentation and clear explanations.
D=Determinism and latency: consistent answers and response time are reliability and performance properties. Neither describes openness about a model or the ability to give reasons for its outputs.
T: Transparency = openness about how the system was built and what it is for. Explainability = being able to say why a model produced an output.

@ AIF-C01 D4 T4.2 applied use-case

A: SageMaker Model Monitor feature attribution drift monitoring, which uses SageMaker Clarify to compare live feature importance with a baseline.
B: SageMaker Model Monitor data quality monitoring, which checks that incoming request data keeps the baseline statistics and constraints.
C: SageMaker Model Monitor model quality monitoring, which compares predictions with ground truth labels to track accuracy metrics over time.
D: SageMaker Model Cards versioning, which stores each approved version of the model's written documentation for later audits.

A model that was explainable at launch can drift. If customer behaviour changes, the features driving predictions can change too, and a model that once relied on income and credit history may start leaning on something less sensible.
- **Feature attribution drift monitoring** in SageMaker Model Monitor uses SageMaker Clarify to compute feature attributions on live traffic. It compares their ranking with a baseline created at launch and raises an alert when they diverge.

- **Model quality monitoring** watches accuracy-type metrics and needs ground truth labels.

@ AIF-C01 D4 T4.2 applied definition
S: In an Amazon SageMaker Clarify report for one loan applicant, the SHAP value for the feature "credit utilization" is -0.12. What does this value mean?
A: For this applicant, credit utilization pushed the predicted score 0.12 below the baseline prediction, so it counted against the applicant.
B: Credit utilization is missing from 12 percent of the training records, so the model treated the feature as unreliable for every applicant.
C: Across all applicants, credit utilization accounts for 12 percent of the model's overall importance, ranked below the other features.
D: The model's accuracy falls by 0.12 whenever credit utilization is included, so the feature should be removed before deployment.
K: A
G: ## Reading a SHAP value
SageMaker Clarify uses a SHAP (Shapley value) approach. It compares the model's prediction with a **baseline** prediction and divides the difference among the features.
- The **sign** shows direction: positive values push the prediction toward the outcome, negative values push away from it.
- The **size** shows how strong the push was for that record.
- Values for one record are a **local** explanation. Averaging absolute values across many records gives a **global** importance ranking.
## For this applicant
A value of -0.12 means credit utilization lowered this applicant's predicted score by 0.12 compared with the baseline, so it is one of the factors that counted against them.
W: A SHAP value is a per-record contribution measured against the baseline prediction, and its sign gives the direction. A value of -0.12 means this feature lowered this applicant's predicted score by 0.12.
X: B=Missing data: SHAP values do not measure how much data is missing. They measure a feature's contribution to a prediction.
C=Global importance: a global ranking averages absolute SHAP values across many records. A single signed value for one applicant is a local explanation.
D=Accuracy effect: a SHAP value describes a feature's contribution to a prediction, not the effect on model accuracy, and a negative sign does not mean the feature is harmful.
T: A SHAP value is a signed, per-prediction contribution relative to a baseline. Positive pushes toward the outcome, negative pushes away.

@ AIF-C01 D4 T4.2 applied use-case
S: A data scientist wants to show a business owner how the predicted probability of churn changes on average as customer tenure increases across the whole customer base. Which explainability output fits?
A: A partial dependence plot, which shows the average effect of one feature on the model's predictions.
B: A confusion matrix, which counts correct and incorrect predictions for each class on a test set.
C: A learning curve, which plots training and validation error as the amount of training data grows.
D: A data lineage graph, which traces datasets and jobs that produced the trained model artifact.
K: A
G: ## Reading a partial dependence plot (PDP)
A PDP shows how a model's predictions change, on average, as one feature varies across its range. To compute it, the feature is set to each value in turn for all records and the predictions are averaged.
- The x-axis is the feature (here, customer tenure in months).
- The y-axis is the average predicted outcome (probability of churn).
A downward slope tells the business owner that longer tenure lowers predicted churn. SageMaker Clarify can include partial dependence plots in its explainability reports for tabular models.
## Why this is useful
PDPs describe the model's overall behaviour and make it easy to sanity-check against domain knowledge, without showing the internals of the model.
W: A partial dependence plot shows the average predicted outcome as a single feature such as tenure varies, which is exactly the relationship the business owner wants to see.
X: B=Confusion matrix: it summarizes classification errors on a test set, such as false positives and false negatives. It says nothing about how one feature changes the prediction.
C=Learning curve: a learning curve shows how error changes as the training set grows and is used to diagnose over- or underfitting. It does not describe feature effects.
D=Lineage graph: lineage documents where data and artifacts came from. It supports traceability, but it does not show how a feature influences predicted churn.
T: Partial dependence plots show the average effect of one feature on predictions, a global view of how the model behaves.

@ AIF-C01 D4 T4.2 advanced use-case
S: A hospital uses an ML model that raises a sepsis-risk alert. Nurses ignore many alerts because they do not know why the model flagged a patient. Which approach best builds trust while keeping clinicians accountable for treatment decisions?
A: Show the main contributing factors, such as rising heart rate, with each alert and require clinician confirmation before treatment.
B: Hide the alert score from nurses and send treatment orders automatically whenever the model's risk score crosses the alert threshold set by the vendor.

K: A
G: ## Explainability as an operational requirement
In healthcare, a prediction is used by a person who is professionally responsible for the outcome. A score without reasons is hard to trust and hard to challenge, so it often gets ignored (or, worse, obeyed blindly).
## Human-centered design for explanations
- **Know the audience**: nurses need short, clinically meaningful reasons, not model internals.
- **Show contributing factors per alert**: local explanations such as "heart rate trending up, lactate elevated" let a clinician compare the alert with what they see.
- **Keep a human in the loop**: the clinician confirms, overrides or escalates, so accountability stays with a person.
W: Showing the top contributing factors with each alert gives nurses the reasons they are missing, and requiring clinician confirmation keeps a human responsible for the treatment decision, which builds appropriate trust.
X: B=Automatic orders: this removes both the explanation and human oversight, which is unsafe in a clinical setting, and it does nothing to help clinicians understand the alerts.
C=Validation statement: a general claim that the model was validated is transparency about the system, not an explanation of this alert, and asking staff to comply without detail invites blind trust.
D=Nightly retraining: fresher data may improve accuracy, but the nurses' problem is missing reasons. Alerts without reasons will still be ignored.
T: Pair each prediction with plain-language reasons and keep a human decision-maker, especially where errors affect people's health.

@ AIF-C01 D4 T4.2 advanced troubleshooting
S: A team wants to explain a foundation model's text answers the same way it explains a tabular model, by computing feature attributions for each generated sentence. Reviewers say this will not give the clear, stable explanations they expect. What is the main reason?
A: Foundation models can only be used through managed APIs, which makes it impossible to record the prompts that were sent to them.
B: Amazon SageMaker Clarify refuses to run against any model that has been trained on more than one language.
C: Generated text is open-ended and produced token by token from billions of parameters, so there is no small, stable set of input features to credit.
D: Foundation models always return identical answers for the same prompt, so there is no variation in behaviour left for an explanation to describe.
K: C
G: ## Why explaining generative models is harder
For a tabular model, the input is a fixed set of features (income, age, utilization) and the output is a single score, so an attribution can say "feature X added this much."
A foundation model works differently.
- The input is free-form text, and the output is a long sequence generated one token at a time from a learned probability distribution.
- Billions of parameters interact, so there is no short list of features to credit.
- Sampling settings such as temperature make outputs **non-deterministic**: the same prompt can give different answers.
## What teams do instead
They rely on transparency artifacts and grounding: documentation of the model, evaluations, human review, and techniques such as citing the source passages used to build an answer.
W: Foundation model text is generated token by token across billions of parameters and can vary between runs, so there is no small set of input features that explains an output the way there is for a tabular model.
X: A=API access: models on Amazon Bedrock are invoked through APIs, but prompts and responses can be logged when invocation logging is enabled. Recording prompts does not produce an explanation.
B=Multilingual restriction: no such Clarify restriction exists. The difficulty is the nature of generated text, not the number of languages the model was trained on.
D=Identical answers: the opposite is true. Generative outputs vary from run to run, which is one reason feature-style explanations are unstable.
T: For generative FMs, feature attribution is limited: outputs are open-ended and non-deterministic, so use documentation, citations, grounding and human review.

@ AIF-C01 D4 T4.2 applied comparison
S: A bank uses a deep learning fraud model and must be able to justify actions taken against customers. A data scientist proposes adding post hoc explanations, such as SHAP values, on top of the existing model. Which statement about this approach is most accurate?
A: Post hoc explanations turn the model into a fully transparent model, so its internal calculations can be read exactly as if it were a decision tree.
B: Post hoc explanations approximate what drove the model's outputs and help stakeholders, but they do not make the underlying model itself interpretable.
C: Post hoc explanations replace the need to document training data, intended use or limitations, because the reasons for each prediction are already available.
D: Post hoc explanations can only be produced during training and cannot be attached to predictions from a model that is already deployed.
K: B
G: ## Interpretable by design versus explained afterwards
- An **inherently interpretable** model (linear model, small decision tree) is understandable from its own structure.
- A **post hoc** explanation method is applied to a trained black-box model. Techniques such as SHAP estimate how features influenced predictions by probing the model with varied inputs.
## Limits to remember
- The explanation is an estimate of the model's behaviour, not a view of its true internals.
- Explanations can be unstable or misleading when features are strongly correlated.
- Explanations describe individual outputs; they do not replace documentation of data, purpose and limitations.
## Use in practice
Post hoc methods are very useful for justifying decisions, spotting odd behaviour and building trust. When the stakes are high and regulators expect a clear rationale, teams weigh them against choosing a simpler model.
W: Post hoc methods estimate which features influenced predictions, which helps stakeholders, but they are approximations that leave the underlying deep model opaque, unlike an inherently interpretable model.
X: A=Fully transparent: explanations do not expose exact internal calculations. The deep model stays a black box, and the explanation only describes its behaviour from outside.
C=Replaces documentation: explanations cover individual predictions or feature importance. Transparency about data, intended use and limitations is still needed for audits.
D=Training-time only: SHAP-style methods work on trained models and can be run on predictions from a deployed model, for instance through SageMaker Clarify explainability jobs and online explainability on endpoints.
T: Post hoc explanations approximate a black-box model's behaviour. They aid trust and justification but do not make the model inherently interpretable.

@ AIF-C01 D4 T4.2 applied troubleshooting
S: Before launch, a team reviews the global feature importance from Amazon SageMaker Clarify for a loan model. The top feature is a customer ID number that has no real link to repayment. What should the team conclude and do?
A: The model learned a spurious pattern, so the team should remove the feature and check for data leakage before retraining.
B: The model is highly reliable because a feature with such strong influence must be the best predictor available for repayment risk.
C: The explanation report is wrong by definition, so the team should ignore feature importance and rely on validation accuracy alone when deciding whether to launch the model.
D: The model should be deployed as is, because feature importance values are only useful after customers complain.
K: A
G: ## Global explanations as a debugging tool
A global explanation summarizes which features matter most overall, typically by averaging the absolute SHAP values of each feature across many predictions. Reviewing it before launch lets domain experts check that the model relies on sensible signals.
## What a suspicious result means
- An ID number should carry no information about repayment. If it ranks high, the model may have **memorized** training records (overfitting) or found an accidental shortcut in the data, such as IDs assigned in an order correlated with the outcome (**data leakage**).
- Such a model looks accurate on validation data drawn from the same source but fails or behaves unfairly on new customers.
## Fix
Remove the feature, examine how the data was collected and split, retrain and review the attributions again.
W: An identifier should not drive repayment predictions, so a high rank signals a spurious pattern or leakage. Removing the feature and checking the data prevents the model from failing on real customers.
X: B=Strong means good: influence does not equal validity. A feature can dominate precisely because the model latched onto an accidental shortcut.
C=Ignore the report: the explanation just did its job by exposing a problem. Accuracy alone would have hidden that the model relies on a meaningless input.
D=Deploy first: explanations are most valuable before launch, when problems are cheap to fix. Waiting for complaints means real customers absorb the harm.
T: Use global attributions to check that a model relies on meaningful features. A high-ranking meaningless feature points to leakage or overfitting.
