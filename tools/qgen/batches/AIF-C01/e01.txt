@ Q000001 explain
G: ## Features: who designs them?
A feature is a measurable input the model uses to decide. In classic machine learning (for example a decision tree or logistic regression), a person decides the features up front: for product photos that might be `average_color`, `edge_count` or `aspect_ratio`, computed by hand-written code.
## How deep learning is different
Deep learning uses neural networks with many layers. Each layer transforms the output of the previous one, so the network builds features itself:
- early layers learn simple patterns such as edges and color blobs
- middle layers combine them into shapes and textures
- later layers combine those into whole objects such as "shoe" or "lamp"
Because the network must discover all of these patterns from examples, it has millions of parameters to fit and needs far more labeled images (and GPU compute) than a small classic model. The payoff is that nobody has to guess which hand-crafted features matter.
W: Layered networks learn features: the layers learn a hierarchy of features directly from raw pixels during training, which removes manual feature design but requires large amounts of data to fit the many parameters.
X: A=Pretrained on rules, no data: deep learning models are learned from data, not built from rules. Even a pretrained model was trained on huge datasets, and adapting it to product photos still needs labeled examples.
B=Stores and looks up images: that describes memorization or a lookup table, which cannot handle a photo it has never seen. A trained network keeps learned weights, not a copy of every image.
D=Fixed expert rules: if-then rules written by experts are a rule-based (expert) system, the opposite of learning features from data, and they would require exactly the manual design the question says is absent.
T: Deep learning trades manual feature engineering for data and compute: stacked layers learn the features, which is why it needs so many examples, unlike rule systems or lookups.

G: ## Algorithm versus model
- An **algorithm** is the learning procedure: the recipe that looks at training data and adjusts numbers to reduce error. XGBoost (gradient-boosted decision trees), linear regression and k-means are algorithms.
- A **model** is what you get after running an algorithm on a specific dataset: the learned parameters (for XGBoost, the set of trees with their split points and leaf values), usually saved as a file.
## A concrete example
A telecom company runs XGBoost on three years of its own customer records and saves the result as `churn-model.tar.gz`. The algorithm is generic and anyone can use it; the file is specific to that company's data and can be loaded to predict whether a given customer will churn.
So "we use XGBoost" tells you how the vendor learns; "download our churn model" hands you a finished, trained artifact ready for inference.
W: XGBoost is the algorithm, the file is the trained model: algorithm plus training data produces a model, and the downloadable file contains the learned parameters that make predictions.
X: B=Both are datasets: a dataset is the examples used for training. XGBoost is a procedure and the model file holds learned parameters; neither is the raw training data.
C=Reversed roles: XGBoost by itself has learned nothing about churn, so it cannot be the model, and a file of learned parameters is the output of training, not the training procedure.
D=Algorithm and model are synonyms: they are different things at different stages. The same algorithm trained on different data gives different models, which is why the terms cannot be interchanged.
T: The algorithm is the reusable learning recipe; the model is the trained artifact that recipe produces from a specific dataset.

- **Training**: the algorithm studies historical, labeled examples (past transactions marked fraud or not fraud) and adjusts its parameters. This is compute-heavy and happens occasionally.

For fraud detection the model is deployed behind an endpoint. X: A=Labeling: labeling attaches the correct answer (fraud or legitimate) to historical examples so a model can be trained; it happens before training and produces no decisions on live transactions.
B=Training: training is when the model learns its parameters from historical data. The question says the model is finished and deployed, so learning is no longer happening.

G: ## Where model bias comes from
A model learns patterns that are present in its training data. If past human decisions were skewed, for example fewer candidates from one group were hired even when equally qualified, the model treats that skew as a "rule" and repeats it.
- Bias can enter through **historical data** (past unfair decisions), **sampling** (one group under-represented), or **proxy features** (a postcode or school name that correlates with a demographic group).
- It shows up as systematically different outcomes for groups that should be treated the same.
## Detecting and reducing it
Teams compare metrics per group, such as selection rate or error rate. On AWS, SageMaker Clarify can measure bias in the training data and in model predictions. Fixes include rebalancing data, removing proxy features and reviewing results with humans.
W: Bias: the model consistently ranks one demographic group lower than equally qualified candidates, a systematic skew it learned from ten years of historical decisions.
X: A=Underfitting: an underfit model is too simple and performs poorly for everyone, on training and new data alike. It does not explain a consistent penalty against one specific group.
B=Reinforcement learning: this is a training approach in which an agent learns from rewards, not a name for unfair outcomes. The screening model here learned from historical hiring records.
D=Overfitting: overfitting means memorizing training data and failing on new data. The problem here is not a train versus test accuracy gap but skewed results across groups.
T: Systematically worse outcomes for a group point to bias learned from skewed data, not to a generic fit problem such as underfitting or overfitting.

@ Q000005 explain
G: ## Why we keep a held-out test set
Data is split before training: the model learns from the **training set**, and a separate **test set** that it never sees measures how well it will do on new data. The goal is **generalization**, performing well on data the model has not seen.
## Reading the accuracy gap
- **Overfitting**: very high training accuracy, much lower test accuracy. The model has memorized noise and specific details of the training examples. 99% versus 62% is a classic sign.
- **Underfitting**: low accuracy on both sets, because the model is too simple to capture the pattern.
- **Good fit**: training and test accuracy are both good and close to each other.
Common remedies for overfitting include more (or more varied) training data, regularization, a simpler model, fewer features and early stopping.
W: Overfitting: the model fits the training data almost perfectly but fails on unseen data, so the large gap shows poor generalization.
X: A=Unlabeled training data: accuracy can only be measured when labels exist, and the team reports accuracy on both sets, so the data must be labeled. Label type does not create a train/test gap.
C=Perfect fairness: fairness concerns how outcomes differ across groups. Nothing in two overall accuracy numbers says anything about fairness, and a 37-point drop is a warning sign, not an achievement.
D=Underfitting: an underfit model would also score poorly on the training set. A 99% training accuracy rules out underfitting.
T: High training accuracy with much lower test accuracy means overfitting; underfitting shows poor accuracy on both.

G: ## What a foundation model is
A foundation model (FM) is a very large model pretrained on broad data so it can be adapted to many tasks. A **large language model (LLM)** is a foundation model for text: it was trained on huge text corpora to predict the next token, and in the process it learned grammar, facts and patterns of many languages.

Because the LLM understands and generates language, you change the task by changing the prompt, not by training a new model:
- "Summarize this report in five bullet points."
- "Translate this email into Spanish."
- "Using the text below, answer: when does the contract expire?"
On AWS, Amazon Bedrock gives API access to many LLMs from different providers, so a company can use one model for all three tasks without building separate ones.

X: B=Linear regression on text length: linear regression predicts a single number from numeric features. It cannot read meaning or generate a summary, translation or answer.
C=Image classification CNN: a convolutional network trained on images outputs a class label for a picture. It does not understand or produce natural language text.
D=Rules engine with dictionaries: hand-written rules and word lists must be built and maintained per task and break on phrasing they did not anticipate; this is the opposite of a single general model.
T: Many different language tasks from one model is the defining strength of an LLM, a text foundation model steered by prompts.

G: ## Two families of models
- **Discriminative models** learn the boundary between classes or the mapping from input to a value. Given an email they answer "spam or not spam"; given a house they predict a price. The output is a label or number.
- **Generative models** learn the patterns of the data itself so they can produce new samples that look like it: text, images, audio, code.
## A concrete contrast
Show both kinds a photo of a cat. A discriminative classifier returns `cat` with a confidence score. A generative image model, asked "a cat wearing a raincoat", creates a picture that did not exist before. Large language models are generative: they produce new text one token at a time.
Both kinds are trained on data, and both can handle text or images; the difference is what they output.
W: Generates new content versus predicts labels: generative AI creates new text, images or other content, while discriminative models classify or predict a value for an input.
X: A=GenAI needs no training data: generative models are trained on very large datasets, usually far more than traditional models, so the claim is backwards.
B=GenAI only handles tabular data: generative AI is best known for unstructured data such as text, images and audio, and traditional ML also handles images and text, so the split is invented.
D=No meaningful difference: the two describe different goals and outputs (create new content versus assign a label or value), so they are not synonyms.
T: Generative models create new content; discriminative models predict a label or value for the input they are given.

@ Q000008 explain
G: ## What makes AI "agentic"
An AI agent does not just answer one prompt. It is given a goal and works toward it in a loop:
- **Plan**: break the goal into subtasks, usually using a foundation model to reason.
- **Act**: call tools, such as APIs, databases, code execution or search.
- **Observe**: read the results of each action.
- **Adjust**: change the plan if a step fails or reveals new information, then continue until the goal is met.
## An example
Goal: "Rebook my cancelled flight and tell my hotel." The agent looks up the booking, searches alternative flights, books one through an airline API, then emails the hotel with the new arrival time, with little human input between steps. On AWS, Amazon Bedrock Agents and Amazon Bedrock AgentCore are used to build and run agents like this.
W: Agentic AI: the system plans subtasks, chooses and calls tools, carries out multi-step actions and adapts its plan from intermediate results with minimal human intervention.
X: A=Supervised classification model: a classifier maps one input to one label, such as spam or not spam. It does not plan steps, call APIs or change its approach.
B=Batch inference pipeline: a batch pipeline runs a fixed model over a large dataset on a schedule. The steps are predefined and there is no autonomous planning or tool choice.
C=Relational database: a database stores and queries structured data. It holds information an agent might use but does not decide or act on its own.
T: Planning, tool use and self-correction toward a goal define agentic AI, unlike single-step prediction or fixed pipelines.

G: ## Batch versus real-time inference
- **Real-time inference**: a model sits behind an always-available endpoint and answers each request in milliseconds, for example a fraud check during checkout.
- **Batch inference**: the model processes a large dataset in one job, reading inputs from storage and writing all predictions back to storage. No endpoint waits for individual requests.
## Why batch fits here
The retailer scores millions of customers once per night, and the results are only needed next morning. Batch inference suits this because:
- compute runs only during the job and is released afterwards, so nothing idles all day
- throughput for the whole dataset matters, not the latency of any one prediction
In SageMaker AI this is a **batch transform** job, which reads input from Amazon S3 and writes predictions back to S3.
W: Batch inferencing: a scheduled job that scores the whole customer base at once fits bulk, offline predictions where individual latency does not matter.
X: B=Sub-second asynchronous inferencing: sub-second response targets are unnecessary when results are used hours later, and a per-request approach adds overhead for millions of records that one bulk job handles more simply.
C=Real-time inferencing: an always-on endpoint built for millisecond answers to single requests pays for constant capacity to solve a problem that only needs one nightly run.
D=Serverless inference per web click: this serves individual requests triggered by user activity. The need here is scoring every customer together overnight, not reacting to clicks.
T: Large, scheduled scoring jobs where nobody waits for an individual answer call for batch inference, not real-time endpoints.

With serverless inference you deploy a model and send requests, and the cloud provider provisions compute when requests arrive and scales it down when traffic stops. You do not choose or patch instances.

D=Requests stored and never processed: an inference service exists to process requests and return predictions. Storing them indefinitely would deliver nothing.
T: Serverless inference means the provider provisions and scales compute on demand and you manage no servers, in contrast to always-on, self-managed instances.

@ Q000012 explain
G: ## When not to use machine learning
Machine learning is useful when the rule is unknown or too complex to write down, so it is learned from examples. Its predictions are statistical estimates and can be slightly wrong.
Interest accrual is the opposite case. The rule is known exactly, for example `interest = balance * annual_rate / 12`, and auditors need the same input to give the same result every time, to the cent.
## Deterministic software fits
- Ordinary code (a SQL query, a batch job, a spreadsheet formula) computes the exact answer.
- It is reproducible: rerunning it yields identical results.
- It is explainable: the formula itself is the audit trail.
An ML model trained to imitate the formula could at best match it approximately while adding cost, error and harder audits. A good rule of thumb: if you can write the formula, write the code.
W: Standard deterministic software: a fixed, known formula is computed exactly and reproducibly by ordinary code, while any ML approach would only approximate it and add error.
X: B=Deep learning regression: a neural network would learn an approximation of a formula that is already known, introducing small errors that fail the 100% reproducibility requirement.
C=Foundation model generating figures: foundation models produce probabilistic text and can state numbers that look plausible but are wrong, and output may vary between runs, which is unacceptable for audited figures.
D=Clustering and per-cluster estimates: grouping accounts and estimating one figure per group replaces each account's exact interest with an approximation, which defeats precise per-account accrual.
T: When the rule is known and exact, reproducible results are required, use deterministic code; ML is for patterns you cannot write down.

G: ## What time-series forecasting is
A time series is a sequence of values measured over time, such as weekly sales for each store. Forecasting uses the history of that series to predict future values. Good forecasting models capture:
- **trend**: sales slowly rising or falling
- **seasonality**: repeating patterns, such as higher sales every December
- **related events**: holidays and promotions supplied as extra inputs
## Prediction intervals
A single number (for example 1,200 units) hides uncertainty. A **prediction interval** gives a range, such as "between 1,050 and 1,380 units with 80% probability", often produced as quantiles like `p10`, `p50`, `p90`. Planners use the low end to avoid overstocking and the high end to avoid stock-outs. On AWS, SageMaker Canvas includes time-series forecasting that produces such quantile forecasts without code.
W: Time-series forecasting with prediction intervals: it predicts future weekly sales per store from historical data, accounts for seasonality and holidays, and returns a range of likely values.
X: A=Sentiment analysis of reviews: sentiment analysis classifies the opinion in text as positive or negative. It does not produce future sales numbers.
B=Clustering stores by past volume: clustering groups similar stores together, which can help segmentation, but it does not predict next quarter's weekly sales or give a range for each week.
D=Binary classification: binary classification predicts one of two classes, such as yes or no. The retailer needs numeric values for future weeks, not a two-way label.
T: Predicting future numeric values over time, with uncertainty ranges, is time-series forecasting; classification and clustering answer different questions.

G: ## What retrieval-augmented generation (RAG) is
A foundation model only knows what was in its training data, which does not include a company's internal documents and stops at a cutoff date. RAG fixes this at question time:
- **Index**: documents are split into chunks, converted into embeddings (numeric vectors of meaning) and stored in a vector store.
- **Retrieve**: the user's question is embedded and the most relevant chunks are found.
- **Augment and generate**: those chunks are added to the prompt, and the model writes an answer grounded in them, often with citations.
## Why it stays current
When a policy document changes, you re-index that document; there is no retraining. **Amazon Bedrock Knowledge Bases** manages this pipeline, connecting data sources such as Amazon S3 to a vector store and a Bedrock model.
W: RAG with a knowledge base of company documents: relevant excerpts are retrieved before each answer is generated, which grounds responses in the company's own, current documents.
X: A=Train a new foundation model from scratch: pretraining a model needs enormous data, compute and time, and the model would still be out of date the moment documents change.
B=Keyword search with no generative component: a keyword engine returns links or passages, but the requirement is a generated natural-language answer, and exact keyword matching misses questions phrased differently from the text.
C=Reinforcement learning from scratch: reinforcement learning trains an agent through rewards for actions. It has no built-in way to retrieve document excerpts or answer questions from them.
T: Retrieving relevant document excerpts and adding them to the prompt (RAG) grounds answers in current company data without training a new model.

G: ## The machine learning lifecycle
Each step feeds the next, so the order matters:
- **Collect**: gather raw data relevant to the business problem.
- **Prepare**: clean it (missing values, duplicates, formats) and engineer features.
- **Train**: fit the model on the prepared data.
- **Evaluate**: test on held-out data and on edge cases, compare against the business goal, and only then approve release.
- **Deploy**: serve the approved model for predictions.
- **Monitor**: watch prediction quality and incoming data in production. When data drifts (for example customer behavior changes), retrain with fresh data and repeat.
## What went wrong in the scenario
The team skipped **evaluate** (edge cases were never tested) and had no **monitor** step (changing data went unnoticed). SageMaker AI supports these steps with tools such as Model Monitor for detecting drift.
W: Collect, prepare, train, evaluate, deploy, monitor: evaluation before deployment catches untested edge cases, and monitoring after deployment detects changing data so the model can be retrained.
X: A=Deploy first: you cannot deploy a model that has not been trained, and collecting and preparing data last means training would have no input.
B=Train before collecting: training needs collected and prepared data first, and this order also has no evaluation step, the exact gap that let edge cases through.
C=Deploy before train, evaluate last: deploying an untrained model is impossible, and evaluating only after monitoring in production repeats the original mistake of releasing untested models.
T: Evaluate before you deploy and monitor after you deploy; data collection and preparation always come before training.

G: ## Data preparation
Raw data is rarely ready for training. Preparation fixes quality problems so the model learns real patterns instead of errors:
- **missing values**: fill them (for example with a median) or drop the rows
- **duplicate rows**: remove them so some examples are not counted twice
- **inconsistent formats**: convert `03/04/2025` and `2025-04-03` to one standard date format
## Feature engineering
Feature engineering creates or transforms inputs so patterns are easier to learn. A raw `last_purchase_date` means little to a model, but `days_since_last_purchase` (today's date minus the last purchase date) directly expresses how recently a customer bought, which is useful for predicting churn.
Both tasks happen after problem framing and data collection and before training. Tools such as SageMaker Data Wrangler support them.
W: Data preparation and feature engineering: fixing missing values, duplicates and date formats is data cleaning, and deriving "days since last purchase" is creating a new feature, both done before training.
X: A=Model monitoring after deployment: monitoring watches a live model's predictions and incoming data for drift. The team here is still cleaning a dataset, before any model exists.
C=Model deployment: deployment makes a trained model available for predictions. Cleaning data and creating columns happen long before a model can be deployed.
D=Business problem framing: framing defines the goal and success metric, such as "reduce churn by 5%". It does not involve cleaning rows or computing new columns.
T: Cleaning data and deriving new input columns is data preparation and feature engineering, which comes after framing and before training, deployment and monitoring.

G: ## Two ways to serve a foundation model
- **Managed model API**: you send prompts to an endpoint, and the provider runs the GPUs, scaling, patching and availability. On AWS, Amazon Bedrock works this way and is priced per use (for example per token).
- **Self-hosting**: you deploy model weights on compute you manage, such as EC2 GPU instances or containers, or on a SageMaker AI endpoint where you pick the instance types.
## What self-hosting gives and costs
Gains: full control over the model version, runtime settings, network placement and custom modifications.
Costs: you choose and size GPU instances, handle scaling, apply patches, monitor health, plan capacity and pay for instances while they run, even when idle.
Neither option is always cheaper; it depends on traffic volume and utilization. The consistent difference is **control versus operational responsibility**.
W: More control, more operational burden: self-hosting lets the company control the environment and customize it, but it takes on infrastructure, scaling, patching and capacity work that the managed API would handle.
X: A=Eliminates all operational responsibility: self-hosting adds responsibility; running your own compute means managing scaling, patching and availability yourself.
B=Managed APIs always cost more: cost depends on usage. Pay-per-use APIs are often cheaper at low or spiky volumes, while steady high traffic can favor dedicated capacity, so "always" is false.
C=Self-hosting is always faster to set up: provisioning GPU instances, deploying the model and configuring scaling takes longer than calling an existing managed API.
T: Self-hosting a foundation model buys control at the price of running the infrastructure yourself; a managed API trades some control for far less operational work.

G: ## Kiro: spec-driven agentic IDE
Kiro is an AI-powered development environment (IDE) from AWS built around **spec-driven development**. Instead of writing code prompt by prompt, you start from a specification:
- Kiro turns a feature request into written requirements and a design
- it breaks the design into an ordered list of implementation tasks
- its agent then carries out those tasks across multiple files, which you review
## Amazon Q: a broader generative AI assistant
Amazon Q is AWS's generative AI assistant family used across many work activities. Amazon Q Developer answers AWS and coding questions, suggests and reviews code and helps troubleshoot; Amazon Q Business answers questions using company data.
So the IDE assistant that plans and implements work from a written specification is Kiro, and the general-purpose assistant for Q&A, reviews and troubleshooting is Amazon Q.
W: Kiro for spec-driven coding, Amazon Q for broader tasks: Kiro turns specifications into planned, multi-step implementation inside its IDE, while Amazon Q covers general Q&A, code review, troubleshooting and task automation.
X: A=Same product under two names: Kiro and Amazon Q are separate offerings with different focus, one a spec-driven agentic IDE, the other a broad assistant used in many places.
B=Roles swapped: this reverses them. The spec-driven, plan-then-implement IDE workflow is Kiro's defining feature, while the broad cross-activity assistant is Amazon Q.
D=SageMaker JumpStart for both: JumpStart is a hub of pretrained models and solution templates for building ML applications. It is not a coding assistant or a general work assistant.
T: Spec-to-implementation agentic coding in an IDE points to Kiro; a general assistant for questions, reviews and troubleshooting points to Amazon Q.
