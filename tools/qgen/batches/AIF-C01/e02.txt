G: ## Repeatability in MLOps
A training run is the combination of three things: the **code** (feature logic, model script), the **data** (the exact snapshot of the training set) and the **settings** (hyperparameters, library versions, random seeds, instance type). Change any one and the resulting model can change.
Repeatability means you can rerun a past experiment and get the same (or explainably similar) model because all three are recorded and versioned.
- Code lives in Git with a commit id per run.
- Data is versioned, for example as dated, immutable S3 prefixes or dataset versions.
- Settings and results are logged as experiment metadata, for example with managed MLflow in Amazon SageMaker AI.
- Automated pipelines such as `SageMaker Pipelines` run the same steps the same way every time, and the SageMaker Model Registry records which artifacts produced each model version.
Example: a model trained in March can be traced to commit `a1b2c3`, dataset `s3://ml/churn/2026-03-01/` and `learning_rate=0.05`, so a colleague can reproduce it in April.
W: Repeatability via versioned code, data and settings: the symptom is that nobody can tell which code, data or configuration produced each result. Versioning and tracking all three is exactly what lets a team reproduce a run and explain why two runs differ.
X: A=Lower inference latency: latency is how fast a deployed endpoint answers a request. It says nothing about which inputs produced a trained model, so improving it does not make retraining reproducible.
C=More training epochs: epochs are one hyperparameter. Changing it without recording it would add yet another untracked difference between runs rather than fixing the traceability gap.
D=Endpoint scalability: scalability is about handling more traffic or more models. The team's problem happens before deployment, when it cannot recreate a training run.
T: When results cannot be reproduced, the missing MLOps principle is repeatability: version code, data and settings, not performance or scale tuning.

G: ## Technical debt in ML systems
Technical debt is the future cost you take on when you choose a quick fix today instead of a clean, maintainable design. Like financial debt, it accrues "interest": every later change becomes slower and riskier.
ML systems collect debt faster than ordinary software because the code is only a small part of the system. Typical sources:
- **Undocumented data dependencies**: a model silently relies on a column another team may rename or drop.
- **Glue code and pipeline jungles**: ad hoc scripts that move data between steps and that nobody fully understands.
- **Manual patches**: one-off fixes applied by hand instead of through a versioned, automated pipeline.
- **Hidden feedback loops and unused features** that are never cleaned up.
Example: a team cannot upgrade a preprocessing library because five scripts depend on an old behavior no one documented. MLOps practices such as automated pipelines, a feature store, versioning and tests are how teams pay the debt down.
W: Technical debt: undocumented dependencies, patched scripts and opaque glue code are classic forms of ML technical debt, and "changes becoming increasingly risky and slow" is exactly the interest that debt charges.
X: A=Data augmentation: augmentation creates extra training examples by transforming existing ones, such as flipping images or paraphrasing text. It is a modeling technique, not a description of accumulated maintenance cost.
B=Real-time inferencing: this is a way of serving predictions with low latency per request. It describes how a model is deployed, not why the surrounding system became hard to change.
D=Overfitting: overfitting is a model that memorizes training data and generalizes poorly. It is a property of one model's accuracy, while the scenario describes the whole system's code and pipelines.
T: Hidden, growing maintenance cost from shortcuts in pipelines and dependencies is technical debt, a system problem rather than a model-accuracy problem like overfitting.

@ Q000028 explain
G: ## Why accuracy misleads on imbalanced data
Accuracy is correct predictions divided by all predictions. When one class is rare, a model can score high accuracy by always predicting the common class.
Example with 1,000 patients, 20 of whom (2%) have the disease: a model that answers "negative" for everyone is right 980 times, so accuracy is 98%, yet it finds zero sick patients.
## Recall and precision
The confusion matrix counts true positives (TP), false negatives (FN), false positives (FP) and true negatives.
- **Recall (sensitivity)** = TP / (TP + FN): of all people who really have the disease, how many did the model catch? The model above has recall 0 / 20 = 0%.
- **Precision** = TP / (TP + FP): of the people flagged positive, how many really are?
- **F1 score** balances the two.
In screening, a missed case (false negative) is usually the costliest error, so recall is the metric that exposes the problem.
W: Recall (sensitivity): it measures the share of actual positive cases the model identifies. A model that labels nearly everyone negative has very low recall, which reveals exactly the failure that 98% accuracy hides.
X: B=Total training time: training time describes compute cost and speed of building the model. It tells you nothing about which cases the model classifies correctly.
C=Overall accuracy: accuracy is the metric that is being fooled here. With 98% negatives, predicting "negative" every time already reaches about 98% accuracy.
D=Cost per user: this is an operational business measure. It does not count missed or detected disease cases, so it cannot reveal poor detection of positives.
T: On imbalanced data where missing a positive is costly, check recall; high accuracy can come from simply predicting the majority class.

G: ## Scalability as an MLOps quality
Scalability means the ML platform keeps working as the number of models, data volume and prediction traffic grow, without a matching growth in manual work.
Going from 5 to 200 models and from thousands to millions of predictions per day stresses two areas:
- **Pipelines**: training, evaluation and deployment must be automated and templated (for example with `SageMaker Pipelines` and a model registry) so one team can operate hundreds of models.
- **Serving**: inference must grow with demand, for example SageMaker AI endpoints with auto scaling, multi-model endpoints that host many models behind one endpoint, serverless inference for spiky traffic, or batch transform for large offline jobs.
Other MLOps qualities matter too, but they answer different questions: repeatability (can we reproduce a run?) and interpretability (why did a model predict this?).
W: Scalability of pipelines and serving: the scenario is purely about growth in the number of models and in prediction volume, and scalability is the quality that lets the platform absorb that growth through automation and elastic infrastructure.
X: A=Single-model interpretability: explaining why one model made a prediction (for example with SageMaker Clarify feature attributions) is useful for trust, but it does nothing to handle 40 times more models or millions of requests.
B=Manual approval of each prediction: human review of every prediction is the opposite of scalable. At millions of predictions per day it would require an impossible amount of reviewer time.
D=Repeatability of one experiment: reproducing a single run is important for traceability, but the challenge here is volume and model count, not reproducing a specific result.
T: Growth in model count and traffic calls for scalability (automated pipelines, auto scaling endpoints), not per-model qualities like interpretability or repeatability.

A model is trained on data from the past. In production, incoming data can change (new customer segments, seasonal patterns, a changed upstream field), and predictions quietly get worse. This is called **drift**.
**Amazon SageMaker Model Monitor** watches deployed models:
- It first creates a **baseline** from the training data: statistics and constraints for each feature (ranges, types, distributions).
- Endpoint **data capture** saves a sample of real requests and responses to S3.
- Scheduled monitoring jobs compare captured data with the baseline and report violations. Metrics go to Amazon CloudWatch, where alarms can notify the team.
Monitor types include data quality, model quality (needs ground-truth labels), bias drift and feature attribution drift (the last two use SageMaker Clarify).
Example: the average `income` feature in live traffic shifts well away from the training baseline; the data quality job flags it and a CloudWatch alarm alerts the team to retrain.

D=Amazon Polly: Polly converts text into lifelike speech. It is an AI service for generating audio, not a monitoring tool.
T: Drift detection on a live SageMaker AI endpoint is Model Monitor (baseline plus captured data plus CloudWatch alarms); data preparation and billing tools do not watch model inputs.

@ Q000031 explain
G: ## What a token is
LLMs do not read characters or whole words; they read **tokens**, chunks of text such as a word, part of a word or punctuation. As a rough rule for English, one token is about three-quarters of a word, so 1,000 words is roughly 1,300 tokens (the exact number depends on the model's tokenizer).
## Why tokens drive cost and limits
- **Pricing**: on-demand inference in Amazon Bedrock is billed per input token and per output token.
- **Context window**: each model has a maximum number of tokens it can consider at once (prompt plus response).
- **Max output tokens**: the request sets a cap such as `maxTokens`; when the reply hits it, generation stops, even mid-sentence, and the API reports a stop reason like `max_tokens`.
Example: pasting a 40-page manual (about 25,000 tokens) into every prompt multiplies the input tokens billed per request, which explains the doubled bill.
W: Tokens: input tokens from the pasted manuals raised the bill, and the output token limit caused replies to stop mid-sentence. Both effects come from the same unit that billing and limits are measured in.
X: A=Parameters: parameter count describes model size and influences the per-token price of a model, but you are not billed per parameter used, and parameters do not cause truncated replies.
C=Embeddings: embeddings are vectors produced by separate embedding models, typically for search and RAG. A chat request is not billed by vector size, and embeddings do not cut off generated text.
D=Epochs: epochs are passes over training data during training or fine-tuning. Inference does not retrain the model on each prompt, so epochs play no role in per-request cost.
T: Long prompts cost more and long answers get cut off because both billing and limits are counted in tokens, not in parameters or epochs.

@ Q000032 explain
G: ## How retrieval works in RAG
Retrieval augmented generation (RAG) finds relevant text and adds it to the prompt. To find it, documents are turned into **embeddings** (vectors that capture meaning) and stored in a vector index; the user's question is embedded too, and the closest vectors are returned.
## Why one vector per 80-page PDF fails
A single vector has to summarize everything in 80 pages, so its meaning is an average of many topics. A specific question ("What is the refund deadline?") does not match that blurred average well, and even when it does, the whole document is too big to put in the prompt.
## Chunking
Chunking splits documents into smaller passages, often a few hundred tokens each, usually with some overlap so sentences are not cut apart. Each chunk gets its own vector.
- Amazon Bedrock Knowledge Bases offers fixed-size, hierarchical and semantic chunking, or no chunking for pre-split files.
Example: the refund section becomes its own chunk, so the search returns that passage directly.
W: Chunk the documents: splitting each PDF into smaller passages gives every topic its own focused vector, so retrieval returns the specific relevant section and the prompt stays small enough to use.
X: A=Raise the temperature: temperature controls randomness in the generated text. It is applied after retrieval, so it cannot fix the wrong or diluted passages being retrieved, and it tends to make answers less reliable.
B=Fine-tune on each PDF: fine-tuning changes model weights and is costly. It does not fix retrieval, and RAG exists precisely so that knowledge can be looked up at query time instead of trained in.
C=One very long vector: this is the current problem. Tokenizing the whole PDF into one embedding still averages all its topics, and embedding models have input limits that an 80-page document can exceed.
T: RAG retrieves at the granularity you embed, so chunk long documents into passages; generation settings or fine-tuning cannot fix bad retrieval.

@ Q000033 explain
G: ## Keyword search versus semantic search
Classic keyword search looks for the same words. "cheap flights" matches documents containing "cheap" or "flights", so a page that only says "low-cost airfare" is missed even though it means the same thing.
## Embeddings
An **embedding** is a list of numbers (a vector, often hundreds or thousands of dimensions) produced by an embedding model, such as Amazon Titan Text Embeddings or Cohere Embed in Amazon Bedrock. The model is trained so that texts with similar meanings get vectors that are close together.
- "cheap flights" and "low-cost airfare" land near each other; "cheap shoes" lands farther away.
- A vector store (for example Amazon OpenSearch Service with vector search) finds the nearest vectors using a similarity measure such as cosine similarity.
This is called semantic search and it is also the retrieval step of RAG.
W: Embeddings: they represent text as vectors that capture meaning, so synonymous phrases sit close together and a similarity search finds "low-cost airfare" for the query "cheap flights".
X: B=Higher model temperature: temperature changes how random a model's generated text is. It has no effect on how documents are matched to a search query.
C=Alphabetical sorting of titles: sorting only changes the order of results. It cannot recognize that two different phrases mean the same thing.
D=Exact keyword matching on "cheap": exact matching requires the same word to appear. A document that says "low-cost" instead of "cheap" would be missed, which is the exact problem.
T: Matching by meaning rather than by exact words is what embeddings plus vector similarity search provide.

@ Q000034 explain
G: ## Ways to improve an LLM's output
The options range from cheap and fast to expensive and slow:
- **Prompt engineering**: change only the input. Clear instructions, a role, the output format, a few examples (few-shot prompting) or asking the model to reason step by step. No training, no weight changes, results in minutes.
- **RAG**: add retrieved reference data to the prompt; also no weight changes, but needs a data source.
- **Fine-tuning**: continue training on labeled examples; changes weights and needs training data.
- **Distillation**: train a smaller student model from a larger teacher's outputs.
- **Pretraining from scratch**: huge data and compute.
Example: instead of "Classify this ticket", write "You are a support triage assistant. Classify the ticket as Billing, Technical or Account. Answer with one word." and add two labeled example tickets in the prompt.
W: Prompt engineering: it improves task accuracy purely by changing the instructions, examples and structure of the input, which satisfies both constraints: no weight changes and no additional training data.
X: A=Fine-tuning: fine-tuning continues training on labeled examples and produces updated weights, so it breaks both constraints in the question.
B=Model distillation: distillation trains a new, smaller model to imitate a larger one. That creates new weights through a training process, which the developer wants to avoid.
D=Retraining from scratch: pretraining a model needs very large datasets and compute and produces entirely new weights. It is the most expensive option and violates both constraints.
T: When weights and training data are off the table, improve results through the prompt; fine-tuning and distillation both require training.

@ Q000035 explain
G: ## The problem with older sequence models
Recurrent neural networks (RNNs and LSTMs) read text one token after another, passing a hidden state forward. That has two drawbacks:
- Processing is sequential, so it cannot be parallelized well on GPUs, which limits training on huge datasets.
- Information from early words fades as it passes through many steps, so long-range references are hard to capture.
## Transformers and self-attention
The transformer architecture (introduced in 2017) replaces recurrence with **self-attention**. For every token, the model computes how much it should "attend" to every other token in the context, all at once.
Example: in "The trophy did not fit in the suitcase because it was too big", attention lets the token "it" link strongly to "trophy" even though other words sit between them.
Because all positions are processed in parallel, transformers train efficiently at scale, which is why GPT-style, Claude, Llama and Amazon Nova models are transformer based.
W: Transformers with self-attention: self-attention relates every token to every other token in one step, enabling parallel processing and direct long-range connections, which are the two weaknesses of word-by-word models.
X: B=Bigger lookup tables of phrases: lookup tables only return stored phrases. They cannot generalize to new sentences or model relationships between distant words.
C=K-means clustering of sentences: k-means is an unsupervised method that groups similar data points. It does not generate text or model word-to-word dependencies within a sequence.
D=Deeper decision trees: decision trees split tabular features with if-then rules. They are not a sequence architecture and are not the basis of LLMs.
T: Modern LLMs are transformers; self-attention is what allows parallel processing and long-range context that sequential RNNs struggled with.

@ Q000036 explain
G: ## Traditional ML models
A traditional model is usually built for one task: you collect labeled data for that task (for example, emails labeled spam or not spam), train, and deploy. A new task means new data and a new model.
## Foundation models
A **foundation model (FM)** is a large model pretrained on broad, diverse data (text, code, images) mostly with self-supervised learning, such as predicting the next token, so no manual labels are needed for pretraining.
The same FM can then be adapted to many tasks:
- through prompting alone (zero-shot or few-shot),
- with RAG to add company knowledge,
- or with fine-tuning on a smaller labeled dataset.
Example: one FM in Amazon Bedrock can summarize reports, draft emails, classify tickets and answer questions.
The trade-off: FMs are large, so they are often slower and more expensive per request than a small task-specific model.
W: Pretrained broadly and adaptable to many tasks: this is the defining difference. Broad pretraining gives general capabilities that prompting, RAG or fine-tuning can direct to many different tasks.
X: A=Never requires labeled data: pretraining is largely self-supervised, but fine-tuning, alignment and evaluation often use labeled or human-rated examples, so "never" is false.
C=Single task only: this describes a traditional task-specific model. A foundation model is the opposite: general purpose and reusable across tasks.
D=Always faster at inference: FMs are typically much larger than task-specific models, so they are often slower and costlier per prediction. "Always faster" is not true.
T: Traditional models are one model per task; foundation models are pretrained broadly and adapted to many tasks, usually at higher inference cost.

@ Q000038 explain
G: ## How diffusion models create images
Diffusion models learn by **destroying and restoring** images:
- **Training (forward process)**: take real images and add random noise in many small steps until only noise remains. The model learns to predict and remove the noise at each step.
- **Generation (reverse process)**: start from pure random noise and apply the model repeatedly, removing a little noise each step, until a clean image appears.
The text prompt is converted into an embedding that **guides** every denoising step, so the image moves toward "a red bicycle on a beach" rather than toward any random picture. Many modern models perform these steps in a compressed latent space for speed.
Because generation starts from random noise, the same prompt with a different random seed gives a different image. In Amazon Bedrock, Stability AI's image models come from the Stable Diffusion family of diffusion models; Amazon Nova Canvas is Amazon's own text-to-image model.
W: Iterative denoising of random noise guided by the prompt: this is the core mechanism of a diffusion model, repeatedly removing noise, step by step, with the prompt steering each step toward a matching image.
X: A=Word-by-word lookup into pixels: no model maps words to fixed pixel values. Images emerge from learned denoising over the whole picture, not from a word-to-pixel table.
B=Convolution filters to sharpen an existing image: that is classic image processing on an input image. Diffusion generates a new image from noise, although diffusion networks may contain convolution layers internally.
D=Retrieve the closest stored image: retrieval returns an existing image from a database. Diffusion creates new images that did not exist before.
T: Diffusion equals starting from noise and denoising step by step under prompt guidance; it generates new images rather than editing or retrieving existing ones.

G: ## From prompt engineering to context engineering
A model only knows what is in its weights plus what is in its **context window** for the current request. Prompt engineering focuses on wording the instruction. **Context engineering** is the broader discipline of deciding everything that goes into that window, and how it is structured, for each call.
The context can include:
- the system instructions and role,
- retrieved documents from RAG,
- relevant conversation history or a summary of it,
- tool definitions and results from earlier tool calls,
- user profile data and memory.
Because the window is limited in tokens and irrelevant text can distract the model, context engineering is about choosing what is relevant, trimming or summarizing the rest, and ordering it clearly.
Example: an agent answering a billing question gets the billing policy chunk, the last three messages and the customer's plan, not the full chat log and every policy manual.
W: Selecting and structuring the context given to the model: context engineering decides which instructions, retrieved data, history and tool outputs the model sees and in what form, which largely determines answer quality.
X: A=Only temperature and top-p: these are inference parameters that control randomness. They are one small setting, not the work of choosing what information the model receives.
B=Low-level training code: writing code to train a transformer from random initialization is model pretraining. Context engineering happens at inference time with an existing model.
D=Physical network infrastructure: networking and hosting are infrastructure engineering. They affect availability and latency, not the content the model reasons over.
T: Context engineering is about what the model sees at inference time (instructions, retrieved data, history, tool results), not sampling knobs, training or infrastructure.

G: ## AI agents
An **agent** is an application in which a model plans steps, calls tools (APIs, search, code execution) and uses the results to reach a goal, rather than answering in a single pass.
## Multi-agent orchestration
In a **multi-agent** system, several agents each specialize in something, and an **orchestrator** (also called a supervisor) coordinates them:
- It breaks the user's request into subtasks.
- It routes each subtask to the right specialist agent.
- It combines the results into a final answer.
Example: "Compare our Q3 sales with the top competitor and chart it" goes to a web-search agent for the competitor figures, a data agent for internal sales, and a code-execution agent to produce the chart.
Amazon Bedrock supports this pattern through multi-agent collaboration (a supervisor agent with collaborator agents), and agents built with frameworks such as Strands Agents or LangGraph can be deployed on Amazon Bedrock AgentCore Runtime.
W: Multi-agent orchestration: an orchestrator decomposing a request and delegating subtasks to specialized agents, then combining their outputs, is the definition of this pattern.
X: A=Single-model fine-tuning: fine-tuning trains one model on labeled examples to change its behavior. It involves no delegation between cooperating agents.
B=Model distillation: distillation trains a smaller student model to imitate a larger teacher. It is a model compression technique, not a runtime task-coordination pattern.
D=Retrieval augmented generation: RAG retrieves documents and adds them to a prompt. A single agent might use RAG as one tool, but RAG itself does not split work among specialized agents.
T: An orchestrator splitting work across specialist agents is multi-agent orchestration; RAG, fine-tuning and distillation are single-model techniques.

@ Q000041 explain
G: ## The integration problem
Agents become useful when they can use tools and data: search a knowledge base, query a database, create a ticket. Without a standard, every agent framework needs custom integration code for every tool, which multiplies work.
## Model Context Protocol (MCP)
MCP is an open protocol, introduced by Anthropic in 2024 and now widely adopted, that standardizes how AI applications connect to external tools and data.
- An **MCP server** wraps a system (for example a Git repo, a database or an internal API) and describes the tools, resources and prompts it offers.
- An **MCP client** inside the agent or AI application discovers those capabilities and calls them in a standard format.
Example: a company writes one MCP server for its ticketing system, and any MCP-compatible agent or assistant can list and create tickets without custom glue code. AWS provides MCP servers for many of its services, and Amazon Bedrock AgentCore Gateway can expose existing APIs as MCP tools.
W: Standardize how agents connect to tools and data: MCP defines a common client-server protocol so agents can discover and call tools and data sources without a custom integration for each pairing.
X: B=Automatic fine-tuning: MCP does not train or change model weights. It governs how a running agent talks to external tools.
C=Compress model weights: compression techniques such as quantization or distillation reduce model size. MCP is a communication protocol and does not touch the model itself.
D=Encrypt user-model traffic: encryption in transit is handled by TLS and the transport. MCP defines the structure of tool and data interactions, not an encryption scheme.
T: MCP is a connectivity standard between agents and tools or data; it is not a training, compression or encryption mechanism.

G: ## One model, many tasks
Before foundation models, each language task typically needed its own model: a classifier for tickets, a summarizer for reports, a separate system for Q&A, each with its own training data and maintenance.
A **foundation model** is pretrained on broad data, so it can perform many tasks when you simply describe the task in the prompt:

- "Draft a polite reply to this customer."

G: ## Hallucination
A **hallucination** is output that is fluent and confident but not supported by facts or by the source data. LLMs generate the most likely next tokens; if the model does not have the company's actual policy, it may produce a plausible-sounding number, such as "90 days", from general patterns in its training data.
## Grounding with RAG
Retrieval augmented generation fixes the root cause by giving the model the real source at answer time:
- The policy documents are chunked, embedded and stored, for example in Amazon Bedrock Knowledge Bases.
- For each question, the relevant passage ("Returns are accepted within 30 days") is retrieved and added to the prompt with an instruction to answer only from it.
- The answer can cite the source, and a contextual grounding check in Amazon Bedrock Guardrails can flag or block responses not supported by the retrieved text.
Example: asked about returns, the bot now answers "30 days" and cites the policy page.
W: Hallucination, grounded with RAG: a confident answer that contradicts company policy is a hallucination, and grounding responses in the actual policy documents is the most direct mitigation because the model then answers from the real text.
X: B=Latency and streaming: streaming only delivers tokens sooner. The problem is a wrong answer, and a faster wrong answer is still wrong.
C=Overfitting and a smaller model: overfitting describes a model that memorizes training data and generalizes poorly. A smaller model has no knowledge of this company's policy either, so it would not fix the wrong fact.
D=Data drift and weekly retraining: drift is a change in input data over time. Retraining on chat logs could even reinforce the wrong answer, and it is far costlier than retrieving the correct policy at query time.
T: Confident but wrong equals hallucination; fix it by grounding answers in trusted sources (RAG plus grounding checks), not by speed tweaks or retraining.

G: ## Measuring business value with ROI
**Return on investment (ROI)** compares what a project returns with what it costs. A common formula:
- ROI = (benefit - cost) / cost
For this assistant: benefit $400K per year, cost $150K. Net gain is $250K, so ROI = 250 / 150, about 167%. Each dollar spent brought back about $2.67 in savings, a net gain of about $1.67.

## Technical versus business metrics
Technical metrics such as accuracy, latency or tokens per second show how well the system works. They matter, but they do not by themselves express financial value; a very accurate model can still lose money.

G: ## Business metrics versus technical metrics
Generative AI projects are evaluated at two levels:
- **Technical metrics** show how the model performs: latency, token throughput, accuracy, F1 score, hallucination rate.
- **Business metrics** show whether the feature changes business outcomes: conversion rate, average order value, customer satisfaction, cost per interaction.

G: ## Customer lifetime value (CLV)
CLV estimates the total revenue (or profit) a customer will generate over their whole relationship with the company, not just one purchase. A simple version:
- CLV = average purchase value x purchases per year x expected years as a customer
Example: a customer spends $50 per order, orders 6 times a year and stays 4 years, so CLV = 50 x 6 x 4 = $1,200. If a loyalty chatbot improves retention so customers stay 5 years, CLV rises to $1,500 even if each order is the same size.
## Why it fits loyalty programs
Loyalty initiatives aim at repeat purchases and longer relationships. Their effect shows up over time in retention and frequency, which a single-transaction metric misses. Companies usually compare CLV (or its leading indicators, such as retention rate) between customers who use the chatbot and those who do not.
