@ Q000051 explain
G: ## Two ways to build an agent
An AI agent is a loop: a foundation model reads the goal, decides which tool to call (an API, a database query, a calculator), reads the result and repeats until it can answer.
- **Graph or workflow first**: you draw every step and branch yourself, like a state machine. Predictable, but a lot of code for every new behavior.
- **Model first**: you give the model a system prompt and a list of tools and let it plan the steps. Much less code; the model does the orchestration.
## Strands Agents
**Strands Agents** is an open-source SDK published by AWS that takes the model-first approach. A minimal agent is a model, a prompt and tools, for example an `Agent` created with a `system_prompt` and tools such as `get_order_status` written as ordinary Python functions. It works with Amazon Bedrock models and other providers and can use tools exposed through the Model Context Protocol (MCP).
W: Strands Agents SDK: it is a lightweight, code-first, open-source agent SDK where behavior comes mainly from the system prompt and the tool list, and the model decides the steps instead of a hand-built orchestration graph.
X: A=AWS Glue: Glue is a serverless data integration (ETL) service for crawling, cataloging and transforming data; it has no concept of an agent, prompts or tool calling.
B=AWS Step Functions: Step Functions is exactly the "build the orchestration graph by hand" style: you define every state and transition in a state machine, which is what the developer wants to avoid.
C=Amazon EventBridge: EventBridge is an event bus that routes events between services by rules; it can trigger an agent but does not define agent behavior, prompts or tools.
T: Strands lets the model plan from a prompt plus tools; Step Functions makes you draw every step yourself.

G: ## Why distance adds latency
Each request to a model travels over the network to the AWS Region that hosts the endpoint and back. Light in fiber covers roughly 200 km per millisecond, so a user in Seoul calling a Region in the United States adds well over 100 ms of round-trip time before the model even starts generating.
## Choosing where to run
- Pick a Region close to users where the model you need is available; this is the most direct way to cut network latency.
- Amazon Bedrock also offers **cross-Region inference**, which can route requests among Regions in a defined geography for higher throughput.
- Tradeoffs: model availability and pricing can differ by Region, and data residency rules may restrict which Regions you can use.
Example: moving a Korean customer's chatbot from a distant Region to `ap-northeast-2` (Seoul), where the model is offered, shortens every round trip.
W: Use a closer Region: network round-trip time grows with distance, so serving the model from a Region near the users is the most direct fix for location-specific latency.
X: A=Provisioned throughput relocates itself: provisioned throughput is purchased for a specific model in a specific Region and reserves capacity there; it does not move traffic closer to users.
B=Region does not matter: the model does affect generation time, but network distance to the Region adds latency on every call, which is why only one geography is affected.
D=Change cloud provider: the problem is distance, which can be solved within AWS by using a nearer Region; changing providers is neither required nor the direct fix.
T: When latency depends on where users are, the network distance to the Region is the cause, and a closer Region is the fix.

G: ## Where the cost of a long prompt comes from
Every request makes the model process all input tokens before it writes an answer. If each request repeats a 10,000-token system prompt plus reference document and only adds a 30-token question, the model does most of the same work every time.
## Prompt caching
**Prompt caching** in Amazon Bedrock, available for supported models, stores the processed state of a marked prompt prefix for a short time.
- You place a cache checkpoint after the static part (instructions and reference document).
- Later requests that start with the same prefix read it from the cache instead of reprocessing it.
- Cached input tokens are billed at a reduced rate and time to first token drops.
- The cache expires after a few minutes without use, so it suits steady repeated traffic.
W: Prompt caching: it reuses the already processed state of the identical prompt prefix, so only the changing question is processed fully, cutting cost and latency.
X: A=Knowledge Bases: they retrieve relevant document chunks into the prompt; they do not reuse processing of repeated prompt text, and the retrieved text is still processed on every call.
C=Model distillation: distillation trains a smaller student model from a larger teacher to lower cost; it does not reuse work on a repeated prompt prefix.
D=Fine-tuning: fine-tuning changes model weights with training data; it could shorten prompts after a training project, but it is not a feature that reuses the processed state of repeated input.
T: Repeated identical prompt prefixes are the job for prompt caching; RAG, distillation and fine-tuning solve different problems.

@ Q000062 explain
G: ## How temperature works
At every step a model assigns probabilities to possible next tokens. **Temperature** reshapes that distribution before a token is picked:
- **Low temperature** (for example 0 to 0.2): the most likely tokens dominate, so the same prompt gives nearly the same wording each time. Good for legal, compliance and extraction tasks.
- **High temperature** (for example 0.8 or more): less likely tokens get a real chance, so outputs vary more. Good for brainstorming, slogans and creative writing.
Related settings such as `topP` and `topK` also limit which tokens can be chosen, but temperature is the main knob for "same versus varied".
Example: "Write a confidentiality clause" at temperature 0.1 returns almost identical text on each run; "Write a slogan for running shoes" at 0.9 gives a new idea each time.
W: Temperature, low for legal and high for marketing: lower temperature makes the clause wording consistent, and higher temperature produces the variety wanted in slogans.
X: A=Model size: size affects capability, cost and speed, but any model can be consistent or varied depending on sampling settings; size is not the knob for randomness.
B=Context window: the context window limits how much text fits in a request; it does not control how much the wording varies between runs.
D=Max tokens: max tokens caps output length; a short limit does not make wording consistent and a long one does not make slogans varied.
T: Temperature controls how random the output is: lower for consistency, higher for creativity.

G: ## What the max output length does
Model inference settings include a limit on how many tokens the model may generate, often called `maxTokens` or max output tokens. A token is roughly a short word or part of a word.
- When the model reaches the limit, generation simply stops, even in the middle of a sentence.
- Amazon Bedrock reports this in the response with a stop reason such as `max_tokens` instead of a natural end of turn.
## Why only complex questions break
Simple answers fit under a low limit. Complex questions need longer answers, so they hit the limit and are cut off.
Example: with a limit of 100 tokens, "What are your hours?" is answered fully, but "Compare our three pricing plans" stops halfway through the second plan.
Better ways to control cost: ask for concise answers in the prompt, and set the limit high enough for the longest acceptable answer.
W: Max output length too low: answers stop exactly when they reach the token cap, which affects the long answers to complex questions first.
X: A=Unsupported input modality: a modality problem would reject or misread the input (for example an image sent to a text-only model), not return text that stops mid-sentence.
B=Temperature too high: high temperature makes wording more random or less focused, but it does not truncate the answer at a fixed length.
D=Prompt caching misconfigured: caching affects how the repeated input prefix is processed and billed; it does not limit how many tokens the model generates.
T: Answers cut off mid-sentence mean the max output token limit was reached; raise it or ask for shorter answers instead.

G: ## Why models go out of date
A foundation model learns facts during training, which ends at a cutoff date. It knows nothing about changes after that, and it may answer confidently with the old information.

RAG adds current knowledge at question time without changing the model:

Example: "How many days of parental leave do I get?" retrieves the 2026 leave policy page, and the model answers from it instead of from training memory.

G: ## What a vector store does in RAG
In RAG, each document chunk is turned into an **embedding**: a list of numbers (for example 1,024 values) that represents its meaning. The question is embedded the same way, and the system looks for stored vectors that are closest to it (a similarity or k-nearest-neighbor search).
A vector store must therefore store embeddings and query them by similarity.
## AWS options
- **Amazon OpenSearch Service** (and OpenSearch Serverless): a k-NN vector search capability, and a common choice for Bedrock Knowledge Bases.
- **PostgreSQL with `pgvector`**: available on Amazon RDS for PostgreSQL and Aurora PostgreSQL; adds a `vector` column type and distance operators, so you can run a query ordered by distance to the question embedding.
- Other options include Amazon S3 Vectors, Amazon MemoryDB and Amazon Neptune Analytics.
W: B=RDS for PostgreSQL with pgvector: the pgvector extension stores embeddings in a vector column and supports similarity search in SQL.
C=Amazon OpenSearch Service: its k-NN vector search stores embeddings and returns the nearest vectors, a standard RAG vector store.
X: A=AWS Step Functions: Step Functions orchestrates workflows; it can coordinate a RAG pipeline but cannot store or search vectors.
D=Amazon SNS: SNS is a publish/subscribe messaging service that delivers notifications; it keeps no queryable data.
E=AWS Glue: Glue runs ETL jobs and maintains a data catalog of table metadata; it can help prepare documents but does not provide vector similarity search.
T: A RAG vector store must store embeddings and run similarity search; OpenSearch and PostgreSQL with pgvector do, while orchestration, messaging and ETL services do not.

G: ## The customization ladder
From cheapest and simplest to most expensive and complex:
- **Prompt engineering (in-context learning)**: change only the prompt, for example add instructions or examples. Minutes of work, no infrastructure.
- **RAG**: add a retrieval system (embeddings, a vector store, a sync process) that inserts relevant data into prompts. More moving parts, but no model training.

- **Full pretraining**: train a model from scratch on massive datasets with large GPU clusters for weeks or months. Only a few organizations do this.
Rule of thumb: start at the bottom of the ladder and move up only if the cheaper step cannot meet your needs.
W: Prompt engineering < RAG < fine-tuning < full pretraining: each step adds more data preparation, infrastructure and expertise, and pretraining from scratch is by far the costliest.

D=Reversed order: this lists the ladder from most to least expensive; full pretraining is the costliest, not the cheapest.
T: Customization gets more expensive from prompts to RAG to fine-tuning to pretraining; start with the cheapest step that works.

@ Q000071 explain
G: ## Chain-of-thought prompting
Multi-step problems go wrong when a model jumps straight to an answer. **Chain-of-thought (CoT)** prompting asks the model to write out intermediate steps first, for example with "Think step by step" or by showing a worked example that includes reasoning.
Because each step is generated before the next, later steps can build on correct earlier ones.
## Example
"A store sells pens at 3 for $2. How much do 12 pens cost? Show your reasoning, then give the final answer."
- 12 pens is 12 / 3 = 4 groups
- 4 groups x $2 = $8
- Final answer: $8
CoT often improves accuracy on math, logic and planning tasks, at the cost of more output tokens.
W: Chain-of-thought prompting: it makes the model work through intermediate reasoning steps before the final answer, which is exactly what improves multi-step math accuracy.
X: B=Negative prompting: negative prompts list things to exclude, mainly in image generation; they do not make a model reason through steps.
C=Prompt templating: templates standardize prompt structure and fields across requests; a template alone does not ask for step-by-step reasoning.
D=Zero-shot prompting: zero-shot means asking the task with no examples; it does not by itself make the model show intermediate steps.
T: When a task needs several reasoning steps, ask the model to show them: that is chain-of-thought prompting.

@ Q000072 explain
G: ## Zero-shot versus few-shot
- **Zero-shot**: the prompt describes the task with no examples, for example "Label this review as positive or negative."
- **Few-shot**: the prompt adds a handful of labeled examples before the new input, so the model sees the pattern you want.
## Why examples help with sarcasm
Sarcasm says something positive while meaning something negative. A model given no examples may read the positive words literally. A few examples teach the intended interpretation:
- "Great, my order arrived broken. Just what I needed." -> negative
- "Five stars for making me wait three weeks!" -> negative
- "Arrived early and works perfectly." -> positive
This changes only the prompt, so it takes minutes and needs no training.
W: Few-shot prompting: adding a few labeled examples, including sarcastic ones, shows the model how to classify them and is the simplest change from zero-shot.
X: A=Image model: the input is text reviews; an image model is built for a different modality and would not understand sarcasm better.

G: ## Why prompts produce broad or inconsistent answers
Consider a vague prompt such as "Tell me about our product": it leaves the model to guess the audience, length, focus and format, so each run may guess differently.
## Prompt engineering best practices
- **Be specific**: state the task, audience, length and format, for example "List the three main benefits of product X for small retailers, one sentence each."
- **Give context and examples** of the desired output.
- **Iterate**: change one thing at a time, compare outputs on the same test inputs, and keep what improves results.
- Keep inference settings such as temperature suited to the task (low for factual consistency).
Prompt engineering is experimental by nature; the first wording is rarely the best.
W: Specific prompts refined through iteration: clear, detailed instructions narrow what the model produces, and testing variations finds the wording that gives consistent results.

C=Maximize temperature: the highest temperature maximizes randomness, which increases inconsistency and drift.
D=Remove task instructions: without instructions the model must guess the task, which produces even broader and less predictable responses.
