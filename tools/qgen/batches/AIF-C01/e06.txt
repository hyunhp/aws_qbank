@ Q000126 explain
G: ## How a VPC normally reaches AWS APIs
Amazon Bedrock is called through regional HTTPS endpoints such as `bedrock-runtime.us-east-1.amazonaws.com`. By default those names resolve to public IP addresses, so an instance in a private subnet needs an internet gateway or a NAT gateway to reach them.
## Interface endpoints (AWS PrivateLink)
An interface VPC endpoint places elastic network interfaces with private IPs from your own subnets into the VPC. With private DNS enabled, the normal Bedrock hostname resolves to those private IPs, so the SDK code does not change.
- Traffic goes from the app to the endpoint's private IP and then over the AWS network to Bedrock, never across the public internet.
- Bedrock offers endpoint services such as `com.amazonaws.<region>.bedrock-runtime` for inference and `com.amazonaws.<region>.bedrock` for control-plane calls.
- You can attach an endpoint policy and security groups to limit who uses the endpoint and which actions are allowed.
W: PrivateLink interface endpoint for Bedrock: it gives the VPC a private path to the Bedrock APIs, so subnets need no internet gateway or NAT route and the isolation requirement is met.
X: B=Internet gateway with security groups: security groups only filter which ports and destinations are allowed; the allowed traffic still goes out through the internet gateway to the public Bedrock endpoint.
C=CloudFront in front of Bedrock: CloudFront is a content delivery network for serving content to clients at the edge. It does not give a VPC a private route to an AWS API, and requests would still go over public networking.
D=NAT gateway: a NAT gateway lets private-subnet instances start outbound connections, but it forwards them through an internet gateway to the public endpoint, which is the path the company wants to avoid.
T: Private access from a VPC to an AWS API means an interface (PrivateLink) endpoint; NAT and internet gateways both lead to the public internet path.

@ Q000127 explain
G: ## Why RAG needs data lineage
In a retrieval-augmented generation (RAG) app, source documents are split into chunks, turned into embeddings and stored in a vector index. When an answer is questioned in a compliance review, you need to know which document, and which version of it, produced the chunk the model used.
## Catalogs and metadata
A data catalog stores metadata about datasets: where they live, their schema, owners, versions and custom properties.
- The AWS Glue Data Catalog holds table and dataset definitions, including their Amazon S3 locations and schemas, and crawlers can keep them up to date as data changes.
- You can add custom properties such as source system, document version and ingestion date to catalog entries, and record the same identifiers as metadata on each chunk in the vector store.
- Example: a chunk tagged `doc=policy-17, version=4` can be matched to the catalog entry that describes the source dataset and its S3 location used for the embedding run.
For end-to-end lineage graphs, AWS also offers lineage features in Amazon SageMaker Catalog (Amazon DataZone), which build on catalog metadata; among the listed options, only the Glue Data Catalog addresses cataloging at all.
W: Glue Data Catalog with metadata tracking: it is the AWS service built to catalog datasets and their metadata, so recording source and version details there gives reviewers a record of which sources fed each embedding build.
X: A=CloudWatch Logs Insights: it queries log events such as application or invocation logs. It can show that a request happened, but it does not keep a catalog of source datasets and their versions.
B=Bedrock Guardrails: guardrails filter prompts and responses for harmful content, denied topics or sensitive information. They do not record where training or retrieval data came from.
D=AWS KMS: KMS creates and controls encryption keys that protect data. It says nothing about which documents or versions a dataset contains.
T: Tracing outputs back to source data is a metadata and cataloging problem (Glue Data Catalog), not logging, content filtering or encryption.

@ Q000128 explain
G: ## Agents act with an IAM role
An Amazon Bedrock agent calls tools through action groups, often AWS Lambda functions that in turn call internal APIs. Every call runs with the permissions of an IAM role, so the role, not the prompt, decides what the agent can actually do.
## Least privilege
Least privilege means granting only the actions and resources a job needs.
- For an order-status lookup, allow only read actions such as a `GetOrderStatus` API on the order resources.
- Leave out write actions like `CancelOrder` or `UpdateOrder`, so even a manipulated or confused agent cannot perform them.
- Prompt instructions are not a security boundary: prompt injection or model mistakes can make an agent try actions it was told to avoid.
W: Least privilege, read-only actions: if the role can only read order status, modification or cancellation is impossible regardless of what the model generates.
X: A=Full access plus prompt instructions: prompts can be bypassed by prompt injection or ignored by the model, and the full permissions would then let the agent change or cancel orders.
B=Shared IAM user credentials: long-term keys shared across agents are hard to rotate, cannot be scoped per agent and make it impossible to tell which agent made a call. Agents should use their own roles with temporary credentials.
D=AdministratorAccess: this grants every action on every resource in the account, the opposite of the requirement, and turns any agent mistake into a possible account-wide incident.
T: Control what an agent can do with narrowly scoped IAM permissions, never with prompt instructions or broad access.

G: ## Data residency on AWS
AWS stores customer content in the Region you choose and does not move it to another Region unless you or a service you configure does. Residency is therefore about making sure nobody creates resources or copies data outside approved Regions.
## Enforcing it
- Create the S3 buckets, training jobs, model artifacts and inference endpoints only in the approved Region.
- Use a **service control policy (SCP)** in AWS Organizations that denies actions when `aws:RequestedRegion` is outside the allowed list, so even administrators in member accounts cannot deploy elsewhere.
- Review features that can move data, such as S3 cross-Region replication or Bedrock cross-Region inference profiles, and enable them only when they keep processing in allowed Regions.
Example: an SCP denies all actions outside `eu-central-1` except for global services such as IAM.
W: Approved Regions enforced with SCPs: keeping training data, artifacts and inference in approved Regions, with an organization-wide guardrail, directly prevents data from leaving the required geography.
X: B=Single global bucket with client-side encryption: an S3 bucket always lives in one Region, and encryption protects confidentiality, not location. Encrypted data stored in the wrong Region still violates residency.
C=CloudFront global caching: caching outputs at edge locations worldwide copies derived data out of the region, which works against the requirement.
D=Default shared responsibility only: data location is the customer's responsibility. Without Region choices and guardrails, nothing stops someone from creating resources elsewhere.
T: Residency is about where data is stored and processed, so pin resources to approved Regions and enforce it with SCPs; encryption and defaults do not control location.

@ Q000135 explain
G: ## S3 Lifecycle rules
An S3 Lifecycle configuration is a set of rules on a bucket that act on objects based on their age.
- **Transition actions** move objects to cheaper storage classes, for example to S3 Glacier Flexible Retrieval after 90 days.
- **Expiration actions** delete objects a set number of days after creation.
- Rules can apply to the whole bucket or to a prefix or tag, such as `inference-logs/`.
Example: a rule with filter `inference-logs/` and `Expiration: Days 400` removes each log object 400 days after it was written, with no scripts or manual work. S3 queues expired objects for removal asynchronously, and you are not billed for storage after the expiration date.
For versioned buckets, add `NoncurrentVersionExpiration` so older versions are removed too.
W: S3 Lifecycle rule expiring at 400 days: it applies the retention period automatically to every log object, which is the most efficient way to enforce time-based deletion.
X: A=Manual yearly deletion: a yearly review cannot delete each object at 400 days, costs staff time and is easy to forget, so logs would be kept too long or deleted too early.
C=Reduced Redundancy Storage: this is a legacy storage class that AWS no longer recommends. A storage class sets durability and price; it never deletes objects.
D=Versioning only: versioning keeps every overwritten or deleted version, so without lifecycle rules data is retained longer, not deleted after 400 days.
T: Time-based deletion in S3 is a Lifecycle expiration rule; storage classes and versioning do not remove data on a schedule.

G: ## Why fixed, rare reviews fail for AI
Generative AI systems change over time: user inputs shift, prompts and retrieval sources are updated, and providers release new model versions. A review every two years cannot catch problems that appear in months.
## Risk-based governance
- **Tier by risk**: review high-impact uses (such as customer-facing or regulated decisions) more often than low-risk internal tools.
- **Monitor continuously**: track output quality, safety filter hits, bias metrics and user feedback, for example with Bedrock model invocation logging, guardrail metrics and CloudWatch alarms.
- **Trigger reviews on events**: a model update, a new data source or an alarm starts a review instead of waiting for the calendar.
This keeps effort focused where risk is highest, so rigor improves without reviewing everything all the time.
W: More frequent, risk-based reviews with monitoring: monitoring catches drift early, and risk tiers keep the review workload proportionate, which balances rigor and overhead.
X: A=Outsource governance to the provider: the model provider does not know your use case, users or regulations, and the company remains accountable for how it uses the model.
B=Rely only on customer complaints: this is purely reactive, so harm reaches customers before anyone notices, and many issues such as subtle bias never produce complaints.
D=Keep two years, longer meetings: longer meetings do not fix the real problem, which is the gap of up to two years in which drift goes undetected.
T: Match governance frequency to risk and add continuous monitoring; rare fixed reviews and reactive approaches let drift go unnoticed.

@ Q002466 explain
G: ## How a model picks the next token
A language model produces a probability for every possible next token. The inference parameters decide how the next token is chosen from that distribution.
## Temperature
Temperature rescales the probabilities before sampling.
- **Low temperature** (for example `0` to `0.2`) sharpens the distribution, so the most likely token almost always wins and the same prompt gives nearly the same answer.
- **High temperature** (for example `0.9` or higher) flattens it, so less likely tokens are picked more often and outputs vary more.
Example: asking "Name a color" at temperature `0` usually returns the same color every time; at `1.0` you may see blue, green or teal on different calls. Even at low temperature, some models are not fully deterministic, but variation drops sharply.
W: Temperature: it directly controls how random the token selection is, so it is the parameter that determines whether the same prompt produces the same or different outputs.
X: A=Context window size: this is the maximum number of tokens the model can take in and produce in one request, a property of the model. It limits length, not randomness.
C=Stop sequences: these end generation when a chosen string appears, such as `\n\nHuman:`. They cut the output short but do not change which tokens are chosen.
D=Maximum tokens: this caps how long the response can be. Two responses with the same length limit can still differ word for word.
T: Randomness is controlled by sampling parameters, mainly temperature; length limits and stop sequences only control where output ends.

@ Q002467 explain
G: ## Narrowing the candidate tokens
Before sampling, a model can restrict which next tokens are allowed.
- **Top-p (nucleus sampling)** sorts tokens by probability and keeps the smallest set whose probabilities add up to at least `p`. With `top_p = 0.9`, it keeps tokens until their total reaches 90% and samples only from those.
- **Top-k** keeps a fixed number of the most likely tokens, such as `top_k = 50`, no matter how the probability is spread.
Example: if the next-token probabilities are 0.6, 0.2, 0.15 and 0.05, top-p 0.9 keeps the first three (0.6 + 0.2 + 0.15 = 0.95) and drops the last. Top-k 2 would keep only the first two.
Because top-p works on probability mass, the number of candidates changes with how confident the model is: few tokens when it is sure, more when it is uncertain.
W: Top-p (nucleus sampling): it keeps exactly the most probable tokens whose combined probability reaches the threshold, 0.9 in this case.
X: A=Temperature scaling: temperature sharpens or flattens the whole distribution, but it does not cut off candidates at a cumulative probability.
C=Maximum output token limit: this controls how many tokens are generated in total, not which tokens can be chosen at each step.
D=Top-k sampling: top-k keeps a fixed count of tokens, not the smallest set that reaches a probability total, so it does not implement a 0.9 cutoff.
T: Top-p cuts by cumulative probability; top-k cuts by a fixed number of tokens; temperature reshapes the distribution.

@ Q002468 explain
G: ## From sequential models to transformers
Older sequence models such as RNNs and LSTMs read text one token at a time and pass a hidden state forward. Information from early words fades over long sentences, and the step-by-step processing is hard to parallelize.
## Self-attention
A transformer processes all tokens of the input together. For each token, **self-attention** computes how relevant every other token is and builds a representation that mixes in the most relevant ones.
- Example: in "The trophy did not fit in the suitcase because it was too big", attention helps the model link "it" to "trophy".
- Multiple attention heads learn different relationships, such as grammar and meaning.
- Positional encodings tell the model the order of tokens.
Because all positions are handled in parallel, transformers train efficiently on huge datasets, which is why they are the basis of modern foundation models.
W: Self-attention across tokens: it lets the model weigh how each token relates to every other one, so distant words in long, complex sentences stay connected.
X: A=Reads one character at a time and forgets: this describes a model with no memory of context; transformers see the whole input window at once and keep all of it available through attention.
C=Looks up the closest stored sentence: transformers generate new text from learned weights; they do not store and retrieve training sentences like a search index.
D=Hand-written grammar rules: that is the older rule-based approach. Transformers learn language patterns from data instead of following rules written by people.
T: The key idea of transformers is self-attention over the whole sequence, not sequential reading, lookup or hand-written rules.

G: ## How diffusion models create images
A diffusion model is trained by taking real images, adding random noise step by step until only noise is left, and learning to reverse each step.
- To generate, the model starts from random noise and removes noise over many steps.
- A text prompt, turned into an embedding, guides each step so the result matches the description.
Example: the prompt "a red running shoe on a white background" steers denoising until the noise becomes that product image.
## On Amazon Bedrock
Bedrock offers image generation models such as Stability AI models and Amazon Nova Canvas. They support text-to-image as well as editing tasks like inpainting and background removal, depending on the model.
W: Diffusion models: they are the standard model type for text-to-image generation, turning noise into an image guided by the text description.
X: A=K-means clustering: k-means groups existing data points into clusters by similarity. It is unsupervised analysis and cannot create new images.
C=Decision tree classifiers: decision trees predict a label from input features, for example whether a transaction is fraud. They output a class, not an image.
D=Linear regression: linear regression predicts a single number, such as price, from input features. It has no way to produce pixels.
T: Generating images from text is a job for generative diffusion models; clustering, classification and regression only analyze or predict from existing data.

@ Q002470 explain
G: ## What hallucination is
Foundation models generate text by predicting likely next tokens. They are optimized to produce fluent, plausible text, not to check facts. When the model does not have the right information, it can still produce an answer that sounds confident but is false.
- Example: citing "Regulation 2024/771" that does not exist, or inventing a court case or a product feature.
## Reducing it
- **Retrieval-augmented generation (RAG)**: give the model trusted documents, for example with Amazon Bedrock Knowledge Bases, and ask it to answer only from them.
- **Grounding checks**: Amazon Bedrock Guardrails contextual grounding checks can flag responses that are not supported by the source content.
- **Prompting and review**: ask for sources, allow "I don't know", and have people verify high-stakes outputs.
W: Hallucination: a fabricated regulation number stated with confidence is the typical example of a model generating plausible but false content.
X: B=Concept drift: drift is when the relationship between inputs and outcomes changes over time, so a trained model's accuracy slowly drops. It does not describe inventing a non-existent fact.
C=Underfitting: underfitting means a model is too simple to learn patterns in its training data and performs poorly overall, not that it makes up specific details.
D=Data leakage: leakage is when information from the test set or future data enters training, giving misleadingly high evaluation scores. It is not about fabricated outputs.
T: Confident but invented facts are hallucinations; reduce them with grounding (RAG, grounding checks) and human verification.

@ Q002471 explain
G: ## Why generative models are not calculators
A foundation model produces text by sampling tokens from probabilities. It has learned patterns of arithmetic, but it does not execute exact calculations.
- Multi-step arithmetic on large numbers can go wrong, for example a digit carried incorrectly in a total.
- With sampling settings above zero, the same prompt can return different answers, so results may not be reproducible.
## A better design
Let the model handle language and let deterministic code handle numbers.
- The model extracts values or decides which calculation to run.
- A tool, such as a Lambda function called by a Bedrock agent or a code interpreter, computes the exact result.
- The model then explains the result in plain language.
Example: the model reads a request for quarterly revenue, calls a function that sums ledger entries, and reports the exact figure returned.
W: Probabilistic outputs and arithmetic errors: exact, reproducible financial calculations need deterministic results, and a generative model cannot guarantee them on its own.
X: A=Numbers must become images: models read numbers as text tokens directly; converting statements to images would add a step, not solve a real limitation.
C=Models always refuse financial tasks: there is no universal built-in refusal of financial work. Models commonly summarize and analyze financial text; the problem is exactness, not refusal.
D=A year of training on company data: using a foundation model needs no training at all, and customization such as fine-tuning takes far less than a year. Training would not make arithmetic exact anyway.
T: Generative AI is probabilistic, so exact and reproducible numbers should come from deterministic tools that the model calls, not from generated text.

G: ## Where generative AI fits
Generative AI is strongest when many acceptable answers exist and a person can review the result.
- Good fits: first drafts of emails and marketing copy, summaries, brainstorming, rewriting for tone, code suggestions.
- Poor fits: tasks where a single exact answer is required, where results must be stored reliably, or where a wrong answer creates legal or security risk.
## Why drafts are a good first pilot
- Output quality is easy to judge, and people edit before anything is sent.
- Mistakes are cheap to catch and fix.
- Value appears quickly as time saved on writing.
Example: a marketer gives a three-line product brief and gets a draft email in seconds, then adjusts the wording and checks the facts before sending.
W: Drafting a marketing email: it is creative, open-ended work where a reviewed draft is valuable and small errors are caught before use, the classic generative AI strength.
X: B=Exact legally binding tax: tax amounts need exact, repeatable calculation and audit trails. A probabilistic model may make arithmetic errors and cannot guarantee identical results.
C=Transactional database of record: a system of record needs guaranteed, consistent storage and retrieval (ACID transactions). A model generates text; it does not store data reliably.
D=Access control decisions: authorization must be deterministic and resistant to manipulation. A model could be tricked by prompt injection or make inconsistent decisions.
T: Pilot generative AI on reviewable drafts and creative content; keep exact, authoritative and security-critical decisions in deterministic systems.

G: ## Bedrock inference options
- **On-Demand**: pay per input and output token with no commitment. Capacity is shared, so requests are subject to account quotas and can be throttled at high volume.
- **Provisioned Throughput**: buy a number of model units for a specific model. Each unit gives a set amount of throughput, dedicated to you, billed by the hour. Commitment terms of 1 month or 6 months lower the hourly rate, and a no-commitment option is available in some cases, such as for customized models. It is also how you serve many customized models.
- **Batch inference**: submit a file of many prompts and collect results later, at a lower price, for offline work.
## When to choose Provisioned Throughput
A steady, predictable, high-volume workload keeps the reserved capacity busy, so the hourly cost is used efficiently and the app gets consistent throughput instead of risking throttling.
Example: a support chatbot with constant traffic all day buys model units sized to its peak rate.
W: Provisioned Throughput: it reserves dedicated model capacity, which gives the guaranteed throughput a steady high-volume workload needs.
X: B=On-Demand pricing: it is flexible and pay-per-token, but capacity is shared and limited by quotas, so throughput is not guaranteed at high volume.
C=Batch inference: batch jobs run asynchronously and return results later. That suits offline processing, not live traffic that needs guaranteed throughput.
D=Model evaluation jobs: these compare model quality with metrics or human reviewers. They are a testing tool and do not serve production requests.
T: Steady high volume with guaranteed capacity means Provisioned Throughput; On-Demand is flexible but shared, and batch is for offline work.

G: ## Batch inference in Amazon Bedrock
Batch inference lets you process many prompts in one asynchronous job instead of calling the model once per request.
- You put the requests in JSONL files in Amazon S3, one record per prompt.
- You create a batch inference job that points to the input location, an output location and the model.
- Bedrock processes the records and writes the responses to S3 when done.
For supported models, batch inference is priced lower than On-Demand invocation (roughly half the On-Demand token price, approximate and model-dependent), and you do not have to build retry and throttling logic for hundreds of thousands of calls.
Example: at 8 PM a job reads 500,000 document prompts from `s3://docs/batch/input/`, and by morning the summaries are in `s3://docs/batch/output/`.
W: Batch inference: it is built for large, non-urgent workloads and costs less than real-time calls, so it is the most cost-effective way to summarize 500,000 documents overnight.
X: A=Continued pre-training: this further trains a model on unlabeled domain data to create a custom model. It does not run inference or produce the summaries.
C=On-Demand real-time invocation: it would work, but you pay the standard per-token price and must handle quotas and throttling for 500,000 calls, when real-time answers are not needed.
D=Provisioned Throughput: it reserves capacity by the hour for steady real-time traffic. For a one-night job with no latency need, it is more expensive than a discounted batch job.
T: Large jobs that can wait go to batch inference; real-time options cost more when nobody needs the answer immediately.

G: ## What makes a model a foundation model
A foundation model is a large model pre-trained on broad, mostly unlabeled data, such as text, code and images from many sources. Pre-training teaches general knowledge and skills that serve as a base for many other tasks.
## Adapting one base to many tasks
- **Prompting**: give instructions and examples at request time (zero-shot or few-shot).
- **Retrieval-augmented generation**: supply relevant documents with the prompt.
- **Fine-tuning or continued pre-training**: adjust the model with your own data for a domain or task.
Example: the same model can summarize contracts, write product descriptions, classify support tickets and answer questions, with no separate model trained for each job.
The name comes from this role as a foundation that many applications are built on.
W: Pre-trained on broad data and adaptable: that is the definition of a foundation model, a general base reused for many downstream tasks through prompting or customization.
X: B=Retrained from scratch per task: the point of a foundation model is the opposite. It is reused as is or lightly adapted, which avoids costly training for every new task.
C=Built for construction engineering: "foundation" describes the model's role as a base for other applications, not any construction industry use.
D=Special foundation tier in one Region: Bedrock has no "foundation tier" of infrastructure, and its models are offered in many AWS Regions.
T: Foundation models are broad pre-trained bases adapted to many tasks, not models retrained from scratch for each use.
