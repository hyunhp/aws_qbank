G: ## Two phases of the ML lifecycle
- **Training** is where the model learns. An algorithm reads historical examples (for example 100,000 past transactions labeled fraud or not fraud) and adjusts its internal parameters until its predictions match the labels well. Training is expensive and happens occasionally.
- **Inference** is where the trained model is used. New data goes in, a prediction comes out, and the parameters do not change.
## Real-time versus batch inference
- **Real-time** inference answers one request at a time with low latency, such as scoring a card payment while the customer waits. On AWS this is a SageMaker AI real-time endpoint or a serverless endpoint.
- **Batch** inference scores a large dataset offline, such as ranking every customer's churn risk overnight. On AWS this is SageMaker batch transform, or batch inference jobs in Amazon Bedrock.
The same model can serve both styles; the choice depends on how fast the answer is needed and how much data arrives at once.
W: C=Real-time or batch inference: the business need decides the mode. Latency-sensitive requests use an online endpoint, while large offline datasets are scored in batch jobs that are cheaper per prediction.
E=Training builds, inference predicts: training learns parameters from data once or periodically; inference applies those fixed parameters to new inputs to produce predictions.
X: A=Inference retrains the model: inference only reads the learned parameters. Retraining is a separate, deliberate step, usually triggered by new labeled data or detected drift, not by each request.
B=Training for each prediction: retraining per prediction would be slow and costly and is never required; a model is trained once and then serves many predictions until it is retrained on a schedule or when quality drops.
D=Batch only for images: batch inference works for any data type, including tabular scoring, text classification and embeddings generation, not only image classification.
T: Training creates the model and inference uses it without changing it; inference can run in real time or in batch depending on latency and volume needs.

G: ## What MLOps adds to machine learning
MLOps applies DevOps ideas to ML so that models reach production reliably and stay healthy there. Unlike ordinary code, a model depends on three things that all change: code, data and trained weights.
## Core practices
- **Versioning**: record which dataset, code commit, hyperparameters and model artifact produced each version, so you can reproduce a result or roll back. SageMaker Model Registry stores model versions with their metadata and approval status.
- **Automated pipelines**: steps such as data preparation, training, evaluation and deployment run as a repeatable pipeline (for example SageMaker Pipelines) instead of by hand, often triggered by new data or a schedule.
- **Monitoring**: after deployment, track data drift and prediction quality (for example SageMaker Model Monitor) and trigger retraining when quality drops.
Example: a demand forecast model is retrained weekly by a pipeline, registered as version 14, compared against version 13 and promoted only if it scores better.
W: D=Version models and data: tying each model to the exact data and code that produced it makes results reproducible and auditable, and allows a quick rollback to a known-good version.
E=Automated pipelines: pipelines make retraining and deployment repeatable and consistent, remove manual errors and let models be refreshed as data changes.
X: A=Skip monitoring after testing: real-world data drifts away from training data, so a model that passed testing can silently degrade. Continuous monitoring is a core MLOps practice.
B=Manual file copying: copying files by hand is error-prone, leaves no audit trail and cannot be reliably repeated or rolled back, which is the opposite of automated deployment.
C=Delete earlier models: removing old versions makes rollback and reproducibility impossible and breaks audit requirements; registries keep version history on purpose.
T: MLOps means reproducible, versioned models delivered through automated pipelines and watched in production, not one-off manual deployments.

G: ## What bias detection needs
Bias can enter at two points:
- **In the data**, before training: for example, one age group has far fewer approved loans in the labels, or is barely represented at all.
- **In the predictions**, after training: the model's approval rate or error rate differs strongly between groups.
## SageMaker Clarify
Amazon SageMaker Clarify computes bias metrics for both stages. You name a sensitive attribute (the facet, such as gender or age group) and Clarify reports metrics like **class imbalance** and **difference in proportions of labels** for the data, and differences in positive prediction rates or accuracy for the trained model.
- Clarify also produces **feature attributions** that explain which inputs drove predictions.
- It can run as a processing job, inside SageMaker Pipelines or with Model Monitor to watch bias drift in production.
W: SageMaker Clarify: it measures pre-training bias in datasets and post-training bias in model predictions across demographic groups, and adds explainability reports.
X: A=SageMaker Debugger: Debugger captures tensors and system metrics during training to catch problems such as vanishing gradients, overfitting or poor GPU usage; it does not compare outcomes between demographic groups.
B=SageMaker Studio Lab: Studio Lab is a free, no-AWS-account notebook environment for learning and experimenting; it provides compute for notebooks, not bias metrics.
C=SageMaker Neo: Neo compiles trained models to run faster on specific cloud or edge hardware; it optimizes performance and says nothing about fairness.
T: Bias across groups in data and predictions is measured with Clarify; Debugger watches training health and Neo optimizes models for hardware.

Guardrails are a configurable safety layer you attach to model calls in Amazon Bedrock (and can also apply to other models through the `ApplyGuardrail` API). A guardrail can include several policies:

G: ## Why representation matters
A model learns patterns from the examples it sees. If a group makes up only 2 percent of the training data, the model has few examples to learn how features relate to outcomes for that group.
- The model tends to optimize for the majority, so overall accuracy can look high while error rates for the minority group are much worse.
- Historical data can also carry past unfair decisions, which the model then repeats.
## What to do about it
- Measure: compare data balance and model outcomes by group, for example with SageMaker Clarify metrics such as class imbalance and differences in approval rates.
- Fix the data: collect more representative records, or rebalance with resampling or weighting.
- Keep checking after deployment, because the population served can change.
In lending, unequal treatment can also create regulatory and reputational risk, which is why fairness is a core responsible AI dimension.
W: Worse or unfair outcomes for the group: with too few examples, the model learns that group's patterns poorly and can give less accurate or systematically biased loan decisions, a fairness concern.
X: A=Faster training: fewer records for one group barely changes training time, and speed is not a responsible AI concern; the risk is the quality of predictions for that group.
C=Model self-corrects imbalance: standard training minimizes overall error and has no built-in goal of fairness; the imbalance persists unless people measure it and rebalance data or adjust the model.
D=Cannot be deployed: data imbalance has no effect on where a model can be deployed; AWS does not block deployment based on dataset composition.
T: Underrepresentation leads to less accurate or unfair outcomes for that group; it does not fix itself and must be measured and corrected.

G: ## Feature attribution
Feature attribution assigns each input feature a number that shows how much it pushed a prediction up or down.
## SHAP in SageMaker Clarify
SageMaker Clarify uses **SHAP** (SHapley Additive exPlanations), based on Shapley values from game theory. Features are treated like players sharing a payout: the prediction's difference from a baseline is split fairly among the features.
- Example: baseline default probability is 10 percent and the model predicts 35 percent for one applicant. SHAP might show `debt_ratio` +18 points, `late_payments` +9 points and `income` -2 points, which add up to the 25-point difference.
- Averaging absolute SHAP values over many rows gives a global view of which features matter most.
Clarify estimates these values with Kernel SHAP, so it works with any model treated as a black box.
W: SHAP values: Clarify computes Shapley-value based attributions that split each prediction among the input features, giving both per-prediction and global feature importance.
X: A=Dropout layers: dropout randomly disables neurons during neural network training to reduce overfitting; it is a regularization technique and produces no explanation of predictions.
B=Gradient boosting: gradient boosting (for example XGBoost) is a family of algorithms that build models from many trees; it is a way to make predictions, not a method to attribute them.
D=K-means clustering: k-means groups unlabeled data points into clusters by similarity; it is unsupervised learning, not feature attribution.
T: Clarify explains predictions with SHAP; dropout, boosting and k-means are ways to train or build models.

G: ## The interpretability versus accuracy trade-off
- **Interpretable models** such as linear regression or a small decision tree let a person follow how inputs lead to the output.
- **Complex models** such as deep neural networks or large ensembles may be slightly more accurate but are harder to explain; post-hoc tools like SHAP give approximations of their behavior.
## How to decide
Start from the requirement, not from the metric. In healthcare, clinicians must be able to check a recommendation against their own judgment, spot errors and justify decisions to patients.
Example: model one has 91 percent accuracy and shows that a risk score rose because of blood pressure and age; model two has 92 percent accuracy but no clear reasoning. With a 1-point gap and a hard need for understanding, the interpretable model is the responsible choice.
If the accuracy gap were large, teams might revisit the trade-off, but a stated requirement that every recommendation be understood should not be dropped.
W: The interpretable model: understanding each recommendation is a stated requirement and the accuracy difference is small, so the model that clinicians can follow and verify fits.
X: A=Complex model with invented explanations: explanations written after the fact without reflecting how the model actually decided are misleading, and they undermine trust and safety instead of providing real interpretability.
B=Accuracy always outweighs interpretability: this is not a rule. When a requirement such as clinician understanding exists and the gain is slight, ignoring it trades a small metric gain for unverifiable, harder-to-trust recommendations.
C=No model for healthcare: ML is used in healthcare with safeguards such as human oversight and interpretable outputs; a blanket ban ignores that both candidate models could be used responsibly.
T: When stakeholders must understand each decision and the accuracy gap is small, choose the interpretable model rather than the slightly more accurate black box.

G: ## Where generative AI energy goes
Energy use scales roughly with the compute each request needs and the number of requests. Bigger models have more parameters to compute for every token, and training from scratch consumes far more compute than inference or light fine-tuning.
## Practical levers
- **Right-size the model**: if a small model answers an FAQ just as well as a very large one, each request uses much less compute. Techniques like distillation and quantization shrink models further.
- **Efficient hardware**: purpose-built chips such as AWS Inferentia (inference) and AWS Trainium (training) are designed to deliver more performance per watt than general-purpose GPU instances for supported workloads.
- **Avoid waste**: cache repeated answers, batch non-urgent work and reuse existing models through fine-tuning instead of full retraining.
These choices also usually lower cost, so sustainability and cost goals tend to align.
W: A=Smallest adequate model: a model that meets quality needs with fewer parameters needs less compute and therefore less energy per request.
E=Energy-efficient accelerators: Inferentia is built for high-throughput inference with better performance per watt, reducing energy for the same workload.
X: B=Duplicate inference on every request: running each request twice roughly doubles compute and energy with no quality requirement behind it; safety is handled with guardrails and evaluation, not duplication.
C=Always the largest model: larger models use more compute per token, and there is no guarantee they reduce retries enough to offset that; for a task a small model handles, it simply wastes energy.
D=Retrain from scratch for small updates: full retraining is the most compute-intensive step; small updates are handled with fine-tuning, retrieval of new data or prompt changes.
T: Reduce environmental impact by using the smallest model that meets quality needs on efficient hardware, not by adding more compute.

Generative models learn from very large datasets that can include copyrighted works. Most outputs are new combinations, but a model can sometimes reproduce long passages close to its training data, a behavior often called memorization or regurgitation.

- Filters or similarity checks against known sources, and prompts that ask for original wording.

D=Underfitting: an underfit model has failed to learn patterns and produces poor, generic output; closely reproducing source text points more toward memorization, and in any case the concern named here is legal, not a training-fit issue.

G: ## What makes a training dataset responsible
Two qualities matter most for a model that serves many kinds of customers.

Large language models generate text by predicting likely next tokens. That makes them fluent, but fluency is not the same as correctness: a model can produce a confident, well-written answer that is wrong. This is called a **hallucination**.

- Limit scope: provide general information and route diagnosis or treatment questions to clinicians.
- Keep human oversight for anything that affects care decisions, and add clear disclaimers.
- Evaluate the system on realistic medical questions before and after launch.
W: Plausible but incorrect advice: hallucinated medical guidance can sound authoritative and directly harm users, which makes it the most serious limitation for customer-facing medical use.
X: B=Special desktop software: generative AI applications are usually delivered through web or mobile interfaces and APIs; no special desktop install is inherently required.
C=Too slow on mobile: latency can be tuned with model choice and streaming responses, and even if it were slow, delay is far less serious than harmful advice.
D=English only: many foundation models support multiple languages; language coverage is a product choice, not the core risk in medical advice.
T: In medical use, the gravest limitation is confident but wrong output that can harm people; performance and delivery issues are secondary.

G: ## Predictive ML versus generative AI
- **Traditional predictive ML** maps an input to a label or number. Examples: a classifier outputs "fraud" or "not fraud", a regression model predicts next month's sales of 12,400 units, a recommender outputs a ranked list of product IDs.
- **Generative AI** produces new content that did not exist before: text, images, audio or code. Example: given "write a product description for a waterproof hiking boot", a foundation model writes a new paragraph.
## What they share
- Both learn from data. Generative foundation models are pre-trained on huge, mostly unlabeled datasets using self-supervised learning.
- Both run in the cloud, on premises or at the edge, depending on the model size and hardware.

G: ## Limitations to plan around
Foundation models are powerful, but several built-in traits affect how businesses use them.
- **Knowledge cutoff**: a model knows only what was in its training data, which ends at a certain date. Ask about last week's price change and it may answer with outdated information or guess. The usual fix is retrieval augmented generation (RAG), such as Amazon Bedrock Knowledge Bases, which supplies current documents at request time.
- **Non-deterministic output**: models sample the next token from probabilities, so the same prompt can produce different wording or even different answers. Lowering `temperature` and `top_p` makes responses more consistent, and structured output formats help downstream processing.
## Other traits to know
- Hallucinations and bias are risks to manage, not guarantees in every response.
- Models process whole token sequences within a context window and do not need retraining per request.
W: D=Training cutoff: models lack information after their training data ends, so businesses must supply current data through RAG or tools when freshness matters.
E=Variable outputs: sampling makes responses vary for the same prompt, so applications must tolerate variation or reduce it with inference parameters and validation.
X: A=One word at a time input: models read the whole prompt as a sequence of tokens within a large context window, often many thousands of tokens; they are not limited to one word.
B=Retrain before every request: inference uses fixed trained weights; retraining is occasional and never required per request.
C=Guaranteed bias every response: bias is a real risk to test and mitigate, but it does not appear in every single response; this overstates the limitation.
T: Plan for a knowledge cutoff (use RAG for fresh data) and for variable outputs (tune temperature and validate), not for per-request retraining.
