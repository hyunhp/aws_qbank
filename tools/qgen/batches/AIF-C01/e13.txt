G: ## Who may read an S3 bucket
Access to Amazon S3 is decided by policies. Two kinds matter here:
- **Identity-based policies** are attached to an IAM user or role and say what that identity may do.
- A **bucket policy** is a resource-based policy attached to the bucket itself. It names the principals (accounts, roles, users) that may act on the bucket and its objects.
## Locking a bucket to one role
Because the bucket policy lives on the bucket, it applies to every request, whoever sends it. A common pattern for a RAG or document-retrieval app:
- Allow `s3:GetObject` and `s3:ListBucket` for the app's role, for example `arn:aws:iam::111122223333:role/doc-retriever`.
- Add a `Deny` for all other principals using a condition such as `aws:PrincipalArn` not equal to that role (usually with an exception for administrators).
- Keep S3 Block Public Access on so no public grant can slip in.
Now even an IAM user with broad S3 permissions in the same account cannot read the documents, because an explicit deny in the bucket policy always wins.
W: Bucket policy for the app's role: it is attached to the bucket and names the allowed principal, so it enforces "only this role may read" at the bucket level regardless of what permissions other identities carry.
X: A=Event notification: notifications send a message to Lambda, SQS, SNS or EventBridge when objects are created or deleted. They react to changes; they never allow or block a read request.
B=Lifecycle rule: lifecycle rules move objects to cheaper storage classes or expire them over time. They manage storage cost and retention, not which principal can call `GetObject`.
C=Glacier Flexible Retrieval: changing the storage class only changes price and retrieval time (objects must be restored before reading). Anyone with permission can still restore and read them, so it is not an access control.
T: Access to a bucket is controlled by policies such as a bucket policy naming the allowed role; notifications, lifecycle rules and storage classes only affect events, retention and cost.

G: ## Human oversight of AI decisions
Even a good content-moderation model makes mistakes: it may remove harmless posts (false positives) or miss harmful ones (false negatives). **Human oversight** means people check and can correct what the model decides.
## Sampling for review
Reviewing every decision is usually too expensive, so teams send a subset to people:
- A random sample (for example, 2% of all decisions) to measure overall quality.
- Low-confidence predictions, where the model is most likely to be wrong.
- High-impact cases, such as account bans.
Reviewers confirm or overturn the decision. Their corrections fix individual errors, show where the model is weak, and can become labeled data for retraining.
On AWS, **Amazon Augmented AI (A2I)** provides this workflow: you define conditions (for example, confidence below 0.8 or a random sample) that route predictions to a human review task and store the results in S3.
W: Human oversight: sampling decisions for people to check catches and corrects model errors, measures real-world accuracy, and feeds corrections back into improving the model.
X: A=Data sharding: sharding splits data across storage partitions so reads and writes scale. It is a storage performance technique and involves no human judgment of model decisions.
B=Model distillation: distillation trains a smaller "student" model to imitate a larger one, lowering inference cost. It changes the model, but nobody checks individual moderation decisions.
D=Token caching: caching reuses computed prompt tokens or responses to cut latency and cost. It speeds up answers but does nothing to find or fix wrong decisions.
T: Having people review a sample of a model's decisions is human oversight, a responsible AI practice, not a performance or cost optimization.

G: ## Reducing harmful output before launch
Generative models can produce toxic, hateful or unsafe text, especially when users try to provoke them. Two complementary controls are standard:
- **Adversarial testing (red teaming)**: before launch, testers deliberately write prompts meant to make the model misbehave, such as role-play tricks, insults to repeat, or jailbreak attempts. Failures show where prompts, filters or the model need work.
- **Content filters**: at run time, both user input and model output are checked against harmful categories (hate, insults, sexual, violence, misconduct, prompt attacks) and blocked above a chosen strength.
## On AWS
**Amazon Bedrock Guardrails** provides configurable content filters, denied topics, word filters and sensitive-information filters, and can be applied to Bedrock models and, through the `ApplyGuardrail` API, to other models. **Amazon Bedrock model evaluation** can help test models against prompt datasets, including toxicity-focused ones.
Testing finds the weak spots; filters catch what still gets through.
W: B=Adversarial testing: red-teaming with hostile prompts before launch reveals how the model can be pushed into toxic output, so the team can fix prompts, filters or model choice first.
E=Content filters: filters for harmful categories block toxic inputs and outputs at run time, catching cases that testing missed.
X: A=Raise temperature: higher temperature makes token choice more random. That does not make outputs safer and can make unexpected, off-policy text more likely.
C=Remove system instructions: system instructions set tone, role and rules such as "do not use offensive language". Removing them takes away one of the ways to steer the model toward safe behavior.
D=Rely on user complaints: complaints arrive only after users have already seen harmful content, so the harm has happened and trust is lost; pre-launch testing is what prevents it.
T: Reduce toxicity by red-teaming before launch and filtering harmful categories at run time; randomness, fewer instructions and waiting for complaints all make things worse.

G: ## Dimensions of responsible AI
AWS describes responsible AI through several dimensions, including fairness, explainability, privacy and security, safety, **controllability**, veracity and robustness, governance, and transparency.
## What controllability means
Controllability is having mechanisms to **monitor and steer** an AI system's behavior. Humans stay in charge:
- Dashboards and alerts show what the system is doing.
- Operators can override decisions, change configuration or limits, or route cases to human review.
- There is a way to pause or shut the system down, for example a kill switch that disables an agent's actions.
Example: an AI agent that issues refunds has a limit above which a person must approve, and support staff can turn the agent off instantly if it misbehaves.
It is easy to confuse this with interpretability. Interpretability helps you **understand** why the model produced an output; controllability lets you **act** on the system.
W: Controllability: it is the dimension about humans being able to monitor the system and intervene, override or stop it when needed, exactly what the team describes.
X: B=Interpretability: interpretability is about understanding how a model reaches its outputs (for example, which features mattered). Understanding a decision does not by itself give anyone a way to intervene or stop the system.
C=Portability: portability is the ability to move a model or workload between environments or platforms. It is an engineering property, not a responsible AI dimension about human control.
D=Efficiency: efficiency is about using compute, time and cost well. A very efficient system can still be impossible to stop or steer.
T: Being able to monitor, intervene and stop an AI system is controllability; being able to understand its outputs is interpretability.

G: ## Explainability for end users
Explainability means people can understand why a model produced a particular output. What counts as a good explanation depends on the audience:
- A data scientist may want feature attributions, such as SHAP values from Amazon SageMaker Clarify.
- A non-technical user needs a short, plain-language reason tied to their own situation.
## Turning model factors into plain language
A recommendation model typically weighs signals such as past purchases, viewed items and what similar customers liked. The app can surface the top one or two factors:
- "Recommended because you bought a tent and hiking boots."
- "Popular with customers who watched the same series."
This helps users judge whether to trust the recommendation, correct wrong assumptions, and feel the system is not arbitrary. Internal details such as architecture or code do not answer the user's real question: "why me, why this?"
W: Main factors in plain language: telling users which of their own signals drove the recommendation, in everyday words, directly answers why it was made and is understandable without technical knowledge.
X: A=Parameter count and training time: these describe the model's size and cost, not the reasons behind any single recommendation. They mean nothing to a typical user.
B=Confidence score alone: a number such as 87% says how sure the model is, but not why it chose this item, so the user still has no reason to trust or question it.
C=Full source code: code is unreadable to non-technical users, and the behavior of a trained model lives largely in learned weights and data, so the code does not reveal why a particular item was recommended.
T: Explain an individual decision to non-technical users with its main factors in plain language, not with model statistics, bare scores or code.

G: ## Fairness in automated hiring
A hiring model can discriminate even if it never sees a protected attribute directly, because other features (school, postcode, career gaps) can act as proxies. Fairness has to be **measured**, not assumed.
## Before and after deployment
- **Before launch**: compare outcomes across groups, for example selection rate, false-negative rate or score distribution by gender or age band. Amazon SageMaker Clarify can compute pre-training bias metrics on the data and post-training metrics on predictions, such as difference in positive proportions.
- **After launch**: keep monitoring, because applicants, job types and data change. SageMaker Clarify integrates with SageMaker Model Monitor to track bias drift over time.
- **Investigate** any disparity: check the data, features and thresholds, fix the cause, and re-measure.
Example: if the model advances 30% of applicants in one group but 12% in another with similar qualifications, that gap must be explained or corrected.
W: Measure outcomes by group and investigate: comparing results across applicant groups before launch and continuing to monitor afterward is how discrimination is detected and addressed.
X: A=Remove human review: consistency does not equal fairness; a model can be consistently biased. Removing review also removes a check that could catch discriminatory outcomes.
B=Faster response time: latency affects user experience, but a fast model can discriminate just as much as a slow one.
D=More applicants per day: throughput is an operational metric. Processing more applicants does not reveal or reduce unequal treatment between groups.
T: Fairness is ensured by measuring outcomes across groups before and after deployment and investigating gaps, not by speed, throughput or removing oversight.

G: ## Interpretability versus accuracy
Models range from simple to complex:
- **Interpretable models** such as linear regression, logistic regression or a shallow decision tree have logic a person can follow: "each extra year of income history lowers risk by X".
- **Complex models** such as deep neural networks or large gradient-boosted ensembles capture subtle, non-linear patterns and often achieve higher accuracy on hard tasks, but their internal reasoning is hard to inspect.
## The trade-off
Choosing a simpler model can mean giving up some accuracy in exchange for explanations you can defend. How much depends on the task; for some tabular problems a simple model is nearly as good, while for images or language complex models are far ahead.
Post-hoc tools (for example SHAP attributions in Amazon SageMaker Clarify) can partly explain complex models, but they approximate rather than expose the full logic.
Regulated uses such as credit decisions often favor interpretable models or require strong explanations.
W: Interpretability may cost some accuracy: simpler, more transparent models are easier to explain but can be less accurate than complex ones, so teams balance the two for each use case.
X: A=No relationship to complexity: complexity often matters; more flexible models can fit patterns simple ones cannot, though they can also overfit. Saying there is never any relationship is false.
C=Interpretable models always most accurate: on many tasks, especially images, audio and text, complex models clearly outperform simple interpretable ones.
D=Transparent models banned for regulated decisions: the opposite is true; regulators and auditors often prefer transparent models because decisions can be explained to applicants.
T: Interpretable models can trade some accuracy for explainability, and the right balance depends on the use case and its regulatory needs.

G: ## How a model reads a prompt
A language model does not see "meaning" directly. The prompt is split into **tokens** (words or word pieces), and the model predicts each output token based on all the tokens before it.
## Why small edits matter
- Changing "Summarize" to "Briefly summarize", or reordering sentences, changes the token sequence, so the model is conditioned on a different context.
- A different context shifts the probability of every next token, and once the first generated tokens differ, the rest of the answer can diverge further.
- Sampling settings such as temperature add randomness on top, but even with low temperature, different input tokens can yield a different answer.
The model's weights did not change; only its input did. This is why prompt engineering works, and why teams version and test prompts like code.
Example: "List risks" may return bullets, while "What are the risks?" may return a paragraph.
W: Output depends on exact tokens: the model generates from the specific token sequence it receives, so a slight wording change alters its context and can change the answer.
X: B=Region switch: the Region is set by the endpoint or SDK configuration (and, with cross-Region inference, by the inference profile the app chooses). The wording of a prompt never decides where a request runs.
C=Automatic retraining: sending or saving a prompt does not update model weights. Retraining or fine-tuning is a separate, explicit job.
D=Only length matters: models are highly sensitive to wording, order and examples in the prompt; two prompts of equal length with different words can produce very different outputs.
T: Models condition on the exact tokens in the prompt, so rewording changes outputs without any retraining or infrastructure change.

Coding assistants such as **Amazon Q Developer** can write functions, tests and whole features quickly. But generated code can:
- contain logic bugs or handle edge cases incorrectly,

C=Merge directly to production: skipping review and staging means any bug or vulnerability in the generated code reaches users immediately.
T: AI-generated code goes through the same human review and automated testing as any other code before it is merged.

G: ## When generative AI is a poor fit
Generative models are probabilistic: they produce likely text, not guaranteed-correct text. They can hallucinate, and the same prompt can give different answers. This makes them strong for drafting, summarizing and brainstorming, but weak where results must be exact.
## Warning signs
- **Exact, auditable results required**: calculating tax, applying a pricing rule, or producing regulatory figures. Deterministic code or rules engines give the same answer every time and can be audited step by step.
- **High cost of error with no review**: automatically executing trades, approving medical doses, or sending legal notices without anyone checking. A single hallucination could be very costly.
## Good fits
Tasks where variation is useful or where a person checks the result: marketing variations, first drafts, and summaries for someone to read.
Many teams combine both: generative AI drafts, deterministic systems compute, and people approve.
W: C=High-cost errors without feasible review: when a mistake is expensive and nobody can check the output, a model that can hallucinate is an unacceptable risk.
E=Exact, auditable results: generative output is non-deterministic and cannot guarantee the same exact answer every time, so rule-based or conventional software is the better tool.
X: A=Many creative variations: producing diverse variations is a core strength of generative AI, so this is a reason to use it, not avoid it.
B=Drafting text people review: human review catches errors, so drafting is a classic good fit that saves time with manageable risk.
D=Summarizing documents for review: summarization is a well-established generative AI use case, and the reviewer can check the summary against the source.
T: Avoid generative AI where results must be exact and auditable or where costly errors cannot be reviewed; use it for creative, draft and summary work people check.

@ Q002641 explain
G: ## How diffusion models generate images
A **diffusion model** learns to reverse a noising process:
- **Training**: take real images, add random noise step by step until they become pure noise, and train a neural network to predict and remove the noise at each step.
- **Generation**: start from a random noise image and apply the learned denoising step many times. Each step makes the image a little clearer.
- **Text guidance**: a text encoder turns the prompt (for example, "a red bicycle on a beach at sunset") into an embedding that conditions every denoising step, so the image moves toward what the prompt describes.
Stable Diffusion models are an example of this family, and are available through Amazon Bedrock.
## Other generative families for comparison
- GANs pit a generator against a discriminator.
- Transformers generate sequences such as text token by token.
W: Diffusion model: iteratively denoising a random starting image under the guidance of a text prompt is exactly how diffusion models generate images.
X: A=Logistic model: logistic regression outputs a probability for a class (for example, spam or not). It classifies inputs and cannot generate images.
B=Recurrent network: RNNs process sequences one step at a time using a hidden state, typically for text or time series. They do not work by denoising an image.
C=Random forest: a random forest is an ensemble of decision trees for classification or regression on tabular data. It predicts labels or values, not new images.
T: Image generation by repeatedly removing noise from random input under prompt guidance is a diffusion model; logistic, RNN and random forest models do not work that way.

@ Q002643 explain
G: ## How a RAG knowledge base stays current
In retrieval-augmented generation (RAG), answers are grounded in documents retrieved from a vector index, not in the model's training data.
With **Amazon Bedrock Knowledge Bases**:
- A data source (for example an S3 bucket) holds the documents.
- An **ingestion job** (sync) reads the documents, splits them into chunks, creates embeddings and writes them to the vector store.
- At query time the knowledge base retrieves the most similar chunks and passes them to the model.
## Why answers go stale
The vector store is a snapshot from the last sync. If a policy PDF in S3 is updated but no sync runs, retrieval still returns chunks from the old version, and the model faithfully repeats outdated content.
The fix: run a sync (the `StartIngestionJob` API) after changes, and automate it, for example on a schedule or triggered by S3 events. Syncs are incremental, processing added, changed and deleted files.
W: Knowledge base not re-synced: the vector index only reflects documents as of the last ingestion job, so without a sync the assistant keeps retrieving and citing the old content.
X: B=Temperature too low: temperature controls randomness in wording. It has no effect on which document versions are retrieved, so it cannot cause outdated facts.
C=IAM role too broad: overly broad permissions are a security risk, but they do not make the index stale; the assistant can read the new documents, it just has not indexed them.
D=Too many embedding dimensions: the embedding model fixes the dimension, and it affects storage and similarity quality, not freshness. Old answers come from old vectors, whatever their size.
T: RAG answers reflect the last knowledge base sync, so re-sync (ideally automatically) whenever source documents change.

G: ## Personal data in fine-tuning data
Customer chat logs often contain names, emails, phone numbers, addresses, account or card numbers. If such text is used to fine-tune a model, the model can **memorize** it and later reproduce it to other users, which is a privacy and compliance failure.
## Preparing the data
- **Detect** personal data (PII). **Amazon Comprehend** can detect PII entities in text and redact them; Amazon Macie can find sensitive data in S3.
- **Remove or mask** it, for example replace "Call Jane Doe at 555-0100" with "Call [NAME] at [PHONE]", so the model learns the conversation pattern without the personal details.
- Keep only data you are permitted to use for training, and restrict access to raw logs.
This step must happen **before** training: once personal data is in the model's weights, it cannot be reliably removed without retraining.
W: Remove or mask personal data: stripping or masking PII before training prevents the model from memorizing it and exposing it to other users later.
X: A=Duplicate every record: duplication adds no new information and makes the model over-weight repeated examples, which even increases memorization risk. It does nothing for privacy.
B=Keep only top-rated chats: filtering by rating can skew the model toward certain topics or customers, and the kept chats still contain personal data.
D=Translate into one language: translation may be unnecessary for the use case, can lose nuance, and leaves the names and numbers in the text, so it does not address privacy.
T: Before fine-tuning on customer data, remove or mask personal data so the model cannot memorize and reveal it.

G: ## Fairness is not a one-time check
A job-ad recommender can pass fairness tests at launch and still become unfair later:
- User behavior and click patterns shift.
- New data is added or the model is retrained.
- Optimizing for clicks can create feedback loops: if one group clicks certain ads more, the model shows those ads even more to that group, and less to others.
For job ads, unequal exposure can mean some groups never see certain opportunities, a serious legal and ethical risk.
## Keeping outcomes fair over time
- **Monitor** who sees each type of ad across demographic groups, and alert on large gaps.
- **Retest** for bias whenever data, features or the model changes. Amazon SageMaker Clarify computes bias metrics and, with SageMaker Model Monitor, can track bias drift over time.
Fairness monitoring usually needs group information (or proxies) for measurement, even if the model does not use it for predictions.

G: ## Human-in-the-loop drafting
Foundation models write fluent replies in seconds, but they can get facts wrong, promise things the company does not offer, or use the wrong tone. In customer support, one wrong message can mislead a customer or create a commitment.
## The balanced pattern
- The model drafts a reply using the ticket and relevant knowledge (for example, retrieved help articles or order data).
- A support agent reviews the draft, fixes errors, adjusts tone and sends it.
- Agent edits can be tracked to improve prompts and measure draft quality.
Agents start from a good draft instead of a blank page, so they work faster, while a human still takes responsibility for each message. Contact-center tools such as the generative AI agent-assistance features in Amazon Connect support this pattern.
Once quality is proven, teams may automate low-risk, well-defined replies, but review stays in place for others.
W: Agents review and edit drafts: the model supplies speed by drafting, and the agent supplies quality by checking accuracy and tone before anything reaches the customer.
X: A=Customers rate drafts first: customers should receive finished answers, not internal drafts, and making them grade drafts adds delay and exposes unreviewed content.
C=Send automatically without review: fastest option, but errors and hallucinations go straight to customers with no chance to catch them.
D=Only for very long replies: reply length is not a sensible criterion for quality or risk; most support replies are short and benefit most from drafting help.
T: Balance speed and quality by having the model draft and a human agent review and edit before sending.
