# AIP-C01 batch 02: Domain 1 (data validation and processing, vector store design)
@ AIP-C01 D1 T1.3 applied use-case
S: A company ingests scanned PDFs with tables and charts into a knowledge base. Answers based on tables are often wrong. Which change helps most?
A: Use an advanced parsing option such as a foundation model or Bedrock Data Automation parser
B: Increase the embedding dimension so that the default parser captures more of the table content in each chunk
C: Convert the PDFs to plain text files manually and delete the original documents
D: Raise the generation temperature so the model can infer missing table values
K: A
W: Advanced parsing preserves table structure and figure content that the default text parser loses.
X: B=Embedding size does not fix parsing. | C=Manual conversion is slow and still loses structure. | D=Temperature does not recover lost data.
T: Complex documents need advanced parsing before chunking.
V: Amazon Bedrock Knowledge Bases, Amazon Bedrock Data Automation

@ AIP-C01 D1 T1.3 applied use-case

A: Redact PII with Amazon Comprehend in a transformation step before embedding

C: Encrypt the vector index so PII in it cannot be read by the model

K: A

@ AIP-C01 D1 T1.3 advanced troubleshooting
S: After adding a large batch of documents, retrieval quality drops because many chunks are near-duplicates of each other. What should be added to the pipeline?
A: Deduplication of near-identical content before embedding
B: A higher top-k to return more chunks for every query
C: A larger generation model with a bigger context window
D: A lower temperature for the final generation step
K: A
W: Duplicates crowd out diverse relevant chunks; deduplicating before indexing improves retrieval diversity and quality.
X: B=More chunks returns more duplicates. | C=A larger model does not fix retrieval. | D=Temperature does not affect retrieval.
T: Deduplicate content before indexing.

@ AIP-C01 D1 T1.4 advanced tradeoff
S: An application already stores product data in Aurora PostgreSQL and needs vector search joined with SQL filters in the same transaction. Which vector store fits?
A: Aurora PostgreSQL with the pgvector extension
B: A separate OpenSearch cluster synced nightly
C: An S3 bucket storing embeddings as CSV files
D: A Redis cache with no persistence configured
K: A
W: pgvector keeps embeddings next to relational data, enabling joins and transactional consistency without syncing another store.
X: B=Nightly sync adds lag and complexity. | C=CSV files do not support efficient vector search. | D=Non-persistent caches risk data loss.
T: Relational data plus vectors in one place → Aurora pgvector.
V: Amazon Aurora
