# AIP-C01 b09: D3 safety controls (T3.1 x8) and data security/privacy (T3.2 x7)

@ AIP-C01 D3 T3.1 advanced tradeoff
S: A telecom company streams answers from a Bedrock model to a web chat widget with ConverseStream, and the same guardrail also masks account numbers in outputs. Product wants the first tokens on screen within a second, but the security team objects that a chunk containing a disallowed answer could already be visible before the guardrail finishes evaluating it. Which configuration decision best explains the trade-off the team must make?
A: Use synchronous stream processing, which buffers response chunks until each is evaluated, and accept higher latency and a less smooth token flow in exchange for guaranteed screening
B: Use asynchronous stream processing, which never sends any chunk to the client until the entire response has been evaluated, and accept a longer wait before the answer starts displaying
C: Use asynchronous stream processing, which sends chunks immediately while the guardrail evaluates in the background, and accept that a violating chunk may already be shown before the guardrail intervenes
D: Disable stream processing for the guardrail and rely on the model's built-in safety training, because streamed responses cannot be evaluated by Bedrock Guardrails in any mode
K: A
G: ## How guardrails work with streaming
When you call a streaming API with a guardrail, the guardrail must evaluate text that arrives in pieces. Bedrock offers two stream processing modes.
- **Synchronous** mode buffers response chunks and evaluates them before they are released to the client. Nothing unscreened is shown, but the first tokens appear later and the flow is less smooth.
- **Asynchronous** mode releases chunks to the client immediately while the guardrail evaluates in parallel. Latency is best, but a chunk can be displayed before the guardrail decides to block or mask it.
The choice is a direct trade-off between responsiveness and the guarantee that no unscreened text reaches the user.
W: Synchronous processing: it holds each chunk until the guardrail has evaluated it, so a disallowed answer or an unmasked account number never reaches the widget. The cost is a slower time to first token, which is the compromise the security team is asking for.
X: B=Async described as buffering: asynchronous mode is the low-latency mode that does not wait; describing it as holding everything until the end reverses what the two modes do.
C=Async with exposure accepted: this is a correct description of asynchronous mode, but it accepts the very risk the security team wants eliminated, so it does not satisfy the stated requirement.
D=No stream processing: guardrails do support streaming responses in both modes, and the base model's safety training does not enforce company-specific rules such as account-number masking.
T: Synchronous stream processing screens before display at the cost of latency; asynchronous is faster but may show a chunk before the guardrail intervenes.
V: Amazon Bedrock

@ AIP-C01 D3 T3.1 advanced use-case
S: A legal-tech company runs a RAG pipeline on a self-hosted model behind an internal API, so it does not call Bedrock InvokeModel. Compliance wants the contextual grounding check to score each generated answer against the retrieved passages and the user question, and to block answers below a threshold. Which approach provides this?
A: Call the ApplyGuardrail API with the retrieved passages marked as the grounding source, the user question marked as the query, and the model answer marked as the content to guard, then act on the returned action
B: Call the ApplyGuardrail API with the prompt, retrieved passages and answer concatenated into one unmarked text block, because the service infers which part is the source and which part is the answer
C: Attach the guardrail to the self-hosted model endpoint directly, because contextual grounding checks run automatically on any HTTPS endpoint that receives the guardrail identifier in a header
D: Run Amazon Comprehend sentiment analysis on the answer and the passages and compare the scores, because Comprehend provides the grounding score that Guardrails uses internally
K: A
G: ## Contextual grounding outside Bedrock invocations
The `ApplyGuardrail` API evaluates text against a guardrail without invoking a model, so it works with self-hosted models and third-party APIs. The contextual grounding check compares an answer with reference material, so the guardrail needs to know which text plays which role. In the request, content blocks carry qualifiers: the reference text is the grounding source, the user's question is the query, and the generated answer is the content to guard. The guardrail then produces grounding and relevance scores and applies the configured thresholds.
W: ApplyGuardrail with qualified content: the passages are supplied as the grounding source, the question as the query, and the answer as the guarded content, so the grounding and relevance checks have all three inputs and the response tells the application whether to block.
X: B=Unmarked concatenation: without qualifiers the guardrail cannot tell what is reference and what is answer, so it cannot compute grounding; the service does not infer the roles.
C=Header on a self-hosted endpoint: a guardrail is not attached to arbitrary endpoints; the application must call ApplyGuardrail or use Bedrock invocation APIs to get evaluation.
D=Comprehend sentiment: sentiment scores say nothing about whether claims are supported by passages, and they are not what grounding checks use.
T: Use ApplyGuardrail with grounding-source, query and guarded-content qualifiers to get contextual grounding checks for models outside Bedrock.
V: Amazon Bedrock

@ AIP-C01 D3 T3.1 advanced troubleshooting
S: A team calls InvokeModel with a guardrail that has the prompt attack filter enabled. They build one prompt string that contains the system instructions, retrieved documents and the user's message. Red-team users type jailbreak text and the request goes through without any prompt attack detection, while the same text sent to a test with ApplyGuardrail is blocked. What is the most likely cause?
A: The prompt attack filter only works when temperature is set to zero, so production requests must lower the model temperature before the filter can score them
B: The guardrail is set to a numbered version instead of the working draft, and numbered versions do not include the prompt attack filter in their evaluation
C: The prompt attack filter needs user text identified with input tags, and the application sent one untagged string, so the guardrail has no marked user input to evaluate
D: The prompt attack filter reads only the system prompt field of the request, so attacks placed in the retrieved documents or the user message are always considered safe
K: C
G: ## Why input tagging matters
A prompt attack (jailbreak or prompt injection) is text supplied by a user that tries to override instructions. A combined prompt mixes trusted text (your instructions) with untrusted text (user input). To evaluate only what should be scrutinised, guardrails use tagged input: with `InvokeModel` you wrap the user content in tags that carry a suffix, and with the Converse API you mark it as guard content. The prompt attack filter checks the tagged user input, not your own system instructions. If nothing is tagged, no prompt attack detection happens on the prompt. A random per-request tag suffix also stops attackers from closing the tag early.
W: Missing input tags: the request contains no marked user text, so the prompt attack filter has nothing to evaluate. ApplyGuardrail worked because the tester passed the attack text explicitly as the content to evaluate.
X: A=Temperature: sampling temperature affects model output randomness, not whether the guardrail evaluates the prompt.
B=Numbered version: a numbered guardrail version contains the full configuration, including the prompt attack filter, as it was saved; versions are the recommended way to deploy.
D=System prompt only: the filter is aimed at user-supplied content; it is not restricted to the system prompt field, and the real gap is that nothing was marked as user input.
T: The prompt attack filter evaluates tagged user input; wrap user content in input tags (or guard content in Converse) and keep the tag suffix unpredictable.
V: Amazon Bedrock

@ AIP-C01 D3 T3.1 advanced tradeoff
S: A medical-education platform deploys a guardrail whose violence and sexual content filters are set to HIGH. Clinicians complain that legitimate questions about surgical procedures and reproductive health are blocked, but the compliance team refuses to remove the filters and wants evidence before changing any strength. Which approach best balances these needs?
A: Lower every content filter to NONE for one week, since the count of requests that would have been affected will show which strengths are appropriate for the platform
B: Deploy the guardrail in detect mode, which reports what would have been blocked without enforcing, review traces against real traffic, then tune strengths before enforcing
C: Move the filter strengths to LOW and add all clinical terms to a word filter allow list, because word filters override content filter decisions for the same text
D: Replace the content filters with one broad denied topic describing harmful content, since denied topics tolerate clinical vocabulary better than content filters
K: B
G: ## Tuning filters without guessing
Content filter strength (NONE, LOW, MEDIUM, HIGH) controls how confident the guardrail must be before it acts, so a higher strength catches more but also blocks more borderline, legitimate text. Guardrails offer a **detect mode**: the guardrail still evaluates and returns its trace showing which filters would fire, but takes no blocking action. Teams use it to measure false positives on real or representative traffic, then adjust strengths per filter and per direction (input or output), and only then switch to enforcement.
W: Detect mode: it gives evidence from real traffic with no user harm, letting the team lower only the filters that produce false positives while leaving compliance-relevant filters in place.
X: A=Set everything to NONE: this removes protection for a week for the whole population, and with strengths at NONE the filters would not report anything useful either.
C=Word filter override: word filters are additional blocks; they do not allow-list text that a content filter rejects.
D=Single broad denied topic: denied topics define subject areas to refuse and would not be more tolerant; one broad topic would likely block even more legitimate clinical text.
T: Use guardrail detect mode to measure false positives before changing filter strengths, then enforce the tuned configuration.
V: Amazon Bedrock

@ AIP-C01 D3 T3.1 applied troubleshooting
S: After the safety team tightened a guardrail's denied topics in the console and tested the changes with the working draft, the production application immediately started refusing many normal requests, although no deployment of the application took place. The application code passes the guardrail identifier and the value DRAFT as the version. What is the best long-term fix?
A: Create an immutable numbered guardrail version after each validated change and reference it from the application, so working draft edits cannot affect production
B: Keep using DRAFT in production but restrict console access, since the working draft is the stable production version and cannot be changed through the API
C: Delete the guardrail and recreate it for each release so the application always receives a fresh configuration with a new identifier and version
D: Switch the guardrail to detect mode permanently so edits made in the console never enforce anything on production traffic
K: A
G: ## Draft versus numbered versions
A guardrail has a mutable **working draft** used for editing and testing. When a configuration is ready, you create a **version**, a numbered snapshot that cannot be changed. Applications invoke a guardrail by identifier plus version; using `DRAFT` means every edit made in the console or API takes effect immediately for those callers. Production callers should pin a numbered version and promote a new one deliberately, which also gives a rollback by pointing at the previous number.
W: Numbered versions: production is decoupled from the draft, so the team can keep editing and testing safely, and rollback is a version change.
X: B=Draft as production: the working draft is the editable copy and can be changed through the API too; using it in production is the cause of the problem.
C=Delete and recreate: this changes identifiers, breaks references and adds risk, and still does not separate edits from production.
D=Permanent detect mode: this disables enforcement, removing the safety control that the tightened topics were meant to provide.
T: Pin production to numbered guardrail versions; treat DRAFT as a test-only working copy.
V: Amazon Bedrock

@ AIP-C01 D3 T3.1 advanced use-case
S: A customer-support assistant renders model output as Markdown in a browser. A security review shows that a prompt injection hidden in a retrieved document could make the model output an image link whose URL carries the user's conversation summary to an attacker's server. The team wants controls that address this exfiltration path. Which TWO measures fit best? (Select TWO)
A: Enable the contextual grounding check in the guardrail, which compares the answer with the retrieved documents and blocks any image link whose destination domain is not on an approved list
B: Validate model output in a Lambda function that strips or rewrites links and images to an allow-listed set of domains before the response reaches the browser
C: Set a Content-Security-Policy on the web application that restricts image and connection sources to approved domains, so injected links cannot be fetched by the browser
D: Increase the temperature of the model, so that repeated injection attempts produce a different link each time and are less predictable
E: Encrypt the conversation summary with a KMS key before adding it to the prompt, since encryption prevents the model from placing it in a link
K: B,C
G: ## Output handling as a security boundary
Indirect prompt injection means untrusted content the model reads (a web page, a document) contains instructions. If the application renders model output as active content, the model can be steered into producing a Markdown image or link whose URL includes sensitive data; the browser fetches it automatically and leaks the data. Guardrails reduce the chance of injection, but the application should also treat model output as untrusted: validate and sanitise it before rendering, and limit what the browser can load.
W: B=Output validation in Lambda: links and images are stripped or limited to allow-listed domains before rendering, which removes the exfiltration channel.
C=Content-Security-Policy: even if a link slips through, the browser refuses to fetch images or connect to domains outside the approved list.
X: A=Contextual grounding: it scores whether claims in the answer are supported by the source text and relevant to the query; it does not inspect link destinations or enforce a domain allow list.
D=Higher temperature: randomness does not stop an injected instruction and makes model behaviour less predictable.
E=Encrypting the summary: the model must read plain text to use it; encryption of a prompt component does not stop the model from repeating text it can read.
T: Treat model output as untrusted: sanitise links and images with an allow list and enforce a browser Content-Security-Policy.
V: AWS Lambda, Amazon Bedrock

@ AIP-C01 D3 T3.1 advanced tradeoff
S: A company serves a fine-tuned model from a SageMaker endpoint. Its guardrail check on each prompt via ApplyGuardrail adds about 250 ms before the model call, and the p95 latency target is tight. Policy still requires that no prompt violating the guardrail ever produces a response for the user. Which design meets both goals best?
A: Start the guardrail input check and the model invocation in parallel, wait for both, and return the model response only if the check returns no intervention, discarding it otherwise
B: Skip the input check for prompts from authenticated users and only apply the guardrail on the output side, because authenticated users are treated as trusted by the policy
C: Run the input check asynchronously after the response has been returned to the user and log violations for review the next business day
D: Cache the guardrail result for each user for 24 hours so that the check is only performed on the first prompt of each day for that user
K: A
G: ## Parallelising safety checks
`ApplyGuardrail` is independent of the model call: it takes text and returns whether the guardrail intervened. Because the two operations do not depend on each other, an application can issue them concurrently. Total latency becomes roughly the slower of the two rather than their sum. The response is held by the application until the guardrail result arrives, so a blocked prompt never produces a visible answer; the model cost for a rejected prompt is the price of the lower latency.
W: Parallel invocation: latency is reduced to about the longer of the two calls, and the application still enforces the policy because it returns nothing to the user when the check intervenes.
X: B=Trust authenticated users: authentication does not prevent prompt attacks or policy-violating requests from legitimate accounts, so the policy is not met.
C=Post-hoc review: the user would already have received the response, which violates the requirement.
D=Cache for a day: each prompt has different content, so a cached result says nothing about later prompts.
T: Run ApplyGuardrail and the model call concurrently and gate the response on the guardrail result to keep both latency and enforcement.
V: Amazon Bedrock, Amazon SageMaker AI

@ AIP-C01 D3 T3.1 applied use-case
S: A retail marketplace lets sellers upload product photos and titles, and a Bedrock multimodal model writes listings from them. Moderation must catch graphic violence and sexual imagery in the uploaded pictures as well as toxic text in the titles, with one managed policy and no custom classifier training. Which solution fits?
A: A guardrail with content filters configured for image content as well as text, applied to the multimodal request through the model invocation
B: A guardrail with a denied topic describing violent and sexual photos, since denied topics classify the pixels of an uploaded file directly without any text
C: An Amazon Comprehend custom classification endpoint trained on the seller photos, because Comprehend analyses image files natively for moderation
D: A word filter containing every violent and sexual term, applied to the file name of each uploaded photo before it is sent to the model
K: A
G: ## Multimodal moderation
Bedrock Guardrails content filters can evaluate images as well as text for categories such as hate, insults, sexual content and violence, using the same strength settings. This lets one guardrail moderate both the picture and the text of a multimodal request without a custom classifier. Other services have different jobs: Comprehend analyses text, Macie finds sensitive data in S3 objects, and denied topics and word filters are text-based.
W: Content filters with image support: they moderate the photo and the title in one managed policy, applied during the model invocation.
X: B=Denied topic for photos: denied topics work on text meaning; describing a topic does not make them analyse pixels.
C=Comprehend on images: Comprehend is a text NLP service and needs a labelled training set for custom classification, which the team wants to avoid.
D=Word filter on file names: file names are not the picture and can be renamed trivially.
T: Guardrails content filters cover images and text with one policy; use them for multimodal moderation instead of building classifiers.
V: Amazon Bedrock

@ AIP-C01 D3 T3.2 advanced troubleshooting
S: A Bedrock application runs in private subnets with no internet route. The team created an interface VPC endpoint for the Bedrock runtime service, and direct InvokeModel calls work. However, calls to retrieve from a Bedrock knowledge base and to invoke a Bedrock agent time out from the same subnets. What is the most likely cause?
A: Knowledge base and agent operations use a separate endpoint service, so an interface endpoint for the agent runtime API is missing
B: Interface endpoints for Bedrock only support the InvokeModel action, and all other Bedrock actions require a NAT gateway with a public address
C: The VPC endpoint policy must list each knowledge base document individually, otherwise retrievals are treated as internet traffic and time out
D: The Bedrock runtime endpoint has to be created in a different Region than the knowledge base for retrieval calls to be routed privately
K: A
G: ## Bedrock has several endpoint services
Bedrock APIs are split across services, and each has its own interface VPC endpoint service name. The control plane (create and manage resources), the runtime (InvokeModel, Converse), the agent build-time API and the agent runtime API (InvokeAgent, Retrieve, RetrieveAndGenerate) are separate. An endpoint for one does not carry calls for another. A private-subnet workload therefore needs an endpoint per API family it uses, with private DNS enabled and security groups permitting HTTPS from the callers.
W: Missing agent runtime endpoint: Retrieve and InvokeAgent go to the agent runtime service, which is not covered by the runtime endpoint that InvokeModel uses.
X: B=NAT requirement: PrivateLink is offered for the other Bedrock API families and keeps traffic off the internet; NAT is not needed.
C=Per-document endpoint policy: endpoint policies are IAM-style policies on actions and resources; they do not enumerate documents.
D=Cross-Region endpoint: an endpoint must be in the same Region as the VPC and the API; placing it elsewhere would not fix reachability.
T: Each Bedrock API family (runtime, agent runtime, control plane) has its own VPC endpoint; create one for every API used from private subnets.
V: Amazon Bedrock, AWS PrivateLink

@ AIP-C01 D3 T3.2 advanced tradeoff
S: A SaaS company offers a RAG assistant to 4,000 business customers on Bedrock Knowledge Bases. Documents are tagged with a tenantId metadata attribute at ingestion. A security architect worries that a user could type text that makes the application search another tenant's documents. Cost rules out one knowledge base per tenant. Which design gives the strongest isolation for the shared knowledge base?
A: Have the backend derive the tenant from the verified token and add it as a metadata filter to every Retrieve call, never accepting the tenant from the prompt or client
B: Place an instruction in the system prompt telling the model to only answer with documents that match the customer's tenantId as stated by the user in the chat
C: Ask the client application to send the tenantId as a request parameter and pass it to the retrieval filter, since the browser knows the customer it belongs to
D: Use a denied topic per tenant listing the names of the other tenants, because a guardrail can enforce document ownership at retrieval time
K: A
G: ## Where tenant isolation is enforced
In a shared vector index, chunks from every tenant sit together and are separated only by metadata. Metadata filtering restricts vector search to chunks whose attributes match, so it can enforce tenancy, but only if the filter value is trustworthy. Authorisation decisions must be made by code the user cannot influence: the tenant identity comes from a verified token (for example a claim in a JWT) and the backend injects it into the retrieval filter. Model instructions, client-supplied values and guardrails are not authorisation controls.
W: Server-side filter from the verified identity: the user can neither choose nor alter the tenant value, so the retrieval step can only return that tenant's chunks.
X: B=System prompt instruction: the model would receive other tenants' text before deciding to ignore it, and prompt injection can override the instruction, so it is not an access control.
C=Client-supplied tenantId: a modified client or intercepted request can send any value, defeating the filter.
D=Denied topics naming tenants: guardrails evaluate text of prompts and responses; they do not filter what the vector search returns.
T: Enforce tenancy with a metadata filter injected server-side from the authenticated identity, never from the prompt or client.
V: Amazon Bedrock, Amazon Cognito

@ AIP-C01 D3 T3.2 advanced use-case
S: A Bedrock agent invokes an action group Lambda function that queries customer orders. The security team wants to be sure that only this specific agent can invoke the function, even if another team's Bedrock agent in the same account learns the function ARN, and that the agent's service role can invoke only one approved foundation model. Which TWO measures fit best? (Select TWO)
A: Add a resource-based policy on the Lambda function that allows the Bedrock service principal to invoke it only when the source ARN is that agent's ARN
B: Give the agent's service role bedrock:InvokeModel on all resources, so that model upgrades never require a permissions change
C: Scope the agent's service role to bedrock:InvokeModel on the ARN of the one approved foundation model or inference profile
D: Make the function reachable through an unauthenticated function URL and check a shared secret in the request, because Bedrock agents cannot use resource-based policies
E: Attach the AdministratorAccess policy to the Lambda execution role, so that the action group can reach any data it may need in the future
K: A,C
G: ## Two layers of least privilege for agents
An agent has two identities. Its **service role** is what Bedrock assumes to call foundation models and other resources, so it should list only the approved model ARNs. The **action group Lambda** is invoked by the Bedrock service, so the function's resource-based policy decides who may call it. Using the Bedrock service principal together with a condition on the agent's ARN (source ARN) stops other agents, including ones in the same account, from calling the function, which is the confused-deputy protection AWS recommends.
W: A=Resource policy with source ARN: only that agent can invoke the function, whatever other agents know about it.
C=Model-scoped service role: the agent can call only the approved model, so a changed configuration cannot switch it to an unapproved or more expensive one.
X: B=Wildcard model access: convenient, but it lets the agent invoke any model and defeats the approval requirement.
D=Public function URL: it exposes the function to the internet and replaces IAM authorisation with a shared secret; resource-based policies are exactly how Bedrock is granted access.
E=AdministratorAccess: the opposite of least privilege, giving an injected agent action access to everything in the account.
T: Restrict agent service roles to approved model ARNs and protect action group Lambdas with resource policies conditioned on the agent's ARN.
V: Amazon Bedrock, AWS Lambda, AWS IAM

@ AIP-C01 D3 T3.2 advanced comparison
S: A German insurer must keep prompts and completions inside the EU. A developer proposes using Bedrock cross-Region inference to obtain higher throughput during peak periods. The architecture team lists options. Which TWO choices allow burst capacity while respecting the EU-only requirement? (Select TWO)
A: Use a geography-scoped EU inference profile, whose requests are routed only among Regions in the European geography
B: Use a global inference profile, because Bedrock only ever routes global profile traffic between EU Regions when the caller sits in Frankfurt
C: Add an IAM or service control policy that denies InvokeModel on global inference profile resources for the application roles, so they cannot be selected by mistake
D: Enable cross-Region replication on the S3 bucket that stores logs, since replication of the logs determines where inference runs
E: Route prompts through an API Gateway edge-optimized endpoint, because edge locations keep inference in the calling Region
K: A,C
G: ## Cross-Region inference and residency
Cross-Region inference profiles let Bedrock route a request to another Region with capacity. **Geography-scoped** profiles (for example the EU profile) keep routing inside a defined geography, so data stays in that group of Regions. A **global** profile can route to Regions worldwide, which trades control of location for the highest throughput. Where residency is a requirement, the team should choose the geography profile and also use IAM or SCP conditions on the profile resource so that a developer cannot pick the global one by mistake.
W: A=EU geography profile: routing stays in EU Regions while capacity is pooled across them.
C=Deny on global profile resources: it enforces the residency decision with a preventive control instead of relying on developers.
X: B=Global profile in Frankfurt: a global profile is not limited to EU Regions; the caller's location does not restrict where the request is processed.
D=Replicating logs: log location is unrelated to where inference is processed, and replication may copy content to other Regions.
E=Edge-optimized API: edge locations accelerate connections; they do not determine which Region runs inference.
T: For residency with cross-Region inference, use a geography-scoped profile and block global profiles with a preventive policy.
V: Amazon Bedrock, AWS Organizations

@ AIP-C01 D3 T3.2 advanced use-case
S: A health insurer indexes claim notes into a Bedrock knowledge base. The notes contain member names and IDs, and the compliance team says the vector store itself must not contain them, since redacting on retrieval would leave sensitive text stored. The team wants automation for each sync of the S3 data source. Which design meets this?
A: Add a custom transformation Lambda function to the ingestion process that calls Amazon Comprehend to redact PII from each chunk before it is embedded and stored
B: Enable a guardrail with a sensitive information filter on the RetrieveAndGenerate call, since masking at answer time removes the stored data from the index
C: Encrypt the vector store with a customer managed KMS key, because encryption at rest removes personal identifiers from the chunks it holds
D: Turn on model invocation logging with a data protection policy, so that log data masks the names held in the index
K: A
G: ## Redact before indexing, not after
A knowledge base stores chunk text and embeddings in the vector store. Controls applied at answer time (guardrails) change what a user sees but do not change what is stored. If policy says sensitive data must not be in the index, it must be removed before chunks are written. Bedrock knowledge bases support a custom transformation step in ingestion that runs your Lambda function on chunks, where Amazon Comprehend PII detection can find and redact entities, so the vector store only receives clean text.
W: Custom transformation with Comprehend: every sync redacts entities before embedding, so the index never holds them.
X: B=Guardrail at answer time: this masks output only; the raw chunks are still in the vector store.
C=Customer managed key: encryption at rest protects against unauthorised storage access, but authorised readers of the index still see the plain names.
D=Log data protection: this masks log data, not the vector index contents.
T: Redact PII before chunks are embedded (custom ingestion transformation with Comprehend); answer-time masking does not clean the index.
V: Amazon Bedrock, Amazon Comprehend, AWS Lambda

@ AIP-C01 D3 T3.2 advanced troubleshooting
S: A security account owns an S3 bucket for Bedrock model invocation logs, and Bedrock in the workload account is configured to deliver logs there. The delivery fails with an access error. The security team wants the narrowest bucket policy that allows delivery while preventing another AWS account from causing Bedrock to write to the bucket. Which statement is best?
A: Allow the Bedrock service principal to put objects under the log prefix, conditioned on the source account and source ARN of the workload account
B: Allow every principal in the organization to put objects into the whole bucket, because organization membership is enough to prevent misuse
C: Make the bucket writable by anyone, because Bedrock cannot authenticate to buckets in a different account and needs anonymous access
D: Allow the Bedrock service principal s3:* on the bucket with no conditions, since service principals are always trusted by the resources they access in AWS
K: A
G: ## Cross-account log delivery and confused deputy
Bedrock delivers invocation logs by acting as a service principal that writes to your S3 bucket. A bucket policy therefore names the Bedrock service principal, grants only the write action on the prefix used for logs, and adds condition keys such as the source account and the source ARN. These conditions prevent the confused-deputy problem: without them, a different account could configure Bedrock logging to point at your bucket.
W: Scoped service principal policy: delivery works, only from the workload account's Bedrock resources, and only to the log prefix.
X: B=Organization-wide write: it grants far more access than needed and does not identify Bedrock delivery.
C=Anonymous write access: this exposes the log bucket, which holds prompts and completions, and is unnecessary because service-principal grants work cross-account.
D=Unconditioned s3:*: trusting the service principal without conditions permits other accounts to abuse it and grants delete and read rights that logging does not need.
T: Give the Bedrock service principal write-only access to the log prefix, conditioned on source account and ARN to prevent confused-deputy abuse.
V: Amazon Bedrock, Amazon S3

@ AIP-C01 D3 T3.2 advanced troubleshooting
S: A team enables a customer managed KMS key on a Bedrock knowledge base backed by an Amazon OpenSearch Serverless collection. The first ingestion job fails with an access denied error on KMS while the S3 data source and IAM permissions for the embedding model look correct. The security team wants the least-privilege fix. What should they do?
A: Grant the knowledge base service role only the KMS actions it needs, such as decrypt and generate data key, on that specific key, and ensure the key policy allows the role
B: Add the knowledge base service role to the key administrators list, because administrators of a key automatically get permission to encrypt and decrypt with the key
C: Replace the customer managed key with the S3 bucket key for the vector store, because bucket keys apply to OpenSearch Serverless collections and remove the need for key policies
D: Disable encryption on the knowledge base, because a knowledge base cannot use a customer managed key for its ingestion storage or for its vector store
K: A
G: ## KMS permissions have two halves
A customer managed key is governed by its key policy, and IAM policies can grant access only if the key policy allows IAM to do so (or names the principal directly). The knowledge base service role needs kms actions such as `kms:Decrypt` and `kms:GenerateDataKey` on the specific key so that data handled during ingestion can be encrypted and read back. Administering a key and using it are separate: key administrator permissions manage the key but do not include using it for encryption.
W: Scoped KMS permissions: allow only the needed actions on that key for the service role, and confirm the key policy trusts the role or account IAM policies, which resolves the error without broad access.
X: B=Key administrators: administration rights manage the key lifecycle and do not grant the ability to encrypt or decrypt data with it.
C=S3 bucket key: bucket keys reduce KMS request costs for S3 objects; they do not encrypt OpenSearch Serverless collections and do not replace key policies.
D=Disabling encryption: knowledge bases support customer managed keys, and dropping encryption would violate the requirement instead of fixing the permission.
T: A customer managed key needs both a key policy that allows it and precise KMS actions for the service role; key administration is not key usage.
V: Amazon Bedrock, AWS KMS
