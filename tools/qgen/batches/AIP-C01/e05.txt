@ Q001520 explain
G: ## Two different kinds of "explainability"
Explaining a prediction depends on what kind of system made it.
- A **traditional ML model** (for example, gradient-boosted trees on tabular credit data) maps input features to a score. The question is "how much did each feature push this prediction up or down?" **SHAP** answers that: it assigns each feature a contribution, and the contributions add up to the difference between this prediction and a baseline. SageMaker Clarify computes SHAP values per prediction and globally.
- A **Bedrock agent** has no fixed feature vector. It reasons in steps: read the request, pick an action group or knowledge base, call a tool, read the result, decide again. The question is "why did it take these steps?" The agent **trace** (enable it with `enableTrace` on `InvokeAgent`) returns the pre-processing, orchestration (rationale, invocation input, observation) and post-processing steps.
## Example
A loan is declined: SHAP might show `debt_to_income` contributed -0.30 and `credit_history_months` -0.12. An agent that refunded an order: the trace shows it called `lookupOrder`, then `issueRefund`, with its rationale for each step.
W: Clarify SHAP for the tabular model and agent trace for the agent: each tool answers the question its system actually poses, feature attribution for the tabular model and step-by-step orchestration reasoning for the agent.
X: A=Agent trace for both: a trace records an agent's orchestration steps. A tabular model makes a single prediction with no steps or tool calls, so there is nothing to trace and no per-feature attribution.
C=Amazon Comprehend for both: Comprehend is an NLP service for entities, sentiment, key phrases and classification. It does not explain predictions of other models or agents.
D=SHAP for both: SHAP attributes a score to fixed input features. An agent's decision to call a tool comes from multi-step LLM reasoning over text, which SHAP values cannot reconstruct.
T: Feature attribution (Clarify SHAP) explains tabular predictions; the agent trace explains an agent's multi-step reasoning, and neither substitutes for the other.

@ Q001521 explain
G: ## Where bias checks fit in the ML lifecycle
SageMaker Clarify offers two families of bias metrics, and the stage decides which you can use.
- **Pre-training metrics** look only at the dataset. You pick a **facet** (a sensitive attribute such as age group) and the label column. Examples: **Class Imbalance (CI)** measures whether one facet has far fewer rows than another; **Difference in Proportions of Labels (DPL)** compares how often the positive label (approved) occurs in each facet.
- **Post-training metrics** compare the trained model's predictions across facets, for example Disparate Impact (DI) or the difference in positive proportions in predicted labels (DPPL). They need a model.
- **Model Monitor bias drift** runs Clarify on a deployed endpoint's live traffic on a schedule, even later in the lifecycle.
## Example
If 5% of rows are applicants under 25 and they have a 30% approval rate against 60% for others, CI flags the under-representation and DPL flags the label gap, before anything is trained.
W: Clarify pre-training metrics (CI and DPL): they run on the raw dataset, and CI and DPL measure exactly the two concerns in the stem, under-representation of a facet and different label rates between facets.
X: A=Post-training bias metrics: these compare a model's predictions across facets, but no model exists yet, so there are no predictions to analyze.
B=Model Monitor bias drift: this watches a deployed endpoint's predictions over time. It requires a model in production, which is two stages later.
D=Quick model feature importance: this trains a quick model to estimate how useful each feature is for prediction. It measures predictive power, not representation or label differences between age groups.
T: Before training, measure dataset bias with Clarify pre-training metrics such as CI and DPL; post-training metrics and bias drift need a model's predictions.

@ Q001522 explain
G: ## Offline tests versus live A/B tests
An offline test set shows how a model behaves on examples someone chose. It can miss the mix of requests, phrasings and customer segments that real traffic brings.
An **A/B test** (a controlled rollout) sends a fixed share of live traffic, for example 10%, to the new model while the rest stays on the current one. Both groups are measured with the same metrics, split by segment.
- On SageMaker, production variants with traffic weights on one endpoint do this; for Bedrock models, the application routes a share of requests to the new model or version.
- Compare per segment: resolution rate, user ratings, escalation rate, and fairness-related measures such as quality gaps between segments.
- If a segment regresses, only a small share of customers is affected and traffic can be shifted back.
## Example
New model at 10%: overall ratings rise, but ratings for Spanish-speaking customers fall 8 points. The team finds this before a full rollout, not after.
W: A/B test on a controlled share of live traffic: it produces real-world, per-segment evidence on quality and fairness while limiting how many customers any regression can reach.
X: A=Curated lab examples: examples chosen by the team reflect the team's assumptions and may under-represent some segments or real phrasing, so they cannot show how the model behaves on live traffic.
B=Skip evaluation: fresher training data does not guarantee equal or better behavior; fine-tuning can shift quality or fairness for particular segments, and nothing would detect it.
D=Full replacement with complaint monitoring: every customer is exposed at once, and complaints are a lagging, incomplete signal, so harm reaches all segments before anyone notices.
T: Prove a new model on a limited slice of real traffic with per-segment metrics before a full rollout, instead of relying on curated tests or complaints.

@ Q001523 explain
G: ## Counterfactual fairness testing at scale
A common way to test a generative model for fairness is **counterfactual prompts**: identical prompts that differ only in a demographic cue, such as the customer's name. If the model is fair, tone and helpfulness should not change with the cue.
At tens of thousands of samples, people cannot read every output. **LLM-as-a-judge** uses a second model with a written rubric to score each response, for example "rate helpfulness 1-5" and "is the tone respectful and consistent?". Amazon Bedrock model evaluation supports judge-based evaluations with built-in and custom metrics.
- Scores are compared across the demographic variants of each prompt; large gaps flag possible bias.
- Humans review a sample of the judge's scores, because the judge is itself a model and can be biased or miscalibrated.
## Example
The pair "Hi, I'm Emily" and "Hi, I'm Lakisha" with the same question should get equal helpfulness scores; a consistent gap across thousands of pairs is a finding.
W: LLM-as-a-judge with periodic human spot-checks: the judge applies the same rubric to every sample at a scale people cannot, and the human checks confirm the judge's own scores are trustworthy.
X: B=Wait for full manual review: fairness risk stays unmeasured while the product is live, and reading every response is not feasible at this volume anyway.
C=Comprehend sentiment averages: sentiment only labels text positive, negative, neutral or mixed. It cannot judge helpfulness, completeness or subtle tone, and group averages can hide per-prompt differences.
D=One engineer reads everything: one person cannot review tens of thousands of samples in reasonable time, fatigue makes judgments drift, and a single reviewer's own bias goes unchecked.
T: Scale fairness evaluation with an LLM judge using a clear rubric, and keep humans sampling its scores, rather than relying on coarse sentiment or impossible manual review.

@ Q001524 explain
G: ## What a post-training bias finding means
SageMaker Clarify post-training metrics compare a model's predictions across groups (facets). **Disparate Impact (DI)** is the ratio of positive-outcome rates: approvals for the disadvantaged group divided by approvals for the advantaged group. A value far below 1, for example 0.6, means the group is approved much less often. When qualifications are held constant, the gap is hard to explain by legitimate factors.
## Where the bias usually comes from
- **Training data**: the group is under-represented, or historical labels reflect past biased decisions.
- **Features**: proxies such as ZIP code can encode the protected attribute.
- **Fine-tuning**: the fine-tuning set or objective amplifies a skew.
Fixes include rebalancing or reweighting data, correcting labels, removing proxy features and adjusting fine-tuning. Then the same Clarify analysis runs again to confirm DI is back in an acceptable range before deployment.
W: Investigate and fix root causes, then re-evaluate: the disparity comes from data, features or fine-tuning, so fixing those and re-running Clarify is the only way to remove it and prove it is gone before release.
X: A=Treat as advisory: a significant disparate impact in lending-style decisions is a material legal and ethical risk. Clarify metrics are exactly the evidence meant to trigger action.
B=Stronger hate speech filter: guardrail content filters block hateful or abusive text. A biased approval recommendation contains no hate speech, so the filter never triggers and the skew remains.
C=Deploy and watch complaints: affected applicants are harmed first, many never complain, and complaint rates are a weak, delayed fairness signal compared with the Clarify measurement already in hand.
T: A confirmed bias metric calls for fixing data and training and re-measuring, not for content filters or waiting for complaints.

@ Q001525 explain
G: ## How LLM-as-a-judge works, and its weak spot
An LLM judge is a model given a rubric and an output to score, for example "Is this response respectful and equally helpful? 1-5". It is fast, cheap per item and consistent, so it can score huge volumes. Amazon Bedrock model evaluation can use Bedrock models as judges.
But the judge is also a model trained on human text, so it can have **systematic biases** of its own:
- rating certain dialects, names or writing styles lower;
- preferring longer or more confident answers (verbosity bias);
- favoring outputs that resemble its own style.
Because it applies the same bias to every item, the error is consistent and silent: the dashboard looks stable while one kind of content is mis-scored.
## Keeping the judge honest
A human-in-the-loop sample, such as a few hundred items per week scored by people, is compared with the judge's scores. Where they disagree systematically, the rubric or judge model is adjusted.
W: The judge can be biased: it is a model with its own blind spots, so periodic human validation is needed to catch systematic mis-scoring that automation alone would never reveal.
X: A=Bedrock models cannot be judges: Amazon Bedrock supports LLM-as-a-judge evaluations with Bedrock-hosted judge models, so no self-hosted model is needed.
B=Human review legally required for everything: AWS service terms do not require a human to review every generated output; the level of human oversight is the customer's own policy decision.
D=Slower than humans: a judge model scores in seconds and runs in parallel, far faster than people at scale. Speed is its main advantage, not its weakness.
T: Use LLM judges for scale but keep human spot-checks, because a judge can carry consistent biases that no one notices without them.

G: ## Denied topics in Bedrock Guardrails
Amazon Bedrock Guardrails apply configurable safeguards to model inputs and outputs. Policy types include content filters, **denied topics**, word filters, sensitive-information filters, contextual grounding checks and automated reasoning checks.
A **denied topic** is defined in natural language: a name, a definition and optional sample phrases. The guardrail classifies prompts and responses against it and blocks matches with a configured message.

- Topic "Competitor promotion": "Recommending or praising products of named competitors."
The guardrail is attached per request (`guardrailIdentifier` and `guardrailVersion` on `InvokeModel` or `Converse`, or configured on an agent or knowledge base query), or called directly with `ApplyGuardrail`. Word filters can add exact competitor names as a backstop.
W: Denied topics attached to all relevant invocations: they turn the two prohibited subjects into runtime checks that block matching inputs and outputs on every call where the guardrail is applied.
X: B=Model Card documenting the policy: a Model Card records intended use and risks for governance, but it has no runtime role and cannot stop a response.
C=Lower maximum token limit: a short response can still name a competitor or state a diagnosis in one sentence, and the limit also cuts off legitimate long answers.
D=Code comments in prompt modules: comments are never executed or seen by the model, so they enforce nothing at runtime.
T: A policy about forbidden subjects is enforced at runtime with guardrail denied topics; documentation and token limits do not block anything.

G: ## Documentation evidence versus enforcement evidence
Responsible-AI audits usually ask two separate questions.
- **Is the system documented?** A **SageMaker Model Card** records intended uses, out-of-scope uses, limitations, risk rating, training details and evaluation results in one versioned record that can be exported as a PDF for auditors.
- **Is policy actually enforced?** The **Bedrock Guardrails configuration** shows which denied topics, content filters and sensitive-information filters exist. Logs show it is really used: CloudTrail records the Bedrock API calls, and model invocation logs or guardrail traces can show the guardrail being applied to requests.
Configuration alone proves only that a control exists; the logs prove the application calls it. A document alone proves only intent.
## Example
Model Card: "Intended use: answering billing questions; not for legal advice; risk rating: medium." Guardrail `support-gr` version 3 denies "legal advice"; logs show requests carrying that guardrail.
W: Model Card plus guardrail configuration and logs: the card satisfies the documentation requirement, while the guardrail configuration together with logs of its use proves runtime enforcement.
X: B=Guardrails only: a guardrail shows what is blocked, not the documented intended use, limitations or risk assessment the auditor asked for.
C=Model Card only: describing controls in a document does not prove they run on each request; the auditor also needs technical evidence of enforcement.
D=General privacy policy: a company-wide privacy notice covers data handling in general. It is neither product-specific documentation nor evidence of runtime content controls.
T: Auditors need both a record of intent (Model Card) and proof of enforcement (guardrail configuration plus logs of it being applied).

G: ## How guardrail changes reach applications
Each Bedrock guardrail has a working **DRAFT** and numbered, immutable **versions**. Applications usually call a specific version (`guardrailVersion: "3"`), so a change means: update the policy, create a new version, and point the application at it.
With 15 separate guardrails, doing this by hand in the console is slow and easy to get wrong: one topic definition typed differently, or one application still pinned to the old version.
## Managing guardrails as code
- Define guardrails in infrastructure as code, for example CloudFormation `AWS::Bedrock::Guardrail` and `AWS::Bedrock::GuardrailVersion`, or the equivalent in AWS CDK or Terraform.
- Keep the new denied topic in one shared module that all 15 guardrail definitions reference.
- One reviewed change runs through the pipeline, creates the new versions and updates the applications' configured version, the same way everywhere.
Teams could also consolidate onto fewer shared guardrails to make future changes simpler.
W: Push the same update centrally with infrastructure as code: one reviewed change is applied identically to all 15 guardrails at once, which is both fast and consistent for an urgent legal requirement.
X: A=Disable all applications: an outage across 15 customer-facing apps is far more disruptive than needed, and the guardrails still have to be updated afterwards.
B=One engineer edits each console: fifteen manual edits and version changes take time and invite inconsistent topic definitions or a missed application.
D=Email teams to update when convenient: the requirement is immediate, and leaving timing and wording to each team produces inconsistent enforcement and gaps.
T: Urgent policy changes across many guardrails are rolled out centrally with infrastructure as code, not by manual console edits, emails or outages.

@ Q001530 explain
G: ## Where token counts live in Amazon Bedrock
**Model invocation logging** writes one record per call to CloudWatch Logs and/or Amazon S3. Each record includes the model ID, timestamp, input token count and output token count, and optionally the prompt and response.
The Converse API accepts a `requestMetadata` map, for example `{"tenant_id": "acme"}`, which is written into the invocation log so logs can be filtered by it.
## Turning logs into chargeback
- Tag every request with the tenant ID.
- Aggregate with CloudWatch Logs Insights or Athena over the S3 logs: sum input and output tokens per tenant per model.
- Multiply by the model's per-token prices.
Another AWS-native option is one **application inference profile** per tenant with cost allocation tags, which splits cost in billing data; that fits a few large tenants better than thousands of small ones.
W: Invocation logging with per-request metadata: every log record already carries exact input and output token counts, and tenant metadata on the request lets you sum them per customer with standard log queries and no extra metering service.
X: B=CloudTrail events for InvokeModel: CloudTrail records who called which API, when and from where. It does not record token consumption per request.
C=Model evaluation job reports: evaluation jobs are offline tests over a prompt dataset. They do not measure production traffic or know which tenant sent what.
D=Cost allocation tags on the service: tags apply to taggable resources, not to individual requests. Tagging shared usage cannot separate customers who share the same model, and Cost Explorer shows cost and usage, not per-customer token counts.
T: Per-tenant token chargeback comes from invocation logs tagged with tenant metadata, not from CloudTrail, evaluation reports or service-level tags.

@ Q001531 explain
G: ## Why long chats get slow and expensive
A model is stateless: every request must resend what it should know. Here each call carries the retrieved passages plus the last 10 turns. As turns get longer, input tokens grow, and both cost (billed per input token) and latency (more tokens to process before the first output token) grow with them.
A large context window only means the request fits; it does not make those tokens free or fast.
## Conversation memory patterns
- **Sliding window**: keep only the last N turns; cheap, but older facts are lost.
- **Rolling summary**: periodically ask a small model to condense older turns into a short summary ("User is on the Pro plan, asked about refunds, prefers email") and send that plus the last 2-3 turns verbatim.
- Retrieval stays on every turn, because each new question may need different passages.
## Example
Ten turns of 600 tokens is 6,000 tokens; a 300-token summary plus 3 recent turns is about 2,100.
W: Rolling summary plus recent turns verbatim: older context is compressed into a few hundred tokens while recent detail is kept exactly, which cuts input tokens sharply without losing what the answer depends on.
X: B=Retrieve more passages: extra passages add input tokens to every request, increasing cost and latency, and do nothing about the growing history.
C=Skip retrieval after the first message: later questions often need different documents, so answers would lose grounding and hallucinations would rise.
D=Model with a larger context window: it only postpones context-length errors; every request still sends the growing history, so cost and latency keep rising.
T: Control token growth by compressing conversation history, not by enlarging the context window or dropping retrieval.

@ Q001532 explain
G: ## Paying for a repeated prompt
Every request is billed for all its input tokens. A long static system prompt with few-shot examples, say 3,000 tokens, sent with every one of 1 million requests is 3 billion input tokens of the same text.
## Two ways to reduce it
- **Prompt caching** in Amazon Bedrock: on supported models, you mark a cache checkpoint after the static prefix. The first request writes that prefix to the cache; later requests with the identical prefix within the cache lifetime (a few minutes, refreshed on each hit) read it at a much lower price and with lower latency. The prefix must be byte-identical, so static content goes first and the per-request document last.
- **Prompt compression or distillation**: rewrite the instructions more concisely, drop redundant examples, or fine-tune a model on the desired format so the instructions are no longer needed in the prompt.
The two combine: shorten what is repeated, then cache what remains.
W: D=Shorter prompt or fine-tuned model: fewer instruction tokens per request directly lowers input-token cost, and a model fine-tuned on the format keeps outputs consistent without the long prompt.
E=Prompt caching for the static prefix: the identical instructions and examples are read from the cache at a reduced rate instead of being processed at full price on every request.
X: A=Higher temperature: temperature only changes how randomly tokens are sampled. It does not shorten the billed input and makes outputs less consistent.
B=More few-shot examples: each example adds input tokens to every request, raising the very cost the team wants to cut.
C=Streaming mode: streaming only delivers output tokens as they are generated. The same input and output tokens are billed.
T: For a large repeated prompt, shrink it and cache it; temperature and streaming do not change the tokens you pay for.

G: ## Model tiering
Foundation models come in sizes and price points. Smaller models, such as Amazon Nova Micro or Lite or small Claude and Llama variants, cost much less per token and respond faster; larger models reason better on open-ended writing.
**Tiering** matches each step of a workflow to the smallest model that meets its quality bar.
- **Classification into eight fixed categories** is a bounded task: short output, a clear right answer, easy to test with a labeled set. Small models usually match large ones here.
- **Drafting a reply** needs tone, context and nuance, so a more capable model may be worth its price, especially for complex tickets.
- Measure each step separately on an evaluation set, then pick per step.
Amazon Bedrock Intelligent Prompt Routing can also route requests within a model family between a smaller and a larger model based on predicted response quality.
## Example
If classification is 70% of calls and a small model is ten times cheaper, tiering removes most of that step's cost with no quality loss.
W: Smaller model for classification, larger only for complex drafting: each step gets the cheapest model that meets its quality need, so spend goes where capability actually matters.
X: A=Smallest model for everything: weak drafts move the cost to human agents who must rewrite them, which can cost more than the model savings.
C=Alternate models per request: the choice ignores task difficulty, so half the complex drafts get a weak model and half the simple classifications pay for a large one.
D=Largest model for every step: it overspends on classification, where a small model is just as accurate, and adds latency to every ticket.
T: Tier models by task difficulty: small models for bounded tasks like classification, larger models only where nuanced generation needs them.

G: ## Bedrock inference options for bulk work
- **On-demand** (`InvokeModel`, `Converse`): pay per token, real-time answers, limited by per-account request and token-per-minute quotas.
- **Provisioned Throughput**: reserved model units billed per hour, with optional 1- or 6-month commitments. Meant for steady, high real-time volume or for serving custom models.
- **Batch inference**: you put requests in JSONL files in Amazon S3 and start a job with `CreateModelInvocationJob`. Bedrock processes them asynchronously and writes results back to S3. Supported models are priced at a discount of about 50% compared with on-demand.
- **Cross-Region inference**: routes on-demand requests across Regions for more capacity; it does not lower the price.
## Example
Two million image-plus-prompt records split into JSONL files, submitted as batch jobs on Monday; results land in S3 without the application managing concurrency, throttling or retries.
W: Bedrock batch inference: the workload is large and tolerates asynchronous results, which is exactly what batch jobs are built for, and they run at a lower per-token price than on-demand calls.
X: A=Provisioned Throughput for peak: you pay hourly for reserved capacity sized for a one-off job, often with a commitment, and still have to drive 2 million synchronous calls yourself.
C=Everything concurrently on demand: 2 million simultaneous calls hit request and token quotas and throttle, and every token is billed at the full on-demand price.
D=Cross-Region inference: it spreads on-demand traffic for more throughput, but pricing stays on-demand, so it adds capacity without reducing cost.
T: Large jobs that can wait go to Bedrock batch inference for the lower price; Provisioned Throughput and cross-Region inference buy capacity, not discounts.

G: ## Capacity for custom models on Bedrock
A custom (fine-tuned) model in Amazon Bedrock needs capacity to run on. Depending on the model type, it is served either through **Provisioned Throughput** (purchased model units dedicated to that model) or, for some supported models, an on-demand deployment that shares Region quotas.

Measure the peak tokens per minute between 9 AM and 6 PM, add headroom, and buy the model units that cover it. Because the load is regular and predictable, dedicated capacity is used efficiently.

D=Exponential backoff alone: retries are good practice but only delay requests; during sustained peaks they add latency without adding capacity.

@ Q001537 explain
G: ## Two different caches
**Prompt caching (Amazon Bedrock)** caches the model's processing of a prompt **prefix**. You put static content first (system prompt, document context) and mark a cache checkpoint. Later requests with the byte-identical prefix within the cache lifetime read it at a reduced price and with lower latency; only the part after the checkpoint, here the new question, is processed at full price. The model is still called and still answers each question freshly.
**A semantic cache** stores complete **responses** keyed by an embedding of the question. A new question is embedded and compared with past ones; if one is close enough, the stored answer is returned and the model is not called at all.
- Prompt caching pays off when the prefix repeats.
- Semantic caching pays off when the questions repeat.
## This scenario
The 6,000-token prefix is identical on every call, but the questions differ, so prompt caching hits almost every time while a semantic cache would rarely find a close enough match.
W: Prompt caching for the repeated prefix: the 6,000 shared tokens are reused on nearly every request, while a semantic cache keyed on constantly changing questions would rarely produce a hit.
X: A=Semantic cache is better: it only saves when a new question closely matches a previous one; with varying questions it misses most of the time and can even return a wrong cached answer on a loose match.
C=Prompt caching only via edge locations: prompt caching is a feature of Bedrock model invocation in a Region, used with normal API calls such as `Converse` and `InvokeModel`; it has nothing to do with edge locations.
D=Same problem, same savings: one discounts a repeated prompt prefix, the other skips the model for repeated questions, so their savings depend on completely different traffic patterns.
T: Repeated prefix with changing questions calls for prompt caching; semantic caching only helps when the questions themselves repeat.

@ Q001538 explain
G: ## Generated once, read many times
When model output rarely changes, it is really **static content**. The cheapest and fastest design is to generate each item once, store it, and serve the stored copy, calling the model only when the input changes.
- Store each description in Amazon S3 (or a database) keyed by product ID.
- Serve it through **Amazon CloudFront**, which caches it at edge locations worldwide, so users get low latency and page views never call the model.
- When a product changes, regenerate its description and write it under a **new versioned key** (for example `desc/1234/v7.json`) that the page references, or invalidate the old path. About 20,000 regenerations per day replace millions of model calls.
## Contrast with model-side caches
Prompt caching and semantic caching reduce the cost of calls that still happen at request time. Here the goal is no model call per view at all.
W: Store outputs and serve via CloudFront, changing keys on update: page views are served from the edge with no model cost, and only the 1% of changed products are regenerated each day.
X: A=Provisioned Throughput per page view: every view still calls the model and pays for dedicated capacity, which contradicts the goal of no model cost per view.
C=Single-Region semantic cache: users far from that Region still get remote round trips, and similarity matching is unnecessary when the exact product ID is known.
D=Bedrock prompt caching: each page view still invokes the model; caching only discounts a repeated prompt prefix, so per-view model cost and latency remain.

G: ## What drives time to first token
Time to first token (TTFT) is mostly how long the model takes to process the prompt and produce its first token. It depends on:
- **Model size and serving setup**: smaller models, and latency-optimized serving, answer faster.

G: ## How OpenSearch vector search scales
Amazon OpenSearch Service k-NN usually uses **HNSW**, a layered graph of vectors. A query walks the graph to find approximate nearest neighbors.
- `m`: how many links each node keeps. Higher values improve recall but use more memory; set at index creation.
- `ef_construction`: how thoroughly the graph is built; also an index-time setting.
- `ef_search`: how many candidates a query explores; higher values give better recall but slower queries.
HNSW graphs should fit in memory. At 40 million chunks, graphs can outgrow the memory available on the nodes, causing slow disk-backed or evicted graphs, and parameters tuned for a small index can lose recall.
## Restoring performance
- Retune `ef_search`, and rebuild with better `m` or `ef_construction` if recall is low.
- Add shards and data nodes, or memory-optimized instances, so graphs stay in memory and queries run in parallel.
- Consider vector quantization to shrink memory per vector.
W: Retune HNSW parameters and add shards or capacity: parameter tuning restores recall, and enough shards and memory for 40 million vectors restores query latency.
X: A=Similarity in the application: loading and comparing 40 million embeddings per query is a brute-force scan, far slower than an index and impossible to keep in application memory.
B=Keyword search only: BM25 cannot match queries worded differently from the documents, so semantic recall drops further; the problem is index sizing, not vector search itself.
D=Increase top-k: returning more neighbors adds work per query, which worsens latency, and it does not fix the graph's recall at its current settings.
T: Growing vector indexes need HNSW tuning and enough shards and memory; brute force, keyword-only search or a larger top-k do not fix both latency and recall.

G: ## Dense versus keyword retrieval
- **Dense (vector) retrieval** embeds text into vectors and finds chunks with similar meaning, so "termination of lease" matches "ending a rental agreement". It is weak on exact identifiers: `Section 1983` and `Section 1981` look almost the same to an embedding model.
- **BM25 keyword retrieval** scores exact term matches, weighting rare terms higher. It finds `42 U.S.C. 1983` exactly, but misses paraphrases.
## Hybrid search
**Hybrid search** runs both and merges the ranked lists, for example by score normalization and weighted combination, or reciprocal rank fusion.
- Amazon OpenSearch Service supports hybrid queries with a normalization search pipeline.
- Amazon Bedrock Knowledge Bases can use hybrid search with supported vector stores.
## Example
Query: "limitations period for claims under Section 1983". BM25 finds chunks containing "1983"; vector search adds chunks about "time limits for civil-rights lawsuits". The merged list has both.
W: Hybrid search with vector similarity and BM25: keyword matching catches exact statute numbers and legal terms, and vector similarity keeps matching concepts written in different words.
X: A=Larger chunk size: bigger chunks dilute each embedding with more content, making exact identifiers even less visible to vector search.
C=Lower the similarity threshold: it returns more loosely related chunks, adding noise, but embeddings still do not reliably separate one statute number from another.
D=Replace with BM25 only: exact matches improve, but queries that describe a concept in different words than the documents would stop finding relevant results.
T: When users need both exact identifiers and paraphrase matching, combine BM25 and vector search in hybrid retrieval.

G: ## Why output length drives throughput
LLMs generate output one token at a time, so the time a request occupies capacity grows with the number of output tokens. Input tokens are processed much faster, in parallel.
- `max_tokens` caps the output. If it is much higher than needed, and the prompt invites verbose sections, the model keeps generating content nobody reads.
- In Amazon Bedrock, quota-based capacity also counts `max_tokens` against the tokens-per-minute quota when a request starts, so oversized values reduce how many requests fit.
- With fixed capacity such as Provisioned Throughput, fewer tokens per report means more reports per minute from the same model units.
## Fixing it
- Set `max_tokens` close to the real maximum useful length, for example 1,500 instead of 8,000.
- Remove boilerplate from the prompt and tell the model to skip preambles and repeated disclaimers.
## Example
Cutting average output from 2,400 to 1,200 tokens roughly doubles reports per minute on the same capacity.
W: Right-size max_tokens and trim boilerplate: shorter useful outputs mean each report holds capacity for less time, so the same Provisioned Throughput produces more reports per minute.
X: A=Buy more model units: extra units raise cost to pay for tokens nobody needs; the waste in each request remains, so it is the expensive fix, not the effective one.
B=Fewer concurrent requests: lower concurrency leaves capacity idle and reduces total reports per minute, while each report still generates the same unnecessary tokens.
D=Raise temperature: temperature changes how randomly tokens are chosen, not how fast they are generated, and it would make reports less consistent.
T: Effective throughput improves by generating only the tokens you need, not by buying more capacity or changing sampling settings.
