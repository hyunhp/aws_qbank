G: ## How to choose a foundation model
Amazon Bedrock offers many foundation models from several providers, and they differ in quality, speed, context window, modality and price. For a customer-facing chat app the choice should rest on evidence from your own workload, not on popularity or appearance.

A slightly weaker but much cheaper and faster model is often the right pick if it passes the quality bar.

T: Pick a model by measuring quality on your own prompts and checking latency and cost at real traffic, not by popularity or cosmetic details.

G: ## Parsing comes before chunking
When a Bedrock knowledge base ingests a file, it first **parses** it into text, then chunks and embeds that text. If parsing loses structure, every later step works with broken input.
- The **default parser** extracts plain text. For scanned PDFs, tables and charts this often yields jumbled cells or missing numbers, so a question like "What was Q3 revenue in the table?" retrieves text where the value is no longer next to its row and column labels.
- **Advanced parsing** can use a **foundation model as parser** or **Amazon Bedrock Data Automation** as parser. These read the page visually, extract tables with their structure (for example as Markdown tables) and describe charts and figures in text.
Once the table survives parsing, chunks contain correct, labeled values and the model can answer from them.
W: Advanced parsing (FM or Bedrock Data Automation parser): it extracts tables and figures from scanned and complex PDFs with their structure intact, which fixes the root cause of wrong table answers.
X: B=Higher temperature: temperature only adds randomness to generation. It cannot recover values the parser dropped and makes invented numbers more likely.
C=Larger embedding dimension: the dimension affects how finely meaning is encoded, but the default parser has already scrambled the table before embedding, so a bigger vector encodes the same broken text.
D=Manual plain-text conversion and deleting originals: plain text flattens tables and charts, the manual effort does not scale, and deleting the source removes the ability to re-parse later.
T: Wrong answers from tables usually mean a parsing problem, so switch to an advanced parser rather than tuning embeddings or generation.

A RAG system can only be as good as its documents. Bad files, such as corrupt PDFs, empty pages or missing required metadata, should be stopped at the door, not discovered by users.
A typical design puts a validation step between the landing zone and the knowledge base source:

- Valid files move to the ingestion prefix; failures go to a quarantine prefix with an alert.
W: Validation step before ingestion: rejecting malformed files and flagging missing metadata up front keeps bad content out of the index and gives a clear, automated record of what failed and why.

B=Rely on the model to ignore bad content: once indexed, broken chunks can be retrieved and used as context, and the model cannot tell a missing metadata field from a valid document.

G: ## Remove PII before it becomes a vector
Anything that is embedded and stored in a vector index can come back in retrieval results and end up in a prompt or answer. If names and phone numbers must not be stored, they have to be removed before the embedding step.
- **Amazon Comprehend** detects PII entity types such as `NAME`, `PHONE`, `EMAIL` and `ADDRESS`, and can return offsets or produce redacted output (for example `[NAME]` or masking characters).
- In a Bedrock knowledge base, this can run in a preprocessing Lambda before files land in the data source, or in a custom transformation Lambda during ingestion.
Example: "Hi, this is Jane Kim, call me at 555-0142" becomes "Hi, this is [NAME], call me at [PHONE]" before it is chunked and embedded.
W: Comprehend PII redaction before embedding: the personal data is removed from the text itself, so neither the stored chunk text nor its vector ever contains it.
X: B=Smaller chunks: splitting text finer leaves the same names and numbers in the index, just spread over more chunks.
C=Encrypt the index: encryption at rest protects against unauthorized storage access, but authorized retrieval decrypts the data, so the PII is still stored and still returned to the model.
D=Filter PII only in the final answer: the requirement is that PII is not stored in the index, and output filtering leaves it there while also depending on catching every case at answer time.
T: If PII must not be in the vector store, redact it with Comprehend before embedding; encryption or output filters do not remove it from storage.

@ Q002841 explain
G: ## Why duplicates hurt retrieval
Retrieval returns the top-k most similar chunks. If the corpus contains many near-identical chunks, such as the same policy copied into several documents or repeated boilerplate, a query often retrieves several copies of the same text.
- The top-k slots fill with redundant chunks, pushing out other relevant, diverse information.
- The model gets less distinct evidence and may over-weight one source.
- Storage and embedding cost grow for no benefit.
**Deduplication** before embedding removes this. Exact duplicates can be found with content hashes; near-duplicates with techniques such as MinHash, shingling or embedding similarity above a threshold. Keep one canonical copy, ideally the latest.
W: Deduplication before embedding: removing near-identical content means each retrieved slot carries new information, which restores retrieval diversity and quality.
X: A=Lower temperature: temperature affects generation randomness only; the retrieved chunks would still be full of duplicates.
B=Higher top-k: more slots mostly return more copies of the same text and add tokens and cost, without fixing the corpus problem.
D=Larger model and context window: a bigger model reads the same redundant context; the retrieval set is still crowded with duplicates.
T: Near-duplicate chunks crowd out useful results, so deduplicate content before embedding instead of tuning generation or top-k.

G: ## Vectors inside the relational database
**pgvector** is a PostgreSQL extension that adds a `vector` data type, distance operators (such as `<=>` for cosine distance) and approximate indexes (HNSW and IVFFlat). Amazon Aurora PostgreSQL supports it.
Keeping vectors in the same database as the product data means one SQL query can combine similarity and business filters, for example:
- `SELECT id, name FROM products WHERE in_stock AND price < 100 ORDER BY embedding <=> $1 LIMIT 10;`
Because it is the same database, vector writes and product updates can happen in one transaction, so embeddings never drift from the rows they describe. Aurora PostgreSQL can also serve as a Bedrock Knowledge Bases vector store.
W: Aurora PostgreSQL with pgvector: vectors live next to the product rows, so similarity search, SQL filters and joins run in one query and updates stay transactionally consistent.
X: B=Redis without persistence: a cache without persistence can lose data on restart and is a separate system, so it cannot join with Aurora rows in the same transaction.
C=Separate OpenSearch synced nightly: data is up to a day stale and lives in another system, so there is no single transaction or SQL join with the product table.
D=Embeddings as CSV in S3: CSV files have no vector index, no query engine for similarity search and no transactional link to Aurora.
T: When data already lives in Aurora PostgreSQL and needs vector search with SQL in one transaction, add pgvector rather than a separate store.

G: ## Metadata filtering in vector search
Vector similarity measures how close in meaning two texts are. It does not reliably enforce hard rules like "only tenant A" or "only 2024 documents".
Most vector stores let each vector carry **metadata fields** (for example `tenant_id` and `doc_date`). A query then combines a similarity search with a filter, such as `tenant_id = "acme"` and `doc_date >= 2024-01-01`. The store searches only among matching vectors, so the top-k results all satisfy the filter.
- In Bedrock Knowledge Bases, filters use operators such as `equals`, `greaterThanOrEquals`, `in` and `andAll`.
- Filtering by tenant also supports data isolation in multi-tenant applications.

C=Index per tenant-date combination: the number of indexes explodes, and a date-range query would need to search many indexes and merge results.
D=Filter after retrieving top 1,000: this wastes work, and if the matching chunks are not in the first 1,000 they are lost, so results can be empty or incomplete.

@ Q002846 explain
G: ## Each embedding model has its own vector space
An embeddings model maps text to a vector. The meaning of each dimension is specific to that model and version. Two models, or two versions of one model, place the same sentence at different coordinates, and they may even use a different number of dimensions (for example 1,024 versus 1,536).
Similarity search only works when the question vector and the stored vectors come from the same model. Comparing vectors from different models gives meaningless distances.
When changing models:
- Re-embed all documents with the new model.
- Build a new index (often side by side), test retrieval quality, then switch traffic.
- In Bedrock Knowledge Bases the embeddings model cannot be changed on an existing knowledge base, so this means creating a new knowledge base and syncing it.
W: Re-embed everything and rebuild: stored vectors and query vectors must share one vector space, so all documents need new embeddings from the new model.
X: B=Keep old vectors, query with new model: the two vector spaces are incompatible, so similarity scores become meaningless and retrieval breaks.
C=All models share one space: each model learns its own representation; there is no universal embedding space across models or versions.
D=Delete the oldest 10%: the problem is incompatibility, not storage space; the remaining 90% would still be in the old model's space.
T: Changing the embeddings model means re-embedding the whole corpus, because vectors from different models cannot be compared.

@ Q002847 explain
G: ## Hierarchical (parent-child) chunking
Small chunks match questions precisely but carry little context; large chunks carry context but match less precisely. **Hierarchical chunking** gets both.
- Documents are split into larger **parent** chunks (for example about 1,500 tokens, a manual section) and smaller **child** chunks inside them (for example about 300 tokens).
- The search runs over the child chunks, so matching is precise.
- The knowledge base then returns the parent chunk that contains the matched child, so the model sees the full surrounding section.
Example: a question matches one paragraph about torque settings; the model receives the whole "Assembly procedure" section with the steps before and after it. Bedrock Knowledge Bases offers this as a built-in chunking strategy with configurable parent and child sizes.
W: Hierarchical chunking: precise matching on small child chunks plus returning their parent sections gives the model the surrounding context that plain fragments lack.
X: A=Smallest fixed chunks, no overlap: this makes fragments even shorter and cuts sentences at boundaries, worsening the missing-context problem.
B=No chunking, one vector per manual: a single vector for a long manual blurs all topics together, retrieval becomes imprecise, and the whole manual may not fit in the prompt.
D=Random chunk boundaries: random splits cut ideas unpredictably and make results inconsistent; they add no context.
T: When retrieved fragments lack context, use hierarchical chunking to search small chunks but return their parent sections.

@ Q002848 explain
G: ## Semantic chunking
**Fixed-size chunking** splits text every N tokens regardless of content, so a chunk can end in the middle of an explanation and the next one starts without its subject.
**Semantic chunking** splits where the meaning changes. It embeds sentences (or small groups), compares neighbors, and starts a new chunk where similarity drops sharply, which usually marks a topic change.
- Chunks follow the document's natural sections, even when sections vary in length.
- Each chunk tends to hold one complete idea, which improves retrieval precision.
- In Bedrock Knowledge Bases it is a built-in strategy with settings such as maximum tokens, buffer size and a breakpoint percentile threshold. It adds some ingestion cost because a model is invoked during chunking.
W: Semantic chunking: boundaries are placed where the topic changes, so chunks match the variable-length sections and ideas are no longer split mid-thought.
X: A=No chunking: whole-document embeddings mix many topics into one vector, reducing retrieval precision and producing very large contexts.
B=Every 100 characters: this is an even smaller fixed split that cuts through words and sentences, making the mid-thought problem worse.
C=Larger fixed-size chunks: bigger chunks split less often but still cut at arbitrary points and mix unrelated topics, because size, not meaning, sets the boundary.
T: For documents with natural sections of varying length, semantic chunking keeps ideas intact where fixed-size chunking cuts them.

@ Q002854 explain
G: ## Two-stage retrieval with a reranker
Vector search is fast but approximate. It compares one question vector with each chunk vector separately, so the ranking is only roughly right. When only the top few chunks go to the model, relevant ones ranked 12th or 15th are lost.
A **reranker** adds a second stage:
- Retrieve a wider candidate set, for example 20 or 50 chunks.
- The reranker model reads the question and each candidate together and scores how well that chunk answers it. This is slower per chunk but more accurate.
- Keep the top few after reranking and send them to the model.
Amazon Bedrock provides reranker models through the `Rerank` API and as a reranking configuration in knowledge base queries.
W: Reranker model: it reorders the 20 candidates by true relevance to the question, so the best chunks move to the top and reach the model.
X: A=Remove metadata: metadata does not cause poor ranking, and removing it only takes away useful filtering.
C=Larger chunks: fewer, larger chunks mix more content per chunk and do not fix the ranking error; relevant text can still be ranked low.
D=Lower temperature: temperature changes generation randomness; it cannot restore chunks that were cut off before generation.
T: When relevant chunks are retrieved but ranked too low, add a reranker to reorder candidates before generation.

@ Q002855 explain
G: ## Why exact identifiers need keyword search
Embedding models capture meaning, not exact strings. "Section 14.3(b)" and "Section 14.3(c)" look almost identical to a vector model, and the clause number may carry little semantic weight, so pure vector search can return the wrong section.
**Keyword (lexical) search**, such as BM25, matches exact tokens and scores rare terms highly, so a precise clause reference finds the chunk that contains it.
**Hybrid search** runs both searches and merges the scores:
- Keyword matching catches exact identifiers, codes and names.
- Semantic matching catches paraphrased questions such as "termination notice rules".
In Bedrock Knowledge Bases with a supported store such as OpenSearch Serverless, the search type can be set to `HYBRID` (the `overrideSearchType` setting) in the retrieval configuration.
W: Hybrid search: keyword matching finds exact clause numbers while semantic matching still handles natural-language questions, fixing the misses of pure vector search.
X: A=Random sampling: random chunks ignore the query entirely and make results worse.
B=More output tokens: output length affects the answer's size, not which chunks retrieval finds.
D=Larger embedding model: a bigger model still encodes meaning rather than exact tokens, so similar-looking clause numbers remain hard to separate.
T: For exact identifiers like clause numbers, add keyword matching through hybrid search; better embeddings alone will not fix it.

G: ## Query decomposition
A compound question like "Compare the warranty terms of the X100 and the Z300" becomes one query vector that sits between the two topics. Retrieval tends to favor one product and misses the other.
**Query decomposition** first splits the question into simpler sub-queries:
- "What are the warranty terms of the X100?"
- "What are the warranty terms of the Z300?"
Each sub-query is retrieved separately, the results are combined, and the model answers the comparison with evidence for both products.
Bedrock Knowledge Bases offers this as a query transformation option (`QUERY_DECOMPOSITION`) in the orchestration settings of `RetrieveAndGenerate`.
W: Query decomposition: breaking the compound question into one sub-query per product ensures retrieval finds chunks for both, so the comparison is complete.
X: B=Higher similarity threshold: a stricter cutoff returns fewer chunks and does not add the missing product; it may even drop the few relevant ones.
C=Shorter system prompt: the problem is in retrieval, which happens before the prompt is used; prompt length does not change which chunks are found.
D=Disable metadata filtering: filtering was not excluding the second product, and disabling it only adds less relevant results.
T: For multi-part questions, decompose them into sub-queries so each part gets its own retrieval.

Bedrock Knowledge Bases offers two query APIs: `Retrieve` returns chunks only, and `RetrieveAndGenerate` retrieves chunks and generates an answer in one call.

G: ## Retrieve versus RetrieveAndGenerate
Bedrock Knowledge Bases supports two patterns:
- **`RetrieveAndGenerate`** is managed: one call retrieves chunks, builds the prompt, calls the model and returns an answer with citations. Some customization is possible through prompt templates, but the orchestration is AWS-managed.
- **`Retrieve`** only returns the relevant chunks with scores and metadata. The application then builds the prompt itself and calls the model with `InvokeModel` or the `Converse` API.
With `Retrieve`, the application decides everything: which chunks to keep, how to order them, how to add conversation history, and how to apply business rules (for example "never quote prices older than 30 days" or "prefer the customer's region").
W: Retrieve, then build the prompt and invoke the model: the application controls exactly how chunks, history and rules are combined before the model call, which is the requirement.
X: B=All documents in the system prompt: this skips retrieval, quickly exceeds the context window, raises cost and latency on every call, and dilutes relevant content.
C=Batch inference for chat questions: batch inference is asynchronous and meant for large offline jobs, so it cannot deliver interactive replies.
D=Edit RetrieveAndGenerate output afterward: changes after generation cannot affect how the prompt was built, so there is no control over what the model saw.
T: When you need full control over prompt assembly, use `Retrieve` and call the model yourself instead of the managed `RetrieveAndGenerate`.

G: ## Keeping answers tied to relevant evidence
Loosely related chunks lead to answers that drift from the question or add unsupported claims. Two controls work at different stages:
- **Before generation, a reranker** scores each retrieved chunk against the question and keeps only the top few, so weakly related chunks never reach the model.
- **After generation, a contextual grounding check** in Amazon Bedrock Guardrails scores the answer for **grounding** (is it supported by the source passages?) and **relevance** (does it answer the question?). Answers below the configured thresholds are blocked or replaced with a safe message.
Example: retrieval returns 10 chunks; the reranker keeps the best 3; the answer is generated; the grounding check blocks it if it states facts not found in those 3 chunks.
W: C=Contextual grounding check: it verifies that each answer is supported by the retrieved sources and relevant to the query, and blocks responses that are not.
E=Reranker with top results only: it removes loosely related chunks before generation, so the model works from the most relevant evidence.
X: A=Higher temperature: more randomness makes the model more likely to stray from the sources, not less.
B=Top-k of 100: more chunks bring in even more loosely related content and raise cost and latency.
D=Remove grounding instruction: telling the model less about staying within the sources increases unsupported answers.
T: Filter weak chunks with a reranker before generation and verify answers with a contextual grounding check after it.
