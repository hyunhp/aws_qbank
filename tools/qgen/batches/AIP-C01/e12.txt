@ Q002885 explain
G: ## Retrieving from more than one store
Many assistants need knowledge that lives in different places: product manuals in one index, resolved tickets in another. Retrieval-augmented generation (RAG) works best when each source is searched with the same user question and the results are then combined.
- **Fan out**: send the query to each store (for example two Amazon Bedrock knowledge bases, or a vector index plus a keyword index) and take the top candidates from each.
- **Merge**: combine the candidate lists and remove duplicates. Scores from different stores are not directly comparable, so a simple fusion method or a reranker is used.
- **Rerank**: a reranker model (Amazon Bedrock offers rerank models through its `Rerank` API) scores every candidate against the question, so the best passages win regardless of which store they came from.
- **Generate**: only the top few passages go into the prompt.
Example: for "printer shows error E42", the manual explains what E42 means and a past ticket shows the fix that worked; the reranker keeps both.
W: Query both sources, merge, rerank: each store contributes its best matches, and reranking picks the most relevant passages across both before the model answers, so neither the documented procedure nor the proven fix is lost.
X: A=One giant ticket document: embedding thousands of tickets as a single vector averages away their meaning, so no query matches any specific fix, and the document cannot fit into a prompt as context anyway.
C=Manuals only: resolved tickets often hold the real-world workarounds and edge cases the manuals lack; informal wording is handled well by semantic embeddings, so excluding them throws away useful answers.
D=Model guesses the source: without a retrieval call the model has no access to either store and can only answer from its training data, which is exactly the hallucination risk RAG is meant to remove.
T: Search every relevant store, then merge and rerank so the best evidence wins; do not collapse sources into one blob or drop one.

@ Q002886 explain
G: ## Why prompts are not fully portable
Each foundation model is trained with its own data, instruction format and alignment, so the same prompt text can behave differently. One model follows a "respond in JSON" instruction exactly; another adds prose around it or ignores a formatting example.
## Managing prompts per model
- Keep a **test set** of representative inputs with expected outputs or scoring criteria.
- When changing models, run the current prompt against the test set, then adjust wording, examples, system instructions and inference parameters until quality matches or beats the baseline.
- Store each tuned prompt as a **versioned, model-specific variant**. Amazon Bedrock Prompt Management supports prompt versions and variants that pair a prompt with a model and settings, so an application can reference a specific version.
- Re-run the evaluation when a model version changes, not only when the model family changes.
Example: a summarization prompt tuned for one model scores 4.5/5; on a new model it scores 3.2 until few-shot examples are rewritten, then 4.6.
W: Re-tune, re-evaluate and version per model: prompt behavior is model-specific, so measuring quality on the new model and keeping a versioned variant for each model is the only way to switch models without silent regressions.
X: B=Switch back permanently: this avoids the symptom but locks the application to one model, giving up better cost, latency or quality from newer models, and it does not remove prompt maintenance for future model versions.
C=Remove all instructions: instructions are what steer format, tone and constraints; stripping them makes every model less predictable, not more consistent.
D=Assume portability: shipping the prompt unchanged is exactly what produced the poor results; without re-evaluation the regression reaches users.
T: Treat a prompt as tuned for one model: evaluate and adjust it on each new model and keep the variants versioned.

G: ## Evidence that a GenAI system meets policy
Internal AI policies usually ask two questions before launch: have the risks been identified and mitigated, and how do we know the system performs acceptably? The design phase should produce documents that answer both, so reviewers can approve against written evidence rather than opinions.
- A **risk assessment** lists what can go wrong: sensitive data in prompts or outputs, harmful or biased content, prompt injection, misuse by users, and over-reliance on answers. For each risk it records likelihood, impact, owner and the mitigation (for example Amazon Bedrock Guardrails, access controls, human review).
- An **evaluation plan** defines the test data, the metrics (accuracy, faithfulness, toxicity, refusal rate) and the **acceptance thresholds** that must be met before launch, such as "faithfulness at least 0.9 on the golden set".
After launch, the same thresholds become the monitoring baseline.
W: C=Risk assessment covering data, safety and misuse: it documents which risks exist and how each is mitigated, which is the core evidence an AI policy review asks for.
E=Evaluation plan with acceptance thresholds: it turns "the system works" into measurable pass or fail criteria, so the team can prove the system meets the bar before launch.
X: A=Seating plan: where the team sits during launch week has no bearing on whether the system is safe, fair or accurate.
B=Marketing plan: a launch campaign describes how the product is promoted, not how its risks are controlled or its quality is measured.
D=List of models not evaluated: models that were never tested provide no evidence about the system actually being launched.
T: Policy compliance needs a documented risk assessment plus an evaluation plan with thresholds; business and logistics documents prove nothing about safety or quality.

@ Q002888 explain
G: ## Cleaning web content before chunking
A web page contains much more than its article: navigation menus, headers, footers, cookie banners, "related links" and ads. If this boilerplate is chunked and embedded, it causes two problems.
- **Noise in every chunk**: the same menu text appears on every page, so many chunks look similar and a query like "cookie settings" or "contact us" matches pages that have nothing to do with the question.
- **Diluted meaning**: a chunk that is half footer has an embedding pulled away from its real topic, so relevant content ranks lower.
The fix is a preprocessing step: parse the HTML, keep the main content (for example the `article` or `main` element, or use a content-extraction library), drop repeated boilerplate, then chunk and embed. On AWS this can run in an AWS Lambda function in the ingestion pipeline; Amazon Bedrock knowledge bases also allow a custom transformation Lambda function during ingestion.
W: Extract main content and strip boilerplate before chunking: chunks then contain only meaningful text, so their embeddings reflect the page topic and retrieval precision improves.
X: A=Embed only titles: titles are short and often vague, so most of the facts users ask about are never indexed and cannot be retrieved.
B=Increase chunk size: the boilerplate is still inside every chunk; larger chunks also blur several topics into one embedding and use more of the prompt budget.
C=Keep boilerplate: menus and cookie banners describe the site, not the answer; they add repeated noise that hurts ranking rather than giving the model useful context.
T: Clean the source before chunking; changing chunk size or indexing less text does not remove noise that is already in the content.

@ Q002889 explain
G: ## Embeddings and a shared vector space
An embeddings model turns input into a vector of numbers so that similar meanings land close together. Search then means "find the stored vectors nearest to the query vector".
- A **text embeddings model** only accepts text, so product photos cannot be embedded at all.
- A **multimodal embeddings model** (for example Amazon Titan Multimodal Embeddings on Amazon Bedrock) accepts text, images or both and maps them into the **same** vector space. A photo of a red running shoe and the text "red running shoe" produce nearby vectors.
This enables cross-modal search:
- text to image: a shopper types "leather backpack with laptop sleeve" and gets matching product photos;
- image to image or image to text: a shopper uploads a photo and finds similar products and their descriptions.
The vectors are stored in a vector store such as Amazon OpenSearch Service and queried with k-nearest-neighbor search.
W: Multimodal embeddings model: it encodes both images and text into one shared vector space, so a text query can be compared directly with image vectors and vice versa.
X: B=Text-only embeddings: it cannot take an image as input, so product photos would have no vectors and could not take part in search.
C=Speech recognition: it converts audio into text; it produces no embeddings and has nothing to do with images.
D=Image generation: it creates new images from prompts; it does not produce vectors for searching existing images and text.
T: Cross-modal search needs one model that embeds every modality into the same space; a text-only model leaves images out.

@ Q002890 explain
G: ## Retrieval gap or generation gap?
A RAG answer can fail at two stages:
- **Retrieval**: the right chunks were never found.
- **Generation**: the right chunks were in the prompt, but the model ignored, shortened or misused them.
Here the chunks are already correct, so the problem most likely sits in generation. Two steps address it.
- **Measure it**: Amazon Bedrock evaluations can score retrieve-and-generate output with metrics such as **faithfulness** (is the answer supported by the retrieved context?) and **completeness** (does it cover everything the question needs?). Low completeness with good context confirms a generation problem and gives a baseline to compare fixes.
- **Fix the prompt**: tell the model explicitly to use all relevant retrieved details, to list every step or condition found in the sources, and to say when information is missing. Structured output formats (for example a required section per item) also reduce omissions.
Re-run the evaluation after each prompt change to confirm the improvement.
W: D=Evaluate faithfulness and completeness: it confirms that retrieval is fine and generation is dropping details, and it gives a measurable baseline for checking fixes.
E=Adjust the generation prompt: since the needed details are already in the context, instructing the model to use all relevant details directly targets the omissions.
X: A=Disable citations: citations do not cause missing details; removing them only makes answers harder to verify.
B=Replace the vector store: the store already returns the correct chunks, so changing the engine costs effort without touching the stage that fails.
C=Retrieve only one chunk: key details are often spread across several chunks; cutting to one would remove information and make omissions worse.
T: When retrieval is already correct, measure and fix generation; do not rebuild the retrieval layer.

@ Q002891 explain
G: ## How Bedrock agents call APIs
An agent in Amazon Bedrock Agents reasons about a user request and decides which action to take. Actions are defined in **action groups**.
- The action group describes the operations the agent can call, either with an **OpenAPI schema** (paths, parameters, descriptions) or with simpler **function details**.
- The descriptions tell the model when to use each operation, for example `GET /orders/{orderId}` "returns the current status of an order".
- When the agent chooses the action, it fills in parameters from the conversation and invokes the **AWS Lambda function** attached to the action group (or returns control to the application).
- The Lambda function calls the internal REST API, gets the live status and returns the result, which the agent uses to answer.
Example: "Where is order 1234?" leads the agent to call `getOrderStatus` with `orderId=1234`; Lambda queries the order service and returns "shipped, arriving Thursday".
W: Action group with OpenAPI schema and Lambda: the schema tells the agent what the operation does and which parameters it needs, and Lambda performs the real API call, so answers use live order data.
X: A=Knowledge base of nightly JSON: indexing responses once a day gives stale status and does not call the API per request; knowledge bases are for retrieving documents, not executing operations.
C=Guardrail policy: guardrails filter or block content in inputs and outputs; they cannot call an API or return order data.
D=Order states in instructions: a list of possible states tells the model what statuses exist, not the status of a specific order, which only the live API can provide.
T: Agents take actions through action groups (schema plus Lambda or return of control); knowledge bases and guardrails do not call APIs.

G: ## Return of control in Bedrock Agents
Normally an action group runs an AWS Lambda function that the agent invokes directly. With **return of control**, the action group is configured so that the agent does not execute anything itself.
- The agent decides which action to call and with which parameters (for example `issueRefund` with `orderId` and `amount`).
- Instead of invoking Lambda, the `InvokeAgent` response returns this action and its parameters to the client application.
- The application can show a confirmation to the user, apply its own business checks, call the refund API with its own credentials, and send the result back to the agent in the next `InvokeAgent` request, so the conversation continues.
This fits cases where the action is sensitive, needs user approval, or must run inside the application's own systems.
W: Return of control: the agent hands the chosen action and parameters to the application, which collects user confirmation and executes the refund itself, exactly the required pause.
X: A=Longer session timeout: it only keeps the session alive longer; the agent would still run the action without any confirmation step.
B=Higher temperature: temperature changes how random the model's text is; it adds no pause and makes decisions less predictable, which is the opposite of what a refund needs.
D=Knowledge base on the action group: knowledge bases supply documents for answers; they cannot stop an action or hand execution to the application.
T: When the application, not the agent, must confirm and run an action, use return of control instead of a Lambda executor.

G: ## A managed front door for agent tools
Agents need tools: internal REST APIs, AWS Lambda functions and servers that speak the **Model Context Protocol (MCP)**, an open standard for describing and calling tools. Wiring each tool into each agent, with its own authentication, quickly becomes unmanageable.
**Amazon Bedrock AgentCore Gateway** provides one managed endpoint for this.
- It turns APIs (described by OpenAPI or Smithy models) and Lambda functions into MCP-compatible tools, and can also connect existing MCP servers as targets.
- Agents connect to the gateway as a single MCP endpoint and discover the available tools, including through semantic tool search.
- **Inbound authentication** checks which agent or user may call the gateway (for example with OAuth tokens); **outbound authentication** handles the credentials the gateway uses to call each target, such as API keys or OAuth, managed with AgentCore Identity.
Example: one agent reaches a ticketing MCP server and an internal inventory API through the same gateway without storing either set of credentials.
W: AgentCore Gateway: it is built to expose APIs, Lambda functions and MCP servers as tools for agents behind one endpoint, with inbound and outbound authentication managed for you.
X: B=API Gateway usage plans only: usage plans set throttling and quotas per API key; they do not turn APIs into agent tools, speak MCP to agents, or aggregate existing MCP servers.
C=CloudFront Functions: these are lightweight edge scripts for viewer request and response changes such as header rewrites; they cannot host tool catalogs or broker agent tool calls.
D=App Mesh routing: App Mesh manages service-to-service traffic inside a microservice mesh (and AWS has announced its end of support); it never provided agent tool discovery or MCP support.
T: For agents calling MCP servers and APIs through one authenticated endpoint, use AgentCore Gateway; generic API, edge or mesh routing services are not tool gateways.

@ Q002894 explain
G: ## Running code that a model writes
Agents doing analysis often write code (for example Python with pandas) to compute results instead of estimating them. That code is **untrusted**: it may contain bugs, consume excessive resources, or be influenced by prompt injection in the data it reads.
The safe pattern is a **sandbox**: an isolated environment with no access to production networks or credentials, limited resources, and a clean state per session.
**Amazon Bedrock AgentCore Code Interpreter** is a managed sandbox for this.
- The agent sends code to a code interpreter session and receives output, files and errors back.
- Execution is isolated from the agent's own runtime and from other systems; network access can be restricted.
- It supports common languages such as Python and can work with files and data uploaded into the session.
Example: a research agent loads a CSV into the session, runs a regression, and returns the coefficients and a chart, while the production database is never reachable from the sandbox.
W: Managed sandboxed code interpreter: generated code runs in isolation, so the agent gets real computed results without any path to production systems.
X: A=Run on the production database host: untrusted code there could read or delete data, exhaust resources or be abused through prompt injection, which is the exposure the scenario forbids.
C=Email code to developers: a human round trip adds hours or days per step, which breaks a long-running autonomous agent and does not scale.
D=Estimate results instead: models are unreliable at exact calculations on real data; skipping execution trades safety for wrong numbers.
T: Execute agent-generated code in an isolated, managed sandbox; never on production hosts and never by guessing.

@ Q002896 explain
G: ## SageMaker AI inference options by traffic shape
- **Real-time inference**: always-on instances, low latency, pay while they run even when idle.
- **Serverless inference**: scales with requests and costs nothing when idle, but limits request payloads to 4 MB, processing time to 60 seconds, and offers no GPU support.
- **Asynchronous inference**: requests are queued; the input is read from Amazon S3 (payloads up to 1 GB) and the result is written back to S3, processing can take up to an hour, and the endpoint can **scale down to zero instances** when the queue is empty, starting again when new requests arrive.
- **Batch transform**: offline jobs over whole datasets.
Example: a document-analysis model gets a few jobs per hour, each a 200 MB file taking 5 minutes. Asynchronous inference queues them, scales up when work arrives, returns results to S3 with an optional Amazon SNS notification, and scales to zero between bursts.
W: Asynchronous inference with scale to zero: it accepts large payloads through S3, allows long processing times, and removes all instance cost during idle periods.
X: A=Real-time with a fixed fleet: the instances bill continuously through the long idle periods, and long-running requests fit poorly with synchronous request timeouts.
B=Serverless inference: request payloads are capped at 4 MB and processing at 60 seconds, so large payloads that take minutes to process would fail.
C=Multi-model endpoint with GPUs always on: hosting several models on one endpoint helps density, but always-on GPUs keep billing during idle time, which is the cost to eliminate.
T: Large, slow, sporadic requests call for asynchronous inference that scales to zero; serverless inference is limited to small, fast requests.

@ Q002897 explain
G: ## Safe model rollouts on SageMaker AI
Replacing a model on a live endpoint is risky: a new version might have higher latency or errors. **Deployment guardrails** for SageMaker AI endpoints make updates gradual and reversible.
- The update uses **blue/green deployment**: a new (green) fleet is created next to the current (blue) one.
- **Traffic shifting modes**: all at once, **canary** (a small share such as 10% first, then the rest), or **linear** (equal steps).
- During a **baking period**, Amazon CloudWatch alarms you choose (for example on 5xx errors or model latency) are watched.
- If an alarm fires, SageMaker AI **automatically rolls back** traffic to the blue fleet; if not, it completes the shift and removes the old fleet.
Example: a new summarization model gets 10% of traffic for 15 minutes; an error-rate alarm triggers and all traffic returns to the previous version without manual action.
W: Deployment guardrails with canary traffic shifting: only a small share of traffic sees the new version first, and CloudWatch alarms trigger an automatic rollback if it misbehaves.
X: A=Manual new endpoint per release: it needs separate traffic switching and has no built-in alarm-based rollback, so recovery depends on someone noticing and acting.
C=Notebook calling both endpoints: a notebook is an interactive development tool, not a production traffic router, and it cannot shift user traffic or roll back automatically.
D=All-at-once update: every user hits the new version immediately, so a bad release affects all traffic before anyone can react.
T: Canary shifting with alarm-based auto-rollback limits the blast radius of a new model; all-at-once or manual switches do not.

G: ## Querying SaaS data at request time
Business data often lives in SaaS systems such as Salesforce (accounts, opportunities) and ServiceNow (incidents, change requests). There are two ways to give an assistant access to it:
- **Copy it**: export records into AWS and index them. This duplicates sensitive data, needs sync jobs, and answers are only as fresh as the last sync.
- **Query in place**: give the assistant **tools** that call the SaaS APIs when a question needs data. On AWS these tools can be agent action groups backed by AWS Lambda, or targets behind Amazon Bedrock AgentCore Gateway, using OAuth credentials scoped to what the assistant may read.
With the second approach, the model decides which tool to call ("get open incidents for customer X"), the tool fetches only the needed records live, and the answer reflects current data. The SaaS system's own permissions still apply, and no bulk copy exists to secure.
W: Agent tools or connectors queried at request time: the assistant fetches only the records a question needs, straight from the source, so data stays current and is never bulk-copied into AWS.
X: A=Monthly fine-tuning on all records: training embeds data into model weights, where it is stale within days, cannot be removed per record, and may be exposed to users who lack access; it also copies everything.
B=Employees paste records: manual copying is slow, error-prone and bypasses access controls, and it moves sensitive data through chat by hand.
C=Nightly export into a vector store: this copies all records into AWS, which the requirement forbids, and answers lag up to a day behind the source.
T: To avoid copying SaaS data, let the assistant call the systems through tools at request time instead of exporting, pasting or training on records.

G: ## Loose coupling with events
In **tight coupling**, each producer knows about and calls each consumer directly, so adding a consumer or taking one offline affects every producer. In **event-driven integration**, producers only publish facts ("ticket created", "order placed") and do not know who reacts.
**Amazon EventBridge** implements this with event buses.
- Producers send JSON events to a bus with `PutEvents`, or SaaS partners and AWS services send them automatically.
- **Rules** match events by pattern, for example `"detail-type": ["TicketCreated"]` with `"priority": ["high"]`.
- Each rule routes matching events to **targets**: a Lambda function that calls a model, a Step Functions workflow, an SQS queue and more.
- Retries, dead-letter queues and archive and replay add resilience.
Example: a "TicketCreated" event triggers a Lambda function that summarizes and classifies the ticket with Amazon Bedrock; a new consumer can later subscribe without changing the ticket system.
W: Event-driven integration with EventBridge: producers emit events without knowing the consumers, and rules route them to the GenAI service in near real time, so systems stay decoupled and the service reacts promptly.
X: B=Nightly FTP batch transfer: the service would react up to a day late, and each system needs custom file export logic tied to the GenAI service.
C=Direct synchronous calls: each system must know the GenAI endpoint and wait for it, so slow model calls or outages propagate back to the producers; this is tight coupling.
D=Shared table polled every few seconds: constant polling wastes resources, adds latency, and couples every system to one database schema.
T: Publish events and route them with EventBridge rules; direct calls, polling and nightly batches couple systems or delay reactions.

G: ## Streaming model output
A large answer can take many seconds to generate. With a normal request, the user sees nothing until the last token is ready. **Streaming** returns the answer in pieces as the model produces them, so text starts appearing almost immediately, which greatly reduces perceived latency.
Amazon Bedrock offers streaming versions of its runtime APIs:
- `ConverseStream`: the streaming form of the unified Converse API. The response is an event stream with events such as `messageStart`, `contentBlockDelta` (each piece of text), `messageStop` and `metadata` (token usage).
- `InvokeModelWithResponseStream`: the streaming form of `InvokeModel`, using the model provider's native payload format.
The backend reads each delta and forwards it to the browser, for example over a WebSocket or server-sent events.
W: ConverseStream or InvokeModelWithResponseStream: both return tokens incrementally while the model generates, so the chat UI can render text as it arrives.
X: A=Batch inference job per message: batch inference processes files of prompts from S3 asynchronously, typically over minutes to hours, which is unusable for interactive chat.
B=Model evaluation job per answer: evaluation jobs score model quality on datasets offline; they do not serve user requests at all.
D=Synchronous Converse awaited in full: `Converse` returns only after the whole response is generated, so the user waits for the full latency before seeing anything.
T: To show tokens as they are generated, call a streaming API; synchronous or offline jobs deliver only complete results.

G: ## Why throttling happens and how to handle it
Amazon Bedrock enforces quotas per account and Region, such as requests per minute and tokens per minute for each model. A burst that exceeds them returns `ThrottlingException`. Two techniques address it together.
- **Retry with exponential backoff and jitter**: wait, for example, 200 ms, then 400 ms, then 800 ms, adding a random amount each time. Backoff gives the quota time to refill; jitter spreads clients out so they do not all retry at the same moment. AWS SDKs include retry modes that do this.
- **Buffer and pace**: put incoming requests into a queue (for example Amazon SQS) and have workers send to Bedrock at a controlled rate or with limited concurrency. Bursts are absorbed by the queue instead of turning into errors.
If the steady workload still exceeds quotas, request a quota increase, use cross-Region inference, or buy Provisioned Throughput.
W: D=Queue and control the send rate: buffering turns a traffic spike into a steady stream that stays within the quota, so fewer requests are throttled in the first place.
E=Exponential backoff with jitter: throttled requests are retried after growing, randomized delays, which lets capacity recover and avoids synchronized retry storms.
X: A=Synchronous batch inference: Bedrock batch inference is asynchronous and job-based, taking minutes to hours, so it cannot serve these calls and there is no synchronous batch mode.
B=Immediate tight-loop retries: instant retries add even more requests during the overload, keep the rate above the quota and prolong throttling.
C=Increase max tokens: max tokens limits output length per call; it does not reduce the number of calls and can increase tokens-per-minute usage.
T: Handle throttling by smoothing demand (queue and pace) and retrying politely (backoff with jitter), not by retrying harder.

G: ## One interface for many models
Each model provider on Amazon Bedrock has its own native request and response format for `InvokeModel`: different field names for messages, system prompts, inference parameters and tool calls. Code written for one model does not work for another.
The **Converse API** (`Converse` and `ConverseStream`) provides one consistent format:
- `messages`: a list of turns with `role` (`user` or `assistant`) and `content` blocks;
- `system`: system prompts; `inferenceConfig`: `maxTokens`, `temperature`, `topP`;
- `toolConfig`: a list of tools, each with a `toolSpec` (name, description, JSON `inputSchema`). When the model wants a tool, the response has `stopReason` `tool_use` and a `toolUse` block; the application runs the tool and sends back a `toolResult`.
Switching between supported Claude, Llama and Nova models then only means changing the `modelId`. Feature support such as tool use still varies by model, so check the supported features list.
W: Converse API with toolConfig: one message format and one tool-use contract work across supported models, so the same code can call different model families by changing only the model ID.
X: A=InvokeModel with each provider's body: every provider has a different payload and tool-call format, so the code needs separate branches per model family.
B=Separate provider SDKs: this multiplies dependencies, authentication methods and code paths, and each SDK covers only its own provider's models, so message and tool formats still differ per family.
D=Custom HTTP client per family: it rebuilds request signing and format translation by hand for each model, which is exactly what Converse already standardizes.
T: Converse normalizes messages and tool use across models; InvokeModel keeps each provider's native format.

G: ## A secure front door for a mobile GenAI backend
A mobile app runs on devices you do not control, so anything embedded in it can be extracted. The backend therefore needs to authenticate each user and protect itself from overload.
**Amazon API Gateway** provides this front door.

- The backend (for example an AWS Lambda function) calls Amazon Bedrock with its own IAM role, so no AWS credentials live in the app.
Example: a signed-in user sends a prompt with their token; API Gateway validates it, applies throttling, and invokes Lambda, which calls Bedrock and returns the answer.

X: A=S3 bucket with public write access: anyone on the internet could write objects, there is no user identity, and S3 is not a request and response API front end.

D=Public Lambda function URL with no authentication: anyone who finds the URL can invoke the function and run up model costs, with no per-user identity or throttling controls.

G: ## Orchestrating a multi-step document workflow
The workflow has several ordered steps (extract, classify, summarize), each of which can fail and need retries, plus a **human review** step that may take hours or days for low-confidence results.
**AWS Step Functions** fits this shape.
- Each step is a state that calls a service, for example Amazon Textract for extraction and Amazon Bedrock for classification and summarization, with built-in retries and error handling.
- A **Choice** state checks the confidence score and routes low-confidence documents to review.
- The review state uses the **wait for task token** pattern (`.waitForTaskToken`): Step Functions passes a token to a review task (for example a queue or a review app) and pauses. When the reviewer finishes, the app calls `SendTaskSuccess` with the token, and the workflow continues.
- Standard workflows can run for up to one year, so long reviews are not a problem, and each run has a visual execution history.
W: Step Functions with a task token for human review: it orchestrates the steps with retries and pauses the execution cheaply until a reviewer responds, however long that takes.
X: B=Single Lambda running for days: a Lambda invocation stops after at most 15 minutes, so it cannot wait for humans or run for days.

G: ## Handling bursts with a queue and paced workers
When thousands of documents arrive at once, calling the model for each immediately would exceed model throughput quotas (requests and tokens per minute) and cause throttling and failures. The one-hour deadline gives room to spread the work out.
- **Queue**: each upload places a message in **Amazon SQS**. The queue durably holds the backlog, so no document is lost during a burst, and failed messages can be retried or moved to a dead-letter queue.
- **Scalable workers**: AWS Lambda functions (or containers) poll the queue and summarize documents with Amazon Bedrock.
- **Controlled concurrency**: cap how many workers run at once, for example with the **maximum concurrency** setting on the Lambda SQS event source, so the request rate stays under the model quota.
Example: 6,000 documents arrive in 5 minutes; 50 concurrent workers each summarize a document in about 20 seconds, clearing the backlog in roughly 40 minutes without throttling.
W: C=Controlled worker concurrency: limiting parallel calls keeps traffic within the model's throughput quotas, avoiding throttling while still meeting the deadline.
E=Queue in SQS with scalable workers: the queue absorbs the burst durably, and workers drain it steadily, so every document gets processed within the hour.
X: A=Drop documents during bursts: every document must be summarized, so discarding them violates the requirement.
B=Synchronous call in the upload handler: uploads become slow and fail when the model throttles during a burst, and there is no buffer to retry from.
D=One long-running request for all documents: one failure or timeout loses the whole run, and a single request cannot parallelize thousands of documents in time.
T: Absorb bursts with a queue and pace workers to the model's limits; do not call synchronously or drop work.

When a system has several specialized agents, such as billing, technical support and account management, users still want one place to ask questions. **Multi-agent collaboration** in Amazon Bedrock Agents provides this.

G: ## Many small fine-tuned variants, one base model
Parameter-efficient fine-tuning methods such as **LoRA** do not change the whole model. They train a small **adapter** (often megabytes) that is applied on top of a shared base model (often many gigabytes).
If each variant gets its own GPU endpoint, dozens of copies of the same base model sit mostly idle. Sharing is much cheaper.
- **SageMaker AI inference components** let one endpoint host several models or adapters, each with its own resource allocation and scaling, including scaling individual components down to zero copies.
- **Multi-adapter (LoRA) serving** loads the base model once and applies the requested adapter per request, so dozens of variants share the same GPU memory and instances.
Example: 40 customer-specific adapters on one base model run on two GPU instances instead of 40, and each request names the adapter to use.
W: Adapters on a shared endpoint: the base model is loaded once and variants are selected per request, so dozens of low-traffic models share a few instances instead of each paying for idle GPUs.
X: A=Own always-on GPU endpoint per variant: each variant pays for a full GPU instance that is idle most of the time, multiplying cost by the number of variants.
B=Merge variants into one prompt: fine-tuned behavior lives in trained weights; instructions in a prompt cannot reliably reproduce dozens of specialized behaviors and make every request longer.
C=Separate CPU-only Lambda functions: Lambda has no GPUs and limited memory and package size, so large language models run far too slowly or cannot be loaded at all.
T: Light-traffic variants of one base model belong on a shared endpoint serving adapters, not on dedicated GPU endpoints each.

G: ## Model APIs are stateless
A call to a model API such as the Amazon Bedrock `Converse` API is independent: the model keeps no memory of earlier requests. Everything the model should consider must be in the current request.
To hold a conversation, the **application** keeps the history and resends it.
- Store each user message and model reply, for example in memory for a session or in Amazon DynamoDB.
- On each new turn, send the `messages` list containing the relevant prior turns plus the new question.
- When history grows beyond the context window or becomes costly, keep the last N turns, summarize older turns into a short recap, or retrieve only relevant earlier facts.
Managed options such as Amazon Bedrock AgentCore Memory or session features in Bedrock Agents handle this storage for you, but they still work by supplying context to each model call.
Example: turn 3 asks "And what about the second one?"; only because turns 1 and 2 are included can the model know what "the second one" refers to.
W: Send the relevant prior messages with each request: the model sees only what is in the current request, so resending history (or a summary) is how context carries across turns.
X: B=Higher temperature: temperature controls randomness in token selection; it adds no memory and makes replies less consistent.
C=New model identifier per turn: switching models does nothing to carry context, and each model is just as stateless as the last.
D=Rely on model memory: the model retains nothing between API calls, so earlier turns are simply unknown to it unless sent again.
T: With a stateless model API, the application owns conversation memory and sends the needed history on every call.
