# ANS-C01 batch 05: Domain 2 (network implementation) and Domain 4 (security, compliance, governance), detailed explanations

@ ANS-C01 D2 T2.1 advanced troubleshooting
S: A company reaches three VPCs (10.10.0.0/16, 10.20.0.0/16, 10.30.0.0/16) from its data center through a transit VIF, a Direct Connect gateway and a transit gateway. A fourth VPC, 10.40.0.0/16, was just attached to the transit gateway. The transit gateway route table associated with the Direct Connect gateway attachment already shows a propagated route for 10.40.0.0/16, but the on-premises router's BGP table does not contain that prefix and on-premises hosts cannot reach the new VPC. What should the network engineer change?
A: Add 10.40.0.0/16, or a summary such as 10.0.0.0/10 that covers it, to the allowed prefixes list of the association between the Direct Connect gateway and the transit gateway
B: Enable route propagation from the new VPC attachment into the transit gateway route table that is associated with the Direct Connect gateway attachment so BGP picks it up
C: Add a static route for 10.40.0.0/16 in the new VPC's subnet route tables that points to the transit gateway, so the transit gateway starts advertising the VPC over BGP
D: Raise the prefix limit on the transit VIF BGP session, because the Direct Connect gateway stops advertising new prefixes once more than three routes are sent to on-premises
K: A
G: ## What the on-premises router learns over a transit VIF
With a transit VIF, the path is: on-premises router → transit VIF → Direct Connect gateway → transit gateway. The transit gateway does **not** advertise its route table contents to the data center. Instead, the **association** between the Direct Connect gateway and the transit gateway carries an **allowed prefixes** list, and exactly those prefixes are advertised over BGP to on-premises.
- For a transit gateway association, the list is the advertisement: the prefixes are sent as written, whether they are single VPC CIDRs or a summary.
- A new VPC attached to the transit gateway is therefore invisible to on-premises until its range is covered by an allowed prefix.
## Two directions to check
- On-premises → VPC needs a BGP route on the customer router (allowed prefixes).
- Transit gateway → VPC needs a route in the transit gateway route table associated with the DX gateway attachment (here already present).
Example: allowed prefixes `10.10.0.0/16, 10.20.0.0/16, 10.30.0.0/16` never included `10.40.0.0/16`; adding it, or replacing the list with a summary, fixes the advertisement.
W: Update the allowed prefixes: for a Direct Connect gateway associated with a transit gateway, the allowed prefixes list is what AWS advertises to the customer router, so the new VPC's range must be added (or covered by a summary) before on-premises learns it.
X: B=Enable propagation into the DX route table: that route already exists, as the stem states. Propagation fills the transit gateway route table; it does not control what the Direct Connect gateway advertises to on-premises.
C=Static route in the VPC route table: VPC route tables steer traffic leaving the VPC. They never feed BGP advertisements toward the data center, so the customer router still has no route to 10.40.0.0/16.
D=Raise the prefix limit: there is no three-route limit. The transit VIF quota for prefixes advertised to on-premises is far higher, and a quota breach would not silently drop only the newest prefix.
T: Over a transit VIF, on-premises learns only what the Direct Connect gateway association's allowed prefixes list says; a propagated transit gateway route alone is not advertised.
V: AWS Direct Connect, AWS Transit Gateway, Amazon VPC

@ ANS-C01 D2 T2.1 advanced use-case
S: A bank reaches AWS through a 1 Gbps hosted Direct Connect connection. A new regulation requires IPsec encryption for all traffic between the data center and its VPCs, and the security team forbids any public IP addresses on either end of the tunnels. The VPCs are already attached to a transit gateway. Which TWO steps implement this? (Select TWO)
A: Associate a Direct Connect gateway with the transit gateway and connect it to the data center through a transit virtual interface on the hosted connection
B: Create a Site-to-Site VPN attached to the transit gateway with the private IPv4 outside IP address type and the Direct Connect gateway attachment as its transport
C: Create a public virtual interface and build a standard Site-to-Site VPN to the transit gateway's public tunnel endpoints over that public virtual interface
D: Enable MACsec on the hosted Direct Connect connection and configure a connectivity association key on the router to encrypt the link at Layer 2 instead
E: Attach an accelerated Site-to-Site VPN to the transit gateway so the tunnels ride the AWS edge network and never touch public internet addresses
K: A,B
G: ## IPsec over Direct Connect without public IPs
A classic Site-to-Site VPN uses public outside IP addresses for its tunnels. Running it over Direct Connect used to require a **public VIF**, which means public addresses.
**Private IP VPN** removes that: the VPN tunnels use private outside IP addresses and run over Direct Connect to a **transit gateway**.
## How it is built
- Connect the data center to a **Direct Connect gateway** with a **transit VIF**, and associate that DX gateway with the transit gateway. This creates a DX gateway attachment on the transit gateway.
- Create the VPN connection on the transit gateway with **outside IP address type** `PrivateIpv4` and choose the DX gateway attachment as the **transport attachment**.
- The customer gateway uses a private IP address that is reachable over the transit VIF.
Example: tunnel outside IPs `172.16.100.10` (customer) and `10.200.1.5` (AWS), all traffic encrypted end to end across the hosted 1 Gbps link.
W: A=DX gateway with a transit VIF: the transit VIF and the association between the DX gateway and the transit gateway create the DX gateway attachment, which is the private transport path the VPN needs.
B=Private IP VPN on that attachment: the VPN connection with private outside IPs uses the DX gateway attachment as transport, so IPsec protects all traffic and no public address is involved on either end.
X: C=Public VIF with a standard VPN: this does encrypt traffic, but the tunnels terminate on public AWS endpoints and the customer side needs a public IP, which the security team forbids.
D=MACsec: MACsec is available only on selected dedicated connections, not on a 1 Gbps hosted connection, and it is Layer 2 link encryption rather than the IPsec the regulation asks for.
E=Accelerated VPN: acceleration uses Global Accelerator with public anycast addresses over the internet; it is not supported for private IP VPN and does not use the Direct Connect link.
T: IPsec over Direct Connect with no public IPs means a transit VIF to a DX gateway on a transit gateway plus a private IP VPN that uses that attachment as transport, not a public VIF VPN or MACsec.
V: AWS Site-to-Site VPN, AWS Direct Connect, AWS Transit Gateway

@ ANS-C01 D2 T2.1 applied troubleshooting
S: A branch firewall that sits behind the building's NAT router is configured as the customer gateway for a Site-to-Site VPN. The customer gateway in AWS uses the NAT router's public IP address. The NAT router forwards UDP 500 and IP protocol 50 (ESP) to the firewall. Firewall logs show the first IKEv2 exchange completing, then no further replies from AWS, and both tunnels stay DOWN. What is the most likely fix?
A: Recreate the customer gateway in AWS with the firewall's private IP address, because AWS must see the real device address to complete IKE authentication
B: Forward UDP 4500 from the NAT router to the firewall and enable NAT traversal on it, because IKE and ESP move to UDP 4500 once NAT is detected
C: Switch the VPN connection from dynamic BGP routing to static routing, because BGP sessions cannot be established through a device that performs NAT
D: Increase the dead peer detection timeout on both tunnels, because the NAT router delays IKE packets long enough for AWS to treat the peer as dead
K: B
G: ## IPsec through NAT
IPsec normally uses UDP 500 for IKE and IP protocol 50 (ESP) for encrypted data. ESP has no ports, so a NAT device that rewrites addresses and ports breaks it.
**NAT traversal (NAT-T)** solves this:
- During the first IKEv2 exchange (`IKE_SA_INIT`) both peers send NAT detection payloads.
- If NAT is detected, the rest of IKE (including `IKE_AUTH`) and all ESP traffic move to **UDP 4500**, with ESP wrapped in UDP.
AWS Site-to-Site VPN supports NAT-T. The customer gateway in AWS must still use the **public** IP that AWS sees, which is the NAT router's address.
## Reading the symptom
The first exchange works on UDP 500, then the conversation switches to UDP 4500. If the NAT router does not forward UDP 4500 to the firewall, AWS replies never arrive and the tunnel stays DOWN.
Example: forward UDP 500 and UDP 4500 to the firewall; ESP forwarding is no longer needed once NAT-T is used.
W: Forward UDP 4500 and enable NAT-T: after NAT is detected in the first exchange, IKE authentication and ESP are carried in UDP 4500, so without that port forwarded the negotiation stops exactly where the logs show.
X: A=Use the private IP: AWS sends IKE to the customer gateway address, and a private RFC 1918 address is unreachable from the AWS public tunnel endpoints. The NAT router's public IP is the correct value.
C=Static routing: BGP runs inside the tunnel after IPsec is up. The tunnel never comes up here, so the routing type is irrelevant, and BGP works fine over NAT-T tunnels.
D=Longer DPD timeout: dead peer detection only matters after a tunnel is established. It cannot fix a negotiation that fails because replies on UDP 4500 are dropped.
T: A VPN peer behind NAT needs UDP 4500 forwarded for NAT-T; allowing only UDP 500 and ESP lets the first IKE exchange succeed and then stalls.
V: AWS Site-to-Site VPN

@ ANS-C01 D2 T2.2 applied troubleshooting
S: A company peers transit gateway TGW-A in us-east-1 (VPC 10.10.0.0/16) with TGW-B in eu-west-1 (VPC 10.20.0.0/16). Both transit gateways use their default route table for association and propagation, the peering attachment is accepted and available, and each VPC route table sends 10.0.0.0/8 to its transit gateway. Traffic between the VPCs still fails. Which TWO actions fix this? (Select TWO)
A: In TGW-A's default route table, add a static route for 10.20.0.0/16 that targets the inter-Region peering attachment to TGW-B
B: In TGW-B's default route table, add a static route for 10.10.0.0/16 that targets the inter-Region peering attachment to TGW-A
C: Enable route propagation for the peering attachment on both transit gateways so each side learns the other VPC CIDR dynamically
D: Configure a BGP session over the peering attachment with distinct ASNs on each transit gateway so routes are exchanged automatically
E: Add a route for the remote VPC CIDR in each VPC route table that targets the peering attachment ID instead of the local transit gateway
K: A,B
G: ## Transit gateway peering is static
An inter-Region transit gateway **peering attachment** connects two transit gateways over the AWS backbone. Unlike VPC, VPN and Direct Connect attachments, a peering attachment **does not support route propagation or BGP**. Each side must be told, with a **static route**, which prefixes live behind the peer.
## Where the routes go
- On TGW-A: `10.20.0.0/16 → peering attachment` in the route table used by the VPC attachment.
- On TGW-B: `10.10.0.0/16 → peering attachment` in its route table.
- Return traffic that arrives on the peering attachment is looked up in the route table associated with that attachment. Here that is the default route table, which already has the local VPC CIDR propagated.
Both directions are needed: with only one static route, packets reach the far VPC but replies are dropped.
W: A=Static route on TGW-A: peering attachments never propagate routes, so TGW-A only learns that 10.20.0.0/16 lives behind the peering attachment from a static route.
B=Static route on TGW-B: the reply direction needs the mirror route for 10.10.0.0/16 on TGW-B; with both routes in place, requests and replies are forwarded.
X: C=Propagation from the peering attachment: transit gateway peering attachments do not support route propagation, so there is nothing to enable; the routes must be static.
D=BGP over the peering: inter-Region transit gateway peering has no dynamic routing protocol. Distinct ASNs are good practice, but no BGP session is formed over the peering attachment.
E=VPC routes to the peering attachment: a VPC route table can target the transit gateway, not an attachment on it. The VPC routes are already correct; the gap is in the transit gateway route tables.
T: Inter-Region transit gateway peering needs a static route on each side pointing at the peering attachment; propagation and BGP do not apply to peering attachments.
V: AWS Transit Gateway, Amazon VPC

@ ANS-C01 D2 T2.2 advanced use-case
S: A SaaS provider publishes its API as a PrivateLink endpoint service behind a Network Load Balancer in us-east-1. A new customer runs all workloads in eu-west-1 and requires private connectivity with no VPC peering, transit gateway or internet path. The provider does not want to deploy the service stack in a second Region. What should be implemented?
A: The customer creates an inter-Region VPC peering to a small provider VPC in us-east-1 and uses an interface endpoint there, reached across the peering
B: The provider enables eu-west-1 as a supported Region on the endpoint service, and the customer creates an interface endpoint in eu-west-1 for that service
C: The provider places a Global Accelerator in front of the Network Load Balancer, and the customer connects to its static IP addresses from eu-west-1
D: The provider creates a second Network Load Balancer in eu-west-1 with IP targets pointing to the us-east-1 instances and publishes it as a service
K: B
G: ## Cross-Region PrivateLink
Traditionally an interface VPC endpoint could only connect to an endpoint service in the **same Region**. Reaching a service in another Region meant peering or a transit gateway to an endpoint in the provider's Region, or deploying the service in every Region.
PrivateLink now supports **cross-Region connectivity** for endpoint services:
- The **provider** adds the consumer Regions to the endpoint service's list of **supported Regions**. The service, NLB and targets stay in us-east-1.
- The **consumer** creates an interface endpoint in its own Region (eu-west-1) and selects the service Region. Consumers need the IAM permission that allows multi-Region endpoint creation.
- Traffic crosses the AWS backbone privately; the endpoint gets IPs from the consumer's own subnets, so CIDR overlap does not matter.
Example: a `com.amazonaws.vpce.us-east-1.vpce-svc-0abc...` service with supported Region `eu-west-1` is consumed from an endpoint in eu-west-1.
W: Supported Regions plus a local interface endpoint: cross-Region PrivateLink lets the eu-west-1 customer create an endpoint in its own Region for the us-east-1 service, with no peering, transit gateway or second deployment.
X: A=Peering plus a remote endpoint: this works technically but uses the inter-Region VPC peering the customer explicitly ruled out, and adds a VPC to manage.
C=Global Accelerator: accelerator addresses are public anycast IPs reached over the internet edge, which breaks the requirement for private connectivity with no internet path.
D=Second NLB with remote IP targets: this still means deploying and operating infrastructure in eu-west-1, and the NLB would need a routed private path such as peering to reach IP targets in us-east-1.
T: For private access to a service in another Region, enable the consumer Region on the endpoint service and create the endpoint locally; peering or a second deployment is no longer needed.
V: AWS PrivateLink, Elastic Load Balancing, Amazon VPC

@ ANS-C01 D2 T2.2 advanced comparison
S: A company runs VPCs in three Regions and wants one policy-driven global network. New VPC attachments must be placed automatically by their tag (env=prod, env=dev or env=shared). Production and development must never communicate, while both must reach the shared services VPCs. Which AWS Cloud WAN core network policy design meets these requirements?
A: One segment named global with attachments from every environment, using the isolate-attachments setting so attachments reach only shared services
B: Segments prod, dev and shared, attachment policies that map the env tag to a segment, and segment actions that share the shared segment with prod and dev
C: Segments prod and dev only, with shared services VPCs attached to both segments at once so each environment can reach them through its own segment
D: One segment per Region that holds that Region's prod, dev and shared attachments, with route filters on the core network edges to separate the environments
K: B
G: ## Cloud WAN building blocks
AWS Cloud WAN builds a global network from a JSON **core network policy**:
- **Segments** are isolated global routing domains, like VRFs. Attachments in the same segment can reach each other; different segments cannot, unless you allow it.
- **Attachment policies** are rules evaluated in order that map a new attachment to a segment, for example by tag: `env=prod` → segment `prod`. Acceptance can be automatic or require approval.
- **Segment actions** such as `share` exchange routes between segments. Sharing is not transitive: sharing `shared` with `prod` and with `dev` lets each reach `shared`, but `prod` and `dev` still cannot reach each other.
## Mapping the requirements
- Three segments `prod`, `dev`, `shared`.
- Tag-based attachment policies place new VPCs automatically.
- `share` actions from `shared` to `prod` and `dev`.
W: Three segments with tag-based attachment policies and sharing: segments keep prod and dev isolated, attachment policies place new VPCs by tag without manual work, and sharing the shared segment with both gives each access to shared services only.
X: A=One segment with isolate-attachments: an isolated segment stops its attachments from reaching each other, including the shared services VPCs in the same segment, so the shared access requirement fails.
C=Shared VPCs in two segments: a VPC attachment belongs to exactly one segment, so the same attachment cannot sit in both prod and dev; the design cannot be built as described.
D=Per-Region segments: segments are global routing domains meant to separate environments, not Regions. Putting prod and dev in one segment makes them mutually reachable by default, grouping by Region ignores the env tag the placement must follow, and layering route filtering on top only adds complexity that segments already solve.
T: In Cloud WAN, isolate environments with segments, place attachments with tag-based attachment policies, and grant access to common services with segment sharing, which is not transitive.
V: AWS Cloud WAN, Amazon VPC

@ ANS-C01 D2 T2.3 applied use-case
S: The networking account owns a Route 53 private hosted zone for internal.example.com. An application team must associate the zone with a VPC in its own account; both DNS resolution and DNS hostnames are already enabled on that VPC. The teams want to use native hosted zone association, not Resolver endpoints. Which TWO actions are required? (Select TWO)
A: From the networking account, create a VPC association authorization for the hosted zone that names the application account's VPC ID and Region
B: From the application account, associate the VPC with the hosted zone by calling the association API with the hosted zone ID from the networking account
C: From the networking account, share the private hosted zone with the application account through AWS Resource Access Manager and accept the share
D: From the networking account console, select the private hosted zone and add the application account's VPC ID under the zone's list of associated VPCs
E: From the application account, create a Resolver inbound endpoint and a forwarding rule for internal.example.com that targets the endpoint's addresses
K: A,B
G: ## Private hosted zones in another account
A private hosted zone answers only for VPCs associated with it. Associating a VPC **from the same account** is a simple console step. For a VPC in **another account**, Route 53 uses a two-step handshake through the API, CLI or SDK:
- In the account that owns the zone: `aws route53 create-vpc-association-authorization --hosted-zone-id Z0123 --vpc VPCRegion=eu-west-1,VPCId=vpc-0abc`
- In the account that owns the VPC: `aws route53 associate-vpc-with-hosted-zone --hosted-zone-id Z0123 --vpc VPCRegion=eu-west-1,VPCId=vpc-0abc`
Afterwards the zone owner can delete the authorization; the association stays in place.
## Prerequisites
The VPC must have `enableDnsSupport` and `enableDnsHostnames` turned on, and the Route 53 Resolver in that VPC then answers `internal.example.com` from the zone.
W: A=Association authorization: the zone owner must first authorize the specific VPC from the other account; without it the association call is rejected.
B=Association from the VPC account: the VPC owner then associates its VPC with the zone through the API or CLI, completing the native cross-account handshake.
X: C=Share the zone with AWS RAM: a private hosted zone is not a resource type that RAM shares directly; cross-account association uses the authorization handshake.
D=Add the VPC in the console: the Route 53 console lists and associates VPCs from the same account only; a VPC in another account must be associated through the API or CLI after authorization.
E=Inbound endpoint and forwarding rule: this builds a forwarding workaround instead of the native association the teams asked for, and forwarding to an inbound endpoint in the same VPC would not make the zone visible anyway.
T: Cross-account private hosted zone association is a two-step API handshake: authorization by the zone owner, then association by the VPC owner.
V: Amazon Route 53, Amazon VPC

@ ANS-C01 D2 T2.3 applied use-case
S: A company has 180 VPCs in 45 accounts. Every VPC must get the same DNS setup: four private hosted zones, Resolver forwarding rules for on-premises domains, and a DNS Firewall rule group. Today a pipeline re-applies each item to each VPC separately, and drift is common. The team wants to define this DNS configuration once and apply updates everywhere. What should they implement?
A: Share the Resolver rules and the DNS Firewall rule group through AWS RAM, and keep associating the private hosted zones per VPC with automation triggered by EventBridge
B: Use AWS Firewall Manager with a DNS Firewall policy for the whole organization and rely on its automatic remediation to also add the hosted zones and forwarding rules
C: Create a Route 53 Profile with the zones, forwarding rules and firewall rule group, share it through AWS RAM, and associate the Profile with every VPC
D: Deploy Resolver inbound endpoints in each VPC and have every VPC forward all queries to a central VPC that holds the zones, rules and firewall rule group instead
K: C
G: ## The per-VPC DNS problem
Private hosted zones, Resolver rules and DNS Firewall rule groups are each associated with VPCs one at a time. With hundreds of VPCs, keeping every VPC identical means thousands of associations, and any new zone or rule must be pushed everywhere.
## Route 53 Profiles
A **Route 53 Profile** is a container for DNS configuration:
- private hosted zones,
- Resolver rules (forwarding and system rules),
- DNS Firewall rule groups,
- related VPC DNS settings.
You create the Profile in a central account, share it with accounts or an OU through **AWS RAM**, and associate it with VPCs (one Profile per VPC). When you add a zone or rule to the Profile, every associated VPC gets it automatically.
Example: Profile `corp-dns` holds `internal.example.com`, a forwarding rule for `corp.local` and a malware-block rule group; associating it with a new VPC applies all three at once.
W: Route 53 Profile: it bundles hosted zones, Resolver rules and DNS Firewall rule groups into one shareable object, so the configuration is defined once and every associated VPC follows updates without per-item associations.
X: A=RAM sharing plus automation: rules and rule groups still need per-VPC associations, and hosted zones still need per-VPC authorization and association, which is the drift-prone approach the team wants to leave.
B=Firewall Manager DNS Firewall policy: Firewall Manager can apply DNS Firewall rule groups across accounts, but it does not associate private hosted zones or Resolver forwarding rules with VPCs.
D=Inbound endpoints everywhere: VPC workloads use the local Resolver, not an inbound endpoint in their own VPC. This adds cost and complexity and still requires forwarding rules in each VPC.
T: To give many VPCs one identical DNS configuration, bundle zones, rules and firewall rule groups in a Route 53 Profile and share it, instead of associating each item per VPC.
V: Amazon Route 53, AWS Resource Access Manager

@ ANS-C01 D2 T2.3 advanced troubleshooting
S: A VPC is associated with a private hosted zone example.com that contains records for web.example.com and api.dev.example.com. A development team then creates a second private hosted zone, dev.example.com, with one record, app.dev.example.com, and associates it with the same VPC. Since then, instances in the VPC get NXDOMAIN for api.dev.example.com, while web.example.com still resolves. What is the cause?
A: A VPC can only be associated with one private hosted zone per parent domain, so the second association silently disabled the example.com zone for dev names
B: The api.dev.example.com record is now cached as NXDOMAIN on each instance and the answer will return once the negative caching TTL of the zone expires
C: With overlapping private zones, the Resolver answers from the most specific matching zone, dev.example.com, and does not fall back to example.com
D: A private hosted zone cannot hold records for a subdomain name, so api.dev.example.com was never valid and only resolved from cached public DNS answers
K: C
G: ## Overlapping private hosted zone namespaces
One VPC can be associated with several private hosted zones, including zones whose names overlap, such as `example.com` and `dev.example.com`.
For each query, the Route 53 Resolver picks the **most specific** matching zone:
- `web.example.com` matches only `example.com`, so that zone answers.
- `api.dev.example.com` matches both, and `dev.example.com` is more specific, so **only** that zone is consulted.
If the record does not exist in the chosen zone, the Resolver returns **NXDOMAIN**. It does not go back and look in the parent zone.
## Fixing it
- Move or copy `api.dev.example.com` into the `dev.example.com` zone, or
- keep all `dev` records in one zone and remove the extra one.
Example: after the new zone was associated, any `*.dev.example.com` name that existed only in `example.com` stopped resolving.
W: Most specific zone wins, with no fallback: the new dev.example.com zone now owns every name under dev.example.com in this VPC, and because api.dev.example.com is not in it, the Resolver returns NXDOMAIN.
X: A=One zone per parent domain: a VPC can be associated with overlapping zones; web.example.com still resolving shows example.com is still active.
B=Negative caching: a cached NXDOMAIN would expire within the zone's negative TTL, but the failure here is persistent because the Resolver keeps choosing the zone that lacks the record.
D=Subdomain records not allowed: a zone can hold records at any depth below its name, and api.dev.example.com resolved correctly from example.com until the second zone was associated.
T: With overlapping private zones, the most specific zone answers alone; a missing record there returns NXDOMAIN instead of falling back to the parent zone.
V: Amazon Route 53, Amazon VPC

@ ANS-C01 D2 T2.3 applied troubleshooting
S: A Route 53 Resolver outbound endpoint forwards queries for corp.local to on-premises DNS servers. Most names resolve, but queries for a few names that return many A records or long TXT records time out. The on-premises firewall allows UDP and TCP 53 from the endpoint's IP addresses. The outbound endpoint's security group allows outbound UDP 53 to the on-premises servers only. What should be changed?
A: Add an outbound rule for TCP 53 to the on-premises DNS servers in the outbound endpoint's security group, so truncated answers can be retried over TCP
B: Add an inbound rule for UDP 53 from the on-premises DNS servers to the outbound endpoint's security group, so large response datagrams are accepted
C: Raise the EDNS buffer size on the outbound endpoint in the Resolver console so that large answers fit in a single UDP response instead of being truncated
D: Add a third IP address in another subnet to the outbound endpoint, because large responses exceed the query capacity of the two existing IP addresses
K: A
G: ## When DNS switches to TCP
DNS normally uses UDP port 53. If an answer is too large for the UDP response size the client and server agreed on, the server sends a **truncated** reply (the `TC` flag). The resolver must then repeat the query over **TCP port 53** to get the full answer.
Typical large answers: many A records, long TXT records (for example SPF), or DNSSEC data.
## Outbound endpoint security groups
The outbound endpoint's elastic network interfaces use a security group. Security groups are **stateful**, so replies to allowed outbound traffic are let back in automatically; you only need outbound rules for the ports the endpoint initiates.
- `UDP 53` to on-premises DNS: normal queries.
- `TCP 53` to on-premises DNS: retries for truncated answers and large responses.
Example: SPF TXT record for `corp.local` returns 1,800 bytes, gets truncated over UDP, and the TCP retry is dropped by the security group.
W: Allow outbound TCP 53: large answers come back truncated over UDP, and the Resolver retries over TCP, which the endpoint's security group currently blocks, so exactly those names time out.
X: B=Inbound UDP 53 rule: security groups are stateful, so UDP replies to allowed outbound queries already return. The small answers working proves that path is fine.
C=EDNS buffer setting: there is no such setting on Resolver endpoints, and a larger UDP buffer would not stop truncation when answers exceed it; TCP fallback is the standard mechanism.
D=Add endpoint IPs: extra IP addresses raise query capacity, but capacity limits would affect names at random under load, not consistently the names with large answers.
T: DNS answers that are truncated over UDP are retried over TCP 53, so Resolver endpoint security groups must allow both UDP and TCP 53 to the target DNS servers.
V: Amazon Route 53, Amazon VPC

@ ANS-C01 D2 T2.4 applied use-case
S: A platform team uses CloudFormation to create VPCs in 30 accounts. CIDR blocks are currently typed into template parameters from a spreadsheet, and two teams recently received overlapping ranges. The organization already runs Amazon VPC IPAM with a pool shared to all accounts. What is the simplest way for each stack to receive a unique CIDR automatically?
A: Use the Fn::Cidr intrinsic function on the IPAM pool's top-level range so CloudFormation computes the next free /20 block for each new VPC stack
B: Add a Lambda-backed custom resource that queries the spreadsheet API, reserves the next free /20, and returns it to the VPC resource as an output value
C: Store the next free CIDR in a Systems Manager parameter that each stack reads through a dynamic reference and that a pipeline step increments after deploy
D: Set Ipv4IpamPoolId and Ipv4NetmaskLength on the AWS::EC2::VPC resource so that IPAM allocates the next free block from the pool at creation time
K: D
G: ## IPAM allocation at VPC creation
Amazon VPC IP Address Manager (IPAM) keeps pools of address space and records every allocation, so it never hands out the same block twice. A VPC can take its CIDR **directly from a pool** at creation instead of being given a fixed range.
In CloudFormation, the `AWS::EC2::VPC` resource supports this:
- `Ipv4IpamPoolId`: the pool to allocate from, for example a Regional pool shared through AWS RAM.
- `Ipv4NetmaskLength`: the size to allocate, for example `20`.
IPAM picks a free block that satisfies the pool's allocation rules and records it. When the stack is deleted, the allocation is released.
## Why it removes overlaps
All stacks in all accounts draw from the same pool tree, so two VPCs cannot receive the same range, and no one has to maintain a list by hand.
Example: `Ipv4IpamPoolId: ipam-pool-0a1b2c` with `Ipv4NetmaskLength: 20` gives `10.12.48.0/20` to one stack and the next free /20 to the next.

B=Stateless domain rules: stateless rules match only addresses, ports and protocols. They cannot match domain names at all.
D=Stateless pass on 443: passing traffic from the stateless engine sends it around stateful inspection entirely, so every HTTPS destination would be allowed, defeating the allowlist.

C: A Network Load Balancer with a TCP listener on 8883 that passes the TLS session through to the brokers, which complete the handshake and check certificates
D: A Gateway Load Balancer with a listener for port 8883 that forwards the encrypted MQTT sessions to the broker instances registered in its target group
K: C
G: ## Terminate or pass through
A load balancer either **terminates TLS** (it holds the certificate and private key, decrypts, and optionally re-encrypts to targets) or **passes TLS through** (it forwards the encrypted bytes and the target completes the handshake).
- **NLB TLS listener**: terminates TLS with a certificate from ACM. The device's client certificate is not passed to the target, and the key lives in the load balancer.
- **NLB TCP listener**: layer 4 pass-through. The broker receives the original TLS handshake, presents its own certificate, and validates the device's client certificate.
- **ALB**: always terminates TLS and speaks HTTP or HTTPS only; it can do mutual TLS itself but cannot carry MQTT over raw TLS.
- **GWLB**: sends traffic to inspection appliances with GENEVE, not to application servers as a normal load balancer.
Example: NLB TCP 8883 → target group TCP 8883 on the brokers.
W: NLB with a TCP listener: TLS passes through untouched, so the private key stays only on the brokers and they validate device certificates themselves, while the NLB still spreads connections across the fleet.
X: A=NLB TLS listener with re-encryption: the NLB terminates the device TLS session with its own certificate and key, which breaks the key-location rule and hides the client certificate from the brokers.
B=ALB with mutual TLS: the ALB terminates TLS, holding the key itself, and it handles HTTP traffic only, so it cannot front MQTT over raw TLS.
D=Gateway Load Balancer: it is built to insert inspection appliances into a traffic path using GENEVE encapsulation, not to load balance client connections to application servers.
T: When the backend must hold the only key and see client certificates, use an NLB TCP listener for TLS pass-through; TLS listeners and ALBs terminate TLS at the load balancer.
V: Elastic Load Balancing, Amazon EC2

@ ANS-C01 D4 T4.3 applied troubleshooting
S: A CloudFront distribution uses an internet-facing ALB as its origin, with the origin domain set to the ALB's default DNS name. The ALB's HTTPS listener has an ACM certificate for app.example.com. After the origin protocol policy is changed to HTTPS only, all requests fail with HTTP 502. The distribution does not forward the viewer Host header. What should be done?
A: Change the origin protocol policy to Match viewer, so that CloudFront keeps HTTPS for secure viewers but can fall back to HTTP when TLS to the origin fails
B: Create an alias record such as origin.example.com for the ALB, add that name to the ALB certificate, and use it as the CloudFront origin domain name
C: Increase the origin response timeout and keep-alive timeout on the origin, because TLS negotiation with the ALB takes longer than the default timeouts
D: Add TLSv1 to the origin SSL protocols on the distribution, because the ALB's default security policy negotiates older TLS versions that CloudFront rejects
K: B
G: ## How CloudFront validates an HTTPS origin
When CloudFront connects to a custom origin over HTTPS, it checks the origin's certificate:
- it must be issued by a trusted certificate authority and not be expired;
- a name in the certificate must match the **origin domain name** configured on the distribution, or the **Host header** if CloudFront forwards the viewer's Host header to the origin.
If the check fails, CloudFront returns **HTTP 502**.
## The mismatch here
The origin domain is `my-alb-123.eu-west-1.elb.amazonaws.com`, but the certificate covers `app.example.com`, and the Host header is not forwarded. You cannot get a certificate for the `elb.amazonaws.com` name.
The fix is to give the ALB a name you own, for example `origin.example.com` as a Route 53 alias to the ALB, cover it with the ALB certificate, and use it as the origin domain.
W: Use a matching origin name: CloudFront requires the origin certificate to match the origin domain name when the Host header is not forwarded, so an alias you own, covered by the ALB certificate, makes validation succeed.
X: A=Match viewer: HTTPS viewers would still cause HTTPS origin requests that fail validation the same way; there is no fallback to HTTP on TLS failure.
C=Longer timeouts: a certificate name mismatch fails immediately and consistently; timeouts would show as intermittent 504 errors, not an immediate 502 on every request.
D=Older TLS versions: default ALB security policies support TLS 1.2, which CloudFront supports for origin connections. Adding TLSv1 weakens security and does not address the name mismatch.
T: CloudFront HTTPS to an ALB fails with 502 when the certificate does not match the origin domain name; use a custom name you own, not the ALB's DNS name.

S: A company's security standard forbids pre-shared keys for IPsec. A new branch connects to a transit gateway with Site-to-Site VPN, and the branch router's public IP address is assigned dynamically by its ISP and can change. The company already runs AWS Private CA. How should the VPN authentication be implemented?
A: Keep pre-shared keys but store them in AWS Secrets Manager with automatic rotation every 30 days, so the keys are never visible to administrators
B: Enable accelerated VPN on the connection, because the Global Accelerator edge authenticates the branch router by its anycast source address instead of a key
C: Create the customer gateway with the router's current IP address and update it through automation each time the ISP assigns a new public address to the router
D: Issue a certificate for the router from AWS Private CA, create the customer gateway with that certificate's ARN, and configure the router with the certificate
K: D
G: ## Authentication options for Site-to-Site VPN
Each VPN tunnel authenticates the peer during IKE:
- **Pre-shared key (PSK)**: a shared secret on both sides. Simple, but it is still a static secret.
- **Certificate-based**: the customer gateway presents an X.509 private certificate issued through ACM from **AWS Private CA**, and AWS validates it.
## Why certificates help with dynamic IPs
When the customer gateway is defined with a **certificate ARN**, its identity comes from the certificate, not its address, so the **IP address can be left out** when creating the customer gateway. The branch router can reconnect from whatever address the ISP gives it; because AWS does not know that address in advance, the router must initiate the IKE negotiation.
Example: issue a certificate for `branch12.corp.example` from the Private CA, export it to the router, and create the customer gateway with `--certificate-arn` and no fixed IP.
W: Certificate-based authentication: a Private CA certificate replaces the forbidden PSK, and because the customer gateway is identified by its certificate, the router's changing public IP no longer breaks the tunnels.
X: A=PSKs in Secrets Manager: storing and rotating the keys improves handling, but authentication still uses pre-shared keys, which the standard forbids.
B=Accelerated VPN: acceleration only changes the network path through AWS edge locations; tunnels still authenticate with a PSK or certificate as usual.
C=Update the IP by automation: this tracks the address but still relies on pre-shared keys, and each address change drops the tunnels until the automation catches up.
T: No PSKs and a dynamic branch IP → certificate-based VPN authentication with AWS Private CA, where the customer gateway is identified by certificate, not address.
V: AWS Site-to-Site VPN, AWS Private CA, AWS Transit Gateway
