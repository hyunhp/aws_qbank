@ Q001744 explain
G: ## What VPC Flow Logs record
VPC Flow Logs capture IP traffic metadata (addresses, ports, protocol, bytes, ACCEPT or REJECT) for network interfaces in a VPC, a subnet or a single interface. They are not a full packet capture, and some traffic is deliberately left out.
## Traffic that flow logs never show
- Traffic to and from the Amazon DNS server (the `.2` address of the VPC, such as `10.0.0.2`, or `169.254.169.253`).
- Instance metadata traffic to `169.254.169.254` and Amazon Time Sync traffic.
- DHCP traffic and traffic to the reserved router address of the subnet.
If an instance uses its own DNS server instead, that traffic is ordinary IP traffic and is logged.
## Where DNS visibility comes from
**Route 53 Resolver query logging** records each query made through the Resolver: the name asked, the record type, the response code and the source instance, delivered to CloudWatch Logs, S3 or Firehose.
W: Amazon DNS traffic is excluded: flow logs by design skip queries to the Amazon-provided resolver, so no filter or format change will make them appear. Resolver query logging is the service that captures these DNS queries.
X: B=Aggregation interval: the interval (1 or 10 minutes) only controls how long packets are grouped into one record. Short flows are still recorded; nothing about DNS depends on it.
C=UDP not captured: flow logs record TCP, UDP, ICMP and other protocols. DNS is missing because of the destination (the Amazon resolver), not the protocol.
D=dns-query field: the custom format has no such field. Flow log fields describe packets and flows (addresses, ports, flags, `pkt-*` addresses), never DNS query names.
T: DNS to the Amazon-provided resolver never shows up in flow logs; use Route 53 Resolver query logging to see which names instances look up.

@ Q001745 explain
G: ## Default versus custom flow log formats
The default flow log format records `srcaddr` and `dstaddr`, which describe addresses as seen at the logged network interface. For an intermediate interface such as a NAT gateway, that view hides who really started the flow.
## The pkt-* fields
A **custom format** lets you pick extra fields, including:
- `pkt-srcaddr`: the source address in the original packet header.
- `pkt-dstaddr`: the destination address in the original packet header.
Example: instance `10.0.1.5` connects to `203.0.113.5` through a NAT gateway. In the NAT gateway's log, `pkt-srcaddr` shows `10.0.1.5` and `pkt-dstaddr` shows `203.0.113.5`, so the originating instance is identifiable.
## Changing the format
A flow log's format cannot be edited after creation. Create a new flow log for the NAT gateway interface with the custom format (then delete the old one if no longer needed).
W: Custom format with pkt-srcaddr and pkt-dstaddr: these fields show the original packet addresses passing through the NAT gateway interface, linking each outbound connection back to the private instance that started it.
X: A=Per-instance ENI logs: instance interface logs do not "ignore NAT"; they simply record what that one interface sees. Using them means enabling and correlating logs on every instance interface, while the NAT gateway's own log can show the original addresses directly.
C=1-minute interval: the aggregation interval only changes how often records are written. It adds no address fields, so the NAT gateway view stays the same.
D=CloudWatch Logs destination: the destination (S3, CloudWatch Logs or Firehose) changes where records go, not which fields they contain.
T: Traffic through a NAT gateway or other middlebox hides the real endpoints in srcaddr and dstaddr; add pkt-srcaddr and pkt-dstaddr in a custom format.

@ Q001746 explain
G: ## Flow logs in S3 as a data lake
Flow logs delivered to S3 can be written in plain text or **Apache Parquet**, a columnar format that compresses well and lets query engines read only the needed columns. Hive-compatible partition prefixes (by date and hour) can be enabled so queries scan only the relevant time range.
## Querying with Athena
Amazon Athena is serverless SQL over data in S3: you define a table over the flow log prefix and pay per data scanned. No servers or pipelines are needed.
Example logic for a port scan:
- Filter `action = 'REJECT'`.
- Group by `srcaddr`, `dstaddr` and a time bucket (for example 5 minutes).
- Keep groups where `COUNT(DISTINCT dstport)` exceeds a threshold, such as 100.
The query can be saved and run on a schedule, and Parquet plus partitions keep it fast and cheap.
W: Athena SQL on REJECT records: Athena queries Parquet flow logs natively, and grouping REJECTs by source, destination and time window while counting distinct destination ports finds scan patterns at scale with no infrastructure to run.
X: A=GuardDuty disables delivery: GuardDuty has no role in turning off flow log delivery, and Athena reads Parquet very well; Parquet is one of the formats it is optimized for.
B=Manual file search: downloading and grepping files does not scale to large volumes, and counting per file cannot relate records across files or time windows to find distinct ports per source.
D=WAF logging on the VPC: AWS WAF protects HTTP(S) resources such as CloudFront, Application Load Balancers and API Gateway. It cannot attach to a VPC and never sees the rejected TCP/UDP packets of a port scan.
T: Flow logs in S3 (ideally Parquet with partitions) plus Athena SQL give serverless, at-scale detection of patterns such as port scans.

@ Q001747 explain
G: ## CloudTrail event types
- **Management events** are control-plane operations that create, change or delete resources or their settings, such as `CreateVpc`, `AuthorizeSecurityGroupIngress` or `CreateRouteTable`.
- **Data events** are high-volume resource operations, such as S3 `GetObject` or Lambda `Invoke`. They are off by default and cost extra.
## Event history versus trails
- **Event history** is on in every account with no setup. It shows the last **90 days** of management events per Region, viewable and searchable in the console or with `LookupEvents`.
- A **trail** delivers events to S3 (and optionally CloudWatch Logs) for as long as you keep them. A new trail logs management events by default.
Example: an auditor asking who opened a security group two months ago can find it in event history; one asking about last year needs a trail or a CloudTrail Lake event data store.
W: Both are management events with 90 days of event history: both calls change resource configuration, so a default trail records them, and without any trail event history still keeps them searchable for 90 days.
X: A=Data events required: data events cover object- and item-level operations such as S3 reads and writes. Creating a VPC or changing a security group is a control-plane change, which is a management event.
B=Only CreateVpc logged: `AuthorizeSecurityGroupIngress` also changes configuration and is a management event. No EC2 security group API needs data events.
D=Only in VPC Flow Logs: flow logs record network packets, not API calls. Every EC2 and VPC API call is recorded by CloudTrail.
T: Configuration-changing API calls are management events, logged by default and visible in 90-day event history even without a trail.

@ Q001748 explain
G: ## Where CloudTrail records an event
CloudTrail records each API call in the Region where the call was made. A peering connection is accepted by calling `AcceptVpcPeeringConnection` in the accepter VPC's Region, so here the event lives in ap-southeast-2.
## Single-Region versus multi-Region trails
- A **single-Region trail** logs only events from its own Region.
- A **multi-Region trail** logs events from all Regions, including new ones enabled later, to one bucket.
## Organization trails
An organization trail is created in the management account (or a delegated administrator account) and applies to every member account automatically. Its Region scope still matters: an organization trail limited to us-east-1 collects only us-east-1 events from each member.
Example: a member account creates a route in eu-west-1; a single-Region us-east-1 organization trail never sees it.
W: Single-Region trail: the trail only covers us-east-1, so the ap-southeast-2 acceptance is never collected. Making it a multi-Region organization trail captures events from every Region in every member account.
X: B=Only IAM events: organization trails capture the same management events as any trail, including all EC2 and VPC networking calls.
C=Member needs own trail: organization trails apply to member accounts automatically and do not skip networking calls; a member trail would not fix the Region scope of the central trail.
D=Requester's Region only: the acceptance is an API call in the accepter's Region (ap-southeast-2), and CloudTrail records it there, not in the requester's Region.
T: CloudTrail records events where the API call happens; only a multi-Region (organization) trail captures every Region centrally.

G: ## AWS Config rules and remediation
AWS Config records resource configurations and evaluates them with rules. The managed rule **restricted-ssh** marks a security group NON_COMPLIANT when it allows inbound TCP `22` from `0.0.0.0/0` (or `::/0`), and it re-evaluates whenever a security group changes.

- An **organization conformance pack** deploys it to every member account from the management or delegated administrator account.
## Automatic remediation
A remediation action runs a Systems Manager Automation document against the non-compliant resource. For example, `AWS-DisablePublicAccessForSecurityGroup` removes rules that open SSH or RDP to everyone. With automatic remediation enabled, it runs without a person.
W: restricted-ssh in a conformance pack with SSM remediation: Config continuously evaluates every security group, the conformance pack spreads the rule across the organization, and the attached Automation document removes the offending rule automatically.
X: A=Inspector reachability reviewed weekly: Inspector network reachability findings show which ports are reachable, but a weekly manual review is neither continuous compliance nor automatic removal.
C=Trusted Advisor cost checks: cost optimization checks look at spend such as idle resources. They do not evaluate security group rules and cannot remediate anything.
D=CloudTrail Insights: Insights flags unusual API call rates or error rates. It does not judge whether a rule is compliant and takes no corrective action.
T: Continuous configuration compliance with automatic fixes across accounts is AWS Config: a rule in an organization conformance pack plus an SSM remediation action.

@ Q001751 explain
G: ## Managed versus custom Config rules
- **Managed rules** are prebuilt by AWS, such as `restricted-ssh` or `vpc-flow-logs-enabled`. You only set parameters.
- **Custom Lambda rules** run your own Lambda function. Config passes the resource's configuration item, and the function can call any AWS API, then reports COMPLIANT or NON_COMPLIANT with `PutEvaluations`.
- **Custom policy rules** use AWS CloudFormation Guard syntax. They check fields of a single configuration item and cannot call other APIs.
## Why this check needs Lambda
Checking whether a VPC's traffic is routed through a firewall means combining several resources: the VPC, its route tables (`DescribeRouteTables`) and the Network Firewall endpoints (`ListFirewalls`, `DescribeFirewall`). Only a Lambda-backed rule can make those lookups and correlate them.
Example: for each VPC, find the firewall associated with it and confirm that the subnet route tables send `0.0.0.0/0` to a firewall endpoint (`vpce-...`).
W: Custom Lambda-backed Config rule: the function can query EC2 route tables and Network Firewall firewalls, correlate them per VPC and report compliance, which no managed rule does.
X: A=Not possible with Config: custom rules exist exactly for checks AWS does not provide, so this can be automated rather than done by hand.
C=Conformance packs express any logic: a conformance pack is a container that deploys rules and remediations. It does not add a way to write cross-resource API lookups; the logic still has to live in a rule.
D=Purpose-built managed rule: the managed Network Firewall rules check firewall and policy settings, not whether each VPC's route tables send traffic through a firewall, and the question states no such rule exists.
T: When no managed rule fits, especially for checks spanning several resources, write a custom Lambda-backed Config rule.

@ Q001754 explain
G: ## Reading GuardDuty finding names
A finding type follows `ThreatPurpose:ResourceType/ThreatFamily`, sometimes with a suffix such as `.Custom` or `!DNS`:
- **UnauthorizedAccess**: the purpose, activity that may indicate unauthorized access.
- **EC2**: the affected resource is an EC2 instance.
- **MaliciousIPCaller**: the instance is communicating with an IP address on a threat list. The current documentation lists the EC2 form as `UnauthorizedAccess:EC2/MaliciousIPCaller.Custom`, meaning the address is on a custom threat list you uploaded; matches against AWS's built-in threat intelligence appear under other types, such as `Backdoor:EC2/C&CActivity.B`.
Either way, the instance itself is talking to a known-bad address, which may mean it is compromised.
## A sound first response
- **Contain**: move the instance to an isolation security group with no rules or tightly restricted ones, or restrict it with a NACL.
- **Preserve evidence**: snapshot EBS volumes and keep logs before terminating anything.
- **Investigate**: use Amazon Detective or flow logs and CloudTrail to learn what it contacted and how it got there.
W: Talking to a threat-listed IP, isolate and investigate: the finding means the instance communicated with a listed malicious address, so contain it, preserve evidence and investigate before deciding on cleanup.
X: A=IAM user from Tor: sign-ins or API calls from Tor exit nodes produce IAM-related findings such as `UnauthorizedAccess:IAMUser/TorIPCaller`, not an EC2 finding.
B=WAF blocked a request: WAF blocks are recorded in WAF logs and metrics; GuardDuty does not report WAF actions as this finding.
C=Security group changed: an unauthorized configuration change is visible in CloudTrail and Config. This finding type describes the instance's network communication, not a change to its security group.
T: Read the finding type (purpose, resource, family): MaliciousIPCaller on EC2 means the instance talked to a known-bad IP; contain, preserve evidence, investigate.

@ Q001757 explain
G: ## Where GuardDuty's DNS data comes from
GuardDuty's DNS analysis uses the query logs of the **Amazon-provided DNS resolver** (Route 53 Resolver at the VPC `.2` address). It sees names queried there, which lets it detect DNS-based threats such as `Trojan:EC2/DNSDataExfiltration` (data hidden in long query names) or lookups of known bad domains.
## What changes if an instance bypasses it
If the instance sends queries straight to an external resolver, for example `8.8.8.8` or a self-hosted server, those queries never reach the Amazon resolver:
- GuardDuty has no DNS log entries for them, so DNS-based findings cannot be produced.
- Flow log data still shows UDP/TCP `53` connections to the external IP, but not the names queried.
Organizations often block outbound port 53 except to the VPC resolver, or use Route 53 Resolver DNS Firewall, to keep DNS observable.
W: Bypassing the Amazon resolver hides DNS queries: GuardDuty's DNS log data source only covers queries that go through the Amazon-provided resolver, so DNS exfiltration from this instance would go undetected by its DNS-based findings.
X: A=Only flow logs affected: the opposite. Flow log data still records the connections to the external resolver; what is lost is GuardDuty's DNS query visibility.
C=Inspects DNS packets at the ENI: GuardDuty does not capture packets on interfaces. It relies on the Amazon resolver's logs for query names.
D=Redirects DNS traffic: GuardDuty is a detection service that is not in the traffic path, so it cannot redirect or alter an instance's DNS traffic.
T: GuardDuty's DNS detections only cover queries sent to the Amazon-provided resolver; using a third-party resolver creates a blind spot.

@ Q001758 explain
G: ## Two tunnels per VPN connection
Every AWS Site-to-Site VPN connection has **two tunnels**, each ending on a different AWS endpoint (outside IP) for redundancy. AWS performs routine maintenance that can take one tunnel down for a short time, one tunnel at a time.
## Making failover automatic
- Configure **both** tunnels on the customer gateway device.
- With **BGP (dynamic routing)**, each tunnel advertises routes; when one tunnel drops, its BGP session ends and traffic moves to the other within the BGP timers. AS-path prepending or local preference can make one tunnel preferred (active/passive).
- With static routing, the device needs tunnel monitoring (for example DPD or SLA probes) to move routes itself.
Example: tunnel 1 is preferred by BGP; during maintenance on tunnel 1, traffic shifts to tunnel 2 with no manual steps.
W: Configure both tunnels, BGP preferred: with both tunnels up, AWS maintenance on one tunnel leaves the other ready, and BGP moves traffic over automatically.
X: B=Manual backup tunnel: waiting for an operator to bring up tunnel 2 means an outage every time tunnel 1 goes down, which is exactly what happened.
C=Second tunnel for IPv6 only: the second tunnel is for redundancy. A VPN connection's tunnels carry one address family (IPv4 or IPv6) set for the connection, so a tunnel cannot be dedicated to IPv6 this way.
D=Ask AWS to skip maintenance: AWS does not exempt individual tunnels from maintenance; the design expects customers to use both tunnels.
T: Always configure both VPN tunnels, ideally with BGP, so AWS maintenance on one tunnel causes automatic failover rather than an outage.

@ Q001759 explain
G: ## What the tunnel options control
Each Site-to-Site VPN tunnel has **tunnel options** that set what the AWS endpoint will accept during IKE negotiation:
- Phase 1 and Phase 2 **encryption algorithms**, such as `AES256` or `AES256-GCM-16`.
- Phase 1 and Phase 2 **integrity algorithms**, such as `SHA2-256` or `SHA2-512`.
- Phase 1 and Phase 2 **Diffie-Hellman group numbers**, such as `14` to `24`.
- **IKE versions** (`ikev1`, `ikev2`).
By default AWS allows a broad set, including AES-128, SHA-1, DH group 2 and IKEv1, for compatibility with older devices.
## Enforcing a standard
Restrict each option on both tunnels with `ModifyVpnTunnelOptions`, in the console, or at creation. The AWS side then refuses any proposal outside the list, even if a customer device offers it.
W: Tunnel options with only approved values: limiting encryption, integrity, DH groups and IKE version on the AWS side guarantees nothing weaker can ever be negotiated.
X: B=Customer gateway only: AWS tunnel options can be customized, and restricting only the customer device leaves the AWS side willing to accept weaker proposals from any misconfigured device.
C=Config rule blocking tunnels: tunnel options are part of the VPN API (`ModifyVpnTunnelOptions`). A Config rule could only report; it does not stop a tunnel from negotiating weak settings.
D=Defaults already strong: the defaults include AES-128, SHA-1, DH group 2 and IKEv1 for backward compatibility, so they do not meet this standard.
T: To enforce cryptographic standards on AWS VPN, restrict the tunnel options on the AWS side; defaults allow weaker proposals.

@ Q001760 explain
G: ## Dead Peer Detection (DPD)
DPD checks whether the IPsec peer is still alive. Each side sends R-U-THERE messages when it has not heard from the peer, and declares the peer dead after a timeout, then takes the **DPD timeout action**: clear the SAs, restart IKE, or do nothing.
## AWS DPD settings
On AWS tunnels, the DPD timeout defaults to 30 seconds and the timeout action can be `clear`, `none` or `restart`, set per tunnel in the tunnel options.
## Why mismatches cause flapping
If one side uses much more aggressive timers or retry counts than the other, it may declare the peer dead after brief delays or lost DPD messages, tear the tunnel down and renegotiate. The tunnel comes back, and the cycle repeats every few minutes even though Phase 1 and Phase 2 negotiate successfully each time.
W: Mismatched DPD timers: an overly aggressive DPD interval on the customer gateway leads to false "peer dead" decisions and repeated teardowns. Aligning DPD timeout, retries and actions on both sides stops the flapping.
X: B=Throughput limit cycling: exceeding a tunnel's bandwidth leads to packet drops, not AWS deliberately taking the tunnel down and up.
C=Five-minute maximum session: there is no such limit. SAs are rekeyed when their lifetimes end (by default 1 hour for Phase 2 and 8 hours for Phase 1) without taking the tunnel down.
D=Customer gateway IP changed: if the public IP changed, the tunnel would not re-establish at all with the configured customer gateway; it would not keep coming back up.
T: A tunnel that repeatedly drops and re-establishes while IKE/IPsec negotiation succeeds points to DPD timer or action mismatches.

@ Q001761 explain
G: ## Two ways to encrypt Direct Connect traffic
- **IPsec VPN over Direct Connect**: a Site-to-Site VPN runs over a public VIF (to public VPN endpoints) or a transit VIF (Private IP VPN to a transit gateway). A standard tunnel supports up to about **1.25 Gbps**, so using a 10 Gbps link needs several tunnels with ECMP, and a single flow still stays on one tunnel. IPsec also adds encryption overhead per packet.
- **MACsec (IEEE 802.1AE)**: Layer 2 encryption between the customer router and the AWS Direct Connect device, done in hardware at close to line rate on supported **dedicated** connections (10, 100 and 400 Gbps at supported locations). It needs MACsec-capable router ports.
## Example
A 10 Gbps dedicated connection with MACsec can carry about 10 Gbps of encrypted traffic. With standard IPsec tunnels, reaching the same needs around eight tunnels and ECMP, and no single flow exceeds one tunnel's limit.
W: VPN caps per tunnel, MACsec runs near line rate: each IPsec tunnel has a fixed bandwidth limit (about 1.25 Gbps for a standard tunnel), while MACsec encrypts in hardware at Layer 2 with close to full connection bandwidth.
X: B=VPN outperforms MACsec: the layers are reversed. MACsec is Layer 2 and IPsec is Layer 3, and MACsec is the faster option on high-speed links.
C=Identical performance: per-tunnel limits and encapsulation overhead make IPsec throughput and latency different from MACsec's, so cost is not the only factor.
D=No MACsec on Direct Connect: MACsec is supported on dedicated Direct Connect connections at eligible speeds and locations.
T: Encrypting a high-speed dedicated Direct Connect link at line rate calls for MACsec; IPsec over DX is limited per tunnel.

@ Q001763 explain
G: ## MACsec key hierarchy
MACsec on Direct Connect uses a pre-shared key pair that you create and associate with the connection:
- **CKN** (Connectivity Association Key Name): identifies the key.
- **CAK** (Connectivity Association Key): the secret itself.

G: ## "Never over the public internet" is a path requirement
TLS protects the contents of traffic but not the path. A rule that traffic must never cross the public internet rules out any public endpoint, even with strong encryption.
## AWS PrivateLink for SaaS
- The provider places its service behind a Network Load Balancer (or Gateway Load Balancer) and publishes an **endpoint service**.
- The customer creates an **interface VPC endpoint** in its own VPC. It appears as network interfaces with private IPs from the customer's subnets.
- Applications call the endpoint's private DNS name or IP, and traffic flows over the AWS network to the provider, without an internet gateway, NAT or public IPs.
Many SaaS providers offer PrivateLink for exactly this, including cross-Region access for supported services.
