@ Q003842 explain
G: ## CloudFront geographic restrictions
CloudFront can decide, per request, whether a viewer's country is allowed to receive content from a distribution. It looks up the viewer's IP address in a GeoIP database and maps it to a country.
- **Allow list**: only the listed countries are served, for example `US`, `CA` and `GB`.
- **Block list**: every country is served except the listed ones.
A blocked viewer receives HTTP `403 (Forbidden)`, and you can configure a custom error page for that response.
## Scope and alternatives
The built-in setting applies to the whole distribution. When rules must differ by path or combine country with other conditions, teams use an AWS WAF geo match rule, or read the `CloudFront-Viewer-Country` header in CloudFront Functions or Lambda@Edge.
W: Geographic restrictions: this is the native CloudFront feature that allows or blocks viewers by country, which is exactly the requirement, with no code or extra service.
X: B=Origin Shield: an additional caching layer in front of the origin that raises the cache hit ratio and reduces origin load. It never looks at the viewer's country or denies requests.
C=Real-time logs: streams request details to Kinesis Data Streams within seconds for monitoring. It records who requested what but cannot stop a request from being served.
D=Field-level encryption: encrypts specific POST form fields at the edge with a public key so only the backend can decrypt them. It protects data, not access by location.
T: Country-based allow or deny at CloudFront is geo restriction; Origin Shield, logging and field-level encryption do not decide who gets served.

@ Q003843 explain
G: ## Route 53 Resolver DNS Firewall
Every VPC has the Route 53 Resolver (the `.2` address, for example `10.0.0.2`) that answers DNS queries from workloads. DNS Firewall inspects those outbound queries before they are resolved.
- You build **domain lists**: your own (for example `*.bad-example.com`) or AWS managed lists of known malware and botnet domains.
- You put rules in a **rule group**; each rule matches a domain list and takes an action: `ALLOW`, `ALERT` or `BLOCK` (answering `NODATA`, `NXDOMAIN` or an override record).
- You associate the rule group with VPCs, directly or across accounts with Firewall Manager or AWS RAM.
Example: an instance infected with malware tries to resolve its command-and-control domain; the query matches a managed list, is blocked, and the malware cannot find its server.
W: Resolver DNS Firewall: it filters DNS queries leaving VPC workloads against domain lists, including AWS managed threat lists, and blocks the malicious ones.
X: A=Public DNSSEC: signs a public hosted zone so resolvers can verify its answers were not tampered with. It protects your own domain's records, not what your workloads look up.
B=Traffic flow: a visual editor for routing policies (latency, geolocation, failover) for records you publish. It shapes answers for your domains; it does not filter queries to other domains.
D=Health checks: monitor endpoint availability to drive DNS failover and alarms. They have no role in inspecting or blocking lookups from a VPC.
T: Blocking what VPC workloads can resolve is DNS Firewall; DNSSEC, traffic flow and health checks all concern records you publish.

@ Q003844 explain
G: ## How an ALB spreads requests across zones
An Application Load Balancer has a node in each enabled Availability Zone, and DNS sends clients to these nodes roughly equally.
- **Cross-zone on**: each node sends requests to healthy targets in all zones, so every target gets about the same share.
- **Cross-zone off**: each node only uses targets in its own zone, so each zone gets about the same share, regardless of how many targets it has.
## Why uneven target counts hurt
Example: three zones with 4, 4 and 2 targets. With cross-zone off, each zone gets about one third of traffic, so each of the 2 targets carries about 16.7% while the others carry about 8.3%. With cross-zone on, each of the 10 targets carries about 10%.
For ALBs cross-zone is on at the load balancer level, but it can be turned off per target group, which produces exactly this symptom.
W: Cross-zone load balancing: it lets every node distribute across all registered targets in all zones, so the zone with fewer targets is no longer overloaded.
X: A=Sticky sessions: bind a client to one target with a cookie. That keeps a user on the same target and can make imbalance worse; it does not rebalance zones.
B=Slow start: gives a newly registered target a ramp-up period before it receives its full share. It affects only new targets, not the split between zones.
C=Deregistration delay: keeps in-flight requests running on a target being removed. It is about draining, not distribution.
T: Uneven target counts per zone are fixed by cross-zone load balancing; stickiness, slow start and draining only change behavior for individual targets.

@ Q003845 explain
G: ## VPC Reachability Analyzer
Reachability Analyzer is a configuration analysis tool. You pick a source (for example an EC2 instance) and a destination (for example an RDS instance's network interface), plus an optional protocol and port such as TCP `5432`.
It builds a model of the network from route tables, security groups, network ACLs, gateways, peering and transit gateway configuration, then reports:
- **Reachable**: the hop-by-hop path the traffic would take.
- **Not reachable**: the exact component that blocks it, for example "security group `sg-0abc` has no inbound rule for TCP 5432".
No packets are sent, so it works even before the application runs and cannot disturb production traffic.
W: Reachability Analyzer: it answers "can A reach B" from the configuration alone and names the blocking component, matching both requirements.
X: A=AWS Config snapshots: record resource configurations at a point in time. You could read them manually, but Config does not compute a path or say which rule blocks it.
C=Traffic Mirroring: copies real packets from a network interface to a monitoring target. It needs actual traffic and shows what flows, not why a path is blocked.
D=Amazon Inspector: finds software vulnerabilities and network exposure of instances to outside networks. It does not analyze a specific instance-to-database path.
T: Path analysis without sending traffic is Reachability Analyzer; Traffic Mirroring needs live packets and Config only stores settings.

@ Q003846 explain
G: ## Why distance hurts dynamic requests
When a response cannot be cached, every request has to travel to the one Region. Over the public internet this means many hops, variable congestion, and a fresh TCP and TLS handshake that costs several round trips across long distances.
## Getting onto the AWS network early
- **CloudFront**: users connect to a nearby edge location, where TLS is terminated. CloudFront keeps persistent, reused connections to the origin and carries requests over the AWS backbone, so even uncached requests get faster.
- **Global Accelerator**: gives two static anycast IP addresses; users enter the AWS network at the nearest edge location and travel the backbone to the Regional endpoint (ALB, NLB or EC2).
Example: a user in Sydney calling an API in `us-east-1` does the handshakes with a Sydney edge instead of with Virginia.
W: D=Global Accelerator: anycast entry at the nearest edge and transport over the AWS backbone reduce latency and jitter for non-cacheable traffic.
E=CloudFront in front of the API: edge TLS termination and persistent origin connections shorten the handshake cost and speed up dynamic requests even with caching disabled.
X: A=S3 Transfer Acceleration: speeds up uploads and downloads to one S3 bucket through edge locations. An unrelated bucket has no effect on requests to the API.
B=Larger instances: help if the servers are CPU or memory bound, but the complaint is from distant users; bigger instances do not shorten the network path.
C=Longer DNS TTL: only reduces how often clients look up the name. The lookup is a tiny part of latency; every API request still crosses the same long path.
T: For far-away users and uncacheable traffic, get onto the AWS edge early with CloudFront or Global Accelerator; server size and DNS TTL do not shorten the path.

@ Q003847 explain
G: ## What a Site-to-Site VPN connection is
Each AWS Site-to-Site VPN connection has **two IPsec tunnels**, each ending on a different AWS endpoint, so one can fail or be under maintenance while the other carries traffic. The customer gateway device must support IPsec (IKEv1 or IKEv2).
## Static versus dynamic routing
- **Static**: you type the on-premises prefixes into the VPN connection; no routing protocol runs.
- **Dynamic**: a BGP session runs inside each tunnel, using link-local inside addresses such as `169.254.10.1/30`. The device advertises its prefixes and learns VPC routes, and failover between tunnels happens automatically when a BGP session drops.
So a dynamic VPN needs a device that speaks both IPsec and BGP, configured on both tunnels.
W: IPsec plus BGP on both tunnels: every tunnel is IPsec, and dynamic routing means a BGP session per tunnel for route exchange and automatic failover.
X: A=Static routes on one tunnel: that is static routing, the opposite of what was chosen, and using a single tunnel removes the redundancy AWS provides.
B=GRE without IPsec: Site-to-Site VPN tunnels are always IPsec. GRE is used by transit gateway Connect attachments for SD-WAN appliances, not by Site-to-Site VPN.
D=MACsec on a cross-connect: MACsec is layer 2 encryption for certain dedicated Direct Connect connections. A VPN runs over the internet or a transport network, not a fiber cross-connect.
T: Dynamic Site-to-Site VPN means IPsec tunnels with a BGP session in each; MACsec belongs to Direct Connect and GRE to transit gateway Connect.

@ Q003848 explain
G: ## Why one VPN connection has a ceiling
Each Site-to-Site VPN tunnel has a maximum bandwidth, and without ECMP a connection typically uses one tunnel actively with the second as backup. Adding more bandwidth therefore means using more tunnels at the same time.
## ECMP on a transit gateway
Equal-cost multi-path (ECMP) lets a router spread flows across several paths that lead to the same prefix with equal cost.
- Enable **VPN ECMP support** on the transit gateway.
- Create several VPN connections to the same customer gateway (or several devices) using **BGP**, and advertise the same prefixes with the same AS path length.
- The transit gateway then balances flows across all active tunnels, so four connections give up to eight tunnels of aggregate capacity.
A single flow still uses one tunnel; the gain is in total throughput across many flows.
W: Multiple VPN connections with ECMP: the transit gateway spreads traffic across all equal-cost tunnels, which is the supported way to aggregate VPN bandwidth.
X: B=Static routes with priority: priority only picks one preferred path; it never uses several paths together, so bandwidth stays at one tunnel.
C=Disabling the second tunnel: this removes redundancy and does not raise the per-tunnel limit, so capacity stays the same or drops.
D=Virtual private gateway with larger MTU: a virtual private gateway does not do ECMP across VPN connections, and a larger MTU only reduces overhead per packet; it cannot add bandwidth.
T: VPN bandwidth is aggregated by running many BGP tunnels with ECMP on a transit gateway; route priority and MTU tweaks leave you on one tunnel.

@ Q003849 explain
G: ## The problem: the internet part of the path
A standard VPN tunnel goes from the office router across the public internet to AWS VPN endpoints in the Region. For offices far away or on poor ISPs, most of the latency and packet loss happens on that long internet stretch.
## Accelerated Site-to-Site VPN
With acceleration enabled, the tunnels use AWS Global Accelerator:
- The office connects to the nearest AWS edge location using anycast addresses.
- From there, traffic rides the AWS global backbone to the Region.
- The internet portion shrinks to the short hop between the office and the nearby edge.
It is enabled when you create the VPN connection and is available for VPN connections attached to a transit gateway, not a virtual private gateway.
W: Accelerated VPN: it moves the traffic onto the AWS backbone at the closest edge, avoiding the poor long-haul internet path that causes the slowdown.
X: A=Second VPC and gateway: adds another destination, but the offices still reach it over the same bad internet paths, so nothing improves.
B=Static routes instead of BGP: the routing protocol only decides which tunnel to use; it does not change packet loss or latency on the internet path.
D=Bigger customer gateway router: helps only if the device's CPU or encryption capacity is the bottleneck. It cannot fix congestion or distance between the office and AWS.
T: When the internet path is the problem, Accelerated VPN via Global Accelerator shortens it; routing tweaks and bigger routers do not.

@ Q003850 explain
G: ## Dedicated versus hosted Direct Connect
- **Dedicated connection**: you order a physical port from AWS, receive a Letter of Authorization (LOA-CFA), and arrange the cross-connect.
- **Hosted connection**: an AWS Direct Connect Partner already has capacity and provisions a connection of a given speed in your account.
- **Hosted VIF**: the partner (or another account) creates a virtual interface on its own connection and assigns it to your account.
## Steps for the customer
- In both hosted cases, the resource appears in your account in a pending state and you must **accept** it.
- For a hosted connection, you then create your private VIF on it; for a hosted VIF, you attach it to a virtual private gateway or Direct Connect gateway while accepting.
- Finally, configure BGP on your router: VLAN, your ASN, peer IP addresses and optional MD5 key.
W: Accept, then configure BGP: the partner provisions the hosted resource, but it stays pending until the customer accepts it; the VIF only comes up after BGP is configured on the customer router.
X: B=Order a dedicated port: that is the dedicated connection process with an LOA. A hosted connection already exists through the partner, so no port order is needed.
C=Public VIF advertising all prefixes: the requirement is a private VIF to a VPC. A public VIF reaches public AWS endpoints and accepts only public prefixes you own, not all company prefixes.
D=Internet gateway on the VPC: a private VIF terminates on a virtual private gateway or Direct Connect gateway; an internet gateway plays no part in bringing it up.
T: Hosted Direct Connect resources are created by the partner and must be accepted by the customer before BGP can come up; no port order is involved.

@ Q003851 explain
G: ## Link aggregation groups (LAG)
A LAG uses the LACP standard to bundle several Direct Connect connections into **one logical connection**.
- All member connections must have the same port speed and terminate at the same Direct Connect location (on the same AWS device).
- Virtual interfaces are created on the LAG, not on individual links, so traffic is spread across all members.
- A **minimum links** setting decides when the whole LAG is declared down, for example "keep the LAG up only while at least 1 of 2 links works".
Example: two 10 Gbps dedicated connections in one location become a single 20 Gbps LAG carrying one set of VIFs.
Note that a LAG adds bandwidth and link-level redundancy but not location redundancy; resilient designs still use a second location.
W: LAG: it is the Direct Connect feature that bundles same-location dedicated connections into one logical link with their combined bandwidth.
X: A=Transit VIF: a virtual interface type that connects a Direct Connect connection to a Direct Connect gateway associated with transit gateways. It runs on a link; it does not merge links.
C=Hosted VIF: a virtual interface a partner or another account provisions for you on its connection. It is one logical interface, not a bundle of ports.
D=Direct Connect gateway: a global object that lets VIFs reach VPCs or transit gateways in many Regions. It connects destinations; it does not combine physical connections.
T: Combining physical Direct Connect ports at one location into one logical link is a LAG; VIFs and Direct Connect gateways sit on top of links.

@ Q003852 explain
G: ## What BGP "Idle" means on a VIF
A VIF has two layers: the layer 2 VLAN on the physical connection, and a BGP session over TCP port `179` between your router and the AWS peer IP. **Idle** means BGP is not even trying to establish or keeps resetting, usually because the two sides disagree on basic parameters.
## Parameters that must match exactly
- **ASN**: your router must use the customer ASN entered on the VIF and expect the Amazon side ASN (for example `64512`).
- **Peer IPs**: the addresses must match the VIF, for example `169.254.100.1` for Amazon and `169.254.100.2` for you.
- **MD5 key**: if one side uses a different key, TCP segments are dropped and the session never forms.
- **VLAN ID** on the subinterface must match the VIF.
W: D=ASN or peer IP mismatch: BGP peers only with the configured neighbor address and expected ASN; if either differs from the VIF, the session stays Idle.
E=Wrong MD5 key: BGP MD5 authentication signs every TCP segment; a mismatched key causes them to be discarded, so the session cannot establish.
X: A=Missing route in a public subnet: VPC subnet route tables affect traffic after routes are exchanged. They have no influence on whether the router and AWS form a BGP session.
B=S3 bucket policy: bucket policies control access to S3 objects through requests to the S3 API. A router's BGP session never touches S3.
C=Security group blocking HTTPS: security groups apply to network interfaces inside the VPC. BGP on a VIF runs on TCP 179 between the router and the AWS peer, outside any security group.
T: A VIF stuck in Idle is almost always a BGP parameter mismatch (ASN, peer IPs, MD5 key, VLAN), not VPC-level settings.

@ Q003853 explain
G: ## Prefix limits on Direct Connect VIFs
When your router advertises routes to AWS over BGP, AWS enforces a maximum number of prefixes per BGP session.
- **Private VIF**: up to 100 prefixes from the customer (counted separately for IPv4 and IPv6).
- If you exceed the limit, AWS puts the BGP session into the **Idle** state, so all traffic on that VIF stops until you reduce the count.
## Staying under the limit
Summarize routes before advertising. Example: instead of 300 separate `/24` networks inside `10.20.0.0/15`, advertise one aggregate such as `10.20.0.0/15` or a handful of `/16` and `/18` summaries.
The limit is fixed and cannot be raised through a quota request.
W: Up to 100 prefixes: a private VIF accepts at most 100 prefixes per address family from the customer, and going over drops the BGP session to Idle.
X: A=Unlimited: AWS enforces a hard limit to protect its routers; exceeding it takes the session down, which is why route summarization matters.
B=Only 1 prefix: you can advertise many prefixes over one private VIF; a single prefix is not a restriction.
C=Up to 10 prefixes: the real limit is ten times higher, so designs advertising a few dozen prefixes work fine.
T: A private VIF takes up to 100 customer prefixes; summarize to stay under it, because exceeding it idles the BGP session.

@ Q003854 explain
G: ## Associations and propagations
Each transit gateway attachment has two independent relationships with route tables:
- **Association**: the one route table used to look up destinations for traffic arriving from that attachment.
- **Propagation**: the route tables into which the attachment's CIDRs are automatically installed.
A VPC can reach another only if the route table it is associated with contains a route to that VPC.
## A segmentation example
- `prod-rt`: associated with production VPCs; receives propagations from shared services (and production if prod must talk to prod).
- `dev-rt`: associated with development VPCs; receives propagations from shared services only.
- `shared-rt`: associated with shared services; receives propagations from both production and development so replies can return.
Production VPCs never learn development routes, so they cannot reach each other, while both reach shared services.
W: Separate route tables with shared-service propagations: associations and propagations isolate production from development at the routing layer while giving both a path to shared services.
X: A=One route table for all: every VPC learns every other VPC's routes, creating full any-to-any reachability that violates the isolation requirement.
C=NACLs denying production: denying production traffic in shared services blocks exactly the access production needs, and it does nothing to separate production from development.
D=Security groups on every instance: manual per-instance rules across 50 VPCs are fragile and easy to miss, and the routes still exist; segmentation belongs in transit gateway route tables.
T: Transit gateway segmentation is done with separate route tables and selective propagation, not with one flat table or per-instance filters.

@ Q003855 explain
G: ## Sharing a transit gateway across accounts
A transit gateway lives in one account (often a central network account). Other accounts cannot see it until it is shared with **AWS Resource Access Manager (RAM)**.
- Create a resource share containing the transit gateway and choose principals: the whole organization, specific OUs, or accounts.
- With sharing enabled for AWS Organizations, accounts in the organization receive it without accepting an invitation.
- Member accounts then create VPC attachments from their own VPCs to the shared transit gateway.
- The owner can accept each attachment request or turn on **auto accept shared attachments**.
The owner keeps control of route tables, so segmentation stays centralized.
W: AWS RAM: it is the supported way to share a transit gateway with other accounts or OUs so they can attach their own VPCs while the owner manages routing.
X: B=Share IAM access keys: handing out long-term credentials of the owner account breaks least privilege and auditing, and it is never the way to share network resources.
C=Peer every VPC with the owner's VPC: VPC peering connects VPCs to each other, not to a transit gateway, and it is not transitive, so it cannot give access to the shared hub.
D=Copy in every account: separate transit gateways fragment routing, need peering between them, and multiply cost and management instead of providing one shared hub.
T: One transit gateway, many accounts: share it with RAM and let members create attachments; do not peer, copy or share credentials.

@ Q003856 explain
G: ## What an active peering connection does not do
An `active` VPC peering connection only means both sides agreed to connect. Traffic still needs two more things on **both** sides:
- **Routes**: each VPC's subnet route tables need a route for the other VPC's CIDR with the peering connection as target, for example `10.1.0.0/16 -> pcx-0abc123`. Without it, packets follow the default route or are dropped.
- **Filters**: security groups on the instances must allow the traffic (they can reference the peer's security group ID within the same Region), and network ACLs on both subnets must allow the request and the return traffic on ephemeral ports.
Example: an app in `10.0.0.0/16` calls a DB in `10.1.0.0/16` on TCP 5432; both route tables, the DB's security group and both NACLs must permit it.
W: C=Security groups and NACLs: even with correct routes, a missing inbound or return rule in either VPC silently drops the traffic.
E=Route tables in both VPCs: peering adds no routes automatically; each side must route the other VPC's CIDR to the peering connection or packets never reach it.
X: A=Same DHCP options set: DHCP options only hand out DNS servers and domain names; different option sets do not affect IP traffic across a peering connection.
B=Internet gateways: peering traffic stays on the AWS private network and never uses an internet gateway, so attaching one changes nothing.
D=NAT gateways: NAT gateways translate outbound traffic to the internet or other networks; direct VPC-to-VPC peering traffic needs no NAT.
T: Peering needs routes in both VPCs plus permissive security groups and NACLs; gateways and DHCP settings are irrelevant.

@ Q003857 explain
G: ## Growing a VPC's address space
A VPC's primary CIDR cannot be changed after creation, and an existing subnet's CIDR cannot be resized. What you can do is **associate secondary IPv4 CIDR blocks** with the VPC.
- Example: a VPC on `10.0.0.0/16` is nearly full; add `10.1.0.0/16` as a secondary block and create new subnets such as `10.1.0.0/20` in each Availability Zone.
- Existing instances keep running untouched; new workloads launch in the new subnets.
- The new block must not overlap existing blocks or connected networks, and some ranges are restricted depending on the primary range.
- Remember to add the new range to route tables of peered VPCs, transit gateway routes, on-premises routes and any firewall rules.
There is a quota on CIDR blocks per VPC (default 5, adjustable).
W: Secondary CIDR plus new subnets: it adds address space to the same VPC with no downtime for existing resources, the least disruptive option.
X: A=Resize subnets in place: a subnet's CIDR is fixed at creation; to change it you must delete and recreate the subnet, which means moving everything in it.
C=Delete and recreate the VPC: this requires migrating every resource and reconnecting everything, the most disruptive option possible.
D=Assign public IPs: instances keep their private IP in the subnet even when they get a public address, so no private addresses are freed.
T: When a VPC runs out of IPs, add a secondary CIDR and new subnets; primary CIDRs and subnet sizes cannot be changed in place.

@ Q003858 explain
G: ## Amazon VPC IP Address Manager (IPAM)
IPAM is a central service for planning, allocating and monitoring IP space across an AWS Organization.
- You build a **pool hierarchy**, for example a top-level pool `10.0.0.0/8`, Regional pools such as `10.16.0.0/12` for `eu-west-1`, and environment pools for prod and dev.
- Pools can be shared with accounts through AWS RAM, and **allocation rules** set allowed netmask lengths and required tags.
- When a team creates a VPC, it requests a CIDR from a pool, and IPAM hands out a free, non-overlapping block.
- IPAM continuously **monitors** usage and flags overlapping or non-compliant CIDRs, and keeps allocation history.
W: IPAM: it is the service built to plan, allocate and track IP address space across accounts and Regions and prevent overlapping CIDRs.
X: A=Resolver query logging: records DNS queries made from VPCs. It helps security analysis, but it knows nothing about CIDR allocation.
B=Config aggregators: collect configuration and compliance data from many accounts into one view. You could see existing CIDRs, but Config cannot hand out non-overlapping ranges.
C=VPC Flow Logs: record accepted and rejected traffic metadata per interface. They show traffic, not address planning or allocation.
T: Organization-wide IP planning and overlap prevention is IPAM; Config and Flow Logs only observe what already exists.

@ Q003859 explain
G: ## Managed prefix lists
A managed prefix list is a named set of CIDR blocks, for example `pl-0abc123` containing `203.0.113.0/24` and `198.51.100.0/24` for a partner.
- Security group rules and route table entries can reference the list instead of individual CIDRs.

- Lists can be shared with other accounts through AWS RAM.
- Each list has a **max entries** value; when referenced, it counts that many entries against security group rule and route table quotas.
AWS also provides AWS-managed prefix lists, for example for S3 or CloudFront origin-facing addresses.
W: Managed prefix lists: they group partner CIDRs into one object referenced by security groups and route tables, so updates happen in one place.
X: B=VPC endpoint policies: IAM-style policies that control which principals and resources can be used through an endpoint. They cannot hold CIDR sets for security groups or routes.
C=DHCP option sets: supply DNS servers, domain name and NTP servers to instances. They have nothing to do with firewall rules or routes.
D=Elastic IP pools: sources of public IPv4 addresses to assign to your resources. They provide addresses, not reusable lists of partner CIDRs.
T: Reusing a changing set of CIDRs across many security groups and route tables is what managed prefix lists are for.

@ Q003860 explain
G: ## Why overlapping VPCs break routing
If VPC-A and VPC-B both use `10.0.0.0/16`, a transit gateway or the shared service cannot tell which VPC a reply for `10.0.5.20` should go to.
## Private NAT gateway pattern
- Add a small **routable** secondary CIDR to each overlapping VPC, unique across the network, for example `100.64.1.0/24` in VPC-A and `100.64.2.0/24` in VPC-B.
- Place a private NAT gateway in a subnet of that routable range and attach the transit gateway there.
- Workloads in the overlapping (non-routable) subnets send traffic to the private NAT gateway, which replaces the source with its own routable IP.
- The shared service sees `100.64.1.x` or `100.64.2.x`, which are unique, so replies return to the right VPC.
This works for connections initiated from the overlapping VPCs toward the shared service.
W: Private NAT gateways: they translate the overlapping source addresses into unique routable ranges, so both VPCs can reach the shared service through the transit gateway.
X: A=Internet gateways and public IPs: this sends private traffic over the internet and exposes every instance publicly, abandoning the private transit gateway design.
B=Direct peering to the shared VPC: this bypasses the required transit gateway, and the shared VPC can route only one path for the duplicated range, so reaching both works only with fragile, more specific per-subnet routes.
D=One route table with both CIDRs: a transit gateway route table holds one route per destination, so the same `10.0.0.0/16` can point to only one of the two VPCs.
T: Overlapping CIDRs are reconciled with private NAT to unique routable ranges; routing cannot distinguish duplicates.

@ Q003861 explain
G: ## Resolving on-premises names from a VPC
By default, workloads query the Route 53 Resolver (the VPC `.2` address), which knows public DNS and Route 53 private hosted zones but not your corporate DNS.
## Outbound endpoint plus forwarding rule
- An **outbound endpoint** places network interfaces in your VPC subnets that send DNS queries to external resolvers over Direct Connect or VPN.
- A **forwarding rule** says which domain goes where, for example `corp.example.com -> 10.50.0.10, 10.50.0.11`.
- Associate the rule with the VPCs (or share it with RAM). Now `app.corp.example.com` goes to on-premises DNS, while everything else is resolved as usual.
The endpoint's security group must allow DNS (TCP and UDP 53) out to the on-premises servers, and a route to them must exist.
W: Outbound endpoint with a forwarding rule: this sends queries for `corp.example.com` from the VPC to the on-premises DNS servers, exactly the required direction.
X: A=DHCP options with AmazonProvidedDNS only: that is the default, and the Resolver alone has no knowledge of the private corporate zone, so the names still fail.
C=Public hosted zone with copied records: it publishes internal names to the internet and becomes a manual copy that drifts from the real on-premises records.
D=Inbound endpoint with a system rule: an inbound endpoint receives queries from on-premises into AWS, the opposite direction, and a system rule makes the Resolver answer locally instead of forwarding.
T: VPC-to-on-premises DNS uses an outbound endpoint and a forwarding rule; inbound endpoints are for the reverse direction.

@ Q003862 explain
G: ## Two directions, two endpoints
Hybrid DNS with Route 53 Resolver has two independent flows:
- **AWS to on-premises**: an **outbound endpoint** plus **forwarding rules** send queries such as `corp.example.com` from VPCs to on-premises DNS servers.
- **On-premises to AWS**: an **inbound endpoint** gives IP addresses inside the VPC, for example `10.0.1.10` and `10.0.2.10`, which on-premises DNS servers use as conditional forwarding targets for zones such as `aws.example.com` (a private hosted zone).
Each endpoint needs at least two IP addresses (placed in different Availability Zones for resilience), and both are reached over Direct Connect or VPN, so no internet exposure is needed.
W: D=Outbound endpoints with forwarding rules: they let AWS workloads resolve on-premises private names by forwarding those domains to corporate DNS.

G: ## Route 53 Resolver query logging
Query logging records the DNS queries that resources in your VPCs send to the Route 53 Resolver.
- Each log entry includes the queried name, record type, response code, the answer, and the source VPC and IP.
- Destinations: **CloudWatch Logs**, **Amazon S3** or **Amazon Data Firehose**.
- You create a query logging configuration and associate it with one or more VPCs; configurations can be shared across accounts with AWS RAM.
Example: security analysts search the logs for an instance that repeatedly resolves a suspicious domain, a sign of malware beaconing. Combined with DNS Firewall, you can both log and block.
W: Resolver query logging: it captures DNS queries from VPC resources and delivers them to a log destination for security analysis.
X: B=Traffic flow policies: define how Route 53 answers queries for your own records (latency, geolocation, failover). They do not record lookups made from your VPCs.
C=Public DNSSEC signing: cryptographically signs your public zone's answers; it produces no log of queries from VPC resources.
D=Health check alarms: notify when monitored endpoints become unhealthy. They track endpoint status, not DNS queries.
T: Logging DNS lookups from VPCs is Resolver query logging; traffic flow, DNSSEC and health checks concern the records you publish.

G: ## Network infrastructure as code
Infrastructure as code (IaC) describes VPCs, subnets, route tables and transit gateway attachments in versioned templates, then deploys them automatically.
- **CloudFormation StackSets** deploy one template to many accounts and Regions; with service-managed permissions and AWS Organizations, they can deploy automatically to new accounts added to an OU.
- **Terraform** modules do the same through a CI/CD pipeline, for example one `vpc` module called per account with a different CIDR from IPAM.
- Pipelines add code review, testing and approvals, and redeploying the template corrects drift.
Example: every new workload account gets the same three-tier VPC layout and a transit gateway attachment with the right tags, without any console work.
W: IaC through pipelines: StackSets or Terraform deploy the same reviewed definitions everywhere, which is the reliable way to get consistent networks across accounts.
X: B=Shared settings document: each owner still configures by hand, so typos and skipped steps cause differences; a document enforces nothing.
C=Screenshots in a wiki: screenshots cannot be deployed or validated and go stale as soon as the reference VPC changes.
D=Manual console configuration: different engineers in different accounts inevitably diverge, and there is no history or repeatable way to fix drift.
T: Consistent multi-account networking comes from IaC deployed by pipelines (StackSets or Terraform), not from documents or console clicks.

G: ## Event-driven transit gateway automation
An attachment is associated with exactly one transit gateway route table. With **default route table association** enabled, every new attachment lands in the same table, which ignores segmentation.
## Tag-based association with EventBridge and Lambda
- An **EventBridge rule** matches the attachment-creation event, for example the CloudTrail-recorded `CreateTransitGatewayVpcAttachment` call or a Network Manager topology change event for a transit gateway registered in a global network.
- It invokes a **Lambda function** that reads tags such as `env=prod` on the attachment.
- The function calls `AssociateTransitGatewayRouteTable` for `prod-rt` and `EnableTransitGatewayRouteTablePropagation` into the right tables (disassociating first if a default association exists).
The attachment is placed in the correct segment within seconds, with no human step.
W: EventBridge plus Lambda: reacting to the creation event and applying tag-based associations automatically is fast, consistent and needs no manual work.
X: A=Email the network team: relies on people remembering to email and on manual follow-up, so attachments sit in the wrong table or unassociated for hours.
C=Weekly manual review: attachments can stay misrouted for up to a week, and fixes still depend on people doing them correctly.
D=Default association for all: every attachment lands in one route table regardless of tags, which breaks environment segmentation instead of enforcing it.
T: Automatic, tag-based transit gateway association is event-driven: EventBridge triggers Lambda; defaults and manual reviews cannot segment reliably.
