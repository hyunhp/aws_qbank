G: ## What AWS Network Manager does
AWS Network Manager is the central console for a **global network**: a container you create that holds your transit gateways, AWS Cloud WAN core network and on-premises resources.
- You register transit gateways from any Region, and Network Manager discovers their attachments (VPCs, VPNs, Direct Connect gateways, peerings).
- You describe on-premises locations as **sites**, **devices** and **links**, so a branch router and its VPN to AWS appear on the same map.
- It draws topology and route views, shows events such as a VPN tunnel going down, and publishes metrics to CloudWatch.
## Example
A company with transit gateways in `us-east-1` and `eu-west-1` plus 30 branch routers registers them all in one global network. The operations team then opens one topology diagram instead of 30 VPN consoles in two Regions.
W: AWS Network Manager: it is built to visualize and monitor a global network made of transit gateways, Cloud WAN and registered on-premises sites, devices and links from a single dashboard.
X: A=Amazon Macie: Macie scans S3 buckets to discover and classify sensitive data such as personal information. It has no view of routers, attachments or network topology.
B=AWS Artifact: Artifact is a portal for downloading AWS compliance reports and accepting agreements. It shows documents, not live network resources.
C=AWS Cost Explorer: Cost Explorer charts spending by service, account or tag. It can show what the network costs but not how transit gateways and sites are connected.
T: Network topology across transit gateways and on-premises sites lives in Network Manager; the other services cover data security, compliance paperwork and cost.

@ Q003868 explain
G: ## Two private ways to reach S3 over Direct Connect
Direct Connect offers different virtual interfaces (VIFs), and each gives a different path to Amazon S3 that never touches the public internet.
- A **public VIF** lets your router receive the AWS public prefixes (including S3's) over BGP. Traffic to S3's public endpoints then flows over the dedicated DX link instead of your ISP.
- A **private VIF** connects to a VPC (through a virtual private gateway or Direct Connect gateway). Inside that VPC, an **S3 interface endpoint** (PrivateLink) places network interfaces with private IPs from the VPC's CIDR. On-premises clients use the endpoint-specific DNS names, such as `bucket.vpce-xxxx.s3.us-east-1.vpce.amazonaws.com`, and reach S3 through those private IPs.
## Example
An on-premises backup server sends data to `10.1.2.15`, the endpoint's IP, over the private VIF; S3 receives it without the traffic leaving AWS or the DX link.
W: C=Private VIF plus S3 interface endpoint: interface endpoints are reachable from on-premises over a private VIF, so clients use private IPs in the VPC to reach S3 entirely over DX.
E=Public VIF: a public VIF advertises S3's public prefixes to the customer router over BGP, so traffic to S3 endpoints uses the Direct Connect link rather than the internet.
X: A=Public hosted zone for S3: a hosted zone only answers DNS queries; it does not create a network path, and public names would still resolve to endpoints reached however the client normally routes.
B=Second internet gateway: a VPC can have only one internet gateway, and an internet gateway is by definition a path to the internet, the opposite of the requirement.
D=NAT gateway: a NAT gateway translates private addresses for outbound internet access and cannot be used by on-premises traffic arriving over DX; it would also send S3 traffic out through the internet gateway.
T: Over DX, reach S3 either through a public VIF to its public endpoints or through a private VIF to an interface endpoint; NAT, internet gateways and DNS zones do not keep traffic off the internet.

@ Q003869 explain
G: ## Gateway endpoints versus interface endpoints for S3
S3 supports two kinds of VPC endpoint.
- A **gateway endpoint** is a target you add to route tables. AWS adds a route whose destination is the S3 **prefix list** (for example `pl-63a5400a`) and whose target is the endpoint (`vpce-...`). Instances keep using normal S3 DNS names, and traffic follows the route to S3 privately. There is **no hourly or per-GB charge**.
- An **interface endpoint** (PrivateLink) creates network interfaces with private IPs in your subnets. It is billed per endpoint per AZ per hour and per GB processed. Its advantage is that it can be reached from on-premises or peered networks.
## Example
Private instances that download 20 TB a month from S3 through a NAT gateway pay NAT data processing on every GB. Adding a gateway endpoint to their route table moves that traffic to a free path, and no application change is needed.
W: S3 gateway endpoint: it gives private subnets a route to S3 without NAT, and it has no hourly or data processing charge, so it is the cheapest option for in-VPC access.
X: A=NAT gateway route: this is what the company wants to avoid; NAT gateways charge per hour and per GB processed for all S3 traffic that passes through them.
B=S3 interface endpoint: it works privately, but it adds hourly charges per AZ and a per-GB processing fee. It is only needed when on-premises or other networks must reach S3.
C=Internet gateway route: an internet gateway is not usable from a private subnet without public IPs, and it sends S3 traffic out to public endpoints instead of keeping it private.
T: For S3 access from inside a VPC, the gateway endpoint is free; pay for an interface endpoint only when traffic comes from outside the VPC.

@ Q003870 explain
G: ## How a gateway endpoint actually works
A gateway endpoint is not a network interface with an IP address. It is a **route table target**: subnets whose route table contains the S3 prefix list route to `vpce-...` send S3 traffic through it.
- Only traffic that originates **inside the VPC** and uses those route tables can use it.
- Traffic that arrives from outside, over Direct Connect, Site-to-Site VPN, VPC peering or a transit gateway, cannot be forwarded on to a gateway endpoint. There is no IP for on-premises routers to point at, and AWS does not transit that traffic.
## What to use instead
An **interface endpoint** for S3 creates ENIs with private IPs such as `10.0.3.25`. On-premises clients reach those IPs over a private VIF or VPN, and the endpoint forwards the request to S3.
W: Reachable only from within the VPC: gateway endpoints are route-table entries used by resources in the VPC itself, so traffic entering the VPC from on-premises over DX cannot use them; an interface endpoint is required.
X: A=Requires a public VIF: gateway endpoints are created inside a VPC with no Direct Connect dependency at all. A public VIF is a separate way to reach public S3 endpoints and is not a prerequisite.
C=DynamoDB only: gateway endpoints exist for exactly two services, S3 and DynamoDB. S3 is the most common use of a gateway endpoint.
D=Unusable by EC2: EC2 instances in the associated subnets are the main consumers of a gateway endpoint; the endpoint is regional, which is why it reaches buckets in the same Region.
T: Gateway endpoints serve only traffic that starts inside the VPC; for on-premises clients over DX or VPN, use an S3 interface endpoint.

@ Q003871 explain
G: ## BGP communities on a Direct Connect public VIF
On a **public VIF** you advertise your own public prefixes to AWS. By default AWS propagates them to all AWS public Regions. You can limit that reach by tagging each prefix with a **scope community**:
- `7224:9100` keeps the prefix within the local AWS Region.
- `7224:9200` propagates it to all Regions on the same continent.
- `7224:9300` (or no tag) propagates it globally.
## Example
A company advertises `203.0.113.0/24` from a DX location near `eu-central-1` with `7224:9100`. Only services in that Region send return traffic over this link; traffic from other Regions uses another path.
AWS also tags the routes it sends you with communities such as `7224:8100` (same Region) so you can filter what you accept.
W: Scope communities such as `7224:9100`: they are the AWS-defined communities that control how far customer prefixes advertised on a public VIF propagate inside AWS (local Region, continent or global).
X: A=MED values: MED is a path-preference hint between links to the same neighbor; it does not tell AWS how widely to propagate a prefix across its network.
B=Local preference communities: the `7224:7100` to `7224:7300` communities influence which path AWS prefers for traffic back to you on private and transit VIFs; they do not control propagation scope.
D=Prepending AWS's routes: AS_PATH prepending is done by the router advertising a route, and the customer cannot change routes that AWS advertises; it also affects preference, not scope.
T: Scope on a public VIF is set with `7224:9100/9200/9300` communities; local preference communities and MED only influence path choice.

@ Q003872 explain
G: ## Why IPv6 needs a different egress component
IPv6 addresses in a VPC are globally unique and publicly routable, so there is no address translation like IPv4 NAT. To give instances outbound-only access you need a device that allows connections that start inside and blocks connections that start outside.
- An **egress-only internet gateway** does exactly that for IPv6. It is stateful: return traffic for outbound sessions is allowed, new inbound connections are dropped.
- You add a route such as `::/0` pointing to `eigw-...` in the private subnet's route table.
## Example
An instance with address `2600:1f18:abcd::10` can download updates over IPv6, but an internet host trying to open a connection to that address is blocked at the gateway, even though the address is public.
W: Egress-only internet gateway: it provides stateful outbound-only IPv6 internet access, allowing replies but blocking any connection initiated from the internet.
X: B=Transit gateway attachment: a transit gateway routes between VPCs and on-premises networks; by itself it provides no internet egress and no inbound filtering.
C=NAT gateway: a NAT gateway translates private IPv4 addresses; it does not provide outbound-only access for native IPv6 traffic, which is what the egress-only gateway exists for.
D=Virtual private gateway: a VGW terminates VPN and Direct Connect connections to on-premises networks and provides no path to the internet.
T: Outbound-only IPv6 uses an egress-only internet gateway; NAT gateways solve the IPv4 private-address problem instead.

@ Q003873 explain
G: ## Sharing Route 53 Resolver rules
A Resolver **forwarding rule** says "send DNS queries for `corp.example.com` to these on-premises DNS servers through this outbound endpoint". Rules are regional resources owned by one account.
- **AWS Resource Access Manager (RAM)** can share a rule with individual accounts or with an organization or OU, once sharing with AWS Organizations is enabled.
- Each receiving account then **associates** the shared rule with its VPCs. The outbound endpoint stays in the central networking account.
- New accounts that join the OU receive the share automatically.
## Example
A networking account creates one rule for `corp.example.com` and shares it with the "Workloads" OU. All 40 accounts associate it with their VPCs, and a later change to the target IPs is made once centrally.
W: Share with the OU through RAM: RAM distributes the same rule to every account in the OU, including future ones, while it is managed in one place.
X: A=Recreate manually: 40 copies each need their own outbound endpoint or rule edits and drift apart over time; every change must be repeated 40 times.
B=Public hosted zone: a public hosted zone holds records answered on the internet; it cannot forward private queries to on-premises DNS servers.
D=DHCP option sets: DHCP options only tell instances which DNS servers and domain name to use; they cannot hold conditional forwarding rules, and pointing instances at on-premises DNS directly bypasses the Resolver.
T: Build Resolver rules once in a central account and share them with the OU through RAM; each account just associates them with its VPCs.

@ Q003874 explain
G: ## Making automated routing changes safe
Routing mistakes spread fast: one wrong route can blackhole traffic for many VPCs. Safe network automation limits how much can break at once and proves the result.
- **Verify intent**: VPC Reachability Analyzer traces a path, for example from an instance to a transit gateway attachment, and says whether it is reachable and which component blocks it. Running the same checks before and after a change shows exactly what changed.
- **Stage the rollout**: deploy to one account, VPC or Region first, watch health checks and alarms, then continue. If an alarm fires, roll back automatically (for example with CloudFormation rollback triggers or a pipeline stage).
## Example
A pipeline updates transit gateway routes in one Region, runs a Reachability Analyzer check, waits for CloudWatch alarms to stay green, and only then moves to the next Region.
W: A=Reachability Analyzer checks: path analysis before and after deployment confirms that the intended paths still work and catches blocked or new paths before users notice.
E=Staged deployment with automated rollback: releasing in small steps with health-check-driven rollback limits the blast radius and restores the last good state quickly.
X: B=Disable monitoring: turning off alarms during the riskiest moment hides failures, so a bad route can stay in place much longer.
C=All Regions at peak: changing everything at once, when the most users are affected, maximizes the blast radius and leaves no healthy Region to fail over to.
D=Manual console edits afterward: manual edits make the real configuration differ from the code, so the next automated deployment may overwrite or conflict with them.
T: Prove paths with Reachability Analyzer and roll out in stages with automatic rollback; big-bang changes, blind spots and manual drift raise risk.

@ Q003875 explain
G: ## What AWS VPN CloudHub is
**AWS VPN CloudHub** uses a single **virtual private gateway** (VGW) as a hub for several Site-to-Site VPN connections (or Direct Connect connections) from different sites.
- Each site's customer gateway uses dynamic routing (BGP) with its own **unique ASN**, and sites must use non-overlapping address ranges.
- The VGW re-advertises each site's prefixes to the other sites, so branch A can reach branch B through AWS, while all sites can also reach the VPC.
## Example
Offices in Seoul (`10.10.0.0/16`, ASN 65001) and Busan (`10.20.0.0/16`, ASN 65002) each have a VPN to the same VGW. Seoul learns `10.20.0.0/16` from the VGW and sends Busan traffic over its tunnel into AWS and back out to Busan.
W: AWS VPN CloudHub: it turns the virtual private gateway into a hub that routes between multiple VPN-connected sites, giving the branch-to-branch hub-and-spoke pattern the company needs.
X: A=NAT gateways: NAT gateways give private IPv4 instances outbound internet access; they do not route between VPN sites.
C=Gateway endpoints: gateway endpoints give a VPC private access to S3 and DynamoDB; they do not carry traffic between on-premises locations.
D=VPC peering mesh: peering connects VPCs to VPCs and is not transitive, so traffic from a VPN on one VPC cannot use a peering connection to reach another network.
T: Branches that share one VGW can talk to each other through VPN CloudHub; peering and endpoints do not provide transit between sites.

@ Q003876 explain
G: ## Multicast in AWS
Multicast sends one packet to a group address (for example `239.1.1.1`) and the network copies it to every member. It is common in trading systems for market data feeds.
- A normal VPC does not forward multicast. **AWS Transit Gateway** can, when multicast support is enabled on the transit gateway.
- You create a **multicast domain**, associate VPC subnets with it, and register sources and members, either statically or dynamically through IGMPv2.
- The transit gateway then replicates each multicast packet to the members, including those in other VPCs attached to the same transit gateway.
## Example
A price-feed server in VPC A sends to group `239.1.1.1`; trading engines in VPCs B and C are members, and each receives a copy through the transit gateway.
W: Transit Gateway multicast domains: they are the AWS feature that routes multicast group traffic between sources and members in subnets across attached VPCs.
X: A=VPC peering: peering carries only unicast traffic between two VPCs; multicast and broadcast are not forwarded across a peering connection.
B=CloudFront: CloudFront caches and serves HTTP(S) content to viewers from edge locations; it has nothing to do with packet replication between EC2 instances.
C=Application Load Balancer: an ALB terminates HTTP/HTTPS connections and forwards each request to one target; it cannot deliver one packet to a group of receivers.
T: In AWS, multicast between instances in different VPCs requires a transit gateway multicast domain; peering and load balancers handle unicast only.

@ Q003878 explain
G: ## Prefix limits on Direct Connect VIFs
BGP on a Direct Connect virtual interface has a hard limit on how many prefixes the customer may advertise to AWS. For a **private VIF** (and a transit VIF) the limit is **100** prefixes per address family (IPv4 and IPv6 counted separately); a public VIF allows 1,000.
- If the customer router advertises more than the limit, AWS puts the BGP session into the **idle** state; it goes down and may come back and fail again as the router retries, which looks like flapping.
- While the session is down, the routes learned over it disappear, so on-premises networks become unreachable from AWS.
## Example
A site advertises 98 `/24` prefixes. A new data center adds five more, the count reaches 103, and the session drops. Summarizing, for example `10.20.0.0/16` instead of many `/24`s, brings the count back under 100.
W: Prefix limit exceeded: going over the private VIF's advertised-prefix limit causes AWS to shut down the BGP session, which matches both symptoms that appeared right after a new prefix was added; route summarization is the fix.
X: A=Permissive security group: a security group filters packets to instances; being too open cannot drop routes or tear down a BGP session on a DX router.
B=DX location address: the street address of a colocation facility is not part of BGP or routing, and a physical move would show as a link outage rather than lost prefixes.
D=DHCP domain suffix: a DHCP options set only affects DNS names instances use; it has no role in BGP advertisements over Direct Connect.
T: A BGP session that fails right after new prefixes are added points to the VIF prefix limit; summarize routes to stay under 100 on a private VIF.

@ Q003879 explain
G: ## Draining a BGP path before maintenance
With two Direct Connect connections, BGP picks one path as primary. If you just power off the primary router, traffic keeps flowing to it until BGP notices, which with default timers can take up to the 90-second hold time (less with BFD), and packets are lost meanwhile.
The safe method is to **drain** traffic first by making the primary path less attractive:
- **Traffic from AWS to on-premises**: prepend your ASN on the prefixes you advertise over the primary link, for example `65001 65001 65001`, or use the AWS local preference communities to prefer the backup.
- **Traffic from on-premises to AWS**: lower the local preference on routes learned over the primary link.
## Example
After the change, monitoring shows traffic has moved to the backup connection; then the primary router is patched and the attributes are restored.
W: Shift traffic to the backup first: changing BGP attributes moves traffic gracefully while both paths are still up, so the maintenance itself causes no packet loss.
X: A=Delete and recreate the VIF: deleting the VIF drops its BGP session abruptly, and recreating it means new configuration and possible new peer settings, which adds risk instead of avoiding it.
B=Change the VPC CIDR: VPC addressing has nothing to do with which DX path traffic uses, and changing the CIDR would disrupt applications rather than reroute traffic.
C=Shut down and wait for timers: until the hold timers expire, both sides keep sending traffic to a dead router, so packets are dropped during that window.
T: Before maintenance, drain traffic with AS_PATH prepending or local preference so BGP moves it while both paths are healthy; do not rely on hold timers to fail over.

@ Q003880 explain
G: ## Direct Connect failover testing
The AWS Direct Connect **Resiliency Toolkit** includes a **failover test** feature. For a chosen virtual interface you start a test that brings its **BGP sessions down** for a set duration.
- The physical connection stays up; only BGP is disabled, so routes are withdrawn and traffic must use the redundant path.
- When the duration ends, or when you cancel the test, the sessions are restored automatically.
- The test history shows when each test ran, which helps prove resiliency to auditors.
## Example
During a planned window, an engineer starts a 30-minute test on the primary VIF, confirms that applications keep working over the backup connection and that alarms fire as expected, and lets the test end.
W: Direct Connect failover testing: it is the built-in, controlled way to take BGP sessions down for a defined time and have them return automatically, which is exactly a safe failover test.
X: B=Unplugging cables unannounced: physical changes need the colocation provider, cannot be undone with a click, and surprise the team, so a real outage and a test become hard to tell apart.
C=Disable route propagation permanently: this removes routes from the VPC instead of testing the backup path, and permanent changes are the opposite of a controlled test.
D=Delete and recreate the DX gateway: deleting the gateway first requires removing its associations and attachments, causes an outage on all paths, and needs full reconfiguration afterward.
T: Use Direct Connect failover testing to temporarily disable BGP with automatic restore; destructive or permanent changes are not tests.

@ Q003881 explain
G: ## MTU, MSS and IPsec overhead
The **MTU** is the largest packet a link can carry, often 1500 bytes on Ethernet. An IPsec tunnel adds its own headers (ESP, new IP header, padding), so less room is left for the original packet.
- AWS Site-to-Site VPN supports a maximum MTU of **1446** bytes and recommends a TCP **MSS** of **1406** bytes.
- If a 1500-byte packet has the Don't Fragment bit set and the ICMP "fragmentation needed" message is blocked, the packet is silently dropped. Small packets such as pings or TCP handshakes still work.
- **MSS clamping** on the customer gateway rewrites the MSS in TCP SYN packets so both ends send smaller segments.
## Example
SSH logins over the tunnel succeed, but file transfers hang: the handshake packets are small, while full-size data segments exceed the tunnel MTU.
W: MTU and fragmentation: large packets that exceed the tunnel's effective MTU are dropped while small ones pass, which is the classic symptom; lowering the tunnel MTU or clamping MSS fixes it.
X: A=Route table by size: route tables choose a target by destination prefix only; packet size is never part of the route lookup.
C=DNS failures: if name resolution failed, no packets of any size would reach the host, because the client would not know its address.
D=Security groups by size: security group rules match protocol, port and source or destination; they have no packet-size condition.
T: Small packets work but large ones fail over a VPN means MTU; set tunnel MTU and MSS clamping to account for IPsec overhead.

@ Q003882 explain
G: ## Jumbo frames in a VPC
A **jumbo frame** is an Ethernet frame larger than the standard 1500-byte payload. Most current-generation EC2 instance types support an MTU of **9001** bytes.
- A bigger MTU means fewer packets for the same data, so less header overhead and fewer per-packet operations, which helps bulk transfers.
- 9001 bytes applies to traffic **within a VPC**. Other paths have smaller limits: inter-Region VPC peering and transit gateway attachments (VPC, Direct Connect and peering, including inter-Region peering) support up to 8500 bytes, traffic through an internet gateway is limited to 1500 bytes, and Site-to-Site VPN to 1446 bytes.
## Example
Two instances in the same VPC copying a 500 GB dataset use 9001-byte packets, sending about one sixth as many packets as with 1500 bytes. You can check a Linux instance's setting with `ip link show eth0`.
W: 9001 bytes (jumbo frames): this is the MTU that most current-generation instances support for traffic inside a VPC, which reduces packet overhead for large transfers.
X: A=576 bytes: 576 is the minimum datagram size every IPv4 host must accept, not a VPC maximum; using it would greatly increase overhead.
B=65535 bytes: 65,535 is the largest possible IPv4 packet length field value, not a supported MTU on any VPC network path.
C=1024 bytes: 1024 is not an Ethernet or VPC MTU value at all; it is smaller than even the standard 1500-byte MTU.
T: Inside a VPC, current instances can use 9001-byte jumbo frames; paths leaving the VPC are smaller.

@ Q003883 explain
G: ## MTU differs by path
An instance can use a **9001-byte** MTU with other instances in the same VPC, but not every path supports that size.
- Traffic that leaves through an **internet gateway** is limited to **1500 bytes**; Site-to-Site VPN is lower still (1446 bytes). Paths inside AWS such as inter-Region VPC peering and transit gateways allow up to 8500 bytes, so the internet path is where jumbo frames clearly break.
- If an instance sends a large packet with the Don't Fragment bit set, the path must return an ICMP "fragmentation needed" message so the sender can lower its size (path MTU discovery). If that ICMP message is blocked, for example by a security group or network ACL, large packets are silently lost.
## Example
After switching `eth0` to 9001 bytes, an instance can still ping a website but downloads stall. Allowing ICMP "destination unreachable, fragmentation needed" in, or setting the MTU to 1500 for internet-bound routes, fixes it.
W: 1500-byte limit through the internet gateway: 9001-byte frames are valid only inside the VPC and the internet path allows 1500 bytes, so large packets headed to the internet must be 1500 bytes or smaller, and the failures come from exceeding that limit.
X: A=Jumbo frames required for internet: the internet path supports only 1500 bytes, so jumbo frames are never required there; they are the cause of the problem.
C=64-byte fragmentation: internet gateways do not split packets into 64-byte pieces; oversized packets with Don't Fragment set are dropped with an ICMP message instead.
D=576-byte limit: internet gateways carry normal 1500-byte packets; if 576 were the limit, almost all internet traffic from AWS would fail.
T: 9001-byte jumbo frames work only inside the VPC; anything leaving through an internet gateway must fit 1500 bytes, so keep path MTU discovery working.

@ Q003884 explain
G: ## Finding who is being rejected
**VPC Flow Logs** record IP traffic metadata for network interfaces, subnets or VPCs: source and destination addresses and ports, protocol, packets, bytes and an `action` field that is `ACCEPT` or `REJECT`.
- Logs sent to **Amazon S3** can be queried with **Amazon Athena** using SQL.
- Logs sent to **CloudWatch Logs** can be queried with **CloudWatch Logs Insights**.
## Example
An Athena query such as `SELECT srcaddr, count(*) AS c FROM vpc_flow_logs WHERE action = 'REJECT' AND day >= '2026/09/22' GROUP BY srcaddr ORDER BY c DESC LIMIT 10` lists the top 10 source IPs whose connections the subnet rejected in the past week.
W: Query Flow Logs with Athena or Logs Insights: Flow Logs contain the per-flow source IP and accept/reject decision, and both tools can aggregate a week of records by source address.
X: B=CloudTrail management events: CloudTrail records API calls such as `AuthorizeSecurityGroupIngress`, not the network packets or connection attempts that reach a subnet.
C=Route 53 health checks: health checks probe endpoints from AWS checkers and report up or down; they do not record who tried to connect to a subnet.
D=AWS Config history: Config tracks configuration changes to resources over time, such as route or ACL edits, not traffic flows.
T: Traffic questions (who connected, what was rejected) are answered by Flow Logs; CloudTrail and Config record API calls and configuration changes.

G: ## Network Access Analyzer
**Network Access Analyzer** (a VPC feature) checks the network configuration of your AWS resources against rules you define.
- You write a **Network Access Scope**, such as "no path from an internet gateway to any instance in the database subnets" or "only the ALB may reach the app tier".

G: ## Measuring network performance to and within AWS
Two related features cover the requirement.
- **Network Manager infrastructure performance** shows near-real-time and historical latency of the AWS global network between Regions, between AZs and within an AZ, and can publish these metrics to CloudWatch. It shows whether the AWS side of the path is healthy.

X: A=AWS Artifact reports: Artifact provides compliance documents such as SOC reports; they describe controls, not live latency or loss.
C=S3 server access logs: these record requests made to a bucket, including request timing, but they do not measure latency or loss between sites and Regions.

G: ## Troubleshooting a Network Load Balancer
An NLB works at layer 4 and passes TCP, UDP or TLS connections to targets. When connections fail intermittently, look at two views.
- **NLB CloudWatch metrics**: `HealthyHostCount` and `UnHealthyHostCount` show targets failing health checks; `TCP_Target_Reset_Count` shows resets sent by targets, `TCP_Client_Reset_Count` resets from clients and `TCP_ELB_Reset_Count` resets generated by the NLB itself, for example after idle timeouts.
- **VPC Flow Logs** on the NLB's network interfaces and on the targets show whether flows are accepted or rejected, for example because a target's security group or a network ACL blocks the NLB or client IPs.
## Example
Failures line up with drops in `HealthyHostCount`, and flow logs show `REJECT` on the health check port for one subnet, pointing to a network ACL that was changed.
W: A=VPC Flow Logs: they reveal accepted and rejected connections on the NLB and target interfaces, which exposes filtering problems between clients, the NLB and targets.
E=NLB CloudWatch metrics: reset counts and healthy host counts show whether targets, clients or the load balancer are closing connections and when targets fail health checks.
X: B=Hosted zone change history: DNS record changes could matter only if the NLB name moved; this history shows no connection-level data about failures.
C=AWS Budgets forecasts: Budgets predicts and alerts on spend; it has no information about connections or targets.
D=IAM credential report: this lists users and the status of their passwords and access keys; it is unrelated to network connections through the NLB.
T: Diagnose NLB connection failures with its CloudWatch metrics (resets, healthy hosts) plus Flow Logs (accept/reject); billing, IAM and DNS history do not show connections.

G: ## Where NAT gateway charges come from
A NAT gateway is billed per hour and per **GB processed**. Every byte that private instances send or receive through it counts, including traffic to AWS services such as S3 and DynamoDB.
- **Gateway VPC endpoints** exist for exactly those two services. Adding one inserts a prefix list route (for example `pl-xxxx` to `vpce-xxxx`) into the private subnets' route tables.
- Because the prefix list route is more specific than `0.0.0.0/0` to the NAT gateway, S3 and DynamoDB traffic now bypasses the NAT gateway.
- Gateway endpoints have **no hourly or data processing charges**.
## Example
Instances that read 50 TB a month from S3 through NAT pay the per-GB NAT fee on all 50 TB. With a gateway endpoint that fee disappears, and the application code does not change.
W: Gateway VPC endpoints for S3 and DynamoDB: they route that traffic around the NAT gateway at no charge, removing the data processing cost for the heaviest traffic.
X: A=More NAT gateways in the same AZ: the per-GB fee applies to every NAT gateway, so the same traffic costs the same, plus extra hourly charges.
B=Larger subnet range: charges depend on data processed and hours, not on how many IP addresses the subnet holds.
C=Public subnets with public IPs: this avoids NAT but exposes instances to the internet, changes the security design, and incurs public IPv4 address charges; it is not the intended fix.
T: For S3 and DynamoDB traffic, a free gateway endpoint replaces the NAT gateway path; more NAT capacity only adds cost.

G: ## Cross-zone load balancing on an NLB
Each NLB has a node in every enabled Availability Zone.
- With **cross-zone load balancing disabled** (the NLB default), each node sends traffic only to registered targets in its own AZ.
- With it **enabled**, each node spreads traffic across targets in all AZs, so a share of traffic crosses AZ boundaries. For NLBs, that traffic is billed as inter-AZ data transfer.
- Disabling it is safe only if clients and targets are balanced per AZ; otherwise one AZ's targets can be overloaded.
## Example
An NLB in two AZs with cross-zone enabled sends about half of each node's traffic to the other AZ. With four targets in each AZ and clients spread evenly, disabling cross-zone keeps traffic AZ-local and removes those charges.
W: Disable cross-zone load balancing when traffic is balanced per AZ: each NLB node then uses targets in its own AZ, so inter-AZ data transfer between the NLB and targets stops.
X: A=Classic Load Balancer: moving to a previous-generation load balancer is a migration, not a setting on the existing NLB, and it gives up NLB features such as a static IP per AZ and very high connection rates; the direct fix is to stop the NLB from sending traffic across AZs.
C=Enable cross-zone for all target groups: this sends more traffic to targets in other AZs, which increases the inter-AZ charges rather than reducing them.
D=Targets in a third AZ: an AZ with no client traffic can only receive requests from other AZs, so its targets create cross-AZ traffic instead of removing it.
T: NLB inter-AZ charges come from cross-zone load balancing; keep it off when each AZ has enough targets for its own traffic.

G: ## What limits single-flow throughput
A single flow is one TCP or UDP 5-tuple (same source and destination IP and port). EC2 limits how fast one flow can go, separately from the instance's total bandwidth.
- **Cluster placement groups** put instances close together in one AZ. Single-flow traffic between instances in the same cluster placement group can reach up to **10 Gbps**, versus about **5 Gbps** otherwise, and latency is lower.
- **Enhanced networking with ENA** uses SR-IOV for higher bandwidth, higher packets per second and lower latency; current-generation instance types use it. **ENA Express** can raise single-flow throughput further between supported instances in the same AZ.
## Example
An HPC job copying data between two instances in the same cluster placement group, both with ENA, can push a single stream up to about 10 Gbps, where the same instances outside the placement group would be capped near 5 Gbps.
W: C=Cluster placement group: placing instances together in a low-latency group raises the per-flow limit and reduces latency.
E=Enhanced networking (ENA): ENA provides higher bandwidth and packet rates with lower latency, which is the basis for high per-flow performance.
X: A=Public internet: sending traffic out and back over the internet adds latency and hops outside AWS's control, and traffic that leaves the VPC through an internet gateway is limited to a 1500-byte MTU.
B=Through a NAT gateway: a NAT gateway adds an extra hop and processing charges and caps bandwidth per gateway; it does nothing to raise per-flow throughput.
D=Smaller previous-generation instances: network bandwidth scales with instance size and generation, so smaller older instances lower the throughput available.
T: Raise single-flow throughput with cluster placement groups and ENA; extra hops, internet paths and smaller instances only reduce it.

G: ## Transit gateway versus peering costs
A transit gateway is billed per attachment-hour and per **GB of data processed** for traffic sent into it from a VPC, VPN or Direct Connect attachment. For two VPCs that exchange many terabytes, that per-GB fee adds up.
- **VPC peering** has no hourly charge and no processing fee. Traffic within the same AZ over a peering connection is free, and traffic across AZs is charged the normal inter-AZ data transfer rate.
- Peering is not transitive, so it is a targeted addition, not a replacement. The heavy pair gets a peering connection with more specific routes, and all other VPCs keep using the transit gateway.
## Example
VPC A (`10.1.0.0/16`) and VPC B (`10.2.0.0/16`) exchange 100 TB a month through a transit gateway. Adding a peering connection and routes to each other's CIDR removes the TGW processing fee for that 100 TB.
W: Peering for the high-volume pair: peering avoids the transit gateway's per-GB processing charge for that traffic while the transit gateway still serves every other connection.
X: A=Increase MTU: charges are per GB processed, not per packet, so larger packets carry the same data at the same cost.
B=Move VPCs to different Regions: inter-Region traffic adds data transfer charges and inter-Region transit gateway peering, so the same traffic becomes more expensive.
C=A second transit gateway: sending traffic through two transit gateways means paying processing on two hops and extra attachment hours.
T: For one heavy VPC pair in the same Region, add a peering connection to skip the transit gateway's per-GB fee and keep the TGW for everything else.
