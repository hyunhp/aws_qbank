# DEA-C01 batch 06: Domain 2 (data store management) and Domain 3 (data operations and support)

@ DEA-C01 D2 T2.1 applied use-case
S: An EMR Spark job and a GPU training fleet run in one Availability Zone and repeatedly read millions of small intermediate files through the S3 API. The files can be regenerated if lost, and per-request latency now dominates job run time. The team wants to keep using the S3 API. Which storage choice fits BEST?
A: An S3 Standard bucket with S3 Transfer Acceleration turned on so that each GET request is served through the nearest edge location
B: An S3 Express One Zone directory bucket created in the same Availability Zone as the compute that reads and writes the files
C: An Amazon EFS One Zone file system mounted on every node so that the jobs can read the small files with low file-system latency
D: An S3 bucket that uses the S3 Intelligent-Tiering storage class so that frequently read files stay in the Frequent Access tier
K: B
G: ## Where S3 latency comes from
S3 Standard stores objects across at least three Availability Zones and typically answers each request in tens of milliseconds. For large sequential reads this is invisible, but a job that makes millions of small GET and PUT calls pays that latency over and over.
## S3 Express One Zone
- Data lives in a **directory bucket** in one Availability Zone you choose, so compute placed in that zone gets consistent **single-digit millisecond** access.
- It still uses the S3 API (with session-based authentication handled by the SDK), so Spark, training code and Mountpoint for Amazon S3 work with little change.
- Request charges are lower than S3 Standard, which suits request-heavy workloads.
- The trade-off is resilience: data is stored in only one zone, so it fits data that can be recreated, such as shuffle output, checkpoints or staged training shards.
Example: `s3://train-cache--use1-az4--x-s3/` placed in `use1-az4` next to the training nodes.
W: S3 Express One Zone: a directory bucket co-located with the compute gives single-digit millisecond requests through the same S3 API, and the single-zone durability is acceptable because the files can be regenerated.
X: A=Transfer Acceleration: speeds up long-distance transfers over the internet through edge locations; compute in the same Region gains nothing and per-request latency stays the same.
C=EFS One Zone: offers low latency but is a file system mounted over NFS, so the jobs would have to move off the S3 API the team wants to keep.
D=Intelligent-Tiering: only changes the price tier based on access patterns; the Frequent Access tier has the same latency as S3 Standard.
T: Latency-bound, re-creatable data read through the S3 API next to compute belongs in S3 Express One Zone; tiering and acceleration do not cut request latency.
V: Amazon S3, Amazon EMR

@ DEA-C01 D2 T2.1 applied use-case
S: A payments company must detect fraud rings by finding accounts that share devices, cards or IP addresses up to five hops apart, and each check must return in well under a second while a payment is being authorized. The relationships change constantly. Which data store fits BEST?
A: Amazon DynamoDB with an adjacency-list design, where the application issues one Query per hop and merges the results in code
B: Amazon Redshift with recursive common table expressions that walk the relationship table from the account to five levels deep
C: Amazon OpenSearch Service with nested documents for each account and terms queries that match shared device and card values
D: Amazon Neptune storing accounts, devices, cards and IPs as vertices and edges, queried with openCypher or Gremlin traversals
K: D
G: ## When relationships are the data
Questions like "which accounts are connected to this one through shared devices or cards, up to five steps away" are **traversals**. In a relational or key-value store, each hop becomes another join or another round trip, and the work grows quickly with depth.
## Graph databases
A graph database stores **vertices** (account, device, card, IP) and **edges** (USES, PAID_WITH, LOGGED_IN_FROM) directly, so following a relationship is a pointer lookup rather than a join.
- **Amazon Neptune** is a managed graph database supporting property graphs queried with **openCypher** or **Gremlin**, and RDF with **SPARQL**.
- It is built for low-latency, high-throughput online traversals on continuously updated data.
Example (openCypher): `MATCH (a:Account {id:$id})-[*1..5]-(b:Account) RETURN DISTINCT b.id`
W: Neptune: multi-hop traversals over accounts, devices, cards and IPs are exactly what a graph database executes natively, with the low latency needed inside payment authorization and constant updates to edges.
X: A=DynamoDB adjacency list: can store edges, but a five-hop search becomes many sequential round trips with fan-out handled in application code, which is slow and complex at depth.
B=Redshift recursive CTE: a warehouse built for analytical scans, not sub-second lookups during each payment; recursive joins over a large relationship table are too slow here.
C=OpenSearch nested documents: finds documents sharing a value, one level at a time; it has no traversal operator, so multi-hop rings need repeated queries and custom logic.
T: Deep relationship traversal at online latency calls for a graph database like Neptune; key-value and warehouse stores turn each hop into another query or join.
V: Amazon Neptune

@ DEA-C01 D2 T2.1 applied use-case
S: A company runs a self-managed Apache Cassandra cluster on EC2 for a time-series application. Operations staff spend most of their time on node repairs, patching and capacity planning. The application team will not rewrite its CQL queries or change its Cassandra drivers. Which option fits BEST?
A: Migrate the tables to Amazon Keyspaces (for Apache Cassandra) and point the existing CQL drivers at the service endpoint
B: Migrate the tables to Amazon DynamoDB and use the DynamoDB SDK because its partition and sort keys match Cassandra keys
C: Move the Cassandra cluster onto larger EC2 instances in an Auto Scaling group so that nodes are replaced when they fail
D: Migrate the tables to Amazon DocumentDB and use its compatibility layer so that the application keeps its query model
K: A
G: ## Compatible managed services
AWS offers several databases that speak the wire protocol of a popular open-source engine, so existing drivers and queries keep working while AWS runs the servers.
- **Amazon Keyspaces (for Apache Cassandra)**: serverless, Cassandra Query Language (CQL) compatible, with on-demand or provisioned capacity, automatic scaling and no nodes to repair or patch.
- **Amazon DocumentDB**: MongoDB API compatible, for JSON document workloads.
- **Amazon DynamoDB**: a key-value and document store with its own API; its data model resembles Cassandra's wide rows, but code must be rewritten for the DynamoDB API.
## Migration outline
Create the keyspace and tables with the same CQL schema, load data (for example with `cqlsh COPY` or AWS Glue), then change the driver contact point to the Keyspaces endpoint with TLS and service credentials.
W: Amazon Keyspaces: it is CQL compatible and serverless, so the application keeps its queries and drivers while repairs, patching and capacity planning disappear.
X: B=DynamoDB: similar key concepts, but it uses its own API, so every CQL query and driver call would have to be rewritten, which the team refuses.
C=Bigger EC2 nodes in Auto Scaling: still self-managed Cassandra, so repairs, patching and capacity planning remain the team's job.
D=DocumentDB: is compatible with the MongoDB API, not with CQL, so the Cassandra drivers and queries would not work.
T: Keep Cassandra drivers and CQL but drop cluster operations with Amazon Keyspaces; DynamoDB and DocumentDB require a rewrite.
V: Amazon Keyspaces (for Apache Cassandra)

@ DEA-C01 D2 T2.2 advanced troubleshooting
S: An AWS Glue crawler runs every hour over an S3 bucket that holds hundreds of millions of objects. New files arrive in both new and existing partition folders, and newly added columns must appear in the Data Catalog. Each crawl now takes hours because the crawler lists the whole bucket. Which change fixes this MOST effectively?
A: Change the recrawl policy to crawl new folders only, so that each run lists and processes only the folders created since the last crawl
B: Lower the crawler sample size so that only a few files in each leaf folder are read, which shortens the schema inference for the bucket
C: Set the crawler to use S3 event notifications delivered to an SQS queue, so that each run processes only the objects that changed
D: Split the bucket into several crawlers with exclusion patterns, and run all of those crawlers on the same hourly schedule in parallel
K: C
G: ## Why large crawls get slow
By default a Glue crawler **lists every object** under its S3 targets on each run, then inspects files to infer schemas and partitions. With hundreds of millions of objects, listing alone can take hours even when only a few thousand files are new.
## Recrawl options
- **Crawl all folders**: full listing every time (the default).
- **Crawl new sub-folders only**: incremental; only folders added since the last run are processed, and existing tables' schemas are not updated, so files added to existing folders and new columns are missed.
- **Crawl based on events**: S3 event notifications for the bucket go to an **SQS queue**. The crawler reads the queue and processes only the changed objects and their folders, which can still update schemas and add partitions.
Example: `RecrawlPolicy: {RecrawlBehavior: CRAWL_EVENT_MODE}` with the S3 target's `EventQueueArn` set to `arn:aws:sqs:...:crawler-events`.
W: S3 event mode: the crawler consumes object-created events from SQS instead of listing the bucket, so each run touches only the changed objects while still detecting new partitions and new columns.
X: A=New folders only: skips files added to existing partition folders and does not update existing table schemas, so it breaks both stated requirements.
B=Smaller sample size: limits how many files are read per folder, but the crawler still lists every object, which is the slow part, and it risks missing new columns.
D=Parallel split crawlers: spreads the listing across crawlers but still lists everything each hour, and multiple crawlers writing related tables adds catalog conflicts to manage.
T: For huge buckets with ongoing changes, drive the crawler from S3 events through SQS; incremental folder crawls miss changes in existing folders and schemas.
V: AWS Glue, Amazon S3, Amazon SQS

@ DEA-C01 D2 T2.2 advanced troubleshooting
S: An Athena table has over one million partitions keyed by event_date and customer_id, where customer IDs are arbitrary strings added daily. Some queries filter only on a customer_id and others only on a date range, and query planning alone takes a long time. The S3 layout must not change. Which change BEST reduces planning time?
A: Configure partition projection with a date range for event_date and the enum type for customer_id listing all existing values
B: Run MSCK REPAIR TABLE after every load so that the Data Catalog always has the full and current list of all table partitions
C: Enable Athena query result reuse on the workgroup so that repeated queries skip planning and read the cached query results
D: Create AWS Glue partition indexes on customer_id and on event_date, and enable partition filtering in the table properties
K: D
G: ## Why planning slows down
Before scanning data, Athena asks the Glue Data Catalog for the partitions that match the query's filters. Without help, the catalog returns partitions in pages and many of them are filtered afterward, so a table with a million partitions can spend seconds or minutes just finding the right folders.
## Two ways to speed this up
- **Partition projection**: Athena computes partition values from rules in the table properties (date ranges, integer ranges, enum lists, or injected values supplied in each query) and skips the catalog. It works best when values are predictable. `enum` needs every value listed in the table properties, and `injected` requires every query to supply the key with an equality filter.
- **Glue partition indexes**: up to three indexes per table on partition keys. The catalog uses them to return only the matching partitions to query engines such as Athena. In Athena, set `partition_filtering.enabled = true` on the table.
Example: indexes `idx_customer (customer_id)` and `idx_date (event_date)` serve both filter patterns.
W: Partition indexes: the catalog can look up matching partitions directly by customer_id or by event_date, cutting planning time without changing the S3 layout and without predicting future customer values.
X: A=Projection with enum: customer IDs are arbitrary and added daily, so the enum list would need constant rewriting, and injected projection fails for the queries that filter only by date.
B=MSCK REPAIR TABLE: registers partitions that are missing from the catalog; it adds more partitions to scan through and does nothing to speed up lookups.
C=Query result reuse: returns cached results only for identical query text within the reuse window, so new filter values still plan from scratch.
T: Unpredictable partition keys and huge partition counts call for Glue partition indexes; projection needs predictable values.
V: AWS Glue Data Catalog, Amazon Athena

@ DEA-C01 D2 T2.2 advanced use-case
S: A producer account governs its S3 data lake with AWS Lake Formation, including column-level permissions on a sales database. Analysts in a consumer account must query some tables with Athena, and the column restrictions must still apply without copying data. Which TWO steps are required? (Select TWO)
A: In the producer account, grant Lake Formation permissions on the selected tables and columns to the consumer account ID
B: In the producer account, add a bucket policy that allows the consumer account to read the S3 prefixes of the sales tables
C: In the consumer account, create a resource link to the shared database and grant the analysts permissions on the tables
D: In the consumer account, run a Glue crawler over the producer's S3 paths so that local tables point to the same data
E: In both accounts, enable S3 Cross-Region Replication so that the consumer receives a synchronized copy of the tables
K: A,C
G: ## Cross-account sharing with Lake Formation
Lake Formation permissions (database, table, column, row and cell level) are stored in the account that owns the Data Catalog. To share them:
- The producer grants permissions on databases, tables or column subsets to an **external AWS account** (or an organization or OU). Lake Formation uses AWS RAM behind the scenes; outside an organization the consumer must accept the RAM invitation.
- The consumer data lake administrator then **re-grants** those permissions to local principals and creates a **resource link**: a catalog object in the consumer account that points to the shared database or table. Athena queries the shared data through the resource link.
- Data stays in the producer's bucket; Lake Formation vends temporary credentials so no bucket policy for the consumer is needed.
Example: resource link `sales_shared` in the consumer catalog points to `producer:sales`; analysts get SELECT on the permitted columns only.
W: A=Producer grant to the account: shares exactly the allowed tables and columns while Lake Formation keeps enforcing column restrictions.
C=Consumer resource link and re-grant: makes the shared database visible to Athena in the consumer account and lets the local administrator give analysts access within what was shared.
X: B=Bucket policy for the consumer: gives raw S3 read access that bypasses Lake Formation, so column restrictions would not apply to anyone reading the files directly.
D=Consumer crawler on producer paths: creates ungoverned duplicate tables in the consumer catalog, again bypassing the producer's column permissions.
E=Cross-Region Replication: copies the data, which the requirement forbids, and replication alone creates no catalog tables or permissions.
T: Share governed tables across accounts with a Lake Formation grant plus a resource link in the consumer; S3 access or copies bypass the permissions.
V: AWS Lake Formation, AWS Glue Data Catalog, Amazon Athena, AWS RAM

@ DEA-C01 D2 T2.2 advanced tradeoff
S: Analysts write Athena queries that join a large Parquet fact table with several dimension tables, and they often list the tables in an inefficient order. Performance varies widely depending on who wrote the query. The team wants the engine to choose better join orders automatically. Which action helps MOST?
A: Enable Athena query result reuse so that queries with the same text return cached results for the configured maximum age
B: Generate column statistics for the tables in the AWS Glue Data Catalog so that the Athena cost-based optimizer can use them
C: Add partition projection to each dimension table so that Athena calculates their partitions instead of calling the catalog
D: Convert all the dimension tables from Parquet to gzip-compressed JSON so that each one of them is read as a single file
K: B
G: ## Rule-based versus cost-based planning
Without statistics, a query engine plans joins mostly in the order they are written, so a query that joins the huge fact table first can shuffle far more data than needed.
## Athena cost-based optimizer
The Athena engine includes a **cost-based optimizer (CBO)**. It reads **column statistics** stored in the Glue Data Catalog, such as number of distinct values, null counts and min/max values, and uses them to:
- reorder joins so smaller inputs are built first,
- push down aggregations when that reduces work.
Glue can generate these statistics on demand or on a schedule for catalog tables, recording them with the table.
Example: after statistics are generated for `sales`, `store` and `product`, a query written as `sales JOIN store JOIN product` is planned with the filtered dimensions first.
W: Glue column statistics: they give the cost-based optimizer the distinct counts, null counts and value ranges it needs to reorder joins, so performance no longer depends on how each analyst wrote the query.
X: A=Query result reuse: only serves identical queries from cache; any new query still runs with the same poor join order.
C=Partition projection: speeds up partition lookup for partitioned tables, but it tells the planner nothing about table sizes for join ordering.
D=gzip JSON dimensions: makes scans slower and larger; row-based text formats remove the column pruning that Parquet provides.
T: To let Athena pick join orders itself, give its cost-based optimizer Glue column statistics; caching and projection do not change join planning.
V: Amazon Athena, AWS Glue Data Catalog

@ DEA-C01 D2 T2.2 applied troubleshooting
S: A Glue crawler runs over S3 folders containing application logs in a custom line format such as "2026-09-29T10:15:02Z INFO [orders] user=42 latency=87ms". The crawler creates a table with classification UNKNOWN and no useful columns. What should the data engineer do so the crawler catalogs the logs correctly?
A: Increase the crawler sample size so that more files in each folder are inspected before a built-in classifier is picked
B: Add a custom CSV classifier with a space delimiter, because the built-in CSV classifier cannot parse the log lines
C: Add a custom JSON classifier with a JSONPath expression that points the crawler to the fields inside each log line
D: Create a custom grok classifier with a pattern that matches the log line format and add it to the crawler's classifiers
K: D
G: ## How crawlers decide the format
A crawler tries **classifiers** on sample files. Custom classifiers attached to the crawler are tried first, in the order listed; if none matches with certainty, the built-in classifiers (JSON, CSV, Parquet, Avro, common log formats and others) are tried. If nothing matches, the table gets the classification `UNKNOWN`.
## Classifier types
- **Grok**: named regular-expression patterns, ideal for log lines. Built-in patterns such as `%{TIMESTAMP_ISO8601}`, `%{LOGLEVEL}` and `%{NUMBER}` can be combined, and custom patterns can be added.
- **CSV**: delimited text with a chosen delimiter and quote character.
- **JSON**: a JSONPath that selects the records inside JSON documents.
- **XML**: a row tag.
Example grok pattern: `%{TIMESTAMP_ISO8601:ts} %{LOGLEVEL:level} \[%{WORD:service}\] user=%{INT:user_id} latency=%{INT:latency_ms}ms`
W: Custom grok classifier: it describes the log line with named patterns, so the crawler recognizes the files and creates columns such as ts, level, service, user_id and latency_ms.
X: A=Larger sample size: reading more files does not help when no classifier understands the format; the result stays UNKNOWN.
B=Space-delimited CSV classifier: splits on every space, so fields like "user=42" keep their labels and the bracketed service name keeps its brackets, producing unusable columns.
C=JSON classifier: the lines are not JSON, so a JSONPath has nothing to select and the classifier will not match.
T: Custom text log formats need a grok classifier; CSV and JSON classifiers only fit data that is actually delimited or JSON.
V: AWS Glue, Amazon S3

@ DEA-C01 D2 T2.3 applied tradeoff
S: A data lake bucket stores several million objects, mostly 5 to 200 MB. Some datasets go untouched for months and then are suddenly read heavily when a new model is trained, and nobody can predict which ones. The team wants to lower storage cost without retrieval fees or lifecycle rules to maintain. Which approach fits BEST?
A: Store the objects in S3 Intelligent-Tiering so that S3 moves each object between access tiers based on its actual access
B: Add a lifecycle rule that moves every object to S3 Standard-IA after 30 days and back to S3 Standard when it is read
C: Add a lifecycle rule that moves every object to S3 Glacier Instant Retrieval after 90 days to reduce the storage price
D: Store all the objects in S3 One Zone-IA from the beginning, because it has the lowest price for instantly readable data
K: A
G: ## Matching storage class to access pattern
Lifecycle rules work well when access is **predictable by age**: hot for 30 days, then cold. When access is unpredictable, age-based rules either move data too early (then pay retrieval fees when it becomes hot again) or too late.
## S3 Intelligent-Tiering
- S3 monitors each object and moves it automatically: to **Infrequent Access** after 30 days without access, to **Archive Instant Access** after 90 days, and back to **Frequent Access** as soon as it is read.
- There are **no retrieval fees**; instead there is a small monthly monitoring charge per object.
- Objects smaller than 128 KB are not monitored or tiered and always bill at the Frequent Access rate, so the class suits larger objects like these.
- Optional Archive and Deep Archive Access tiers can be enabled for data that may wait hours for retrieval.
Example: a 150 MB training file untouched since spring sits in Archive Instant Access, then is read in milliseconds without a retrieval charge.
W: Intelligent-Tiering: it tiers each object by its real access pattern, returns it to Frequent Access when read, charges no retrieval fees and needs no lifecycle rules to tune, which fits unpredictable access to large objects.
X: B=Standard-IA after 30 days: charges per-GB retrieval fees on every read, and lifecycle rules cannot move objects back to Standard when they get hot again.
C=Glacier Instant Retrieval: has higher retrieval fees than Standard-IA, which a sudden heavy read of a whole dataset would multiply.
D=One Zone-IA: keeps data in one Availability Zone and still charges retrieval fees, so it adds risk without solving the unpredictable-read cost.
T: Unpredictable access to large objects fits S3 Intelligent-Tiering; age-based lifecycle rules to IA or Glacier add retrieval fees when data turns hot.
V: Amazon S3

@ DEA-C01 D2 T2.3 applied use-case
S: Financial records in an S3 bucket must be retained for 7 years and protected from deletion or overwrite by engineers and pipelines. However, a small compliance team must be able to remove objects that were uploaded in error, after an approval process. Which configuration fits BEST?
A: Enable Object Lock in compliance mode with a 7-year default retention, and let the account root user delete erroneous objects
B: Place a legal hold on every object as it arrives, and give pipeline roles permission to remove legal holds whenever needed
C: Enable Object Lock in governance mode with a 7-year default retention, and grant only the compliance role bypass permission
D: Enable versioning with MFA Delete, so that deleting an object version always requires the root user's MFA device and code
K: C
G: ## S3 Object Lock basics
Object Lock stores objects in a write-once-read-many (WORM) model on a versioned bucket. A locked object version cannot be deleted or overwritten until its protection ends.
## Retention modes and legal hold
- **Compliance mode**: nobody, including the root user, can delete the version or shorten its retention until the period ends.
- **Governance mode**: most users are blocked, but a principal with `s3:BypassGovernanceRetention` can delete or change retention by sending the `x-amz-bypass-governance-retention:true` header.
- **Legal hold**: an on/off flag with no end date; anyone with `s3:PutObjectLegalHold` can remove it.
- A **default retention** on the bucket applies a mode and period to every new object automatically.
Example: default retention governance, 7 years; only `ComplianceAdminRole` has the bypass permission, and its deletions can be audited with CloudTrail data events.
W: Governance mode with bypass for one role: every object is locked for 7 years against engineers and pipelines, while the approved compliance role can still remove erroneous uploads through the audited bypass permission.
X: A=Compliance mode with root delete: in compliance mode not even the root user can delete a locked version before retention ends, so erroneous uploads could never be removed.
B=Legal hold removable by pipelines: legal holds have no retention period, and letting pipeline roles remove them defeats the protection against those same pipelines.
D=MFA Delete: protects against version deletion but provides no retention period, and it is managed only by the root user, not a compliance team.
T: WORM retention that a controlled exception role can override is governance mode; compliance mode allows no override at all.
V: Amazon S3

@ DEA-C01 D2 T2.3 applied tradeoff
S: An auditor needs 40 TB of log archives, about 3 million objects in the S3 Glacier Flexible Retrieval storage class, restored for analysis. The analysis can start any time within the next 24 hours, and the company wants the lowest restore cost with minimal custom code. Which approach fits BEST?
A: Use S3 Batch Operations with a manifest of the objects and a Restore job that uses the Bulk retrieval tier
B: Use S3 Batch Operations with a manifest of the objects and a Restore job that uses the Expedited retrieval tier

G: ## Reading archived objects
Objects in S3 Glacier Flexible Retrieval must be **restored** before they can be read. A restore creates a temporary copy in S3 for the number of days you specify, while the archived object stays in its class.
## Retrieval tiers for Flexible Retrieval
- **Expedited**: typically 1 to 5 minutes, highest cost, meant for small urgent requests.

- **Bulk**: typically 5 to 12 hours, the lowest-cost tier, designed for large volumes.

@ DEA-C01 D2 T2.4 advanced tradeoff
S: An Athena table over Parquet files in S3 is registered in the Glue Data Catalog as a standard Hive-style table. Over the next year the team must rename several columns, drop others and reorder some, while older files keep their original column names and existing queries return correct data. Which approach fits BEST?
A: Rename and drop the columns directly in the Glue Data Catalog table definition, and let Athena map them onto the old files
B: Set the table property that makes Athena read Parquet columns by position, then rename the columns in the table definition
C: Convert the table to Apache Iceberg and apply the changes with ALTER TABLE statements, which track columns by internal IDs
D: Keep the Hive-style table unchanged and create a view that renames the columns, adding a new view version for every change
K: C
G: ## How Parquet columns are matched
A Hive-style table in the Glue Data Catalog is only a schema; the Parquet files carry their own column names. By default Athena matches catalog columns to file columns **by name**. Rename `cust_id` to `customer_id` in the catalog, and old files have no `customer_id`, so the column reads as NULL.
Athena can instead read Parquet **by position**, which survives a rename but breaks as soon as columns are dropped or reordered, because positions then point at the wrong data.
## Apache Iceberg schema evolution
Iceberg records a **unique ID for every column** in table metadata, and data files are read by ID, not by name or position. Therefore:
- rename, drop, add and reorder are metadata-only changes, with no file rewrites,
- old files continue to return correct values under the new names.
Example in Athena: `ALTER TABLE orders CHANGE COLUMN cust_id customer_id string`.
W: Iceberg with ALTER TABLE: column IDs let renames, drops and reorders happen as metadata changes while older files still map to the right columns, so queries stay correct across the whole history.
X: A=Rename in the catalog: Athena matches Parquet columns by name, so renamed columns return NULL for every file written before the change.
B=Read Parquet by position: survives a pure rename, but dropping or reordering columns shifts positions, so values land in the wrong columns.
D=View per change: the base table keeps the old names, so new files written with the new column names do not match it by name, and every change adds another view layer to maintain.
T: Frequent renames, drops and reorders need Iceberg's ID-based columns; Hive-style tables match by name or position and break.
V: Amazon Athena, AWS Glue Data Catalog, Amazon S3

@ DEA-C01 D2 T2.4 advanced use-case
S: An Apache Iceberg table of clickstream events is partitioned by day of event_ts. Traffic has grown so that daily partitions are huge, and most new queries filter by hour. The team wants new data partitioned by hour without rewriting the existing history, and queries should keep filtering only on event_ts. Which approach fits BEST?
A: Recreate the table with a CREATE TABLE AS SELECT statement that partitions all history by hour, then switch the readers to it
B: Use Iceberg partition evolution in Spark SQL to add an hours(event_ts) partition field and drop the days(event_ts) field
C: Add a new event_hour column populated by the writers, and register it as an extra Hive-style partition column on the table
D: Configure Athena partition projection with an hourly date range on event_ts so that queries compute the hour partitions
K: B
G: ## Hidden partitioning in Iceberg
Iceberg partitions with **transforms** on source columns, such as `days(event_ts)` or `hours(event_ts)`. The partition value is derived from the column, so queries just filter on `event_ts`, and Iceberg prunes files; users never reference a separate partition column.
## Partition evolution
The partition spec is table metadata and can change over time:
- `ALTER TABLE db.events ADD PARTITION FIELD hours(event_ts)`
- `ALTER TABLE db.events DROP PARTITION FIELD days(event_ts)`
These statements run in Spark with the Iceberg SQL extensions, for example in AWS Glue or Amazon EMR. Existing files keep the daily layout, new files are written hourly, and the planner prunes each set according to its own spec. Nothing is rewritten unless you choose to run a compaction or rewrite later.
Example: a filter `event_ts BETWEEN '2026-09-29 10:00' AND '2026-09-29 11:00'` prunes old day partitions and new hour partitions in one query.

1. COPY the batch into a **staging table**.

@ DEA-C01 D3 T3.2 applied tradeoff
S: A product dashboard shows daily unique visitors computed with COUNT(DISTINCT user_id) over billions of rows in Athena, and the query is slow and expensive. Product managers accept an answer within a few percent of the exact value. Which change gives the BIGGEST improvement with the least effort?

G: ## Why exact distinct counts are expensive
`COUNT(DISTINCT x)` must track every distinct value it has seen, then combine those sets across workers. With billions of rows and hundreds of millions of users, this needs a lot of memory and data shuffling.

Athena (Trino engine) provides `approx_distinct(x)`, based on the **HyperLogLog** algorithm. Each worker keeps a small fixed-size sketch instead of the full set, and sketches merge cheaply.

D=GROUP BY before counting: performs the same distinct aggregation in a different form, so the cost stays the same.
T: When a few percent error is fine, approx_distinct beats COUNT(DISTINCT); scaling up a sample does not work for distinct counts.
