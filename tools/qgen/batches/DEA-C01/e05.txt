@ Q000351 explain
G: ## Distribution keys and sort keys in Redshift
A Redshift cluster spreads each table's rows across compute node slices. The **distribution style** decides which slice a row lands on; the **sort key** decides the order of rows on disk inside each slice.
- `DISTKEY(customer_id)` on both the fact and the dimension table hashes the same `customer_id` value to the same slice, so a join on `customer_id` runs locally with no network redistribution (a "collocated join").
- `SORTKEY(order_date)` stores rows in date order. Redshift keeps min/max values for every 1 MB block (zone maps), so a filter like `WHERE order_date >= '2026-01-01'` skips whole blocks that cannot match.
## Example
An orders fact table with billions of rows joined to `customers` on `customer_id` and filtered by last month's `order_date`: with these keys, the join avoids broadcasting data between nodes and the scan reads only the blocks for last month.
W: DISTKEY customer_id and SORTKEY order_date: the distribution key matches the join column so joins are collocated, and the sort key matches the filter column so zone maps prune blocks during scans.
X: A=Sort on customer_id with EVEN: EVEN distribution scatters matching customer rows across slices, forcing data redistribution for every join, and sorting on the join column does little for the `order_date` filters that dominate the workload.
B=Unused sort column with ALL on the fact table: a sort key that never appears in filters prunes nothing, and ALL copies the entire large fact table to every node, multiplying storage and load time; ALL suits small dimension tables, not big fact tables.
D=No keys, decided at query time: Redshift cannot pick a physical layout per query. AUTO distribution and sort keys are adjusted in the background over time, but when the join and filter columns are well known, choosing them explicitly gives the predictable win the question asks for.
T: Distribute on the join column to avoid shuffling rows between nodes, and sort on the filter column so zone maps skip blocks; ALL distribution is for small tables only.

@ Q000352 explain
G: ## Fine-grained access in AWS Lake Formation
Lake Formation governs tables registered in the AWS Glue Data Catalog. Instead of granting access to S3 paths, you grant permissions on databases, tables and columns, and integrated engines such as Athena, Redshift Spectrum, EMR and Glue enforce them.
- **Column-level security**: grant `SELECT` on a table while including or excluding specific columns, for example everything except `national_id`.
- **Data filters**: a data cells filter combines a column list with an optional row filter expression, such as `tenant_id = 'acme'`, and can be granted to a principal like a table.
- **LF-Tags**: tag sensitive columns (for example `classification=pii`) and grant access by tag, so new tables inherit the policy.
## Example
A multi-tenant lake stores all tenants in one `customers` table. Analysts of tenant A get a data filter with `tenant_id = 'A'` and all columns except `national_id`; the compliance team gets the full column set.
W: Identify sensitive columns and use Lake Formation filters: once sensitive columns are identified, column-level grants and data cells filters make the query engines themselves hide those columns (and rows) from principals who are not entitled to them.
X: A=Same table, application-level filtering: any user or tool that queries the table directly bypasses the application, so the national IDs are fully exposed; nothing in the data layer enforces the restriction.
B=One shared KMS key with decrypt for everyone: encryption at rest protects against storage-level access, but granting decrypt to all users means everyone can read every column. Encryption is not an authorization boundary per column.
C=Separate account with no catalog entry: data with no Data Catalog entry cannot be governed by Lake Formation at all, and moving whole datasets to another account does not provide per-column control within a table that users still need.
T: Column-level security in a Lake Formation data lake comes from column grants, data filters and LF-Tags enforced by the query engines, not from application logic or blanket encryption.

@ Q000353 explain
G: ## How DynamoDB spreads writes
DynamoDB hashes the partition key value to choose a physical partition. Each partition has throughput limits (about 1,000 write units and 3,000 read units per second), so all writes for one key value go through one partition.
- With `order_status` as the key there are only four values, such as `PENDING`, `PAID`, `SHIPPED`, `CANCELLED`. Most new orders share one status, so almost every write hits the same partition: a **hot partition**.
- **Higher-cardinality key**: use an attribute with many distinct values, such as `order_id` or `customer_id`, so writes spread evenly.
- **Write sharding**: append a suffix to a low-cardinality value, for example `PENDING#0` to `PENDING#9`, chosen randomly or by hash; readers query all shards and merge.
## Example
10,000 new orders per second all written with `order_status = PENDING` throttle; keyed by `order_id`, the same load spreads over many partitions.
W: Higher-cardinality key or write sharding: both spread writes across many partition key values, which is the only way to remove a per-partition throughput bottleneck caused by a key with just four values.
X: B=GSI on the same order_status key: a GSI with the same low-cardinality key is just as hot, and a throttled GSI can also throttle writes to the base table; it adds write cost instead of capacity.
C=Reduce read capacity: read and write capacity are separate settings and lowering one does not transfer capacity to the other, and the limit being hit is per partition, not the table's total.
D=Switch to provisioned billing: the billing mode does not change how keys map to partitions. A hot key throttles under either mode, and provisioned mode adds the risk of under-provisioning.
T: Hot partitions come from low-cardinality keys; fix them by choosing a high-cardinality key or sharding the key, not by adding indexes or changing capacity settings.

G: ## Partition pruning in Athena
Athena charges by bytes scanned, so the fastest and cheapest query is the one that reads the fewest files.
- **Partitioning** stores data in S3 prefixes by a column value, for example `s3://lake/events/event_date=2026-09-28/`. The Glue Data Catalog (or partition projection) knows which prefix holds which value.
- When a query has `WHERE event_date = DATE '2026-09-28'`, Athena reads only that prefix and ignores the rest: this is **partition pruning**.
- Parquet adds further savings: it is columnar and compressed, so only the needed columns are read.
## Example
A table with 3 years of daily data has about 1,100 partitions. A one-day query reads roughly 1/1,100 of the data instead of all of it.
W: Partition by event_date: since almost every query filters on `event_date`, Athena can skip every partition outside the requested dates, which directly reduces bytes scanned, cost and latency.
X: A=Global secondary index on the bucket: GSIs are a DynamoDB feature; S3 buckets have no indexes, and Athena prunes data through partitions and file statistics instead.
B=One huge file regardless of date: a single file forces a full scan for every date filter and also limits parallel reading; very large or very small files both hurt performance.
D=Uncompressed CSV instead of Parquet: CSV is row-based and uncompressed, so every query reads every column and many more bytes, raising cost and latency.
T: For Athena, match partitions to the most common filter column and keep columnar compressed formats; bytes scanned drive both cost and speed.

@ Q000359 explain
G: ## Column compression encodings in Redshift
Redshift stores each column separately and can compress each one with its own **encoding**, for example `AZ64` for numbers and dates, `ZSTD` or `LZO` for text, `BYTEDICT` for low-cardinality values, and `RAW` (no compression).
- Smaller columns mean less disk usage and fewer blocks to read per scan, so queries become faster as well as cheaper to store.
- `ANALYZE COMPRESSION table_name` samples the table and reports the recommended encoding per column and the estimated space saving.
- You apply the result with `ALTER TABLE ... ALTER COLUMN ... ENCODE ...` or by recreating the table. Columns created with `ENCODE AUTO` let Redshift manage encodings over time.
## Example
A `status` column with five distinct values stored as `RAW` occupies far more blocks than the same column encoded with `BYTEDICT` or `ZSTD`.
W: Apply suitable column encodings (ANALYZE COMPRESSION): the command recommends the best encoding per column from real data, and applying those encodings shrinks storage and the number of blocks each scan must read.
X: B=Add nodes without changing encoding: more nodes add capacity and cost, but each column still wastes space and every scan still reads the same inflated blocks; it treats the symptom, not the cause.
C=Convert the table to a view: a view stores no data of its own and must query an underlying table, so the data still has to live somewhere with the same encoding problem.
D=Disable compression entirely: that is the cause of the problem; uncompressed columns take the most space and need the most I/O per scan.
T: Wasteful storage and slow scans on a Redshift table point to missing column encodings; use ANALYZE COMPRESSION or ENCODE AUTO rather than adding hardware.

@ Q000360 explain
G: ## Two different tools for fast access
- A **Redshift sort key** defines the physical order in which rows are stored inside each slice. Redshift keeps min/max values per 1 MB block (zone maps), so range filters on the sort key skip blocks. It is part of the table's storage layout; changing it rewrites the data (for example `ALTER TABLE ... ALTER SORTKEY`, which reorganizes the table in the background).
- A **DynamoDB global secondary index (GSI)** is a separate, automatically maintained copy of selected attributes with its own partition key and optional sort key. It lets you query items by attributes other than the base table's primary key. The base table is not reordered.
## Example
A `game_scores` DynamoDB table keyed by `player_id` gets a GSI keyed by `game_id` and `score` to answer "top scores for a game". A Redshift `orders` table sorted by `order_date` answers "last week's orders" by reading only recent blocks.
W: Sort keys order data on disk; GSIs add query patterns: a sort key is a storage-order optimization for scans in one table, while a GSI is an extra index structure that enables new access patterns.
X: B=Identical purposes, different names: they solve different problems, scan pruning in a columnar warehouse versus alternative key lookups in a key-value database, and they work in completely different ways.
C=A GSI reorders the base table: a GSI is stored separately from the base table and is updated asynchronously; the base table's item layout stays organized by its own primary key.
D=Sort keys change at query time with no layout effect: a sort key is defined on the table and determines how data is stored; queries cannot choose a different one, and changing it means rewriting data.
T: A Redshift sort key is about how one table's rows are physically ordered; a DynamoDB GSI is a separate index that adds new ways to query the data.

@ Q000361 explain
G: ## Where the embedding model fits in RAG
Retrieval-augmented generation (RAG) has two stages: retrieve relevant text, then let a language model answer using it.
- An **embedding model** turns text into a vector of numbers so that texts with similar meaning land close together, even with different wording.
- At ingestion, a knowledge base (for example Amazon Bedrock Knowledge Bases) splits documents into chunks, embeds each chunk and stores the vectors in a vector store such as Amazon OpenSearch Serverless.
- At query time the question is embedded with the same model, and the nearest vectors are returned as context.
If the embedding model does not capture the meaning of your domain or language well, "How do I reset my login?" may not land near a chunk titled "Password recovery", and retrieval returns the wrong chunks.
## Choosing better
Pick an embedding model suited to the content (language, domain, dimensions), such as Amazon Titan Text Embeddings or Cohere Embed on Bedrock, and re-embed the documents when you change it.
W: It maps text to vectors for semantic search; choose a suitable one: retrieval quality depends on how well the embedding model places paraphrased questions near the right chunks, so a better-suited model fixes mismatched wording.
X: A=It generates the final answer; use a larger LLM: generation happens after retrieval, so a larger LLM still receives the same irrelevant chunks; the embedding model does not generate answers.
B=It compresses documents; compress more: embeddings are not a storage compression step, and more aggressive reduction would lose meaning and make retrieval worse.
C=It translates queries; turn translation off: an embedding model does not translate text, and there is no translation step to disable; the query must be embedded to be searched at all.
T: In RAG, the embedding model decides what gets retrieved; fix paraphrase mismatches with a better-suited embedding model, not a bigger generator.

@ Q000362 explain
G: ## Normalized versus denormalized items in DynamoDB
DynamoDB has no joins. How you store related data decides how many requests a read needs.
- **Normalized**: an order item holds only `product_id`; showing an order means reading the order, then each product, which is several requests and more latency.
- **Denormalized**: the order item embeds the product name and price at the time of purchase (or items share a partition key and are read with one `Query`), so one request returns the whole order view.
## The cost of denormalizing
Embedded copies of data must be kept consistent. If a product name changes, every copy that should reflect it has to be updated, for example through DynamoDB Streams and a Lambda function, and item sizes grow (items are limited to 400 KB).
Some copies are intentionally frozen, such as the price an order was placed at, which is often exactly what the business wants.
W: Faster reads, at the cost of duplicated data to keep in sync: denormalization designs the table around access patterns so reads need fewer requests, and the price is redundancy that writes must maintain.
X: A=Only affects write costs, not reads: the main purpose of denormalizing is to change read patterns, turning several lookups into one request.
B=No downsides; always prefer it: duplicated data increases storage and item size and requires update logic; normalized items still fit data that changes often and is read rarely.
D=Not possible in DynamoDB: DynamoDB items can hold nested maps and lists, and single-table designs that denormalize are a standard, recommended pattern.
T: Denormalizing in DynamoDB trades extra storage and sync work on writes for fewer, faster reads that match known access patterns.

@ Q000363 explain
G: ## Orchestrating mixed services with Step Functions
AWS Step Functions runs **state machines** defined in Amazon States Language. Each state does one thing:
- **Task** states call services; optimized integrations such as `glue:startJobRun.sync` and `elasticmapreduce:addStep.sync` start a job and wait until it finishes, and a Task can also invoke a Lambda function.
- **Choice** states branch on data (for example, run a cleanup path when a row count is zero).
- **Retry** and **Catch** blocks add retries with backoff and error handling per state.
- **Wait**, **Parallel** and **Map** states handle delays and fan-out.
The console draws the workflow as a graph and colors each state in every execution, so operators can see where a run is or where it failed.
## Example
Start a Glue job and wait, add an EMR step and wait, then a Choice state checks whether the job output is non-empty and, only if it is, a Task state invokes a Lambda function to publish results; failed steps retry three times.
W: AWS Step Functions: it natively coordinates Glue, EMR and Lambda, waits for jobs to complete, supports branches and retries, and gives operators a visual execution view.
X: A=A single Glue trigger: Glue triggers start Glue jobs and crawlers based on schedules or events within Glue workflows; they do not run EMR steps or Lambda with general branching logic.
B=A cron job on an EC2 instance: this means writing and hosting your own orchestration code, retries and monitoring, with a server to patch and no built-in visual view of runs.
C=An EventBridge rule per step: rules react to events one at a time; chaining them spreads the logic across many rules, with no single place for branching, retries or a view of the whole run.
T: When a workflow spans several AWS services with branching, retries and waits, use Step Functions rather than per-service triggers or custom scripts.

G: ## Why MWAA tasks sit in "queued"
In Amazon Managed Workflows for Apache Airflow (MWAA), the scheduler puts ready tasks on a queue, and **workers** pick them up. A task stays queued while no worker slot is free.
- The **environment class** (`mw1.small`, `mw1.medium`, `mw1.large` and larger) sets how much CPU and memory each worker has and the default number of tasks a worker runs at once.
- **Minimum and maximum workers** set how far MWAA can autoscale the worker fleet when the queue grows.
- Airflow settings such as `celery.worker_autoscale` and pool sizes also cap concurrency.
## Example
An environment with `max workers = 1` on a small class can run only a handful of tasks at a time. If 40 tasks become ready at midnight, most wait in the queue; raising max workers lets MWAA add workers and drain the queue.
W: Raise the environment class or max workers: long queue times with healthy DAGs and scheduler mean the environment lacks worker capacity, and a larger class or higher worker limit adds task slots.
X: A=Enable S3 bucket versioning: MWAA already requires versioning on its bucket for DAGs, plugins and requirements; versioning affects file history, not how many tasks run at once.
B=Decrease schedule_interval: running the DAG more often creates even more task instances, making the queue longer.
D=Earlier start_date: moving the start date back can trigger catch-up runs for past intervals, which adds work instead of freeing workers.
T: Tasks stuck in queued on MWAA signal too few worker slots; scale the environment class or max workers instead of changing DAG scheduling.

G: ## Starting a Glue job from code
AWS Glue exposes a `StartJobRun` API. In Python, the AWS SDK Boto3 calls it as `glue.start_job_run()`:
- `JobName` picks the existing job definition.

The Lambda execution role needs `glue:StartJobRun` permission on that job.
## Example
A Lambda function triggered by an SQS message reads the message body, calls `start_job_run(JobName="daily-etl", Arguments={"--file": key})`, and writes the returned `JobRunId` with the message ID to a tracking table.

X: A=Invoke through the S3 script URL: the script location in S3 is just where Glue reads the code from; fetching that URL downloads a file and does not start a job run.
B=CloudFormation creates a new job each time: creating a stack per message is slow, leaves many job definitions to clean up, and still does not start a run or return a run ID by itself.
D=Arguments in an SNS topic for Glue: Glue jobs do not subscribe to SNS topics; publishing a message does not start a job or pass arguments to it.

G: ## Token-based pagination
Many APIs return results in pages. Each response contains a slice of the data and, if more exists, a continuation token such as `nextToken`.
- The client sends the first request without a token.
- If the response includes `nextToken`, the client sends the next request with that token.
- It repeats until a response arrives with no token, which means the last page has been read.
## Example
A loop in the Lambda function: call `GET /records`, save `items`, read `nextToken`; while the token is present, call `GET /records?nextToken=<value>` and append the results. After the loop, write the combined data to S3.
Keep an eye on the Lambda 15-minute maximum: for very large result sets, save the last token (for example in DynamoDB) so a later invocation can continue, or move to a Step Functions loop.
W: Loop, passing nextToken until none is returned: this reads every page the API offers and stops exactly when the API signals that no more data exists.
X: A=API Gateway merges the pages: API Gateway fronts your own APIs; it does not call a third-party API repeatedly and combine paginated responses on your behalf.
B=Increase the Lambda timeout: a longer timeout gives the function more time but does not make it request the next pages; without the loop it still reads only the first page.
D=Single call, assume all data returned: the presence of `nextToken` shows the API returns partial results, so a single call silently drops every page after the first.
T: Paginated APIs require a loop that follows the continuation token until it disappears; more time or a gateway does not fetch the missing pages.

G: ## CREATE TABLE AS SELECT in Athena
A CTAS statement runs a query and saves its result as a new table in one step:
- the result files are written to S3 in the format you choose, such as Parquet with Snappy compression,
- a table definition pointing to those files is added to the AWS Glue Data Catalog,
- optional properties set `partitioned_by` and `bucketed_by` columns.
Example:
`CREATE TABLE sales_summary WITH (format = 'PARQUET', write_compression = 'SNAPPY', external_location = 's3://lake/sales_summary/') AS SELECT region, month, SUM(amount) AS total FROM sales GROUP BY region, month`
Downstream Athena, Glue or EMR jobs then query `sales_summary` directly instead of re-running the expensive query. `INSERT INTO` can add new rows later.
W: CREATE TABLE AS SELECT (CTAS): it materializes the query result as compressed Parquet in S3 and registers a permanent Data Catalog table, exactly as required.
X: B=Named query with parameters: a named query stores SQL text for reuse; running it returns results but creates no permanent table.

G: ## Event-driven start of a state machine
To start Step Functions with no polling code, combine two features:
- **S3 to EventBridge**: turn on EventBridge notifications for the bucket. Every object event, such as `Object Created`, is sent to the default event bus.
- **An EventBridge rule**: an event pattern filters the events, for example on the bucket name and a key pattern using `prefix`, `suffix` or `wildcard` matching such as `uploads/*.csv`. The rule's target is the state machine ARN, with an IAM role that allows `states:StartExecution`.
The event JSON (bucket, key, size) becomes the execution input, so the first state knows which object to process.
## Example
A rule matches objects created under `raw/` ending in `.parquet` and starts the `ingest-pipeline` state machine once per file.
W: S3 EventBridge notifications and a rule targeting the state machine: S3 publishes the events, the rule filters for the object pattern, and EventBridge starts the execution directly with the event as input.
X: A=Poll with a Wait state every 5 minutes: this is exactly the custom polling the company wants to avoid; it also adds up to five minutes of delay and needs an execution already running to poll.
B=AWS Config plus manual start: Config records resource configuration changes, not individual object uploads, and a manual start is not automatic.
D=SNS with only an email subscription: email is for people; someone still has to start the execution by hand, so nothing is automated.
T: For automatic reaction to matching S3 uploads, send S3 events to EventBridge and target the state machine from a rule with the right key pattern.

G: ## GROUP BY, then HAVING
SQL evaluates a query roughly in this order: `FROM`, `WHERE`, `GROUP BY`, `HAVING`, `SELECT`, `ORDER BY`.
- `WHERE` filters individual rows before grouping; it cannot use aggregates like `SUM`.
- `GROUP BY region` collapses all rows with the same region into one group.
- `HAVING` filters those groups after aggregation, so it is the place to test aggregates such as `SUM(amount) > 100000`.
## Example
Rows: East 60,000 + 70,000; West 40,000 + 30,000; North 150,000.
- Groups: East 130,000, West 70,000, North 150,000.
- `HAVING SUM(amount) > 100000` keeps East and North.
Result: two rows, `East 130000` and `North 150000`. West disappears even though it exists, because its total is too small. No ranking or limit is applied, so several regions can qualify.
W: Each region's total, only where the total exceeds 100000: the query sums `amount` per region and HAVING removes groups whose sum is 100,000 or less.
X: A=Only the single highest region: nothing in the query sorts or limits results; returning only the top region would need `ORDER BY total_sales DESC LIMIT 1`.
B=Error, HAVING cannot use aggregates: filtering on aggregates is the purpose of HAVING; it is WHERE that cannot contain aggregate functions.
D=Individual rows with amount over 100000: that would be `WHERE amount > 100000` without grouping; this query compares each region's total, not single rows.
T: WHERE filters rows before grouping; HAVING filters groups after aggregation, so this query returns every region whose total exceeds the threshold.
