@ Q000401 explain
G: ## The shared responsibility model moves with the service
AWS always secures the physical data centers, host hardware and hypervisor. How much of the software stack above that belongs to you depends on how managed the service is.
- On **Amazon EC2** you get a virtual machine. You install and patch the operating system, install PostgreSQL, apply engine updates, configure backups and replication, and tune everything yourself.
- On **Amazon RDS** AWS runs the instance for you. AWS supplies and applies patches for the underlying OS and the database engine: required OS updates and, when auto minor version upgrade is on, minor engine versions are applied during the weekly **maintenance window** you choose, while major version upgrades are started by you.
## What stays with you either way
Your data, schemas and SQL, database users and grants, security groups, encryption choices and parameter settings are always your job. For example, a slow query caused by a missing index is your problem on both RDS and EC2.
W: RDS patched by AWS, EC2 patched by you: on RDS the OS and engine patching are part of the managed service, while on EC2 the customer owns the guest OS and any database software installed on it.
X: A=AWS patches everything, including SQL: no managed service writes or fixes your SQL, schemas or data. Application code and data are always the customer's responsibility, even on RDS.
B=AWS patches the EC2 OS; you patch the RDS engine: this is the split reversed. EC2 guest OS patching is the customer's job, and on RDS the engine is patched by AWS during the maintenance window.
C=You patch the hypervisor and hardware: customers never have access to the hypervisor or physical hosts for either service; that layer is always AWS's responsibility.
T: The more managed the service, the more patching moves to AWS: RDS covers OS and engine, EC2 leaves both to you, and your data and SQL are always yours.

@ Q000402 explain
G: ## CloudFormation StackSets across an organization
A **StackSet** is one CloudFormation template that is deployed as individual stacks into many accounts and Regions from a single administrator account. StackSets needs permission to create stacks in each target account, and there are two permission models.
- **Self-managed permissions**: you create an administration role in the admin account and an execution role (for example `AWSCloudFormationStackSetExecutionRole`) in every target account yourself.
- **Service-managed permissions**: you enable **trusted access** between CloudFormation StackSets and AWS Organizations from the management account. StackSets then creates the needed service-linked roles in member accounts for you.
## Why service-managed fits this case
With service-managed permissions you target organizational units (OUs) instead of listing account IDs, and you can turn on **automatic deployment** so that accounts later added to those OUs receive the baseline (IAM roles, logging resources) automatically. A delegated administrator account can also manage the StackSets instead of the management account.
W: Trusted access with service-managed permissions: enabling trusted access lets StackSets create and use the cross-account roles itself, so the team deploys to all 40 accounts by OU without creating or assuming a role in each one.
X: A=S3 bucket policy granting PutObject: a bucket policy only controls who can write objects to one bucket. It gives CloudFormation no ability to create stacks in member accounts.
C=Secret replicated to every account: Secrets Manager stores credentials; replicating a secret does not give StackSets permission to deploy resources, and StackSets does not need stored credentials to work.
D=AWS Config aggregator: an aggregator collects configuration and compliance data from accounts into one view. It is read-only reporting and cannot deploy stacks.
T: Organization-wide stack deployment without per-account roles means StackSets service-managed permissions, which require trusted access with Organizations first.

@ Q000403 explain
G: ## How SageMaker Unified Studio organizes collaboration
Amazon SageMaker Unified Studio (built on Amazon DataZone concepts) gives data engineers, analysts and ML practitioners one place to work with data, analytics and ML tools. Access is organized in layers:
- A **domain** is the top-level container. It holds the catalog of data assets, the user directory integration (IAM Identity Center or IAM), and the AWS accounts and Regions the domain can use.
- **Domain units** subdivide a domain, usually by business line or team (for example `Sales` and `Finance`). Authorization policies on a domain unit decide who can create projects or own assets inside it.
- **Projects** are where people actually collaborate. A project has members, its own compute and storage resources, and the data assets it publishes or subscribes to.
## Example
A company creates one domain, adds a `Marketing` domain unit, and inside it a `campaign-analytics` project. Analysts added as project members can query the data the project has subscribed to, while other teams cannot.
W: Domain, then domain units, then projects: this is the documented hierarchy, with policies at the domain and domain-unit levels and day-to-day membership and resources at the project level.
X: B=S3 bucket policies only, no domains: Unified Studio has a domain concept and manages access through project membership and catalog subscriptions; bucket policies alone cannot express who may publish, subscribe to or use assets.
C=Projects contain domains: this reverses the hierarchy. Projects live inside a domain (and its domain units), and users are added as project members rather than being held directly by a domain.
D=One global namespace for all accounts: each domain is created in a specific account and Region and is subdivided into domain units and projects; there is no single namespace shared by every AWS account.
T: SageMaker Unified Studio nests domain, domain units and projects; access is governed from the top and collaboration happens in projects.

@ Q000404 explain
G: ## What an Athena query needs permission for
Running an Athena query touches several services, so a least-privilege policy has to cover each of them narrowly:
- **Athena**: actions such as `athena:StartQueryExecution`, `athena:GetQueryExecution` and `athena:GetQueryResults`, ideally limited to one workgroup ARN.
- **Glue Data Catalog**: read actions like `glue:GetDatabase`, `glue:GetTable` and `glue:GetPartitions` on the catalog, the one database and its tables (for example `arn:aws:glue:us-east-1:111122223333:table/sales_db/*`).
- **Amazon S3**: `s3:GetObject` and `s3:ListBucket` on the data location, plus write access only to the query results location.
## What to leave out
Actions such as `glue:UpdateTable`, `glue:DeleteTable` and `glue:CreateTable` are simply not granted, so analysts can read tables but cannot change or remove them. If the tables are governed by Lake Formation, a `SELECT` grant there is also needed.
W: Custom read-only policy scoped to the database: it grants only the Athena, Glue read and S3 read actions the queries need, restricted to that database's resources, which is exactly least privilege.
X: A=AdministratorAccess: grants every action on every resource in the account, including deleting tables and changing IAM, which is the opposite of least privilege.
B=AmazonAthenaFullAccess: this managed policy allows broad Athena actions and Glue catalog actions across all databases, including create, update and delete operations, so it does not restrict analysts to one database or to read-only use.
C=Root account access: the root user has unrestricted access that cannot be limited by identity-based IAM policies and should not be used for daily work at all, let alone shared with analysts.
T: Least privilege for Athena means a custom policy listing only the Athena, Glue read and S3 read actions on the specific workgroup, database and bucket, not a broad managed policy.

@ Q000405 explain
G: ## Secrets Manager versus Parameter Store
Both services store values that applications read at runtime, but they are priced and built for different jobs.
- **AWS Secrets Manager** is built for credentials. It can **rotate** secrets automatically on a schedule using a rotation Lambda function, and AWS provides ready-made rotation functions for Amazon RDS, Aurora, Redshift and DocumentDB credentials. It charges per secret per month plus per API call.
- **Systems Manager Parameter Store** holds configuration values. **Standard** parameters (up to 4 KB) have no storage charge, and `SecureString` parameters can be encrypted with KMS. Parameter Store has no built-in rotation.
## Example
The app reads `prod/orders/db` from Secrets Manager, which rotates the database password every 30 days, and reads `/orders/batch-size` (value `500`) as a free standard `String` parameter. Changing the batch size is just a `PutParameter` call.
W: Password in Secrets Manager, setting in Parameter Store: the password gets managed rotation, and the non-secret setting sits in a standard parameter at no storage cost, which gives the lowest total cost.
X: A=Both as SecureString without rotation: Parameter Store has no built-in rotation, so the password requirement is not met unless you build and operate your own rotation process.
B=Both in Secrets Manager: this works functionally, but you pay the per-secret monthly charge for a plain, non-sensitive setting that could be stored for free.
D=Hardcoded in the application: hardcoding a password exposes it in source code and deployments and makes rotation require a redeploy; changing the batch size also needs a new release.
T: Put rotating credentials in Secrets Manager and plain configuration in Parameter Store standard parameters; paying Secrets Manager prices for non-secrets adds cost with no benefit.

@ Q000406 explain
G: ## Attribute-based access control (ABAC)
In **ABAC**, a policy grants access based on tags (attributes) instead of naming each resource. The policy uses condition keys that compare tags at request time, for example:
- `aws:ResourceTag/project` compares a tag on the resource being accessed.
- `aws:PrincipalTag/project` compares a tag on the calling role or user.
A statement such as "allow these actions when `aws:ResourceTag/project` equals `analytics`" covers every resource that has that tag, where the service supports tag-based authorization for that resource.
## ABAC in Amazon S3
S3 general purpose buckets support ABAC on **bucket tags**, but it is off by default: after ABAC is enabled on a bucket, `aws:ResourceTag/<key>` conditions in IAM and bucket policies are evaluated against that bucket's tags. Tags on individual objects are checked with the separate S3 key `s3:ExistingObjectTag/<key>`.
## Why this removes policy edits
With a list of ARNs, each new bucket requires someone to add its ARN to the policy. With ABAC, tagging a new bucket `project=analytics` (and enabling ABAC on it) is enough: the existing policy already matches it. Teams usually also control who can set or change the tag, so that tagging cannot be used to gain access.
W: ABAC with resource tags in conditions: the permission is written once against the `project=analytics` tag, so every new bucket carrying that tag is covered automatically without changing the policy.
X: B=S3 bucket ACLs: ACLs are set per bucket or object by hand, are disabled by default on new buckets (Object Ownership set to bucket owner enforced), and have no concept of tags, so nothing applies automatically.
C=RBAC with a fixed list of bucket ARNs: a fixed list only covers the buckets already named. Every new bucket requires a policy update, which is exactly what the company wants to avoid.
D=Security groups: security groups filter network traffic to resources in a VPC such as EC2 instances. S3 is accessed through its API, and security groups cannot grant or deny S3 permissions.
T: Permissions that follow a tag onto new resources are ABAC; lists of ARNs are role-based and must be edited for each new resource.

@ Q000407 explain
G: ## RBAC and ABAC at scale
- **Role-based access control (RBAC)**: permissions are attached to a role for a job function, and resources are named explicitly in its policies. If every team and resource combination needs its own role, the number of roles and policies grows roughly as teams multiplied by resources.
- **Attribute-based access control (ABAC)**: a smaller set of policies compares tags, for example allowing access when `aws:PrincipalTag/team` equals `aws:ResourceTag/team`. New teams and resources are covered by tagging them correctly.
## Example
With 20 teams and 50 data stores, a pure RBAC design may need hundreds of roles or constant policy edits as each new store appears. With ABAC, a new store tagged `team=finance` is immediately reachable by roles tagged `team=finance`, with no policy change.
ABAC still needs governance: consistent tag keys, control over who may change tags, and sometimes tag policies in AWS Organizations.
W: RBAC sprawls, ABAC scales with tags: the key operational tradeoff is that RBAC multiplies roles and policy updates as teams and resources grow, while ABAC keeps policies stable and relies on tagging discipline.
X: A=RBAC inherits permissions from tags: that describes ABAC. A pure RBAC policy names roles and resources explicitly and does nothing with tags unless you add tag conditions.
B=ABAC is impossible in IAM: IAM supports ABAC through condition keys such as `aws:PrincipalTag`, `aws:ResourceTag` and `aws:RequestTag`, and AWS documents it as a recommended pattern.
C=RBAC needs no policy management: every new resource or job function in an RBAC design means creating or editing roles and policies; that ongoing management is exactly its scaling cost.
T: RBAC grows by adding roles and policy edits for every new team or resource; ABAC grows by tagging, which is why it scales better in fast-growing organizations.

@ Q000408 explain
G: ## Two layers of Redshift permissions
- **IAM** controls the AWS API: creating clusters or workgroups, getting temporary credentials, calling the Data API.
- **Database privileges** control what a database user can do with schemas and tables. They are managed in SQL with `GRANT`, and Redshift supports **roles** (role-based access control) inside the database.
## Granting read access to two schemas
- `GRANT USAGE ON SCHEMA sales TO ROLE analyst_ro;` lets the role see objects in the schema.
- `GRANT SELECT ON ALL TABLES IN SCHEMA sales TO ROLE analyst_ro;` covers tables that exist today.
- `ALTER DEFAULT PRIVILEGES IN SCHEMA sales GRANT SELECT ON TABLES TO ROLE analyst_ro;` covers tables created later (by the user who runs it, or by the user named with `FOR USER`).
Repeat for the second schema, then `GRANT ROLE analyst_ro TO alice;`. The analyst can read those schemas and nothing else.
W: Role with USAGE, SELECT and default privileges: USAGE and SELECT give read access to current tables, and default privileges extend SELECT to future tables, with no write or admin rights.
X: A=IAM policy with `redshift:*`: IAM actions control the Redshift API such as modifying or deleting clusters, not SELECT on tables; this grants far too much control-plane access, and IAM permissions by themselves are not SQL table privileges.
B=Superuser account: a superuser bypasses all permission checks and can read, change or drop anything in the database, which violates least privilege.
D=Admin user's credentials: sharing the admin login gives full privileges, removes individual accountability in audit logs, and still ignores the "nothing else" requirement.
T: Table access in Redshift is granted in SQL: USAGE and SELECT for today's tables plus ALTER DEFAULT PRIVILEGES for tomorrow's, never IAM wildcards or superuser access.

@ Q000409 explain
G: ## How Lake Formation authorizes a query
When an S3 location is registered with AWS Lake Formation and its tables use Lake Formation permissions, access is checked in two places:
- **IAM** must allow the calling principal to use the services, for example Athena actions, `glue:GetTable` and `lakeformation:GetDataAccess`.
- **Lake Formation** must grant the principal permission on the catalog resource, such as `SELECT` on the table or specific columns.
## Credential vending
Athena does not read the data with the caller's own `s3:GetObject` permission. After Lake Formation confirms the grant, it vends temporary credentials scoped to the table's S3 location, and Athena uses those. Without a Lake Formation grant, the query is denied even if the IAM policy allows S3 and Glue.
Example: granting `SELECT` on `sales_db.orders` to the analyst role in the Lake Formation console (or with `aws lakeformation grant-permissions`) is what makes the query succeed.
W: Missing Lake Formation grant on the table: for a governed table, IAM permissions alone are not enough; the role also needs a Lake Formation `SELECT` grant, and its absence produces exactly this access denied error.
X: B=The S3 bucket was deleted: a missing bucket would cause a "bucket does not exist" or no-data style failure, not a permissions denial, and nothing in the scenario suggests the data location was removed.
C=Policy is invalid JSON: IAM rejects malformed JSON when the policy is created or attached, so an invalid policy could not be attached to the role in the first place.
D=Athena cannot query governed tables: Athena is one of the main engines integrated with Lake Formation and enforces its table, column and row-level permissions.
T: For Lake Formation-governed tables, IAM opens the door to the services, but the Lake Formation grant decides whether the data can be read.

@ Q000410 explain
G: ## Key policies are the starting point in KMS
Every AWS KMS key has exactly one **key policy**. Unlike most AWS resources, IAM policies alone cannot grant access to a KMS key: the key policy must allow the access, either directly to a principal or by delegating to IAM.
- The default key policy contains a statement giving the account (`arn:aws:iam::111122223333:root`) full access. That statement **enables IAM policies** in the account to grant use of the key.
- If the key policy does not contain that delegation and does not name the user, no IAM policy can give the user access.
## Applied to SSE-KMS on S3
To read an SSE-KMS object, the user needs `s3:GetObject` and `kms:Decrypt` on the key; uploading needs `kms:GenerateDataKey`. S3 calls KMS on the user's behalf, so the user's own KMS permissions are evaluated.
In the usual setup, the key policy delegates to IAM and the user's IAM policy then allows `kms:Decrypt`: both documents play a part.
W: Both key policy and IAM policy must allow it: the key policy has to permit the use (directly or by enabling IAM policies), and the user's IAM policy must allow the KMS actions when access is delegated to IAM.
X: A=Only the key policy matters: once the key policy enables IAM policies, IAM policies do govern who can use the key; in that common setup a user without IAM permission is denied.
C=IAM policy alone is enough: KMS always evaluates the key policy first. If the key policy does not allow the access or delegate to IAM, an IAM allow has no effect, including when S3 calls KMS for you.
D=Bucket policy alone controls the key: a bucket policy controls S3 actions on the bucket; it cannot grant `kms:Decrypt` on a KMS key, which only the key policy (and IAM, if delegated) or grants can do.
T: KMS access starts with the key policy; IAM policies count only when the key policy delegates to them, so for SSE-KMS both must allow the user.

@ Q000411 explain
G: ## Enforcing HTTPS on an S3 bucket
Amazon S3 accepts both HTTP and HTTPS requests unless a policy says otherwise. The global condition key `aws:SecureTransport` is `true` when the request came over TLS and `false` when it did not.
A bucket policy with an explicit deny blocks every plain-HTTP request, no matter who sends it:
- `"Effect": "Deny"`, `"Principal": "*"`, `"Action": "s3:*"`
- `"Resource"`: the bucket ARN and `arn:aws:s3:::my-bucket/*`
- `"Condition": {"Bool": {"aws:SecureTransport": "false"}}`
## Why a deny in the bucket policy
Because the policy is attached to the bucket, it applies to every caller: users, applications, other accounts and requests through VPC endpoints. An explicit deny also overrides any allow the caller has in an IAM policy.
W: Deny when `aws:SecureTransport` is false: an explicit deny in the bucket policy rejects any request not made over TLS from any principal or network path, which guarantees encryption in transit.
X: A=VPC endpoint policy only: an endpoint policy applies only to traffic that passes through that endpoint. Requests over the internet or other endpoints bypass it, and it does not by itself require TLS.
C=Default SSE-S3 encryption: this encrypts objects at rest after S3 receives them. It does not stop a client from sending data over unencrypted HTTP.
D=S3 Versioning: versioning keeps multiple versions of objects for recovery from overwrites and deletes; it has nothing to do with how requests are transported.
T: Encryption in transit is enforced with a bucket policy deny on `aws:SecureTransport` = false; SSE settings only cover data at rest.

@ Q000412 explain
G: ## Dynamic data masking in Amazon Redshift
**Dynamic data masking (DDM)** changes what a column returns at query time based on who runs the query. The stored data is not changed.
- `CREATE MASKING POLICY mask_ssn WITH (ssn VARCHAR(11)) USING ('XXX-XX-' || SUBSTRING(ssn, 8, 4));` defines how the value is shown.
- `ATTACH MASKING POLICY mask_ssn ON customers(ssn) TO ROLE data_scientist;` applies it to one role.
- A different policy (or none) can be attached for the `compliance` role, and a `PRIORITY` value decides which policy wins when a user holds several roles.
## Example
`SELECT name, ssn FROM customers;` returns `XXX-XX-6789` for a data scientist and `123-45-6789` for a compliance officer, from the same table and the same query. There is only one copy of the data to load and secure.
W: Dynamic data masking policies by role: masking policies attached to roles return masked SSNs to data scientists and full values to the compliance role from the single table at query time.
X: A=KMS encryption with a separate key: encryption protects data at rest; any user allowed to query the table sees decrypted plaintext, so it cannot show different values to different roles.
C=Masked copy per team: a second table duplicates data, must be kept in sync with every load, and adds storage and governance overhead, while the requirement is to use the same table.
D=Row-level security only: RLS filters which rows a user can see. It cannot transform a column's value, so users would see either full SSNs or no row at all.
T: Different views of a column for different roles from one table is dynamic data masking; RLS filters rows and encryption protects data at rest.

@ Q000413 explain
G: ## Cross-account access to SSE-KMS objects
Reading an object encrypted with SSE-KMS needs two permissions: `s3:GetObject` on the object and `kms:Decrypt` on the KMS key. When the reader is in another account, each owner must allow it on its side:
- **Account A's key policy** must allow Account B (or a specific role in B) to use the key, for example `kms:Decrypt`.
- **Account A's bucket policy** must allow B's role to read the objects.
- **Account B's IAM policy** on the role must allow `s3:GetObject` on A's bucket and `kms:Decrypt` on A's key ARN.
## A common pitfall
Objects encrypted with the AWS managed key `aws/s3` cannot be shared this way, because you cannot edit the policy of an AWS managed key. That is one reason to use a customer managed key, as in this scenario.
W: A's key policy grants B's role `kms:Decrypt`: without this cross-account grant in the key policy, B's role is denied no matter what its own IAM policy says; with it (plus bucket and IAM permissions), B can decrypt the objects.
X: A=Works across accounts by default: KMS keys are private to their account. Only principals allowed by the key policy can use a key, and by default that is only the owning account.
C=B creates its own copy of the key: the objects were encrypted under A's key, so only A's key can decrypt them. A new key in B has different key material and cannot decrypt that ciphertext.
D=Only the bucket policy: the bucket policy allows `s3:GetObject`, but S3 still has to call KMS to decrypt the data key, and that call is denied unless the key policy grants B access.
T: Cross-account SSE-KMS reads need A's key policy (plus bucket policy and B's IAM policy) to allow B; S3 permissions alone are not enough.

@ Q000414 explain
G: ## Where the encryption happens
- **Server-side encryption** (SSE-S3, SSE-KMS): the client sends plaintext over TLS, and the AWS service encrypts it before writing to disk. AWS handles the plaintext briefly while encrypting.
- **Client-side encryption**: the application encrypts the data before it leaves, and sends only ciphertext. The service stores exactly what it receives and never sees the plaintext.
## Tools for client-side encryption
- The **Amazon S3 Encryption Client** encrypts objects before upload and decrypts after download.
- The **AWS Encryption SDK** encrypts any data using envelope encryption, often with a data key from AWS KMS (`GenerateDataKey`) or a key you manage.
- The **AWS Database Encryption SDK** encrypts attributes before writing items to DynamoDB.
Client-side and server-side can be combined, but only client-side meets "AWS stores only ciphertext it never saw in plaintext".
W: Client-side encryption: data is encrypted inside the application, so every AWS service in the path receives and stores only ciphertext.
X: A=SSE-KMS on the bucket: S3 receives the plaintext and encrypts it with a KMS data key after arrival, so the service does see unencrypted data.
B=TLS for transit only: TLS protects data on the network, but it is decrypted when it reaches the service, which then stores it unless another layer encrypts it.
C=SSE-S3 default encryption: like SSE-KMS, the encryption is performed by S3 after it receives plaintext, only with S3-managed keys instead of KMS keys.
T: If AWS must never see plaintext, encrypt on the client before sending; any SSE option means the service encrypts data it received in the clear.

@ Q000415 explain
G: ## Aliases point to keys; ciphertext belongs to a key
A KMS **alias** such as `alias/app-data` is a friendly name that points to one KMS key at a time. You can re-point it with `UpdateAlias`, which is one way to do manual key rotation.
Every ciphertext is bound to the key that created it. Data encrypted months ago can only be decrypted with the **old** key's material; re-pointing the alias does not change or re-encrypt existing data.
## What goes wrong
- If the application passes the alias as the `KeyId` in `Decrypt`, KMS now resolves it to the new key, and decrypting old ciphertext fails because it was not produced by that key.
- If the old key was disabled or scheduled for deletion, or the app lost permission on it, old ciphertext also cannot be decrypted.
The fix is to keep the old key enabled and let `Decrypt` use the key ID embedded in symmetric ciphertext (or pass the old key's ARN), and to re-encrypt old data with `ReEncrypt` if it should move to the new key.
W: Old data still needs the old key: manual rotation by alias only changes the key used for new encryption; older ciphertext can only be decrypted with the key that encrypted it.
X: A=Secrets Manager rotation failure: the scenario involves a new KMS key and a re-pointed alias, with no secret being rotated; the failure follows directly from the alias change.
B=KMS re-encrypts old objects on alias change: KMS never re-encrypts existing data when an alias moves or a key rotates. Re-encryption only happens if you call `ReEncrypt` or rewrite the data.
D=KMS deleted the old key material: re-pointing an alias does not delete anything, and a KMS key cannot be deleted immediately; deletion must be scheduled with a 7 to 30 day waiting period.
T: Moving an alias to a new key affects only new encryptions; old ciphertext still needs the old key, unlike automatic rotation, which keeps old key material inside the same key.

G: ## Discovering sensitive data versus hiding it
These are two different jobs handled by two different services.
- **Amazon Macie** scans objects in S3 using managed data identifiers (names, national IDs, credit card numbers and many more) and custom identifiers. **Automated sensitive data discovery** samples buckets continuously, and **discovery jobs** scan chosen buckets. Findings say which bucket and object hold which type of sensitive data.
- **Amazon Redshift dynamic data masking** hides column values at query time based on the user's role, for example showing `***@***.com` instead of an email address to analysts while a privileged role sees the real value.
## Putting them together
Macie tells you where PII is sitting unnoticed in the data lake; masking policies on the Redshift columns make sure analysts querying the warehouse only see protected values.
W: Macie to find PII, Redshift dynamic masking to hide it: Macie inspects S3 object contents for sensitive data, and DDM applies role-based masking to the Redshift columns at query time.
X: A=CloudTrail and IAM: CloudTrail records API activity and never inspects object contents, and IAM decides whether a query is allowed but cannot transform the values it returns.
B=GuardDuty and Macie: GuardDuty detects threats such as unusual API calls or compromised credentials, not PII in data, and Macie discovers sensitive data but does not mask Redshift query results.
D=Config and KMS: AWS Config tracks resource configuration and compliance rather than data contents, and KMS encrypts data at rest; authorized queries still return plaintext.
T: Discover PII in S3 with Macie and mask it in query results with Redshift dynamic data masking; activity, threat and configuration services do not look inside data.

@ Q000417 explain
G: ## KMS keys are Regional by default
A normal KMS key exists in one Region, and its key material never leaves that Region. Ciphertext produced in `us-east-1` can only be decrypted by calling KMS in `us-east-1`.
## Multi-Region keys
A **multi-Region key** is a set of related keys in different Regions that share the **same key ID and key material**. Their IDs start with `mrk-`, for example `mrk-1234abcd...`.
- You create a **primary key** in one Region and **replicate** it to other Regions as replica keys.
- Data encrypted with the primary in Region A can be decrypted by the replica in Region B, without a cross-Region call.
- Each key is still a separate resource with its own key policy, grants and aliases, and rotation of the primary is shared with its replicas.
Example: a pipeline writes encrypted data in `eu-west-1`; during an outage the standby in `eu-central-1` decrypts and keeps encrypting with the replica key.
W: Multi-Region keys in each Region: primary and replica keys share one key ID and key material, so both Regions can decrypt the same data and either can take over encryption during a Regional disruption.
X: B=AWS managed keys (`aws/s3`): these are single-Region keys owned by the service; each Region has its own `aws/s3` key with different material, and you cannot replicate them.
C=Single-Region key shared through IAM: IAM permissions can let principals call the key, but the key still lives only in its Region, so decryption depends on that Region being available.
D=Automatic annual rotation: rotation creates new key material inside the same key on a schedule; it does nothing to make the key available in a second Region.
T: Decrypting the same data in two Regions with one key identity requires KMS multi-Region keys; permissions and rotation do not move key material across Regions.

@ Q000418 explain
G: ## CloudTrail Lake
**AWS CloudTrail Lake** is a managed data lake for CloudTrail events. Instead of delivering log files to S3 and then defining Athena tables, you create an **event data store** and query it directly with SQL.
- An event data store can collect events from all accounts in an AWS Organization and from multiple Regions.
- Retention is configurable for long periods, measured in years, so historical investigations do not require separate archiving.
- Queries use SQL, for example `SELECT eventName, userIdentity.arn FROM <event-data-store-id> WHERE eventTime > '2026-01-01 00:00:00'`.
## Availability note
Since May 31, 2026, CloudTrail Lake is closed to new customers; existing customers can keep using it, and AWS points new customers to Amazon CloudWatch for similar capabilities. The feature set described here is what the question tests.
## Compared with the do-it-yourself path
A trail to S3 plus Athena works well too, but you manage the bucket, the table definition and partitions yourself. CloudTrail Lake removes those steps, which is what this requirement asks for.
W: CloudTrail Lake: event data stores aggregate CloudTrail events across accounts and Regions, retain them for years, and are queried with SQL without loading data into S3 or creating Athena tables.

G: ## Management events versus data events
CloudTrail separates API activity into categories:
- **Management events** are control-plane operations on resources, such as `CreateBucket`, `PutBucketPolicy` or `RunInstances`. Trails log them by default.
- **Data events** are operations on or inside a resource, such as S3 `GetObject`, `PutObject` and `DeleteObject`, or Lambda `Invoke`. They are high volume, so they are **not logged by default** and are billed separately.
## Turning on S3 data events
You add data event selectors to the trail, typically **advanced event selectors** with `resources.type` = `AWS::S3::Object` and a `resources.ARN` prefix like `arn:aws:s3:::sensitive-bucket/` to limit logging (and cost) to that bucket. You can also choose read-only, write-only or both.
Note that CloudTrail **Event history** in the console shows management events only, so data events are seen in the trail's log files or a CloudTrail Lake event data store.
W: The trail logs management events, not data events: object-level `PutObject` and `DeleteObject` calls are data events, which must be enabled explicitly on the trail for that bucket.
X: A=CloudTrail cannot log S3 events: CloudTrail logs both S3 bucket-level management events and object-level data events once data events are configured.
C=Server-side encryption disabled: bucket encryption settings affect how objects are stored, not which API calls CloudTrail records.
D=Missing trust policy on the role: a trust policy controls who can assume a role; a missing one would make calls fail, but it would not stop CloudTrail from recording calls that do happen.
T: Bucket configuration calls are management events and are logged by default; object reads and writes are data events that must be enabled on the trail.

G: ## Reacting to API calls in near real time
CloudTrail sends management events to **Amazon EventBridge** as events with the detail type `AWS API Call via CloudTrail` (a trail with logging enabled is needed for these events). An EventBridge rule can match specific calls and send them to a target within seconds.
## Example rule
- `source`: `aws.iam`
- `detail-type`: `AWS API Call via CloudTrail`
- `detail.eventName`: `AttachUserPolicy`
- `detail.requestParameters.policyArn`: `arn:aws:iam::aws:policy/AdministratorAccess`
The target is an **SNS topic** that emails or pages the compliance team. Because IAM is a global service, its events are delivered in `us-east-1`, so the rule is created there. Other event names such as `PutUserPolicy` or `AttachGroupPolicy` can be added to the same pattern.
W: EventBridge rule on the API call, notifying through SNS: the rule matches the CloudTrail event for the admin policy attachment as it happens and pushes a notification within seconds.
X: A=Daily manual review: a once-a-day check can leave an administrator grant unnoticed for up to 24 hours and depends on a person, which is neither near real time nor reliable.
C=Config conformance pack with no further action: a conformance pack evaluates resources against rules and records compliance, but by itself it sends no notification, and it reports configuration state rather than the API call.
D=Default encryption on the log bucket: encrypting the CloudTrail bucket protects stored logs at rest; it does not analyze events or alert anyone.
T: Near-real-time alerts on specific API calls are built with an EventBridge rule on the CloudTrail event and an SNS target, not with periodic reviews or compliance checks.

G: ## Redshift data sharing
**Data sharing** lets a producer Redshift cluster or Serverless workgroup give consumers live access to its data **without copying it**. Consumers query the producer's managed storage using their own compute, so they always see the latest committed data.
## Cross-account steps
- The producer creates a datashare and adds objects: `CREATE DATASHARE sales_share; ALTER DATASHARE sales_share ADD SCHEMA finance;` plus the tables in each schema.
- The producer grants the share to the consumer account: `GRANT USAGE ON DATASHARE sales_share TO ACCOUNT '444455556666';` and an administrator authorizes it.
- In the consumer account, an administrator associates the share, and the consumer creates a database from it: `CREATE DATABASE sales_db FROM DATASHARE sales_share OF ACCOUNT '111122223333' NAMESPACE '<producer-namespace-id>';`
Both sides must use encrypted RA3 clusters or Serverless.
W: Cross-account Redshift data sharing: consumers read the three schemas live from the producer's storage, with no copies, ETL or refresh schedule to manage.
X: A=DMS replication: AWS DMS copies the tables into another database and keeps a replication task running, which is the data copying and extra pipeline the requirement rules out.
B=UNLOAD and COPY: exporting to S3 and loading into the consumer is a batch ETL process; the consumer sees data only as of the last run and stores a second copy.
D=Nightly snapshot restore: restoring a snapshot creates a full separate copy that is up to a day old, and every restore costs time and storage.
T: Live, copy-free, cross-account read access between Redshift warehouses is data sharing; replication, UNLOAD/COPY and snapshots all create stale copies.

G: ## Discover, tag, then control
This requirement has two steps that different services own:
- **Amazon Macie** inspects the contents of S3 objects and produces findings that name the bucket, object and type of sensitive data found; for structured files, findings can point to where in the file (such as the column) the data occurs.
- **AWS Lake Formation** controls access to tables in the Glue Data Catalog at database, table, **column** and row level for engines like Athena, Redshift Spectrum and EMR.
## Connecting them
A common pattern: Macie findings flow to EventBridge, and an automation (for example a Lambda function) applies an **LF-Tag** such as `sensitivity=pii` to the matching catalog columns. Lake Formation **tag-based access control** then grants `SELECT` on `sensitivity=pii` columns only to authorized roles, while other roles get the remaining columns.
New PII columns become protected as soon as they are tagged, without rewriting grants.
W: Macie findings driving Lake Formation access: Macie discovers the PII columns, and Lake Formation column-level or tag-based permissions ensure only authorized roles can query them through the catalog.
X: A=AWS Config alone: Config evaluates resource configurations such as bucket settings; it does not scan data contents for PII and cannot grant or restrict column-level access to catalog tables.
C=S3 bucket policies only: bucket policies work at bucket and object prefix level, cannot find PII, and cannot restrict individual columns inside a table that query engines read through the catalog.
D=CloudTrail Insights: Insights flags unusual API call volumes or error rates; it analyzes management activity, not the contents of data files, so it cannot find PII columns.
T: Macie finds where PII is and Lake Formation controls who can query those columns; configuration, bucket and API-activity tools can do neither.
