@ Q003688 explain
G: ## What Amazon Data Firehose does
Amazon Data Firehose (formerly Kinesis Data Firehose) is a fully managed delivery service. Producers send records to a Firehose stream, and Firehose buffers them and writes them to a destination such as Amazon S3, Amazon Redshift, Amazon OpenSearch Service, Splunk or an HTTP endpoint.
- **Buffering**: records are grouped by size (for example 64 MB) or time (for example 60 seconds), whichever comes first, so S3 receives fewer, larger objects in near real time.
- **Compression**: GZIP, Snappy, ZIP or Hadoop-compatible Snappy can be applied on delivery; when records are converted to Parquet or ORC, the columnar format's own compression (Snappy by default) is used instead.
- **Record format conversion**: JSON input can be converted to Apache Parquet or ORC using a table schema from the AWS Glue Data Catalog.
- **Dynamic partitioning**: object prefixes such as `year=2026/month=09/` can be built from record fields.
## Example
IoT devices publish JSON readings through AWS IoT Core, whose rule action sends them to a Firehose stream. Firehose converts them to Parquet and writes them to `s3://iot-lake/readings/` every minute, with no servers or code to maintain.
W: Amazon Data Firehose: it buffers, compresses and converts records to Parquet as built-in configuration settings, and delivers to S3 within seconds to minutes, which matches every requirement without custom code.
X: A=Daily Glue batch jobs: running once per day gives up to 24 hours of delay, which is not near real time, and a Glue job still requires writing or generating ETL scripts.
C=EMR with Spark Streaming: it can produce Parquet, but you must write the streaming application and run and scale a cluster, which contradicts the no-custom-code requirement.
D=Kinesis Data Streams with custom consumers: Data Streams stores the records durably, but the batching, compression and Parquet conversion would all live in consumer code you write and operate.
T: For managed near-real-time delivery to S3 with batching, compression and Parquet conversion and no code, use Firehose; Data Streams and EMR need custom consumers or applications.

G: ## Full load plus change data capture
AWS Database Migration Service (DMS) moves data from a source database to a target such as Amazon S3, Redshift or another database. A replication instance (or DMS Serverless) reads the source and writes the target.
- **Full load** copies the existing rows of each selected table once.
- **Change data capture (CDC)** then reads the database transaction log (for Oracle, through LogMiner or Binary Reader) and applies every insert, update and delete continuously.
- A task type of `full-load-and-cdc` does both in order, so the target starts complete and stays current.
## Example
An on-premises Oracle database reaches AWS over AWS Direct Connect or VPN. A DMS task writes the initial tables to `s3://lake/raw/oracle/` as Parquet, then writes change files with an operation column (`I`, `U`, `D`) that downstream jobs merge into analytics tables.
W: DMS with full load and CDC: it reads Oracle's redo logs to capture ongoing changes and writes them to S3 continuously, which is exactly "continuously replicate changes" rather than periodic copies.
X: A=Weekly Snowball Edge: shipping a device moves a bulk copy offline with days of delay; it cannot deliver a continuous stream of row changes.
C=Amazon AppFlow: AppFlow connects SaaS applications such as Salesforce or ServiceNow; it has no connector that reads an on-premises Oracle transaction log.
D=DataSync file transfers: DataSync copies files and objects between storage systems; copying the database host's files would not give consistent, row-level changes that analytics can use.
T: Continuous replication of database changes means CDC from the transaction log, which is what DMS provides; file and device transfer tools only move snapshots.

G: ## What Amazon AppFlow is for
Amazon AppFlow is a managed integration service that moves data between SaaS applications and AWS services without code. You create a **flow** in the console or API by choosing:
- a **source connector**, such as Salesforce, ServiceNow, Zendesk, Slack, SAP OData or Google Analytics;

- a **trigger**: on demand, on a schedule (for example every hour), or on an event for sources that support it, such as Salesforce change events;

AppFlow handles authentication (OAuth with the SaaS provider), pagination, API limits, and incremental transfers that pull only records changed since the last run.

A scheduled flow copies new Salesforce `Opportunity` records every hour to `s3://crm-lake/salesforce/`, and a second flow does the same for ServiceNow incidents.

C=Kinesis Video Streams: it ingests video and other time-encoded media from devices such as cameras; it has nothing to do with SaaS business records.
D=DataSync agents: DataSync moves files and objects between storage systems such as NFS, SMB, HDFS and S3; it cannot read data through SaaS application APIs.
T: SaaS applications to S3 on a schedule without code is AppFlow; Transfer Family and DataSync move files, not SaaS API data.

G: ## AWS Transfer Family
AWS Transfer Family is a managed file transfer service. It gives you a server endpoint that speaks **SFTP**, **FTPS**, **FTP** or **AS2**, and it stores the files directly in **Amazon S3** or **Amazon EFS**.
- You do not run any file transfer servers; AWS scales and patches the endpoint.

A partner runs `sftp acme@s-1234abcd.server.transfer.us-east-1.amazonaws.com` and uploads `orders.csv`. The file appears at `s3://partner-inbound/acme/orders.csv`, where an S3 event can start processing.

B=Amazon MQ: it is a managed message broker for ActiveMQ and RabbitMQ that carries messages between applications, not an SFTP file upload server.
C=AWS DMS: DMS replicates databases between engines and into S3; it does not accept files uploaded by partners over SFTP.
T: SFTP, FTPS or AS2 uploads that must land in S3 or EFS call for Transfer Family; AppFlow, MQ and DMS serve SaaS, messaging and database needs.

G: ## Managed Apache Kafka on AWS
Apache Kafka is a distributed log: producers write records to **topics**, topics are split into **partitions**, and consumer groups read them at their own pace. Running Kafka yourself means managing brokers, storage, patching and, in older versions, ZooKeeper.

- AWS handles broker replacement, patching and multi-AZ replication; security uses IAM, TLS or SASL/SCRAM.
## Example
A team changes only the `bootstrap.servers` setting of its Java producer to the MSK broker endpoint, such as `b-1.mycluster.xxxx.kafka.us-east-1.amazonaws.com:9098`, and keeps the rest of its code unchanged.

X: A=Amazon SNS: SNS is a push-based publish/subscribe notification service with its own API; it does not speak the Kafka protocol or offer replayable partitioned topics.
C=Amazon SQS: SQS is a message queue where each message is deleted after processing; it has a different API and cannot be used by Kafka clients.
D=AWS Batch: Batch schedules containerized batch compute jobs; it is not a streaming platform or message broker.
T: If the clients are already Kafka, choose MSK to keep the protocol; SNS and SQS would require rewriting producers and consumers.

G: ## Redshift streaming ingestion
Amazon Redshift can read directly from **Amazon Kinesis Data Streams** and **Amazon MSK** without staging data in S3 first.
- You create an external schema that points at the stream source, for example `CREATE EXTERNAL SCHEMA kds FROM KINESIS IAM_ROLE '...'`.
- You create a **materialized view** over a stream or topic. Each refresh pulls new records into Redshift.
- With `AUTO REFRESH YES`, Redshift refreshes the view continuously, giving latency of seconds.
- Record payloads arrive as `VARBYTE`; you convert them with `FROM_VARBYTE` and parse them with `JSON_PARSE` into `SUPER` to query with SQL.
## Example
Clickstream events flow into a Kinesis data stream. A materialized view `clicks_mv` over the stream refreshes automatically, and a dashboard query `SELECT page, COUNT(*) FROM clicks_mv WHERE event_time > DATEADD(minute, -5, GETDATE()) GROUP BY page` shows activity from the last few minutes.
W: Redshift streaming ingestion: materialized views read straight from Kinesis Data Streams or MSK and refresh continuously, giving near-real-time data in Redshift without an S3 staging step.
X: A=Daily COPY from CSV: COPY is efficient for bulk loads, but a daily export gives up to a day of lag, far from near-real-time dashboards.
C=Hourly manual INSERTs: row-by-row inserts are slow in a columnar warehouse, depend on people running them, and still leave up to an hour of lag.
D=Spreadsheets uploaded by hand: this is manual, error-prone and slow, and gives no automated or low-latency path into Redshift.
T: For low-latency loading of streams into Redshift, use streaming ingestion materialized views; COPY and manual loads are batch paths.

@ Q003694 explain
G: ## Why consumers fall behind in Kinesis Data Streams
A Kinesis data stream is made of **shards**. In provisioned mode, each shard accepts up to 1 MB/s or 1,000 records/s of writes and serves 2 MB/s of reads **shared by all standard consumers** of that shard, with a limit of 5 `GetRecords` calls per second per shard.
- When several consumers poll the same shard, they compete for that 2 MB/s and fall behind. `GetRecords.IteratorAgeMilliseconds` rises.
- If the iterator age approaches the retention period (24 hours by default, extendable up to 365 days), unread records expire and are lost.
## Ways to add read capacity
- **Enhanced fan-out**: each registered consumer gets its own dedicated 2 MB/s per shard, delivered by push over HTTP/2 (`SubscribeToShard`).
- **More shards**: split shards (`UpdateShardCount`) or switch to **on-demand** mode, which scales shards automatically based on traffic. More shards also allow more parallel consumer workers.
W: D=Enhanced fan-out: heavy consumers stop sharing the 2 MB/s per-shard read limit and receive a dedicated pipe with lower latency, so they can catch up.
E=More shards or on-demand mode: more shards raise total read throughput and allow more parallel consumer workers, which reduces iterator age.
X: A=Retention of one hour: shortening retention makes lagging records expire sooner, so the backlog is lost rather than processed. It worsens the problem.
B=Removing partition keys: every `PutRecord` requires a partition key, which decides the target shard; you cannot remove it, and doing so would not add read capacity.
C=Zero consumers: with no consumers nothing is read at all, so every record eventually expires unprocessed.
T: Lagging consumers need more read throughput, from enhanced fan-out or more shards, not shorter retention, which only deletes the backlog.

@ Q003695 explain
G: ## How Glue job bookmarks work
An AWS Glue ETL job reading an S3 prefix reads every object by default. A **job bookmark** is state that Glue keeps between runs of the same job so it can skip data already processed.
- For S3 sources, Glue records which objects it has processed, using their paths and modification times, and later runs read only new objects.
- For JDBC sources, it tracks the values of bookmark key columns, such as an increasing `id`.
- Enable it with the job parameter `--job-bookmark-option job-bookmark-enable`, give each source a `transformation_ctx`, and call `job.commit()` at the end so the state is saved.
- You can pause or reset the bookmark to reprocess data on purpose.
## Example
On Monday the job processes 500 files under `s3://raw/sales/`. On Tuesday 40 new files arrive; with bookmarks enabled the job reads only those 40 instead of all 540.
W: Glue job bookmarks: they persist which S3 objects have been processed, so each daily run reads only the newly arrived files instead of the whole prefix.
X: B=Glue Schema Registry: it stores and enforces schemas for streaming data such as Kafka or Kinesis records; it does not track which files a job has processed.
C=Glue crawlers only: crawlers infer schemas and add partitions to the Data Catalog, but the ETL job would still read every file in the prefix.
D=Data Catalog versions: table versions keep a history of schema changes; they do not tell a job which data it has already read.
T: To make a Glue job incremental over S3, enable job bookmarks; crawlers and the Schema Registry manage metadata, not processing state.

@ Q003696 explain
G: ## The small-files problem
Distributed engines such as Spark pay a fixed cost for every file they read: listing it in S3, opening it, reading footers or headers, and scheduling a task.
- With millions of tiny files (for example 10 KB each), that overhead dominates, S3 request counts explode, and the job spends more time on metadata than on data.
- Columnar formats also lose their benefit, because each tiny Parquet file has its own footer and very small row groups.
## Compaction
**Compaction** rewrites many small files into fewer large ones, commonly **128 MB to 1 GB** each, ideally in a splittable columnar format such as Parquet.
- Spark reads each large file with a few efficient range requests, and parallelism comes from splitting row groups.
- Compaction can be a scheduled Spark or Glue job (for example `df.coalesce(n).write.parquet(...)`), or be done automatically for table formats such as Apache Iceberg.
## Example
10 million files of 10 KB (about 100 GB) become about 400 Parquet files of 250 MB, turning millions of S3 GET requests into a few thousand.
W: Compacting into large Parquet files: it removes the per-file listing and open overhead and gives Spark efficient columnar reads, which targets the actual cause of the slowness.
X: A=Uncompressed CSV: CSV is row-based and larger to read, and changing format does not reduce the number of files, so the per-file overhead remains.
B=Splitting into even more files: more, smaller files multiply the per-file overhead that is already the bottleneck.
C=More master nodes: EMR primary nodes coordinate the cluster (multiple primary nodes are for high availability); they do not run Spark tasks, so adding them does not speed up reading.
T: Too many tiny files is fixed by compacting them into large columnar files, not by adding coordination nodes or splitting files further.

G: ## Serverless options for Apache Spark on AWS
"Serverless Spark" means you submit Spark code and the service provides and scales the compute, with no cluster to create, size, patch or shut down.
- **AWS Glue Spark jobs**: you write a PySpark or Scala script (or build it in Glue Studio), choose a worker type such as `G.1X` and a maximum number of workers, and Glue runs it. **Auto scaling** adds and removes workers during the run, and you pay per DPU-hour used.

Both integrate with the AWS Glue Data Catalog and S3, so the same tables can be read and written.

A nightly PySpark job that joins orders and customers can run as a Glue job with auto scaling up to 20 workers, or as an EMR Serverless job run with a maximum capacity limit on the application.
W: B=AWS Glue Spark jobs: Glue runs Spark on managed workers with auto scaling and per-use billing, so the team never manages a cluster.
E=Amazon EMR Serverless: it runs Spark job runs on automatically provisioned and released capacity, without creating or sizing an EMR cluster.
X: A=ElastiCache clusters: ElastiCache is an in-memory cache for Redis OSS, Valkey or Memcached; it stores data in memory for fast lookups and does not run Spark ETL.
C=RDS for PostgreSQL: it is a managed relational database, not a distributed Spark engine for large-scale ETL.
D=Spark on one EC2 instance: you would install, patch and size the server yourself, and a single machine cannot scale out automatically.
T: For Spark without clusters, choose Glue Spark jobs or EMR Serverless; databases, caches and self-managed EC2 do not provide serverless Spark.

G: ## From CSV to an Athena-ready table
Athena queries data in S3 using table definitions in the **AWS Glue Data Catalog**. Queries are faster and cheaper when data is:
- **Columnar** (Parquet), so only the needed columns are read;
- **Partitioned**, for example `s3://lake/sales/dt=2026-09-29/`, so a filter such as `WHERE dt = '2026-09-29'` skips the other folders.
## Doing it with a Glue ETL job
A Glue Spark job can read CSV, write Parquet with `partitionKeys=["dt"]`, and, with `enableUpdateCatalog=True` on the sink (the `getSink` API in a script, or the equivalent option in Glue Studio), create or update the table and its partitions in the Data Catalog in the same run.
- The job runs on serverless Glue workers, so there are no servers to provision.
- Job bookmarks can make later runs process only new CSV files.
## Example
Each day's `sales.csv` is converted into `sales/dt=YYYY-MM-DD/part-0000.snappy.parquet`, and the table `lake.sales` immediately shows the new partition in Athena.
W: Glue ETL writing partitioned Parquet and updating the catalog: one managed, serverless job converts the format, partitions the output and registers the table and partitions for Athena, with no infrastructure to run.
X: A=Manual spreadsheet conversion: it does not produce Parquet or partitions, does not register anything in the catalog, and cannot be repeated reliably.
B=Lambda loading everything into memory: Lambda is limited to 10 GB of memory and 15 minutes per invocation, so loading the whole dataset at once fails as data grows, and you would still write the Parquet and catalog code yourself.
D=Custom Java on EC2: you must build, patch and scale the server and write the conversion and catalog updates, and processing one file at a time is slow.
T: A Glue ETL job can convert, partition and catalog data in one serverless run; Lambda and EC2 require building and maintaining that logic yourself.

@ Q003700 explain
G: ## What data skew is
In Spark, a join or aggregation shuffles rows so that all rows with the same key end up in the same partition, processed by one task.
- If one key is very common (for example `customer_id = 'GUEST'` holding 60% of rows), one task gets most of the data, runs far longer than the others, and may spill to disk or run out of memory.
- The stage finishes only when that slowest task finishes, so the extra executors sit idle.
## Salting
**Salting** adds a random suffix to the hot key so its rows spread over several partitions.
- On the large side, `salted_key = concat(key, '_', floor(rand()*10))` splits `GUEST` into `GUEST_0` to `GUEST_9`.
- On the smaller join side, each row is replicated for every salt value so matches still work; for aggregations, aggregate by the salted key first and then again by the original key.
Spark 3 **adaptive query execution** (`spark.sql.adaptive.skewJoin.enabled`) can also split skewed partitions automatically in joins.
W: Salting the skewed key: it breaks the hot key's rows into many partitions, so the work is shared across tasks instead of piling onto one.
X: A=Removing output partitioning: output file layout is not where the skew happens; the imbalance comes from the shuffle by key during the join or aggregation.
B=Converting to CSV: the file format does not change how rows are distributed by key, and CSV is also slower to read than columnar formats.
D=Fewer executors: fewer executors reduce parallelism, and the single oversized task still runs alone; it gets slower, not faster.
T: Skew is one key overloading one task; salting (or adaptive skew join handling) spreads that key, while changing formats or resources leaves the imbalance.

@ Q003701 explain
G: ## Window functions
A **window function** computes a value for each row using a set of related rows (the "window"), without collapsing rows the way `GROUP BY` does.
- `PARTITION BY` defines the groups, such as one window per customer.
- `ORDER BY` inside `OVER` sets the order within each group.
- Ranking functions include `ROW_NUMBER()` (1, 2, 3 with no ties), `RANK()` (ties share a rank, then a gap) and `DENSE_RANK()` (ties share a rank, no gap).
## Example
`SELECT customer_id, order_id, order_date, ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY order_date) AS order_seq FROM orders;`
Customer 42's orders from January, March and May get `order_seq` 1, 2 and 3, and numbering restarts at 1 for the next customer. Every order row is kept.
This works in Amazon Athena, Amazon Redshift and Spark SQL.
W: Window function with PARTITION BY customer ORDER BY date: it ranks orders within each customer by date while keeping every order row, which is exactly the requested output.
X: A=CROSS JOIN: it pairs every order with every customer, producing a huge result that assigns no ranking at all.
B=GROUP BY with MAX(date): it collapses each customer to one row with the latest date, losing the individual orders and their positions.
D=DISTINCT: it only removes duplicate rows; it assigns no order or rank within a customer.
T: Rankings within groups while keeping all rows need a window function; GROUP BY collapses rows and DISTINCT only de-duplicates.

G: ## CREATE TABLE AS SELECT (CTAS) in Athena
A normal Athena `SELECT` writes its result as a CSV file to the query result location and does not create a reusable table. **CTAS** runs a query and stores the result as a new table:
- the data is written to an S3 location you choose, in a format such as `PARQUET` or `ORC`, with compression;
- `partitioned_by` and `bucketed_by` lay out the files for efficient filtering;
- the table is registered in the AWS Glue Data Catalog automatically, ready to query.
## Example
`CREATE TABLE lake.sales_opt WITH (format = 'PARQUET', external_location = 's3://lake/sales_opt/', partitioned_by = ARRAY['dt']) AS SELECT order_id, amount, dt FROM raw.sales_csv;`
Partition columns must be listed last in the `SELECT`. A single CTAS query can write up to 100 partitions; larger backfills use `INSERT INTO` in additional steps.
W: CTAS in Athena: one statement writes the query result as partitioned Parquet in S3 and registers it as a new table in the catalog.
X: A=SELECT saved as CSV: the result is an unpartitioned CSV file in the results location with no table definition, so it is neither optimized nor directly queryable as a table.
C=Glue crawler on the results bucket: it could catalog the CSV output, but it does not convert it to Parquet or partition it, so the data stays unoptimized.
D=S3 Select: S3 Select filters the contents of a single object and returns the result to the caller; it does not create tables or write partitioned Parquet (and it is no longer offered to new customers).
T: To turn a query result into a partitioned Parquet table, use CTAS; a plain SELECT or crawler leaves unoptimized CSV.

G: ## Orchestrating dependent steps with Step Functions
AWS Step Functions runs **state machines** defined in Amazon States Language (JSON). Each state is a step, and transitions define the order.
- **Service integrations** call AWS services directly, such as `glue:startJobRun`, the Redshift Data API and `sns:publish`. The `.sync` pattern waits for a Glue job to finish before moving on.
- **Retry** and **Catch** fields on each task handle errors with backoff and fallback paths.
- The console shows a **visual graph** of each execution, highlighting which step succeeded, failed or is running, with inputs and outputs for each step.
- It is serverless: no scheduler or server to run.
## Example
`Ingest` (Lambda) leads to `Transform` (Glue job with `.sync`), then `Load` (Redshift Data API `ExecuteStatement`), then `Notify` (SNS publish). A `Retry` on `Transform` retries twice with backoff, and a `Catch` sends failures to an alert.
W: AWS Step Functions: it enforces step order, waits for Glue jobs, retries failures and shows each run visually, all as a managed serverless service.
X: B=SQS standard queues only: queues decouple producers and consumers, but they do not define step order, track a workflow's state or show a visual execution graph; standard queues can also deliver messages out of order.
C=CloudFront distributions: CloudFront is a content delivery network that caches web content at edge locations; it does not run or coordinate data pipelines.
D=Cron on EC2: you must maintain the server and write your own dependency, retry and monitoring logic, which is the opposite of minimal infrastructure.
T: Ordered, dependent steps with retries and visual monitoring point to Step Functions; queues and cron jobs lack workflow state and visibility.

G: ## Apache Airflow and DAGs
Apache Airflow is an open-source orchestrator. Workflows are **DAGs** (directed acyclic graphs) written in Python: each task is an operator, such as `GlueJobOperator` or a Redshift SQL operator, and dependencies are declared with `>>`.
Running Airflow yourself means operating the scheduler, workers, web server and metadata database.

**Amazon Managed Workflows for Apache Airflow (MWAA)** runs Airflow for you.
- You place DAG files, `requirements.txt` and plugins in an S3 bucket, and MWAA loads them.
- AWS runs the scheduler, workers and web server inside your VPC, scales workers, and handles patching and upgrades to supported Airflow versions.
- Logs go to Amazon CloudWatch, and access to the Airflow UI is controlled with IAM.
## Example
The team copies its existing `daily_sales.py` DAG to `s3://mwaa-bucket/dags/`, and it appears in the Airflow UI with the same tasks and schedule, without being rewritten.
W: Amazon MWAA: it runs real Apache Airflow, so the team's existing Python DAGs work unchanged while AWS manages the Airflow infrastructure.
X: A=EventBridge Scheduler only: it invokes a target at a time or rate, but it has no concept of Airflow DAGs, task dependencies or Airflow operators.
B=AWS Batch compute environments: Batch runs containerized jobs on managed compute; it does not execute Airflow DAG definitions.
C=Glue DataBrew recipe jobs: DataBrew applies visual data-preparation recipes to datasets; it is not a workflow orchestrator and cannot run DAGs.
T: Existing Airflow DAGs belong on MWAA; other schedulers would require rewriting the workflows.

G: ## Event-driven job starts
Instead of polling for new files, S3 can **emit an event** when an object is created, and a rule can react to it.
- Enable **Amazon EventBridge** delivery on the bucket; every `Object Created` event is then sent to the default event bus.
- An EventBridge **rule** matches events by bucket and prefix, for example `{"source":["aws.s3"],"detail-type":["Object Created"],"detail":{"bucket":{"name":["raw-data"]},"object":{"key":[{"prefix":"orders/"}]}}}`.
- The rule's target can be a **Glue workflow** (an EventBridge-type trigger can start it once, or after a batch of events), a Step Functions state machine, or a Lambda function that calls `StartJobRun`.
## Example
A file `orders/2026-09-29.csv` lands in `raw-data`. The rule matches within seconds, starts the Glue workflow, and the job processes the file with no idle polling.
W: EventBridge rule on the S3 event: it starts the Glue job or workflow automatically in response to the upload, with no people involved and no polling.
X: A=Manual starts: people watching a bucket are slow, miss files outside working hours, and the question asks for an automatic start.
B=Glue job every minute: the job starts, bills for its run, and usually finds nothing, and it still adds up to a minute of delay; it is wasteful polling, not an event.
D=S3 lifecycle rule: lifecycle rules only transition objects to other storage classes or expire them; they cannot run a Glue job.
T: To run a job when a file arrives, use S3 events through EventBridge; lifecycle rules manage storage, and polling schedules waste runs.

G: ## Glue workflows and triggers
An **AWS Glue workflow** groups crawlers, jobs and triggers into one orchestrated unit.
- **Triggers** start the next nodes: a *scheduled* or *on-demand* trigger starts the workflow, and a *conditional* trigger fires when watched jobs or crawlers reach a state such as `SUCCEEDED` or `FAILED`. An *event* trigger can start it from EventBridge.
- The Glue console shows each workflow run as a graph, with the status of every crawler and job in one view.
- Workflow **run properties** let jobs share small values, such as the processing date.
## Example
Trigger T1 (daily at 02:00) starts crawler `raw_crawler`. A conditional trigger T2 fires when it succeeds and starts jobs `clean_orders` and `clean_customers`. A trigger T3 waits for both to succeed and starts `build_sales_mart`. One graph shows the run's progress.
W: Glue workflows with triggers: they chain crawlers and jobs in dependency order using conditional triggers and show the whole run's status in one graph.
X: A=DataBrew projects: DataBrew projects are interactive workspaces for building data-preparation recipes; they do not orchestrate Glue crawlers and jobs.
B=Interactive notebook sessions: they are for developing and testing Spark code interactively; they do not schedule or chain jobs in production.
D=Glue Schema Registry: it stores and validates schemas for streaming records; it has no role in ordering or monitoring jobs.
T: Ordering Glue crawlers and jobs with one status view is what Glue workflows and triggers do; DataBrew, notebooks and the Schema Registry serve other purposes.

G: ## Error handling in Step Functions
Task states in AWS Step Functions support two fields for failures.
- **Retry** re-runs the task when specific errors occur. `IntervalSeconds`, `BackoffRate` and `MaxAttempts` control **exponential backoff**, and optional `MaxDelaySeconds` and `JitterStrategy` cap and randomize the wait. For example, waits of 2, 4 and 8 seconds before giving up.
- **Catch** runs after retries are exhausted (or for errors not retried) and routes the execution to another state, such as a fallback, a compensation step or an alert, instead of failing the whole workflow. `ResultPath` can keep the error details.
## Example
`"Retry": [{"ErrorEquals": ["States.TaskFailed"], "IntervalSeconds": 2, "BackoffRate": 2, "MaxAttempts": 3}]` rides out a brief API outage. `"Catch": [{"ErrorEquals": ["States.ALL"], "Next": "NotifyAndQueueForLater"}]` handles a longer outage cleanly.
W: D=Catch blocks with a fallback path: if the API stays down after retries, the workflow moves to a defined fallback or alert instead of simply failing.
E=Retry with exponential backoff: temporary unavailability usually clears within seconds, so retrying with growing waits recovers most failures automatically.
X: A=Removing the failing step: the step does required work; deleting it breaks the pipeline's output instead of handling the error.
B=Disabling logging: logging does not cause API failures, and turning it off only makes failures harder to investigate.
C=Running all steps in parallel: the steps depend on each other, so ignoring their order produces wrong results and does nothing about the API being briefly down.
T: Transient failures are handled with Retry and backoff, with Catch as the fallback when retries run out; removing steps or logs hides the problem.

G: ## Lambda layers
A **Lambda layer** is a .zip archive of code or dependencies that you publish once and attach to many functions.
- Each published layer version is immutable and has an ARN, such as `arn:aws:lambda:us-east-1:111122223333:layer:data-utils:4`.
- At runtime the layer is extracted to `/opt`, and for Python its `python/` folder is on the import path, so functions can use `from transforms import normalize_address`.
- A function can use up to five layers, and the function plus its layers must stay within the 250 MB unzipped deployment size limit.
- Updating means publishing a new version and pointing functions at it, so every pipeline runs the same tested code.
Layers apply to .zip-packaged functions; container-image functions include shared code in the image instead.
## Example
The `data-utils` layer contains `transforms.py`. Three ingestion functions attach version 4, and a fix is rolled out by publishing version 5 and updating each function's layer reference.
W: Lambda layer: it packages the transformation function once, versions it, and lets every Lambda pipeline import the same code without copying it.
X: B=Copying by hand: copies drift apart over time, and every fix must be applied separately to each function.
C=Rewriting in each pipeline: separate implementations behave inconsistently and multiply testing and maintenance effort.
D=Environment variables: they hold configuration strings, limited to 4 KB in total per function, and are not a mechanism for sharing importable code.
T: Share code across Lambda functions with a versioned layer; copying or rewriting leads to drift.

G: ## Infrastructure as code for data pipelines
**Infrastructure as code (IaC)** describes resources in version-controlled files that a tool deploys the same way every time.
- **AWS CloudFormation** uses YAML or JSON templates; a stack creates or updates all resources and can roll back on failure. Resource types include `AWS::Glue::Job`, `AWS::Glue::Crawler`, `AWS::IAM::Role` and `AWS::S3::Bucket`.
- **AWS CDK** lets you define the same resources in Python, TypeScript or other languages and synthesizes CloudFormation templates.
- A **CI/CD pipeline** (for example AWS CodePipeline or GitHub Actions) deploys the same code to dev, test and prod, with parameters such as bucket names or worker counts per environment.
## Example
A CDK app defines a `DataPipelineStack` with the raw bucket, the Glue crawler, the ETL job and its IAM role. A merge to `main` deploys it to dev, and after tests the pipeline promotes the same template to prod.
W: CDK or CloudFormation through CI/CD: the pipeline's resources are defined as versioned code and deployed identically to every environment, with review and rollback.
X: A=Screenshots of production: screenshots are incomplete and cannot be executed, so recreating resources from them is manual and error-prone.
B=Manual console copying: clicking through settings in each environment causes drift and mistakes and leaves no reviewable history.
D=Shared text file of settings: it documents intent but deploys nothing, so environments still have to be built by hand and quickly diverge from the file.
T: Consistent deployment across environments comes from IaC (CDK or CloudFormation) in CI/CD; documentation and manual copies are not executable.

G: ## Sort keys and zone maps in Redshift
Amazon Redshift stores each column in 1 MB blocks. For every block it keeps a **zone map**: the minimum and maximum values in that block.
- When a query filters on a column, Redshift checks zone maps and skips blocks whose range cannot match.
- This works well only when the table is **sorted** on that column. Otherwise, every block contains a mix of dates, so each block's min to max range covers almost everything and nothing can be skipped.
- A **sort key** (for example `SORTKEY (sale_date)`, or `AUTO` chosen by Redshift) stores rows in that order, so each block covers a narrow date range.
## Example
A 3-year sales table sorted on `sale_date` is queried with `WHERE sale_date >= '2026-09-01'`. Redshift reads only the blocks for September 2026, a small fraction of the table, instead of scanning all of it.
W: Sort key on the date column: sorting by date makes zone maps narrow, so a date filter lets Redshift skip most blocks instead of scanning the whole table.
X: A=DISTSTYLE ALL: it copies the full table to every node to help joins with small tables; it does nothing to skip blocks and multiplies storage for a large table.
C=Removing compression: uncompressed columns take more blocks and more I/O, and it does not enable block skipping.
D=Adding more columns: extra columns add storage and do not change how the date filter is evaluated.
T: Range filters in Redshift are sped up by a sort key that makes zone maps selective; distribution style and compression address other problems.

G: ## Distribution styles in Redshift
A Redshift cluster spreads each table's rows across **slices** on its compute nodes. The **distribution style** decides where each row goes.
- **KEY**: rows with the same value in the distribution key column go to the same slice.
- **EVEN**: rows are spread round-robin, ignoring values.
- **ALL**: a full copy of the table on every node, good only for small, slowly changing dimension tables.
- **AUTO**: Redshift chooses and can change the style over time.
When two tables are joined and matching rows sit on different slices, Redshift must **redistribute** or **broadcast** rows across the network (visible in `EXPLAIN` as `DS_DIST_BOTH` or `DS_BCAST_INNER`).
## Collocated joins
If both tables use `DISTKEY(customer_id)`, every row for a given customer is already on the same slice in both tables, so the join runs locally (`DS_DIST_NONE`) with no data movement.
W: KEY distribution on customer_id for both tables: matching rows are stored on the same slice, so the frequent join is collocated and needs no redistribution.
X: A=ALL on both large tables: copying two large tables to every node multiplies storage and slows every load; ALL is meant for small dimension tables.
B=EVEN on both tables: round-robin placement ignores `customer_id`, so matching rows are scattered and the join still has to redistribute data.
C=Querying tables separately: it avoids the problem by not answering the question; the application would have to join the data itself, which is slower and more complex.
T: Frequently joined large tables should share a DISTKEY on the join column so the join is collocated; EVEN scatters rows and ALL is for small tables.

G: ## Managed stream processing options
Stream processing handles records continuously as they arrive, instead of on a batch schedule.
- **AWS Glue streaming ETL** runs Apache Spark Structured Streaming as a serverless Glue job. It reads from Kinesis Data Streams, Amazon MSK or self-managed Kafka and processes micro-batches at a configurable `windowSize` (100 seconds by default, and it can be set lower), writing to S3, Data Catalog tables or other sinks.
- **Amazon Managed Service for Apache Flink** runs Apache Flink applications (Java, Python, or SQL in Studio notebooks) on managed infrastructure. Flink processes records one by one with sub-second latency and supports windows and stateful operations.
Both handle scaling, checkpoints and recovery for you.
## Example
Clickstream events in a Kinesis data stream are enriched and aggregated per session. A Glue streaming job writes results to S3 every 30 seconds, or a Flink application updates per-minute counts for alerts within seconds.
W: Glue streaming ETL or Managed Service for Apache Flink: Glue streaming runs the Spark transformation itself as a managed Structured Streaming job with sub-minute micro-batches, and Managed Flink is the managed alternative when the logic can be written for Flink; both process the stream continuously on managed infrastructure.
X: A=Daily Glue batch job with bookmarks: bookmarks make batch runs incremental, but a once-a-day run still has up to 24 hours of delay.
C=Nightly Redshift COPY: COPY is a bulk load from S3; running it nightly is batch loading with hours of latency and no stream processing logic.
D=Hourly manual Athena queries: Athena queries data at rest in S3 on demand; manual hourly runs are neither streaming nor sub-minute.
T: Sub-minute processing of streaming data needs a stream processor; for Spark code that means Glue streaming ETL, with Managed Flink as the Flink option. Scheduled batch jobs, however incremental, add hours of delay.
