@ Q003492 explain
G: ## What investigators need from many accounts
A security investigation asks two questions: **who did what** in the control plane, and **what talked to what** on the network. In a multi-account organization, both answers must live in one place that the accounts under investigation cannot tamper with.
- **AWS CloudTrail** records API calls: the caller identity, time, source IP, action and parameters. An organization trail created in the management (or delegated admin) account captures every member account and delivers to one S3 bucket, typically in a dedicated log archive account.
- **VPC Flow Logs** record accepted and rejected IP traffic for ENIs, subnets or VPCs: source and destination addresses, ports, protocol, bytes and action. They can be published to a central S3 bucket or CloudWatch Logs.
## Example
An attacker uses a stolen key to call `AuthorizeSecurityGroupIngress`, then exfiltrates data. CloudTrail shows the key, the call and the time; Flow Logs show the new inbound connections and the outbound volume to an unknown IP.
W: A=CloudTrail logs from all accounts: the authoritative record of API activity and identities across the organization, needed to trace actions back to a principal.
E=VPC Flow Logs from key VPCs: the network-level record of connections, needed to see lateral movement or data leaving the VPC.
X: B=Local shell history: it lives on personal machines, is easily edited or cleared, is incomplete and cannot be collected reliably, so it has no evidential value at scale.
C=Console screenshots: static images of whatever someone happened to view; they are not searchable, not complete and not a record of who changed what.
D=Printed IAM policies: a snapshot of intended permissions, not a log of activity; they go stale immediately and show nothing about actual events.
T: Centralize machine-generated, tamper-resistant logs (CloudTrail for API calls, Flow Logs for network traffic), not artifacts people create by hand.

@ Q003493 explain
G: ## How a CloudWatch alarm decides to fire
An alarm evaluates a metric in fixed **periods** (for example 300 seconds). Each period produces one datapoint using the chosen statistic, such as `Average`.
- **Evaluation periods** is how many recent datapoints the alarm looks at.
- **Datapoints to alarm** is how many of those must breach the threshold (by default, all of them).
## Example
Period 5 minutes, 3 evaluation periods, 3 of 3 datapoints: the alarm goes to `ALARM` only when average CPU is above 80% in three consecutive 5-minute windows, so for 15 minutes. A 2-minute spike raises one 5-minute average at most, which is not enough.
Auto Scaling group EC2 metrics such as `CPUUtilization` come every 5 minutes by default (basic monitoring), so a 5-minute period also matches the data resolution; 1-minute data needs detailed monitoring.
W: 5-minute period with 3 evaluation periods: 3 x 5 minutes requires the condition to hold for 15 minutes continuously, which filters out short spikes exactly as asked.
X: A=Metric filter on boot messages: it counts matching log lines such as startup messages, which says nothing about sustained CPU load.
C=1-minute period, 1 evaluation period: a single breaching datapoint fires the alarm, so any spike longer than a minute triggers it; this is the noisy behavior the team wants to avoid.
D=Dashboard threshold line: a dashboard only visualizes data; it does not evaluate conditions or send notifications.
T: Sustained duration = period x evaluation periods; use several periods instead of a single short one to ignore brief spikes.

@ Q003494 explain
G: ## Log analytics needs an inverted index
Searching free text across billions of log lines quickly requires a search engine that builds an **inverted index**: for each term, the list of documents that contain it. A query like `error AND payment-service` then touches only matching documents.
**Amazon OpenSearch Service** is a managed OpenSearch (and legacy Elasticsearch) cluster. It provides:
- Full-text search, filters and aggregations over JSON documents such as log events.
- **OpenSearch Dashboards** for visualizations and dashboards.
- Ingestion from sources such as Amazon Data Firehose, OpenSearch Ingestion pipelines or CloudWatch Logs subscriptions.
- An OpenSearch Serverless option when you do not want to manage cluster capacity.
## Example
Application logs flow through Firehose into an index per day; engineers search for a request ID and build a dashboard of 5xx counts by service.
W: Amazon OpenSearch Service: it is built for full-text search and aggregation of log data at scale, and ships with OpenSearch Dashboards for visualization.
X: A=Amazon ElastiCache: an in-memory cache (Redis OSS, Valkey, Memcached) for key-based lookups; it does not index text for search or provide log dashboards.
B=Amazon Neptune: a graph database for relationship queries (Gremlin, openCypher, SPARQL), not for full-text log search.
D=Amazon DocumentDB: a MongoDB-compatible document database for application data; it is not a log analytics platform with dashboards.
T: For searching and visualizing logs, pick a search engine (OpenSearch), not a cache, graph or document database.

G: ## From alarm to a human who responds
A CloudWatch alarm can publish to SNS, but SNS just delivers a message: it does not know who is on call, does not wait for someone to acknowledge, and does not try the next person if nobody answers.
**AWS Systems Manager Incident Manager** adds the paging layer:

- **Response plans** that a CloudWatch alarm or EventBridge rule can start, creating an incident that engages the right contacts.
## Example
A `5xx` alarm starts a response plan; the primary on-call engineer gets an SMS and a voice call. With no acknowledgement in 5 minutes, the escalation plan pages the secondary engineer.

For new accounts AWS points to Systems Manager OpsCenter and AWS Partner paging tools, but the exam still treats Incident Manager as the on-call escalation answer.

X: A=SQS standard queues with polling: a queue holds messages for programs to consume; it cannot page people, track acknowledgement or escalate.
B=AWS Config aggregators: they collect configuration and compliance data from many accounts and Regions; they have nothing to do with paging responders.
C=AWS Batch job queues: they schedule batch compute jobs, not notifications or on-call engagement.
T: SNS or queues deliver messages; on-call paging with acknowledgement and escalation is what Incident Manager adds.

@ Q003496 explain
G: ## ECS log drivers
Each container in an ECS task definition has a `logConfiguration` that picks a log driver.
- `awslogs` sends container stdout/stderr to **one CloudWatch Logs log group**. It is simple but has a single destination.
- `awsfirelens` enables **FireLens**: ECS adds a log router sidecar container running **Fluent Bit** (AWS for Fluent Bit image) or **Fluentd**. Application containers send their logs to the sidecar, which can filter, enrich and fan out to multiple outputs.
FireLens works on both Fargate and EC2 launch types.
## Example
The Fluent Bit configuration has two `[OUTPUT]` sections: the `cloudwatch_logs` plugin writing to `/ecs/orders`, and an HTTP or vendor plugin (Datadog, Splunk, New Relic and others) sending the same stream to the observability tool.
W: FireLens log router with multiple outputs: the Fluent Bit or Fluentd sidecar can send the same container logs to CloudWatch Logs and to a third-party destination at once.
X: A=ECS Exec into each container: it opens an interactive shell for debugging; reading logs by hand does not route anything anywhere and does not scale.
B=awslogs driver with one log group: it has exactly one destination, CloudWatch Logs, so the third-party tool would need a separate forwarding pipeline.
C=Environment variables only: variables configure the application process; by themselves they do not change where the container runtime sends logs.
T: One destination = `awslogs`; multiple or non-AWS destinations = FireLens with Fluent Bit outputs.

@ Q003497 explain
G: ## Correlating traces and logs
A **trace** follows one request across services (for AWS X-Ray, identified by a trace ID such as `1-5f84c7a1-...`). **Logs** describe what each service did. They become useful together only if they share a key.
- Emit **structured logs** (JSON) with fields such as `trace_id`, `service`, `level` and `message`.
- Propagate the trace context through service calls (for example the `X-Amzn-Trace-Id` header or W3C `traceparent` with OpenTelemetry) and inject the current trace ID into every log entry.
- Libraries such as Powertools for AWS Lambda can add the X-Ray trace ID to log entries automatically.
## Example
A slow trace shows the payment service took 4 seconds. Querying CloudWatch Logs Insights with `filter trace_id = "1-5f84..."` returns exactly the log lines for that request across all services, including the timeout warning.
W: Trace IDs in structured log entries: a shared, queryable ID lets you jump from a trace to the matching log lines (and back) instead of guessing by timestamp.
X: A=Free-text messages without context: nothing ties a line to a request, so you must match by time and guesswork, which fails under load.
B=Separate accounts for logs and traces: separation adds friction and does nothing to link a trace to its logs; the missing piece is a common ID, not location.
D=Disable tracing: it removes the trace data entirely, making troubleshooting slower; sampling is the usual way to control tracing cost.
T: Correlation needs a shared key: put the trace ID in every structured log line.

@ Q003498 explain
G: ## Amazon EventBridge as an event router
EventBridge receives events as JSON on **event buses** and routes them with **rules**.
- The **default event bus** receives events from AWS services automatically (for example EC2 state changes or CodePipeline execution changes).
- **Partner event buses** receive events from supported SaaS partners, such as Zendesk or Datadog, through a partner event source.
- **Custom event buses** receive your own application events via `PutEvents`.
A rule has an **event pattern** (for example `source: aws.codepipeline`, `detail.state: FAILED`) and up to five targets such as Lambda, Step Functions, SQS, SNS or SSM Automation.
## Example
One rule sends failed pipeline executions to a Lambda function that opens a ticket; another sends a partner's security alert to a Step Functions workflow.
W: EventBridge event buses with rules: a single managed router that natively receives AWS service and SaaS partner events and filters them to the right automated targets.
X: A=SQS FIFO queue per service: queues buffer messages for one consumer group; they have no content-based routing, and AWS services and SaaS partners do not publish into them natively.
C=S3 buckets collecting event files: files are batch storage, not a routing layer; responders would have to poll and parse, adding delay.
D=Batch job queue per event type: AWS Batch schedules compute jobs; it does not ingest or pattern-match events.
T: Central receive-and-route for AWS and SaaS events is EventBridge buses plus rules, not queues or storage.

@ Q003499 explain
G: ## Cross-account event routing
EventBridge can send events from one account's bus to an event bus in another account.
- In the **central operations account**, a custom event bus has a **resource-based policy** allowing `events:PutEvents` from the member accounts, often with a condition on `aws:PrincipalOrgID` so every account in the organization is allowed.
- In each **member account**, a rule matches the relevant events and uses the central bus ARN as its target, typically with an IAM role that allows `events:PutEvents` on that bus.
- In the central account, rules on the central bus trigger the automation (Lambda, Step Functions, SSM Automation).
## Example
Each of the 30 accounts forwards `aws.guardduty` and `aws.health` events to `arn:aws:events:us-east-1:111122223333:event-bus/central-ops`, where one rule starts a remediation workflow. Rolling out the member-side rule with CloudFormation StackSets keeps all accounts consistent.
W: Forward to a central event bus with a resource policy: events arrive in near real time in one place, and one set of automation handles all 30 accounts.
X: B=Lambda emailing summaries: email is meant for humans, not for automation to consume; it adds delay and parsing and loses the structured event.
C=Manual CSV uploads to S3: manual steps are slow, error-prone and not event-driven, so automation cannot react in minutes.
D=Daily dashboard review: a person looking once a day is neither automated nor central, and events wait up to 24 hours.
T: Multi-account automation = member rules forwarding to a central EventBridge bus whose resource policy allows the organization.

G: ## AWS Health and EventBridge
**AWS Health** reports events that affect your account's resources, such as scheduled maintenance (EC2 instance retirement, RDS maintenance), service issues in a Region, and account notifications. The same information appears in the Health Dashboard.
AWS Health publishes these events to **EventBridge** with `source: aws.health`. A rule can match fields such as `detail.service` (`EC2`), `detail.eventTypeCategory` (`scheduledChange`, `issue`) or a specific event type code.
- Targets can notify people (SNS, chat) and act automatically (Lambda, SSM Automation).
- With AWS Organizations, organizational view in AWS Health and cross-account event routing let one account see events from many.
## Example
An `AWS_EC2_INSTANCE_RETIREMENT_SCHEDULED` event triggers an Automation runbook that stops and starts the instance in a maintenance window so it moves to healthy hardware.
W: AWS Health events through EventBridge: they are the authoritative, resource-specific source for maintenance and service issues, and EventBridge lets automation act on them.
X: B=Cost Explorer reports: they show spending and usage trends; they contain no maintenance or service-health information.
C=Config rules on every resource: Config evaluates your own configuration against rules; it does not know about AWS-side maintenance or outages.
D=Trusted Advisor cost checks: they recommend savings, such as idle resources, on a periodic basis; they are not event notifications about health issues.
T: AWS-side maintenance and outages come from AWS Health; route them with EventBridge to automate the response.

@ Q003501 explain
G: ## What happens when an EventBridge target fails
EventBridge delivers to a target asynchronously. If delivery fails (for example throttling, or the target is unavailable), EventBridge retries with backoff according to the target's **retry policy**:
- `MaximumRetryAttempts` (0 to 185) and `MaximumEventAgeInSeconds` (60 seconds to 24 hours).
- When retries are exhausted, the event is dropped unless the target has a **dead-letter queue** (an SQS queue). The DLQ stores the event with attributes explaining the error, so it can be inspected and redriven.
For Lambda, EventBridge invokes asynchronously, so Lambda's own asynchronous retries and an on-failure destination or DLQ on the function also help for errors raised inside the function code.
## Example
Retry policy: 24 hours, 185 attempts; DLQ `orders-rule-dlq`. A 10-minute outage of a downstream dependency is absorbed by retries, and anything older than 24 hours lands in the DLQ instead of vanishing.
W: B=Retry policy on the target: it controls how long and how often EventBridge keeps trying, so transient failures are redelivered.
E=Dead-letter queue on the target: events that still fail after retries are kept in SQS for analysis and replay instead of being lost.
X: A=Larger memory size: it may speed up the function, but it does not make EventBridge keep or redeliver events that fail.
C=New event bus per failed event: buses are long-lived routing resources; creating one per event does not store or retry anything.
D=Longer log retention: it keeps logs longer, but logs do not contain the lost events in a form that can be redelivered.
T: For failed EventBridge deliveries, retries handle transient errors and a DLQ keeps what still fails.

@ Q003502 explain
G: ## EventBridge archive and replay
An **archive** stores events that arrive on an event bus. You can archive all events or only those matching an event pattern, and set a retention period (or keep them indefinitely).
A **replay** sends archived events from a chosen time window back to the same event bus. You pick which rules receive the replayed events, so only the fixed consumer processes them again. Replayed events carry a `replay-name` field, so consumers can recognize them.
## Example
A bug in the `invoice-generator` Lambda function mishandled orders from Monday to Friday. After deploying the fix, the team starts a replay of the `orders` archive for that time window, targeting only the `invoice-generator` rule, so other consumers do not see duplicates.
Replays are not instant: events are re-sent over time and the replay shows its progress and state until it completes.
W: Event archive and replay: the archive keeps last week's events, and replay re-delivers that time window to selected rules, which is exactly reprocessing after a bug fix.
X: A=Scheduled rules only: they fire on a cron or rate schedule; they generate new trigger events and cannot resend past events.
B=Schema registry only: it discovers and stores event structures for code generation; it holds no event data to replay.
D=API destinations only: they let a rule call an external HTTP endpoint; they are a target type, not a store of past events.
T: To reprocess past events, archive them in advance and replay a time window to chosen rules.

@ Q003503 explain
G: ## Detect and auto-remediate with AWS Config
AWS Config records resource configuration and evaluates it with **rules**. Managed rules such as `s3-bucket-public-read-prohibited`, `s3-bucket-public-write-prohibited` or `s3-bucket-level-public-access-prohibited` are triggered by configuration changes, so a newly public bucket is evaluated shortly after the change.
A rule can have **automatic remediation**: when a resource becomes `NON_COMPLIANT`, Config runs a Systems Manager Automation document with parameters taken from the resource.
- AWS provides documents such as `AWS-DisableS3BucketPublicReadWrite`, which turns on S3 Block Public Access for the bucket.
- Remediation needs an IAM role for Automation and supports retry settings.
## Example
A developer adds a bucket policy allowing `Principal: "*"`. Config evaluates the change, marks the bucket non-compliant, and the remediation re-enables Block Public Access within minutes.
Account-level S3 Block Public Access prevents most of these changes in the first place; auto-remediation covers the rest.
W: Config rule with automatic remediation via SSM Automation: it detects the change and reverts it without humans, within minutes.
X: A=Email reminders: guidance does not detect or fix anything; a bucket that becomes public stays public.
B=Weekly review with manual fixes: exposure could last up to a week, far longer than minutes, and depends on people.
C=Dashboard of public bucket counts: it shows the problem but takes no action to revert it.
T: "Automatically reverted within minutes" means a detective rule plus automatic remediation, not reports or reminders.

G: ## Reporting versus enforcing configuration
Detection alone lists drift; the requirement here is correction without human work. Two AWS mechanisms do that:
- **AWS Config rules with automatic remediation**: when a rule marks an instance `NON_COMPLIANT`, Config runs an SSM Automation document to fix it, such as enabling detailed monitoring or attaching a required IAM instance profile.
- **Systems Manager State Manager associations**: an association applies a document (for example `AWS-RunPatchBaseline`, `AWS-ConfigureAWSPackage`, or a custom Command document) to targeted instances on a schedule, re-applying it if the instance drifts from the desired state inside the OS.
## Example
An association runs every 30 minutes and ensures the CloudWatch agent is installed and running on every instance tagged `env=prod`. If someone stops the agent, the next association run starts it again, and association compliance shows which instances were fixed.
W: Config remediation or State Manager associations: both automatically bring noncompliant instances back to the required configuration, rather than only reporting them.
X: A=Tag policies: they standardize tag keys and values across an organization; they do not change instance configuration and cannot fix drift.
B=Manually updated spreadsheet: it is a manual report, not correction, and it is always out of date.
D=CloudTrail trails: they record API calls for auditing; they neither detect OS-level drift nor correct anything.
T: "Corrected, not just reported" = automatic remediation (Config + Automation) or desired-state enforcement (State Manager).

@ Q003506 explain
G: ## CodeDeploy lifecycle hooks on EC2
The `appspec.yml` file maps lifecycle events (`BeforeInstall`, `AfterInstall`, `ApplicationStart`, `ValidateService`) to scripts that the CodeDeploy agent runs on the instance. Each hook can set a `timeout` in seconds (up to 3600); if the script has not exited when it expires, the deployment fails.
Common causes of an `ApplicationStart` timeout:
- The script starts the server in the foreground and never returns. It should start the service (for example `systemctl start myapp`) or background the process and redirect stdout/stderr so the agent is not left waiting.
- The script waits on a dependency (database, port) that never becomes ready.
- The timeout value is too short for a legitimately slow start.
## Where to look
On Linux, the agent logs are under `/opt/codedeploy-agent/deployment-root/`, including `deployment-logs/codedeploy-agent-deployments.log`, which shows the script output. The CodeDeploy console also shows the event's error for each instance.
W: Script logs and the hook timeout in appspec.yml: the failure is inside the hook script on the instance, so its output and the configured timeout reveal whether it hangs or needs more time.
X: B=IAM password policy and MFA: they govern console users signing in; they do not affect a script the agent runs on an instance.
C=S3 lifecycle rules for artifacts: the revision was already downloaded, since the deployment reached `ApplicationStart`; lifecycle rules would not make a script hang.
D=Route 53 TTL: DNS caching affects how clients resolve a name, not whether a local start script exits in time.
T: A hook timeout is a script problem on the instance: read the agent's deployment log and check the hook's `timeout`.

@ Q003507 explain
G: ## Why ECS tasks behind an ALB keep restarting
When an ECS service uses a load balancer, a task is considered healthy only when the **target group health check** passes. ECS stops and replaces tasks that fail it (after the service's health check grace period), and also replaces tasks whose essential container exits. Two usual causes:
- **The container itself crashes or fails at startup**: missing environment variable, bad secret, wrong image tag, out of memory. The task's stopped reason and the container logs (for example via the `awslogs` driver in CloudWatch Logs) show the error.
- **The health check is misconfigured**: the path (for example `/health` versus `/healthz`), the port, the expected status codes (`200` versus `200-399`), or the timeout do not match what the app serves, so a working app is marked unhealthy and replaced.
## Example
The app listens on port 8080 and serves `/status`, but the target group checks `/` on the traffic port and expects `200`; the app returns `302`, so every task is replaced after the grace period.
W: B=Task logs for startup errors or crashes: they reveal whether the container is failing on its own, before it could ever pass a health check.
E=Target group health check path and port: a wrong path, port or success code makes healthy tasks look unhealthy, causing the endless replacement loop.
X: A=Hosted zone name server records: DNS delegation affects clients resolving the domain, not whether the ALB's health checks against tasks succeed.
C=IAM credential report: it lists IAM users' passwords and access keys; it does not describe container or health check behavior.
D=Storage class of unrelated buckets: storage class affects cost and retrieval of S3 objects that this service does not even use.
T: Tasks that never become healthy either crash (check container logs) or fail a misconfigured health check (check path, port and matcher).

@ Q003508 explain
G: ## Reading CloudFormation stack events
Every change to a stack produces **stack events**: one entry per resource status change, such as `UPDATE_IN_PROGRESS`, `UPDATE_FAILED` or `UPDATE_ROLLBACK_IN_PROGRESS`. A failed event includes a **status reason** with the underlying service error.
- Look for the **first** `CREATE_FAILED` or `UPDATE_FAILED` event in time; later failures are often side effects ("Resource update cancelled").
- The status reason usually names the problem directly, such as a missing IAM permission, an invalid parameter, a name that already exists, or a service quota.
- The console's **Events** tab can highlight the root cause, and `aws cloudformation describe-stack-events` returns the same data.
## Example
An update fails with `UPDATE_FAILED` on `AppBucket`, status reason "my-app-logs already exists". The stack then rolls back. Renaming the bucket or removing the explicit `BucketName` fixes it.
W: Stack events with status reason: CloudFormation records which resource failed and the error returned by the service, which is exactly the specific cause needed.
X: A=EC2 system log only: it helps only when the failure is inside an instance's boot; most resource errors (IAM, S3, parameters) never appear there.
B=IAM Access Analyzer findings: they report external access and unused access, not why a stack operation failed.
C=Billing console: charges and invoices show cost, not deployment errors.
T: For a CloudFormation failure, read the first failed stack event and its status reason.

@ Q003509 explain
G: ## How CodeDeploy rolls back a Lambda deployment
For Lambda, CodeDeploy shifts traffic between two versions by changing the **weights of an alias** (for example the predefined configurations `CodeDeployDefault.LambdaCanary10Percent5Minutes` or `CodeDeployDefault.LambdaLinear10PercentEvery1Minute`).
CodeDeploy only knows something is wrong if it is told:
- The deployment group lists **CloudWatch alarms** (for example on the function's `Errors` metric for the new version or alias).
- **Automatic rollback** is enabled for "when alarm thresholds are met". If an alarm goes to `ALARM` during the deployment, CodeDeploy stops and shifts all traffic back to the old version.
- Pre-traffic and post-traffic hook functions can also fail the deployment.
Without alarms or failing hooks, the deployment "succeeds" from CodeDeploy's point of view even if errors rise, so nothing rolls back.
## Example
An alarm `orders-live-errors` on `Errors > 5` for 1 minute is attached to the deployment group. With a 10% canary, the alarm fires within minutes and CodeDeploy restores 100% of traffic to the previous version.
W: No alarm on the deployment group: CodeDeploy has no signal that errors increased, so it completes the traffic shift instead of rolling back.
X: B=Manual approval before deploy: it happens before the deployment starts and does not affect monitoring or rollback once traffic shifts.
C=Higher memory: more memory does not cause errors and has no link to whether CodeDeploy decides to roll back.
D=Weighted alias during the shift: weighted aliases are how CodeDeploy shifts Lambda traffic; they are expected, not a reason for missing rollback.
T: CodeDeploy rolls back on metrics only when alarms are attached to the deployment group and rollback on alarm is enabled.

@ Q003510 explain
G: ## Automated isolation for forensics
Amazon GuardDuty publishes each finding to EventBridge with `source: aws.guardduty`. Crypto-mining appears as finding types such as `CryptoCurrency:EC2/BitcoinTool.B!DNS`.
A rule matching those findings can start automation (Lambda, Step Functions or SSM Automation) that **contains the instance but keeps the evidence**:
- Replace its security groups with an **isolation security group** that has no inbound or outbound rules. Existing tracked connections may continue, so some teams also add a restrictive network ACL.
- Create **EBS snapshots** of its volumes, and optionally capture memory, for analysis.
- Tag the instance (for example `quarantine=true`), detach it from its Auto Scaling group and deregister it from load balancers.
## Example
Within a minute of the finding, a Step Functions workflow swaps `sg-app` for `sg-isolate`, snapshots `vol-0a1b`, and posts a message to the security channel.
W: EventBridge rule triggering isolation automation: it reacts to the finding in near real time, cuts the instance off from the network, and preserves the disks for forensics.
X: A=Terminate immediately: it stops the mining but destroys memory and, with default delete-on-termination, the root volume, so the evidence the company wants is lost.
C=Ignore until quarterly review: the attacker keeps using the instance and the account for months.
D=Email asking for manual shutdown: slow, depends on availability, and shutting down loses memory evidence instead of isolating the instance.
T: For forensics, isolate and snapshot automatically; do not terminate or wait for people.

G: ## What InsufficientInstanceCapacity means
`InsufficientInstanceCapacity` means AWS does not currently have enough capacity of the **requested instance type in that Availability Zone** to fulfill the launch. It is not a limit on your account (that would be a quota error such as `VcpuLimitExceeded`).
The fix is to give Auto Scaling more choices:
- **Multiple Availability Zones**: the group can launch in a zone that still has capacity.
- **Multiple instance types** with a mixed instances policy (for example `m6i.large`, `m5.large`, `m6a.large`), or attribute-based instance type selection. Auto Scaling tries other types when one is unavailable.
- For guaranteed capacity, **On-Demand Capacity Reservations** can be used.
## Example
A group limited to `c5.xlarge` in `us-east-1a` fails repeatedly. After adding `us-east-1b` and `us-east-1c` and allowing `c6i.xlarge` and `c5a.xlarge`, launches succeed.
W: Multiple instance types and Availability Zones: the error is about capacity for one type in one zone, so widening the pool of type and zone combinations lets launches succeed.
X: B=Longer health check grace period: it changes how long a launched instance has before health checks count; it does not help when no instance can be launched at all.
C=Minimum size of zero: it only lowers the floor; the group still cannot launch instances when it needs to scale out.
D=Termination protection: it protects existing instances from scale-in; it does not create capacity for new launches.
T: Capacity errors are specific to an instance type and AZ; diversify types and zones rather than tuning health checks or sizes.

G: ## Response plans in Incident Manager
**AWS Systems Manager Incident Manager** manages an incident from detection to post-incident analysis. The central object is a **response plan**, which defines what happens when an incident starts:
- **Engagement**: which contacts, on-call schedules or escalation plans are paged (SMS, voice, email), with acknowledgement.
- **Runbook**: a Systems Manager Automation document that runs automatically to diagnose or mitigate.
- **Chat channel**: an Amazon Q Developer in chat applications (formerly AWS Chatbot) channel for the responders.
- **Timeline**: Incident Manager records events such as engagements, runbook steps and related alarms, and responders can add notes.
Incidents can be started by CloudWatch alarms, EventBridge events or manually. Afterwards, a **post-incident analysis** uses the timeline.
Availability note: Incident Manager stopped accepting new customers on November 7, 2025; accounts that already use it continue as before. For new accounts AWS points to Systems Manager OpsCenter and AWS Partner paging tools, but the exam still treats response plans as the detection-to-response answer.
## Example
An `API 5xx high` alarm starts the `checkout-outage` response plan: the on-call engineer is paged, a runbook collects diagnostics and restarts unhealthy tasks, and every step appears on the incident timeline.
W: Systems Manager Incident Manager: its response plans combine on-call engagement, automated runbooks and an incident timeline in one service.
X: A=Cognito user pools: they handle sign-up and sign-in for application users, not incident response.
B=Storage Gateway volumes: they give on-premises applications access to AWS storage; they have no incident features.
D=CloudFront distributions: they deliver content from edge locations; they do not page responders or run runbooks.
T: Automated engagement, runbooks and incident timelines together describe Incident Manager response plans.

G: ## When an ALB returns 503
An Application Load Balancer sends requests only to targets registered in the target group, preferring those passing **health checks**.
- If the target group has **no registered targets**, the ALB returns `HTTP 503 Service Unavailable`.
- If targets are registered but all of them are unhealthy, the ALB "fails open" and sends traffic to all of them anyway; if they really are broken, clients usually see `502` or `504` rather than an ALB-generated 503.
During deployments, old targets are **deregistered** (after a deregistration delay for draining) and new ones are registered but count as healthy only after passing the health check. Orchestrators such as ECS and Auto Scaling also deregister and replace targets that fail health checks. If old or failing targets are removed before replacements are registered and healthy, there are windows with no usable targets and clients see 503s.
## Example
A deployment deregisters all old tasks before the new ones pass their health checks. For about 90 seconds the target group has nothing to route to, and the ALB access logs show 503 with target `-`. Keeping a minimum healthy percentage of 100% (new targets healthy before old ones leave) and correct health check settings removes the gap.
W: Failing health checks or deregistration during deployments: targets that fail checks get replaced and deregistered, and deployments remove old targets before new ones are ready, so at those moments the target group has no usable targets and the ALB answers with 503.
X: A=HTTPS listener instead of HTTP: the listener protocol affects how clients connect; it does not empty the target group, and TLS problems fail at connection time rather than as 503s.
C=Versioning on the access logs bucket: it only keeps previous versions of log files; it has no effect on request routing.
D=Short Route 53 alias TTL: it only changes how long resolvers cache the ALB address; the ALB still answers, so it cannot cause zero healthy targets.
T: ALB 503 with zero healthy targets points to the target group (health checks and deployment deregistration), not DNS or logging.

G: ## Cross-account deployment without long-term credentials
Long-term credentials are IAM user access keys and root credentials: they never expire on their own and leak easily. The alternative is **temporary credentials from AWS STS**.
- In the tooling account, the pipeline (for example CodePipeline and CodeBuild) runs with a **service role**.
- Each workload account has a **deployment role** whose trust policy allows that service role (or the tooling account) to call `sts:AssumeRole`.
- The pipeline assumes the target role for each account and receives credentials that expire (by default after one hour). For CodePipeline, the artifact bucket must use a customer managed KMS key that the other accounts can use.
## Example
The role `arn:aws:iam::222233334444:role/deploy` trusts `arn:aws:iam::111122223333:role/pipeline-role`. A CloudFormation deploy action in the pipeline specifies this role, and CloudFormation creates the stack in account 222233334444. The same pattern repeats for all 20 accounts, often rolled out with StackSets.
W: Service role assuming deployment roles through STS: every credential is short-lived and issued on demand, so no access keys exist anywhere in the process.
X: A=IAM user keys in the pipeline: 20 sets of long-term access keys stored in the pipeline are exactly what the company wants to avoid.
B=Shared IAM user with six-month rotation: it is still a long-term key, shared across accounts, so one leak exposes everything for months.
C=Root credentials as pipeline variables: root credentials are the most powerful long-term credentials and must never be used for automation, encrypted or not.
T: No long-term credentials means roles plus STS AssumeRole across accounts, never access keys stored in the pipeline.

G: ## IAM Access Analyzer policy generation
Writing least-privilege policies by hand is hard because you must know every API a workload calls. **IAM Access Analyzer policy generation** builds a policy from what the role actually did:
- You choose an IAM role (for example a Lambda function's execution role), a **CloudTrail trail** and a time range (up to 90 days).
- Access Analyzer reads the CloudTrail events for that role and produces a policy template with the services and actions used (action-level detail for supported services), with placeholders for resources.
- You review and refine it (for example replacing resource placeholders with specific ARNs) and then attach it.
## Example
A new function runs for two weeks with a broad test policy. Policy generation shows it only calls `dynamodb:GetItem`, `dynamodb:PutItem` and `s3:GetObject`; the team scopes those actions to the one table and bucket the function uses and replaces the broad policy.
Unused access findings in Access Analyzer can later reveal permissions that stay unused.
W: Access Analyzer policy generation from CloudTrail: it derives a least-privilege policy from the function's real API activity, which is what the company wants.
X: A=Allow * and rely on SCPs: SCPs set a coarse account-wide ceiling; the function would still have far more access than it uses, the opposite of least privilege.
B=Copying the most permissive policy: it spreads excess permissions to new functions instead of fitting them to actual usage.
D=AdministratorAccess until incidents: it grants full access and only tightens after damage is done.
T: For least privilege based on real usage, generate policies from CloudTrail activity with Access Analyzer, then refine.

G: ## Permissions boundaries for delegated role creation
A **permissions boundary** is a managed policy attached to a user or role that sets the **maximum** permissions it can have. Effective permissions are the intersection of the identity policy and the boundary (and any SCPs), so a role cannot do anything the boundary does not allow, even with `AdministratorAccess` attached.
To let developers create roles safely:
- Give developers `iam:CreateRole` and `iam:PutRolePolicy`/`iam:AttachRolePolicy` only with a condition such as `"iam:PermissionsBoundary": "arn:aws:iam::111122223333:policy/DevBoundary"`.
- Deny changing or removing the boundary (`iam:DeleteRolePermissionsBoundary`, editing the boundary policy itself) so it cannot be escaped.
## Example
A developer creates `app-role` with a policy allowing `*`. Because `DevBoundary` only allows S3, DynamoDB and CloudWatch Logs actions, the role's effective permissions stay limited to those.
W: Require a permissions boundary on created roles: IAM enforces the maximum automatically, so developers keep autonomy but cannot escalate beyond the defined limit.
X: A=Developers' promise: a policy by agreement is not enforced by IAM and does not stop mistakes or abuse.
C=Quarterly manual review: it finds problems up to three months later, after excess permissions could already have been used.
D=Disable IAM for developers: it blocks the requirement that developers create roles for their applications.
T: Delegate role creation with a mandatory permissions boundary: IAM enforces the ceiling, not reviews or promises.
