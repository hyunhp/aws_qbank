# DVA-C02 fixes of published questions (full blocks pinned with I:)

@ DVA-C02 D3 T3.2 advanced troubleshooting
S: A developer's dev stack was deployed with AWS SAM. A teammate later deleted the stack's SQS queue directly in the console instead of changing the template. The next sam deploy only changes that queue's visibility timeout, but the stack update fails because CloudFormation cannot find the queue. What is the underlying cause?
A: The SAM CLI does not support updating existing stacks
B: Drift: resources no longer match CloudFormation's recorded state
C: The associated API Gateway stage was deleted by another deployment
D: The Lambda function has exceeded its reserved concurrency limit
K: B
G: ## What stack drift is
CloudFormation keeps a record of every resource it manages and the properties it last applied. When someone changes or deletes a resource outside CloudFormation (console, CLI, SDK), the real resource no longer matches that record. This is called **drift**.
## Why drift breaks later deployments
CloudFormation plans an update against its recorded state, not against the live account. Here it still believes the queue exists, so it tries to modify the queue's `VisibilityTimeout` on a resource that is gone, and the update fails and rolls back.
- Detect it with **Detect stack drift** (`DetectStackDrift`): the deleted queue shows the drift status `DELETED`.
- Fix it by bringing reality back in line with the template, for example removing the queue from the template and re-adding it, or importing a recreated queue, then redeploy.
- Prevent it by making every change through the template and the pipeline, and by restricting console changes to stack resources.
Example: a manually deleted `OrdersQueue` makes every later `sam deploy` that touches `OrdersQueue` fail until the drift is resolved.
W: Drift: deleting the queue outside CloudFormation means the live resources no longer match what the stack recorded, so an update that tries to modify the recorded queue fails because the queue no longer exists.
X: A=SAM cannot update stacks: `sam deploy` routinely updates existing stacks through CloudFormation change sets; updating is its normal job and not why this one deployment fails.
C=API stage deleted elsewhere: nothing in the scenario involves an API Gateway stage, and the failure names the queue that the teammate deleted by hand in the console.
D=Reserved concurrency exceeded: concurrency limits throttle function invocations at runtime; they have no effect on whether a CloudFormation stack update can modify a queue.
T: Resources changed or deleted outside CloudFormation create drift that breaks later updates; detect it, reconcile the template, and make changes only through IaC.
V: CloudFormation, AWS SAM

@ DVA-C02 D1 T1.1 applied tradeoff
S: An order service publishes messages to Amazon SQS. Orders must be processed in the exact order they were sent, and when a producer retries a send after a network timeout, the identical retried message must not be delivered a second time. The producer already sets a message group ID but cannot be changed to add a deduplication ID to each message. Which SQS configuration meets these requirements?
A: FIFO queue with a maximum message retention period of 14 days
B: FIFO queue with content-based deduplication enabled
C: Standard queue with a short visibility timeout
D: Standard queue with a dead-letter queue configured
K: B
G: ## Standard versus FIFO queues
- A **standard queue** offers nearly unlimited throughput but only best-effort ordering and at-least-once delivery, so messages can arrive out of order and occasionally twice.
- A **FIFO queue** delivers messages in the order they were sent within a message group and removes duplicates, at a lower maximum throughput.
## How FIFO deduplication works
Every message sent to a FIFO queue needs a deduplication ID. SQS drops any later message with the same ID that arrives within the 5-minute deduplication interval. The ID can come from two places:
- The producer sets `MessageDeduplicationId` explicitly on each send.
- The queue has **content-based deduplication** enabled, and SQS uses a SHA-256 hash of the message body as the ID.
If neither is present, `SendMessage` to a FIFO queue fails. Example: a producer times out and resends the same order body 20 seconds later; with content-based deduplication the hash matches and the retry is accepted but not delivered again.
W: FIFO with content-based deduplication: the FIFO queue keeps the send order, and because the producer cannot supply IDs, the body hash becomes the deduplication ID, so an identical retry within 5 minutes is not delivered a second time.
X: A=FIFO with 14-day retention: retention only controls how long unread messages are kept; without content-based deduplication and without producer-supplied IDs, sends to the FIFO queue are rejected outright.
C=Standard with short visibility timeout: a standard queue gives no ordering guarantee, and a short timeout makes duplicate processing more likely because messages reappear before work finishes.
D=Standard with dead-letter queue: a dead-letter queue only collects messages that repeatedly fail processing; it neither orders messages nor removes duplicate sends from retries.
T: Ordered, duplicate-free delivery needs a FIFO queue, and when producers cannot set deduplication IDs, turn on content-based deduplication.
V: Amazon SQS

@ DVA-C02 D4 T4.3 applied troubleshooting
S: A Lambda function that processes orders begins returning TooManyRequestsException (HTTP 429) errors to synchronous callers during a traffic spike, even though the account-level concurrent execution limit has not been reached. The function's Throttles metric in CloudWatch is increasing. What is the most likely cause?
A: Reserved concurrency is set below current demand
B: The function's memory allocation is set too high
C: The function uses an unsupported runtime version
D: The execution role is missing a required permission
K: A
G: ## Where Lambda throttling comes from
Lambda throttles an invocation when there is no concurrency available for it. That can happen at two levels:
- **Account level**: all functions in the Region together exceed the account concurrency quota.
- **Function level**: the function has **reserved concurrency** configured, and that value is a hard ceiling. With reserved concurrency of 20, the 21st simultaneous request is throttled even if the account has hundreds of unused executions.
## Reading the metrics and errors
The function's `Throttles` metric counts rejected invocations. Comparing `ConcurrentExecutions` for the function with its reserved concurrency shows whether it hits its own cap. Synchronous callers receive `TooManyRequestsException` (HTTP 429); for asynchronous invocations and event source mappings, Lambda retries instead.
Example: an order function reserved at 20 handles normal load, but a sale pushes demand to 60 concurrent requests, so two thirds of the spike is throttled while the account total is far below its limit.
W: Reserved concurrency below demand: reserved concurrency is also the maximum the function can scale to. When the spike needs more concurrent executions than that value, Lambda rejects the extra requests with 429 errors and the `Throttles` metric rises while the account limit is unused. Raise or remove the setting.
X: B=Memory set too high: memory affects cost per millisecond and CPU share, not how many concurrent executions are allowed, so a large memory size does not produce 429 throttling errors.
C=Unsupported runtime: runtime deprecation affects whether the function can be created or updated, and a broken runtime shows up as invocation errors, not a throttle count rising with traffic.
D=Missing execution role permission: a missing permission makes the function's own SDK calls fail with access denied inside the code; Lambda still starts the invocation, so `Throttles` would not rise.
T: Throttling while the account limit is unused points to the function's own reserved concurrency cap, not to memory, runtime or IAM.
V: Lambda, CloudWatch

@ DVA-C02 D2 T2.3 advanced use-case
S: A developer wants to scan code for hardcoded credentials and security issues during development. Which tool helps?
A: AWS Budgets alerts configured for spending in the development account
B: Amazon Q Developer security scans or Amazon Inspector code security
C: Amazon CloudWatch dashboards for the running application's metrics
D: AWS Trusted Advisor cost optimization checks run across the whole account
K: B
G: ## Static security scanning of code
Some security problems are visible in the source itself: hardcoded AWS keys or passwords, SQL injection, insecure cryptography, or overly permissive settings in infrastructure code. **Static application security testing (SAST)** and secrets detection tools read the code and flag these before deployment.
On AWS:
- **Amazon Q Developer** runs code reviews and security scans from the IDE, detecting hardcoded credentials and vulnerabilities and suggesting fixes.
- **Amazon Inspector code security** connects to source repositories such as GitHub and GitLab and scans application code, dependencies and infrastructure as code for vulnerabilities and exposed secrets, including on pull requests.
- Amazon CodeGuru Security once filled this role, but AWS ended support for it on November 20, 2025 and points users to the two services above.
Run scans early (in the IDE and in CI) so issues are fixed before code is merged. Any secret that was committed should be rotated and moved to AWS Secrets Manager.
W: Q Developer or Inspector code security: both scan source code for hardcoded secrets and security flaws during development, in the IDE and in repositories, which is exactly the need described.
X: A=AWS Budgets alerts: Budgets notify when spending or usage crosses a threshold you define; they never read or analyze application source code for secrets.
C=CloudWatch dashboards: dashboards visualize runtime metrics and logs of a running application; they cannot find credentials written into source files.
D=Trusted Advisor cost checks: these review deployed account resources for savings opportunities, not the contents of application code or repositories.
T: Finding secrets and vulnerabilities in code is a code scanning job for Amazon Q Developer or Amazon Inspector code security, not a cost or monitoring tool.
V: Amazon Q Developer, Amazon Inspector

@ DVA-C02 D1 T1.1 applied use-case
S: An application must send messages that are several megabytes in size through Amazon SQS. Which approach fits?
A: Store payloads in S3 and send references using the SQS Extended Client Library
B: Increase the queue's message size limit to 2 GB in the queue settings
C: Compress every message with a custom algorithm on each producer
D: Split the message into many small unordered messages without any tracking
K: A
G: ## SQS message size limits
Each queue has a maximum message size (the `MaximumMessageSize` attribute). The service maximum was 256 KB for many years and is now 1 MiB, so a queue can accept payloads up to 1 MiB, but a message of several megabytes still does not fit, and payloads with no fixed upper bound need a different approach.
## The claim-check pattern
For payloads that do not fit, store the data elsewhere and send only a reference:
- The producer writes the payload to S3, for example `s3://orders-payloads/2026/09/29/abc.json`.
- It sends a small SQS message containing the bucket and key.
- The consumer receives the message, reads the object from S3 and processes it.
## SQS Extended Client Library
AWS provides this pattern as a library (for example for Java and Python). Above a size threshold it uploads the body to S3 and sends a pointer; the receiving side fetches it transparently and can delete the S3 object when the message is deleted. Payloads up to 2 GB are supported.
W: S3 plus the Extended Client Library: the multi-megabyte payload is stored in S3 and only a small pointer travels through SQS, so the queue's 1 MiB message limit no longer matters and no custom storage code is needed.
X: B=Raise the queue limit to 2 GB: `MaximumMessageSize` can only be set up to the service maximum of 1 MiB; no queue setting allows messages of several megabytes or gigabytes.
C=Custom compression: compression ratios depend on the data, so some payloads will still exceed the limit, and every producer and consumer must share and maintain the custom code.
D=Split without tracking: without sequence numbers and a reassembly step, consumers cannot tell which pieces belong together or whether any are missing, and standard queues do not preserve order.
T: For SQS payloads beyond the 1 MiB message limit, store the data in S3 and send a pointer, which the Extended Client Library automates.
V: Amazon SQS, Amazon S3
