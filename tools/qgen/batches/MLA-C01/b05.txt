@ MLA-C01 D1 T1.1 advanced tradeoff
S: A SageMaker Feature Store feature group ingests about 20,000 small records per minute. Its offline store in S3 now holds millions of tiny files, and Athena queries that build weekly training sets have become slow and expensive. The team is creating a replacement feature group. Which configuration addresses the root cause?
A: Create the new feature group with the Apache Iceberg table format for the offline store and run periodic compaction on it
B: Disable the offline store on the new feature group and build training sets by calling GetRecord on the online store for every customer
C: Keep the default Glue table format and raise the Athena workgroup's per-query data scan limit so the weekly queries are not cancelled
D: Move the offline store bucket to S3 Glacier Flexible Retrieval so the growing number of small files costs less to keep over time
K: A
G: ## Why many small files hurt queries
Feature Store writes online-store records to the offline store in S3 in small batches. At high ingest rates this creates a very large number of small Parquet files. Athena and Spark pay a fixed cost per file (listing, opening, reading footers), so query time and cost grow with file count, not only with data size.
## Offline store table formats
When you create a feature group you choose the offline store table format:
- `Glue` (default): plain Parquet files registered in the AWS Glue Data Catalog.
- `Iceberg`: the same data managed as an Apache Iceberg table. Iceberg tracks files in metadata, so engines plan queries without listing every object, and you can compact small files into larger ones (for example with Athena `OPTIMIZE ... REWRITE DATA USING BIN_PACK`) and remove old snapshots.
The format is set when the feature group is created, which is why the team builds a replacement.
Example: `OfflineStoreConfig={"S3StorageConfig": {...}, "TableFormat": "Iceberg"}`.
W: Iceberg offline store with compaction: Iceberg metadata avoids expensive S3 listing, and compaction merges the tiny files into larger ones, which directly fixes the slow, costly scans.
X: B=GetRecord on the online store: the online store keeps only the latest value per record, so it cannot give historical, point-in-time training data, and millions of API calls are slower and costlier than one query.
C=Raise the scan limit: a higher limit only stops queries from being cancelled. The same millions of files are still listed and opened, so the queries stay slow and expensive.
D=Glacier Flexible Retrieval: archived objects cannot be read by Athena without a restore, and the storage class does nothing about the per-file overhead that causes the slowness.
T: Small-file overhead in the offline store is fixed by the Iceberg table format plus compaction, not by bigger query limits or colder storage.
V: Amazon SageMaker Feature Store, Amazon Athena, Apache Iceberg

@ MLA-C01 D1 T1.1 advanced troubleshooting
S: A churn model uses features from SageMaker Feature Store. Validation AUC is 0.95, but production AUC is 0.74. The training set was built by joining each labeled churn event with the most recent feature values currently in the offline store, regardless of when those values were written. What should the team change?
A: Build the training set with a point-in-time join that uses only feature records whose event time is at or before each label's timestamp
B: Build the training set from the online store instead, because it always returns the freshest feature values for every customer record
C: Increase the number of validation folds so that the reported validation AUC becomes a more stable estimate of production performance
D: Add more trees and a larger maximum depth to the model so it can learn the production patterns that the current version is missing
K: A
G: ## What point-in-time correctness means
Each training example should look exactly like what the model would have seen at prediction time. If a label is dated 1 March, its features must come from records written on or before 1 March.
Joining with the latest values leaks the future: a customer who churned in March may have `days_since_last_login = 60` written in May. The model learns from information it will never have in production, so validation scores look great and live scores drop.
## How Feature Store supports it
Every record in a feature group has an `EventTime`. The offline store keeps all versions, so you can join each label to the newest feature row whose event time is not later than the label's timestamp. The SageMaker Python SDK dataset builder does this with `point_in_time_accurate_join()`, or you write the equivalent Athena query.
W: Point-in-time join: restricting each label to features that existed at the label's time removes the future information that inflated validation AUC.
X: B=Online store: it holds only the latest value per record, which is the same leakage problem in a worse form, and it has no history to rebuild past examples.
C=More validation folds: every fold is drawn from the same leaked dataset, so cross-validation will keep reporting the same inflated score.
D=Bigger model: the gap comes from leaked features, not from underfitting. A larger model would exploit the leak even more and widen the gap.
T: A validation-to-production gap after joining "latest" features points to time leakage; fix it with a point-in-time join on event time.
V: Amazon SageMaker Feature Store, Amazon Athena

@ MLA-C01 D1 T1.1 applied troubleshooting
S: A SageMaker Processing job with 40 instances writes millions of small feature files to one S3 prefix, `s3://ml-feat/out/`. The job intermittently fails with `503 Slow Down` errors. Which change is MOST likely to fix the errors?
A: Spread the output across many prefixes, for example with a hash component in each key, and let writers retry with backoff
B: Turn on S3 Transfer Acceleration for the bucket so the processing instances upload their files through the nearest edge locations
C: Enable S3 Versioning on the bucket so concurrent writes to the same prefix are stored as separate object versions without conflicts
D: Switch the bucket's default encryption from SSE-S3 to SSE-KMS so each write is authorized by a dedicated customer managed key
K: A
G: ## S3 request rates are per prefix
Amazon S3 scales automatically, but each partitioned prefix supports about 3,500 PUT/COPY/POST/DELETE and 5,500 GET/HEAD requests per second. When a burst of writers targets a single prefix faster than S3 can scale it, S3 answers with HTTP `503 Slow Down`.
## How to spread the load
- Use more prefixes, for example `out/part=17/...` or a short hash of the file name at the start of the key. Throughput adds up across prefixes.
- Retry with exponential backoff; the AWS SDKs do this by default, and S3 keeps scaling while clients back off.
- Write fewer, larger files where possible (for example 128 MB Parquet parts instead of thousands of tiny ones).
Example: 40 instances each writing 150 small files per second is 6,000 PUTs per second, well above one prefix's baseline.
W: Many prefixes plus retries: request limits apply per prefix, so spreading keys multiplies the available write rate and backoff absorbs short bursts.
X: B=Transfer Acceleration: it speeds long-distance uploads over the internet. The instances are in the same Region, and the limit hit here is request rate per prefix, not network distance.
C=Versioning: versioning keeps old copies of overwritten objects. It does not raise request limits and adds storage cost for every write.
D=SSE-KMS: every write would also call AWS KMS, which has its own request quotas, so this adds another throttling point instead of removing one.
T: `503 Slow Down` means too many requests on one prefix; spread keys across prefixes and retry, instead of changing encryption or transfer paths.
V: Amazon S3, Amazon SageMaker Processing

A: Nightly AWS Glue ETL jobs that read the Aurora tables over JDBC and load the transformed rows into Redshift with a COPY command

@ MLA-C01 D1 T1.1 advanced troubleshooting
S: A Kinesis data stream with 8 provisioned shards feeds a real-time feature pipeline. Producers get `ProvisionedThroughputExceededException`, yet CloudWatch shows one shard at its write limit while the other seven are nearly idle. Producers use the store ID as the partition key, and one flagship store generates most events. What is the BEST fix?
A: Add eight more shards with UpdateShardCount so the stream's total write capacity doubles from 8 MB/s to 16 MB/s
B: Increase the data retention period from 24 hours to 7 days so that throttled records can be accepted and written again later on
C: Use a higher-cardinality partition key, such as store ID plus a random suffix, so records spread across all shards
D: Switch the consumers to enhanced fan-out so each consumer gets its own 2 MB/s of read throughput for every shard
K: C
G: ## How Kinesis places records
Each record's partition key is hashed with MD5, and the hash decides which shard receives it. All records with the same key go to the same shard. Each shard accepts up to 1 MB/s or 1,000 records/s of writes.
If one key dominates the traffic, its shard hits the limit even though the stream as a whole has spare capacity. This is a **hot shard**.
## Fixing a hot shard
- Choose a partition key with many distinct, evenly used values, for example an event ID, or `storeId#<random 0-9>` when related records do not need strict ordering.
- Adding shards only helps if the keys spread evenly; one key still maps to one shard.
- On-demand capacity mode also scales total throughput, but it has the same per-shard, per-key behavior.
W: Higher-cardinality partition key: spreading records across many hash values uses all eight shards and removes the single-shard bottleneck.
X: A=Add eight shards: the flagship store's key still hashes to exactly one shard, so that shard stays at 1 MB/s and keeps throttling while the new shards sit idle.
B=Longer retention: retention controls how long written records stay readable. It does nothing for writes that are rejected before they reach the stream.
D=Enhanced fan-out: it adds dedicated read throughput for consumers. The exception here is on the write side.
T: One busy shard among idle ones is a partition-key problem; fix the key distribution, because adding shards or read capacity does not move a hot key.
V: Amazon Kinesis Data Streams, Amazon CloudWatch

@ MLA-C01 D1 T1.2 applied use-case
S: A neural network predicts hourly ride demand. The raw feature `hour_of_day` is an integer from 0 to 23, and the model treats 23:00 and 00:00 as far apart even though demand is similar. Which feature engineering step fits BEST?
A: One-hot encode `hour_of_day` into 24 binary columns so each hour becomes an independent category the network can weigh separately
B: Min-max scale `hour_of_day` to the range 0 to 1 so the feature has the same scale as the other numeric inputs of the network
C: Bin `hour_of_day` into four six-hour buckets (night, morning, afternoon, evening) and encode each bucket as an ordinal integer
D: Replace `hour_of_day` with two features, `sin(2*pi*hour/24)` and `cos(2*pi*hour/24)`, so the hours lie on a circle
K: D
G: ## Cyclical features
Some features wrap around: hour of day, day of week, month, compass direction. As plain integers, 23 and 0 are 23 units apart, but in reality they are neighbours. Models that use distances or smooth functions (linear models, neural networks, k-NN) then learn a false jump at midnight.
## Sine and cosine encoding
Map the value onto a circle with two features:
- `hour_sin = sin(2*pi*hour/24)`
- `hour_cos = cos(2*pi*hour/24)`
Now 23:00 and 00:00 are close in the two-dimensional space, and the distance between any two hours reflects how far apart they really are on the clock. Both features are needed: sine alone gives the same value (about 0.71) for 03:00 and 09:00, and cosine separates them.
Tree models are less affected, but for neural networks this encoding usually helps.
W: Sine and cosine encoding: placing hours on a circle makes 23:00 and 00:00 close neighbours, so the network sees the real cyclical similarity.
X: A=One-hot encoding: every hour becomes an unrelated category, so the model loses the fact that neighbouring hours are similar and must learn 24 separate effects.
B=Min-max scaling: scaling changes the range, not the order, so 23:00 maps to about 1.0 and 00:00 to 0.0, still the two furthest points.
C=Ordinal buckets: coarse bins throw away detail, and the ordinal code still puts the last bucket and the first bucket at opposite ends.
T: For values that wrap around, encode with sine and cosine; scaling, bins and one-hot do not make the ends of the cycle neighbours.
V: Amazon SageMaker

@ MLA-C01 D1 T1.2 applied comparison
S: A linear regression model uses `annual_income`, which is strongly right-skewed (most values between 30,000 and 90,000, a long tail up to 20 million). The residuals are large and uneven. Which TWO transformations reduce the skew of this feature? (Select TWO)
A: A log transform such as `log1p(annual_income)`
B: Min-max scaling of `annual_income` to the range 0 to 1
C: A Box-Cox or Yeo-Johnson power transform
D: Standardization of `annual_income` to zero mean and unit variance
E: One-hot encoding of every distinct `annual_income` value
K: A,C
G: ## Skewed features and linear models
A right-skewed feature has most values bunched at the low end and a long tail of very large values. A linear model fits one slope for the whole range, so the tail dominates the fit and the residuals grow with income.
## Shape-changing versus scale-changing transforms
- **Log transform** (`log1p(x) = log(1 + x)`) compresses large values much more than small ones. 30,000 and 20,000,000 become about 10.3 and 16.8.
- **Power transforms**: Box-Cox (positive values only) and Yeo-Johnson (also handles zero and negatives) search for the exponent that makes the distribution most normal-like. scikit-learn exposes both in `PowerTransformer`.
- **Min-max scaling and standardization** are linear: they shift and stretch values but keep the shape exactly the same, so a skewed feature stays just as skewed.
W: A=Log transform: `log1p` compresses large values far more than small ones, pulling in the long income tail so the feature becomes much more symmetric for the linear model.
C=Box-Cox or Yeo-Johnson power transform: it is non-linear and fits the exponent that makes the distribution most normal-like, which reduces the skew instead of only rescaling it.
X: B=Min-max scaling: it is a linear rescale, so the tail keeps the same relative shape, now squeezed between 0 and 1.
D=Standardization: it also only shifts and rescales, so the skew value is unchanged.
E=One-hot of each value: thousands of sparse columns remove the numeric order and make the linear model overfit, without addressing skew.
T: To reduce skew use non-linear transforms such as log or Box-Cox/Yeo-Johnson; min-max and z-score scaling change the scale, not the shape.
V: Amazon SageMaker

@ MLA-C01 D1 T1.2 advanced troubleshooting
S: A gradient boosting model forecasts next-day sales per store. The engineer added a feature `rolling_mean_7d`, computed as the average of sales over a centered 7-day window (3 days before, the day itself, and 3 days after). Offline error dropped sharply, but live forecasts are poor. What is the MOST likely cause and fix?
A: The window is too short to capture weekly seasonality; widen it to a centered 28-day window so the model sees monthly patterns
B: Gradient boosting cannot use rolling features; replace the model with an LSTM that learns the temporal averages by itself
C: The window uses future sales; compute the rolling mean only over days before the forecast date, for example the 7 days ending yesterday
D: The feature is not scaled; standardize `rolling_mean_7d` with the training mean and standard deviation before training the model
K: C
G: ## Lag and rolling features must look backwards
Time series features describe the past relative to the moment of prediction. A lag feature `sales_lag_1` is yesterday's sales. A rolling feature such as `rolling_mean_7d` should be the mean of the 7 days that end before the forecast date.
A centered window includes days after the target date. When forecasting tomorrow, those days have not happened yet, so the feature cannot be computed in production. Offline, it quietly hands the model part of the answer: this is target leakage through time.
## Safe construction
- Sort by store and date, then `shift(1)` before `rolling(7).mean()` in pandas, so the window ends yesterday.
- Split train and validation by time, not randomly.
- Rebuild the feature exactly the same way in the inference pipeline.
W: Backward-looking window: a centered window leaks future sales, which explains the great offline score and the poor live forecasts. Using only past days removes the leak.
X: A=Wider centered window: it looks even further into the future and makes the leak larger, not smaller.
B=Switch to LSTM: gradient boosting uses rolling features very well; the problem is what the feature contains, and an LSTM fed the same leaked input would fail the same way.
D=Scaling: tree-based gradient boosting splits on thresholds and is insensitive to feature scale, and scaling does not remove future information.
T: Rolling and lag features must use only data available before the prediction time; centered windows leak the future.
V: Amazon SageMaker

@ MLA-C01 D1 T1.3 advanced use-case
S: A dataset for a claim-fraud model has 1.2 million rows from 90,000 customers; each customer appears in many rows, and only 2% of rows are fraud. The team must build train and validation sets that give a trustworthy estimate on new customers. Which TWO practices should they apply? (Select TWO)
A: Split by customer ID so that all rows of a customer fall into either the training set or the validation set
B: Keep the fraud rate about the same in each split by stratifying on the label while grouping by customer
C: Oversample the fraud rows with SMOTE on the full dataset first and then split the result randomly into train and validation
D: Shuffle all 1.2 million rows and assign 80% to training and 20% to validation at the row level for maximum randomness
E: Compute standardization statistics on the full dataset before splitting so that both sets share identical scaling
K: A,B
G: ## Group leakage
When one entity (customer, patient, device) contributes many rows, those rows share patterns. A random row-level split puts some of a customer's rows in training and others in validation, so the model partly "recognises" validation customers. Scores look better than they will be on truly new customers.
Fix: split by the group key, for example with scikit-learn `GroupShuffleSplit` or `GroupKFold` on `customer_id`.
## Keeping rare classes represented
With 2% fraud, a random split can leave one fold with noticeably fewer positives. Stratification keeps the label ratio similar in every split. `StratifiedGroupKFold` does both: groups stay intact and the fraud rate stays balanced.
## Order of operations
Resampling (such as SMOTE) and fitting scalers must happen after the split and only on training data; otherwise validation information leaks into training.
W: A=Split by customer ID: keeping all rows of a customer on one side of the split measures performance on truly unseen customers and prevents group leakage.
B=Stratify while grouping: keeping the 2% fraud rate similar in every split leaves enough fraud cases in each for stable metrics, while customer groups stay intact.
X: C=SMOTE before splitting: synthetic points are interpolated from real fraud rows, so near-copies of training examples land in validation and inflate the scores.
D=Row-level shuffle: rows of the same customer end up on both sides of the split, which is exactly the group leakage to avoid.
E=Statistics on full data: fitting the scaler on all rows leaks validation information into training; fit on the training split only.
T: Many rows per entity → split by entity; rare labels → stratify; and do resampling and scaling only after the split.
V: Amazon SageMaker

@ MLA-C01 D1 T1.3 applied use-case
S: An image classifier trained on 6,000 product photos reaches 99% training accuracy but 78% validation accuracy. Collecting more photos will take months. Which data preparation step is MOST appropriate to reduce overfitting?
A: Apply random flips, crops, rotations and color jitter to the training images during each epoch, and keep validation images unchanged
B: Apply the same random flips, crops, rotations and color jitter to both training and validation images before splitting the data
C: Duplicate each training image five times on disk so the model sees more examples of every product during each training epoch
D: Remove the validation set and train on all 6,000 images so the model learns from more examples of every product it must recognize
K: A
G: ## Why the model overfits
99% on training data but 78% on validation data means the model memorises details of the specific training photos (exact position, lighting, background) instead of learning the product itself. More varied data is the usual cure.
## Data augmentation
Augmentation creates new, realistic variations of training images on the fly: horizontal flips, random crops, small rotations, brightness and color changes. Each epoch the model sees slightly different versions, so it must learn features that survive those changes.
Rules that keep the evaluation honest:
- Augment only the training data; validation and test images stay as they are, so they still reflect real inputs.
- Split before augmenting, so variants of one photo never appear on both sides.
- Pick transforms that keep the label valid (a vertical flip may not suit text or digits).
W: Training-only augmentation: random transforms add realistic variety and reduce memorisation, while untouched validation images keep the measurement honest.
X: B=Augment before splitting: variants of the same photo end up in both sets, so validation accuracy is inflated by near-duplicates of training images.
C=Duplicate images: identical copies add no new information, so the model memorises the same pixels even harder.
D=Drop the validation set: the model gets marginally more data, but the team loses the only way to detect overfitting.
T: Overfitting on a small image set → augment the training images only; duplicating data or augmenting validation data gives false confidence.

G: ## How built-in XGBoost reads CSV
The SageMaker built-in XGBoost algorithm accepts CSV (`text/csv`), LIBSVM, Parquet and RecordIO-protobuf. For CSV it assumes:
- The **target is the first column**.
- There is **no header row**.
The algorithm does not look at column names. If the label is last, XGBoost treats the first feature as the label and the real label as a feature. A header row adds a bad first record as well. Training still "succeeds", so the mistake only shows up as nonsense metrics.
## Preparing the file
In pandas: `df[["defaulted"] + features].to_csv("train.csv", header=False, index=False)`. Do the same for the validation channel, and make sure the inference payload contains only the feature columns in the same order.
W: Label first, no header: that is the CSV layout the built-in XGBoost algorithm expects, so it trains on the right target.
X: A=JSON Lines: built-in XGBoost reads CSV natively, and JSON Lines is not one of its training input formats.
C=Second header row: the algorithm reads no header at all; an extra header only adds another bad record.
D=Wrong content type: declaring gzip-compressed CSV as Parquet makes the job fail to parse the input, and the label is still in the wrong column.
T: Built-in XGBoost CSV input = label in the first column, no header; the algorithm never uses column names.

@ MLA-C01 D3 T3.1 advanced troubleshooting
S: A SageMaker batch transform job reads input files of about 2 GB each, where every line is one CSV record. The job fails with errors that the request payload is too large. Which configuration change fixes this?
A: Increase `MaxPayloadInMB` to 2048 so each whole 2 GB file can be sent to the model container as one single request
B: Set `SplitType` to `None` and `BatchStrategy` to `SingleRecord` so each file is processed by the container as a single record
C: Increase the instance count of the transform job so that each instance receives a smaller share of the 2 GB files
D: Set `SplitType` to `Line` and `BatchStrategy` to `MultiRecord` so the file is split into mini-batches under `MaxPayloadInMB`
K: D
G: ## How batch transform sends data to the model
A batch transform job reads objects from S3 and sends them to the model container over HTTP, like calls to `/invocations`. Three settings control the size of each request:
- `SplitType`: how to cut an input object into records. `None` sends the whole object; `Line` splits on newlines; `RecordIO` and `TFRecord` split binary formats.
- `BatchStrategy`: `SingleRecord` sends one record per request; `MultiRecord` packs as many records as fit.
- `MaxPayloadInMB`: the maximum size of one request, with an upper limit of 100 MB.
With `SplitType=None`, a 2 GB file is one request, which exceeds any allowed payload.
## Fix
`SplitType="Line"`, `BatchStrategy="MultiRecord"`, `MaxPayloadInMB=6` sends many small mini-batches. `AssembleWith="Line"` stitches the outputs back into one result file per input.
W: Line splitting with MultiRecord: the job cuts each file into line-based mini-batches that fit under the payload limit, so no single request is too large.
X: A=MaxPayloadInMB of 2048: the parameter is capped at 100 MB, so a whole 2 GB file can never be one request.
B=SplitType None with SingleRecord: without splitting, the whole file is still the one record, so the request is still 2 GB.
C=More instances: files are distributed between instances, but each file is still sent unsplit, so every request stays too large.
T: Large files in batch transform must be split (`SplitType=Line`) into mini-batches; the payload limit cannot be raised to fit a whole file.

@ MLA-C01 D3 T3.2 applied tradeoff
S: An endpoint uses target tracking on invocations per instance with 2 to 12 instances. Every weekday at 08:00 traffic jumps fivefold within a few minutes, and for the first 10 minutes latency breaches the SLA while new instances start. Which change is MOST effective?
A: Lower the target value of the tracking policy so scaling reacts to smaller increases in the invocations per instance
B: Remove the maximum capacity limit from the scalable target so the endpoint can add as many instances as it needs

Target tracking reacts to metrics after the load has arrived: CloudWatch alarms need data points, then new ML instances must launch, pull the container and load the model. For a sudden, large jump this can take many minutes, and the first users feel it.

For most cross-account access in AWS, both sides must agree:

@ MLA-C01 D3 T3.3 advanced tradeoff
S: A large model runs on a real-time endpoint with 16 GPU instances. The team wants guarded updates with automatic rollback on CloudWatch alarms, but the account's GPU quota cannot fit a second full fleet during the update. Which deployment option fits BEST?
A: A blue/green update with all-at-once traffic shifting, because it provisions the new fleet and switches traffic in a single step
B: A blue/green update with canary traffic shifting that sends 10% of traffic to a full new fleet before the remaining 90% moves
C: Deleting the endpoint and creating a new one with the updated model, followed by a manual check of the CloudWatch alarms
D: A rolling deployment that replaces instances in small batches, with alarms that trigger an automatic rollback if they fire
K: D
G: ## Deployment guardrails for SageMaker endpoints
When you update an endpoint, SageMaker can apply guardrails with automatic rollback on CloudWatch alarms.
- **Blue/green** (all at once, canary, or linear shifting): SageMaker provisions a complete new (green) fleet next to the old (blue) one, shifts traffic, and then removes the old fleet. For a moment you run both fleets, so you need roughly double the capacity.
- **Rolling deployment**: SageMaker updates the fleet in batches. You set `MaximumBatchSize` (for example 4 instances or 25%), `WaitIntervalInSeconds` to watch alarms between batches, and `RollbackMaximumBatchSize`. Only one batch of extra capacity is needed at a time.
## When to pick rolling
Large models on scarce or expensive GPU instances often cannot get a second full fleet. Rolling updates trade a slower rollout for a much smaller extra capacity need, and still roll back automatically.
W: Rolling deployment: it needs only one batch of spare GPU capacity at a time and still watches alarms and rolls back automatically, which fits the quota limit.
X: A=Blue/green all at once: it still provisions a complete new fleet before switching, which the GPU quota cannot fit.
B=Blue/green canary: only 10% of traffic goes to the new fleet at first, but the new fleet is still provisioned at full size.
C=Delete and recreate: it causes downtime and has no automatic rollback, so failures reach users.
T: Blue/green needs a full second fleet; rolling deployment updates in batches with rollback when capacity is limited.
V: Amazon SageMaker, Amazon CloudWatch
