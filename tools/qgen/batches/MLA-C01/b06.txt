@ MLA-C01 D2 T2.1 applied tradeoff
S: A company wants an internal assistant on Amazon Bedrock that answers employee questions from 40,000 policy documents. About 200 documents change every day, answers must cite the source document, and the team has no labeled question-answer pairs. Which approach fits BEST?
A: Fine-tune a Bedrock foundation model every night on the full document set so that the model memorizes the newest policy wording
B: Run continued pre-training every week on the changed documents so the model absorbs the new policy text before users ask about it
C: Create an Amazon Bedrock knowledge base over the documents and answer with retrieval-augmented generation that returns citations
D: Paste as many complete policy documents as fit into every prompt so the model can read the relevant text directly for each question
K: C
G: ## Two ways to give a model company knowledge
- **Customization** (fine-tuning or continued pre-training) changes the model's weights. It is good for style, tone and task format, but facts learned this way are frozen at training time, cannot be traced back to a source, and every refresh is a new training job.
- **Retrieval-augmented generation (RAG)** leaves the model unchanged. At question time, relevant passages are retrieved from an index and inserted into the prompt, so the answer is based on the current text.
## Amazon Bedrock Knowledge Bases
A knowledge base connects a data source such as an S3 bucket, splits documents into chunks, creates embeddings and stores them in a vector store. A sync job picks up added or changed documents. The `RetrieveAndGenerate` API returns the answer plus citations that point to the source chunks.
Example: a policy changes on Monday, the sync runs, and the next answer quotes the new wording with a link to that document.
W: Knowledge base with RAG: daily changes are handled by syncing the data source instead of retraining, answers come with citations to the retrieved documents, and no labeled training data is needed.
X: A=Nightly fine-tuning: fine-tuning needs labeled prompt-response pairs, which the team does not have, it does not produce citations, and retraining every night is slow and costly.
B=Weekly continued pre-training: the model would be up to a week out of date, it still cannot say which document a fact came from, and each run is an expensive training job.
D=Stuffing whole documents into prompts: only a tiny fraction of 40,000 documents fits in a context window, so without retrieval the model usually sees the wrong ones, and very long prompts are slow and costly.
T: Frequently changing facts that need citations call for RAG with a knowledge base; fine-tuning changes behavior, not up-to-date, traceable knowledge.
V: Amazon Bedrock, Amazon Bedrock Knowledge Bases, Amazon S3

@ MLA-C01 D2 T2.1 applied use-case
S: An online bank wants to flag logins where a customer account signs in from an IP address that is unusual for that particular account. It has 18 months of login logs with account IDs and IPv4 addresses but no labeled fraud examples. Which SageMaker built-in algorithm fits BEST?
A: IP Insights, trained on account ID and IP address pairs to score how unusual each new pairing is
B: Random Cut Forest, trained on the IPv4 addresses converted to integers to find outlying address values
C: XGBoost, trained as a binary classifier on the login logs to predict which sign-ins are fraudulent ones
D: K-means, trained on the IPv4 octets to group addresses and flag logins that fall into the small clusters
K: A
G: ## Anomalies that depend on who, not only on what
A login from `203.0.113.7` is normal for one customer who always uses it and suspicious for another who has never used that network. The signal is the **pairing** of an entity and an IP address, not the address on its own.
## SageMaker IP Insights
IP Insights is an unsupervised built-in algorithm that learns vector representations of entities (account IDs, user names) and IPv4 addresses from historical pairs.
- Training input: CSV rows of `entity_id, ip_address`, with no labels.
- At inference, it returns a score for each pair that indicates how well the address fits the entity's history, so unusual pairings stand out from normal ones.
- It generates negative samples during training by pairing entities with random addresses, so no fraud labels are required.
Typical uses: account takeover detection, triggering MFA, or flagging suspicious API key use.
W: IP Insights: it is designed for exactly this problem, learning which IP addresses belong with which accounts from unlabeled history and scoring each new account-IP pair.
X: B=Random Cut Forest on IP integers: it finds unusual values in the data as a whole, ignoring which account made the login, and numeric distance between addresses has no meaning for network ownership.
C=XGBoost classifier: supervised learning needs labeled fraud and non-fraud examples, which the bank does not have.
D=K-means on octets: clustering addresses by octet values ignores the account, so a rare-but-legitimate network is flagged for everyone and a common network is never flagged for anyone.
T: Unusual entity-to-IP pairings without labels point to IP Insights; Random Cut Forest looks for outliers in the values alone.
V: Amazon SageMaker

Amazon Comprehend's standard entity detection does not return these as distinct types. The team has lists of known part numbers and codes but no ML engineers. Which option fits BEST?
A: Amazon Comprehend topic modeling run on the notes so that part numbers and failure codes are grouped together into their own topics
B: Amazon Comprehend custom entity recognition trained with the existing entity lists for the part numbers and the failure codes
C: Amazon Textract with Queries that ask for the part number and failure code in each note that has been stored as a plain text file

@ MLA-C01 D2 T2.2 applied troubleshooting
S: A SageMaker hyperparameter tuning job runs a custom PyTorch script. Every training job completes, but the tuning job shows no objective metric values. The metric definition uses the regex `val_loss=([0-9\.]+)`, and the script's log lines look like `epoch 5 validation loss: 0.2310`. What should the engineer do?
A: Change the tuning strategy from Bayesian to random search so that the objective metric does not need to be read from the logs
B: Enable SageMaker Debugger on the training jobs so that it collects the validation loss tensors and passes them to the tuner
C: Increase MaxRuntimeInSeconds for each training job so the script has enough time to write its final validation metric line
D: Fix the metric definition regex, or the script's log format, so the regex matches the validation loss lines the script prints
K: D
G: ## How SageMaker finds your metrics
For training scripts that you write yourself, SageMaker does not know what "validation loss" is. It reads the job's log stream in CloudWatch Logs and applies each `MetricDefinitions` entry, a name plus a regular expression with one capture group.
- Every log line that matches produces a data point for that metric name.
- A hyperparameter tuning job reads its objective metric from exactly one of these definitions.
If the regex never matches, the metric is empty, and the tuner has nothing to compare between jobs.
## Example
Log line: `epoch 5 validation loss: 0.2310`
Working definition: `{"Name": "validation:loss", "Regex": "validation loss: ([0-9\\.]+)"}`
The regex `val_loss=([0-9\.]+)` expects different text, so it never matches.
W: Fix the regex or log format: the objective metric is parsed from the logs with the metric definition regex, so making the pattern match the printed line gives the tuner its values.
X: A=Random search: every tuning strategy, including random search, still needs the objective metric to rank the training jobs and report the best one.
B=Debugger: Debugger saves tensors for analysis and rules; it does not feed values to the tuner's objective metric, which comes from the metric definitions.
C=Longer runtime: the jobs already complete and print the loss lines. The problem is that the pattern does not match them, not that they are missing.
T: An empty objective metric in a tuning job usually means the metric definition regex does not match the script's log lines.
V: Amazon SageMaker, Amazon CloudWatch Logs

@ MLA-C01 D2 T2.2 advanced troubleshooting
S: An image model trained on one GPU with batch size 64 and learning rate 0.01 reaches 91% accuracy. The team moves to SageMaker distributed data parallel on 8 GPUs, keeping 64 images per GPU, the same learning rate and the same 30 epochs. Training is 7 times faster, but accuracy drops to 84%. The team wants to keep the speedup. What should it change FIRST?
A: Scale the learning rate up in proportion to the larger global batch, with a short warm-up period at the start of training
B: Lower the per-GPU batch size to 8 so that the global batch size across all eight GPUs goes back to the original 64
C: Switch from data parallelism to model parallelism so that each GPU holds a part of the model instead of a full copy
D: Increase the number of epochs from 30 to 240 so that the model receives as many weight updates as it did on one GPU
K: A
G: ## What data parallelism changes
With data parallelism each GPU holds a full model copy, processes its own mini-batch, and gradients are averaged across GPUs before each update. The effective, or **global**, batch size is `per-GPU batch x number of GPUs`: here 64 x 8 = 512.
With the same epochs, the model now makes 8 times fewer weight updates, each an average over more examples. Keeping the old learning rate means each epoch moves the weights much less, so the model ends up undertrained.
## The linear scaling rule
A common fix is to scale the learning rate with the global batch size: 8 times the batch, roughly 8 times the learning rate (0.01 to about 0.08). Because a large learning rate can destabilize the first steps, it is combined with a **warm-up** that ramps the rate up over the first few epochs.
Some optimizers such as LAMB or LARS are designed for very large batches if linear scaling is not enough.
W: Scale the learning rate with warm-up: this compensates for the 8 times larger global batch and fewer updates, restoring accuracy while keeping the 7 times speedup.
X: B=Per-GPU batch of 8: it restores the original dynamics, but small per-GPU batches leave the GPUs underused and add communication overhead, so much of the speedup is lost.
C=Model parallelism: it is for models that do not fit on one GPU. This model fits, and splitting it would add communication without fixing the learning rate mismatch.
D=240 epochs: eight times more epochs gives back the number of updates but also eight times the compute, cancelling the speedup the team wants to keep.
T: More GPUs in data parallel training mean a larger global batch; adjust the learning rate (with warm-up) instead of shrinking batches or adding epochs.
V: Amazon SageMaker

@ MLA-C01 D2 T2.2 applied tradeoff
S: A single-instance SageMaker training job reads 1.5 TB of images from S3 in File mode. Each run spends about 40 minutes copying data before the first epoch starts. The training script opens image files from a local directory, and the team does not want to change how it reads data or build new storage infrastructure. Which change fits BEST?
A: Switch the input channel to Pipe mode so that data is streamed from S3 directly into the training container as it is needed
B: Switch the input channel to FastFile mode so that S3 objects appear as local files and are streamed on demand while training
C: Increase the job's VolumeSizeInGB so that the full dataset copy completes faster on a larger ML storage volume before training
D: Set the channel's S3DataDistributionType to ShardedByS3Key so that the instance downloads only a portion of the objects in S3
K: B
G: ## SageMaker training input modes
- **File mode** (default): the whole channel is copied from S3 to the instance's storage volume before training starts. Simple, but start-up time grows with dataset size.
- **Pipe mode**: data is streamed through Unix named pipes (FIFOs). The script must read from the pipe, for example with a RecordIO or TFRecord reader, so file-based code has to change.
- **FastFile mode**: SageMaker exposes S3 objects as a POSIX file system at the usual `/opt/ml/input/data/<channel>` path. Files are fetched from S3 on demand as the script opens them, so training starts almost immediately.
## Choosing
FastFile is the easiest way to remove the download wait when code already reads files and access is mostly sequential. Amazon FSx for Lustre is another option, but it is extra infrastructure to create and manage.
Example: `TrainingInput(s3_data="s3://bkt/images/", input_mode="FastFile")`.
W: FastFile mode: the script keeps opening local file paths, while SageMaker streams each object from S3 when it is read, so the 40 minute copy disappears with no code or infrastructure changes.
X: A=Pipe mode: it also avoids the copy, but the script must read a stream from a named pipe instead of opening files, which is the code change the team wants to avoid.
C=Larger volume: a bigger volume holds the data but does not make the full copy meaningfully faster; training still waits for all 1.5 TB.
D=ShardedByS3Key: sharding splits objects across multiple instances. With one instance, that instance still receives every object, and it would change the data each epoch sees if more instances were added.
T: File mode waits for a full copy, Pipe mode needs stream-reading code, and FastFile streams on demand behind normal file paths.
V: Amazon SageMaker, Amazon S3

@ MLA-C01 D2 T2.2 applied use-case
S: A fraud model uses the SageMaker built-in XGBoost algorithm with `objective=binary:logistic`. Only 0.8% of training rows are fraud. With `eval_metric=error` and early stopping, the model predicts almost no fraud, yet validation error is only 0.8%. Which TWO changes are MOST appropriate? (Select TWO)
A: Set `scale_pos_weight` to about the ratio of negative to positive rows so that errors on fraud rows weigh more
B: Change the objective to `multi:softmax` with `num_class=2` so that the two classes are learned as separate outputs
C: Set `eval_metric` to `aucpr` so that early stopping and model selection track how well fraud cases are ranked
D: Remove early stopping and set `num_round` to 5,000 so that the trees keep learning until they finally fit the fraud rows
E: Set `subsample` to 0.1 so that each boosting round sees fewer legitimate rows and the classes appear more balanced
K: A,C
G: ## Why error is misleading here
`error` is the fraction of wrong predictions at a 0.5 threshold. With 0.8% fraud, a model that predicts "not fraud" for everything scores 0.8% error, so early stopping happily keeps a model that finds nothing.
## Two XGBoost tools for imbalance
- `scale_pos_weight` multiplies the gradient of positive examples. A common starting value is `count(negative) / count(positive)`, here about 99.2 / 0.8 = 124. The trees then pay attention to fraud rows instead of treating them as noise.
- `eval_metric` controls what the validation channel reports and what early stopping watches. `aucpr` (area under the precision-recall curve) and `auc` measure how well positives are ranked above negatives, independent of a 0.5 cut-off. With `aucpr`, early stopping keeps the rounds that actually improve fraud detection.
After training, choose a decision threshold from the precision-recall trade-off instead of assuming 0.5.
W: A=scale_pos_weight: re-weights the rare fraud rows so the model learns them instead of ignoring them.
C=aucpr: gives early stopping and model comparison a metric that reflects fraud detection, unlike error on imbalanced data.
X: B=multi:softmax: two-class softmax is mathematically the same problem as binary logistic, loses the probability output, and does nothing about the imbalance.
D=5,000 rounds without early stopping: more rounds under the same unweighted loss mostly overfit; the model still has little reason to predict the rare class.
E=subsample 0.1: subsample drops rows at random from both classes equally, so the class ratio does not change; it only adds noise.
T: For rare positives in XGBoost, re-weight them with scale_pos_weight and watch a ranking metric such as aucpr, not error.
V: Amazon SageMaker

@ MLA-C01 D2 T2.2 advanced tradeoff
S: A tuning job for a gradient boosting model searches 8 continuous hyperparameters with the Bayesian strategy, `MaxNumberOfTrainingJobs=100` and `MaxParallelTrainingJobs=100`. The best result is no better than what random search found earlier. Which change is MOST likely to improve the Bayesian search?
A: Switch to the grid search strategy so that every combination of the eight continuous hyperparameters is tried at least once
B: Enable warm start from the earlier random search and also raise MaxParallelTrainingJobs to 200 to explore more combinations
C: Set the scaling type of every hyperparameter to Logarithmic so that the search explores a wider range of values in each run
D: Lower MaxParallelTrainingJobs to a small number, such as 5, so each new batch of jobs can use the results of completed jobs
K: D
G: ## How Bayesian tuning learns
Bayesian optimization builds a model of "hyperparameters to objective" from the jobs that have **finished**. It then chooses the next values where that model predicts good results or has high uncertainty. Each new job is informed by earlier ones.
## The parallelism trade-off
- If all 100 jobs start at once, no job has finished when the values are chosen, so every choice is made with no information: that is effectively random search.
- With a parallelism of 5, after the first few waves the tuner has dozens of results to learn from.
More parallelism finishes sooner in wall-clock time; less parallelism usually finds better values for the same number of jobs.
Example: 100 jobs with parallelism 5 gives 20 waves, and 19 of them are guided by earlier results.
W: Lower parallelism: the Bayesian strategy only improves on random search when it can learn from completed jobs, and running all jobs at once removes that feedback.
X: A=Grid search: grid search needs a discrete set of values per hyperparameter and grows exponentially with 8 dimensions; it does not learn from earlier results either.
B=Warm start with 200 in parallel: warm start helps, but launching everything at once still stops the tuner from learning during the new job, and the job limit stays at 100.
C=Logarithmic scaling: it suits values spanning orders of magnitude, such as learning rate, but it is not a fix for every parameter and does not address the root cause.
T: Bayesian tuning needs finished jobs to learn from; full parallelism turns it into random search.
V: Amazon SageMaker

@ MLA-C01 D2 T2.2 advanced tradeoff
S: A team must adapt a 13-billion-parameter open language model to its support-ticket style on SageMaker. Its budget allows one ml.g5.2xlarge instance with a single 24 GB GPU. Full fine-tuning runs out of GPU memory immediately. Which approach fits BEST?
A: Full fine-tuning with batch size 1 and gradient checkpointing so that activations are recomputed and the whole model fits in memory
B: Parameter-efficient fine-tuning with LoRA adapters on a 4-bit quantized copy of the base model (QLoRA) so only small adapters train
C: Pre-training a new 13-billion-parameter model from scratch on the support tickets so that the whole model learns the company style
D: Full fine-tuning with a much larger dropout rate so that fewer neurons are active in each step and the memory needed is much lower
K: B
G: ## Where fine-tuning memory goes
Full fine-tuning keeps, per parameter: the weight, its gradient and the optimizer state (Adam keeps two values). In mixed precision this is roughly 16 bytes per parameter, so a 13B model needs around 200 GB before counting activations. One 24 GB GPU cannot hold it.
## Parameter-efficient fine-tuning (PEFT)
- **LoRA** freezes the base weights and trains small low-rank matrices added to selected layers, often well under 1% of the parameters. Only those need gradients and optimizer state.
- **QLoRA** also loads the frozen base model in 4-bit precision: 13B x 0.5 bytes is about 6.5 GB, which leaves room for adapters and activations on a 24 GB GPU.
The result is a small adapter file that is loaded on top of the base model for inference, or merged into it.
W: QLoRA: quantizing the frozen base model and training only LoRA adapters cuts memory by an order of magnitude, so the 13B model fits on one 24 GB GPU while still learning the ticket style.
X: A=Batch size 1 with gradient checkpointing: these reduce activation memory only; the weights, gradients and Adam states of 13B parameters still need far more than 24 GB.
C=Pre-training from scratch: it needs vastly more data and compute than one GPU and a set of tickets, and it would discard the language ability of the existing model.
D=Higher dropout: dropout zeroes activations randomly for regularization. All weights, gradients and optimizer states are still stored, so memory use does not drop.
T: When full fine-tuning does not fit, train small adapters on a frozen (optionally quantized) base with LoRA or QLoRA.
V: Amazon SageMaker

@ MLA-C01 D2 T2.3 applied use-case
S: Before training a loan-approval model, a compliance team wants to know whether the historical labels already approve applicants aged 60 or over at a lower rate than younger applicants. No model exists yet. Which approach fits BEST?
A: Run a SageMaker Clarify pre-training bias analysis and review the Difference in Proportions of Labels (DPL) for the age facet
B: Run a SageMaker Clarify pre-training bias analysis and review the Class Imbalance (CI) metric for the age facet in the data
C: Run a SageMaker Clarify post-training bias analysis and review Disparate Impact (DI) for predictions made on the age facet
D: Schedule SageMaker Model Monitor bias drift monitoring on the endpoint and alarm when the age-group metrics begin to differ

G: ## Pre-training versus post-training bias
SageMaker Clarify computes bias metrics at two stages:
- **Pre-training** metrics look only at the dataset: the facet (a sensitive attribute such as age group) and the label.

## Two common pre-training metrics
- **Class Imbalance (CI)** compares how many rows each facet group has. It answers: "Are older applicants underrepresented?"
- **Difference in Proportions of Labels (DPL)** compares the rate of positive labels between groups: `q_a - q_d`, the approval rate of one group minus the other.

W: Pre-training DPL: it measures the difference in approval rates between the two age groups directly in the labeled data, which is the exact question, and needs no model.
X: B=Class Imbalance: CI only compares group sizes. Older applicants could be well represented yet approved far less often, and CI would not show it.
C=Post-training Disparate Impact: post-training metrics are computed on model predictions, and no model exists yet.
D=Model Monitor bias drift: it watches a deployed endpoint over time. There is no endpoint, and the question is about historical labels.
T: Unequal positive-label rates in the data before training is DPL; unequal group sizes is CI; prediction disparities are post-training metrics.

@ MLA-C01 D2 T2.3 applied troubleshooting
S: Instance metrics show that a PyTorch image training job on an ml.p3.8xlarge instance keeps GPU utilization around 25%. One CPU core is at 100% while the others are mostly idle, and the DataLoader decodes and resizes full-size JPEGs every epoch. Which TWO actions will MOST improve GPU utilization? (Select TWO)
A: Move the training job to an ml.p4d.24xlarge instance so that the model has faster GPUs with more memory available for each batch
B: Increase the DataLoader `num_workers` so that several CPU processes decode and augment images in parallel with the training steps
C: Resize and encode the images once in a SageMaker Processing job so the training job reads smaller, ready-to-use inputs every epoch
D: Increase the learning rate and the number of epochs so that the GPUs perform more useful work each time a new batch reaches them
E: Split the model across the GPUs with model parallelism so that each GPU runs fewer layers and waits less for every training batch

G: ## Reading utilization metrics
Low GPU utilization with busy CPUs usually means the GPUs are waiting for data. Training job instance metrics and SageMaker Debugger's built-in profiling rules (such as `LowGPUUtilization` and `CPUBottleneck`) point to the input pipeline, not to the model.
## Why one busy core matters
In PyTorch, `DataLoader(num_workers=0)` loads data in the main process. Decoding a full-size JPEG, resizing it and augmenting it then runs on one core, one image at a time, while the GPU sits idle.
## Fixes
- Raise `num_workers` (for example to the number of vCPUs divided by the number of GPUs) so batches are prepared in parallel and in advance.
- Do the fixed, deterministic work once: decode and resize the images offline to the training resolution, and keep only random augmentation in the loader.
Example: an ml.p3.8xlarge has 32 vCPUs and 4 GPUs, so 6 to 8 workers per GPU process are reasonable.
W: B=More DataLoader workers: spreads decoding and augmentation over the idle cores so batches are ready when the GPU needs them.
C=Offline preprocessing: removes the repeated full-size decode and resize, so each epoch needs much less CPU work per image.
X: A=Bigger GPU instance: faster GPUs finish each batch sooner and then wait even longer for the same slow loader, so utilization gets worse.
D=Higher learning rate and more epochs: these change what is learned, not how quickly data reaches the GPU, and more epochs only add idle time.
E=Model parallelism: the model already fits and computes quickly; splitting it adds communication but leaves the single-core data bottleneck in place.
T: Low GPU utilization with a busy CPU is an input bottleneck; parallelize and precompute the data loading instead of buying more GPU.

@ MLA-C01 D2 T2.3 advanced troubleshooting
S: A credit model's SageMaker Clarify SHAP report is confusing: nearly every applicant gets a large positive attribution for `age` and `income`. The analysis configuration uses a baseline record where every feature, including age and income, is set to 0. What should the engineer change?
A: Increase `num_samples` in the SHAP configuration so the Kernel SHAP estimates become more precise for every applicant record
B: Replace SHAP with partial dependence plots so that each feature's average effect is shown without having to use any baseline
C: Use a representative baseline, such as a summary of the training data from K-means centroids, instead of the all-zero record
D: Remove `age` and `income` from the model inputs so that the other features receive a fairer share of every applicant attribution
K: C
G: ## What a SHAP value is relative to
Kernel SHAP, used by SageMaker Clarify, explains a prediction as the difference from a **baseline** prediction. Each feature's attribution says how much it moved the output away from what the model predicts for the baseline record.
## Why the baseline matters
If the baseline is unrealistic, every real applicant looks very different from it. With `age = 0` and `income = 0`, every applicant has an age and income far from the baseline, so those features always get large attributions, even when they barely influence decisions among real applicants.
## Better baselines
- A typical record, such as the median or mode of each feature.
- A small set of representative records, for example K-means cluster centers of the training data. If no baseline is provided, Clarify can compute one this way from the input dataset.
Example: with a median baseline, an applicant close to the median age and income gets near-zero attribution for those features.
W: Representative baseline: SHAP attributions are measured against the baseline, so a realistic baseline removes the artificial attribution caused by comparing everyone with a zero-age, zero-income record.
X: A=More samples: more samples reduce the variance of the estimate, but the estimate is still relative to the same unrealistic baseline, so the bias remains.
