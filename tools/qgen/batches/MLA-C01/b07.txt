Which change fixes the error while keeping least privilege?
A: Attach the AdministratorAccess managed policy to the data scientist so that any role in the account can be handed to SageMaker jobs

G: ## Two different permissions are involved
- The **execution role** is what the training container assumes at run time. Its trust policy names `sagemaker.amazonaws.com`, and its permissions policy covers the data, images and keys the job touches.
- The **caller** (the data scientist) is the identity that starts the job. To hand a role to a service, the caller needs `iam:PassRole` on that role. AWS requires this so that a user cannot give a service a more powerful role than the user is allowed to use.
## Scoping PassRole
Grant `iam:PassRole` only on the specific role ARN, and add the `iam:PassedToService` condition so the role can be passed only to SageMaker and not to other services such as Lambda or EC2.
Example: the policy on the data scientist allows PassRole for `arn:aws:iam::111122223333:role/ml-team-execution` with `iam:PassedToService` equal to `sagemaker.amazonaws.com`, and nothing broader.

X: A=AdministratorAccess: it does fix the error but grants every permission in the account, far beyond what starting a training job requires.
C=Adding the user to the trust policy: the training job must be assumed by the SageMaker service principal, and this does not give the caller the PassRole permission that the API call checks.
D=AmazonS3FullAccess: the error is about passing the role, not about reading S3, and the execution role already has the data access the job needs.
T: Starting a SageMaker job with an execution role needs iam:PassRole on that role for the caller; scope it to one role ARN and iam:PassedToService = sagemaker.amazonaws.com.

@ MLA-C01 D4 T4.3 applied use-case
S: Applications in a private VPC call a SageMaker real-time endpoint through an interface VPC endpoint for the SageMaker Runtime service. The security team wants to make sure those applications can invoke only the `fraud-scoring` endpoint and cannot use the same network path to invoke any other endpoint, including endpoints in other AWS accounts. What should the ML engineer do?
A: Attach a security group to the interface endpoint that allows outbound traffic only to the private IP address of the fraud-scoring instances
B: Add a network ACL to the private subnets that denies traffic to the DNS names of every SageMaker endpoint other than fraud-scoring
C: Attach a bucket policy to the model artifact bucket that denies reads of any model.tar.gz that does not belong to the fraud-scoring endpoint
D: Attach a VPC endpoint policy that allows sagemaker:InvokeEndpoint only on the fraud-scoring endpoint ARN and denies it for other resources
K: D
G: ## Endpoint policies control what can be done through the endpoint
An interface VPC endpoint (AWS PrivateLink) carries API calls to a service privately. Each endpoint can have an **endpoint policy**, an IAM-style resource policy that limits which principals, actions and resources are allowed **through that endpoint**. The default policy allows everything.
## Applying it here
The SageMaker Runtime endpoint (`com.amazonaws.<region>.sagemaker.runtime`) carries `InvokeEndpoint` calls. A policy that allows `sagemaker:InvokeEndpoint` only on the ARN of the `fraud-scoring` endpoint means a call for any other endpoint, in this account or another one, is denied when it uses this path. IAM policies on the callers still apply as well, so the effective permission is the intersection of the two.
W: VPC endpoint policy: it is evaluated for every request that uses the interface endpoint and can restrict InvokeEndpoint to one endpoint ARN.
X: A=Security group on the endpoint: security groups filter by IP address and port, they cannot see which SageMaker endpoint name a request is for, and the runtime API is reached through the service, not the instance addresses.
B=Network ACLs: ACLs work on IP ranges and ports, not on DNS names, and all runtime calls share the same PrivateLink addresses.
C=Bucket policy on model artifacts: this controls access to files in S3, not which endpoints can be invoked, and invocation does not read from the bucket at request time.
T: To limit what can be invoked through a private path, attach an endpoint policy to the interface VPC endpoint and combine it with IAM permissions on the callers.
V: Amazon SageMaker AI, AWS PrivateLink, Amazon VPC

G: ## Cross-account access to SageMaker endpoints
SageMaker endpoints do not support resource-based policies. Cross-account invocation therefore uses **role assumption**: the caller assumes a role in the account that owns the endpoint and calls the API with the short-lived credentials that `sts:AssumeRole` returns.
## Both sides must allow it
- In the owner account, the role's **trust policy** names the partner account (or a specific partner role), and its **permissions policy** allows `sagemaker:InvokeEndpoint` on the endpoint ARN only.
- In the partner account, the calling identity needs an IAM permission for `sts:AssumeRole` on the owner's role ARN.
An external ID condition can be added to the trust policy when a third party is involved. No long-term secrets are exchanged.
W: A=Trusted role with narrow permissions: this gives the partner a controlled entry point with permission only to invoke the one endpoint.
D=AssumeRole from the partner side: the partner's role must be allowed to assume the owner's role, and the temporary credentials expire without any rotation work.
X: B=Resource-based policy on the endpoint: SageMaker endpoints have no resource-based policy, so there is nothing to attach.
C=IAM user with rotated keys: this still shares a long-term credential with the partner, which the security team explicitly wanted to avoid.
E=Second endpoint in the partner account: this copies the model outside the owner's control and adds cost, and it does not grant access to the owner's endpoint.
T: SageMaker endpoints have no resource policies, so grant cross-account invocation with an assumable role that allows only InvokeEndpoint, plus sts:AssumeRole permission on the caller's side.

S: A team trains a model in one account with output encrypted by a customer managed KMS key using SSE-KMS. The deployment execution role has `s3:GetObject` on the artifact bucket, and the bucket policy allows that role. What is the most likely missing piece?
A: The KMS key policy and the deployment role's IAM policy must both allow kms:Decrypt so that the role can decrypt the artifact objects
B: The S3 bucket needs versioning enabled so that the deployment role can read the encrypted objects that the training job wrote
C: The deployment role needs the AmazonSageMakerFullAccess managed policy so that it can read encrypted objects in another account
D: The endpoint configuration must set network isolation so that the artifacts are decrypted before the container starts downloading
K: A
G: ## Reading an SSE-KMS object takes two permissions
For an object encrypted with SSE-KMS, `s3:GetObject` is not enough. S3 asks KMS to decrypt the object's data key on the caller's behalf, so the caller also needs `kms:Decrypt` on the key.
## Cross-account rules
A customer managed key belongs to one account. When the caller is in another account, **both** must allow it: the **key policy** must permit the external account or role (for example with a statement for `kms:Decrypt` and `kms:DescribeKey`), and the **caller's IAM policy** must allow the same actions on the key ARN. If either is missing, the request is denied, and S3 reports it as AccessDenied.
The AWS managed key `aws/s3` cannot be shared across accounts, which is why cross-account artifacts should use a customer managed key.
W: KMS permissions on both sides: the object read succeeds only when the key policy and the role's IAM policy both allow kms:Decrypt for the deployment role.
X: B=Versioning: it protects against overwrites and deletions, and has no effect on whether a role may decrypt an object.
C=AmazonSageMakerFullAccess: it does not grant access to a KMS key in another account, and the key policy would still have to allow the role.
D=Network isolation: it blocks the container's outbound calls at run time and does not change how model artifacts are decrypted or downloaded by the service.
T: SSE-KMS objects need kms:Decrypt in addition to s3:GetObject, and across accounts both the key policy and the caller's IAM policy must allow it.
V: AWS KMS, Amazon S3, Amazon SageMaker AI

The monitoring executions complete, yet the reports contain no accuracy or AUC values and a note says no records could be merged with ground truth. Which TWO actions are needed to fix this? S: A lending model's feature attribution drift monitor, configured with SageMaker Clarify, reports a violation even though all input feature distributions still match the data quality baseline. Which statement explains what the monitor compares and why this can happen?
A: It compares the ranking of features by their SHAP-based attribution in live data with the ranking in the baseline, using the NDCG score
B: It compares the mean and standard deviation of each input column in live data with the training statistics, using a Kolmogorov-Smirnov test
C: It compares the count of missing values and data types for every input column, and flags any column that has a new data type
D: It compares the model's average predicted probability per day with the average in the baseline, using a population stability index
K: A
G: ## Distributions and attributions are different things
- **Data quality monitoring** looks at the inputs: statistics such as mean, min, max, missing values and data types, compared with baseline constraints.
- **Feature attribution drift monitoring** (SageMaker Clarify with Model Monitor) looks at **why the model predicts what it does**. It computes SHAP-based attributions for live inference data and ranks the features by importance.
## The comparison
The monitor compares the live ranking with the baseline ranking using the **normalized discounted cumulative gain (NDCG)** score. If the score falls below the constraint, a violation is reported, meaning the features driving predictions have changed in importance.
This can happen even when each input distribution looks the same, for example when the relationship between two features and the label has shifted, so the model leans on different features than at training time.
W: NDCG on SHAP-based rankings: the monitor detects a change in which features drive predictions, which is invisible to input distribution checks.
X: B=Column statistics with a statistical test: this describes the checks that data quality monitoring performs on inputs, and it would not explain a violation when the inputs match.
C=Missing values and data types: this is also a data quality check, and it does not involve model explanations.
D=Average predicted probability per day: that would be prediction distribution drift, which Clarify's feature attribution monitor does not compute.
T: Feature attribution drift compares SHAP-based feature rankings with an NDCG score, so it can fire while input distributions look unchanged.

@ MLA-C01 D4 T4.1 applied tradeoff
S: A demand-forecast endpoint has a Model Monitor data quality schedule and a model quality schedule, each emitting CloudWatch metrics. Retraining costs about $3,000 per run, and the drift alarm on one feature fires several times a month even though forecast accuracy stays within target. The team wants to retrain only when there is evidence of harm. Which approach fits BEST?
A: Retrain on every data drift alarm because the cost of a bad forecast is always greater than the cost of a training run
B: Lower the data quality constraint thresholds so that the drift alarm fires more often and retraining happens earlier
C: Create a composite alarm that is in ALARM only when the feature drift alarm and the model quality alarm are both in ALARM
D: Disable the model quality schedule and use only the data drift alarm because ground truth arrives too slowly to be helpful
K: C
G: ## Drift is a signal, not proof of harm
Data drift says the inputs changed. Model quality says whether the predictions are still correct. Inputs can drift in ways that do not matter to the model, so retraining on every drift alarm pays for runs that add nothing.
## Composite alarms
A CloudWatch **composite alarm** evaluates a rule expression over other alarms, for example `ALARM(feature-drift) AND ALARM(model-quality)`. It triggers its actions (SNS notification, EventBridge event that starts a SageMaker Pipeline) only when the rule is true, which reduces noisy notifications.
## Trade-off
The design waits for labeled evidence, so it reacts more slowly than a drift-only trigger. Add a rule for severe drift alone, for example `OR ALARM(severe-drift)`, if waiting is too risky.
W: Composite alarm on drift and model quality: retraining starts only when the inputs moved and measured quality actually dropped.
X: A=Retrain on every drift alarm: this repeats a $3,000 run several times a month without evidence that forecasts got worse.
B=Lower thresholds: a more sensitive alarm fires even more often, which increases unneeded retraining.
D=Dropping model quality monitoring: this removes the only signal of actual harm, and slow labels are handled by scheduling the monitor accordingly.
T: Combine drift and model quality alarms in a CloudWatch composite alarm so retraining requires evidence of both changed inputs and degraded predictions.

@ MLA-C01 D4 T4.1 applied troubleshooting
S: A team's endpoint accepts JSON requests containing a nested `customer` object and a list of `events`. What should the ML engineer do?

B: Increase the instance size of the monitoring processing job so that it can parse the nested JSON records that are in the captured data

G: ## What Model Monitor expects
Data Quality monitoring works on **tabular** records. For an endpoint that accepts CSV or flat JSON lines, the built-in analyzer can read the captured data directly. The schedule accepts a **record preprocessor script** (`record_preprocessor_script`), a Python function that runs on each captured record and returns a flat dictionary or list of feature values with the same names as in the baseline. There is a matching **post-analytics processor script** for custom checks after analysis.
Example: the function extracts `customer.age`, `customer.tenure` and the summary of `events` into columns, so live data is compared with the training statistics column by column.
W: Record preprocessor script: it converts each nested captured record into the tabular feature layout that the baseline and constraints use.
X: B=Larger instance: the failure is a format mismatch and not a lack of memory or CPU, so more capacity yields the same wrong columns.
C=100 percent sampling: sampling changes how many records are captured and does not alter their structure.
D=CSV-only container: this forces a change to the model container and all clients to fix a monitoring problem that a script solves without touching the endpoint.
T: For nested or custom payloads, give the Model Monitor schedule a record preprocessor script that flattens records into the baseline's feature columns.
