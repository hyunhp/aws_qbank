@ Q000878 explain
G: ## Nominal versus ordinal categories
A **nominal** feature has values with no natural order, such as `red`, `green`, `blue`. An **ordinal** feature has a real order, such as `small < medium < large`.
## What label encoding tells a model
Label encoding replaces each category with an integer: `red=0`, `green=1`, `blue=2`. A linear model multiplies that number by one weight, so it treats blue as "twice green" and assumes green lies between red and blue.
- Example: if the weight is 0.5, blue adds 1.0 to the score, green 0.5 and red 0. The model cannot give green a high effect and both red and blue a low one.
## What one-hot encoding does instead
One-hot creates one 0/1 column per value (`is_red`, `is_green`, `is_blue`). Each color gets its own weight, and no order or distance between colors is implied. Tree-based models are less sensitive to this issue because they split on thresholds, but linear models are not.
W: False order between categories: the integers 0, 1, 2 give a linear model a fake ranking and equal spacing, so it learns one slope across colors that have no numeric relationship, which distorts predictions.
X: B=One-hot always worse: no encoding is always better. For a nominal feature with three values in a linear model, one-hot is usually the correct choice, not the worse one.
C=Cannot encode strings: label encoding exists precisely to turn string categories into integers; tools such as scikit-learn's `LabelEncoder` and `OrdinalEncoder` do it routinely.
D=Uses more memory: label encoding needs a single integer column, while one-hot needs one column per category, so label encoding is the smaller of the two.
T: Integers imply order and distance: use them only for truly ordered categories, and use one-hot for unordered ones like colors.

@ Q000879 explain
G: ## The high-cardinality problem
One-hot encoding creates one column per category. A feature with 10,000 values, such as product IDs or zip codes, becomes 10,000 mostly-zero columns, which slows training, uses memory and invites overfitting.
## How binary encoding works
Binary encoding first maps each category to an integer, then writes that integer in base 2 and puts each bit in its own column.
- `2^14 = 16,384`, so 10,000 categories fit in about 14 columns instead of 10,000.
- Example: category number 5 becomes bits `...0101`, category 6 becomes `...0110`.
The price is that categories share bit columns, so some unrelated values look partly similar; it is a compromise between one-hot (no false similarity, huge width) and plain label encoding (one column, false order).
## Other options for high cardinality
- **Target encoding**: replace each category with a smoothed average of the target (compute it on training folds to avoid leakage).
- **Feature hashing**: hash categories into a fixed number of columns.
- **Embeddings**: learned dense vectors in neural networks.
W: Binary encoding: it stores each category as a compact bit pattern across roughly log2(10,000) ≈ 14 columns, which removes the width and sparsity problem of one-hot while still distinguishing every category.
X: A=Standardization: it rescales numeric values to zero mean and unit variance. It does not turn categories into numbers and does not change the number of columns.
B=One-hot encoding: this is the approach that produces the 10,000-column sparse matrix the question is trying to avoid.
D=Tokenization: it splits free text into words or subwords for NLP. A category code such as a product ID is a single value, not text to be split.
T: Many categories and one-hot is too wide → binary, hashing or target encoding compresses them into far fewer columns.

G: ## From raw text to model input
Models cannot read strings, so text goes through a pipeline: **tokenize** (split into units), map each token to an ID, then turn IDs into vectors (bag-of-words counts, TF-IDF or learned embeddings).
## Tokenizer choices matter
A tokenizer decides what a "unit" is: words, subwords (such as BPE or WordPiece), or characters. Many classic pipelines strip punctuation and emojis as noise, but for sentiment they carry signal.
- Example: "Great product!!! 😍" and "Great product... 🙄" have the same words but opposite sentiment. Keeping `!!!`, `...`, `😍` and `🙄` as tokens lets the model see the difference.
- Modern subword tokenizers for transformer models usually handle emojis and punctuation as tokens already.
The result is a sequence of tokens per review that generalizes: the token `great` learned from one review helps with every other review containing it.
W: Tokenize and keep emojis and punctuation: tokenization turns each review into reusable units a classifier can learn from, and keeping the sentiment-bearing symbols preserves exactly the signal the question says matters.
X: A=Label-encode whole reviews: each review becomes one arbitrary integer, so the model sees no words at all and cannot relate a new review to anything it learned; the integer also implies a false order.
B=Normalize text length: scaling the length to 0-1 keeps a single number about the review and throws away its content, so the words and emojis that express sentiment are lost.
D=One-hot unique reviews: every distinct review gets its own column, so almost every new review is an unseen category; nothing about wording is shared, and the matrix is enormous.
T: Text becomes model input through tokenization; choose a tokenizer that keeps the symbols (emojis, punctuation) that carry the signal you need.

@ Q000881 explain
G: ## When order is real
Some categories have a natural ranking. Education level is one: `high school < bachelor's < master's < doctorate`. The order carries information, for example about expected income.
## Ordinal encoding
Ordinal encoding maps each category to an integer in its natural order:
- `high school = 0`, `bachelor's = 1`, `master's = 2`, `doctorate = 3`
A linear model can then learn "more education, higher (or lower) prediction" with one weight, and a tree can split at "at least a master's" with one threshold.
You must set the order explicitly (for example with the `categories` argument of scikit-learn's `OrdinalEncoder`); default encoders often sort alphabetically, which would scramble the ranking.
## Caveat
Ordinal integers also imply equal spacing (the step from high school to bachelor's equals the step from master's to doctorate). Tree models ignore spacing; for linear models this is usually an acceptable simplification.
W: Ordinal encoding in natural order: the integers follow the real ranking, so models that benefit from order can use it directly in a single feature.
X: A=One-hot preserves order: one-hot gives each level its own independent 0/1 column, so the model sees four unrelated categories and the ranking is lost, not preserved.
B=Tokenization: tokenization splits free text into words for NLP. Splitting "master's" into tokens does not produce a number that reflects its rank.
D=Binary encoding ignoring order: bit patterns assigned without regard to rank scatter the levels across columns, so neighboring levels do not look related and the ordering disappears.
T: Ordered categories → ordinal encoding with an explicit order; unordered categories → one-hot.

G: ## The accuracy paradox
With 1% fraud, a model that always predicts "not fraud" is right 99% of the time, so 99% accuracy can mean it learned nothing about fraud.
## Metrics that focus on the rare class
- **Recall** = TP / (TP + FN): what share of real fraud was caught. Here it is near zero.
- **Precision** = TP / (TP + FP): of the transactions flagged, how many were really fraud.
- **PR-AUC**: area under the precision-recall curve across thresholds; unlike ROC-AUC it stays sensitive when negatives vastly outnumber positives.
Example: 10,000 transactions, 100 frauds, the model flags 5 and 3 are real. Accuracy is about 99%, but recall is only 3%.
## Fixes
Resample or weight classes, tune the decision threshold, and choose the metric that reflects the business cost of missed fraud.
W: Class imbalance with recall, precision and PR-AUC: the 99% accuracy comes from the majority class, and positive-class metrics expose that almost no fraud is caught.
X: B=Label leakage: leakage makes a model look too good at finding the target, including fraud; here fraud detection is poor, so leakage does not explain it, and dropping the top feature is not a diagnosis.
C=Underfitting fixed with more layers: the symptom is a metric problem caused by imbalance; a bigger, longer-trained model can still just predict the majority class and keep 99% accuracy.
D=Data drift: nothing in the question says the data changed over time; the problem exists on the current data because of class balance, and weekly retraining would repeat it.
T: Rare positive class → accuracy misleads; judge with recall, precision and PR-AUC.

G: ## Clarify pre-training bias metrics
SageMaker Clarify can analyze a dataset before any model exists. You name a **facet** (a sensitive attribute such as age group) and the label column, and Clarify computes metrics such as:
- **Class Imbalance (CI)**: how unequal the number of members of each facet value is. With `na` members of the advantaged group and `nd` of the disadvantaged group, `CI = (na - nd) / (na + nd)`, ranging from -1 to 1; 0 means equal representation.
- **Difference in Proportions of Labels (DPL)**: difference in the share of positive labels between facet groups.
- **KL divergence, JS divergence** and others: how different the label distributions of the groups are.
Example: 9,000 records for one group and 1,000 for the other gives `CI = 0.8`, a strong representation gap.
## Post-training metrics
Metrics with "predicted labels" in the name, such as DPPL or CDDPL, need a trained model's predictions.
W: Class Imbalance (CI): it measures how unevenly facet groups are represented in the training data, before training, which is exactly the disparity described.
X: A=DPL: it compares the proportion of positive labels between groups, a label-outcome gap, not how many members each group has in the dataset.
B=CDDPL: it is a post-training metric computed on a model's predicted labels, conditioned on subgroups, so it cannot run before training and does not measure representation.
D=KL divergence on predictions: KL divergence compares distributions, and applied to model predictions it needs a trained model; it measures distribution difference, not group representation.
T: How many of each group are in the data → Class Imbalance; how labels or predictions differ between groups → DPL and post-training metrics.

G: ## Why accuracy hides the problem
If 95% of examples are negative, a model that predicts negative for everything scores 95% accuracy. Training on such data pushes the model toward the majority class because that minimizes average loss.
## Better evaluation metrics
- **Recall** of the positive class: share of real positives found.
- **Precision**: share of predicted positives that are correct.
- **F1**: harmonic mean of precision and recall, one number that drops if either is poor.
- **AUC-PR**: precision-recall trade-off across thresholds, informative when positives are rare.
Example: 1,000 records, 50 positives; the model finds 5. Accuracy is 95.5%, recall only 10%.
## Remedies
Class weights, oversampling or SMOTE on the training split, undersampling, and lowering the decision threshold, all judged with these metrics.
W: Imbalance favors the majority, so use recall, precision, F1 or AUC-PR: the high accuracy comes from the majority class, and these metrics reveal the weak performance on the positive class that matters.
X: B=Learning rate too high: the learning rate affects how training converges; lowering it does not change the class ratio or the model's bias toward the majority class.
C=Overfitting fixed by more epochs: more epochs make overfitting worse, not better, and the symptom here is majority-class bias, not memorized noise.
D=More features, same metrics: new features might help later, but keeping accuracy as the metric would still hide the problem; the question asks what reveals it.
T: High accuracy plus low minority recall → class imbalance; evaluate with recall, precision, F1 or AUC-PR.

G: ## Ways to rebalance training data
- **Random undersampling** drops majority examples until classes match. Simple, but it throws information away.
- **Random oversampling** duplicates minority examples. Exact copies make models memorize them (overfitting).
- **SMOTE** creates new synthetic minority examples by interpolating between a minority point and one of its nearest minority neighbors, so the model sees variety instead of copies.
- **Class weights** keep the data as is and make each minority error cost more in the loss (for example `scale_pos_weight` in XGBoost or `class_weight` in scikit-learn).
## Split first, then rebalance
Always split into train, validation and test first and rebalance only the training split. If duplicates or synthetic points are created before the split, near-copies of training rows land in validation, and scores look better than reality (leakage).
Example here: 2,000 vs 200,000 is a 1:100 ratio; weighting the minority class by about 100, or using SMOTE on the training split, uses all data.
W: SMOTE or class weights on the training split: both balance the classes without discarding the 200,000 majority examples or repeating identical rows, and applying them only to training data keeps validation honest.
X: A=Remove the minority class and train one-class: it throws away the 2,000 labeled minority examples that are the most valuable data; one-class methods are for when you have almost no positive labels.
B=Duplicate minority rows 100 times before splitting: exact copies encourage overfitting, and duplicating before the split leaks copies into validation and test, inflating scores.
C=Undersample the majority to 2,000: it discards 198,000 majority examples (99%), losing information the team explicitly wants to keep.
T: Rebalance without losing data → SMOTE or class weights, applied only to the training split.

@ Q000893 explain
G: ## SMOTE step by step
SMOTE (Synthetic Minority Over-sampling Technique) adds new minority examples instead of copying existing ones:
- Pick a minority example `x`.
- Find its k nearest minority-class neighbors (k is often 5) and pick one, `x_nn`.
- Create a new point on the line between them: `x_new = x + λ × (x_nn - x)`, with `λ` random between 0 and 1.
Example: minority points at (1, 2) and (3, 6) with `λ = 0.5` give a new point (2, 4).
## Why this helps
The synthetic points fill the region around the minority class, so the classifier learns a broader decision region instead of memorizing a few duplicated rows. SMOTE is applied to training data only, and works on numeric features; variants such as SMOTE-NC handle categorical ones.
W: SMOTE: it generates synthetic minority examples by interpolating between existing minority points and their nearest neighbors in feature space, exactly as described.
X: A=PCA: Principal Component Analysis reduces the number of features by projecting data onto directions of highest variance; it does not create new rows or change class balance.
B=Random undersampling: it balances classes by removing majority examples, the opposite of generating new minority examples.
D=One-hot encoding: it converts categorical values into 0/1 columns; it changes how features are represented, not how many examples each class has.
T: Interpolate between minority neighbors to create new samples → SMOTE; remove majority samples → undersampling.

G: ## Encryption
Encryption transforms data with a key so it is unreadable without that key. It is **reversible**: anyone with the key and permission can decrypt and see the original value. It protects data at rest (S3, EBS, databases with KMS) and in transit (TLS).
## Masking and anonymization
Masking replaces values with placeholders or partial values (for example `***-**-1234`); anonymization transforms data so records cannot be tied back to individuals. Done properly, they are **irreversible**: no key restores the original.
## Which fits this case
Data scientists need aggregate analysis (counts, averages, distributions) but must not see individuals. If the PII fields were only encrypted, anyone who can decrypt sees the real values. Masking or anonymizing the PII fields keeps aggregate patterns usable while hiding individual identities.
Often both are used: encrypt the whole dataset at rest, and mask the PII columns in the analytical copy.
W: Encryption is reversible with a key, masking irreversibly hides PII: this is the real distinction, and it explains why masking suits analysts who should never see individual values.
X: A=Encryption only in transit: encryption covers data at rest as well, for example SSE-KMS on S3 and KMS-encrypted EBS volumes.
B=Masking needs a decryption key: masking replaces values; there is no key that restores masked data, which is exactly why it is irreversible.
C=Functionally identical: encryption lets key holders recover the original values while masking does not, so they give different protection for this use case.
T: Encryption is reversible for key holders; masking and anonymization are not, so they fit users who must never see individual PII.

G: ## What PHI is
Under the US HIPAA law, **protected health information (PHI)** is health information that can be linked to an individual and is held by a covered entity (such as a health plan or provider) or its business associate. Diagnosis codes and claims tied to patients are PHI, even without names, because they are linked to identifiable people.
## Handling PHI on AWS
- Sign a **Business Associate Addendum (BAA)** with AWS (done through AWS Artifact).
- Store and process PHI only in **HIPAA-eligible services**; many services, including Amazon S3 and Amazon SageMaker, are on that list.
- Apply safeguards: encryption at rest and in transit (for example KMS and TLS), least-privilege access, and logging with CloudTrail.
Under the shared responsibility model, AWS secures the infrastructure; the customer configures the services correctly.
W: PHI requiring a BAA, eligible services and encryption: patient-linked diagnosis codes and claims are PHI for a covered entity, so the company needs a BAA with AWS, HIPAA-eligible services and safeguards such as encryption.
X: B=Anonymous statistics: data linked to patients is not anonymous just because names are absent; the link to individuals is what makes it PHI.
C=Public data: patient diagnoses and claims are confidential health records, and HIPAA requires safeguards for them.
D=Regulated only outside the US: HIPAA applies to covered entities' PHI wherever it is stored, including US Regions; location does not remove the obligation.
T: Health data linked to patients at a covered entity is PHI → BAA, HIPAA-eligible services and safeguards like encryption.

G: ## Data residency on AWS
Data in S3, SageMaker and most services stays in the **Region** where you create the resource; AWS does not move it to another Region unless you configure replication or use a global service. So residency is mainly about making sure nobody creates resources or copies data outside the allowed Regions.
## Enforcing it with SCPs
A **service control policy** in AWS Organizations sets the maximum permissions for accounts. A common pattern denies actions when `aws:RequestedRegion` is not an EU Region such as `eu-central-1` or `eu-west-1`, with exceptions for global services such as IAM. AWS Control Tower offers a Region deny control built on the same idea.
- Also restrict S3 cross-Region replication destinations and avoid services that cache data outside the EU.
Example: an engineer trying to start a training job in `us-east-1` gets an access-denied error, even as an administrator of that member account.
W: EU Regions only, enforced with SCPs: the data is kept in EU Regions and an organization-wide guardrail blocks creating resources elsewhere, which directly enforces residency.
X: A=Transfer Acceleration: it speeds uploads to a bucket through global edge locations; it does not restrict where data is stored or processed.
C=CloudFront global caching: caching at edge locations worldwide copies content outside the EU, which works against residency.
D=Any Region with encryption: encryption protects confidentiality, but the data would still physically reside outside the EU, which residency rules forbid.
T: Data residency → keep resources in allowed Regions and enforce it with SCP Region restrictions; encryption does not change location.

G: ## Fixing a PII incident in an ML pipeline
If raw Social Security numbers were used as a feature, two problems exist:
- **The deployed model**: it was trained on PII. SSNs are also a poor feature (identifiers invite memorization), and models can leak training data.
- **The pipeline**: nothing stopped PII from reaching training.
## Remediation steps
- Remove or mask SSNs in the training data (they have no legitimate predictive meaning).
- Retrain and redeploy the model on the cleaned data, then retire the old model and artifacts according to policy.
- Prevent recurrence: **Amazon Macie** discovers PII such as SSNs in S3 buckets; pipeline checks (for example Glue Data Quality or sensitive data detection) can block datasets that contain PII columns; add review steps before training.
W: Remove or mask the PII, retrain, and add Macie and data quality checks: this fixes the data, removes the non-compliant model, and adds automated detection so PII cannot reach training again.
X: B=Code comment only: documenting the issue changes nothing; SSNs remain in the data and the model, and the policy violation continues.
C=Do nothing: good model performance does not excuse a policy violation; the compliance gap and the risk of exposing SSNs remain.
D=Encrypt the model artifact only: encryption protects the file at rest, but the model was still trained on SSNs and the pipeline would still accept PII next time.
T: PII in training data → clean the data, retrain, and add automated PII detection; encrypting or documenting alone does not fix it.

G: ## SageMaker Clarify
Clarify covers two related needs in regulated ML:
- **Bias detection**: pre-training metrics on the dataset (for example Class Imbalance and Difference in Proportions of Labels across age groups) and post-training metrics on the model's predictions (for example Difference in Positive Proportions in Predicted Labels, which compares approval rates between groups).
- **Explainability**: feature attributions based on SHAP values, both for each individual prediction ("income and debt ratio drove this decision") and globally.
Clarify produces reports you can share with auditors, and it integrates with **SageMaker Model Monitor** to track bias drift and feature attribution drift in production.
Example: for a rejected loan, Clarify shows that `debt_to_income` contributed most to the low score, and a post-training report shows approval rates for applicants over 60 versus under 30.
W: SageMaker Clarify: it computes bias metrics before and after training, including differences in approval rates across age groups, and SHAP-based explanations for individual predictions.
X: A=SageMaker Debugger: it inspects training internals such as tensors, gradients and loss trends to find training problems; it does not measure fairness across groups or explain individual predictions.
B=Model Monitor data quality: it detects drift in the statistics of production input data against a baseline; bias and explainability monitoring in Model Monitor rely on Clarify, not the data quality monitor.
C=Amazon Comprehend: it is an NLP service for entities, sentiment and PII in text; it does not evaluate a lending model's bias or explain its predictions.
T: Bias metrics plus per-prediction explanations → Clarify; Debugger is training internals and data quality monitoring is input drift.

G: ## Two phases of Clarify bias analysis
- **Pre-training bias** looks only at the dataset: the facet (for example gender or age group) and the labels. It asks "is the data itself skewed?". Metrics include Class Imbalance (CI), Difference in Proportions of Labels (DPL) and KL divergence. No model is needed.
- **Post-training bias** looks at a trained model's predictions compared with labels across facet groups. It asks "does the model treat groups differently?". Metrics include Difference in Positive Proportions in Predicted Labels (DPPL), Disparate Impact (DI) and differences in accuracy or recall between groups. Clarify runs the model (or a shadow endpoint) to get predictions.
## Why run both
Biased data can produce a biased model, but a model can also amplify or reduce bias present in the data. Comparing the two runs shows where a disparity comes from, and post-training bias can be monitored in production through Model Monitor.
W: Pre-training checks the dataset, post-training checks predictions: pre-training metrics measure imbalance in the data and labels before any model exists, while post-training metrics measure how the trained model's predictions differ across groups.
X: B=Post-training only manual: Clarify computes post-training bias metrics itself as a processing job, and they can also be monitored in production.
C=Images versus tabular: the two phases differ in what they analyze (data versus predictions), not in data type; Clarify's bias metrics are designed for tabular data in both phases.
D=No difference: Clarify supports two distinct kinds of bias analysis, each with its own set of metrics.
T: Pre-training bias = skew in the data; post-training bias = skew in the model's predictions.
