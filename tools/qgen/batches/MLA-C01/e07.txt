@ Q001003 explain
G: ## CloudWatch Logs Insights
SageMaker endpoints write container logs to CloudWatch Logs, in a log group such as `/aws/sagemaker/Endpoints/<endpoint-name>`. **CloudWatch Logs Insights** is a query engine built into CloudWatch that searches those log groups directly: you pick a time range (hours or days), write a query, and get results in seconds. There is nothing to provision, no data to export and no schema to define up front.
## How a query looks
`ModelLatency` is published by default as a CloudWatch **metric** (namespace `AWS/SageMaker`), which gives aggregates such as averages and percentiles but not individual requests. To find specific slow requests, the per-request latency must be in log lines, for example written by the inference container or its serving code.
Insights uses a pipe-style query language with commands such as `fields`, `filter`, `stats`, `sort` and `limit`. If each log line carries a latency field, a query like `fields @timestamp, @message | filter ispresent(ModelLatency) | sort ModelLatency desc | limit 20` returns the 20 slowest requests with their full log lines.
- `stats avg(ModelLatency) by bin(1h)` shows how latency changes hour by hour.
- You pay per GB of log data scanned, so a narrow time range keeps queries cheap.
W: CloudWatch Logs Insights: it queries the endpoint's existing log groups in place over several days, and can filter, sort and aggregate to find the individual slowest requests without building any pipeline.
X: A=Athena on CloudTrail: CloudTrail records who called which AWS API and when; it does not contain the model's per-request latency, so querying it cannot surface the slowest inference requests.
B=X-Ray service map: the service map is a picture of how traced services connect and their aggregate health; it is not a tool for searching several days of endpoint log lines for the highest latency values.
D=QuickSight: QuickSight is a BI dashboard service that needs a prepared data source; getting log data into it would mean building exactly the analytics pipeline the team wants to avoid.
T: To dig into specific log records ad hoc, query them where they already live with CloudWatch Logs Insights; CloudTrail is about API callers, not model latency.

@ Q001004 explain
G: ## What CloudTrail records
AWS CloudTrail logs API calls made in an account, whether from the console, the CLI, an SDK or another AWS service. Each event includes:
- `eventName`, for example `DeleteEndpoint`, and `eventSource` (`sagemaker.amazonaws.com`)
- `userIdentity`: the IAM user or assumed role that made the call
- `sourceIPAddress` and `eventTime`
- request parameters, such as the endpoint name
## Event history versus trails
**Event history** is on by default and keeps the last 90 days of management events for searching in the console, which covers "last month". A **trail** delivers events to an S3 bucket (and optionally CloudWatch Logs) for as long as you retain them, which is what audits usually rely on for longer periods. Deleting an endpoint is a management event, so it appears in both.
Example: filtering event history on `DeleteEndpoint` shows that the role `ml-admin` deleted `churn-prod` from `203.0.113.10` on a given date.
W: CloudTrail event history or trail logs: CloudTrail records the `DeleteEndpoint` API call with the calling identity, time and source IP address, which is exactly who did it and from where.
X: A=Invocations metric: this CloudWatch metric counts inference requests sent to an endpoint; it holds no information about who issued control-plane calls such as deleting the endpoint.
B=Conformance pack scores: AWS Config conformance packs report how many resources comply with a set of rules; the score does not identify the principal or IP address behind a specific deletion.
D=Model Monitor reports: Model Monitor compares captured inference data against a baseline for data and model quality drift; it does not log management API calls or their callers.
T: "Who did what, when and from where" in AWS is answered by CloudTrail; metrics, Config and Model Monitor describe performance, compliance and model quality instead.

@ Q001005 explain
G: ## Matching hardware to the model
A deep learning image classifier does heavy matrix math that GPUs run in parallel, so on a GPU instance (for example the `ml.g5` or `ml.g6` families) each request finishes far faster than on a CPU. Running the same model on CPUs usually means higher latency and more instances to reach the same throughput.
## Handling bursty traffic
GPU instances cost more per hour, so you do not want a fixed fleet sized for peak load. **Endpoint auto scaling** uses Application Auto Scaling to change the instance count of a production variant. A target tracking policy on a metric such as `SageMakerVariantInvocationsPerInstance` adds instances when load rises and removes them when it falls, within a minimum and maximum you set.
- Example: a minimum of 1 and a maximum of 6 GPU instances; a burst scales the fleet out, and quiet hours scale it back to 1.
- Cool-down periods prevent the fleet from flapping up and down.
W: GPU instances with endpoint auto scaling: the GPU gives the model the acceleration it needs for low latency, and auto scaling adds capacity only during bursts, so you pay for GPUs roughly in line with demand.
X: A=Largest CPU-only instance permanently: the model benefits heavily from GPUs, so CPUs give poor latency, and a permanently large instance still pays for peak capacity during quiet periods.
C=Real-time endpoint on Spot: managed Spot in SageMaker is a training feature; real-time endpoints are not offered on Spot capacity, and an interruptible fleet would not suit a latency-sensitive endpoint anyway.
D=Serverless Inference: Serverless Inference runs on compute sized by the memory you configure and does not support GPUs, so it cannot provide the acceleration this model needs.
T: Pick the hardware the model needs (GPU) and control cost with auto scaling; Spot and Serverless Inference are not available for GPU real-time serving.

@ Q001012 explain
G: ## Who a SageMaker job acts as
When you call `CreateTrainingJob`, you pass an **execution role** in `RoleArn`. SageMaker assumes that role and uses its temporary credentials for everything the job does: reading input data from S3, pulling the training image from ECR, writing logs to CloudWatch and saving the model artifact.
- The caller only needs permission to create the job and `iam:PassRole` on that role.
- The caller's own S3 or ECR permissions are never used by the job.
## What the role needs here
- S3: `s3:GetObject` and `s3:ListBucket` on the training data, plus write access to the output location.
- ECR: `ecr:GetAuthorizationToken`, `ecr:BatchGetImage` and `ecr:GetDownloadUrlForLayer` for the custom image.
- If the data is encrypted with a customer managed KMS key, `kms:Decrypt` on that key.
W: The execution role lacks S3 and ECR permissions: the job reads data and pulls the image with the execution role's credentials, so AccessDenied means that role is missing the needed permissions, whatever the data scientist is allowed to do.
X: A=Root credentials: SageMaker never uses the account root user's credentials for jobs; it uses the execution role you pass in.
C=Instance network size: AccessDenied is an authorization error returned by S3 and ECR; the instance size affects performance, not whether a request is permitted.
D=Data scientist needs more permissions: the data scientist already has access, and the job does not use the caller's identity to read data or pull images, so adding permissions to that user changes nothing.
T: A SageMaker job acts as its execution role, not as the person who launched it, so data and image permissions belong on that role.

@ Q001014 explain
G: ## Policies versus roles
- A **policy** is a JSON document listing permissions, for example `s3:GetObject` on `arn:aws:s3:::ml-data/*`. It does nothing on its own until it is attached to an identity or a resource.
- **Identities** are users, groups and roles. A policy can be attached to any of them. A **group** is just a way to give the same policies to several users.
- A **role** is an identity without long-term credentials. A trusted principal, such as a user or an AWS service, assumes it and receives temporary credentials.
## How SageMaker fits in
A SageMaker training job does not belong to any IAM group. It runs as the execution role whose trust policy allows `sagemaker.amazonaws.com` to assume it. To let jobs read the bucket, attach the S3 read policy (or an equivalent one) to that execution role as well.
W: Policies grant permissions and SageMaker assumes a role: permissions are defined in policies, and SageMaker jobs use them only when the policy is attached to the execution role the service assumes.
X: A=Reversed definitions: it is the other way around; roles are assumable identities and policies are the permission documents.
B=Policies only on roles: identity-based policies can be attached to users, groups and roles, as the team already did with the group.
D=Group policy applies to jobs: a group policy applies only to the IAM users in that group; a SageMaker job runs as its execution role and never inherits a group's permissions.
T: Policies hold permissions and roles are what services act as, so a job gets S3 access only through the policy on its execution role.

G: ## Keeping SageMaker traffic private
By default, SageMaker Studio can reach the internet and the SageMaker APIs through AWS-managed networking. For strict requirements, a Studio domain can use **VPC only** network access: all Studio traffic goes through your own VPC subnets and security groups, and there is no direct internet access.

@ Q001017 explain
G: ## How a VPC training job connects
When a training job has a `VpcConfig` with subnets and security groups, SageMaker creates elastic network interfaces (ENIs) in those subnets and attaches the security groups you specify. All network traffic from the training containers goes through those ENIs.
## Security groups as the ENI firewall
A security group is a stateful firewall on each ENI. You list the allowed outbound destinations and ports; everything else is dropped, and return traffic is allowed automatically.
- Outbound rule: TCP 443 to the internal feature API's security group or CIDR.
- Outbound rule: TCP 443 to the S3 prefix list used by the gateway endpoint.
- No other outbound rules, so the job cannot reach anything else.
Network ACLs can add stateless subnet-level rules, but only security groups are applied at the ENI.
W: Security group on the job's ENIs: security groups filter traffic at each network interface SageMaker creates, so outbound rules limited to the feature API and S3 restrict the job exactly as required.
X: A=KMS key policy: a key policy controls who may use an encryption key; it does not filter network connections from the job.
B=Lifecycle configuration: lifecycle configurations are startup scripts for notebook instances and Studio apps; they do not apply to training jobs or control network traffic.
D=IAM policy on the execution role: IAM decides which AWS API actions the job may call; it does not block TCP connections to an internal service on port 443.
T: Network paths are controlled by security groups on the ENIs; IAM and KMS control API and key permissions, not packets.

@ Q001018 explain
G: ## Network isolation for training
Setting `EnableNetworkIsolation` to true on a training job runs the container with **no network access**. The algorithm code cannot make inbound or outbound calls, not to the internet, and not even to other AWS services.
- SageMaker itself still copies the input data from S3 into the container and uploads the model artifact after training, outside the container's control.
- Anything the code needs, such as Python packages, must already be in the image or the input data.
## Why it helps here
If a dependency is compromised and tries to send data to an external server, there is simply no network to use. This does not depend on the correct subnets, routes or security group rules. Network isolation can be combined with a VPC configuration and KMS encryption for defense in depth.
W: Network isolation on the training job: it removes all network access from the training container, so even malicious or accidental code cannot make any outbound call.
X: B=Disable data capture: data capture is a feature of endpoints that records inference requests and responses; it is not a training job setting and does not block network access.
C=Public subnet with a public IP: this gives the job a direct path to the internet, the opposite of preventing outbound calls.
D=Internet gateway on the subnet: an internet gateway adds a route to the internet, again enabling exactly the traffic that must be blocked.
T: To guarantee a training container cannot talk to anything, enable network isolation; public subnets and internet gateways do the opposite.

@ Q001020 explain
G: ## Container supply chain risk
A container image bundles the model server, libraries and OS packages. Pulling an unauthenticated image from a public registry means you cannot be sure who built it or whether it was changed, and a tampered image runs with the endpoint's execution role.
## Hardening the pipeline
- **Private Amazon ECR repository**: the pipeline builds or copies approved images into a repository only your accounts can push to, and endpoints pull only from it.
- **Image scanning**: ECR basic scanning, or enhanced scanning with Amazon Inspector, reports known vulnerabilities (CVEs) in OS and language packages.
- **Verification stage**: before deployment, a pipeline step checks scan results against a threshold and can verify an image signature, for example one created with AWS Signer, stopping deployment if checks fail.
- Tag immutability prevents a tag such as `v1.4` from being silently overwritten.
W: A scanned private ECR repo plus a verification stage: controlling where images come from, scanning them and gating deployment on verification stops a tampered or vulnerable image before it reaches the endpoint.
X: A=Disable CloudTrail logging: turning off CloudTrail removes the audit record of who changed the pipeline or endpoint; it adds risk and does nothing to verify images.
B=Public pulls only off-peak: the image is just as unverified at night; the time of the pull does not change whether it was tampered with.
C=More endpoint instances: every instance would run the same compromised image, so scaling out spreads the problem rather than limiting it.
T: Supply chain risk is reduced by trusted private sources, scanning and a verification gate; timing and capacity changes do nothing to verify an image.

G: ## Amazon GuardDuty
GuardDuty is a threat detection service. Once enabled, it continuously analyzes data sources such as CloudTrail management events, VPC Flow Logs and DNS logs, without you creating trails or agents for this foundational monitoring.
It uses threat intelligence and machine learning to learn normal behavior for principals in the account. When an IAM user or role suddenly calls APIs it has never used, in unusual volume or from unusual locations, GuardDuty raises a finding, such as an anomalous behavior finding for that principal.

G: ## Why accuracy misleads on imbalanced data
With 0.4% fraud, a model that predicts "not fraud" for everything scores 99.6% accuracy while catching zero fraud. Accuracy is dominated by the majority class, so it hides failure on the class you care about.
## Better metrics
- **Precision**: of the transactions flagged as fraud, how many really are.
- **Recall**: of all real fraud, how much the model catches.
- **PR-AUC**: the area under the precision-recall curve across thresholds; unlike ROC-AUC, it is sensitive to performance on the rare class.
## Fixing training without leakage
Class weights (for example `scale_pos_weight` in XGBoost) make errors on fraud cost more. Resampling, such as undersampling the majority or SMOTE oversampling, changes the class mix. Always split first and resample only the training split, so the test set keeps the real 0.4% rate and contains no synthetic rows.
W: C=Precision, recall and PR-AUC: these measure how well the model finds the rare fraud class, exposing the failure that accuracy hides.
E=Class weights or resampling on the training split only: this makes the model pay attention to fraud while keeping validation and test data untouched and realistic.
X: A=Remove all positive examples: without fraud examples the model cannot learn to recognize fraud at all; it would guarantee the failure.
B=SMOTE before the split: synthetic samples are built from neighbors, so points derived from test rows end up in training and vice versa, which leaks information and inflates test scores.
D=Keep accuracy as the main metric: accuracy is high only because fraud is rare; it is the metric hiding the problem, not evidence the model works.
T: On imbalanced data, judge the model with precision, recall and PR-AUC, and rebalance only the training split so evaluation stays honest.

G: ## Training-serving skew
Skew happens when the features a model sees at inference are computed differently, or are fresher or staler, than the features it was trained on. A common cause is two separate code paths: one batch job for training data and another in the endpoint.
## SageMaker Feature Store
Feature Store keeps features in **feature groups**, written once through a common ingestion path, with two stores:
- **Online store**: holds the latest value per record ID (for example `customer_id`) for low-latency `GetRecord` lookups, typically in single-digit milliseconds, at inference time.
- **Offline store**: an append-only history in S3, cataloged for querying with Athena, used to build training datasets, including point-in-time correct joins so training uses the values known at each event time.
Because both stores are fed by the same feature definitions and pipeline, training and inference use consistent features.
W: Feature Store with online and offline stores: the online store serves features at millisecond latency during inference, and the offline store supplies the same features historically for training, which prevents skew.
X: A=CSV files in S3: reading and scanning files per request is far too slow for single-digit millisecond lookups, and S3 has no index for fetching one customer's record from inside CSV files.
B=Recompute from raw logs per request: this adds heavy latency and creates a second feature code path that can drift from training logic, which is the definition of training-serving skew.
D=Redshift queried at inference: a data warehouse is built for analytical queries, not single-digit millisecond point lookups at high request rates, and it does not supply point-in-time training features by itself.
T: Use one feature pipeline with two stores: online for fast inference lookups and offline for training history, so both sides see the same features.

G: ## Data leakage through preprocessing
Standardization rescales a feature as (x - mean) / standard deviation. The mean and standard deviation are **learned parameters**, just like model weights. If you compute them on the entire dataset before splitting, statistics from the validation rows flow into the training data, so validation is no longer truly unseen.
## Symptom
Validation scores look excellent, and production, where data is really new, is much worse. Here the drop from 0.97 to 0.71 AUC points to evaluation that was too optimistic.
## The correct order
- Split into train, validation and test first.
- Fit the scaler on the training split only.
- Apply that fitted scaler to validation, test and later production data.
In scikit-learn, putting the scaler inside a `Pipeline` ensures that cross-validation refits it within each fold automatically. The same rule applies to imputers, encoders and feature selection.
W: Leakage, fit the scaler on training data only: the scaler learned from the whole dataset included validation data, and fitting it only on the training split makes validation scores honest and representative of production.
X: A=Underfitting: an underfit model scores poorly on validation too; a 0.97 validation AUC is the opposite, and adding layers would not fix leaky evaluation.
B=Concept drift: drift would explain gradual decline over time, but the investigation already found a leaky preprocessing step, and daily retraining would repeat the same flawed validation.
D=Class imbalance: imbalance does not create a gap between validation and production when both have the same class mix, and oversampling does nothing about statistics leaked from validation rows.
T: Every preprocessing statistic must be learned from training data only; fitting on the full dataset leaks information and inflates validation scores.

G: ## Pre-training bias in SageMaker Clarify
SageMaker Clarify can analyze a dataset **before** any model is trained. You specify the label column, the positive label value and a **facet**, the sensitive attribute such as an age group. Clarify then computes pre-training bias metrics and writes a report.
- **Class Imbalance (CI)**: compares how many rows each facet group has. If under-40 applicants are 85% of the data and over-40 only 15%, CI is large and the model sees few examples of the smaller group.
- **Difference in Proportions of Labels (DPL)**: compares the share of positive labels between groups. If 70% of one group was approved in the historical data and 45% of the other, DPL shows that gap.
Other pre-training metrics include KL divergence and Jensen-Shannon divergence of label distributions. After training, Clarify offers post-training bias metrics and SHAP-based explanations.
W: Clarify pre-training bias metrics (CI, DPL): CI measures how imbalanced the facet groups are in the data, and DPL measures whether positive labels differ between groups, exactly the two checks required before training.
X: A=Debugger vanishing gradient rules: Debugger monitors training dynamics such as gradients and loss; it runs during training and says nothing about demographic balance in the data.
B=Macie discovery: Macie finds sensitive data such as PII in S3 buckets; it does not measure how labels are distributed across groups.
D=Model Monitor model quality: model quality monitoring compares a deployed model's predictions with ground truth labels; it requires a trained, deployed model and does not measure facet imbalance in training data.
T: Bias in the data itself, before training, is measured with Clarify pre-training metrics such as CI and DPL; Debugger and Model Monitor act later in the lifecycle.

G: ## High-cardinality categorical features
A ZIP code feature with 40,000 values becomes 40,000 mostly zero columns when one-hot encoded. That slows training and memory use, and tree models struggle because each split can only isolate one rare ZIP at a time.
## Better encodings
- **Target encoding** replaces each ZIP with a statistic of the target for that ZIP, such as the mean default rate, usually smoothed toward the global mean for rare ZIPs. It must be **fitted within folds**: compute each row's value from other folds' data only, so a row's own label never leaks into its feature.
- **Grouping** maps ZIPs to broader units such as region, state or the first three digits, keeping geographic signal with far fewer categories.
- Frequency encoding is another compact option.
Example: ZIP `10001` becomes 0.042 (its smoothed target rate computed from other folds), one numeric column that a tree can split on.
W: Fold-fitted target encoding or grouping into regions: both turn 40,000 categories into a compact representation that keeps the location signal, and fitting within folds avoids target leakage.
X: B=Drop the feature: high-cardinality features often carry strong signal, such as location-related risk; the problem is the encoding, and dropping the feature throws that signal away.
C=Label encode as continuous: ZIP numbers have no meaningful order or distance, so treating them as continuous gives trees fake numeric relationships that happen to follow postal numbering.
D=Duplicate one-hot columns: duplicate columns add no new information, double the size of an already huge matrix and make training even slower.
T: For very high-cardinality categories, use leakage-safe target encoding or grouping instead of huge one-hot matrices or fake ordinal numbers.
