G: ## Turning text into numbers
Classical classifiers such as logistic regression, linear SVMs or XGBoost only accept numeric vectors, so free text must be converted first.
- **Bag of words**: tokenize each review and count how often each vocabulary word appears. Each word becomes one column.
- **TF-IDF** (term frequency x inverse document frequency) scales those counts down for words that appear in almost every document ("the", "product") and up for words that are frequent in one review but rare overall ("refund", "broken").
## Example
In a corpus of 10,000 reviews, "great" appears in 4,000 of them, while "leaking" appears in 30. In a review that says "the bottle is leaking", "leaking" receives a much higher TF-IDF weight than common words, which is exactly the signal a sentiment or defect classifier needs.
TF-IDF is fast, needs no GPU and is easy to interpret, which makes it the usual baseline before trying embeddings or fine-tuned language models.
W: TF-IDF vectors: they encode which words a review contains and how distinctive those words are, giving a classical classifier a meaningful, content-based numeric representation.
X: A=Review length only: a single length column throws away every word, so a short angry review and a short happy review look identical to the model.
B=Random numbers per word: assigning an arbitrary number to each word creates a fake ordering (word 17 is not "bigger" than word 3), so the model learns patterns that do not exist.
C=Timestamp in seconds: the time a review was posted says nothing about what it says, so it cannot capture the text content the classifier is supposed to learn from.
T: For a classical text baseline, represent the words themselves with TF-IDF; metadata such as length or time is not a substitute for content.

@ Q003572 explain
G: ## Why time series need a chronological split
A forecasting model is used to predict the future from the past. A validation set is only honest if it imitates that situation: the model is trained on earlier periods and scored on later periods it has never seen.
## What random shuffling does
If rows are shuffled before splitting, training data ends up containing points from after many validation points.
- Example: daily sales for 2023-2025 are shuffled. The model trains on 2025-06-10 and 2025-06-12 and is then "validated" on 2025-06-11. Neighbouring days are highly correlated, so predicting the middle day is easy.
- The score looks excellent, but in production the model never has tomorrow's data, so real accuracy is much lower.
## Doing it correctly
- Split by time: for example train on 2023-2024, validate on the first half of 2025, test on the rest.
- For cross-validation, use expanding or rolling windows (such as scikit-learn `TimeSeriesSplit`) so every validation fold comes after its training fold.
W: Future information leaks into training: shuffling lets the model see observations from after the validation period, so validation scores are inflated and do not reflect real forecasting performance.
X: A=Dataset becomes too small: shuffling only reorders rows; the number of records is exactly the same before and after.
C=Seasonality is removed: each value keeps its timestamp and magnitude, so the seasonal pattern is still in the data; the problem is the leaky evaluation, not lost seasonality.
D=Becomes a classification problem: the target is still a numeric future value, so the task remains regression/forecasting regardless of row order.
T: Split time series chronologically so validation always lies in the future of training; random shuffling leaks the future and inflates scores.

G: ## Why PII must leave before training
A model can memorize rare strings from its training data. If names and email addresses are present, they can end up in model weights, logs, feature stores and even generated outputs. The safe approach is data minimization: the pipeline removes or transforms PII before any training job reads the data.
## How to do it on AWS
- **Amazon Comprehend** `DetectPiiEntities` finds entities such as `NAME` and `EMAIL` in text so they can be redacted.
- **AWS Glue** offers sensitive data detection in Glue Studio jobs to find and mask PII columns.
- **Amazon Macie** discovers sensitive data in S3 buckets so you know where it lives.
Example: a preprocessing step replaces `jane.doe@example.com` with `<EMAIL>` or a salted hash, and drops the name column entirely, then writes the cleaned dataset used for training.
W: Detect and remove or mask PII during preprocessing: the model never sees the personal data, so it cannot learn, memorize or leak it, while the rest of the dataset stays useful.
X: A=Encrypt the dataset: encryption protects data at rest and in transit, but the training job decrypts it to read it, so the model still trains on the names and emails.
C=Train on PII then delete the model: the PII has already been processed and possibly copied into artifacts and logs, and the requirement was that it must not be used for training at all.
D=Restrict the model's outputs: output filtering only hides some leaks after the fact; the PII has still been used for training, which violates the requirement.
T: PII that must not be used for training has to be removed or masked before training; encryption or output filters do not keep it out of the model.

C=Check only if accuracy drops: training compute is wasted on bad data first, and some data problems do not lower validation accuracy at all, so they are never detected.
T: Put automated data quality rules in front of training so every run is gated; epochs, manual sampling or after-the-fact checks do not stop bad data.

@ Q003577 explain
G: ## Three splits, three jobs
- **Training set**: the model learns its parameters (weights) from it.
- **Validation set**: you compare hyperparameter choices (learning rate, depth, regularization) and pick the best.
- **Test set**: used once, at the end, to estimate how the chosen model will perform on new data.
## Why tuning on the test set is a problem
Every time you look at test results and change a setting, you are fitting the model to the test data. After 50 tuning trials, the best test score is optimistic because you picked it for being high.
Example: 70% training, 15% validation, 15% test. SageMaker automatic model tuning optimizes an objective metric computed on the validation channel; the test set is scored only after the final model is chosen. With small datasets, k-fold cross-validation on the training data can replace a fixed validation split, but the test set is still kept separate.
W: Separate training, validation and test sets: hyperparameters are chosen on validation data, so the untouched test set gives an unbiased final performance estimate.
X: A=Test set only: a model needs data to learn its parameters; with no training data there is nothing to fit.
B=One dataset for everything: the model is trained, tuned and scored on the same rows, so the score measures memorization and says little about new data.
C=Tuned on the test set: selecting hyperparameters by test score leaks test information into model choice, so the final test estimate is biased upward.
T: Tune on validation and touch the test set only once at the end; tuning on test data makes the final estimate optimistic.

@ Q003578 explain
G: ## Why outliers hurt linear models
Linear regression minimizes squared error, so one point far from the rest contributes a huge squared residual and pulls the fitted line toward itself.
Example: temperature readings are mostly 15-35 degrees, but a faulty sensor sometimes reports 9,999. A few such rows can tilt the coefficient for temperature badly.
## Two standard fixes
- **Remove known errors**: if a value is confirmed to be a sensor fault (impossible physically, flagged by the device), it is not real data and can be dropped or set to missing and imputed.
- **Clipping (winsorizing)**: cap values at chosen percentiles, for example the 1st and 99th. Anything above the 99th percentile is set to that value, so extreme points keep their direction but lose their outsized weight.
Other options include robust scalers, a log transform for skewed positive data, or robust loss functions such as Huber loss.
W: C=Cap or clip at percentiles: limiting values to a reasonable range keeps the rows but stops extreme values from dominating the squared-error fit.
E=Remove confirmed sensor errors: values known to be faulty are not real observations, so dropping them removes the distortion at its source.
X: A=Duplicate outlier rows: adding more copies of extreme values increases their weight in the loss and distorts the model even more.
B=Random categories: replacing a numeric feature with random buckets destroys its relationship to the target, so the model loses the information entirely.
D=Multiply by a constant: scaling changes the units but keeps every value in the same relative position, so outliers stay just as extreme compared with the rest.
T: Handle erroneous outliers by clipping or removing them; rescaling or duplicating keeps (or amplifies) their influence.

@ Q003580 explain
G: ## What target leakage is
Target leakage happens when a training feature contains information that would not be available at the moment the model makes a prediction, often because it is created by the outcome itself.
## This scenario
- The goal: predict which active customers will churn.
- `account_closed_date` is filled only after a customer has already churned. In training data it is effectively a copy of the label: non-empty means churned, empty means stayed.
- The model learns "date present -> churn" and scores nearly 100% on validation, because validation rows have the same leaked column.
- In production, active customers never have a closed date, so the feature is always empty and the model cannot predict anything useful.
## How to catch it
- Suspiciously perfect scores are a red flag.
- Ask, for each feature, "would I know this value at prediction time?"
- Feature importance showing one feature dominating, or the target leakage analysis in the SageMaker Data Wrangler Data Quality and Insights report, can highlight it.
W: Target leakage: the feature is only populated after the outcome happens, so it reveals the label during training and validation but is unavailable when real predictions are made.
X: A=Overfitting from hyperparameters: overfitting shows as high training accuracy with worse validation accuracy; here validation is also near perfect because the leaked feature is present there too.
B=Class imbalance from date format: the format of a date column does not change how many churned and retained customers there are; imbalance is a property of the label distribution.
D=Underfitting: an underfit model performs poorly on both training and validation data, the opposite of the near-perfect accuracy observed.
T: A near-perfect score driven by a feature that only exists after the outcome is target leakage, not overfitting or underfitting; remove such features.

G: ## Why annotators disagree
Human labels contain noise: people get tired, interpret guidelines differently, or face genuinely ambiguous images. A single annotation per item turns each individual mistake into a wrong training label.
## Consolidation
- Send each item to several annotators (for example three or five).
- **Consolidate** the answers: majority vote for classes, or averaging and weighting for boxes. SageMaker Ground Truth does this with annotation consolidation, which can weight workers by their estimated accuracy.
- **Audit disagreements**: items where annotators split are routed to an expert reviewer (Ground Truth supports label verification and adjustment jobs, and Amazon Augmented AI supports human review workflows). Frequent disagreement on a class often means the labeling instructions need to be clearer.
Example: three workers label an image "cat", "cat", "fox". The consolidated label is "cat", but because agreement is only 2 of 3, the item is flagged for review.
W: Multiple annotations with consolidation and audits: combining several independent labels cancels individual mistakes, and reviewing disagreements fixes the truly ambiguous items and the guidelines behind them.
X: A=Model labels its own data: a model trained on its own predictions reinforces its existing mistakes instead of correcting them, because nothing independent checks the labels.
B=Remove every hard image: dropping all difficult examples removes exactly the edge cases the model must handle and makes the dataset unrepresentative of production.
C=Use only the first annotation: throwing away the other annotators' answers keeps each first annotator's errors and wastes the information needed to detect them.
T: Improve noisy human labels by collecting several per item, consolidating them and auditing disagreements, not by trusting one person or the model itself.

G: ## Why raw dates are hard for models
A timestamp like `2025-11-14 18:32:05` is almost unique per row. Weekly or monthly patterns (weekend spikes, month-end payments) are hidden inside it.
## Extracting calendar components
Split the date into features that repeat:
- `day_of_week` (0-6), `is_weekend`
- `month` (1-12), `day_of_month`, `is_month_end`
- `hour`, `quarter`, `is_holiday` (from a holiday calendar)
A tree model can then split on `day_of_week >= 5` to learn "sales are higher on weekends" or on `month == 12` for holiday season. For linear or neural models, cyclical encodings such as sine and cosine of the day of week are sometimes added so that Sunday and Monday are close.
Example: an electricity demand model gains accuracy once `hour` and `day_of_week` are added, because consumption follows daily and weekly cycles.
W: Extract components such as day of week and month: these repeating features expose weekly and monthly cycles directly, so tree splits can capture them.
X: A=One-hot every unique timestamp: each timestamp becomes its own column with a single 1, so no two rows share a value and nothing generalizes to new dates.
C=Drop the date: trees cannot use a raw date string, but dates are very informative once converted into numeric calendar features, so dropping them discards useful signal.
D=One large integer only: an epoch number increases steadily, so the model can learn a trend but cannot see that every Monday or every December is similar.
T: Turn dates into calendar components so repeating patterns become visible; unique timestamps or a single epoch value hide periodicity.

G: ## Representative training data
A model generalizes only to data that looks like what it was trained on. If the training set differs from what production sends, accuracy in production drops even when validation looks good. This mismatch is called **training-serving skew** or, over time, **data drift**.
## Two practical checks
- **Distribution comparison**: compare each feature's distribution in training data with recent production data (histograms, mean and percentiles, or statistics such as KL divergence and population stability index). - **Segment coverage**: confirm that important groups (regions, device types, customer tiers, age groups) appear in reasonable proportions. SageMaker Clarify class imbalance metrics help for sensitive groups.

W: C=Segment proportions: checking that key groups are adequately represented catches training data that ignores parts of the real population.
E=Compare feature distributions with production: aligning training statistics with recent production data directly measures whether the model will see familiar inputs.
X: A=File naming pattern: consistent file names help organization and automation but say nothing about whether the values inside reflect production.
B=CSV instead of Parquet: storage format affects size and read speed; the same records in either format are equally representative or unrepresentative.
D=Weekday-only collection: restricting data to weekdays removes weekend behavior, which makes the training set less representative, not more.
T: Representativeness is about content: compare distributions with production and check segment coverage; file format and naming are irrelevant.

G: ## Multicollinearity
Two features are collinear when one is nearly a linear function of the other, for example `house_size_sqft` and `house_size_m2`, or `total_spend` and `num_orders x average_order`.
In a linear model, the effect can be split between them in countless ways: 10 and 0, 5 and 5, or 100 and -90 all give similar predictions. Small data changes then swing the coefficients wildly and they become hard to interpret, even if overall predictions look fine.
## Remedies
- **Drop one** of the pair (check with a correlation matrix or variance inflation factor, VIF).
- **Combine** them into one feature (a ratio, a sum, or a principal component from PCA).
- **Regularize**: L2 (ridge) shrinks correlated coefficients toward similar, small values; L1 (lasso) tends to keep one and zero the other. SageMaker Linear Learner supports both through `wd` (L2) and `l1` hyperparameters.
W: Remove one feature, combine them, or apply regularization: each removes the redundancy or penalizes large offsetting coefficients, so the estimates become stable.
X: A=Convert to text strings: turning numbers into strings discards their numeric meaning and would require encoding again; it does not address the correlation.
B=Increase the learning rate: the learning rate only changes how fast the optimizer moves; collinearity is a property of the data, and a higher rate can even make training unstable.
D=Duplicate both features: exact copies are perfectly collinear, which makes the coefficient instability worse, not better.
T: Fix collinear features by dropping, combining or regularizing them; optimizer settings and duplication do not change the redundancy.

G: ## Label noise
When labels come from heuristics or rules, some are wrong. With a 10% error rate, the model is partly trained to reproduce the rule's mistakes, and, just as important, evaluation against the same labels cannot tell you how accurate the model really is.

G: ## Leakage in feature engineering
Leakage happens when information from outside the training data (validation rows, test rows, or the outcome itself) influences features the model learns from. The model then looks better in evaluation than it will be in production.
## Common leak sources
- Fitting a scaler, imputer or encoder on the whole dataset: the mean used for scaling already includes test rows.
- Target encoding (replacing a category with its average label) computed across all rows, including those being evaluated.
- Features created after the outcome (for example "refund issued" when predicting fraud).
## Safe practice
- **Fit on training data only**: within cross-validation, fit transforms on the training folds and apply them to the held-out fold.
- **Use pipelines**: bundle preprocessing and model together (for example a scikit-learn `Pipeline`, or a SageMaker inference pipeline) so the exact fitted steps are reused at inference and in validation.
W: D=Pipelines with the same fitted steps: packaging fitted preprocessing with the model ensures validation and inference use training-derived statistics only, with no refitting on new data.
E=Fit transformations on training folds only: statistics such as means, scales and encodings never see the validation or test rows, so nothing leaks from them.
X: A=Post-outcome features: features that exist only after the outcome encode the label itself and are unavailable at prediction time.

G: ## Anomaly detection without labels
Labeled anomaly data is rare: spikes are infrequent and nobody has tagged them. An unsupervised method learns what normal looks like and flags points that differ.
## SageMaker Random Cut Forest (RCF)
- RCF builds many random trees, each by repeatedly cutting the data along randomly chosen dimensions.
- Normal points sit in dense regions and need many cuts to isolate; unusual points are isolated after few cuts.
- Each data point receives an **anomaly score**; a common rule flags scores more than about three standard deviations above the mean score.
- Training needs no labels. You can use shingling (sliding windows) so the model sees short sequences of a metric instead of single values.
Example: CPU utilization normally ranges from 20% to 60%; a sudden jump to 98% at 3 a.m. receives a high score and triggers an alert.
W: Random Cut Forest: it is an unsupervised algorithm that assigns anomaly scores to data points, so it detects spikes without any labeled anomalies.
X: A=XGBoost classifier: a classifier learns from labeled examples of each class, and there is no labeled anomaly data to train it on.
C=Factorization Machines: this is a supervised algorithm for sparse, high-dimensional data such as recommendations; it needs labels and is not an anomaly detector.
D=Linear Learner: Linear Learner performs supervised regression or classification, which requires target labels that do not exist here.
T: No labels plus the need to find unusual points means unsupervised Random Cut Forest; supervised algorithms need labeled anomalies.

G: ## Sparse interaction data
Recommendation data is usually encoded with one-hot columns for each user and each item. With 1 million users and 100,000 items, each row has only a handful of non-zero values among more than a million columns. Most user-item pairs have never been observed.
## SageMaker Factorization Machines
Factorization Machines is a supervised algorithm for classification or regression on such sparse, high-dimensional input.
- Besides a linear term per feature, it models **pairwise interactions** between features by giving each feature a small latent vector; the interaction strength is the dot product of those vectors.
- Because latent vectors are shared, it can estimate interactions for user-item pairs that never appeared together in training.
- Input is typically `recordIO-protobuf` with `Float32` values, which stores sparse data efficiently.
Example: predict whether a user will click a movie from sparse user ID, movie ID and genre features.
W: Factorization Machines: it is built to learn feature interactions in very sparse, high-dimensional data, which is exactly the user-item recommendation case.
X: A=DeepAR forecasting: DeepAR predicts future values of time series; user-item interactions are not a sequence to forecast.
B=Image Classification: this algorithm assigns labels to images using a convolutional network; it has no notion of users, items or sparse feature interactions.
D=Semantic Segmentation: this labels each pixel of an image; it is a computer vision algorithm unrelated to recommendation data.
T: Sparse user-item recommendation data points to Factorization Machines; forecasting and vision algorithms do not model sparse interactions.
