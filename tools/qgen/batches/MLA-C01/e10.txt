G: ## Reading the train/validation gap
A model is evaluated on data it trained on (training accuracy) and data it has not seen (validation accuracy). The gap between the two is the key signal.
- **Overfitting**: high training accuracy, much lower validation accuracy. The model memorized noise and details of the training set instead of general patterns.
- **Underfitting**: both scores are low.
Here 99% versus 70% is a classic overfitting gap.
## Standard fixes
- **Regularization** limits how complex the learned function can be. L2 penalizes large weights; dropout randomly disables neurons during training so the network cannot rely on single paths.
- **Early stopping** watches validation loss after each epoch and stops (keeping the best weights) once it stops improving, before the model starts memorizing.
- Other options: more or augmented training data, fewer features, a simpler model.
W: B=Early stopping on validation loss: it halts training at the point where the model generalizes best, before further epochs widen the gap between training and validation performance.
E=L2 or dropout regularization: both constrain the model so it learns smoother, more general patterns rather than memorizing the training set, which directly narrows the gap.
X: A=Many more epochs: more passes over the same data let the model memorize it even more, so training accuracy rises further while validation accuracy stays flat or drops.
C=Removing the validation set: this only removes the evidence of overfitting. The model would still perform at about 70% on real unseen data.
D=More layers: adding capacity gives the model even more ability to memorize, which usually makes overfitting worse, not better.
T: A large train-validation gap means overfitting: constrain the model (regularization) and stop at the best validation point (early stopping) instead of adding capacity or epochs.

G: ## Diagnosing with training and validation error
Comparing the two errors tells you which way the model is failing:
- **Low training error, high validation error**: overfitting (high variance). The model is too flexible for the data.
- **High training error and high validation error**: underfitting (high bias). The model cannot even fit the data it trains on, so it certainly cannot generalize.
## Fixing underfitting
- Use a more expressive model: a deeper tree ensemble, more layers or units, or a non-linear model instead of a linear one.
- Improve features: add informative variables, interactions, or better encodings so the pattern is learnable.
- Reduce regularization and train longer if the model has not converged.
Example: a linear model predicting delivery time from distance only misses traffic and time of day; adding those features and using gradient-boosted trees lowers both errors.
W: Underfitting with more capacity or better features: when the model does badly even on its own training data, it lacks the capacity or the signal to learn the pattern, so giving it a stronger model or better features is the direct fix.
X: A=Data leakage: leakage lets information about the label slip into features, which usually makes scores look too good, not uniformly poor. Changing features in the validation set only would also make training and validation inconsistent.
C=Class imbalance by deleting the majority class: imbalance typically shows up as poor minority-class recall, not high error everywhere, and throwing away most of the data would make an underfit model even weaker.
D=Overfitting with more regularization: overfitting means low training error, which is not the case here. Extra regularization and dropout reduce capacity and would push both errors higher.
T: High error on both training and validation data is underfitting; add capacity or better features, whereas regularization is the cure for the opposite problem.

@ Q003599 explain
G: ## Search strategies in SageMaker Automatic Model Tuning
Automatic Model Tuning (AMT) runs many training jobs with different hyperparameter values and keeps the best by an objective metric such as `validation:auc`. How it picks the next values matters for cost.
- **Grid search** tries every combination of listed values. Five values for each of four hyperparameters is 5^4 = 625 jobs.
- **Random search** samples combinations independently; cheap and parallel, but it does not learn from earlier results.
- **Bayesian optimization** builds a model of how hyperparameters relate to the metric from the jobs finished so far and chooses the next values where improvement looks most likely.
- **Hyperband** runs many configurations briefly and gives more resources to the promising ones.
Because Bayesian search learns as it goes, it usually reaches a good configuration in far fewer jobs than grid search.
W: Bayesian optimization in AMT: it uses the results of completed training jobs to choose the next hyperparameter values, so it concentrates on promising regions and needs fewer jobs than exhaustively testing a grid.
X: A=Manual weekly changes: one change per week based on intuition is slow, unrepeatable and ignores interactions between hyperparameters; it is neither efficient nor systematic.
B=Exhaustive grid search: the number of jobs grows multiplicatively with each hyperparameter and value, which is the expensive behavior the team wants to avoid.
C=Same defaults everywhere: default values are a starting point, not tuned for each dataset, so this skips tuning rather than doing it efficiently.
T: When tuning must use fewer jobs than grid search, pick Bayesian optimization, which learns from earlier runs instead of trying every combination.

G: ## Stopping hopeless tuning jobs early
A tuning job launches many training jobs. Some configurations are clearly bad after a few epochs, yet by default each job runs to its full length and you pay for all of that compute.
SageMaker Automatic Model Tuning offers two ways to cut this waste:
- **Early stopping** (`TrainingJobEarlyStoppingType` set to `Auto`): the tuner compares each job's intermediate objective metric with earlier jobs at the same point and stops jobs that are unlikely to beat the best result.
- **Hyperband strategy**: starts many configurations with a small budget and only continues the best-performing ones, with its own internal early stopping, so the separate `TrainingJobEarlyStoppingType` setting is left `Off` when Hyperband is used.
The training algorithm must emit the objective metric during training (for example per epoch) for these features to judge progress.
W: Early stopping or Hyperband: both end underperforming training jobs after a few epochs based on their intermediate metrics, so compute is spent only on configurations that still have a chance of winning.
X: A=Run everything to completion: this is exactly the current wasteful behavior; poor jobs keep consuming instance hours until their last epoch.
B=More concurrent jobs: higher concurrency makes the tuning job finish sooner in wall-clock time but still runs every bad job fully, and it can reduce how much Bayesian search learns between rounds.
D=Larger instances: bigger instances cost more per hour and still run the bad configurations to the end, so waste goes up rather than down.
T: To stop paying for obviously bad tuning trials, enable early stopping or use Hyperband; concurrency and instance size do not remove wasted runs.

G: ## Managed Spot Training and interruptions
SageMaker managed spot training runs training jobs on spare EC2 capacity at a large discount compared with On-Demand. The trade-off: Spot capacity can be reclaimed with a two-minute warning, interrupting the job.
- You set `EnableManagedSpotTraining`, `MaxRuntimeInSeconds` and `MaxWaitTimeInSeconds` (total time including waiting for Spot capacity).
- With **checkpointing**, the training script periodically saves model state to a local path that SageMaker syncs to an S3 `CheckpointConfig` location.
- When capacity returns, SageMaker restarts the job, copies the checkpoints back, and the script resumes from the latest one instead of epoch 1.
Example: a 10-hour job interrupted at hour 8 resumes from its last checkpoint rather than repeating 8 hours of paid compute.
W: Checkpointing to S3 with managed spot training: saved checkpoints survive the interruption, and the restarted job loads them to continue where it left off, so progress is not lost.
X: B=More epochs per job: this makes each job longer and therefore more likely to be interrupted, and it saves nothing when an interruption happens.
C=Smaller batch size: batch size affects memory use and training dynamics, but the model state still lives only on the instance and disappears when Spot capacity is reclaimed.
D=Disabling shuffling: shuffling controls the order in which examples are seen; turning it off can hurt model quality and does nothing to persist progress across an interruption.
T: Spot interruptions are survived by checkpointing to S3, which managed spot training restores automatically; training settings like epochs or batch size do not preserve state.

@ Q003602 explain
G: ## Data parallelism versus model parallelism
Distributed training comes in two main forms:
- **Data parallelism**: every GPU holds a full copy of the model and processes a different slice of each batch; gradients are then averaged. It speeds up training but requires the whole model (weights, gradients, optimizer state, activations) to fit on each GPU.
- **Model parallelism**: the model itself is split across GPUs, for example different layers on different devices (pipeline parallelism) or large weight matrices split across devices (tensor parallelism). Each GPU holds only part of the model.
Sharded approaches such as fully sharded data parallelism also spread parameters and optimizer state across GPUs. SageMaker provides a model parallelism library for PyTorch to handle these techniques.
Example: a model needing 120 GB of GPU memory cannot run on an 80 GB GPU, but split across several GPUs each holds a manageable share.
W: Model parallelism across GPUs: when the model's memory footprint exceeds one GPU, splitting its layers or tensors across several devices is the approach that lets it train at all.
X: A=Smaller dataset: the dataset streams from storage in batches; GPU memory is consumed by the model parameters, gradients and activations, so fewer training rows do not make the model fit.
C=CPU instances with more RAM: the model might fit in host memory, but training a large deep learning model on CPUs is dramatically slower than on GPUs, making it impractical.
D=Data parallelism with the full model per GPU: each GPU still needs the entire model, so the same out-of-memory error occurs on every device.
T: Too big for one GPU means split the model (model parallelism); data parallelism only helps when a full model copy fits on each GPU.

@ Q003603 explain
G: ## Scaling training when the model fits
If a model fits on one GPU but the dataset is huge, the bottleneck is the number of examples to process, not memory.
**Distributed data parallel** training solves this:
- Each GPU (on one or many instances) holds a full model copy.
- Each global batch is split so every GPU processes a different shard of data at the same time.
- Gradients are averaged across GPUs (all-reduce), so all copies stay identical after each step.
With 8 GPUs, each epoch processes roughly 8 times as many examples per step, cutting training time substantially (minus communication overhead). SageMaker supports this with PyTorch DDP and its own distributed data parallel library, and usually the learning rate or batch size is adjusted when scaling out.
W: Distributed data parallel training: the model fits on each GPU, so splitting the data across many GPUs processes the dataset in parallel and directly reduces training time.
X: A=Model parallelism: splitting layers is meant for models that do not fit on one GPU. For a model that fits, it adds communication and idle time between devices without the throughput gains of data parallelism.
B=Smaller learning rate on one GPU: a smaller learning rate usually needs more steps to converge, so training would take longer, and one GPU still processes the whole dataset alone.
D=Single CPU instance: more CPU cores cannot match GPU throughput for deep learning matrix operations, so training would get slower, not faster.
T: Model fits but data is huge means data parallelism; model parallelism is for models that are too big for one device.

During backpropagation, gradients are multiplied layer by layer. In deep networks with certain activations (such as sigmoid) or poor initialization, they can shrink toward zero before reaching early layers, so those layers stop learning and training loss plateaus.

@ Q003605 explain
G: ## Precision and recall from the confusion matrix
For a binary classifier, predictions fall into four cells: true positives (TP), false positives (FP), true negatives (TN) and false negatives (FN).
- **Recall (sensitivity)** = TP / (TP + FN): of all real positives, how many did the model catch?
- **Precision** = TP / (TP + FP): of everything flagged positive, how many really were positive?
- **Accuracy** = (TP + TN) / all predictions.
Example: 1,000 patients, 10 with the disease. A model that always says "healthy" is 99% accurate but has 0% recall: it misses every sick patient.
In screening, a missed case (FN) is the costly error, so the model is tuned to maximize recall, accepting more false alarms that later tests can rule out.
W: Recall (sensitivity): it directly measures the share of actual positive cases that the model identifies, so maximizing it minimizes missed diagnoses.
X: A=Overall accuracy: with rare positives, accuracy is dominated by the many negatives and can look excellent while most positive cases are missed.
B=Training loss: it is an optimization quantity on the training data, not an evaluation of how many real positive cases the model misses on unseen data.
D=Precision only: precision penalizes false positives (false alarms), not false negatives, so a model can have high precision while still missing many sick patients.
T: When missing a positive is the worst error, prioritize recall; precision is for when false alarms are the costly error.

@ Q003606 explain
G: ## Which error hurts: false positives or false negatives
In a spam filter, "positive" means "spam".
- A **false positive** is a legitimate email sent to the spam folder: the user may miss an important message.
- A **false negative** is spam that reaches the inbox: annoying but less harmful.
**Precision** for the spam class = TP / (TP + FP). High precision means that when the filter says "spam", it is almost always right, so few legitimate emails are flagged.
**Recall** for the spam class = TP / (TP + FN) measures how much spam is caught.
Example: flagging 100 emails with 98 real spam gives 98% precision; the 2 wrongly flagged emails are the errors the business wants to minimize. Raising the decision threshold usually increases precision at the cost of recall.
W: Precision for the spam class: it falls whenever legitimate emails are wrongly flagged, so it is the metric that directly tracks the requirement to rarely misclassify good mail.
X: A=Recall for spam: recall rewards catching as much spam as possible; a filter can reach high recall by flagging aggressively, which increases the false positives the business wants to avoid.
C=Mean absolute error: MAE measures the average absolute difference for continuous numeric predictions (regression), not correct versus incorrect class labels.
D=R-squared: R-squared measures how much variance a regression model explains; it has no meaning for spam or not-spam decisions.
T: When false positives are the costly mistake, optimize precision; when missed positives are costly, optimize recall.

G: ## Threshold-independent classifier metrics
A binary classifier outputs a score, and a threshold (often 0.5) turns it into a label. Metrics such as accuracy, precision and recall change as the threshold moves. To compare models fairly regardless of threshold, sweep all thresholds and summarize the curve:
- **ROC AUC**: area under the curve of true positive rate versus false positive rate. 0.5 is random, 1.0 is perfect. It measures how well the model ranks positives above negatives.
- **PR AUC** (area under the precision-recall curve): focuses on the positive class. With rare positives it is often more informative than ROC AUC, because a large number of true negatives can make the false positive rate look small.
Example: in fraud detection with 0.5% fraud, two models can share a ROC AUC of 0.95 yet differ clearly in PR AUC.
W: D=PR AUC: it summarizes precision and recall across every threshold and concentrates on the minority positive class, which makes it well suited to imbalanced data.
E=ROC AUC: it summarizes the trade-off between true and false positive rates across all thresholds, giving a single threshold-independent measure of ranking quality.
X: A=Accuracy at 0.5: it depends on one fixed threshold and, on imbalanced data, can look high simply by predicting the majority class.
B=Number of epochs: the epoch count is a training setting, not a measure of how well the classifier separates the classes.
C=RMSE: root mean squared error is a regression metric for continuous targets and does not evaluate class separation across thresholds.
T: To compare classifiers without picking a threshold, use ROC AUC and PR AUC, with PR AUC being especially telling when positives are rare.

@ Q003609 explain
G: ## Regression error metrics
For a model that predicts a number, such as a house price, error metrics compare predicted and actual values:
- **MAE** (mean absolute error): average of absolute errors, in the target's units.
- **RMSE** (root mean squared error): square the errors, average them, then take the square root. Squaring punishes large misses more, and the square root brings the result back to the target's units.
- **MSE**: like RMSE without the square root, so it is in squared units (dollars squared), which is hard to interpret.
- **R-squared**: share of variance explained, unitless.
Example: errors of $10,000, $20,000 and $30,000 give MAE $20,000 and RMSE about $21,600, so a stakeholder reads RMSE as "typical error around $22K".
W: RMSE: it is the square root of the mean squared error, so it is expressed in the same currency as the price and describes the typical size of a prediction error.
X: B=F1 per price band: F1 combines precision and recall for class labels; turning prices into bands discards the actual numeric error.
C=Precision at top 10: this is a ranking or recommendation metric about whether the top results are relevant, not how far a predicted value is from the real one.
D=ROC AUC: it measures how well a binary classifier ranks positives above negatives and has no notion of numeric distance from a true price.
T: For regression, RMSE and MAE report error in the target's own units; F1, precision at k and AUC belong to classification and ranking.

G: ## The learning rate and convergence
Gradient descent updates weights by `learning_rate x gradient` each step.
- **Too high**: steps overshoot the minimum, bouncing from side to side, so loss oscillates wildly or even diverges to `NaN`.
- **Too low**: loss decreases smoothly but very slowly and can stall.
- **Well chosen**: loss drops quickly, then flattens smoothly.
Example: if a learning rate of 0.1 makes loss jump between 0.4 and 2.0, trying 0.01 or 0.001 usually produces a steady decline. Learning-rate schedules (warm-up, decay) and adaptive optimizers such as Adam also help, and AMT can search the learning rate on a log scale.
W: Reduce the learning rate: smaller update steps stop the optimizer from overshooting the minimum, which is the typical cause of wildly oscillating, non-converging loss.
X: A=Increase the learning rate: larger steps overshoot even more, making oscillation worse and risking divergence.
B=Remove regularization: regularization limits model complexity to fight overfitting; it is not what makes the loss jump around, and removing it does not stabilize optimization.
C=More classes: the number of classes is fixed by the problem's labels; changing it would alter the task rather than fix unstable training.
T: Wildly oscillating loss points to a learning rate that is too high; lower it (or use a schedule) rather than raising it or changing unrelated settings.

G: ## Cutting training time and cost
Two widely used levers on SageMaker:
- **Mixed-precision training**: most operations run in 16-bit floating point (FP16 or BF16) while critical values stay in FP32. Modern GPUs have Tensor Cores that run 16-bit math much faster, and 16-bit activations use less memory, allowing larger batches. - **Managed spot training**: jobs run on spare EC2 capacity at a large discount compared with On-Demand. Checkpoints saved to S3 let an interrupted job resume instead of restarting.
Other good practices: transfer learning from pre-trained weights, parallel data loading, and right-sizing instances.
W: A=Mixed-precision training: 16-bit computation on GPUs with Tensor Cores speeds up math and reduces memory, so jobs finish faster and use fewer instance hours.
E=Managed spot training with checkpoints: Spot capacity lowers the price per hour substantially, and checkpoints ensure interruptions do not throw away completed work.
X: B=Disabling data loader parallelism: loading and preprocessing batches serially leaves expensive GPUs waiting for input, making training slower and costlier.
C=Always random weights: starting from scratch usually needs far more data and epochs than fine-tuning pre-trained weights, so it increases time and cost.

T: Faster math (mixed precision) and cheaper capacity (Spot with checkpoints) cut deep learning training cost; serial loading and oversized instances waste it.

G: ## The confusion matrix
For a binary classifier, a common layout puts actual classes in rows and predicted classes in columns, giving four cells:
- **True positive (TP)**: actually positive, predicted positive.
- **False positive (FP)**: actually negative, predicted positive (a false alarm).
- **True negative (TN)**: actually negative, predicted negative.
- **False negative (FN)**: actually positive, predicted negative (a miss).
Memory aid: the second word is what the model predicted, and "false" says the prediction was wrong. A false negative is therefore a wrong "negative" prediction for a real positive.
Example: a fraud model with 40 FN let 40 fraudulent transactions through as legitimate. Many FNs mean low recall, and lowering the decision threshold is a common way to reduce them.
W: Actual positives predicted as negative: that is the definition of a false negative, the model missed cases that were really positive.
X: A=No negative examples: false negatives are counted among actual positives and say nothing about whether negatives exist; a real dataset usually contains many negatives.
B=Actual negatives predicted positive: this describes false positives, the opposite error from the one shown in the matrix.
D=Perfect positive predictions: many false negatives mean the model is missing positive cases, which is the opposite of predicting positives perfectly.
T: A false negative is a missed positive (actual positive, predicted negative); a false positive is a false alarm on an actual negative.

G: ## Why aggregate metrics are not enough
An overall metric is an average across all records. If one customer segment is small, its poor results barely move the average.
Example: 95% overall accuracy can hide 70% accuracy for a segment that makes up 5% of the data.
## Segment-level evaluation
- Slice evaluation results by segment (region, age band, product line) and compute metrics for each slice.
- Investigate causes: too few training examples for the segment, missing or poor-quality features, labels that behave differently, or a distribution shift.
- Fix with more or better data for that segment, reweighting or resampling, new features, or a model that handles the segment better, then re-evaluate.
SageMaker Clarify can compute post-training bias metrics that compare model performance across groups, such as differences in accuracy or recall, to support this analysis.
W: Evaluate per segment and fix the gaps: measuring metrics for each segment exposes where the model fails, and addressing the underlying data or model causes improves it for those customers before they are affected.
X: A=Deploy anyway: the overall target is met only because the segment's poor performance is averaged away; those customers would still receive bad predictions in production.
C=Raise that segment's threshold: a segment-specific threshold only shifts the trade-off between false positives and negatives; it does not repair the model's weak signal, and treating a group differently without analysis can create fairness and compliance issues.
D=Remove the segment from evaluation: this inflates the reported score while leaving the model just as bad for those customers, hiding the problem rather than solving it.
T: Good overall numbers can hide segment failures; evaluate per segment and fix the data or model, rather than deploying anyway or manipulating thresholds and test sets.

Amazon Rekognition detects common objects, scenes and faces out of the box, but not your own product categories. **Rekognition Custom Labels** adds that:
- Upload labeled images (for example to Amazon S3, organized by folder per class) or label them in the console.
- Rekognition trains a model using transfer learning from its pre-trained vision models, so a relatively small number of images per class (often tens to a few hundred) can be enough.
- Review evaluation metrics (precision, recall, F1 per label), then start the model and call it through an API.
Example: 20 product categories with a few hundred photos each can become a classifier without writing training code.
W: Rekognition Custom Labels: it builds image classifiers for your own categories from a modest labeled image set, using managed transfer learning so little ML expertise is needed.
X: A=Comprehend custom classification: Comprehend is a natural language service; its custom classifiers categorize text documents, not images.
C=Textract queries: Textract extracts text, forms and tables from scanned documents, and queries ask for specific fields in them; it does not assign product categories to photos.
D=Forecast predictors: Amazon Forecast predicts future values of time series such as demand (and has been closed to new customers since 2024); it does not classify images.
T: Custom image categories from a small labeled set with little ML skill point to Rekognition Custom Labels; Comprehend, Textract and Forecast handle text, documents and time series.

G: ## Experiment tracking
Over many training runs, a team needs to record, for each run, the hyperparameters, metrics (loss, accuracy per epoch), code version and output model, and then compare runs side by side.
**MLflow** is a widely used open-source tool for this. SageMaker offers **managed MLflow**:
- AWS hosts and scales the MLflow tracking server, so the team does not run it.
- Training scripts call `mlflow.log_param`, `mlflow.log_metric` and `mlflow.log_artifact` (or use autologging) against the managed server.
- The MLflow UI compares runs with charts and tables, and models can be registered and linked to SageMaker Model Registry.
Example: 50 runs of a churn model with different learning rates can be sorted by validation AUC to find the best one.
W: Managed MLflow experiment tracking: it records parameters, metrics and artifacts for every run in one place and provides comparison views, which is exactly what experiment tracking means.
X: B=S3 server access logs: they record requests made to a bucket (who read or wrote which object), not training hyperparameters or model metrics.
C=CloudTrail management events: they record API calls such as `CreateTrainingJob` for auditing; they do not capture per-epoch metrics or let you compare model quality across runs.
D=AWS Config history: Config tracks configuration changes of AWS resources for compliance; it knows nothing about the results of training runs.
T: Comparing training runs by parameters and metrics is experiment tracking (managed MLflow); S3 logs, CloudTrail and Config are audit and compliance records.

G: ## Choosing a decision threshold by cost
A classifier outputs a score; the threshold decides which scores become "positive". Moving it trades false positives against false negatives. When the two errors have different costs, the best threshold minimizes total expected cost:
`expected cost = FP_count x cost_FP + FN_count x cost_FN`
Steps:
- Score a validation set that reflects production.
- For each candidate threshold (for example 0.05 to 0.95), count FP and FN.
- Multiply by the business cost of each error, sum, and choose the threshold with the lowest total.
Example: if a missed fraud costs $500 and a false alarm costs $5 in review time, the minimum-cost threshold will be well below 0.5, flagging more transactions.
W: Expected cost across thresholds: calculating the business cost at each threshold and picking the minimum aligns the model's decisions with the real impact of each type of error.
X: A=Fewest positive predictions: pushing the threshold high minimizes false positives but lets false negatives pile up, ignoring their cost entirely.
B=Always 0.5: 0.5 is a convention that implicitly treats both errors as equally costly and assumes calibrated scores; it rarely matches real business costs.
C=Maximize accuracy: accuracy counts every error the same, so with asymmetric costs the most accurate threshold can still be the expensive one.
T: When false positives and false negatives cost different amounts, pick the threshold that minimizes expected business cost, not the default 0.5 or maximum accuracy.

G: ## Interpretability versus accuracy
- **Interpretable models** such as linear or logistic regression, small decision trees or scorecards expose their logic directly: each feature's weight or split explains a decision.
- **Complex models** such as large gradient-boosted ensembles or deep networks are often more accurate but act as "black boxes".
When regulations require explanations for individual decisions (for example why a loan was denied), a team can:
- Prefer the interpretable model if the accuracy loss is small and acceptable, or
- Use the complex model together with robust post-hoc explanation tools, such as SHAP values from SageMaker Clarify, validated for consistency, documented, and reviewed as part of model governance.
Either way, the explanation requirement is treated as a hard constraint, not a trade-off against a few points of accuracy.
W: Interpretable model or complex model with robust explanations: both paths meet the regulatory need to explain individual decisions, and the choice depends on how much accuracy the simpler model gives up.
X: A=Most parameters: more parameters do not guarantee higher accuracy (they can overfit), and choosing by size ignores the explainability requirement.
B=Avoid ML entirely: many models can be explained, either inherently or with tools like SHAP, so abandoning ML is unnecessary.
D=Complex model with no explanations: this directly violates the regulatory requirement, regardless of any accuracy gain.
T: When regulators require individual explanations, choose an interpretable model or pair a complex one with robust explanation tooling; accuracy never replaces compliance.
