# SAA-C03 batch 05: Domain 1 (secure architectures), continued
@ SAA-C03 D1 T1.1 applied use-case
S: A company wants to grant a contractor temporary access to one S3 bucket for two weeks without creating long-term credentials. Which approach fits?
A: An IAM role the contractor can assume with a scoped policy and limited session duration
B: An IAM user with access keys that the contractor must promise to delete afterward
C: The company administrator's credentials shared for the two-week project period
D: A bucket policy that allows public read and write access for the two weeks
K: A
W: Role assumption provides temporary credentials with scoped permissions.
X: B=Access keys are long-term credentials. | C=Sharing admin credentials is insecure. | D=Public access exposes data.
T: Temporary access → assumable roles, not users or shared keys.
V: AWS IAM, AWS STS

@ SAA-C03 D1 T1.1 advanced use-case
S: A policy allows s3:* on a bucket, but a user still gets Access Denied. The bucket belongs to another account. What is the most likely cause?
A: The bucket policy in the owning account does not grant the user access
B: The user's password has expired and must be reset in the console
C: The S3 bucket is in a Region that the user's policy does not name
D: The user needs MFA only for console access, not for API calls
K: A
W: Cross-account access requires permission from both the caller's identity policy and the resource owner's bucket policy.
X: B=Password expiry affects console sign-in, not API permissions here. | C=S3 permissions do not require naming Regions. | D=MFA is not implied as the cause.
T: Cross-account access needs both identity and resource policy grants.
V: AWS IAM, Amazon S3

@ SAA-C03 D1 T1.2 applied use-case
