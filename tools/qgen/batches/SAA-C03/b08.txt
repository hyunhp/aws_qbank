# SAA-C03 batch 08: D1 secure architectures (15) + D4 cost-optimized architectures (10), detailed explanations

@ SAA-C03 D1 T1.1 advanced use-case
S: A security team must guarantee that no principal outside the company's AWS organization can read data from any S3 bucket in its 60 member accounts, even if a developer later writes a bucket policy that grants access to an external account. Which solution meets this requirement with the LEAST ongoing effort?
A: Attach a resource control policy (RCP) to the organization root that denies S3 access when aws:PrincipalOrgID does not match the organization
B: Attach a service control policy (SCP) to the organization root that denies S3 access when aws:PrincipalOrgID does not match the organization
C: Enable S3 Block Public Access at the account level in every member account and turn on IAM Access Analyzer for all of those accounts
D: Deploy an AWS Config rule that detects external principals in bucket policies and triggers a Lambda function to remove the offending statements
K: A
W: Resource control policy: an RCP sets the maximum permissions on the resources in member accounts, whoever the caller is. A deny for callers whose `aws:PrincipalOrgID` is not the organization therefore blocks external accounts even when a bucket policy grants them access, and it is set once at the root.
X: B=Service control policy: SCPs only limit principals that belong to the organization's own accounts. A role in an external account is not governed by the company's SCPs, so a permissive bucket policy would still let it in.
C=Block Public Access plus Access Analyzer: Block Public Access stops public (anonymous or everyone) grants, but a grant to one specific external account ID is not public. Access Analyzer only reports such access after the fact; it does not prevent it.
D=Config rule with Lambda remediation: this is detective and reactive. Between the policy change and the remediation run the external account can read data, and the custom rule and function must be maintained.
T: SCPs cap what your own principals can do; RCPs cap what anyone can do to your resources, which is how you build an organization-wide data perimeter.
G: ## Two kinds of organization guardrails
AWS Organizations offers two authorization policy types that set a ceiling on permissions but never grant anything:
- **Service control policies (SCPs)** apply to IAM users and roles *in* member accounts. They answer "what may my principals do?"
- **Resource control policies (RCPs)** apply to resources *in* member accounts, such as S3 buckets, KMS keys, SQS queues and Secrets Manager secrets. They answer "what may anyone do to my resources?"
## Building a data perimeter
A typical RCP statement denies `s3:*` on all resources when the caller's `aws:PrincipalOrgID` is not `o-exampleorgid`, with an exception such as `aws:PrincipalIsAWSService` so AWS services acting on your behalf keep working.
Because the RCP is evaluated together with the bucket policy, an explicit deny in the RCP wins over any allow a developer writes later. Example: a bucket policy grants `s3:GetObject` to account `999988887777`; with the RCP in place the request from that account is still denied.
RCPs do not apply to resources in the management account or to actions taken by service-linked roles, so keep workload data in member accounts.
V: AWS Organizations, Amazon S3, IAM Access Analyzer

@ SAA-C03 D1 T1.1 applied use-case
S: A company with data residency rules must prevent every IAM principal in its workload accounts, including account administrators, from creating resources outside eu-west-1 and eu-central-1. Global services such as IAM, CloudFront, and Route 53 must keep working. What should a solutions architect do?
A: Opt out of all other Regions in each account's settings page so those Regions cannot be used, and leave global service endpoints enabled for every principal
B: Attach an SCP that denies all actions except global services when aws:RequestedRegion is not eu-west-1 or eu-central-1 to the workload OU
C: Attach a permissions boundary to every IAM user and role in the workload accounts that allows actions only when aws:RequestedRegion is an EU Region
D: Deploy an AWS Config rule in every Region that marks resources outside the EU as noncompliant and deletes them with an automatic remediation action
K: B
W: SCP with aws:RequestedRegion: a deny statement using `NotAction` for the global services and a `StringNotEquals` condition on `aws:RequestedRegion` blocks every Regional API call outside the two allowed Regions for all principals in the OU, and account administrators cannot remove an SCP.
X: A=Opt out of Regions: only opt-in Regions (those launched after March 2019) can be disabled. Default Regions such as us-east-1 or ap-northeast-1 are always enabled and cannot be turned off, so this leaves most Regions open.
C=Permissions boundaries: boundaries must be attached to each principal, and administrators in the account can create new roles without one or detach it. It is not a guardrail they are unable to bypass.
D=Config rule with deletion: this detects resources after they already exist outside the EU, which may already violate residency rules, and automatic deletion of workloads is risky. It does not prevent creation.
T: To restrict Regions for everyone in an account, including admins, use an SCP on aws:RequestedRegion with a NotAction exception for global services, not per-principal policies or detective rules.
G: ## How Region restriction works
Every Regional API call carries the condition key `aws:RequestedRegion`, for example `eu-west-1`. A service control policy (SCP) attached to an organizational unit (OU) can deny calls when that key is not in an approved list.
## The global service exception
Some services, such as IAM, CloudFront, Route 53, Organizations and Support, are global and their API calls are made against `us-east-1`. A plain Region deny would break them, so the statement uses `NotAction` to exclude them:
- `"Effect": "Deny"`, `"NotAction": ["iam:*", "cloudfront:*", "route53:*", ...]`
- `"Condition": {"StringNotEquals": {"aws:RequestedRegion": ["eu-west-1", "eu-central-1"]}}`
## Why an SCP
SCPs apply to every IAM user and role in the member accounts, including administrators, and they can be changed only from the management account (or a delegated administrator for policy management), never from the member account itself. The root user of a member account is also restricted.
V: AWS Organizations, AWS IAM

@ SAA-C03 D1 T1.1 applied use-case
S: A SaaS monitoring vendor asks each customer to create an IAM role that the vendor's AWS account can assume to read CloudWatch metrics. The customer's security team is worried that another vendor customer could trick the vendor into using this role by supplying the customer's role ARN. What should the customer add to the role?
A: A trust policy condition requiring sts:ExternalId to equal the unique value the vendor assigned to this customer
B: A trust policy condition requiring aws:MultiFactorAuthPresent to be true for every AssumeRole call from the vendor
C: A permissions boundary on the role that limits it to cloudwatch:GetMetricData and cloudwatch:ListMetrics actions only
D: A trust policy condition limiting aws:SourceIp to the public IP address ranges the vendor publishes for its platform
K: A
W: External ID in the trust policy: the vendor generates a unique ID per customer and always sends it on `AssumeRole`. Another customer who enters this customer's role ARN in the vendor console gets their own external ID sent, which does not match, so the vendor cannot be used as a confused deputy.
X: B=MFA condition: the vendor's automated service calls `AssumeRole` without a human present, so requiring MFA would break the integration. It also does not tell the vendor which customer the request is for.
C=Permissions boundary: limiting actions reduces what can be read, but the other customer could still read these metrics through the vendor. The problem is who triggers the assumption, not how much the role can do.
D=Source IP condition: the confused deputy attack goes through the vendor's own platform, so the calls still come from the vendor's published IP ranges and the condition would allow them.
T: For third-party cross-account roles, the external ID stops the confused deputy problem; permissions and network conditions do not, because the vendor itself is the caller.
G: ## The confused deputy problem
A "deputy" is a service that acts for many clients, such as a vendor whose single AWS account assumes roles in hundreds of customer accounts. If customer X can type customer Y's role ARN into the vendor's console, the vendor would assume Y's role on X's behalf. The vendor was "confused" into misusing its own trusted identity.
## How the external ID fixes it
- The vendor generates a unique, non-secret identifier for each customer, for example `ext-4f1a92`.
- The customer's role trust policy trusts the vendor account and adds `"Condition": {"StringEquals": {"sts:ExternalId": "ext-4f1a92"}}`.
- The vendor always passes the external ID of the customer who is logged in to its console.
When X enters Y's ARN, the vendor sends X's external ID, the condition fails, and the assumption is denied.
V: AWS STS, AWS IAM, Amazon CloudWatch

@ SAA-C03 D1 T1.1 advanced troubleshooting
S: An application on EC2 in Account A must assume a role in Account B. The role's trust policy lists arn:aws:iam::<Account-A-ID>:root as the principal. The instance profile role in Account A has only S3 permissions. The AssumeRole call returns AccessDenied. What is the MOST likely fix?
A: Replace the trust policy principal with the ARN of the EC2 service so that instances in any account can assume the role
B: Add sts:AssumeRole on the Account B role ARN to the identity policy of the instance profile role in Account A
C: Add a resource-based policy to the role in Account B that allows sts:GetSessionToken for principals in Account A
D: Enable IAM Access Analyzer in Account B so that it can approve the cross-account trust relationship for the role
K: B
W: Identity policy in the caller's account: trusting `arn:aws:iam::<Account-A-ID>:root` delegates the decision to Account A's administrators. Account A must still grant `sts:AssumeRole` on the target role ARN to the instance role; without that allow, the call is denied even though the trust policy matches.
X: A=Trust the EC2 service principal: `ec2.amazonaws.com` is used for roles that instances in the same account wear through an instance profile. It would not let a role in Account A assume the role, and trusting the service broadly would weaken security.
C=Allow GetSessionToken: `GetSessionToken` returns temporary credentials for the caller's own identity and is not how cross-account access works. The role's trust policy is already its resource-based policy, and it already allows Account A.
D=Access Analyzer approval: IAM Access Analyzer reports resources shared outside the account or organization. It has no approval step and does not change whether an `AssumeRole` call is allowed.
T: Cross-account role assumption needs both sides: the target role's trust policy must trust the caller, and the caller's identity policy must allow sts:AssumeRole on that role.
G: ## Cross-account access has two halves
When a principal in Account A calls `sts:AssumeRole` on a role in Account B, AWS checks:
- **Account B's side**: the role's trust policy must allow the caller. It can name a specific role ARN or the whole account, written as `arn:aws:iam::111122223333:root`.
- **Account A's side**: the caller's own identity-based policies must allow `sts:AssumeRole` on `arn:aws:iam::444455556666:role/ReadReports`.
## What "trusting the account root" means
`:root` does not mean only the root user. It means "any principal in that account that its administrators have allowed". The trust policy hands the final say to Account A's IAM policies. If those policies do not allow the call, the request fails with AccessDenied, even though the trust policy looks correct.
V: AWS STS, AWS IAM, Amazon EC2

@ SAA-C03 D1 T1.1 advanced use-case
S: A company has 200 project teams. Engineers sign in through IAM Identity Center, and each engineer's department and project are sent as attributes from the corporate IdP. The company wants engineers to manage only EC2 instances tagged with their own project, without writing a new policy for every new project. Which TWO actions meet this requirement? (Select TWO)
A: Enable attributes for access control in IAM Identity Center so the project attribute is passed as a session tag
B: Write one permission set policy that allows EC2 actions when aws:ResourceTag/project equals ${aws:PrincipalTag/project}
C: Create a separate permission set per project that lists the instance ARNs belonging to that project's team
D: Create an AWS Resource Groups group for each project and grant engineers access to their project's group
E: Attach an SCP per project OU that allows only EC2 actions on instances in the same OU as the engineer
K: A,B
W: A=Attributes for access control: this passes the IdP's `project` attribute into each session as the principal tag `aws:PrincipalTag/project`, so the value is available to policies.
B=One tag-matching policy: a single statement that compares `aws:ResourceTag/project` with `${aws:PrincipalTag/project}` works for all 200 projects and for any new project, because the match is computed at request time.
X: C=Permission set per project: this is role-based access control. Every new project or new instance means editing or creating a permission set, which is exactly the growth problem the company wants to avoid.
D=Resource Groups: a resource group is a way to view and act on tagged resources. It is not an authorization mechanism, so membership in a group grants no permissions.
E=SCP per project OU: SCPs never grant permissions, so an SCP gives engineers no access by itself. It would also need a new OU and SCP for every project, which is the growth problem the company wants to avoid.
T: ABAC scales by comparing a principal tag with a resource tag in one policy; RBAC needs a new role or permission set for every new project.
G: ## RBAC versus ABAC
- **Role-based access control (RBAC)** writes a policy per job or team, often listing specific resource ARNs. It grows with every new team.
- **Attribute-based access control (ABAC)** writes one policy that compares attributes (tags) of the caller with tags on the resource.
## How ABAC works with IAM Identity Center
1. The IdP (for example Okta or Microsoft Entra ID) sends user attributes such as `project=atlas`.
2. With **attributes for access control** enabled, Identity Center passes them as session tags, visible to policies as `aws:PrincipalTag/project`.
3. The permission set contains a condition like `"StringEquals": {"aws:ResourceTag/project": "${aws:PrincipalTag/project}"}`.
An engineer tagged `atlas` can stop an instance tagged `project=atlas` but not one tagged `project=orion`. A new project only needs new tags, not new policies.
V: AWS IAM Identity Center, AWS IAM, Amazon EC2

@ SAA-C03 D1 T1.2 advanced use-case
S: EC2 instances in private subnets use an S3 gateway endpoint. Security is worried that a compromised instance could copy data to an S3 bucket in an attacker's personal AWS account through the endpoint. How can the company block this path while keeping access to its own buckets?
A: Add a bucket policy on each company bucket that denies requests whose aws:SourceVpce value does not match the gateway endpoint ID
B: Add a security group outbound rule that allows HTTPS only to the S3 managed prefix list and denies all other outbound traffic
C: Attach a VPC endpoint policy that allows S3 actions only when aws:ResourceOrgID matches the company's organization ID
D: Add a network ACL outbound rule that denies HTTPS to all S3 IP ranges except the ones assigned to the company's own buckets
K: C
W: VPC endpoint policy on the resource's organization: the endpoint policy is evaluated for every request going through the endpoint. Allowing S3 actions only when `aws:ResourceOrgID` equals the company's organization means requests to a bucket owned by any other account are denied, while company buckets keep working.
X: A=Bucket policy with aws:SourceVpce: this controls who can reach the company's buckets, not which buckets the instances can reach. The attacker's bucket has its own policy, so this does nothing to stop uploads to it.
B=Security group with prefix list: the S3 prefix list contains the IP ranges for all of S3 in the Region. Every bucket, including the attacker's, is served from those same addresses, so the rule cannot tell buckets apart.
D=NACL with S3 IP ranges: S3 does not assign dedicated IP addresses per bucket or per customer, so there are no "company bucket" ranges to allow. The same endpoints serve every account.
T: Bucket policies decide who may reach your bucket; the VPC endpoint policy decides which buckets your VPC may reach, which is what stops exfiltration.
G: ## Two policies, two directions
Traffic from a private subnet to S3 through a gateway endpoint can be controlled at two points:
- **Bucket policy** (on the destination): "Which callers may use my bucket?" A condition on `aws:SourceVpce` lets the bucket accept requests only from a specific endpoint.
- **VPC endpoint policy** (on the path): "Which S3 resources may traffic from this VPC reach?" It applies to every request through the endpoint, whatever the bucket.
## Why network controls fail here
S3 is a shared service. All buckets in a Region answer on the same IP ranges, published as the managed prefix list `pl-xxxxxxxx`. Security groups and NACLs see only IPs and ports, never bucket names or owners.
## Example endpoint policy condition
`"Condition": {"StringEquals": {"aws:ResourceOrgID": "o-a1b2c3d4e5"}}` allows S3 calls only to buckets owned by accounts in the organization. A `PutObject` to `s3://attacker-bucket` is denied at the endpoint. In practice, add explicit exceptions for any AWS-owned buckets the instances need, such as OS package repositories.
V: Amazon VPC, Amazon S3, AWS Organizations

@ SAA-C03 D1 T1.2 applied use-case
S: A company serves a web application through Amazon CloudFront with an Application Load Balancer as the origin. Security requires that the ALB is not reachable from the internet at all, and only this CloudFront distribution may send it traffic. Which solution meets the requirement with the LEAST operational overhead?
A: Keep the ALB internet-facing and allow inbound HTTPS only from the CloudFront origin-facing managed prefix list in its security group
B: Keep the ALB internet-facing and add network ACL rules that allow only the CloudFront IP ranges, updated by a scheduled function
C: Keep the ALB internet-facing and attach an AWS WAF web ACL that blocks requests from every country except the CloudFront edge countries
D: Move the ALB to private subnets as an internal load balancer and register it as a CloudFront VPC origin for the distribution
K: D
W: CloudFront VPC origin: CloudFront can deliver to an internal ALB in private subnets through a VPC origin. The ALB has no public IP address, so it cannot be reached from the internet, and only CloudFront, through the VPC origin, can connect to it.
X: A=Managed prefix list in security group: the ALB is still internet-facing, and the prefix list covers all CloudFront edge servers, including distributions owned by other AWS customers. Anyone could point their own distribution at the ALB.
B=NACL with CloudFront ranges: NACLs have a small rule limit, CloudFront publishes many ranges that change, and the scheduled updater is extra code to run. The ALB would still be internet-facing and reachable from any distribution.
C=WAF geo blocking: CloudFront edge locations are in most countries, so geography does not identify CloudFront traffic. Attackers in allowed countries could still reach the public ALB directly.
T: To make an origin truly private behind CloudFront, use a VPC origin with an internal ALB; a prefix list only narrows a public ALB to all of CloudFront.
G: ## Ways to lock an ALB behind CloudFront
- **Public ALB + prefix list**: the security group allows `com.amazonaws.global.cloudfront.origin-facing`. This limits traffic to CloudFront servers, but every customer's distribution uses the same servers, so a custom secret header checked by the ALB is usually added too.
- **VPC origin**: CloudFront connects to an internal ALB, NLB or EC2 instance in a private subnet. The load balancer is never exposed to the internet, and there is no header secret to rotate.
## Example layout
- `internal-app-alb` in two private subnets, security group allowing HTTPS from the CloudFront VPC origin.
- The distribution uses the VPC origin as its origin; users reach `www.example.com` only through CloudFront, where WAF and caching apply.
With no public endpoint, scanners and attackers have nothing to hit directly, which is the strongest form of "only through CloudFront".
V: Amazon CloudFront, Elastic Load Balancing, Amazon VPC

@ SAA-C03 D1 T1.2 applied use-case
S: A company wants to remove bastion hosts and stop opening port 22. Administrators must get shell access to Amazon Linux 2023 instances in private subnets that have no NAT gateway or internet access, and all sessions must be logged. Which TWO steps are required? (Select TWO)
A: Attach an instance profile whose role includes the AmazonSSMManagedInstanceCore managed policy to each instance
B: Create interface VPC endpoints for Systems Manager (ssm, ssmmessages, and ec2messages) in the private subnets' VPC
C: Allow inbound TCP port 22 in the instance security groups from the Systems Manager service IP address ranges
D: Associate an Elastic IP address with each instance so the Session Manager service can initiate the connection
E: Store each instance's SSH private key in AWS Secrets Manager so Session Manager can retrieve it during login
K: A,B
W: A=Instance profile with AmazonSSMManagedInstanceCore: the SSM Agent (preinstalled on Amazon Linux 2023) uses this role to register the instance and open the session channel.
B=Systems Manager interface endpoints: with no NAT or internet, the agent needs private endpoints to reach the service: `ssm` and `ssmmessages`, plus `ec2messages`, which older agent versions still use. Session activity is recorded in CloudTrail, and session output can be sent to CloudWatch Logs or S3.
X: C=Open port 22: Session Manager needs no inbound ports at all. The agent makes an outbound HTTPS connection, so opening SSH would only add attack surface.
D=Elastic IP per instance: Session Manager never connects inbound to the instance, and a public IP does nothing in a subnet without an internet gateway route. It would expose the instances for no benefit.
E=SSH keys in Secrets Manager: Session Manager does not use SSH keys. Access is controlled by IAM policies on the user, which removes key distribution and rotation entirely.
T: Session Manager replaces bastions with an outbound agent connection: give the instance an SSM role and a path to the SSM endpoints; no inbound ports, public IPs or SSH keys.
G: ## How Session Manager works
AWS Systems Manager Session Manager gives an interactive shell without SSH. The SSM Agent on the instance opens an **outbound** HTTPS (443) connection to Systems Manager and keeps it open. When an administrator starts a session from the console or `aws ssm start-session`, traffic flows over that existing channel.
## What an instance needs
- **The agent**: preinstalled on Amazon Linux 2023 and many other AMIs.
- **Permissions**: an instance profile role with `AmazonSSMManagedInstanceCore` (or the account-wide Default Host Management Configuration).
- **Network path**: a NAT gateway, or, for isolated subnets, interface endpoints `com.amazonaws.<region>.ssm` and `.ssmmessages`, plus `.ec2messages` for older agent versions. Sending session output to CloudWatch Logs or S3 also needs a `logs` interface endpoint or an S3 gateway endpoint.
## Why it is more secure
- No inbound rules, no bastion host, no SSH keys.
- Who may start a session is decided by IAM, and every session is recorded in CloudTrail; session output can be sent to CloudWatch Logs or S3.

@ SAA-C03 D1 T1.2 applied troubleshooting
S: A Lambda function was attached to private subnets so it can query an RDS database. Since then, its calls to AWS Secrets Manager to read the database password time out after 3 seconds. The VPC has no NAT gateway, and the secret's permissions have not changed. What should the solutions architect do?
A: Create an interface VPC endpoint for Secrets Manager with private DNS and allow HTTPS from the function's security group
B: Enable the option to assign a public IP address to the function's network interfaces and add a route to an internet gateway
C: Add a resource policy to the secret that grants the function's execution role secretsmanager:GetSecretValue on the secret
D: Increase the function timeout to 60 seconds and add retries with backoff to the SDK client that calls Secrets Manager
K: A
W: Secrets Manager interface endpoint: once a function runs in a VPC, its traffic follows the subnets' routes, and these have no path to the public Secrets Manager endpoint. An interface endpoint with private DNS makes the normal endpoint name resolve to private IPs inside the VPC, so the SDK works unchanged.
X: B=Public IP for the function: Lambda network interfaces in a VPC never receive public IPs, even in a public subnet, so an internet gateway route does not give the function internet access.
C=Secret resource policy: a permission problem would return AccessDenied immediately, not a timeout. The stem also states the permissions have not changed; the request is not reaching the service.
D=Longer timeout and retries: there is no network path, so every attempt will hang until it times out. Waiting longer only increases cost and latency.
T: A timeout from a VPC-attached Lambda means no network path; add a VPC endpoint (or NAT), since Lambda in a VPC never gets a public IP.
G: ## What changes when Lambda joins a VPC
By default a function runs in a Lambda-managed network with internet access. When you attach it to your subnets, Lambda creates elastic network interfaces there, and all outbound traffic follows those subnets' route tables and security groups.
## Reaching AWS APIs from private subnets
Services such as Secrets Manager, SQS or STS are public endpoints like `secretsmanager.us-east-1.amazonaws.com`. From a private subnet you reach them through:
- a **NAT gateway** (per-hour and per-GB charges, traffic leaves through the internet gateway), or
- an **interface VPC endpoint** (AWS PrivateLink), which puts private IPs for the service in your subnets.
## Private DNS
With private DNS enabled on the endpoint, the standard service name resolves to the endpoint's private IPs, so no code change is needed. The endpoint's security group must allow TCP 443 from the function's security group.
## Reading the symptom
AccessDenied means the request arrived and was refused. A timeout means it never arrived.

@ SAA-C03 D1 T1.2 applied use-case
S: An internal HR API built on Amazon API Gateway must be callable only by applications running in one specific VPC. It must not be reachable from the internet, even with valid credentials. Which design meets these requirements?
A: A Regional REST API with an AWS WAF web ACL that allows only the VPC's NAT gateway Elastic IP address as the source of requests
B: An edge-optimized REST API that requires IAM authorization and a policy allowing only roles used by applications in the VPC
C: A private REST API reached through an execute-api interface endpoint, with a resource policy allowing only that endpoint's ID
D: An HTTP API with a Lambda authorizer that inspects the X-Forwarded-For header and rejects addresses outside the VPC CIDR
K: C
W: Private REST API with execute-api endpoint: a private API has no public endpoint at all. Clients in the VPC reach it through an interface endpoint for `execute-api`, and the resource policy's `aws:SourceVpce` condition limits calls to that one endpoint, so other VPCs and the internet cannot invoke it.
X: A=Regional API with WAF IP allowlist: the API is still public on the internet, and the allowlist depends on traffic leaving through the NAT gateway. The endpoint remains discoverable and the design fails if routing changes.
B=Edge-optimized API with IAM auth: IAM authorization checks who calls, not where from. Anyone holding valid credentials for those roles could call the public endpoint from anywhere, which the stem forbids.
D=HTTP API with header check: the API is public, and `X-Forwarded-For` can be spoofed by the client. HTTP APIs also do not support the private endpoint type.
T: For an API reachable only from a VPC, use a private REST API with an execute-api interface endpoint and a resource policy on aws:SourceVpce; authentication alone does not remove the public endpoint.
G: ## API Gateway endpoint types
- **Edge-optimized**: public, fronted by CloudFront edge locations.
- **Regional**: public, served from one Region.
- **Private**: no public endpoint; reachable only through an interface VPC endpoint for `execute-api`. Only REST APIs support this type.
## Locking a private API to one VPC
1. Create an interface endpoint `com.amazonaws.<region>.execute-api` in the VPC.
2. Attach a resource policy to the API, for example allow `execute-api:Invoke` only when `aws:SourceVpce` equals `vpce-0abc123`.
3. Deploy the API so the resource policy takes effect.
A request from another VPC, even one with its own execute-api endpoint, fails the condition and is denied. Authentication (IAM, Cognito, Lambda authorizers) can still be added on top to decide which applications in the VPC may call it.

@ SAA-C03 D1 T1.3 advanced use-case
S: An application encrypts sensitive fields with AWS KMS before writing them to a DynamoDB global table replicated between us-east-1 and eu-west-1. During a regional outage of us-east-1, the application in eu-west-1 must still decrypt every item without calling us-east-1. Which approach meets this requirement?
A: Create a single-Region customer managed key in us-east-1 and grant the eu-west-1 application role permission to call kms:Decrypt on it
B: Create a KMS multi-Region primary key in us-east-1 with a replica key in eu-west-1 and decrypt with the local key in each Region
C: Create single-Region customer managed keys in both Regions and import the same key material into each key so they are interchangeable
D: Rely on the AWS owned key that DynamoDB uses for encryption at rest, because global table replicas decrypt items automatically
K: B
W: Multi-Region keys: a primary key and its replica share the same key ID and key material. Ciphertext produced in us-east-1 can be decrypted by the replica in eu-west-1 with a local call, so decryption does not depend on the failed Region.
X: A=Single-Region key with cross-Region grant: decryption would always call KMS in us-east-1. During the outage those calls fail, so the eu-west-1 application cannot read any encrypted field.
C=Imported identical key material: each KMS key has its own key ID, and ciphertext is bound to the key that created it. Even with the same material, one single-Region key cannot decrypt ciphertext from the other; only multi-Region keys are interoperable.
D=DynamoDB encryption at rest: table encryption is transparent and handled per Region, but these fields were encrypted by the application itself with its own KMS key before being written. The table's key cannot decrypt application-level ciphertext.
T: Multi-Region KMS keys share key ID and material, so ciphertext moves between Regions and decrypts locally; single-Region keys, even with imported copies, cannot.
G: ## Why client-side encryption needs care across Regions
DynamoDB already encrypts tables at rest. Some applications additionally encrypt fields such as `ssn` themselves (client-side) before writing. That ciphertext is replicated byte for byte to every global table replica, so each Region must be able to decrypt it.
## Single-Region versus multi-Region keys
- A **single-Region key** lives in one Region. Ciphertext it creates can be decrypted only by calling KMS in that Region.
- A **multi-Region key** has a primary (for example `mrk-1234abcd` in us-east-1) and replicas in other Regions with the **same key ID and key material**. Each replica is an independent KMS resource with its own key policy.
## Example
The app in us-east-1 encrypts a field with `mrk-1234abcd`. The replicated item arrives in eu-west-1, where the app calls `Decrypt` against the local replica of `mrk-1234abcd`. No cross-Region call is needed, so an outage in us-east-1 does not block reads.

X: B=Provisioned capacity: capacity mode affects the cost of reads and writes only. Storage is billed per GB-month in both modes, so the largest part of this bill would not change.
C=Export to Glacier Deep Archive: restores from Deep Archive take up to 12 hours or more, which fails the requirement that older orders are read with millisecond latency, and it adds a pipeline to maintain.
D=DynamoDB Accelerator: DAX caches reads to lower latency and read cost, but it adds cluster charges and does nothing to the stored 30 TB, which is where the cost is.
T: When storage dominates a DynamoDB bill and latency must stay the same, use the Standard-IA table class; capacity modes and caches only change request costs.
G: ## DynamoDB table classes
Each table has a table class that sets how storage and requests are priced:
- **DynamoDB Standard**: default; balanced storage and request prices.
- **DynamoDB Standard-Infrequent Access (Standard-IA)**: storage costs about 60% less per GB, while read and write requests cost more.
Both classes have the same single-digit millisecond performance, durability, and features such as global tables and point-in-time recovery.
## When Standard-IA wins
It is aimed at tables where storage is the largest part of the bill, such as logs, order history or old social posts that are kept but rarely touched.
## Example
A 30 TB table where storage is 80% of cost: cutting the storage price by about 60% lowers the total by roughly 40%, even after the higher request prices. The class can be changed on an existing table with no downtime, and you can switch back later (a limited number of times per 30 days).

@ SAA-C03 D4 T4.4 applied use-case
S: An Amazon ECS cluster on Fargate runs in private subnets and pulls large container images from Amazon ECR many times a day. The NAT gateway's data processing charges have become the largest networking cost. Which TWO changes remove image pull traffic from the NAT gateway? (Select TWO)
A: Create an S3 gateway VPC endpoint and add it to the private subnets' route tables, because ECR stores image layers in S3
B: Create interface VPC endpoints for ECR (ecr.api and ecr.dkr) in the VPC so the ECR API calls stay on private addresses
C: Add a second NAT gateway in each Availability Zone so each task uses the NAT gateway closest to it for image downloads
D: Move the tasks to public subnets with public IP addresses and keep the NAT gateway in place for all other outbound traffic
E: Create a VPC peering connection to the AWS account that hosts ECR so image pulls take a private path through the peering
K: A,B
W: A=S3 gateway endpoint: the image layers themselves are downloaded from Amazon S3. A gateway endpoint has no hourly or per-GB charge, so the bulk of the pull traffic stops flowing through the NAT gateway.
B=ECR interface endpoints: `ecr.api` serves ECR API calls such as getting the authorization token, and `ecr.dkr` serves the Docker registry calls such as fetching manifests. With both in place, a task in a private subnet can complete the whole image pull without the NAT gateway.
X: C=More NAT gateways: extra NAT gateways add hourly charges and still bill every GB processed. They can reduce cross-AZ transfer, but image traffic still goes through NAT.
D=Public subnets with public IPs: each public IPv4 address has an hourly charge, the tasks become reachable from the internet, and it abandons the private-subnet design just to avoid NAT fees.
E=VPC peering to ECR: ECR is a managed regional service, not a VPC in another account that you can peer with, so there is nothing to connect to.
T: Private-subnet image pulls need an S3 gateway endpoint for the layers and ECR interface endpoints for the registry API; both take traffic off the NAT gateway.
G: ## What happens during an image pull
Pulling an image from Amazon ECR involves three services:
1. `ecr.api`: ECR API calls, such as getting an authorization token.
2. `ecr.dkr`: the Docker registry API, such as fetching the image manifest.
3. **Amazon S3**: the image layers, usually most of the bytes, are downloaded from S3.
## Why NAT gets expensive
A NAT gateway charges per hour and per GB processed (approximately $0.045/GB in many Regions; check current pricing). A 1 GB image pulled 500 times a day is 500 GB/day through NAT.
## The endpoint setup
- **S3 gateway endpoint**: a route table entry, with no hourly or data charge.
- **Interface endpoints** `com.amazonaws.<region>.ecr.api` and `.ecr.dkr`: small hourly and per-GB charges, much lower than NAT for this traffic.
- For Fargate tasks that send logs, a `logs` interface endpoint lets CloudWatch Logs traffic skip NAT too.

@ SAA-C03 D4 T4.4 applied troubleshooting
S: Two EC2 instances in the same VPC and the same Availability Zone exchange about 50 TB of data per month. The bill shows unexpected data transfer charges for this traffic. The application is configured to reach its peer using the peer's Elastic IP address. What change removes these charges?
A: Place both instances in a cluster placement group so that traffic between them uses a faster network path within the AZ
B: Enable enhanced networking with ENA on both instances so that data transfer between them is billed at a lower rate
C: Configure the application to use the peer's private IP address or private DNS name so traffic stays on the private network
D: Replace the Elastic IP addresses with new auto-assigned public IP addresses, because Elastic IP traffic is billed at a premium
K: C
W: Private IP addressing: traffic between instances in the same AZ over private IPv4 addresses is free. When the application sends to the Elastic IP, AWS bills it as public-address traffic in each direction, even though both instances sit in the same AZ.
X: A=Cluster placement group: it improves latency and throughput between instances, but billing depends on the addresses used. Traffic sent to the Elastic IP is still charged.
B=Enhanced networking: ENA raises bandwidth and packet rates; it does not change data transfer pricing at all.
D=Auto-assigned public IPs: public IPv4 traffic is billed the same whether the address is an Elastic IP or auto-assigned. The charge comes from using a public address, not from the Elastic IP type.
T: Within an AZ, traffic is free only over private IPs; talking to a peer's public or Elastic IP makes the same traffic billable.
G: ## How EC2 data transfer is priced inside a Region
- Same AZ, **private IPv4** addresses: free.
- Different AZs in the same Region: charged per GB in each direction.
- To or from a **public IPv4 or Elastic IP** address in the same Region: charged per GB in each direction (approximately $0.01/GB), even if both instances are in the same AZ.
## Why this happens
When an application uses a peer's public address, traffic is handled as public-address traffic, which AWS bills.
## Example
50 TB/month through Elastic IPs is about 50,000 GB x $0.01 x 2 directions = about $1,000/month. Using `10.0.1.25` instead, or the instance's private DNS name such as `ip-10-0-1-25.ec2.internal`, makes it $0.
Inside a VPC that uses the Amazon-provided DNS with DNS hostnames enabled, the public DNS name of an instance resolves to its private IP, which is another safe option.
V: Amazon EC2, Amazon VPC
