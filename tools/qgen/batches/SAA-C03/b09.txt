# SAA-C03 batch 09: D2 resilient architectures (13) + D3 high-performing architectures (12), detailed explanations

@ SAA-C03 D2 T2.1 advanced troubleshooting
S: A Lambda function consumes an SQS standard queue with a batch size of 10. Each message triggers a charge to a customer's card through an idempotent-unaware payment API. When one message in a batch fails validation, the function throws an exception, and customers in the other nine messages are charged again on the retry. What is the MOST efficient fix?
A: Enable ReportBatchItemFailures on the event source mapping and return the IDs of only the failed messages in the batchItemFailures list
B: Reduce the batch size on the event source mapping to 1 so that each invocation handles one message and a failure affects only that message
C: Increase the queue's visibility timeout to six times the function timeout so that failed batches are not delivered again as quickly
D: Replace the standard queue with a FIFO queue and set a deduplication ID on each message so that already-charged messages are dropped
K: A
W: Partial batch response: with `ReportBatchItemFailures` turned on, the function catches per-message errors and returns `batchItemFailures` containing only the failed message IDs. Lambda deletes the nine successful messages and makes only the failed one visible again, so no customer is charged twice and batching efficiency is kept.
X: B=Batch size of 1: this does stop the duplicate charges, but it multiplies invocations and polling cost by up to ten and lowers throughput. The partial batch response solves the same problem while keeping batches.
C=Longer visibility timeout: this only delays the retry. When the timeout expires the whole batch is delivered again and the nine good messages are still charged a second time.
D=FIFO with deduplication ID: deduplication applies to messages sent within a 5-minute window, not to redeliveries after a failed batch. A failed FIFO batch is also returned as a whole, so the successful messages would still be processed again.
T: When one bad message should not replay a whole SQS batch, report partial batch failures; shrinking the batch works but throws away throughput.
G: ## How Lambda processes an SQS batch
The Lambda event source mapping polls the queue and invokes the function with up to `BatchSize` messages. By default the batch succeeds or fails as a unit:
- If the function returns normally, Lambda deletes every message in the batch.
- If the function throws, no message is deleted. After the visibility timeout all of them become visible again and are retried.
With side effects such as payments, that means the successful messages are processed twice.
## Partial batch responses
Set `FunctionResponseTypes` to `ReportBatchItemFailures` on the mapping. The function then catches errors per message and returns, for example:
`{"batchItemFailures": [{"itemIdentifier": "msg-7"}]}`
Lambda deletes the other nine messages and retries only `msg-7`. After `maxReceiveCount` attempts the redrive policy moves it to the dead-letter queue.
V: AWS Lambda, Amazon SQS

@ SAA-C03 D2 T2.1 applied tradeoff
S: An IoT platform receives about 40,000 device events per second. Each event starts a short workflow of three steps (validate, enrich, store) that finishes in under 2 seconds, and every step is idempotent. The team wants AWS Step Functions for visual orchestration at the lowest cost. Which workflow type should they use?
A: Standard workflows, because they guarantee exactly-once execution of every step and keep a detailed execution history for 90 days
B: Express workflows, because they support very high start rates for short runs and are billed by request count and duration
C: Standard workflows started through an SQS queue, so that the queue absorbs the event rate and smooths out the execution starts
D: Express workflows invoked synchronously, because only synchronous runs are allowed to call other AWS services from a step
K: B
W: Express workflows: they are designed for high-volume, short-lived event processing that runs for up to 5 minutes. They accept very high start rates and are priced per request and by duration and memory, which is far cheaper than per-state-transition pricing at 40,000 events per second. At-least-once semantics are fine because every step is idempotent.
X: A=Standard for exactly-once: Standard workflows are priced per state transition and have much lower start-rate quotas. Exactly-once and long history are valuable for long-running business processes, not for millions of 2-second idempotent runs.
C=Standard behind SQS: a queue can smooth bursts, but the sustained rate of 40,000 starts per second remains, and every transition is still billed at the Standard price. It adds latency and cost without changing the mismatch.
D=Synchronous-only service calls: both synchronous and asynchronous Express workflows can call AWS services from their steps. The choice between sync and async depends on whether the caller waits for the result.
T: Short, high-volume, idempotent workflows fit Express (per-request pricing, at-least-once); long-running, exactly-once business processes fit Standard (per-transition pricing).
G: ## Two workflow types in Step Functions
- **Standard workflows** can run for up to one year, execute each step exactly once, and keep an execution history you can inspect for 90 days. They are billed per state transition and have moderate start-rate quotas. Typical use: order fulfilment, human approvals.
- **Express workflows** run for up to 5 minutes and are built for event rates of tens of thousands of starts per second. Asynchronous Express runs have at-least-once semantics, synchronous ones at-most-once. They are billed by number of requests and by duration and memory, and logs go to CloudWatch Logs.
## Choosing
Example: 40,000 events per second with 4 state transitions each is 160,000 transitions per second on Standard pricing. The same load on Express is billed per execution and for 2 seconds of duration each, which is far cheaper. Because every step is idempotent, an occasional duplicate run does no harm.
V: AWS Step Functions

@ SAA-C03 D2 T2.1 applied use-case
S: A retailer publishes price changes for each product. Three independent services (pricing cache, search index, and audit) must each receive every price change for a given product in the exact order it was published, process at their own pace, and retry failures separately. Which design meets these requirements?
A: An Amazon SNS standard topic with three Amazon SQS FIFO queues subscribed to it, using the product ID as the message group ID on each queue
B: An Amazon EventBridge custom event bus with three rules, each targeting a separate Amazon SQS FIFO queue that uses the product ID as group ID
C: An Amazon SNS FIFO topic with three subscribed Amazon SQS FIFO queues, publishing each change with the product ID as the message group ID
D: A single Amazon SQS FIFO queue shared by all three services, publishing each change with the product ID as the message group ID for ordering
K: C
W: SNS FIFO fan-out to SQS FIFO: the FIFO topic keeps messages with the same message group ID (the product ID) in order and delivers each one to every subscribed FIFO queue. Each service reads its own queue in order, at its own pace, with its own retries and dead-letter queue.
X: A=Standard topic with FIFO queues: a standard SNS topic uses best-effort ordering and can deliver messages out of order, so FIFO queues behind it cannot restore the publish order. Ordered fan-out to SQS FIFO queues requires an SNS FIFO topic.
B=EventBridge rules to FIFO queues: EventBridge does not guarantee the order in which events are delivered to targets, so two quick price changes could arrive in a FIFO queue in the wrong order.
D=One shared FIFO queue: consumers of one queue compete for messages, so each change is processed by only one of the three services. Fan-out needs one queue per service.
T: Ordered fan-out is SNS FIFO plus one SQS FIFO queue per consumer; a single queue load-balances instead of fanning out, and a standard topic or EventBridge does not keep order.
G: ## Fan-out versus competing consumers
- **Fan-out**: one message is copied to several subscribers, and each processes every message. With SNS and SQS, each service gets its own queue subscribed to the topic.
- **Competing consumers**: several workers read the same queue and each message goes to only one of them.
## Keeping order in a fan-out
An **SNS FIFO topic** orders messages per **message group ID** and deduplicates them. It delivers to **SQS FIFO queues**, which keep that order for their consumer.
Example: `price-changed` messages for product `p-123` are published with `MessageGroupId=p-123`. The search, cache and audit queues each receive them in publish order. Different products use different group IDs, so they are processed in parallel and a slow product does not block others.
Each queue has its own redrive policy, so a failure in the audit service is retried there without affecting the other two services.
V: Amazon SNS, Amazon SQS

@ SAA-C03 D2 T2.1 applied use-case
S: A web application runs in an EC2 Auto Scaling group. New instances take about 12 minutes to become ready because they download a large machine-learning model and warm local caches. Traffic spikes are sudden and do not follow a daily pattern, and users see errors while new instances initialize. What should a solutions architect do?
A: Configure a predictive scaling policy so that the Auto Scaling group forecasts the load and launches instances before the spikes arrive
B: Add a warm pool to the Auto Scaling group that keeps pre-initialized instances in the Stopped state, ready to move into service quickly
C: Add a lifecycle hook for launching instances so that each new instance stays in Pending:Wait until its model download has completed
D: Create a scheduled scaling action that raises the group's minimum capacity every morning and lowers it again every evening after peak
K: B
W: Warm pool: the group keeps instances that have already run their startup work (model download, cache warm-up) and are then stopped. At scale-out they only need to start, which takes seconds to a few minutes instead of 12, and stopped instances incur only EBS storage charges while waiting.
X: A=Predictive scaling: it learns from daily and weekly patterns in historical load. Sudden spikes with no recurring pattern cannot be forecast, so instances would still launch late.
C=Launch lifecycle hook: a hook keeps an instance out of service until it is ready, which prevents traffic to half-initialized instances, but it does not make initialization any faster. Users still wait 12 minutes for new capacity.
D=Scheduled scaling: it helps only when load follows a known timetable. The spikes are unpredictable, and keeping extra running capacity all day costs more than a pool of stopped instances.
T: Slow boot plus unpredictable spikes calls for a warm pool of pre-initialized instances; predictive and scheduled scaling need a pattern, and lifecycle hooks only gate readiness.
G: ## Why scale-out can be too slow
Auto Scaling reacts to a metric, launches instances, and then waits for them to boot and run user data. If an application needs 12 minutes to initialize, capacity arrives 12 minutes after the spike started.
## What a warm pool is
A **warm pool** is a set of instances that sit next to the Auto Scaling group, already launched and initialized. You choose the state they wait in:
- `Stopped`: you pay only for EBS volumes; startup takes seconds to a few minutes.
- `Hibernated`: memory contents are saved to EBS, so warm caches survive.
- `Running`: fastest, but billed like normal instances.
When the group scales out, it takes instances from the pool first. Lifecycle hooks can still run a final check before an instance enters service.
Example: the model download runs once when an instance joins the pool, not on every scale-out.
V: Amazon EC2 Auto Scaling

@ SAA-C03 D2 T2.1 applied use-case
S: Orders flow through an Amazon EventBridge custom event bus to several consumers. A bug in the invoicing consumer caused it to discard events for 6 hours before it was fixed. The team must reprocess those 6 hours of order events for the invoicing consumer only, and wants the same capability for future incidents. What should the team do?
A: Enable an archive on the event bus, and after a fix start a replay for the affected time window targeting only the invoicing rule
B: Add an Amazon SQS dead-letter queue to the invoicing rule's target, and redrive the dead-letter queue after deploying each fix
C: Turn on CloudTrail data events for the event bus, and resubmit the logged PutEvents calls for the time window with a script
D: Configure the rule's retry policy with a maximum event age of 24 hours so that failed events are delivered again automatically
K: A
W: Archive and replay: an archive stores events from the bus (optionally filtered) for a retention period you choose. A replay sends archived events from a chosen time window back to the bus, and you can limit it to specific rules, so only the invoicing consumer processes them again.
X: B=Target dead-letter queue: a DLQ captures events that EventBridge could not deliver to the target. Here delivery succeeded and the consumer itself discarded the events, so nothing reached the DLQ.
C=CloudTrail and a script: CloudTrail is an audit log of API calls, not a message store designed for reprocessing, and a custom resubmission script would reach every rule on the bus, not only invoicing.
D=Retry policy with maximum age: retries apply only when delivery to the target fails. Events that were delivered and then dropped by buggy code are never retried.
T: To reprocess events that were delivered but mishandled, archive the bus and replay a time window to chosen rules; DLQs and retries only cover delivery failures.
G: ## Delivery failure versus processing failure
EventBridge guarantees delivery to targets with retries and an optional dead-letter queue. That covers cases where the target is unreachable or throttling. It cannot help when the target accepted the event and then mishandled it.
## Archive and replay
- An **archive** is attached to an event bus. It can capture all events or only those that match an event pattern, and keeps them for a retention period (or indefinitely).
- A **replay** reads events from an archive for a start and end time and sends them back to the same bus. You can select which rules receive the replay.
Example: archive `detail-type = "OrderPlaced"` events for 30 days. After the invoicing bug is fixed, replay 02:00-08:00 to the `invoicing` rule only. Replayed events carry a `replay-name` field, so consumers can tell them apart. Consumers should be idempotent in case some events were already processed.
V: Amazon EventBridge

@ SAA-C03 D2 T2.1 advanced troubleshooting
S: A Lambda function reads orders from an SQS queue and writes them to an Amazon RDS for MySQL database. During a large import, the queue backlog made Lambda scale to about 900 concurrent executions, the database ran out of connections, and unrelated functions in the account were throttled. Lambda must not throttle the SQS poller. Which TWO changes meet these requirements? (Select TWO)
A: Set a maximum concurrency on the SQS event source mapping so that the poller never invokes more than a fixed number of function instances at once
B: Put Amazon RDS Proxy between the function and the database so that many function instances share a small pool of database connections
C: Set reserved concurrency on the function to a low value so that Lambda rejects invocations from the poller above that limit during an import
D: Enable provisioned concurrency of 900 on the function so that execution environments are already initialized when the import traffic arrives
E: Increase the queue's visibility timeout to six times the function timeout so that messages stay hidden longer while the database is busy
K: A,B
W: A=Event source mapping maximum concurrency: this caps how many concurrent invocations the SQS poller itself starts. Excess messages simply wait in the queue, so the account's concurrency is not exhausted and Lambda never throttles the poller.
B=RDS Proxy: the proxy keeps a pool of database connections and multiplexes requests from many function instances onto it, so bursts of executions no longer translate into bursts of new MySQL connections.
X: C=Low reserved concurrency: it limits the function, but the poller keeps invoking at a higher rate and receives throttling errors. Throttled messages return to the queue, their receive count grows, and they can end up in the dead-letter queue.
D=Provisioned concurrency of 900: this pre-initializes environments to cut cold starts. It does not limit concurrency, so the database would still see 900 callers, and it adds a large ongoing cost.
E=Longer visibility timeout: this changes how long an in-flight message stays hidden. It does not limit how many functions run at once or how many connections they open.
T: To protect a downstream database from SQS-driven Lambda bursts, cap concurrency on the event source mapping and pool connections with RDS Proxy; reserved concurrency alone causes throttling.
G: ## How SQS drives Lambda concurrency
The SQS event source mapping adds pollers as the backlog grows, and each poller invokes the function. With a large backlog, concurrency can rise to hundreds of executions, consuming the account's shared concurrency pool.
## Two ways to limit it
- **Reserved concurrency** is a limit on the function. The poller does not know about it, so extra invocations fail with throttling errors and messages are retried.
- **Maximum concurrency** (`ScalingConfig.MaximumConcurrency`) is a limit on the event source mapping. The poller stops invoking beyond it, and messages stay in the queue until capacity frees up.
## Connections
Each execution environment opens its own database connection. **RDS Proxy** holds a warm pool and shares it between callers.
Example: max concurrency 50 plus RDS Proxy means at most 50 functions, served by a pool of connections well below the MySQL limit.
V: AWS Lambda, Amazon SQS, Amazon RDS Proxy, Amazon RDS

@ SAA-C03 D2 T2.2 advanced use-case
S: A company runs an Aurora PostgreSQL global database with its primary cluster in us-east-1 and a secondary cluster in us-west-2. For a quarterly disaster recovery exercise, the company must move the writer role to us-west-2 with no data loss, keep the global database topology intact, and later move it back. What should a solutions architect use?
A: A global database failover, which promotes the secondary cluster immediately without waiting for replication to catch up with the primary
B: Detaching the us-west-2 cluster from the global database and promoting it to a standalone cluster that accepts writes in that Region
C: A global database switchover, which synchronizes the secondary with the primary before changing roles and keeps the replication topology
D: An Aurora Backtrack operation on the primary, followed by restoring an automated snapshot of it as a new cluster in the us-west-2 Region
K: C
W: Global database switchover: it is the planned operation for healthy clusters. Aurora waits until the secondary is fully synchronized, then swaps the roles, so the RPO is zero, and the old primary becomes a secondary, which makes switching back just as easy.
X: A=Global database failover: this is meant for an unplanned Regional outage. It does not wait for replication to catch up, so any writes not yet replicated can be lost, which fails the no-data-loss requirement for a planned test.
B=Detach and promote: the promoted cluster becomes a separate, standalone cluster. The global database topology is broken, un-replicated writes can be lost, and the setup must be rebuilt afterwards.
D=Backtrack and snapshot restore: Backtrack rewinds a cluster in place to an earlier time and is not a cross-Region mechanism. Restoring a snapshot takes a long time and loses every write after the snapshot.
T: Planned Region swap with RPO zero means switchover; unplanned outage means failover, which may lose the last un-replicated writes.
G: ## How an Aurora global database replicates
One **primary cluster** accepts writes. Up to several **secondary clusters** in other Regions receive changes through storage-level replication with typical lag under one second, and serve reads.
## Two ways to change the writer Region
- **Switchover** (formerly called managed planned failover): used when both Regions are healthy, for DR drills or moving the workload closer to users. Aurora stops writes, waits until the chosen secondary has every change, then promotes it and demotes the old primary to a secondary. RPO is zero and the topology stays the same.
- **Failover**: used when the primary Region is impaired. The secondary is promoted right away, so changes still in flight are lost (RPO equals the replication lag). Aurora can later rebuild the old primary as a secondary.
Example: a drill uses switchover to us-west-2, runs there for a day, then switches back to us-east-1.
V: Amazon Aurora

@ SAA-C03 D2 T2.2 applied troubleshooting
S: A Network Load Balancer spans two Availability Zones with default settings. After a partial deployment, AZ-a has 2 registered targets and AZ-b has 6. Clients resolve the NLB DNS name to both zonal IP addresses evenly. The 2 targets in AZ-a run at 100% CPU while those in AZ-b are nearly idle. What should a solutions architect do?
A: Change the target group's load balancing algorithm to least outstanding requests so that busy targets automatically receive fewer new connections
B: Enable cross-zone load balancing for the NLB so that each load balancer node distributes traffic across the registered targets in both zones
C: Enable sticky sessions based on source IP on the target group so that each client keeps using the same target for its later connections
D: Increase the deregistration delay on the target group so that connections to the overloaded targets are drained more slowly and evenly
K: B
W: Cross-zone load balancing: it is off by default for NLBs, so each zonal node sends traffic only to targets in its own AZ. With half the traffic arriving in AZ-a, its 2 targets carry 50% of the load. Turning it on lets every node use all 8 targets, so each gets about one eighth. Note that NLB charges for inter-AZ data transfer when it is enabled.
X: A=Least outstanding requests: this algorithm exists only for Application Load Balancer target groups. An NLB routes connections by flow hash, and the problem is the per-AZ split, not the algorithm.
C=Source IP stickiness: stickiness keeps a client on one target, which would not move any traffic from AZ-a to AZ-b and can make imbalance worse.
D=Longer deregistration delay: this controls how long a target being removed keeps existing connections. It has nothing to do with how new traffic is spread between zones.
T: With cross-zone off (the NLB default), each AZ's share of traffic goes only to that AZ's targets; enable cross-zone or keep target counts equal per AZ.
G: ## How a load balancer spreads traffic across zones
A load balancer has one node per enabled Availability Zone, and DNS spreads clients roughly evenly across those nodes.
- **Cross-zone off**: a node forwards only to targets in its own AZ.
- **Cross-zone on**: a node forwards to healthy targets in all enabled AZs.
## Defaults differ
- Application Load Balancer: cross-zone is on by default (it can be turned off per target group) and inter-AZ traffic is not charged.
- Network Load Balancer: cross-zone is off by default. You can enable it on the load balancer or the target group, and inter-AZ data transfer is charged.
## Example
2 targets in AZ-a and 6 in AZ-b, 1,000 connections per second split evenly:
- Off: each AZ-a target gets 250, each AZ-b target about 83.
- On: every target gets about 125.
V: Elastic Load Balancing, Network Load Balancer

@ SAA-C03 D2 T2.2 advanced troubleshooting
S: An application runs on EC2 instances in an Auto Scaling group behind an Application Load Balancer in three Availability Zones. A networking problem in one AZ causes intermittent timeouts for requests handled there, but the target health checks keep passing. The team needs to stop sending traffic to that AZ within minutes and restore it easily afterwards. What should they do?
A: Change the Route 53 alias record for the application to failover routing and point the secondary record at a static maintenance page in S3
B: Update the Auto Scaling group to remove the impaired AZ's subnet so that its instances terminate and capacity is launched in the other zones
C: Start a zonal shift in Amazon Application Recovery Controller for the ALB, moving traffic away from the impaired AZ for a set duration
D: Tighten the target group health check to a 2-second timeout with a threshold of 2 so the impaired zone's targets are marked unhealthy
K: C
W: Zonal shift: it tells the load balancer to stop routing to one AZ for a duration you choose. Traffic moves to the healthy AZs within minutes, nothing is terminated or redeployed, and when the shift ends or is cancelled traffic returns automatically.
X: A=Route 53 failover to a maintenance page: failover routing is for when the whole endpoint is unhealthy. It would take the entire application offline for everyone instead of shifting away from one bad AZ.
B=Remove the subnet from the group: this terminates and relaunches capacity, which takes time and must be undone by hand. The ALB would still route to that AZ until the instances are gone.
D=Aggressive health checks: gray failures are intermittent, so tighter checks would make the impaired zone's targets flap between healthy and unhealthy rather than cleanly removing the AZ, and brief slowdowns could mark healthy targets in other zones as failed too.
T: For a gray failure in one AZ that health checks miss, shift traffic away with ARC zonal shift; DNS failover and redeployments act on the wrong scope or too slowly.
G: ## Gray failures
A gray failure is a partial impairment: some requests in one AZ time out or slow down, but simple health checks still pass. Load balancers keep sending traffic there because every target looks healthy.
## Zonal shift
**Amazon Application Recovery Controller (ARC) zonal shift** lets you move traffic for a supported resource, such as an ALB or NLB, away from one Availability Zone:
- You pick the resource, the AZ to avoid, and an expiry time (you can extend it).
- The load balancer stops routing to that AZ; the other AZs take the load.
- When the shift expires or you cancel it, traffic returns. Nothing is deleted.
**Zonal autoshift** lets AWS start a shift for you when it detects an AZ impairment.
## Design implication
Shifting away one AZ out of three removes a third of capacity, so size each AZ to carry the load of a lost zone (static stability).
V: Amazon Application Recovery Controller, Elastic Load Balancing, Amazon EC2 Auto Scaling

@ SAA-C03 D2 T2.2 applied use-case
S: A company replicates new objects from an S3 bucket in eu-west-1 to a bucket in eu-central-1. A regulator requires that the company can show that 99.99% of new objects are copied to the second Region within 15 minutes, and operations must be alerted when an object misses that threshold. What should a solutions architect configure?
A: Cross-Region Replication with S3 Replication Time Control enabled, plus replication metrics and event notifications for missed thresholds
B: Cross-Region Replication with S3 Transfer Acceleration enabled on both buckets, plus an S3 Storage Lens dashboard for replication status
C: A nightly S3 Batch Replication job that copies all new objects, with an Amazon EventBridge rule that reports failed tasks in each job
D: Cross-Region Replication with delete marker replication enabled, plus an AWS Config rule that checks the replication status of each object
K: A
W: Replication Time Control: RTC is designed to replicate 99.99% of new objects within 15 minutes and is backed by a service level agreement. It turns on replication metrics (pending bytes, pending operations, latency) and can raise S3 event notifications when an object exceeds the threshold, which covers both the evidence and the alerting requirement.
X: B=Transfer Acceleration and Storage Lens: Transfer Acceleration speeds up client uploads over long distances through edge locations; it does not apply to replication between buckets. Storage Lens gives aggregated usage insights, not per-object alerts.
C=Nightly Batch Replication: Batch Replication is for existing objects or retries of failed ones. A nightly job means new objects wait up to 24 hours, which breaks the 15-minute requirement.
D=Delete marker replication and Config: replicating delete markers changes what is copied, not how fast. AWS Config checks resource configurations and does not track the replication time of individual objects.
T: Plain replication is asynchronous with no time guarantee; when you need a 15-minute SLA with metrics and alerts, enable S3 Replication Time Control.
G: ## S3 replication basics
**Cross-Region Replication (CRR)** asynchronously copies new objects from a source bucket to a destination bucket in another Region. Versioning must be on for both buckets. Most objects arrive within seconds, but plain CRR gives no time guarantee.
## Replication Time Control
**S3 Replication Time Control (RTC)** is an option on a replication rule:
- It is designed to replicate 99.99% of new objects within 15 minutes, backed by a service level agreement.
- It enables **replication metrics** in CloudWatch: bytes pending, operations pending and replication latency.
- It can emit **S3 event notifications** such as `s3:Replication:OperationMissedThreshold` and `OperationReplicatedAfterThreshold`, which can go to SNS, SQS, Lambda or EventBridge.
Example: an EventBridge rule on missed-threshold events pages the on-call engineer.
## Related tools
**Batch Replication** copies objects that existed before the rule or that failed earlier.
V: Amazon S3, Amazon EventBridge, Amazon CloudWatch

@ SAA-C03 D2 T2.2 applied troubleshooting
S: A Java application connects to an Aurora MySQL cluster by using the instance endpoint of the current writer instance. During a test failover, a replica was promoted in about 30 seconds, but the application kept failing writes for more than 10 minutes until it was restarted. Which TWO changes reduce the outage in future failovers? (Select TWO)
A: Change the application's connection string to the cluster endpoint, which always points to the instance that is currently the writer
B: Configure the JVM DNS cache TTL to a few seconds, or use the AWS Advanced JDBC Wrapper, so the new writer's address is picked up quickly
C: Change the application's connection string to the reader endpoint, which balances connections across all instances of the cluster
D: Create a custom endpoint that contains only the current writer instance and point the application's write connections at that endpoint
E: Add an Aurora cross-Region replica in a second Region so that the application can switch its write connections to it during a failover
K: A,B
W: A=Cluster endpoint: Aurora updates the cluster (writer) endpoint's DNS record to the new primary during failover. An instance endpoint keeps pointing to the old instance, which is now a read-only replica, so writes fail.
B=Short DNS caching or a failover-aware driver: the JVM can cache DNS lookups for a long time, so even the cluster endpoint would resolve to the old address. A TTL of a few seconds, or the AWS Advanced JDBC Wrapper which tracks the cluster topology, reconnects to the new writer within seconds.
X: C=Reader endpoint for writes: the reader endpoint routes to replicas, which are read-only. Write statements would fail even without a failover.
D=Custom endpoint with the writer: custom endpoints have a fixed membership. After failover the listed instance becomes a replica, so the endpoint still points at a read-only instance.
E=Cross-Region replica: it adds Regional disaster recovery, but promoting it is a manual, slower step. It does not fix the stale endpoint that caused a 10-minute outage inside one Region.
T: Aurora failover is fast only if the app follows it: connect to the cluster endpoint and avoid long DNS caching (or use a failover-aware driver), never a fixed instance endpoint.
G: ## Aurora endpoints
- **Cluster endpoint**: always resolves to the current writer. Use it for writes.
- **Reader endpoint**: spreads connections across replicas. Use it for read-only traffic.
- **Instance endpoint**: points to one specific instance, whatever its role.
- **Custom endpoint**: a fixed set of instances you choose, for example large replicas for reports.
## What happens during failover
Aurora promotes a replica, typically in about 30 seconds, and updates the cluster endpoint's DNS record, which has a short TTL. Clients must:
1. Use the cluster endpoint, not an instance endpoint.
2. Not cache DNS for long. In Java, set `networkaddress.cache.ttl` low.
3. Reconnect on errors.
The **AWS Advanced JDBC Wrapper** knows the cluster topology and switches to the new writer without waiting for DNS, which shortens the outage further.
V: Amazon Aurora

@ SAA-C03 D2 T2.2 advanced troubleshooting
S: A company uses a Route 53 private hosted zone with failover routing for an internal API. The primary record points to the private IP address of an internal Network Load Balancer, and the record has a standard HTTPS health check on that IP. The health check always reports unhealthy, even when the API works. What should a solutions architect do?
A: Allow inbound HTTPS in the NLB's security group from the Route 53 health checker IP address ranges published by AWS for each Region
B: Move the NLB to a public subnet and assign it an Elastic IP address so the Route 53 health checkers can reach the health check target
C: Enable health checks on the NLB's target group and associate the target group with the failover record instead of a Route 53 health check
D: Create a CloudWatch alarm on the NLB's HealthyHostCount metric and associate a Route 53 health check based on that alarm with the record
K: D

The company wants events stored under prefixes such as customer_id=123/date=2026-09-01/ with no custom servers. What should a solutions architect do?
A: Configure dynamic partitioning on the Firehose stream, extracting customer_id and the date from each JSON record to build the S3 prefix
B: Add an S3 event notification that invokes a Lambda function to copy each delivered file into per-customer prefixes and delete the original
C: Configure the Firehose stream's S3 buffer size to 128 MB and its buffer interval to 900 seconds so that each file holds fewer customers
D: Schedule an AWS Glue crawler every hour so that it detects customer_id in the data and adds it as a partition column in the Data Catalog
K: A
W: Firehose dynamic partitioning: Firehose reads partition keys from each record, using inline JSON parsing (jq expressions) or a Lambda function, and writes records to S3 prefixes built from them, such as `customer_id=!{partitionKeyFromQuery:customer_id}/`. Athena can then prune partitions and read only one customer's files.
X: B=Lambda to copy files: each delivered file mixes many customers, so the function would have to split files record by record, and copying then deleting objects doubles writes and adds code to run and maintain.
C=Bigger buffers: buffering controls how often and how large files are written. Each file would still mix all customers under one prefix, and Athena would still scan everything.
D=Hourly Glue crawler: a crawler records partitions that already exist as folders. It cannot move data into per-customer prefixes, so a column inside mixed files does not let Athena skip them.
T: To lay out streaming data by key for partition pruning, use Firehose dynamic partitioning at write time; crawlers and buffering do not reorganize files.
G: ## Why the S3 layout matters for Athena
Athena reads the files under a table's location. With **Hive-style partitions** such as `customer_id=123/date=2026-09-01/`, a query that filters on those columns reads only the matching folders (partition pruning), which cuts both time and cost.
## Dynamic partitioning in Firehose
- Enable dynamic partitioning on the stream.
- Define partition keys, either with inline JSON parsing using jq, for example `customer_id: .customer_id`, or from a Lambda transformation.
- Build the S3 prefix from the keys: `customer_id=!{partitionKeyFromQuery:customer_id}/date=!{partitionKeyFromQuery:event_date}/`.
Firehose buffers records per partition and writes separate objects for each one. Dynamic partitioning is set when a stream is created, so for an existing stream you create a replacement stream with it enabled and point producers at it. It can also convert the records to Parquet before writing.
## Registering partitions
Use partition projection in the Athena table or a Glue crawler so new partitions become queryable.

S: A Kinesis data stream with 10 shards feeds five separate consumer applications that use the GetRecords API. Writers are well below the shard write limits, but consumers regularly receive ReadProvisionedThroughputExceeded errors and lag several seconds behind. Two more consumers are planned. Each consumer needs its own read throughput and low latency. What should a solutions architect do?
A: Double the number of shards in the stream so that the shared read throughput and the GetRecords call limits of the stream are doubled
B: Register the consumers for enhanced fan-out so that each consumer receives its own 2 MB per second per shard through SubscribeToShard
C: Increase the stream's data retention period to 7 days so that lagging consumers can catch up later without losing any of the records
D: Configure every consumer to call GetRecords with a larger batch limit so that each call returns more records for each of the shards
K: B
W: Enhanced fan-out: every registered consumer gets a dedicated 2 MB per second per shard, and records are pushed over HTTP/2 with latency around 70 ms. Adding consumers no longer divides the shared read limit, so the two planned consumers do not slow the others.
X: A=Double the shards: it doubles the shared read capacity for now, but all consumers still split it, and the planned consumers would reduce it again. It also doubles shard cost even though writers do not need more capacity.
C=Longer retention: keeping data longer prevents loss while consumers lag, but it does nothing to remove the throttling or the delay.
D=Larger GetRecords batches: the limit is 2 MB per second per shard shared by all consumers, plus 5 calls per second per shard. Bigger batches do not raise the byte limit, so throttling continues.
T: Shared-throughput consumers split 2 MB/s per shard; enhanced fan-out gives each consumer its own 2 MB/s per shard with push delivery.
G: ## Reading from a Kinesis data stream
Each shard supports writes of 1 MB per second and reads of 2 MB per second.
- **Shared throughput (standard) consumers** poll with `GetRecords`. All of them share the 2 MB per second per shard and a limit of 5 read calls per second per shard. With five consumers, each gets about 400 KB per second, and polling adds delay.
- **Enhanced fan-out consumers** register with the stream and call `SubscribeToShard`. Kinesis pushes records to each one over HTTP/2 with a dedicated 2 MB per second per shard.
## Example
10 shards, 7 consumers:
- Shared: 20 MB per second in total, split seven ways.
- Enhanced fan-out: 20 MB per second for each consumer, 140 MB per second in total.
Enhanced fan-out is billed per consumer-shard hour and per GB retrieved, so use it when several consumers or low latency are needed.
