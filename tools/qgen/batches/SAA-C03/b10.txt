# SAA-C03 batch 10: D1 secure architectures (20), detailed explanations

@ SAA-C03 D1 T1.1 advanced use-case
S: A platform team wants application developers to create their own IAM roles for new microservices without waiting for a central team. Developers must never be able to create a role that has more permissions than an approved ceiling, even if they write an administrator policy for it. Which design enforces this?
A: Give developers an identity policy that allows iam:CreateRole only when the request sets the approved permissions boundary through the iam:PermissionsBoundary condition key
B: Give developers an identity policy that allows iam:CreateRole on all resources and rely on an IAM Access Analyzer external access analyzer to alert on any overly broad role
C: Attach a service control policy to the developers' OU that lists the approved AWS services, and let developers create roles with any policy they like inside the OU
D: Give developers an identity policy that allows iam:CreateRole only for role names that start with the team prefix, and review each new role manually once per week
K: A
G: ## What a permissions boundary does
A permissions boundary is a managed policy attached to an IAM user or role as an upper limit. The effective permissions of that identity are the intersection of its identity policies and its boundary, so a role with an `AdministratorAccess` policy and a narrow boundary can still do only what the boundary allows.
## Making the boundary mandatory
Delegating role creation is safe only if the delegated permission itself forces the boundary. The developer's policy allows `iam:CreateRole` (and `iam:AttachRolePolicy`, `iam:PutRolePolicy`) with a `Condition` that `iam:PermissionsBoundary` equals the ARN of the approved boundary policy. A request that omits the boundary or names a different one is not allowed. A second statement denies `iam:DeletePolicy` and `iam:DeleteRolePermissionsBoundary` so the boundary cannot be removed later.
W: Condition on the boundary: because creation is allowed only when the approved boundary is attached, every developer-created role is capped at that ceiling no matter which policies are attached, and no central team needs to approve each role.
X: B=Access Analyzer alerts: an external access analyzer reports resources shared outside the account or organization. It detects nothing about how powerful a role is inside the account, and an alert arrives after the role already exists.
C=Service control policy: an SCP limits which actions accounts can use, but it is an account-wide guardrail. It cannot cap one role differently from another, and inside the allowed services a developer could still create a role with full access to them.
D=Name prefix and manual review: a naming rule limits which roles can be created, not what they can do, and a weekly review leaves a window in which an over-privileged role is already in use.
T: To delegate role creation safely, allow iam:CreateRole only with the iam:PermissionsBoundary condition set to the approved boundary.
V: AWS IAM

@ SAA-C03 D1 T1.1 advanced troubleshooting
S: A company attached a service control policy to the root of its organization that denies ec2:RunInstances in every Region except eu-west-1. Instances are correctly blocked in all member accounts, but an administrator signed in to the organization's management account was still able to launch an instance in us-east-1. What explains this?
A: The SCP was attached to the organization root, and SCPs attached there apply only to organizational units and never to accounts that sit directly under the root
B: SCPs are evaluated only for IAM users, so the administrator would have been blocked only if the request had been made by an assumed IAM role instead
C: SCPs do not restrict the management account at all, so the administrator there is limited only by IAM policies, and workloads should run in member accounts
D: The deny statement in the SCP takes effect only after the Region us-east-1 is explicitly disabled in the account settings of the management account
K: C
G: ## What SCPs control
Service control policies in AWS Organizations set the maximum permissions for principals in member accounts. Whatever an IAM policy grants, the action must also be allowed by every SCP on the path from the organization root down to the account. An explicit deny in an SCP always wins.
## The management account exception
SCPs never affect principals in the management account, even when attached to the root. They also do not affect service-linked roles. This is why AWS advises keeping the management account free of workloads and using it only for organization management, billing and a small set of administrators.
W: Management account exemption: the SCP works as designed in member accounts, and the management account is simply outside its scope. Moving workloads into a member account brings them under the guardrail.
X: A=Root attachment: an SCP attached to the root is inherited by every OU and every member account below it, including accounts placed directly under the root. The attachment point is not the cause.
B=IAM users only: SCPs apply to all principals in member accounts, users and roles alike, as well as the account root user. They are not limited to IAM users.
D=Region disabled first: SCP denies work independently of Region enablement settings. Disabling a Region controls whether the Region can be used at all, and is not a prerequisite for a deny statement to apply.
T: SCPs guard member accounts only; the management account is never restricted by them, so keep workloads out of it.
V: AWS Organizations

@ SAA-C03 D1 T1.1 applied use-case
S: An application team has run a set of EC2 and Lambda workloads in a production account for a year using a broad role with dozens of service permissions. Security wants to replace it with a least-privilege policy based on what the role actually calls, with as little manual analysis as possible. Which approach fits?
A: Use IAM Access Analyzer policy generation, which reviews the role's AWS CloudTrail activity for a chosen period and produces a policy containing only the actions used
B: Use IAM Access Analyzer to check for external access, which lists each unused action of the role and rewrites the role's policy automatically without any review
C: Use the IAM credential report, which lists every action the role called in the last 90 days and can be imported directly as a replacement policy
D: Use AWS Config with the iam-policy-no-statements-with-admin-access rule, which generates a narrower policy for every role that it flags as non-compliant
K: A
G: ## Getting to least privilege from real usage
Teams often start with broad permissions to ship quickly. Trimming them later is hard because nobody knows which actions the workload really calls.
IAM Access Analyzer can generate a policy from access activity. You pick a principal and a time window (up to 90 days), and it analyzes the CloudTrail logs of the account (a trail must exist) to build a policy with only the actions and, for many services, the resources that were used. You then review it, fill in resource-level restrictions, and attach it.
W: Policy generation: it produces a starting least-privilege policy from CloudTrail data, so the team does not read logs by hand. Access Analyzer also offers unused access findings for unused roles, keys and permissions.
X: B=External access analyzer: this analyzer type finds resources shared outside the account or organization. It does not report per-action usage, and no Access Analyzer feature rewrites a role's policy automatically without review.
C=Credential report: the report lists IAM users and the status of their passwords and access keys. It contains no record of the actions a role called.
D=AWS Config rule: the managed rule only flags policies that grant full administrator access. It reports compliance and does not generate replacement policies.
T: Use Access Analyzer policy generation to turn CloudTrail activity into a least-privilege policy, then review it before attaching.
V: AWS IAM, AWS CloudTrail

@ SAA-C03 D1 T1.1 applied use-case
S: A manufacturer runs a data collection service on servers in its own data centers. The service must upload files to Amazon S3, but the security policy forbids long-term IAM user access keys on those servers. The company already runs an internal public key infrastructure that issues X.509 certificates to each server. Which solution meets the requirements?
A: Store an access key for an IAM user in AWS Secrets Manager and have each server fetch it, rotating the key every 30 days with a Lambda function
B: Configure IAM Roles Anywhere with a trust anchor for the internal certificate authority, and let each server exchange its certificate for temporary credentials of a role
C: Create an IAM user for each server and require MFA through a hardware device that is installed on the server, so the keys can only be used with the second factor
D: Set up an Amazon Cognito identity pool that accepts the server certificates as an authentication provider, and return temporary credentials to each server after sign-in
K: B
G: ## Temporary credentials for workloads outside AWS
Workloads on AWS get temporary credentials from an instance profile or execution role. Workloads outside AWS lack that, so teams historically created IAM users with long-term access keys, which are hard to rotate and easy to leak.
IAM Roles Anywhere lets such workloads use an X.509 certificate they already have. You register the company's certificate authority (or AWS Private CA) as a trust anchor, create a profile that maps to one or more IAM roles, and each server presents its certificate signature to receive short-lived credentials, usually through the credential helper tool.
W: Roles Anywhere: no long-term keys exist anywhere, the existing PKI is reused, and the role can be limited by conditions on the certificate attributes.
X: A=Stored access key: the requirement forbids long-term keys, and rotating them only shortens how long a leaked key works. It is still an IAM user key.
C=IAM user with MFA: this is still a long-term access key per server. Hardware MFA also protects console and API sign-in with a person present, and does not fit unattended servers.
D=Cognito identity pool: identity pools federate users signed in through user pools, social or SAML and OIDC providers. They do not accept machine X.509 certificates as an authentication provider.
T: For servers outside AWS that already hold X.509 certificates, use IAM Roles Anywhere instead of IAM user keys.
V: AWS IAM Roles Anywhere, AWS IAM

@ SAA-C03 D1 T1.1 applied tradeoff
S: A shared S3 data lake bucket is used by finance, marketing and a fraud analytics application, and each group may read only its own prefix. The bucket policy has grown to several hundred lines and hits size limits whenever a new team joins. Which change reduces the policy complexity while keeping access separated?
A: Create one bucket per team and copy data from the data lake every night, so that each bucket needs only a short policy
B: Create an S3 access point per team with its own policy limited to that team's prefix, and delegate access control from the bucket policy
C: Enable S3 Object Ownership set to bucket owner enforced, so that access to each prefix follows the ACL that each team sets on the objects it uploads
D: Replace the bucket policy with S3 Block Public Access settings for each team, limiting each team to its prefix
K: B
G: ## The problem access points solve
A bucket policy is a single document capped at 20 KB. In a data lake shared by many applications, each new consumer adds statements, and one mistake can affect everyone.
## Access points
An S3 access point is a named network endpoint attached to a bucket, with its own access point policy and its own network origin control (internet or a specific VPC). The bucket policy needs only one statement that delegates control to access points owned by the account. Each team's policy then grants access to its prefix on its own access point, and applications use the access point alias or ARN as the bucket name.
W: Access points: every team gets an independent, small policy, adding a team means adding an access point, and the bucket policy stays short and stable.
X: A=One bucket per team: copying creates duplicate data, storage costs and a stale-data problem between the nightly runs. It also moves the complexity into managing many buckets.
C=Object Ownership with ACLs: bucket owner enforced disables ACLs completely, so per-object ACLs cannot be used for access control at all. It is also the opposite of a per-prefix access model.
D=Block Public Access: this setting prevents public access through ACLs and policies. It has no per-team, per-prefix configuration and does not grant private access to anyone.
T: Use S3 access points to give each consumer its own policy and network origin, instead of growing one large bucket policy.
V: Amazon S3

@ SAA-C03 D1 T1.1 applied use-case
S: A developer with an IAM user in the dev account must run a deployment script that assumes an IAM role in the production account. Which TWO configurations are required for the role assumption to succeed? (Select TWO)
A: A trust policy on the production role that names the dev account, or the specific dev principal, as allowed to call sts:AssumeRole
B: A copy of the developer's IAM user, created with the same name in the production account, so that the two identities can be matched
C: A VPC peering connection between the dev and production accounts, so that the security token service can be reached privately
D: An identity policy for the developer's user in the dev account that allows sts:AssumeRole on the ARN of the production role
E: A resource share created with AWS Resource Access Manager that includes the production role and is accepted by the dev account
K: A,D
G: ## Two sides of a cross-account role assumption
IAM evaluates cross-account access from both accounts. The account that owns the resource, here the role, must trust the caller, and the calling account must let its principal make the call.
- The role's trust policy is a resource-based policy. It lists who may assume the role, for example the dev account ID or one specific user or role ARN.
- The caller's identity policy must allow `sts:AssumeRole` on the role's ARN, unless a permissions boundary or SCP blocks it.
The result is a set of temporary credentials with the role's permissions, and nothing is copied between the accounts.
W: A=Trust policy: the production role must allow the dev principal, otherwise the call is denied by the owner of the role.
D=Identity policy: the developer's user in the dev account must be allowed to call sts:AssumeRole on that role, because cross-account access needs an allow on both sides.
X: B=Duplicate user: roles are assumed by the identity in its own account. A same-named user in the production account would be an unrelated identity and is not needed.
C=VPC peering: the STS API is a public AWS endpoint that IAM authenticates independently of any network. Peering has no effect on role assumption.
E=Resource share: AWS RAM shares supported resources such as subnets and license configurations. IAM roles cannot be shared this way, and access uses trust policies.
T: Cross-account role assumption needs a trust policy on the role and an sts:AssumeRole allow on the caller's side.
V: AWS IAM, AWS STS

@ SAA-C03 D1 T1.1 applied use-case
S: A company exposes a REST API through Amazon API Gateway to its customer-facing mobile app. Customers sign in through an Amazon Cognito user pool. The company wants API Gateway to reject any request that does not carry a valid token from that user pool, without writing or hosting authorization code. Which option meets this?
A: Create an API Gateway Lambda authorizer that downloads the user pool's public keys and validates the JWT signature and expiry in custom function code
B: Require an API key on every method and give each customer a key in a usage plan, so that only registered customers can invoke the API
C: Turn on AWS IAM authorization for the methods and have the mobile app sign each request with Signature Version 4 using an access key that is embedded in the app
D: Configure a Cognito user pool authorizer on the API methods, so that API Gateway validates the token that the client sends in the Authorization header
K: D
G: ## Choosing an API authorization method
API Gateway REST APIs support several ways to authorize callers:
- **IAM authorization** uses Signature Version 4 and suits callers that already hold AWS credentials.
- **Lambda authorizers** run your own code for custom schemes.
- **Cognito user pool authorizers** validate tokens issued by a Cognito user pool with no code.
- **API keys** identify clients for throttling and quotas and are not an authentication mechanism.
## How the Cognito authorizer works
After sign-in the app receives JWTs. It sends the token in the `Authorization` header, and API Gateway checks the signature, expiry and issuer against the user pool before it calls the integration.
W: Cognito authorizer: validation is done by API Gateway itself, so there is no code to write, host, or scale, and invalid tokens are rejected before reaching the backend.
X: A=Lambda authorizer: this works, but it is custom code to write, test and pay for on each unauthenticated request, which the requirement asked to avoid.
B=API keys: keys are meant for usage plans and are easy to extract from a mobile app. Anyone holding the key would be accepted, so this does not check the user's sign-in.
C=IAM authorization with embedded key: it requires long-term credentials inside the app, which can be extracted, and it does not use the user pool tokens at all.
T: Use a Cognito user pool authorizer to have API Gateway validate user pool tokens with no custom code.
V: Amazon API Gateway, Amazon Cognito

@ SAA-C03 D1 T1.2 advanced troubleshooting
S: A web application on EC2 has a server-side request forgery flaw: an attacker can make the application send HTTP requests to a URL of their choice. The attacker used it to read the instance's IAM role credentials from the link-local metadata address. The application cannot be patched immediately. Which change removes this attack path with the LEAST impact on the application?
A: Require IMDSv2 on the instance by setting the metadata option HttpTokens to required, so that a session token from a PUT request is needed to read credentials
B: Add an outbound rule to the instance's security group that denies traffic to 169.254.169.254, so that the instance can no longer reach the metadata service
C: Turn off the instance metadata service completely, and pass the role credentials to the application through environment variables in its startup script
D: Move the instance to a private subnet without a route to the internet, so that the attacker cannot send the forged request from outside the VPC
K: A
G: ## Why IMDSv1 is exposed to SSRF
The instance metadata service (IMDS) serves the role's temporary credentials at a link-local address. IMDSv1 answers a simple GET request, so any bug that lets an attacker make the server issue a GET can leak them.
## IMDSv2
IMDSv2 is session based. The caller first sends a `PUT` request with a TTL header to get a token, then sends the token in a header on each request. Typical SSRF flaws only allow GET-style requests and cannot set these headers, and the default hop limit of 1 also keeps the token off proxies beyond the instance. You can require it per instance (`HttpTokens=required`), in launch templates, or as an account default per Region.
W: IMDSv2 required: the application and SDK, if current, already use IMDSv2 automatically. The forged request cannot obtain a token, so the credentials cannot be read.
X: B=Security group rule: security groups do not filter traffic to the instance metadata service, and rules can only allow. The request would still succeed.
C=Disable IMDS: this breaks the role-based credentials the SDK obtains automatically and pushes teams towards long-term keys in environment variables, which is worse.
D=Private subnet: the flaw makes the application itself send the request to the metadata address on its own host. Where the instance is placed does not change that.
T: Require IMDSv2 to make SSRF credential theft from the metadata service fail; security groups cannot block IMDS.
V: Amazon EC2, AWS IAM

@ SAA-C03 D1 T1.2 advanced tradeoff
S: A company with 80 accounts in AWS Organizations wants every Application Load Balancer, including those in accounts created in the future, to be protected by AWS WAF with a baseline web ACL that the security team controls. Teams must not be able to detach it silently, and a single team should manage it. Which solution meets this?
A: Use AWS Firewall Manager with a delegated administrator account and an AWS WAF policy that applies the baseline web ACL to all ALBs in scope
B: Use a service control policy that denies elasticloadbalancing:CreateLoadBalancer unless a WAF web ACL is named in the request that creates the load balancer
C: Use an AWS CloudFormation StackSet that deploys the web ACL and association to the existing accounts, and rerun it manually each time a new account is created
D: Use an AWS Config conformance pack that reports ALBs with no web ACL, and have each application owner attach the ACL when a finding appears
K: A
G: ## Central WAF management
AWS WAF web ACLs are regional resources that must be associated with each ALB, API Gateway stage or CloudFront distribution. Across many accounts, doing that by hand does not scale.
## AWS Firewall Manager
Firewall Manager runs in a delegated administrator account of an organization with AWS Config enabled. A WAF policy defines the rule groups and the scope (accounts, OUs, resource types or tags). Firewall Manager automatically associates the web ACL to matching resources, including ones created later, and can auto-remediate a resource whose ACL was removed. It also manages Shield Advanced, security groups, Network Firewall and DNS Firewall policies.
W: Firewall Manager: it covers new and existing accounts automatically and keeps the baseline in place, with one team managing it.
X: B=SCP on load balancer creation: the CreateLoadBalancer request does not carry a web ACL, since association is a separate WAF call afterwards, so this condition cannot be evaluated. Nothing would attach the ACL either.
C=Manual StackSet reruns: a StackSet can deploy the ACL, but without automation new accounts stay unprotected until someone remembers, and a detached ACL is not restored.
D=Conformance pack reporting: Config only detects and reports. Each owner must fix findings, so unprotected ALBs remain until then.
T: For an organization-wide, self-healing WAF baseline, use AWS Firewall Manager with a WAF policy.
V: AWS Firewall Manager, AWS WAF, AWS Organizations

@ SAA-C03 D1 T1.2 applied use-case
S: A company builds container images in a CI pipeline, pushes them to Amazon ECR, and runs them on ECS with AWS Fargate. Security wants each image scanned for known software vulnerabilities when it is pushed and rescanned when new vulnerabilities are published, with findings sent to one central place. Which service fits?
A: Amazon GuardDuty with Runtime Monitoring turned on, which reports known CVEs for packages in each image
B: Amazon Macie with a scan job on the ECR repository, which lists the operating system and library CVEs found in each image layer
C: Amazon Inspector with enhanced scanning for ECR, which scans on push and rescans as new CVEs appear, with findings sent to Security Hub
D: AWS Config with a managed rule for ECR image scanning, which patches the vulnerable libraries in each stored image after the scan completes
K: C
G: ## Vulnerability management versus threat detection
- **Amazon Inspector** is a vulnerability management service. It scans EC2 instances (using SSM), ECR container images and Lambda functions for software vulnerabilities (CVEs) and unintended network exposure.
- **Amazon GuardDuty** detects suspicious behavior and threats, such as credential misuse or malware activity, from logs and runtime signals.
- **Amazon Macie** finds sensitive data in S3.
## Continuous scanning
With enhanced scanning Inspector scans an image when it is pushed and rescans it when a new CVE is added to its database, without a new push. Findings are sent to Security Hub, and EventBridge events can drive tickets or notifications.
W: Inspector for ECR: on-push and continuous rescanning matches the requirement, and findings flow to central tools.
X: A=GuardDuty Runtime Monitoring: it observes running workloads for suspicious behavior. It does not inventory packages in images or report CVEs before a push.
B=Macie: Macie classifies sensitive data such as personal information in S3 objects. It does not read container layers for vulnerabilities.
D=AWS Config rule: Config evaluates the configuration state and reports compliance. It does not patch images, which are immutable and must be rebuilt.
T: Use Amazon Inspector for CVE scanning of ECR images, EC2 instances and Lambda functions; GuardDuty detects threats instead.
V: Amazon Inspector, Amazon ECR

@ SAA-C03 D1 T1.2 applied use-case
S: Security analysts found that malware on several EC2 instances resolves attacker-controlled domain names, using DNS queries to carry stolen data out of the VPC. Outbound web traffic is already filtered. The company needs to block resolution of known malicious domains and log such queries from all VPCs. Which service fits?
A: AWS Network Firewall with a stateful domain list rule group, deployed in each VPC and applied to the DNS queries that instances send to the Route 53 Resolver, blocking the malicious domains
B: Network ACLs on every subnet with outbound deny rules for the IP addresses of the malicious domains, kept up to date by a scheduled Lambda function that reads a threat intelligence feed
C: AWS WAF web ACLs associated with each VPC, using AWS managed rule groups that block requests to domains flagged by AWS threat intelligence and log every matching DNS query
D: Amazon Route 53 Resolver DNS Firewall with AWS managed domain lists and custom lists, associated with the VPCs and configured to block and log matching queries
K: D
G: ## DNS as an exfiltration path
Every instance can query the Amazon-provided DNS resolver at the VPC base address +2 even if all other outbound traffic is blocked. Malware can hide data in the names of queries (DNS tunneling) or look up command-and-control domains.
## Route 53 Resolver DNS Firewall
DNS Firewall filters outbound queries handled by Route 53 Resolver. You build rule groups with domain lists, either AWS managed lists of malicious domains or your own, choose an action (allow, alert or block with a chosen response), and associate them with VPCs. AWS Firewall Manager can apply them across accounts. Queries are logged through Resolver query logging.
W: DNS Firewall: it works on the domain name in the query itself and works for all VPCs it is associated with, with logging.
X: A=Network Firewall: it inspects traffic that flows through its endpoints, such as HTTP host and TLS SNI. Queries sent to the Route 53 Resolver are not routed through a firewall endpoint, so they are not inspected there.
B=Network ACLs: NACLs match IP addresses and ports. Malicious domains change addresses constantly, and a DNS query goes to the resolver, not to the malicious address.
C=AWS WAF: WAF inspects HTTP requests sent to CloudFront, ALB and API Gateway. It cannot be attached to a VPC and does not see DNS queries.
T: Use Route 53 Resolver DNS Firewall to block and log DNS queries to malicious domains from your VPCs.
V: Amazon Route 53, AWS Network Firewall

@ SAA-C03 D1 T1.2 applied use-case
S: A security team runs AWS Security Hub in 40 accounts and three Regions. Analysts must see all findings in one console and enable Security Hub in new accounts automatically. Which TWO actions set this up? (Select TWO)
A: Designate a delegated administrator account for Security Hub in AWS Organizations and enable automatic enrollment of new member accounts
B: Configure cross-Region aggregation in the administrator account, choosing one aggregation Region and linking the other two Regions so that their findings appear there
C: Export findings from each account to an S3 bucket every hour, and query the objects with Athena from the security account
D: Turn on AWS CloudTrail in every account, because Security Hub reads only management events from CloudTrail to produce its findings
E: Create an IAM user in each member account, and have the analysts sign in to each of them to review its Security Hub findings

G: ## Central visibility in Security Hub
Security Hub collects findings from AWS services (GuardDuty, Inspector, Macie, IAM Access Analyzer and others) and from partner products, and evaluates security standards.
- **Multiple accounts:** with AWS Organizations, you designate a delegated administrator account. It can enable Security Hub in member accounts, including new ones automatically, and sees their findings.
- **Multiple Regions:** Security Hub is regional. Cross-Region aggregation links other Regions to one aggregation Region so findings and updates are visible in one place.
W: A=Delegated administrator: it gives one account control over all member accounts and auto-enables new ones.

@ SAA-C03 D1 T1.2 applied use-case
S: A photo sharing service lets customers upload files directly to an S3 bucket. The company must detect malware in each newly uploaded object before other systems process it, prefers a managed service over running scanning servers, and wants results as object tags for downstream automation. Which solution fits?
A: Amazon GuardDuty Malware Protection for Amazon S3, enabled for the bucket, which scans new objects and tags each one with the scan result
B: Amazon Macie with an automated discovery job on the bucket, which scans new objects for malware signatures and tags each infected object
C: Amazon Inspector with S3 scanning turned on, which checks each object for known CVEs and marks the infected objects as unsafe
D: An EC2 Auto Scaling group running an open source antivirus engine that polls the bucket every hour, and copies the clean objects to a second bucket

G: ## Scanning uploads for malware
GuardDuty Malware Protection for S3 is a managed feature that scans objects newly uploaded to a protected bucket. It can be enabled for a bucket without turning on the rest of GuardDuty. Each scanned object gets a result tag (for example no threats found or threats found), and scan status events go to Amazon EventBridge, so a Lambda function or workflow can move, quarantine or delete infected files.
Similar sounding services do different jobs: Macie finds sensitive data in S3, Inspector finds software vulnerabilities in compute and images.
W: GuardDuty Malware Protection: it is managed, scans on upload, and produces tags and events for automation, so no scanning fleet is needed.
X: B=Macie: it classifies sensitive data such as personal information. It does not search for malware signatures.
C=Inspector: Inspector scans EC2 instances, container images and Lambda functions for software vulnerabilities. It does not scan S3 objects for malware.

V: Amazon GuardDuty, Amazon S3

@ SAA-C03 D1 T1.2 applied tradeoff
S: A team has 300 application settings for a fleet of Lambda functions, including 20 that are passwords or API tokens for third-party services that never need automated rotation. Values must be encrypted with a KMS key, changed without redeploying code, and the company wants the lowest cost. Which option fits?
A: Store every value as a standard tier SecureString parameter in AWS Systems Manager Parameter Store, encrypted with a customer managed KMS key
B: Store every value as a separate secret in AWS Secrets Manager, and turn on automatic rotation for all secrets so that values are changed regularly
C: Store every value in a JSON file in an S3 bucket, encrypted with SSE-S3, and have each function download the file at every cold start
D: Store every value in the Lambda function environment variables, and use the default Lambda encryption that AWS manages for the variables
K: A
G: ## Parameter Store or Secrets Manager
- **Systems Manager Parameter Store** holds configuration and secrets as String, StringList or SecureString parameters. SecureString values are encrypted with KMS. Standard parameters have no additional charge (KMS and API usage still apply), and each parameter is versioned and can be read with IAM permissions.
- **AWS Secrets Manager** is designed for secrets that need lifecycle features: built-in rotation with managed Lambda functions for databases, cross-Region replication, and resource policies. It is charged per secret per month plus API calls.
## Deciding
When there is no rotation requirement and cost matters, Parameter Store is the cheaper fit for hundreds of values. Secrets Manager is worth its price for credentials that must be rotated, such as database passwords.
W: Parameter Store SecureString: encrypted by KMS, updated without redeploying, no per-parameter fee for standard tier, and fine-grained IAM access.
X: B=Secrets Manager for all values: 300 secrets have a monthly per-secret charge, and rotation is not needed for these values, so most of the extra cost buys nothing.
C=Values in S3: SSE-S3 keys are managed by S3, so KMS key policy control and CloudTrail records of key use are missing, and downloading a file adds latency at each cold start.
D=Environment variables: changing a value needs a function configuration update, values are visible in the console to anyone who can read the configuration, and the limit is 4 KB for all variables of a function.
T: For non-rotating values at scale, Parameter Store SecureString is the low-cost choice; use Secrets Manager when rotation or replication is needed.
V: AWS Systems Manager, AWS Secrets Manager, AWS KMS

@ SAA-C03 D1 T1.3 applied comparison
S: A company must rotate its KMS keys every 180 days to meet an internal policy. Its applications use a customer managed symmetric key through an alias, and existing S3 objects and EBS snapshots must stay readable without being re-encrypted or reconfigured. Which approach meets this?
A: Enable automatic rotation on the customer managed key with a 180 day period, so the key ID and alias stay the same and older key material is kept
B: Create a new key every 180 days, repoint the alias to it, and re-encrypt existing objects and snapshots before deleting the old key
C: Import the company's own key material into the key and rely on automatic rotation to replace the imported material with new material every 180 days
D: Run a Lambda function that calls ReEncrypt on every object protected by the key each 180 days, storing the new ciphertext
K: A
G: ## How KMS key rotation works
For a customer managed symmetric encryption key with KMS-generated material, automatic rotation creates new key material on a schedule. The key ID, ARN, alias and policy stay the same. KMS keeps all older material, so data encrypted before a rotation still decrypts, and new encryption operations use the newest material. You can set the rotation period from 90 to 2,560 days (the default is 365).
## What rotation does not do
Rotation does not re-encrypt existing data. It also is not available for keys with imported key material, so those need manual rotation with a new key and an alias change.
W: Automatic rotation with a 180 day period: it meets the schedule with no application change and no data re-encryption.
X: B=New key and re-encryption: this is the manual pattern, needed only when automatic rotation is not available. It means re-encrypting all data and much operational effort.
C=Imported key material: KMS does not generate new material for keys with imported material, so automatic rotation is not supported for them.
D=ReEncrypt on a schedule: this makes a large, costly job for all objects and snapshots, and it is unnecessary because KMS keeps the old material for decryption.
T: Turn on automatic rotation with a custom period for customer managed symmetric keys: key ID and ciphertext stay valid, and no data is re-encrypted.
V: AWS KMS

@ SAA-C03 D1 T1.2 advanced use-case
S: A company serves private product images from an Amazon S3 bucket through an Amazon CloudFront distribution. The objects are encrypted with SSE-KMS using a customer managed key. Requests that go straight to the S3 URL must be denied, and only this one distribution may read the objects. Which configuration meets this?
A: Create an origin access control for the S3 origin, allow the cloudfront.amazonaws.com principal in the bucket policy with an aws:SourceArn condition for this distribution, and allow kms:Decrypt in the key policy
B: Create an origin access identity for the S3 origin, allow its canonical user in the bucket policy, and allow that identity to call kms:Decrypt on the customer managed key through the key policy statement
C: Enable static website hosting on the bucket with public read access, and have CloudFront send a secret Referer header that the bucket policy checks before it allows any GetObject request from the distribution
D: Keep the bucket readable through a bucket policy that allows GetObject only from the published CloudFront IP address ranges, and refresh the policy through a scheduled job whenever AWS changes those ranges
K: A
G: ## Restricting an S3 origin to CloudFront
CloudFront can sign its requests to S3 so that the bucket stays private and only the intended distribution can read from it. The current mechanism is origin access control (OAC). CloudFront signs each origin request with Signature Version 4, and the bucket policy allows the `cloudfront.amazonaws.com` service principal with an `aws:SourceArn` condition that names one distribution. That condition matters: without it, any distribution in any account could be pointed at the bucket.
## Encrypted objects
OAC supports SSE-KMS. The key policy must also let the CloudFront service principal use `kms:Decrypt`, again limited to the distribution with `aws:SourceArn`. The older origin access identity (OAI) cannot read SSE-KMS objects and does not cover newer Regions and features, so AWS recommends OAC for all new distributions.
W: Origin access control: the bucket stays private, the bucket and key policies trust exactly one distribution, and SSE-KMS objects can still be read.
X: B=Origin access identity: this is the legacy mechanism. It does not support objects encrypted with SSE-KMS, so reads of these objects would fail, and new work should use OAC.
C=Public website endpoint with a Referer header: the bucket must be public, and a header value is a shared secret that leaks easily. It is not an identity check, and anyone who learns it can read the bucket directly.
D=CloudFront IP ranges: the ranges are shared by every CloudFront customer, so any other distribution could read the bucket, the ranges change often, and the policy identifies a network instead of one distribution.
T: Use CloudFront origin access control with a bucket policy on aws:SourceArn (and a key policy for SSE-KMS) to keep an S3 origin private.
V: Amazon CloudFront, Amazon S3, AWS KMS

@ SAA-C03 D1 T1.3 applied troubleshooting
S: A security policy requires that connections to an Amazon RDS for PostgreSQL 14 instance use TLS. A penetration test shows that a client can still connect with a plain, unencrypted session, although storage encryption is enabled and the security group allows only the application subnet. What should the team do?
A: Re-create the DB instance from an encrypted snapshot copy that uses a customer managed key, which also requires TLS for every client session
B: Restrict the security group so that port 5432 is open only to the application subnet and to the bastion host that the testers used
C: Set the rds.force_ssl parameter to 1 in the instance's custom DB parameter group, so that the server rejects connections that do not use TLS
D: Move the DB instance into a private subnet, so that unencrypted sessions from inside the VPC are dropped by the network
K: C
G: ## At rest and in transit are separate controls
- **Encryption at rest** protects storage volumes, snapshots and backups. It does not change how clients connect.
- **Encryption in transit** protects the network session. RDS supports TLS, but it is optional on many engine versions unless the server is told to require it.
## Requiring TLS
For RDS for PostgreSQL and SQL Server, set `rds.force_ssl = 1` in a custom parameter group attached to the instance. For RDS for MySQL and MariaDB, use `require_secure_transport`. Newer versions (RDS for PostgreSQL 15 and later) already default to requiring TLS in new default parameter groups, so this gap appears on older versions or where the parameter was set to 0. Clients should also validate the server certificate using the current RDS CA bundle.
W: rds.force_ssl: the server itself refuses non-TLS connections, whatever the network path.
X: A=Encryption at rest: this protects the disks and does not affect the client connection, so plain sessions would keep working.
B=Security group rules: they control who can reach the port. A permitted client could still connect without TLS, and the tester was already inside the allowed range.
D=Private subnet: network placement limits reachability, but traffic inside the VPC is not encrypted by the subnet type, and an allowed client can still connect in plain text.
T: Require TLS on the database with rds.force_ssl (PostgreSQL, SQL Server) or require_secure_transport (MySQL, MariaDB); encryption at rest does not do that.
V: Amazon RDS

@ SAA-C03 D1 T1.3 applied use-case
S: A company has an Amazon EFS file system, created without encryption, that stores customer documents for Linux application servers. A new policy requires encryption of the data at rest and in transit. Which TWO actions meet the policy? (Select TWO)
A: Create a new file system with encryption at rest turned on, and copy the data into it by using AWS DataSync
B: Edit the existing file system and turn on encryption at rest, so that EFS re-encrypts the stored data in the background
C: Mount the file system with the amazon-efs-utils mount helper and the tls option, so that NFS traffic is encrypted with TLS
D: Restrict the mount target security group to accept NFS traffic on port 2049 only from the application servers' security group
E: Move the documents to an Amazon EBS volume that is attached to a single instance, and take snapshots of the volume every day
K: A,C
G: ## EFS encryption
- **At rest:** encryption is chosen when the file system is created and cannot be turned on for an existing file system. To encrypt existing data, create a new encrypted file system and copy data across, for example with AWS DataSync or AWS Backup restore.
- **In transit:** NFS traffic is not encrypted by default. The EFS mount helper (`amazon-efs-utils`) with `-o tls` sets up a TLS tunnel. A file system policy with a condition on `aws:SecureTransport` can deny connections that do not use TLS.
W: A=New encrypted file system with DataSync: this is the only way to get encryption at rest for these documents, and DataSync preserves file metadata during the copy.
C=Mount helper with TLS: it encrypts NFS traffic between the servers and EFS, meeting the in-transit part.
X: B=Editing the existing file system: encryption at rest can only be enabled at creation, so there is no setting to change on the existing file system.
D=Security group restriction: this limits who can connect but does not encrypt the traffic, so it satisfies neither part of the policy.
E=EBS volume: EBS is block storage that normally attaches to one instance (Multi-Attach is limited to certain io1 and io2 volumes in one Availability Zone), so it does not replace a shared file system, and the option does not turn on encryption.
T: EFS at-rest encryption is fixed at creation (migrate to a new file system); in-transit encryption uses the mount helper with TLS or a policy on aws:SecureTransport.
V: Amazon EFS, AWS DataSync

@ SAA-C03 D1 T1.3 applied comparison
S: A DynamoDB table stores payment records. Compliance says the company must be able to disable the encryption key to render the data unreadable in an emergency, and must see every use of that key in AWS CloudTrail. The table currently uses the default encryption. Which change meets the requirements?
A: Keep the default encryption with an AWS owned key, which the company can disable from the DynamoDB console and which logs each use in CloudTrail
B: Switch the table to the AWS managed key aws/dynamodb, which the company can disable at any time and whose key policy it can edit
C: Enable client-side encryption of the sensitive attributes and store the encryption keys in a private table of the same DynamoDB account
D: Switch the table encryption to a customer managed KMS key, which the company can disable and whose use appears in CloudTrail
K: D
G: ## Three key types for DynamoDB encryption
DynamoDB always encrypts data at rest. You choose which key protects it:
- **AWS owned key:** the default. It is managed entirely by DynamoDB, at no extra charge. You cannot see, audit or control it.
- **AWS managed key (`aws/dynamodb`):** it lives in your account and its use is logged in CloudTrail, but AWS controls its policy and lifecycle, and you cannot disable or delete it.
- **Customer managed key:** you own the key policy, can disable it or schedule deletion, and every use is logged. There are KMS charges for requests. You can switch the key type on an existing table.
W: Customer managed key: disabling the key blocks access to the data, and CloudTrail records each use of it, meeting both requirements.
X: A=AWS owned key: it is not visible in your account, so it cannot be disabled by you and its use does not appear in your CloudTrail.
B=AWS managed key: use is logged in CloudTrail, but only KMS-generated policies apply. You cannot edit its key policy or disable it.
C=Client-side encryption with keys in the same table: the keys would sit next to the data they protect, with no key policy, no disable switch, and no KMS audit trail, and the design adds application complexity.
T: Choose a customer managed KMS key when you need to disable a key and audit each use; AWS owned and AWS managed keys give you neither.
V: Amazon DynamoDB, AWS KMS

@ SAA-C03 D1 T1.3 advanced troubleshooting
S: An administrator scheduled deletion of a customer managed KMS key that was believed to be unused. Two days later, applications that read S3 objects encrypted with that key start failing with KMSInvalidStateException errors. The key had a 30-day waiting period. What is the correct recovery?
A: Cancel the scheduled key deletion, and then enable the key, since the key returns in a disabled state after cancellation
B: Create a new KMS key with the same alias name, and the applications will decrypt the existing objects with the new key
C: Restore the key from the automatic KMS backup that is kept for the waiting period, then reimport its key material
D: Open a support case to request an extension of the waiting period, and wait until the key is fully deleted to restore it
K: A
G: ## The KMS key deletion safety net
Deleting a KMS key is destructive: all data encrypted under it becomes unrecoverable. So KMS never deletes at once. Scheduling deletion puts the key in the **Pending deletion** state for 7 to 30 days. During that time the key cannot be used for encryption or decryption, and requests fail with an invalid state error.
## Getting the key back
While the key is still pending deletion, you can cancel the deletion. The key then becomes **Disabled**, and you must enable it again before it can be used. After the waiting period ends, deletion is permanent. To prevent accidents, disable the key first to test the impact, and use a CloudWatch alarm on failed requests to a key pending deletion.
W: Cancel and enable: because the waiting period is still running, the key and its data are intact, and enabling the key restores decryption for all objects.
X: B=New key with the same alias: an alias only points to a key. Objects are encrypted under the old key's material, and a new key cannot decrypt them.
C=Restore from a KMS backup: KMS does not offer key backups or restore of a deleted key. Only imported key material can be reimported, and only if the key itself still exists.
D=Support case and waiting: waiting for the deletion to finish destroys the key permanently, and support cannot restore it afterwards.
T: A key pending deletion can be recovered by cancelling the deletion and then enabling the key; after the waiting period ends, the data is lost.
V: AWS KMS, Amazon S3
