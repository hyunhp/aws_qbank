@ Q000431 explain
G: ## The shared responsibility model
AWS is responsible for security **of** the cloud (data centers, hardware, the hypervisor, and the software of managed services). The customer is responsible for security **in** the cloud: what it configures and deploys.
- **Amazon EC2** is infrastructure as a service. You choose the AMI and own the guest operating system, so you patch it (for example with Systems Manager Patch Manager), install agents and configure the firewall.
- **Amazon RDS** is a managed service. You never log in to the host OS; AWS patches the operating system and applies database engine updates during the maintenance window you choose (major version upgrades are something you approve).
## Security groups are always yours
A security group is a virtual firewall you define. Whether it is attached to an EC2 instance or an RDS DB instance, AWS enforces the rules but you write them, for example allowing TCP `3306` only from the app tier's security group.
W: Customer: EC2 guest OS and all SGs; AWS: the RDS operating system: the customer controls the EC2 guest OS and every security group rule, while RDS hides its OS and AWS patches it.
X: A=AWS patches EC2 on request: AWS has no access to your EC2 guest OS and does not patch it for you, and on RDS the engine patching is performed by AWS in the maintenance window, not by the customer logging in.
C=AWS patches both: AWS patches the RDS host, but the EC2 guest operating system belongs to the customer, who chose the AMI and must keep it updated.
D=Customer patches both, AWS manages SGs: the customer cannot reach the RDS operating system to patch it, and security group rules are always written by the customer, not by AWS.
T: The more managed the service, the more AWS patches: EC2 guest OS is yours, the RDS OS is AWS's, and security group rules are always yours.

@ Q000432 explain
G: ## Protecting the root user
The root user is the email address that created the AWS account. It has unrestricted access to everything in the account and some tasks only it can do (for example changing the account's support plan or closing the account).
- **Multi-factor authentication (MFA)** requires a second factor, such as a passkey, a hardware security key or an authenticator app code, in addition to the password. A stolen password alone is not enough to sign in.
- **Root access keys** allow programmatic calls with full root power and cannot be limited by IAM policies. AWS recommends not creating them at all and deleting any that exist.
## Other good root habits
- Use the root user only for the few tasks that require it; do daily work with IAM Identity Center users or IAM roles.
- Keep contact and recovery information up to date, and in AWS Organizations consider centrally managing root access for member accounts.
W: MFA on root; also delete root access keys: a phished password fails without the second factor, and removing root access keys eliminates the other path to unrestricted access.
X: A=Password policy and sharing: an IAM password policy applies to IAM users, not the root user, so it did not stop the login, and sharing the root password with more people increases the risk.
C=SCP denying root actions: SCPs do not apply to the management account at all, and an SCP restricts what an authenticated principal can do; it does not make a sign-in attempt fail.
D=Permissions boundary on root: permissions boundaries can be attached only to IAM users and roles, not the root user, and the root user should have no access keys to rotate.
T: A stolen password is defeated by MFA, not by policies; secure root with MFA and no access keys.

@ Q000433 explain
G: ## Single sign-on across many accounts
**AWS IAM Identity Center** is the recommended way to give workforce users access to multiple accounts in an AWS Organization.
- You connect an identity source: the built-in directory, an external SAML identity provider, or Active Directory (through **AD Connector** or AWS Managed Microsoft AD).
- **AD Connector** is a proxy: authentication requests go to your on-premises domain controllers, so users keep their existing AD passwords and those passwords are never copied into AWS.
- You create **permission sets** (for example `ReadOnlyAccess`) and assign AD groups to accounts with those permission sets. Identity Center creates the matching IAM roles in each account for you.
## Example
An employee in the AD group `Finance-Analysts` signs in once at the access portal and sees the three accounts that group is assigned, each with a read-only role. Removing them from the AD group removes access everywhere.
W: IAM Identity Center via AD Connector: users sign in once with their AD credentials, and access to all 12 accounts is managed centrally by assigning AD groups to permission sets, with no per-account IAM users.
X: A=Bastion host storing credentials: a bastion is for network access to instances, and storing credentials for 12 accounts on one host creates a high-value target and still requires IAM users in each account.
C=IAM users synced by script: this is exactly the per-account IAM user sprawl the company wants to avoid, and the custom sync script adds ongoing maintenance and long-term passwords or keys.
D=Shared IAM user: shared access keys give no individual accountability, cannot enforce per-person permissions, and are long-term secrets that leak easily.
T: For workforce single sign-on to many accounts with existing AD identities, use IAM Identity Center with an AD identity source, not IAM users.

@ Q000434 explain
G: ## Service control policies (SCPs)
AWS Organizations lets you attach **SCPs** to the root, an organizational unit (OU) or an account. An SCP does not grant permissions; it sets the maximum permissions available to IAM users and roles in the affected member accounts.
- An explicit `Deny` in an SCP wins over any `Allow` in an identity or resource policy, including a policy that grants `AdministratorAccess`.
- Account administrators cannot remove or edit an SCP from inside the member account; only the organization's management account (or a delegated administrator) can.
- SCPs do not restrict the management account itself.
## Example
An SCP attached to the `Workloads` OU:
- `Effect: Deny`, `Action: cloudtrail:StopLogging, cloudtrail:DeleteTrail, cloudtrail:UpdateTrail`, `Resource: *`
Now even an admin role in those accounts gets Access Denied when trying to turn logging off.
W: SCP denying CloudTrail stop and delete actions: the deny applies to every principal in the member accounts, overrides their IAM allows, and cannot be removed by the account's own administrators.
X: A=Deny in each identity policy: account administrators can edit or detach their own identity policies, so this is not permanent, and every new user or role would need the statement added.
B=Permissions boundary on every principal: administrators with IAM permissions can remove or change boundaries, and any new user or role created without one is not covered.
D=GuardDuty detection: GuardDuty can raise a finding when logging is disabled, but it detects after the fact; it does not prevent the API call.
T: To enforce a guardrail that even account admins cannot bypass, use an SCP from Organizations; IAM policies and boundaries live inside the account and can be changed there.

@ Q000435 explain
G: ## How EC2 applications get AWS credentials
An **IAM role** is an identity with permissions but no permanent password or keys. To use one on EC2 you attach it through an **instance profile**, a container that passes the role to the instance.
- The instance metadata service (preferably `IMDSv2`) serves temporary credentials for the role at a local endpoint.
- The AWS SDKs and CLI find these credentials automatically, so the application code contains no secrets.
- The credentials are short-lived and are refreshed automatically before they expire.
## Example
Create role `app-s3-dynamodb` with a policy allowing `s3:GetObject` on one bucket and `dynamodb:PutItem` on one table, attach it to the instance, and the code simply calls `boto3.client('s3')`.
W: Attach an IAM role to the EC2 instance profile: the application receives short-lived, automatically rotated credentials scoped by the role's policy, with no keys stored anywhere.
X: B=Access keys in a config file: long-term keys on disk can be copied, leak through backups or images, and must be rotated manually.
C=Hardcoded credentials: keys in source code end up in version control and every build artifact, which is one of the most common causes of credential leaks.
D=Root credentials: the root user has unrestricted access and cannot be limited by IAM policies, so a leak would compromise the whole account; it should never be used by applications.
T: On EC2, use an instance role for temporary credentials instead of any stored long-term keys.

@ Q000436 explain
G: ## Regions, Availability Zones and edge locations
- An **Availability Zone (AZ)** is one or more discrete data centers with independent power, cooling and networking. AZs in a Region are physically separated by a meaningful distance but connected with low-latency links, so synchronous replication (for example RDS Multi-AZ) is practical.
- A **Region** is a separate geographic area containing several AZs. Regions are far apart, so a disaster affecting a whole metropolitan area does not hit two Regions at once, but cross-Region latency is too high for chatty web-to-database traffic.
- **Edge locations** run CloudFront and Route 53; they cache and route but do not host your web servers or database.
## Putting it together
Run the web tier and database across several AZs of one Region to survive a data center failure with low latency. Then keep a disaster recovery copy (for example backups, a cross-Region read replica or Aurora Global Database) in a second Region for a regional disaster.
W: Multiple AZs in one Region plus a DR copy in another Region: Multi-AZ handles a data center power failure with low latency, and the second Region covers a disaster affecting the whole metro area.
X: A=Edge locations with a single-AZ database: edge locations do not run EC2 web servers, and a database in one AZ fails with that data center.
B=Two Regions with synchronous replication: the distance between Regions adds latency that makes synchronous replication and web-to-database calls slow; cross-Region copies are normally asynchronous.
D=One AZ across racks plus Local Zones: racks share the same data center, so a power failure takes them all down, and Local Zones are extensions tied to one parent Region's metro area, not a disaster recovery Region.
T: Multi-AZ gives high availability with low latency; a second Region gives disaster recovery for large-scale events.

@ Q000437 explain
G: ## SAML 2.0 federation to the console
Federation lets users from an external identity provider (IdP) use AWS without IAM users.
- You create an **IAM SAML identity provider** in the account by uploading the IdP's metadata (for example from on-premises **AD FS**).
- You create IAM roles whose trust policy trusts that provider, such as `arn:aws:iam::111122223333:role/ADFS-Admins`.
- The user signs in to AD FS with corporate credentials. AD FS sends a signed SAML assertion listing the roles the user may use (often based on AD group membership).
- The browser posts the assertion to the AWS sign-in endpoint, which calls the AWS STS `AssumeRoleWithSAML` API, and the user lands in the console with temporary credentials.
No AWS Directory Service is needed, because AD FS itself is the identity provider.
W: SAML 2.0 federation with AD FS and IAM roles: employees authenticate to AD FS and receive temporary role credentials for the console, with no directory deployed in AWS and no IAM users.
X: A=Direct Connect: it provides a private network link to AWS, but it has no role in authenticating users or mapping corporate identities to AWS permissions.
B=NAT gateway: a NAT gateway lets private subnet resources make outbound connections; it does not carry identity or grant console access.
D=IAM users with synced passwords: this creates and maintains separate IAM identities, so passwords can drift, leavers may keep access, and it is not using the existing corporate credentials.
T: An existing SAML IdP such as AD FS federates to IAM roles; networking services like Direct Connect or NAT do not provide identity.

@ Q000438 explain
G: ## Cross-account access needs both sides
When a principal in one account accesses a resource in another account, AWS requires permission from **both** accounts:
- **Account B** (the caller's account) must allow the action in the role's identity-based policy.
- **Account A** (the resource owner) must allow the principal through a resource-based policy, here the **S3 bucket policy**, for example `Principal: arn:aws:iam::222222222222:role/Reader`, `Action: s3:GetObject`, `Resource: arn:aws:s3:::bucket-a/*`.
If either side is missing, the request is denied.
## Why the encryption type matters
With **SSE-S3**, S3 manages the keys itself, so no KMS permission is involved. With **SSE-KMS**, the caller would additionally need `kms:Decrypt` through the KMS key policy. Here the objects use SSE-S3, so the bucket policy is the only missing piece.
W: Bucket policy in Account A granting the role access: the identity policy in Account B is only half of a cross-account grant; the bucket owner must also allow that role in a resource policy.
X: A=SCP in Account A that allows access: SCPs only limit the principals inside their own organization's accounts; they never grant access and do not act as a resource policy for callers from another account.
B=Permissions boundary listing GetObject: a boundary only caps what the role can do; the role's identity policy already allows the action, so the missing permission is on the bucket side.
D=KMS key policy: SSE-S3 uses S3-managed keys, not a customer KMS key, so there is no key policy to update.
T: Cross-account S3 access needs an allow in the caller's IAM policy and in the bucket policy; KMS permissions matter only for SSE-KMS.

@ Q000439 explain
G: ## Resource-based policies for cross-account sharing
An **S3 bucket policy** is a resource-based policy attached to the bucket. It can name principals from other AWS accounts, so the bucket owner can share data without creating any IAM users of its own.
## Example
In Account 111111111111, the bucket policy allows:
- `Principal: {"AWS": "arn:aws:iam::222222222222:root"}` (the whole account, which then delegates) or a specific role ARN in Account 222222222222
- `Action: s3:GetObject`
- `Resource: arn:aws:s3:::team-a-bucket/*`
Account 222222222222 then gives Team B's role or users an identity policy allowing `s3:GetObject` on that bucket. Both sides agree, so Team B can read objects using its own credentials, and Account A can revoke access at any time by editing the policy.
W: Bucket policy granting s3:GetObject to Account B's principal: it grants read-only cross-account access using Team B's own identities, with no IAM users in Account A.
X: B=Emailing the owner's access keys: sharing long-term keys gives Team B every permission the owner has, breaks accountability and leaves a secret in email.
C=Shared NAT gateway: a NAT gateway provides outbound network connectivity for private subnets; S3 authorization is decided by IAM and bucket policies, not by network paths.
D=Public read by prefix: public access exposes the objects to everyone on the internet, not just Team B, and S3 Block Public Access is designed to prevent exactly this.
T: Share S3 across accounts with a bucket policy naming the other account's principals, never with shared keys or public access.

@ Q000440 explain
G: ## Two different kinds of permission ceilings
Both SCPs and permissions boundaries limit permissions without granting any, but they apply at different scopes.
- **Service control policy (SCP)**: attached in AWS Organizations to the root, an OU or an account. It sets the maximum permissions for every IAM user and role in all affected member accounts. Ideal for organization-wide guardrails such as "no one may leave the organization" or "only approved Regions".
- **Permissions boundary**: a managed policy attached to one IAM user or role. The effective permissions are the intersection of its identity policy and the boundary.
## Example
A role has `AdministratorAccess` but a boundary allowing only `s3:*` and `dynamodb:*`. Even though its policy says everything, it can only use S3 and DynamoDB, and only within whatever the SCPs allow.
W: SCP organization-wide; permissions boundary for the role: the SCP caps every principal across all member accounts, and the boundary caps one specific role inside one account.
X: A=Boundary organization-wide and SCP for one role: a permissions boundary cannot be attached across an organization, and an SCP targets accounts or OUs, not a single IAM role.
B=Two boundaries on the Organizations root: permissions boundaries attach only to IAM users and roles, not to the organization root, OUs or accounts.
D=Two nested SCPs: SCPs attach to the root, OUs or accounts and act as account-wide guardrails, so nesting them at different OUs still caps whole accounts and does not provide the per-role cap inside one account that a permissions boundary gives.
T: SCPs are account-level guardrails for the whole organization; permissions boundaries are per-principal caps inside an account.

@ Q000441 explain
G: ## IAM condition keys for MFA
IAM policies can include a `Condition` block that checks request context. The key `aws:MultiFactorAuthPresent` is `true` when the caller's credentials were obtained with MFA.
## A common pattern
- Statement: `Effect: Deny`, `Action: s3:DeleteBucket`, `Resource: *`
- Condition: `BoolIfExists` with `aws:MultiFactorAuthPresent` equal to `false`
`BoolIfExists` matters because requests signed with long-term access keys do not include the key at all; with it, those requests are also denied. An explicit deny always wins over any allow, so users without MFA cannot delete buckets whatever else their policies grant.
When the user signs in to the console with MFA (or calls `sts:GetSessionToken` with an MFA code), the key is `true`, the deny does not match, and their normal allow applies.
W: Deny when aws:MultiFactorAuthPresent is false: a conditional explicit deny blocks bucket deletion for any request made without MFA and cannot be overridden by an allow.
X: A=SCP blocking S3: blocking the whole S3 service would stop every S3 action, not only deletion, and SCPs require the accounts to be in an organization; the MFA check itself is still done with the condition key.
B=Resource policy on IAM: there is no resource-based policy on IAM that governs S3 actions (the only IAM resource-based policy is a role's trust policy); MFA conditions on S3 actions go in identity policies, SCPs or the bucket policy.
C=Permissions boundary without DeleteBucket: that blocks deletion for everyone, always, even with MFA, which is not the requirement.
T: Require MFA for a sensitive action with an explicit Deny conditioned on aws:MultiFactorAuthPresent being false.

@ Q000442 explain
G: ## AWS STS and temporary credentials
**AWS Security Token Service (STS)** issues temporary security credentials: an access key ID, a secret key and a session token that expire (from minutes to hours).
- `AssumeRole`: an IAM principal or AWS service assumes a role. EC2 instance profiles use this under the hood, and the SDK refreshes the credentials automatically.
- `AssumeRoleWithWebIdentity`: exchanges an OpenID Connect token for role credentials. A CI system in another cloud (for example GitHub Actions or another provider's workload identity) can use its OIDC token this way, with no stored AWS keys.
- `AssumeRoleWithSAML`: for SAML federation.
Mobile apps typically use **Amazon Cognito identity pools**, which themselves obtain temporary credentials from STS for the signed-in or guest user.
W: AWS STS temporary credentials: every one of these clients ends up with short-lived STS credentials through AssumeRole or web-identity federation, so no long-term keys are stored.
X: B=KMS data keys: KMS data keys encrypt and decrypt data; they are not credentials and cannot authorize AWS API calls.
C=IAM access keys per session: IAM access keys are long-term credentials; creating and deleting them per session is fragile and still exposes long-term secrets.
D=Secrets Manager rotating a shared key: rotating a shared IAM user key still distributes a long-term secret to many clients and loses individual accountability.
T: Temporary AWS credentials come from STS; KMS, IAM access keys and Secrets Manager do not replace it.

A **landing zone** is a well-architected, multi-account starting point: an organization with separate accounts for logging, security and workloads, plus baseline controls.

@ Q000444 explain
G: ## Groups versus roles
- An **IAM group** is a collection of IAM users. Policies attached to the group apply to every member, which simplifies management (for example a `Developers` group). A group is not an identity: it cannot sign in, cannot be assumed and cannot be named as a principal in a policy.
- An **IAM role** is an identity with permissions but no long-term credentials. A trusted principal assumes it and receives temporary credentials from AWS STS. Trusted principals can be IAM users, AWS services such as EC2 or Lambda, users in other accounts, or federated users.
## Example
Users in the `Developers` group get read access to logs through the group policy. When they need to deploy to production, they assume the `ProdDeploy` role for one hour.
W: A group bundles users with shared policies; a role is assumed for temporary credentials: groups organize users, while roles are identities that anyone trusted can assume.
X: A=Identical except for naming: groups contain users and cannot be assumed, while roles are assumable identities with a trust policy, so they behave very differently.
B=Roles only for the root user: roles are assumed by IAM users, AWS services, other accounts and federated users; AWS actually discourages using the root user for such work.
D=EC2 assumes a group: it is the reverse; EC2 instances use roles through an instance profile, and groups can never be assumed.
T: Groups are for organizing IAM users; roles are assumable identities that hand out temporary credentials.

@ Q000445 explain
G: ## How AWS evaluates a request in an organization
For a principal in a member account, the request is allowed only if every applicable policy type allows it and nothing explicitly denies it:
- **SCPs** from AWS Organizations must allow the action (at every level from the root down to the account).
- The **identity-based policy** (and any permissions boundary or session policy) must allow it.
- A **resource-based policy** such as the bucket policy may add or deny access.
An **explicit Deny anywhere wins**. So an administrator in the management account can add an SCP to an OU, and suddenly users whose IAM policies did not change get Access Denied.
## Example
An SCP with `Effect: Deny`, `Action: s3:PutObject`, plus a condition requiring encryption headers or a specific Region, would block the upload even though the user's IAM policy allows `s3:PutObject`.
W: An SCP explicitly denies s3:PutObject: a newly applied or changed SCP can block an action account-wide without any change to the developer's own IAM policy.
X: A=Storage class does not support PutObject: every S3 storage class accepts uploads; storage class affects price and retrieval, not whether PutObject is allowed.
C=Expired console password: API calls are signed with access keys or temporary credentials, not the console password, so a password expiry does not cause Access Denied on uploads.
D=Different Availability Zone: S3 buckets are Regional resources, not placed in a single AZ, and location never produces an authorization error.
T: When IAM allows but the request is still denied in an organization, look for an explicit deny in an SCP (or a bucket policy).

@ Q000446 explain
G: ## Least privilege in practice
Least privilege means granting only the actions and resources a task needs.
- **Action**: the role only uploads, so `s3:PutObject` is enough instead of `s3:*` (which includes delete, policy and ACL changes).
- **Resource**: limit it to one prefix, for example `arn:aws:s3:::app-uploads/incoming/*`.
## Finding what is actually used
**IAM Access Analyzer** helps right-size permissions:
- It can generate a policy based on the role's activity recorded in CloudTrail, listing the actions and services actually used.
- Unused access findings show permissions a role has not used; IAM last-accessed information also shows which services were used and when.
- Policy validation checks a new policy for errors and overly broad statements.
W: Scope to PutObject on the prefix; verify with Access Analyzer: the role gets only the upload action on the one prefix, and Access Analyzer confirms from real activity that nothing else is needed.
X: A=Boundary allowing s3:* on all buckets: the effective permissions are the intersection, so a boundary that also allows everything restricts nothing.
B=Keep s3:* and rely on CloudTrail: CloudTrail only records what happened; it does not prevent a misused or compromised role from deleting data.
D=AmazonS3ReadOnlyAccess: it removes the upload permission the role actually needs and still grants read access to every bucket in the account.
T: Least privilege means narrowing both actions and resources, then using Access Analyzer to confirm the policy matches real usage.

@ Q000447 explain
G: ## Stateful security groups versus stateless NACLs
- A **security group** is stateful: if an inbound connection is allowed, the reply is allowed automatically, whatever the outbound rules say.
- A **network ACL** is stateless: it evaluates every packet in each direction on its own. Replies need their own rule.
## How a reply looks
A client connects from its own random source port, for example `203.0.113.10:51544`, to the server's port `443`. The server's reply therefore leaves from port `443` **to** destination port `51544`. The NACL outbound rule is checked against the destination port, so an outbound rule for port 443 does not match the reply.
The fix is an outbound NACL rule allowing TCP `1024-65535` (the ephemeral port range) to the clients' addresses.
W: The NACL must allow outbound ephemeral ports for replies: responses to clients go to their ephemeral ports, which the stateless NACL currently blocks, so clients time out.
X: A=Security group outbound rule: security groups are stateful, so responses to allowed inbound traffic are permitted without any outbound rule.
B=Inbound ephemeral NACL rule: the client's requests arrive on port 443, which is already allowed inbound; ephemeral ports are the destination of the outbound replies, not the inbound requests.
C=NACL rules ignored: both layers apply to every packet; traffic must pass the NACL at the subnet boundary and the security group at the instance.
T: NACLs are stateless, so a server needs an outbound NACL rule for ephemeral ports even though its security group handles replies automatically.

@ Q000448 explain
G: ## Public versus private subnets
- A **public subnet** has a route `0.0.0.0/0` to an **internet gateway**. Instances with a public IP there can be reached from the internet (if their security group allows it).
- A **private subnet** has no route to an internet gateway, so nothing on the internet can initiate a connection to its instances.
## NAT gateway for outbound-only access
A **NAT gateway** lives in a public subnet with an Elastic IP. The private subnet's route table sends `0.0.0.0/0` to the NAT gateway.
- Database servers can start outbound connections, for example to download updates, and the replies come back through the NAT gateway.
- Connections started from the internet cannot reach the servers, because they have only private IPs and the NAT gateway does not forward unsolicited inbound traffic.
W: Private subnet with outbound routing via a NAT gateway: servers can download updates, while having no public address or inbound path from the internet.
X: A=Public IPs with restricted ports: public addresses make the servers directly addressable from the internet; one misconfigured rule would expose the database.
B=Remove the security groups: every instance network interface must have a security group, and weakening firewalling does not create outbound access; it only increases exposure.
C=Public subnet with an internet gateway: that places the database on a routable path from the internet, which the requirement forbids.
T: Outbound-only internet for private resources = private subnet plus a route to a NAT gateway.

@ Q000449 explain
G: ## AWS Shield Standard versus Shield Advanced
- **Shield Standard** is automatically included for all customers at no extra cost. It protects against common network and transport layer (layer 3/4) DDoS attacks.
- **Shield Advanced** is a paid subscription that you enable on specific resources such as CloudFront distributions, ALBs, Elastic IPs, Global Accelerator and Route 53 hosted zones. It adds:

- **Cost protection**: service credits for scaling charges caused by a DDoS attack on protected resources.

W: AWS Shield Advanced on the distribution and ALB: it is the only option that provides 24/7 SRT help and credits for attack-related scaling costs.
X: B=WAF rate-based rules alone: rate-based rules can throttle some layer 7 floods, but WAF by itself gives no access to AWS DDoS experts and no cost protection.
C=GuardDuty with automated blocking: GuardDuty detects threats from logs; it is not a DDoS mitigation service and offers no response team or scaling credits.
D=Shield Standard: it is free and automatic but does not include the Shield Response Team or cost protection.
T: DDoS expert support and cost protection are Shield Advanced features; Shield Standard and WAF alone do not include them.

@ Q000450 explain
G: ## Amazon GuardDuty
**GuardDuty** is a managed threat detection service. Once enabled it analyzes AWS data sources without any agents or log pipelines for you to manage:
- **AWS CloudTrail** management events, for unusual API calls such as calls from known malicious IPs or disabling of logging.
- **VPC Flow Logs**, for example an instance talking to a known command-and-control server or doing port scans.
- **DNS query logs**, for example instances resolving domains used for crypto mining.
It uses threat intelligence and machine learning to produce findings such as `CryptoCurrency:EC2/BitcoinTool.B` or `UnauthorizedAccess:IAMUser/...`. Optional protection plans extend it to S3, EKS, RDS logins, Lambda, runtime monitoring and malware scanning. With AWS Organizations, a delegated administrator can enable it across all accounts.
W: Amazon GuardDuty: it continuously analyzes flow logs, DNS logs and CloudTrail events to detect compromised instances and suspicious API activity across accounts.
X: A=AWS Config: Config records resource configuration changes and evaluates compliance rules; it does not analyze network or DNS traffic for threats.
B=AWS Trusted Advisor: it checks accounts against best practices such as open security group ports, but it does not detect active malicious behavior.
C=Amazon Macie: Macie discovers sensitive data such as PII in S3 buckets; it does not analyze flow logs or API activity for threats.
T: Threat detection from CloudTrail, VPC Flow Logs and DNS logs is GuardDuty; Macie is for sensitive data and Config is for configuration compliance.

@ Q000451 explain
G: ## Amazon Macie
**Macie** is a data security service that uses machine learning and pattern matching to find sensitive data in Amazon S3.
- **Managed data identifiers** recognize many types of data such as passport numbers, credit card numbers, bank account numbers and credentials. You can add **custom data identifiers** with your own regular expressions.

G: ## What an instance needs to be reachable from the internet
For inbound HTTPS from the internet to reach an EC2 instance, every layer must allow it:
- A **public IP** or Elastic IP on the instance.
- A route `0.0.0.0/0` to an **internet gateway** in the subnet's route table.
- A **network ACL** allowing inbound TCP 443 and outbound ephemeral ports (the default NACL allows all traffic).
- A **security group** with an inbound rule for TCP `443`, for example from `0.0.0.0/0`.
- The application listening on port 443 and the OS firewall allowing it.
## Why the security group is the usual culprit
Security groups deny all inbound traffic by default. A new security group has no inbound rules, so even with the public IP and route in place, HTTPS connections are silently dropped and clients time out.
W: The security group lacks an inbound TCP 443 rule: with the public IP and route already correct, the default-deny inbound behavior of the security group is the most likely thing blocking HTTPS.
X: A=NAT gateways block inbound HTTPS: a NAT gateway is used only for outbound connections from private subnets; the instance here uses an internet gateway, so no NAT gateway is in the path.
C=VPC needs extra setup for HTTPS: a VPC carries any TCP traffic, including HTTPS, as long as routes, NACLs and security groups allow it.
D=Different Region from DNS records: clients can reach resources in any Region over the internet, and DNS records point to IP addresses, not Regions.
T: Public IP and internet gateway route are necessary but not sufficient; the security group must explicitly allow the inbound port.

G: ## Direct Connect versus Site-to-Site VPN
- **AWS Site-to-Site VPN** creates IPsec tunnels over the public internet. It can be set up in minutes and is encrypted, but throughput per tunnel is limited (a standard tunnel supports up to about 1.25 Gbps) and latency varies with internet conditions.
- **AWS Direct Connect** is a physical, private connection from your data center or colocation facility to AWS through a Direct Connect location. Traffic does not cross the public internet, so latency and throughput are consistent.
- Dedicated connections are available at speeds such as 1, 10, 100 and 400 Gbps; hosted connections from partners come in smaller increments.
- Setup can take weeks, because a cross-connect or partner circuit must be provisioned.
- Traffic is not encrypted by default; you can add MACsec on supported dedicated links or run a VPN over Direct Connect.
W: AWS Direct Connect: a dedicated private link gives the consistent low latency and high bandwidth the trading application needs, and the company accepts the longer lead time.
X: A=Amazon CloudFront: CloudFront caches content at edge locations for end users; it does not connect a data center to a VPC for trading traffic.
B=Transit Gateway alone: a transit gateway is a hub that interconnects VPCs and on-premises attachments, but it still needs a VPN or Direct Connect to reach the data center.
D=Site-to-Site VPN: it is fast to set up but runs over the internet, so it cannot guarantee consistent latency or match Direct Connect bandwidth.
T: Choose Direct Connect for consistent private performance and VPN for quick, encrypted internet-based connectivity or as a backup.

G: ## How a private subnet reaches the internet
Every subnet's route table has a `local` route for the VPC CIDR, so instances can talk inside the VPC. Traffic to other destinations follows the most specific other route; without one, it is dropped.
A NAT gateway only helps if traffic is sent to it:
- The NAT gateway sits in a **public subnet** whose route table sends `0.0.0.0/0` to the **internet gateway**.
- The **private subnet's** route table must send `0.0.0.0/0` to the NAT gateway (`nat-0abc...`).
## Traffic flow
Instance `10.0.2.15` sends a request to the internet, the private route table forwards it to the NAT gateway, which replaces the source with its Elastic IP and forwards it through the internet gateway. Replies return the same way.
W: Add 0.0.0.0/0 to the NAT gateway in the private subnet's route table: without that default route, the instances' internet-bound traffic never reaches the existing NAT gateway.
X: A=Default route to the internet gateway: instances without public IPs cannot use an internet gateway for internet access, and this would turn the subnet into a public subnet.
B=Route in the public subnet's table: routes apply to traffic leaving the subnet they belong to; the private subnet's traffic uses only its own route table.
D=Security group on the NAT gateway: NAT gateways do not use security groups; the problem is a missing route, not a firewall rule.
T: A NAT gateway works only when the private subnet's route table points 0.0.0.0/0 at it.
