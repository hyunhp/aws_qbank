G: ## Chargeback needs a label and a report
AWS bills every line item to an account, but a business unit's share of a shared service (a shared database, a shared EKS cluster) is invisible unless the resources carry a label you can group by.
- **Cost allocation tags** are resource tags such as `CostCenter=CC-1042`. Applying the tag is not enough: a user-defined tag must be **activated** in the Billing and Cost Management console of the management (payer) account before it appears as a dimension in billing data.
- The **Cost and Usage Report** (delivered to S3, today through Data Exports as CUR 2.0) lists every line item with its tag columns, so you can sum cost per `CostCenter` in Athena, QuickSight or a spreadsheet.
## Example
A shared logging cluster is tagged `CostCenter=Retail` and `CostCenter=Payments` on the respective nodes. After activation, a query grouping the CUR by that tag produces the monthly amount to charge each unit. Cost Categories and split cost allocation data can refine the split further.
W: A=Analyze the CUR by tag: the CUR is the most detailed billing dataset and carries the activated tag columns, so grouping by the tag yields the per-cost-center totals needed for chargeback.
E=Apply and activate cost allocation tags: tags identify which business unit owns each resource, and activation is what makes them usable in the CUR and Cost Explorer.
X: B=S3 Requester Pays: it only shifts request and data transfer charges of specific S3 buckets to the caller; storage and all other shared services stay with the owner, so it is not a chargeback model.
C=Trusted Advisor cost checks: these give savings recommendations such as idle resources, not a breakdown of who consumed which part of the bill.
D=Estimated charges dashboard: the CloudWatch `EstimatedCharges` metric shows totals by account or service, not by tag, so it cannot split a shared service among business units.
T: Chargeback = activated cost allocation tags plus a tag-grouped Cost and Usage Report; recommendation or alarm tools do not attribute cost.

@ Q000557 explain
G: ## AWS Budgets in one paragraph
AWS Budgets lets you set a spending (or usage, RI or Savings Plans) target and attach alerts that fire on thresholds.
- Each alert can compare against **actual** spend (what has already accrued this month) or **forecasted** spend (what AWS predicts the month will end at).
- Thresholds can be absolute amounts or percentages of the budget, for example "forecast > 100%" and "actual > 80%".
- Notifications go to email addresses and to an Amazon SNS topic. From SNS, or directly from Budgets, **Amazon Q Developer in chat applications** (formerly AWS Chatbot) can post the alert to a Slack channel.
## Example
Budget `monthly-total` = `$10,000`. Alert 1: forecasted > 100% to finance@example.com. Alert 2: actual > 80% to an SNS topic subscribed by the chat integration, so the Slack channel is told soon after accrued spend passes `$8,000` (Budgets refreshes cost data several times a day, not in real time). Budget actions can even apply an IAM policy or SCP automatically if needed.
W: AWS Budgets forecast and actual alerts: one budget holds both a forecast-based and an actual-based threshold and delivers them by email and SNS, which reaches Slack through the chat integration.
X: A=CUR to S3: the Cost and Usage Report is a raw billing data file for analysis; it has no thresholds and sends no notifications.
C=Cost Explorer saved reports: Cost Explorer visualizes and forecasts cost when someone opens it, but a saved report does not push an alert when a threshold is crossed.
D=Trusted Advisor cost checks: these flag optimization opportunities like idle load balancers; they do not track spend against a monthly target.
T: Proactive alerts on forecast or actual spend are what AWS Budgets is for; Cost Explorer and the CUR analyze, they do not alert.

@ Q000558 explain
G: ## Warm and cold storage in AWS Backup
A backup plan in AWS Backup has rules that define the schedule, the target vault, and a **lifecycle**:
- **Transition to cold storage** after N days moves recovery points to a much cheaper tier intended for long retention.
- **Expire** after N days deletes them automatically. A recovery point must stay in cold storage for at least 90 days, so the expiry must be at least 90 days after the transition.
Cold storage transition is available only for resource types that support it (for example EBS snapshots, EFS and DynamoDB with advanced features). Amazon RDS snapshots do not support it, so for RDS the lifecycle rule only enforces the expiry while the EBS recovery points get the cold-tier savings; check the feature availability table by resource type.
## Example
Rule: daily backup, transition to cold after 30 days, expire after 2,555 days (about 7 years). Recent restores come from warm storage; old compliance copies sit in cold storage at a fraction of the price. A Backup Vault Lock can also make the retention tamper-proof for compliance.
W: AWS Backup lifecycle rules to cold storage: the plan itself moves older recovery points to the low-cost tier and deletes them after 7 years, with no custom code and with retention enforced by the service.
X: B=Scripts copying to S3 Glacier: AWS Backup recovery points are not objects you can copy into a Glacier storage class yourself, and a homegrown script adds failure points and breaks the managed restore path.
C=Disable backups after 90 days: this deletes the data the company must keep for 7 years, so it violates the compliance requirement.
D=Warm storage indefinitely: it meets retention but pays warm-tier prices for years of rarely restored data, which is the cost the company wants to avoid.
T: Long compliance retention in AWS Backup = lifecycle rule to cold storage plus an expiry, not scripts and not warm storage forever.

@ Q000559 explain
G: ## How EBS SSD volumes get their performance
- **gp2** ties performance to size: 3 IOPS per GiB (with burst credits for small volumes). To get 6,000 IOPS you must buy 2,000 GiB, even if you only need 400 GiB.
- **gp3** decouples performance from size. Every volume gets a baseline of 3,000 IOPS and 125 MiB/s, and you pay separately to provision more IOPS and throughput, well beyond 6,000 IOPS and 250 MiB/s.
- **io1/io2** are Provisioned IOPS SSDs for the highest IOPS and most consistent latency (io2 Block Express also offers higher durability); the per-IOPS price is higher than gp3.
- **st1** is a throughput-optimized HDD for large sequential reads, rated in MB/s, with only a few hundred IOPS.
## Example
400 GiB gp3 with `Iops=6000` and `Throughput=250`: you pay for 400 GiB plus 3,000 extra IOPS and 125 extra MiB/s. The same IOPS on gp2 needs a 2 TiB volume; on io2 you pay the higher Provisioned IOPS rate for all 6,000.
W: gp3 with provisioned IOPS and throughput: it delivers exactly 6,000 IOPS and 250 MiB/s on a 400 GiB volume, paying only for the extra performance at gp3's low rates.
X: A=gp2 at 2 TiB: the IOPS target is met only by paying for five times the needed capacity, which costs more than a right-sized gp3 volume.
B=st1 HDD: an HDD designed for sequential throughput cannot sustain 6,000 random IOPS for a database.
C=io2 with 6,000 IOPS: it meets the requirement, but Provisioned IOPS pricing is higher than gp3, and its extra durability and latency consistency are not required here.
T: When the need is moderate IOPS and throughput on a small volume, provision them on gp3 instead of oversizing gp2 or paying io2 prices.

G: ## AWS services for moving file data
- **AWS DataSync** is an online transfer service. You deploy a DataSync agent (a VM) near the NFS or SMB server, create a task from that source to an S3 bucket, EFS or FSx, and run it on a schedule. It copies only changed data, verifies integrity, encrypts in transit, and handles retries and bandwidth limits for you.
- **Storage Gateway** exposes AWS storage to on-premises applications (file shares, volumes or virtual tapes); it is not a sync tool for an existing file server.
- **AWS Snowball** ships a physical device for offline bulk transfers where the network is too slow.
- **AWS Transfer Family** runs managed SFTP, FTPS, FTP and AS2 endpoints so partners can push or pull files to S3 or EFS.
## Example
A task `nfs://filer01/projects` to `s3://proj-archive/` scheduled hourly: each run scans the share, transfers only new or changed files, and reports results in CloudWatch, with no scripts to maintain.
W: AWS DataSync: it is purpose-built for recurring, incremental, verified transfers from on-premises NFS to S3, with built-in scheduling and monitoring.
X: A=Tape Gateway: it presents a virtual tape library to backup software over iSCSI; it does not read an existing NFS file server and sync its files to S3.
B=AWS Snowball: shipping a device suits a one-time or occasional bulk move, not continuous scheduled synchronization.
C=AWS Transfer Family: it provides protocol endpoints like SFTP that clients push files into; it does not pull from an NFS share on a schedule.
T: Scheduled online sync from NFS or SMB to AWS storage is DataSync; Snowball is offline, Transfer Family is SFTP endpoints, Tape Gateway is backup tapes.

@ Q000561 explain
G: ## What Cross-Region Replication costs
S3 Replication copies new objects from a source bucket to a destination bucket. With CRR you pay for:
- **Inter-Region data transfer** for every replicated GB (us-east-1 to eu-west-1 here), usually the largest part of the bill.
- Replication PUT requests and storage in the destination bucket (plus Replication Time Control if enabled).
Replication rules can be **filtered** by prefix, by object tags, or both. Only matching objects are replicated.
## Example
The bucket holds `critical/` (orders, customer records) and `tmp/` and `logs/` (large, easy to regenerate). A rule with `Filter: {Prefix: "critical/"}` replicates only the data DR actually needs, cutting transferred GB while keeping a second-Region copy of what matters. Tags such as `dr=true` work the same way across prefixes.
W: Replicate only the needed prefixes or tags: fewer bytes cross Regions, so transfer and request charges drop, while the DR copy in eu-west-1 still exists for the data that matters.
X: A=Same-Region Replication: keeping the copy in us-east-1 removes the inter-Region transfer charge but also removes protection against a Regional outage, which is the DR requirement.
C=Disable versioning: S3 Replication requires versioning on both buckets, so turning it off stops replication instead of making it cheaper.
D=Transfer Acceleration: it speeds client uploads and downloads through edge locations for an extra per-GB fee; it does not apply to replication traffic and would only add cost.
T: To cut CRR cost without losing DR, shrink what is replicated with prefix or tag filters; do not move the copy into the same Region.

@ Q000562 explain
G: ## How S3 Intelligent-Tiering works
Intelligent-Tiering watches each object's access and moves it between tiers automatically:
- **Frequent Access** for new or recently read objects.
- **Infrequent Access** after 30 days without access, and **Archive Instant Access** after 90 days, both still millisecond reads.
- Optional **Archive Access** and **Deep Archive Access** tiers you opt into; those require a restore before reading.
When an object in the automatic tiers is read, it moves back to Frequent Access, and there are **no retrieval fees**. The trade-off is a small monthly monitoring fee per object (objects under 128 KB are not monitored and stay in Frequent Access).
## Example
800 million 2 MB objects: each carries a tiny monitoring fee, which is small relative to the savings of moving cold 2 MB objects to cheaper tiers. An object that becomes hot again after months simply returns to Frequent Access with no penalty.
W: S3 Intelligent-Tiering: it is designed for unknown or changing access patterns, moves objects automatically in both directions, and charges no retrieval fees for its automatic tiers.
X: A=S3 Standard-IA: it charges a per-GB retrieval fee and never moves objects back when they get hot, so objects that become busy again cost more than in Standard.
B=Glacier Flexible Retrieval: reads require a restore that takes minutes to hours and can incur per-GB retrieval charges, which does not fit objects that can become hot again.
D=S3 One Zone-IA: it has the same retrieval fees and static placement as Standard-IA and also stores data in a single AZ, lowering resilience.
T: Unknown or shifting access with no retrieval fees points to Intelligent-Tiering; the IA classes and Glacier charge you for reading.

@ Q000563 explain
G: ## Spot Instances for interruptible work
Spot Instances use spare EC2 capacity at a steep discount (up to about 90% off On-Demand). EC2 can reclaim them with a two-minute interruption notice.
- Workloads that checkpoint, like transcoding or batch jobs, simply resume from the last checkpoint on a new instance.
- **Diversification** means allowing many instance types and sizes across several AZs. Each type in each AZ is a separate capacity pool, so more pools means more places to get capacity.
- The **price-capacity-optimized** allocation strategy (for EC2 Fleet, Spot Fleet and Auto Scaling groups) picks the pools that have the most available capacity and, among them, the lowest price, which lowers interruption rates.
## Example
An Auto Scaling group with a mixed instances policy lists `c6i.xlarge`, `c7i.xlarge`, `c6a.xlarge`, `m6i.xlarge` in three AZs, 100% Spot, price-capacity-optimized. If one pool is reclaimed, replacements come from another pool and jobs resume from checkpoints.
W: Diversified Spot, price-capacity-optimized: the work is interruptible and not urgent, so Spot gives the biggest discount, and diversified pools with this strategy keep interruptions low.
X: A=Standard RIs for peak: a 1- or 3-year commitment sized for peak is paid even when the queue is empty, and it is still more expensive than Spot for flexible work.
B=On-Demand, one type: it has no interruptions but pays full price for work that tolerates interruption and delay.
D=Dedicated Hosts for three years: dedicated physical servers are for licensing or compliance needs and are the most expensive way to buy capacity for a queue like this.
T: Checkpointed, deadline-tolerant work belongs on diversified Spot with price-capacity-optimized allocation, not on commitments or On-Demand.

G: ## Commitment discounts compared
- **Compute Savings Plans**: commit to a dollar amount per hour for 1 or 3 years. The discount applies automatically to EC2 in any instance family, size, AZ, Region, operating system or tenancy, and also to Fargate and Lambda.
- **EC2 Instance Savings Plans**: a larger discount, but locked to one instance family in one Region (size, OS and AZ can change).
- **Standard Reserved Instances**: fixed instance type attributes; Regional RIs can flex across sizes within one family for some platforms, but never across families.
- **Zonal Reserved Instances**: tied to a specific instance type in one AZ and also reserve capacity there.
In AWS Organizations, Savings Plans and RI discounts are shared across member accounts by default through consolidated billing.
## Example
A commitment of `$50/hour` covers today's `m5` fleet in one account, and when a team moves to `c7g` in another account and Region next year, the same plan keeps applying.
W: Compute Savings Plans: the discount follows usage across families, sizes, Regions and accounts, which fits a mixed fleet expected to change instance types over three years.
X: A=Zonal RIs: they are locked to one instance type in one AZ, so a move to another family or size loses the discount.
C=Standard RIs: they cannot be exchanged for another instance family, so shifting workloads can leave the reservation unused.
D=EC2 Instance Savings Plans: they allow size changes but are bound to a single instance family in one Region, so a family change drops out of coverage.
T: For maximum flexibility across family, size and Region, choose Compute Savings Plans; RIs and EC2 Instance Savings Plans trade flexibility for a deeper discount.

G: ## Rightsizing with AWS Compute Optimizer
Compute Optimizer uses machine learning on CloudWatch utilization metrics (by default the last 14 days, extendable with enhanced infrastructure metrics) to classify resources as under-provisioned, over-provisioned or optimized.
- For EC2 it proposes up to three alternative instance types with the projected utilization and the price difference, so you can see the risk of downsizing.
- It also covers Auto Scaling groups, EBS volumes, Lambda functions, ECS services on Fargate and RDS instances.
- Memory is not visible to EC2 by default; installing the CloudWatch agent adds memory metrics and makes recommendations more accurate.
## Example
An `m5.2xlarge` with CPU peaking at 12% is flagged over-provisioned, with a recommendation for `m5.large` (or a Graviton type) and the estimated monthly saving. It is opted in once at the organization level for all accounts.
W: AWS Compute Optimizer: it is the service built to analyze utilization history and produce specific, ranked instance-size recommendations for underused EC2 instances.
X: A=AWS Config: Config records resource configuration and evaluates compliance rules; it does not analyze CPU or memory usage or suggest instance sizes.
C=AWS Trusted Advisor: its low-utilization check flags idle-looking instances with a simple threshold but does not model and recommend a specific target instance type the way Compute Optimizer does.
D=CloudWatch Logs Insights: it queries log data you collect; building rightsizing logic on it would be a custom project, not automated recommendations.
T: Automated rightsizing recommendations come from Compute Optimizer; Config tracks configuration and Trusted Advisor gives broader, coarser checks.

G: ## What an Application Load Balancer can do at layer 7
An ALB reads HTTP requests, so one load balancer can front many services:
- **Listener rules** route by path (`/orders/*`), host header, headers or query strings to different target groups; an ALB supports many rules, enough for dozens of services.
- **TLS termination** with certificates from AWS Certificate Manager, including several certificates via SNI.
- **Authentication**: an `authenticate-oidc` (or `authenticate-cognito`) action redirects unauthenticated users to the identity provider and passes verified user claims to targets in headers.
## Example
`https://api.example.com/cart/*` goes to the cart target group, `/users/*` to the users target group, and every rule first runs the OIDC authenticate action. One ALB replaces 25 separate entry points, and you pay for one load balancer plus its capacity units.
W: One ALB with path rules and OIDC auth: a single ALB covers path routing, ACM TLS termination and OIDC authentication, which is both the functional fit and the lowest-cost design.
X: B=NLB per microservice: an NLB works at layer 4, so it cannot route by path or run OIDC authentication, and 25 load balancers multiply the hourly charges.
C=CLB per microservice: the Classic Load Balancer is a previous-generation service with no path-based routing or built-in authentication, and 25 of them also multiply cost.
D=Gateway Load Balancer: it distributes traffic to network appliances such as firewalls using GENEVE; it does not terminate TLS, route HTTP paths or authenticate users.
T: HTTP path routing plus login at the load balancer means one ALB with listener rules and an authenticate action.

G: ## Matching capacity to a known schedule
EC2 Auto Scaling groups keep a desired number of instances between a minimum and maximum. **Scheduled actions** change those values at set times using a cron expression and time zone.
- Scale in for nights and weekends so you stop paying for idle instances.
- Scale out before business hours so capacity is ready when users arrive, instead of reacting after load rises.
- Combine with a target tracking policy to absorb unexpected spikes, or use predictive scaling, which learns daily and weekly patterns.
## Example
`scale-up`: `0 7 * * MON-FRI` sets min 10, desired 10. `scale-down`: `0 20 * * MON-FRI` sets min 2, desired 2, and the weekend keeps 2. Instead of paying for 10 instances 168 hours a week, you pay for 10 for about 65 hours and 2 for the rest.
W: Auto Scaling with scheduled actions: capacity drops automatically during predictable quiet periods and returns before peak, so the company pays for peak capacity only when it is needed.
X: A=Single large instance: it must be sized for peak and runs 24/7, so it wastes money off-hours and is also a single point of failure.
B=RIs sized for peak: the reservation is billed every hour whether or not instances run, so the off-hours capacity is paid for anyway.
C=Peak On-Demand always: running peak capacity all the time is the most expensive option and ignores the predictable low-demand periods.
T: Predictable daily or weekly load is solved with scheduled (or predictive) Auto Scaling, not with capacity sized permanently for peak.

@ Q000568 explain
G: ## Stop versus hibernate
- **Stop**: the instance shuts down, RAM is lost, and on start the OS boots and applications reload from scratch.
- **Hibernate**: EC2 writes the contents of RAM to the EBS root volume, then stops. On start, RAM is restored and processes continue where they left off, with the same instance ID and private IP.
While stopped or hibernated you pay no instance-hour charges, only for EBS storage (and any Elastic IP addresses).
## Requirements
- Hibernation must be enabled at launch, on a supported instance type and AMI.
- The root volume must be an encrypted EBS volume large enough to hold the RAM contents.
- There are limits on RAM size and on how long an instance can stay hibernated.
## Example
A test server that takes 40 minutes to warm caches hibernates at 19:00 and resumes at 08:00 with its in-memory state intact in a couple of minutes.
W: EC2 hibernation: it preserves in-memory state across the overnight stop, so environments resume quickly, while instance charges stop during the night.
X: A=Dedicated Instances: this changes tenancy to single-customer hardware, adds cost, and does nothing to preserve memory between stops.
C=Auto Scaling termination policies: they decide which instance to terminate when scaling in; terminated instances lose all state.
D=Spot Fleet: it lowers the hourly price but Spot instances can be interrupted and a normal stop still loses RAM, so the startup delay remains.
T: To save cost overnight and still resume with RAM intact, hibernate instead of stop.

G: ## Where AWS infrastructure can run
- **AWS Outposts**: AWS-designed racks or servers installed in your own data center or factory, managed by AWS, running services such as EC2, EBS, ECS, EKS and RDS locally. You use the same APIs, console and tools, and pay through your AWS bill. Each Outpost connects back to a parent Region.
- **Local Zones**: AWS-operated locations in large metro areas that bring compute closer to users, but they are AWS facilities, not your site.
- **Wavelength Zones**: AWS compute inside telecom carriers' 5G networks for mobile-device latency.
- **Direct Connect**: a private network link to AWS; it adds no compute anywhere.
## Example
A factory places an Outposts rack next to its production line. Vision-inspection workloads run on local EC2 instances with single-digit millisecond latency to machines, the data stays on site, and the team manages it like any other subnet of its VPC.
W: AWS Outposts: it puts AWS-managed compute physically on the factory premises, meeting residency and latency needs while keeping AWS APIs, tooling and billing.
X: B=AWS Local Zones: compute runs in AWS metro facilities, so data leaves the factory and latency depends on the distance to that city.
C=AWS Wavelength: it targets mobile and 5G device traffic inside carrier networks, not workloads that must stay inside a customer's own facility.
D=AWS Direct Connect: a dedicated connection only improves the network path to a Region; the compute and the data still live in AWS.
T: AWS compute on your own premises is Outposts; Local Zones and Wavelength are AWS-run edge locations elsewhere.

G: ## ECS capacity providers
A capacity provider tells ECS where tasks run. Clusters can use `FARGATE`, `FARGATE_SPOT`, or Auto Scaling group providers for EC2 instances.
A **capacity provider strategy** splits tasks between providers with a **base** (tasks placed first on one provider) and **weights** (the ratio for the rest).
- **Fargate Spot** runs tasks on spare capacity at a large discount compared with regular Fargate. When AWS needs the capacity back, the task gets a two-minute warning (a `SIGTERM` and a task state change event) before it stops.
- Batch jobs that can retry or checkpoint handle this easily; the scheduler or service simply starts a new task.
## Example
Strategy: `FARGATE` base 1, weight 1; `FARGATE_SPOT` weight 4. One task always runs on regular Fargate, and 80% of the rest land on Fargate Spot, so most of the batch work runs at the Spot price.
W: Capacity provider strategy favoring Fargate Spot: the jobs tolerate interruptions, so running most tasks on discounted spare capacity gives the largest compute saving with no servers to manage.
X: A=On-Demand outside Auto Scaling: full-price instances that do not scale in keep costing money between batch runs.
C=Only Reserved Instances: a long-term commitment for bursty batch work means paying for reserved capacity that sits idle between jobs, and it gives less discount than Spot for interruptible work.
D=Fargate On-Demand for every task: it works but pays the full Fargate rate even though the jobs could run on Spot.
T: Interruptible ECS tasks should lean on Fargate Spot (or EC2 Spot) through a capacity provider strategy, not on full-price or reserved capacity.

G: ## Running code at CloudFront
CloudFront offers two ways to run your code near viewers:
- **CloudFront Functions**: lightweight JavaScript at edge locations, sub-millisecond, for viewer request and viewer response events. Ideal for URL rewrites, header changes, redirects or choosing which image variant to fetch. No network calls and no access to the body.
- **Lambda@Edge**: Node.js or Python functions that run at regional edge caches for viewer and origin events, with more memory, longer run time and network access. This suits heavier work such as generating a resized image.
Both are serverless and billed per request and execution, so there are no central servers to run.
## Example
A CloudFront Function normalizes `/img/cat.jpg?w=300` to `/img/300/cat.jpg` so the cache key is consistent. On a cache miss, a Lambda@Edge origin-response function creates the 300-pixel version and returns it; later requests are served from the cache.
W: Lambda@Edge or CloudFront Functions: code runs at CloudFront locations close to users, removing the central servers and lowering latency; Functions handle the light request logic and Lambda@Edge the actual resizing.
X: A=EC2 Auto Scaling: it scales servers inside one Region, so requests still travel to that Region and the company keeps managing dedicated instances.
B=AWS Batch: it schedules queued batch jobs in a Region; it does not execute per-request logic in the CloudFront path.
D=AWS Outposts: it places AWS hardware in the company's own facility, which neither reaches global end users nor reduces cost for this use case.
T: Per-request logic near users on a CloudFront site means CloudFront Functions or Lambda@Edge, not Regional compute.

G: ## Gateway Load Balancer
A Gateway Load Balancer (GWLB) inserts virtual appliances (firewalls, IDS/IPS, deep packet inspection) into the traffic path without changing source or destination addresses, a "bump in the wire".
- It works at layer 3 and forwards whole IP packets to the appliances using **GENEVE** encapsulation on port `6081`.
- It health-checks the appliances and keeps each flow on the same appliance (flow stickiness), so stateful firewalls work, and the fleet can scale out behind one endpoint.
- **GWLB endpoints** (powered by PrivateLink) are placed in route tables, for example as the next hop for traffic from the internet gateway, so traffic from many VPCs can be sent to a central inspection VPC.
## Example
Ingress route table on the internet gateway: `10.0.1.0/24` to `gwlbe-0abc`. Every packet to the web subnet passes through the firewall fleet and then continues to its original destination.
W: Gateway Load Balancer: it is built for transparent, scalable insertion of third-party network appliances, with one load balancer serving a whole appliance fleet and many VPCs.
X: A=Application Load Balancer: it terminates HTTP connections and routes requests to targets, so it is not transparent and cannot inspect non-HTTP traffic in-line.
B=Classic Load Balancer: a previous-generation proxy for HTTP or TCP that terminates connections; it has no mechanism to pass packets through appliances unchanged.
D=Network Load Balancer: it balances TCP, UDP and TLS connections to targets as the destination; it cannot be used as a transparent next hop that sends traffic on to its original destination.
T: Inline, transparent appliance inspection is Gateway Load Balancer with GENEVE and GWLB endpoints; ALB and NLB are destinations, not bumps in the wire.

@ Q000573 explain
G: ## DynamoDB capacity modes
- **On-demand**: you pay per read and write request, with no capacity to plan. The table adapts to traffic automatically, accommodating sudden jumps up to double its previous peak instantly and scaling further as traffic grows, and costs nothing for requests when idle (storage is still billed). You can optionally set a maximum throughput to cap spend.
- **Provisioned**: you set read and write capacity units per second and pay for them every hour, used or not. Auto scaling adjusts them based on utilization, but it reacts over minutes, and a high minimum is billed all the time.
- **Reserved capacity**: a 1- or 3-year commitment on provisioned capacity for steady, predictable workloads.
## Example
A new app sees 50 requests per second most of the day and 20,000 during a marketing push. On-demand simply bills the requests; provisioned would either be sized for 20,000 units all day or risk throttling while auto scaling catches up.
W: On-demand capacity mode: it absorbs unpredictable spikes without capacity planning and charges only for requests actually made, so idle periods are cheap.
X: B=Provisioned with a high fixed minimum: the minimum capacity is billed every hour even when the app is idle, and auto scaling may still lag a sudden spike.
C=Reserved Capacity: it is a long-term discount on provisioned throughput and only pays off for steady, predictable usage, the opposite of this workload.
D=Provisioned with no auto scaling: fixed capacity either sits idle and wasted or throttles requests once a spike exceeds it.
T: Unknown, spiky DynamoDB traffic fits on-demand; provisioned and reserved capacity reward steady, predictable load.

G: ## Why DynamoDB fits high-rate key-value data
Amazon DynamoDB is a serverless key-value and document database. Data is spread across partitions by the partition key, and the service adds partitions as traffic and storage grow.
- Single-item reads and writes by key return in single-digit milliseconds at almost any scale; very high request rates are handled by spreading requests across many keys (and account and table quotas can be raised).
- There are no instances, replicas or patching to manage, and you pay per request (on-demand) or per provisioned capacity.
- **TTL** can expire old sessions automatically at no extra cost.
## Example
Table `Sessions` with partition key `sessionId`, attributes `userId`, `cart`, `expiresAt` (TTL). Each page view is one `GetItem` or `PutItem` on a distinct key, so load spreads evenly across partitions.
W: Amazon DynamoDB: simple key-value access at hundreds of thousands of requests per second is its core design, with no servers to operate and cost that follows usage.
X: B=Amazon Redshift: a columnar data warehouse built for analytical queries over large datasets, not for many small low-latency lookups and writes per second.
C=RDS for PostgreSQL, large Multi-AZ: a single writer instance must be sized and paid for peak, and relational features add overhead that simple sessions do not need.
D=RDS for MySQL with read replicas: replicas help reads only; all session writes still hit one primary, and every replica is another instance to pay for.
T: Massive-scale simple key-value traffic belongs in DynamoDB; relational engines and data warehouses scale and cost poorly for it.

G: ## Tiering old relational data
Relational database storage (RDS) is priced for fast, always-on access. Data that is rarely read but must be kept can live much more cheaply in **Amazon S3**.
- Export old rows (for example with an RDS snapshot export, which writes Apache Parquet to S3, or with AWS Glue or DMS).
- Partition the files by date, for example `s3://tx-archive/year=2019/month=03/`.
- **Amazon Athena** queries the files with standard SQL on demand, billed by data scanned. Columnar Parquet and partitions keep scans, and cost, small.
- S3 Lifecycle and Object Lock can move the files to cheaper classes and enforce the 10-year retention.
## Example
Rows older than 2 years are exported each month and deleted from RDS. An auditor runs `SELECT * FROM tx_archive WHERE year = 2019 AND account_id = '123'` in Athena and gets results in seconds, while the RDS instance stays small.
W: Archive old rows to S3 and query with Athena: rarely read history moves to low-cost durable storage, stays queryable with SQL whenever needed, and the database shrinks.
X: A=Delete old rows: it breaks the regulatory requirement to keep 10 years of transactions queryable.
B=Grow RDS storage for all 10 years: it keeps paying database storage prices, and larger backups, for data that is almost never read.
D=Larger instance class: it adds compute cost and does nothing about the storage growth driving the bill.
T: Keep hot data in the database and move cold, must-keep data to S3 queried with Athena.

G: ## Aurora Serverless v2
Aurora Serverless v2 is a capacity mode of Amazon Aurora (MySQL- or PostgreSQL-compatible). Instead of choosing an instance class, you set a minimum and maximum capacity in **Aurora Capacity Units (ACUs)**; each ACU is roughly 2 GiB of memory with matching CPU and networking.
- Capacity adjusts in fine-grained steps within seconds as load changes, without dropping connections.
- On supported engine versions the minimum can be set to 0 ACUs, so a database with no connections automatically pauses and incurs no compute charges until the next connection resumes it (storage is still billed). Otherwise the minimum is 0.5 ACU.
- It supports Aurora features such as Multi-AZ readers and Global Database, and can be mixed with provisioned instances in one cluster.
## Example
Min `0`, max `16` ACUs: business hours run around 4 to 8 ACUs, and when nights and weekends have no connections for the configured idle period the instance pauses at 0 ACUs (resuming takes a few seconds on the next connection). Capacity is billed per second for the ACUs actually used.
W: Aurora Serverless v2: a relational database whose capacity scales up for business hours and down to near zero when idle, so the company pays mostly for what it uses.
X: A=Fixed-size RDS Multi-AZ: the instance and its standby are billed every hour at full size, including the idle nights and weekends.
B=DynamoDB provisioned: it is not a relational database, and provisioned capacity is billed whether or not it is used.
D=Redshift with Concurrency Scaling: Redshift is an analytics warehouse, and Concurrency Scaling adds temporary capacity for query bursts; it does not provide a scale-to-zero transactional database.
T: Variable or intermittent relational workloads fit Aurora Serverless v2; fixed instances bill for idle time.

G: ## Leaving a commercial database engine
Oracle and SQL Server license fees are often the largest part of a database's cost. Amazon Aurora is MySQL- and PostgreSQL-compatible and has no license fees.
- **AWS SCT (Schema Conversion Tool)** or **DMS Schema Conversion** converts the schema and database code (tables, views, stored procedures, functions) to the target dialect and reports what needs manual fixes.
- **AWS Database Migration Service (DMS)** copies the data with a full load and then keeps the target in sync with change data capture (CDC), so cutover downtime is short.
- For SQL Server applications, **Babelfish for Aurora PostgreSQL** can accept T-SQL, further reducing code changes.
## Example
Oracle on RDS to Aurora PostgreSQL: SCT converts the PL/SQL packages, DMS runs full load plus CDC for a week of testing, then the application switches its connection string during a short maintenance window.
W: Migrate to Aurora with DMS and SCT: the move removes commercial license fees, and AWS-managed schema conversion and data replication keep code changes and downtime low.
X: A=Rebuild on DynamoDB: a full rewrite to a NoSQL data model is the opposite of minimal code change and carries large cost and risk.
B=Smaller RDS instance: license fees still apply, and shrinking the instance can hurt performance without addressing the main cost.
C=Manual export with custom scripts: it is not AWS-managed, does not convert stored procedures, and requires long downtime or custom sync logic.
T: Cut license costs by moving to Aurora with SCT for schema and code and DMS for data, not by rewriting or resizing.

G: ## RDS storage types
- **General Purpose SSD (gp3)**: for MySQL, MariaDB and PostgreSQL, volumes under 400 GiB get a fixed 3,000 IOPS and 125 MiB/s; at 400 GiB and above the included baseline rises to 12,000 IOPS and 500 MiB/s, and you can provision more at a low per-IOPS price (Oracle's threshold is 200 GiB; SQL Server lets you provision roughly 3,000 to 16,000 IOPS at any size). Latency is good but less consistent than Provisioned IOPS.
- **Provisioned IOPS SSD (io1, io2 Block Express)**: highest and most consistent performance with sub-millisecond latency for io2, at a higher price per IOPS. Nothing requires production databases to use it.
- **Magnetic**: a legacy previous-generation type kept for backward compatibility, with low performance and no support for thousands of sustained IOPS.
## Example
A 500 GiB PostgreSQL database on gp3 already has a 12,000 IOPS baseline included in the storage price, which covers the steady 8,000 IOPS. Buying 8,000 IOPS on io1 or io2 adds a per-IOPS charge for latency consistency the team said it does not need.
W: gp3 with 8,000 provisioned IOPS: gp3 meets the steady IOPS need at the lowest price per IOPS, and the workload explicitly tolerates occasional latency variation.
X: A=io1 because production requires it: there is no such rule; io1 costs more per IOPS and its benefit, consistent latency, is not required here.
B=io2 Block Express for lowest latency: it buys the lowest, most consistent latency, which the workload does not need, at a higher cost than gp3.
C=Magnetic storage: it is a legacy type that cannot deliver 8,000 steady IOPS and is not recommended for new databases.
T: When cost matters and latency variation is acceptable, provision IOPS on gp3; pay for io1 or io2 only when consistent low latency is required.

G: ## Scan versus Query in DynamoDB
- **Scan** reads every item in the table (1 MB per page) and only then applies a `FilterExpression`. You are charged read capacity for everything read, not for what matches, so a frequent Scan on a large table is very expensive and slow.
- **Query** reads only items with a given partition key (optionally narrowed by sort key), so you pay only for matching items.
- A **global secondary index (GSI)** is a copy of selected attributes with a different partition key. It lets you Query by an attribute that is not the table's key. It adds some write and storage cost, because each table write also updates the index.
## Example
Orders table keyed by `orderId`; the app scans for `status = "PENDING"`. A GSI with partition key `status` (or better, a higher-cardinality key such as `status#date`) lets the app call `Query` on the index and read only pending orders.
W: Add a GSI and use Query instead of Scan: reads drop from the whole table to just the matching items, which cuts consumed read capacity and cost directly.
X: A=On-demand and keep the Scan: on-demand still bills every item read by the Scan, so the inefficient access pattern keeps driving cost.
B=DAX write-through caching: DAX adds a paid cluster and only helps repeated identical reads; each cache miss still scans the table, and the design problem remains.
C=More provisioned write capacity: the cost comes from reads by the Scan, so adding write capacity only increases the bill.
T: Expensive Scans are fixed by a better access pattern, a GSI plus Query, not by changing capacity mode or adding caches.

G: ## What a NAT gateway costs
A NAT gateway lets instances in private subnets start outbound IPv4 connections to the internet. It is charged per hour per gateway and per GB processed.
- One gateway per AZ is the high-availability design: each AZ keeps outbound access if another AZ fails, and traffic stays within the AZ.
- With a single gateway, subnets in other AZs send traffic across AZs, which adds a per-GB cross-AZ charge and makes that AZ a single point of failure.
## Gateway endpoints
**Gateway VPC endpoints** for Amazon S3 and DynamoDB are free. You add them to route tables and S3 or DynamoDB traffic goes directly to the service, bypassing the NAT gateway entirely, so no NAT processing and no cross-AZ trip for that traffic.
## Example
Three NAT gateways become one in AZ-a. The largest outbound flows (S3 backups, DynamoDB calls) now use gateway endpoints, so only a small amount of internet traffic crosses AZs to the single NAT gateway.
W: One NAT gateway plus S3/DynamoDB gateway endpoints: it removes two gateways' hourly charges, accepted because non-production can tolerate an AZ failure, and the free endpoints keep the heaviest traffic off the NAT path and off cross-AZ links.
X: A=Second NAT gateway per AZ: it doubles the hourly cost and adds redundancy that the non-production environment explicitly does not need.
C=Egress-only internet gateway: it only provides outbound access for IPv6; IPv4 instances in private subnets still need NAT.
D=Route private subnets to the internet gateway: instances without public IP addresses cannot use an internet gateway, and giving them public IPs would make the subnets public and expose the instances.
T: For low-cost non-production egress, use one NAT gateway and move S3 and DynamoDB traffic to free gateway endpoints.
