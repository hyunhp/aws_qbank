@ Q003219 explain
G: ## Finding savings versus watching activity
AWS has separate tools for cost, security and compliance. Only some of them tell you where money is being wasted.
- **AWS Cost Explorer** charts past spending by service, account, tag or usage type, forecasts future spend, and shows Savings Plans and Reserved Instance purchase recommendations and rightsizing suggestions for EC2.
- **AWS Compute Optimizer** analyzes CloudWatch utilization metrics for EC2 instances, Auto Scaling groups, EBS volumes, Lambda functions, ECS services on Fargate and some RDS databases, then recommends smaller or different resource types.
## A small example
Cost Explorer shows that EC2 spend in `us-east-1` doubled last quarter. Compute Optimizer then shows that many `m5.2xlarge` instances average under 10% CPU and that `m5.large` would fit. Together they answer "where is the money going" and "what should change".
W: D=AWS Cost Explorer: it visualizes and forecasts spending and surfaces Savings Plans, Reserved Instance and rightsizing recommendations, which directly point to savings.
E=AWS Compute Optimizer: it uses real utilization data to recommend right-sized or cheaper resource configurations, a direct source of cost reductions.
X: A=AWS CloudTrail Lake: it stores and queries API activity events with SQL for auditing and investigations; it records who did what, not how much it cost or how to spend less.
B=AWS Artifact: it is a portal for downloading AWS compliance reports (such as SOC and ISO) and accepting agreements; it has no view of your usage or spend.
C=Amazon Inspector: it scans EC2, container images and Lambda functions for software vulnerabilities and network exposure; its findings are about security risk, not cost.
T: Cost Explorer shows where money goes and Compute Optimizer shows what to resize; audit and security tools such as CloudTrail Lake and Inspector do not find savings.

@ Q003220 explain
G: ## Serverless SQL on S3
**Amazon Athena** runs SQL directly against files in Amazon S3. There is no cluster to start or keep running; for SQL queries you pay per terabyte of data scanned (with a small minimum per query).
## Why file format matters
Because the bill follows bytes scanned, the layout of the data drives cost:
- **Columnar formats** such as Parquet or ORC let Athena read only the columns a query uses.
- **Compression** shrinks the bytes that are read.
- **Partitioning** (for example `s3://logs/year=2026/month=09/`) lets a query with `WHERE year=2026 AND month=9` skip every other folder.
Example: a query that needs 2 columns out of 40 for one month out of three years might scan a tiny fraction of what the same query scans on raw CSV, and cost that much less.
W: Amazon Athena on compressed, partitioned Parquet data: Athena has no idle cost and bills per data scanned, and columnar, compressed, partitioned data minimizes what each occasional query scans.
X: A=RDS instance loaded every morning: the database instance bills every hour whether or not anyone queries it, and the daily load job adds work and cost for data that could be queried in place.
B=Provisioned Redshift cluster running continuously: a provisioned cluster bills per node-hour around the clock, which is wasteful for occasional queries; it suits steady, heavy warehouse workloads.
D=EMR cluster running 24/7: the EC2 instances behind the cluster bill continuously even when no ad hoc query runs, and the team must manage the cluster as well.
T: For occasional SQL on S3, pay per query with Athena and cut scanned bytes with Parquet, compression and partitions; always-on clusters charge for idle time.

@ Q003221 explain
G: ## Where ECS on EC2 wastes money
With the EC2 launch type, you pay for container instances whether tasks fill them or not. Low utilization means you are paying for idle CPU and memory.
## Two ways to fix it
- **AWS Fargate**: each task gets exactly the vCPU and memory you request and you pay only for that, with no instances to patch or scale.
- **Capacity providers with bin-packing**: an Auto Scaling group capacity provider with managed scaling adds and removes instances based on task demand. The `binpack` placement strategy (on CPU or memory) places tasks on as few instances as possible, so empty instances can be removed.
Example: 20 small tasks spread across 10 instances at 15% each could be packed onto 3 instances, and the other 7 are terminated by managed scaling.
W: Fargate or right-sizing with bin-packing capacity providers: Fargate removes idle instance capacity and instance management, while bin-packing plus managed scaling raises utilization so fewer, better-sized instances run.
X: A=Dedicated Hosts for all container instances: Dedicated Hosts reserve a whole physical server and are priced for licensing or compliance needs; they raise cost and do nothing about low utilization.
C=More EC2 instances for headroom: adding instances to an already underused cluster increases the idle capacity you pay for.
D=Each container on its own large instance: one container per large instance guarantees very low utilization and multiplies the number of instances to manage.
T: Low ECS utilization is fixed by paying per task (Fargate) or packing tasks densely with capacity providers, never by adding or dedicating more hosts.

@ Q003222 explain
G: ## Bridging on-premises apps to cloud storage
**AWS Storage Gateway** is a hybrid service that runs on premises as a virtual machine (or in some deployments on EC2) and presents standard storage protocols to local applications while storing the data in AWS.
- **S3 File Gateway**: NFS or SMB file shares whose files are stored as objects in Amazon S3.
- **Volume Gateway**: iSCSI block volumes backed by S3, with EBS snapshots; cached mode keeps frequently used data locally.
- **Tape Gateway**: a virtual tape library for existing backup software, with tapes stored in S3 and archived to S3 Glacier storage classes.
Each type keeps a local cache so recent data is read at LAN speed. Because the gateway can be a VM on existing hypervisors, little new hardware is needed.
Example: backup software writes to a Tape Gateway exactly as it did to physical tapes, but the tapes land in S3.
W: AWS Storage Gateway: it gives on-premises applications file, volume or tape interfaces backed by AWS storage, with a local cache, and runs as a VM so on-premises hardware stays minimal.
X: B=AWS Direct Connect: it is a dedicated private network link to AWS; it can carry backup traffic but provides no storage interface or caching.
C=Amazon FSx for Lustre: it is a high-performance file system for compute workloads in AWS such as HPC and ML; it is not a backup gateway with an on-premises cache.
D=Amazon EBS snapshots: they back up EBS volumes attached to EC2 instances in AWS; on-premises applications cannot write to them directly.
T: When on-premises apps need cloud-backed storage with a local cache, use Storage Gateway; Direct Connect is only the network path.

@ Q003224 explain
G: ## Temporary access with IAM roles
An **IAM role** has permissions but no long-term password or access keys. A trusted principal calls `sts:AssumeRole` and receives temporary credentials that expire automatically, from 15 minutes up to the role's maximum session duration (up to 12 hours).
How it fits a contractor:
- The role's **trust policy** names who may assume it, for example the contractor's own AWS account or a federated identity.
- The role's **permissions policy** allows only the actions needed on `arn:aws:s3:::project-bucket` and `arn:aws:s3:::project-bucket/*`.
- When the two weeks end, delete the role or remove the trust; there are no keys left behind to revoke.
A `DateLessThan` condition on `aws:CurrentTime` in the permissions policy can also make access stop on a specific date.
W: IAM role with scoped policy and limited session duration: the contractor gets short-lived credentials restricted to one bucket, and access ends by removing the role, with no long-term keys created.
X: B=Public read and write bucket policy: it opens the bucket to everyone on the internet, not just the contractor, and allows anyone to change or delete data.
C=Sharing the administrator's credentials: it gives full account access, breaks accountability because actions look like the admin's, and relies on long-term credentials.
D=IAM user with access keys: access keys are long-term credentials, exactly what the requirement excludes, and relying on a promise to delete them provides no enforcement.
T: Temporary, scoped access means an assumable IAM role with STS credentials; IAM users with access keys are long-term by design.

@ Q003225 explain
G: ## Capping what delegated admins can grant
A **permissions boundary** is a managed policy attached to an IAM user or role that sets the maximum permissions that entity can ever have. Effective permissions are the intersection of the identity policy and the boundary.
## Using it for safe delegation
Developers can be allowed to create roles only if they attach a specific boundary:
- Their policy allows `iam:CreateRole` with a condition that `iam:PermissionsBoundary` equals the approved boundary ARN.
- Even if a developer attaches `AdministratorAccess` to the new role, the role can do only what the boundary allows.
- They are also denied permission to change or remove the boundary.
Example: the boundary allows only `s3:*` and `dynamodb:*` on project resources, so no role a developer creates can touch IAM or billing.
W: IAM permissions boundaries: a boundary sets the ceiling on permissions for the roles developers create, so whatever policies they attach, effective access cannot exceed it.
X: A=Security group references: they allow network traffic from members of another security group; they control packets, not IAM permissions.
B=S3 bucket ACLs: they are a legacy way to grant access to a bucket or object; they cannot limit what IAM roles in general can do.
C=AWS Budgets with alert actions: budgets watch spending and can apply actions when costs exceed a threshold; they do not define a maximum set of IAM permissions.
T: To limit what delegated role creators can grant, require a permissions boundary; network and storage controls do not cap IAM permissions.

@ Q003226 explain
G: ## The IAM credential report
The **IAM credential report** is a CSV file you generate for the whole account (console or `aws iam generate-credential-report` then `get-credential-report`). It lists every IAM user and the root user with the status of their credentials, including:
- `password_enabled`, `password_last_used`, `password_last_changed`, `password_next_rotation`
- `mfa_active`
- `access_key_1_active`, `access_key_1_last_rotated`, `access_key_1_last_used_date` (and the same for key 2)
A new report can be generated at most every four hours.
Example: filtering for rows where a key is active but `access_key_1_last_used_date` is `N/A` or more than 90 days old finds unused keys in seconds.
W: The IAM credential report: one account-wide file shows each user's access key status and last use along with password last-changed dates, which is exactly what the auditor asked for.
X: A=CloudFront usage report: it summarizes requests and data transfer for CloudFront distributions; it has no information about IAM users or credentials.
C=S3 inventory report: it lists objects in a bucket with metadata such as size, storage class and encryption status, not IAM credentials.
D=Cost and Usage Report: it details billing line items by service and resource; it does not show key usage or password age.
T: Questions about IAM users' keys, passwords and MFA across the account are answered by the credential report, not by service usage or billing reports.

@ Q003227 explain
G: ## Two policies must agree across accounts
Within one account, an allow in either an identity policy or a resource policy is usually enough. For **cross-account** access both sides must allow the request:
- The caller's **identity policy** in account A must allow `s3:GetObject` (or `s3:*`) on the bucket.
- The **bucket policy** in account B, which owns the bucket, must grant that principal, for example `"Principal": {"AWS": "arn:aws:iam::111122223333:user/alice"}`.
If only account A allows it, account B's side has no allow and the request is implicitly denied.
Other causes to keep in mind: an explicit deny, a KMS key policy that does not allow the caller when objects use SSE-KMS, or object ownership settings on older uploads.
W: The bucket policy does not grant the user access: cross-account S3 access needs an allow from the owning account's bucket policy in addition to the user's own `s3:*` identity policy.
X: A=MFA for console only: MFA is not mentioned as a policy condition; if a condition required MFA, the fix would be in policy, and nothing indicates MFA is the cause.
B=Region not named in the policy: S3 bucket ARNs do not contain a Region, and an `s3:*` allow on the bucket applies wherever the bucket is.
D=Expired password: a console password does not affect API calls signed with access keys, and an expired password blocks sign-in rather than returning Access Denied on one bucket.
T: Cross-account access needs both the caller's identity policy and the owner's resource policy to allow it; an allow on one side alone is not enough.

@ Q003228 explain
G: ## Chaining security groups between tiers
A **security group** is a stateful firewall on each network interface. It has only allow rules, and a rule's source can be another security group instead of a CIDR.
A three-tier chain:
- `sg-web`: allows 443 from `0.0.0.0/0` (or from the load balancer's group).
- `sg-app`: allows 8080 only from `sg-web`.
- `sg-db`: allows 3306 only from `sg-app`.
Any instance with `sg-web` can reach the app tier, no matter its IP, and nothing else can. Because responses are stateful, return traffic needs no extra rules. Placing the app and database tiers in private subnets adds another layer.
W: Separate security groups per tier: each tier accepts traffic only from the group of the tier in front of it, which enforces exactly web to app to database and nothing else.
X: A=Public subnets with groups open to 0.0.0.0/0: every tier, including the database, becomes reachable from the internet, the opposite of the requirement.
B=NACLs allowing the whole VPC CIDR: any subnet in the VPC could reach the database directly, so the tiers are not isolated from each other.
C=One shared group allowing all inbound: a single permissive group lets any source reach any tier and cannot express per-tier rules.
T: Tier isolation comes from one security group per tier with rules that reference the previous tier's group, not from broad CIDR or shared rules.

@ Q003229 explain
G: ## Security groups versus network ACLs
- **Security groups** attach to network interfaces, are stateful, and support **allow rules only**. Anything not allowed is dropped, but you cannot write "deny this IP".
- **Network ACLs** attach to subnets, are stateless, and support both **allow and deny** rules. Rules are evaluated in order by rule number, lowest first, and the first match wins.
To block specific addresses, add deny rules with low numbers before the broad allow rules:
- Rule 50: deny all traffic from `203.0.113.0/24`
- Rule 100: allow TCP 443 from `0.0.0.0/0`
Applying these to the NACL of each public subnet blocks the addresses for every instance in those subnets at once. A NACL has a limited number of rules, so very large or changing lists are better handled by AWS WAF or AWS Network Firewall.
W: Network ACL deny rules on the public subnets: NACLs support explicit deny rules at the subnet boundary, so the malicious IPs are blocked for all resources in those subnets quickly.
X: B=Security group deny rule: security groups have no deny rules at all, which the question itself points out.
C=IAM policy denying the IPs: IAM policies control authorized API actions by principals; an `aws:SourceIp` condition affects signed AWS API calls, not network packets reaching instances.
D=Route 53 record to a blackhole: DNS controls how names resolve for clients; attackers can still send traffic directly to the IP addresses.
T: To explicitly block IP addresses at the subnet level use network ACL deny rules; security groups can only allow.

@ Q003230 explain
G: ## Controlling egress by domain name
Security groups and NACLs filter by IP, port and protocol. Many internet destinations sit behind changing IP addresses, so domain-based egress control needs a firewall that reads the traffic.
**AWS Network Firewall** is a managed, stateful firewall deployed in a VPC with firewall endpoints in dedicated subnets. Route tables send traffic through those endpoints.
- A **domain list rule group** can allow or deny domains such as `.amazonaws.com` or `updates.example.com`.
- For HTTPS it matches the TLS SNI, and for HTTP the Host header.
- A default action drops anything not on the allow list.
Example: private subnets route `0.0.0.0/0` to the firewall endpoint, the firewall allows only approved domains, then forwards to a NAT gateway and the internet gateway.
W: AWS Network Firewall with domain allow lists: it inspects outbound traffic statefully and allows only approved domain names, dropping everything else.
X: A=Amazon GuardDuty: it analyzes logs to detect threats and produces findings, but it does not sit in the traffic path and cannot block or filter connections.
C=Security groups with outbound IP rules: they filter only by IP and port and cannot match domain names, and service IP addresses change often.
D=Internet gateway with a route table only: routing sends traffic to the internet but performs no inspection or filtering of destinations.
T: Domain-based egress filtering needs an inline firewall such as Network Firewall; security groups work on IPs and GuardDuty only detects.

@ Q003231 explain
G: ## Why overlapping CIDRs break routing
If two VPCs both use `10.0.0.0/16`, an address like `10.0.1.5` exists in both. Any design that routes between the networks cannot tell which VPC a packet belongs to.
- **VPC peering** cannot be created between VPCs with overlapping CIDR blocks.
- A **transit gateway** route table can send a given CIDR to only one attachment, so one of the two VPCs becomes unreachable for that range.
## PrivateLink avoids routing entirely
With **AWS PrivateLink**, the provider puts the service behind a Network Load Balancer and creates an **endpoint service**. The consumer creates an **interface VPC endpoint**, which is a network interface with an IP from the consumer's own subnets. Applications connect to that local IP and AWS delivers traffic to the service, so the two address ranges never need to be routed to each other.
W: AWS PrivateLink with an endpoint service: the consumer reaches the service through a local endpoint IP, and no routes between the VPCs are needed, so overlapping CIDRs do not matter.
X: A=Transit gateway with one route table: a single route table can point `10.0.0.0/16` to only one attachment, so traffic to the overlapping range cannot reach both VPCs correctly.
B=VPC peering: AWS does not allow a peering connection between VPCs whose CIDR blocks overlap.
C=Public internet with IP allow lists: it exposes an internal service publicly and sends private traffic over the internet, which conflicts with keeping the service internal.
T: When VPC CIDRs overlap, expose the single service with PrivateLink; peering and transit gateway routing need unique address ranges.

**Amazon GuardDuty** is a threat detection service you turn on per account and Region, or across an organization with a delegated administrator. It reads its foundational data sources directly from AWS, without you enabling or storing the logs yourself:

X: A=AWS Artifact: it provides AWS compliance reports and agreements for download; it does not analyze any of your logs.

D=AWS Firewall Manager: it centrally deploys and enforces firewall policies such as WAF, security group and Network Firewall rules across accounts; it does not perform threat detection.
T: Continuous threat detection from CloudTrail, flow logs and DNS logs is GuardDuty; Inspector finds vulnerabilities and Firewall Manager applies rules.

G: ## Storing and rotating database credentials
**AWS Secrets Manager** stores secrets such as database passwords, encrypted with AWS KMS, and controls access to them with IAM.
- Applications call `GetSecretValue` at runtime instead of keeping passwords in code or configuration files.

@ Q003234 explain
G: ## KMS versus CloudHSM
Both services protect keys with hardware security modules (HSMs), but who controls the HSM differs.
- **AWS KMS**: a managed, multi-tenant service. AWS operates the HSMs and your keys never leave them unencrypted, but you do not get dedicated hardware.
- **AWS CloudHSM**: you get **single-tenant** HSM instances in a cluster in your VPC. You create and manage the HSM users and keys, and AWS cannot access your key material. The HSMs are validated under FIPS 140 at Level 3.
Applications use CloudHSM through standard interfaces such as PKCS#11, JCE or OpenSSL. KMS can also use a CloudHSM cluster as a **custom key store** when you want KMS integrations with keys held in your own HSMs.
W: AWS CloudHSM: it provides dedicated, single-tenant HSMs that the customer controls exclusively, meeting regulatory requirements for customer-controlled hardware.
X: A=AWS KMS keys: standard KMS keys are stored in AWS-managed, shared HSMs, so the customer does not control single-tenant hardware.
B=AWS Secrets Manager: it stores secrets such as passwords and encrypts them with KMS; it is not a hardware key store under customer control.
D=Amazon Macie: it discovers and classifies sensitive data such as PII in S3 buckets; it does not store or manage keys.
T: Single-tenant, customer-controlled HSMs mean CloudHSM; standard KMS is managed and multi-tenant.

@ Q003235 explain
G: ## EBS encryption by default
**EBS encryption by default** is an account setting that you turn on **per Region**. After it is enabled:
- Every new EBS volume created in that Region is encrypted, whether from the console, CLI, CloudFormation or an Auto Scaling launch.
- New volumes restored from unencrypted snapshots are encrypted too, and copies of snapshots are encrypted.
- It uses the AWS managed key `aws/ebs` unless you choose a customer managed KMS key as the default.
It does not change existing volumes. To encrypt an existing unencrypted volume, snapshot it, copy the snapshot with encryption, and create a new volume. Instance types that do not support EBS encryption cannot launch while the setting is on.
Example: enable it in `us-east-1` and `eu-west-1` with a customer managed key, and every new volume there is encrypted automatically.
W: Enable EBS encryption by default in each Region: once set, every new volume in that Region is encrypted automatically without relying on anyone to choose it.
X: B=Ask engineers to select encryption: it depends on people remembering every time, so it is not automatic and one missed choice leaves an unencrypted volume.
C=Instance store volumes: instance store is temporary storage tied to the instance's host; it does not replace EBS for persistent data and does not meet the requirement for EBS volumes.
D=Encrypt existing snapshots only: it affects old data at best and does nothing for new volumes created later.
T: Automatic encryption of all new EBS volumes is a per-Region account setting; manual choices and after-the-fact fixes are not automatic.

@ Q003236 explain
G: ## Locking a bucket to a VPC endpoint
A **gateway VPC endpoint** (or interface endpoint) for S3 lets instances reach S3 privately. Each request through it carries the endpoint ID, which S3 exposes as the condition key `aws:SourceVpce`.
A bucket policy can deny everything that did not arrive through that endpoint:
- `"Effect": "Deny"`, `"Principal": "*"`, `"Action": "s3:*"`
- `"Condition": {"StringNotEquals": {"aws:SourceVpce": "vpce-0abc1234"}}`
Because an explicit deny overrides any allow, even users with broad IAM permissions cannot access the bucket from the internet or another VPC. Use care: the same deny also blocks console access from outside the VPC, so admins often add an exception.
W: Bucket policy denying requests where `aws:SourceVpce` is not the endpoint: the resource policy applies to every caller and rejects any request that did not come through the specified endpoint.
X: A=NACL denying S3 IPs: NACLs filter traffic in one subnet only; they cannot stop access to the bucket from any other network, and S3 uses many changing IP ranges.
B=IAM user policy denying outside-the-office access: it applies only to users it is attached to, and an office IP condition says nothing about the VPC endpoint.
D=Security group on the bucket: S3 buckets are not in a VPC and cannot have security groups attached.
T: To force all S3 access through one endpoint, deny in the bucket policy when `aws:SourceVpce` does not match; network controls and user policies do not cover every caller.

@ Q003237 explain
G: ## S3 Block Public Access
**S3 Block Public Access** is a set of four settings you can turn on for the account or for each bucket:
- `BlockPublicAcls`: rejects requests that add public ACLs.

D=Transfer Acceleration: it speeds up long-distance uploads and downloads through edge locations; it does not affect access control.
T: To stop objects from becoming public through ACLs or policies, use S3 Block Public Access; storage classes and transfer features do not control access.

@ Q003238 explain
G: ## The principle of least privilege
**Least privilege** means each identity gets only the permissions it needs for its tasks, and no more.
- Start from the specific actions and resources a job needs, for example `s3:GetObject` on `arn:aws:s3:::reports/*` instead of `s3:*` on `*`.
- Tighten over time: IAM Access Analyzer can generate policies from CloudTrail activity and report unused access, and last-accessed information shows services a role never uses.
- Use individual identities and temporary credentials so each action is traceable to a person.
Example: a reporting job that only reads one bucket gets a role with read access to that bucket; unused permissions found in a quarterly review are removed.
W: D=Grant only required permissions: scoping each permission to the task is the definition of least privilege.
E=Review and remove unused permissions: regular pruning keeps permissions from growing beyond what is needed as roles and tasks change.
X: A=Share one IAM user among the team: shared credentials give everyone the union of all needed permissions and remove individual accountability.
B=Use the root user for daily tasks: the root user has unrestricted access to the account and should be reserved for the few tasks that require it.
C=AdministratorAccess for all developers: full access by default is the opposite of granting only what each task needs.
T: Least privilege means granting just what each task needs and pruning what goes unused; shared, root and admin-by-default access all violate it.

@ Q003239 explain
G: ## Protecting a web app at the edge
AWS edge locations sit close to users around the world. Stopping bad traffic there keeps it away from your origin.
- **Amazon CloudFront** is a content delivery network. It terminates connections at edge locations, caches content, and includes AWS Shield Standard, which absorbs common network and transport layer DDoS attacks. The origin can be restricted so it accepts traffic only from CloudFront.
- **AWS WAF** is a web application firewall attached to CloudFront (or to an ALB, API Gateway and others). Its web ACL rules block SQL injection, cross-site scripting, bad bots and known malicious IPs, and **rate-based rules** limit request floods.
Example: a web ACL with AWS managed rule groups and a rate-based rule of 2,000 requests per 5 minutes per IP, attached to the CloudFront distribution.
W: D=Amazon CloudFront: it serves and absorbs traffic at edge locations with Shield Standard included, shielding the origin from direct attack.
E=AWS WAF: attached to CloudFront, it filters malicious HTTP requests at the edge before they reach the application.
X: A=Amazon EBS: it is block storage for EC2 instances and has no role in filtering or absorbing web traffic.
B=Amazon RDS: it is a managed relational database behind the application, not an edge protection layer.
C=AWS Batch: it schedules and runs batch computing jobs; it does not handle or protect incoming web requests.
T: Edge protection for a public web app is CloudFront plus WAF; storage, databases and batch services sit behind the edge.

@ Q003240 explain
G: ## At rest versus in transit
- **Encryption at rest** protects stored data. S3 encrypts objects when writing them to disk and decrypts them when you read them.
- **Encryption in transit** protects data moving over the network, for example with TLS (HTTPS).
S3 server-side encryption options:
- **SSE-S3**: keys managed entirely by S3 with AES-256. All new objects get at least this by default.
- **SSE-KMS**: keys in AWS KMS, either the AWS managed key `aws/s3` or a customer managed key, giving key policies, CloudTrail logging of key use and separation of duties.
- **DSSE-KMS**: two layers of encryption with KMS keys, and **SSE-C** with keys supplied by the customer.
Example: a bucket default encryption of SSE-KMS with a customer managed key and S3 Bucket Keys to reduce KMS request costs.
W: A=SSE-S3: S3 encrypts each object at rest with keys it manages, with no extra configuration needed.
E=SSE-KMS: S3 encrypts objects at rest using KMS keys, adding control and auditing of key usage.
X: B=VPC endpoints for S3: they keep traffic to S3 on a private path, which affects network routing, not how stored objects are encrypted.
C=Transfer Acceleration: it speeds up transfers through edge locations and does not change storage encryption.
D=TLS on client connections: TLS encrypts data in transit between client and S3; once stored, the object's at-rest protection comes from server-side or client-side encryption.
T: At-rest S3 encryption comes from SSE options such as SSE-S3 and SSE-KMS; TLS, endpoints and acceleration are about the network path.

G: ## One place for security findings
**AWS Security Hub** gives a central, normalized view of security posture across accounts and Regions.
- It collects findings from AWS services such as GuardDuty, Inspector, Macie, IAM Access Analyzer and Firewall Manager, plus supported partner tools, in a common normalized format.
- It runs automated **security standards** checks, such as AWS Foundational Security Best Practices and CIS AWS Foundations Benchmark, using AWS Config rules and gives compliance scores (this posture-check capability is now branded AWS Security Hub CSPM).
- With AWS Organizations, a delegated administrator account sees findings from all member accounts, and cross-Region aggregation can gather them in one Region.
Example: a security team opens one dashboard to see failed checks like "S3 bucket allows public read" across 50 accounts.
W: AWS Security Hub: it aggregates security findings and runs compliance checks against standards, across all accounts in the organization, in one view.
X: A=AWS Cost Explorer: it analyzes and forecasts spending; it has no security findings or compliance checks.
C=AWS DataSync: it moves data between on-premises storage and AWS storage services; it does not assess security.
D=Amazon CloudFront: it is a content delivery network for serving content; it does not aggregate findings.
T: A central view of security findings and compliance checks across accounts is Security Hub; the detectors feed it, and cost or data tools do not.

G: ## Zero trust access without a VPN
**AWS Verified Access** lets users reach private applications in a VPC over the internet without a VPN, checking every request.
- A **Verified Access endpoint** fronts the application, for example an internal ALB or network interface.
- **Trust providers** supply identity (IAM Identity Center or an OIDC provider) and optionally device posture (such as supported device management tools).
- **Policies** written in the Cedar language decide per request, for example allowing only users in the `finance` group with a compliant device.
Because each request is evaluated against current identity and device context, changes in group membership or device status are reflected without reconfiguring network access, and access logs record the decisions.
W: AWS Verified Access: it provides VPN-less access to private applications and evaluates identity and device context on every request.
X: A=AWS Direct Connect: it is a dedicated private network link from a data center to AWS; it does not authenticate individual users or work for remote employees without that link.
B=AWS Global Accelerator: it improves availability and performance with static anycast IPs and the AWS backbone; it does not perform identity-based access checks.
D=Amazon Route 53: it is a DNS service that resolves names; it cannot authorize individual users or requests.
T: Per-request, identity-aware access to private apps without a VPN is Verified Access; networking and DNS services only move or resolve traffic.

G: ## Recording configuration history
**AWS Config** continuously records the configuration of supported resources, such as security groups, and keeps a history of every change.
- Each change creates a **configuration item** with the before and after state, the time, and relationships to other resources such as the instances using the group.
- The history is delivered to an S3 bucket and can be viewed as a timeline for each resource.
- **Config rules** can evaluate compliance, for example flagging a security group that allows `0.0.0.0/0` on port 22.
Config shows what the configuration was and when it changed; CloudTrail complements it by showing who made the API call.
Example: an auditor opens a security group's timeline and sees that port 3389 was opened on 12 March and closed two days later.
W: AWS Config: it records every configuration change to security groups as configuration items with history, which provides the audit record required.
X: A=AWS Glue: it is a data integration service for ETL jobs and a data catalog; it does not track resource configuration.
C=Amazon Polly: it converts text to speech and has no connection to auditing resources.
D=Amazon SQS: it is a message queuing service for decoupling applications; it keeps no history of resource settings.
T: A history of resource configuration changes for audits comes from AWS Config, with CloudTrail adding who made the call.
