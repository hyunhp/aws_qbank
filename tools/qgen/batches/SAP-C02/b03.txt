# SAP-C02 batch 03: Domain 1 (organizational complexity)
@ SAP-C02 D1 T1.1 advanced use-case
S: A company has 60 VPCs across three Regions and 25 accounts, plus two data centers. It needs centrally managed, segmented routing between production and development networks. Which solution fits?
A: AWS Cloud WAN with a core network policy defining production and development segments
B: A full mesh of VPC peering connections between all 60 VPCs in every Region
C: Site-to-Site VPN tunnels from each VPC directly to both on-premises data centers
D: Internet gateways in every VPC with security groups restricting cross-VPC traffic
K: A
W: Cloud WAN manages global networks centrally with policy-defined segments across Regions and on-premises locations.
X: B=A 60-VPC mesh is unmanageable and non-transitive. | C=Per-VPC VPNs do not scale or segment centrally. | D=Routing over the internet is insecure and unsegmented.
T: Global, segmented multi-Region networking → Cloud WAN.
V: AWS Cloud WAN

@ SAP-C02 D1 T1.1 applied use-case
S: Workloads in many VPCs need to resolve DNS names hosted in on-premises DNS, and on-premises systems must resolve private AWS names. Which solution centralizes this?
A: Route 53 Resolver inbound and outbound endpoints in a shared services VPC with rules shared through RAM
B: Custom DNS servers on EC2 in every VPC that forward all queries to the internet
C: Public hosted zones that duplicate every private record so that on-premises and cloud systems can all resolve them
D: Hard-coded IP addresses in application configuration files instead of DNS names
K: A
W: Centralized Resolver endpoints with forwarding rules shared via RAM provide hybrid DNS across many VPCs.
X: B=Per-VPC DNS servers add management overhead and forward to the wrong place. | C=Public zones expose internal records. | D=Hard-coded IPs are fragile.
T: Centralize hybrid DNS with Resolver endpoints and shared rules.
V: Amazon Route 53 Resolver, AWS RAM

@ SAP-C02 D1 T1.1 advanced use-case
S: A company needs 10 Gbps of private, consistent connectivity from on-premises to multiple VPCs in several Regions and accounts. Which design fits?
A: Direct Connect with a Direct Connect gateway associated with transit gateways in each Region
B: One Site-to-Site VPN connection per VPC, each running over the public internet from the on-premises data center
C: VPC peering between the on-premises network and each VPC using public IP addresses
D: A single Direct Connect private VIF attached directly to one VPC in one Region only
K: A
W: A Direct Connect gateway connects DX to transit gateways across Regions and accounts, reaching many VPCs.
X: B=Many VPNs over the internet lack consistency. | C=Peering does not connect on-premises networks. | D=A single VIF to one VPC does not reach the others.
T: DX to many VPCs across Regions → DX gateway plus transit gateways.
V: AWS Direct Connect, AWS Transit Gateway

@ SAP-C02 D1 T1.1 applied use-case

A: VPC sharing with AWS Resource Access Manager
B: VPC peering between every application account
C: A separate VPC per application with NAT each
D: Public subnets exposed to all accounts globally
K: A

X: B=Peering still requires many VPCs. | C=Separate VPCs increase sprawl and cost. | D=Public exposure is insecure.

@ SAP-C02 D1 T1.3 advanced use-case
S: A company's shared services VPC hosts Active Directory and monitoring used by 40 accounts. An outage there would affect all workloads. Which design improves resilience?
A: Deploy shared services across multiple AZs, with redundant connectivity through the transit gateway
B: Place all shared services in a single AZ close to the most important workload
C: Copy the shared services into each of the 40 accounts and have each account team manage its copy separately
D: Remove the shared services and let each team choose its own tools independently
K: A
W: Multi-AZ deployment and redundant transit connectivity remove single points of failure for shared services.
X: B=Single-AZ placement is a single point of failure. | C=Duplicating everywhere increases cost and drift. | D=Removing shared services fragments operations.
T: Make shared services multi-AZ and redundantly connected.

@ SAP-C02 D1 T1.1 advanced tradeoff
S: Two business units have overlapping VPC CIDR ranges and need one service in each to communicate privately. Re-addressing is not possible soon. Which option fits?
A: Expose the service with AWS PrivateLink (endpoint service) to the other VPC
B: Create a VPC peering connection between the overlapping VPCs
C: Attach both VPCs to a transit gateway that uses a single shared route table
D: Route traffic between them over the internet with public IPs
K: A
W: PrivateLink connects consumers to a specific service without routing between VPCs, so overlapping CIDRs are fine.
X: B=Peering does not work with overlapping CIDRs. | C=Overlapping routes conflict on the transit gateway. | D=Public internet routing is insecure.
T: Overlapping CIDRs → PrivateLink for service access.
V: AWS PrivateLink

A: NAT gateways in each AZ of the egress VPC, with transit gateway attachments in multiple AZs
B: One NAT gateway in a single AZ of the egress VPC shared by all AZ routes
C: A single NAT instance with a large instance type and enhanced networking in one Availability Zone
D: Internet gateways attached directly to every spoke VPC's private subnets
K: A
W: Per-AZ NAT gateways and multi-AZ attachments avoid a single-AZ dependency for centralized egress.
X: B=A single-AZ NAT gateway fails with its AZ. | C=A single NAT instance is a single point of failure. | D=Attaching IGWs to private subnets breaks the centralized design and exposes subnets.
