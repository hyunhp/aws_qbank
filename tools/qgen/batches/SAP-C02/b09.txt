# SAP-C02 batch 09: security and governance reinforcement (T1.2, T1.4, T2.3, T3.2)

@ SAP-C02 D1 T1.2 advanced use-case
S: A company runs 120 accounts in one AWS Organization. Application teams own their S3 buckets and KMS keys and regularly write bucket and key policies that grant access to partner accounts. A recent review found a bucket policy that allowed an AWS account outside the organization to read customer exports. Security wants a preventive control that guarantees only principals from inside the organization (plus AWS service principals acting on the company's behalf) can ever use S3 buckets and KMS keys in member accounts, no matter what a team writes in a resource policy. Which solution meets this requirement?
A: Attach an RCP at the organization root that denies S3 and KMS actions when aws:PrincipalOrgID does not match, excepting AWS service principals
B: Attach a service control policy at the organization root that denies s3:PutBucketPolicy and kms:PutKeyPolicy unless the caller is a central security role
C: Enable S3 Block Public Access and IAM Access Analyzer external access findings for the organization, and auto-remove any bucket policy that produces a finding
D: Deploy an AWS Config conformance pack that flags resource policies naming external accounts and triggers an SSM Automation runbook to overwrite the policy
K: A
G: ## Two kinds of organization policy
- **Service control policies (SCPs)** set the maximum permissions of the principals (users and roles) in member accounts. They never apply to a principal from another account.
- **Resource control policies (RCPs)** set the maximum permissions available on resources in member accounts. They apply to every principal that calls the resource, including principals from outside the organization. RCPs launched for S3, STS, KMS, SQS and Secrets Manager, and AWS has added more supported services since, so check the current list before relying on one.
Like SCPs, an RCP never grants access; it is a guardrail evaluated in addition to the resource policy and identity policy. The default `RCPFullAWSAccess` policy must stay attached unless you replace it.
## The data perimeter pattern
A typical RCP statement denies the resource actions when `aws:PrincipalOrgID` is not your organization ID, using `StringNotEqualsIfExists` and a `BoolIfExists` check on `aws:PrincipalIsAWSService` so that AWS services calling on your behalf keep working.
W: Resource control policy: it is evaluated on the resource side for every caller, so even if a team writes a bucket or key policy naming an outside account, the RCP deny wins. It is preventive, centrally owned, and needs no per-account setup.
X: B=SCP on policy-editing actions: it only restricts principals inside the organization and relies on a manual review of every change. It does not stop a legitimately allowed principal from writing a bad policy through an approved path, and it cannot limit who is granted access.
C=Block Public Access and Access Analyzer: Block Public Access covers public policies and ACLs, not grants to a specific outside account. Access Analyzer detects external access after the fact, so the bad policy is live until remediation runs.
D=Config conformance pack with remediation: it is detective and reactive. The outside account can read data between the policy change and the overwrite, which fails a guarantee that access can never happen.
T: To bound who may touch your resources, use RCPs (resource side, all callers); SCPs bound only your own principals. Detective tools such as Access Analyzer and Config do not give a guarantee.
V: AWS Organizations, Amazon S3, AWS KMS

@ SAP-C02 D1 T1.2 advanced tradeoff
S: A financial company runs analytics workloads in private subnets of many VPCs. Workloads reach Amazon S3 through gateway endpoints. An internal audit shows that a compromised workload could copy sensitive objects to an S3 bucket in an attacker's personal AWS account, because the network path allows any S3 destination. The company must block this exfiltration path at the network layer while keeping access to its own organization's buckets working. Which approach is the most effective?
A: Add a bucket policy to every bucket in the organization that denies any request whose aws:SourceVpc is not one of the company's approved VPC IDs
B: Attach an SCP that denies s3:PutObject unless aws:PrincipalOrgID equals the organization ID, so that only roles from company accounts can upload data
C: Replace the gateway endpoints with a NAT gateway and use security group egress rules limited to the S3 IP ranges published for the Region
D: Attach a gateway endpoint policy allowing S3 actions only where aws:ResourceOrgID equals the organization ID, plus statements for needed AWS-owned buckets
K: D
G: ## Where each perimeter control acts
A data perimeter combines three ideas: trusted identities, trusted resources and expected networks. The exfiltration risk here is about the destination resource, so the control must evaluate which bucket the request targets.
- A **VPC endpoint policy** is a resource policy on the endpoint. It is evaluated for every request through that endpoint, and it can use `aws:ResourceOrgID` to say "only resources owned by accounts in my organization".
- Bucket policies live on the destination bucket, which the attacker controls in a personal account, so they cannot protect against writes to it.
Endpoint policies also block access to AWS-owned buckets (for example those used for package repositories or agents) unless you add explicit allow statements for them.
W: Gateway endpoint policy with aws:ResourceOrgID: requests to any bucket outside the organization are denied at the endpoint, while the company's own buckets keep working. Explicit exceptions cover the few AWS-owned buckets that are still required.
X: A=Bucket policies with aws:SourceVpc: these protect the company's buckets from outside networks, which is a different threat. They cannot be attached to the attacker's bucket, so the copy to the personal account is untouched.
B=SCP on the principal organization: the compromised workload is a legitimate company role, so aws:PrincipalOrgID matches and the upload is allowed. The condition checks who is calling, not which bucket receives the data.
C=NAT gateway with security groups: S3 IP ranges include every S3 bucket in the Region, including the attacker's, so IP filtering cannot distinguish destinations. It also adds data processing cost and removes the private path.
T: Use endpoint policies with aws:ResourceOrgID to stop data leaving to outside buckets; use aws:PrincipalOrgID and RCPs to control who can enter your own resources.
V: Amazon S3, AWS PrivateLink, AWS Organizations

@ SAP-C02 D1 T1.2 advanced troubleshooting
S: A company uses IAM Identity Center with an external identity provider for 40 accounts. A platform engineer created a permission set named PlatformDeploy that attaches a customer managed policy named DeployBoundaryPolicy, and assigned it to a group for 15 accounts. Provisioning the permission set succeeds in 9 accounts but fails in the other 6, where the roles are not created. The AWS managed policies and inline policy in the permission set are valid. What is the most likely cause and fix?
A: The 6 accounts sit under an SCP that denies iam:CreateRole, which blocks Identity Center from creating the roles; move them to another OU and reprovision
B: The policy is referenced by name and path and must exist in every target account; create it with the same name and path in the 6 accounts and reprovision
C: Identity Center copies customer managed policies to accounts, so the policy exceeded the size limit; shorten it and reprovision
D: The 6 accounts are missing an IAM identity provider for the external IdP; create a SAML provider in each account and reprovision
K: B
G: ## How permission sets become IAM roles
An IAM Identity Center permission set is a template. When it is assigned to an account, Identity Center creates a role named `AWSReservedSSO_<permission set>_<id>` in that account and attaches the policies the permission set lists.
- **AWS managed policies and inline policies** live in Identity Center itself and are copied into the account.
- **Customer managed policies and permissions boundaries** are stored only as a reference: a name and an optional path. Identity Center looks the policy up in the target account when it provisions.
If no policy with that name and path exists in the account, provisioning of the role fails for that account, while accounts that have the policy succeed.
W: Missing customer managed policy in the failing accounts: the permission set holds only a reference to the name and path, so the same policy must be deployed to every target account first. A StackSet or the account baseline is the usual way to keep it consistent.
X: A=SCP blocking role creation: Identity Center creates the roles by using a service-linked role in each account, and SCPs do not restrict service-linked roles. The stem also points to the customer managed policy as the only difference the permission set depends on per account.
C=Central storage of the policy: this is the reverse of how it works, since customer managed policies are not stored in Identity Center at all. Size limits would also affect all accounts equally, not just 6.
D=SAML provider per account: Identity Center federates through its own service and creates the roles with a trust to it. Member accounts do not need an IAM SAML provider for the external IdP.
T: Permission sets that use customer managed policies or permission boundaries depend on same-named policies existing in every target account; deploy them with StackSets or the baseline before assigning.
V: AWS IAM Identity Center, AWS CloudFormation, AWS IAM

@ SAP-C02 D1 T1.2 advanced use-case
S: A company has 90 accounts in one Organization and operates AWS Security Hub CSPM from a delegated administrator account. Production OUs must run the CIS AWS Foundations and PCI DSS standards with all controls enabled. Sandbox OUs must run only the AWS Foundational Security Best Practices standard with a few noisy controls disabled. Account owners must not be able to change these settings, and new accounts moved into an OU must pick up the OU's settings automatically. Which solution requires the LEAST ongoing operational effort?
A: Use Security Hub CSPM central configuration to create configuration policies in the delegated administrator account and associate each policy with the matching OU
B: Turn on Security Hub CSPM auto-enable for new accounts with the default standards, and ask each account owner to enable or disable controls in their own console
C: Deploy a CloudFormation StackSet to each OU that enables the standards, and use a second StackSet to disable controls in the sandbox OU
D: Create an AWS Config organization conformance pack per OU containing the equivalent Config rules, and disable the Security Hub standards
K: A
G: ## Two ways to configure Security Hub CSPM across an organization
The security standards and controls in this question (CIS, PCI DSS, Foundational Security Best Practices) belong to AWS Security Hub CSPM, the cloud security posture management capability of AWS Security Hub. Central configuration works the same way in concept: a delegated administrator defines policies and associates them with the organization structure.
- **Local configuration** lets each account enable standards and controls itself. The delegated administrator can only auto-enable defaults for new accounts, and owners can change them.
- **Central configuration** lets the delegated administrator create **configuration policies** that choose which standards and controls are enabled, and associate them with accounts, OUs or the root. Policies are inherited down the OU tree, and associated accounts cannot change those settings locally.
Central configuration is set up in a home Region, and it applies the policy to the linked Regions. AWS Config recording must be on for the controls to evaluate.
W: Central configuration policies: one policy per environment type, attached to the OU, gives different standards and control sets, blocks local changes, and applies automatically to accounts that join the OU. Nothing has to be redeployed per account.
X: B=Auto-enable with local edits: auto-enable applies to new accounts only with a single default, and owners can change or disable controls, so the different per-OU sets and the tamper-resistance requirement both fail.
C=StackSets per OU: this can work but is custom plumbing that must be updated when controls change, drifts if owners toggle settings, and does not create a managed inheritance model. It is more effort than the built-in policy feature.
D=Conformance packs instead of Security Hub standards: this replaces the Security Hub CSPM control set and its aggregated findings with hand-built rules, and loses standard scores and automated updates to controls.
T: For different Security Hub CSPM settings per OU with owner tamper-resistance, use central configuration policies from the delegated administrator, not per-account or StackSet toggles.
V: AWS Security Hub CSPM, AWS Organizations, AWS Config

@ SAP-C02 D1 T1.2 advanced use-case
S: A company operates 60 workload accounts in an Organization. Each account runs internal services that need TLS certificates issued by the company's own private root and intermediate hierarchy so internal clients trust them. The security team wants one private CA operated only by the PKI team in a dedicated account, no CA private key material copied to workload accounts, and workload teams able to request and renew certificates in ACM by themselves with usage visible in one place. Which solution meets these requirements?
A: Create a private CA in each workload account by using AWS Private CA and import the root certificate from the PKI account as the signing parent
B: Export the intermediate CA private key and store it in Secrets Manager in each workload account so teams can sign their own certificates
C: Create the private CA in the PKI account and share it through AWS RAM, so workload accounts issue certificates in ACM signed by that CA
D: Issue public ACM certificates from the workload accounts and configure internal clients to trust the public Amazon root CAs for private hostnames
K: C
G: ## Sharing a private CA
AWS Private CA hosts the CA hierarchy and its keys in managed hardware, and the private key of a CA cannot be exported. Access to issue is granted, not copied.
- With **AWS Resource Access Manager (RAM)**, the owning account shares a CA with other accounts, OUs or the whole organization.
- Principals in the shared accounts request certificates in **AWS Certificate Manager (ACM)** and pick the shared CA. Issuance and managed renewal work as usual.
- The CA owner keeps control of the CA and its policy, and can generate audit reports that list the certificates the CA has issued, including those requested from shared accounts.
W: RAM-shared private CA: the CA and its keys stay in the PKI account, workload teams issue and renew through ACM on their own, and the hierarchy is single and centrally audited. No key material moves.
X: A=CA per account: it multiplies CAs, each with its own cost and management, and puts CA administration in every workload account. This breaks the requirement that only the PKI team operates the CA.
B=Export the CA key: private CA keys cannot be exported from AWS Private CA, and even if a key could be copied, spreading it across accounts would remove central control.
D=Public ACM certificates for private hostnames: public CAs issue only for publicly validated domain names, not internal-only hostnames, and this does not use the company's own hierarchy that internal clients trust.
T: Centralize a private CA in a PKI account and share it with RAM; consumers issue through ACM without ever holding the CA's key.
V: AWS Private CA, AWS Certificate Manager, AWS Resource Access Manager

@ SAP-C02 D1 T1.2 advanced use-case
S: A central data platform account owns a customer managed KMS key that encrypts data in many workload accounts of the same Organization. New accounts join monthly and their roles must be able to decrypt with the key without the security team editing the key policy every time. Security also requires that accounts outside the organization can never use the key. Which TWO actions together meet these requirements? (Select TWO)
A: Add a statement to the key policy that allows kms:Decrypt for all principals with a condition that aws:PrincipalOrgID equals the organization ID
B: Add an identity-based policy to each workload role that allows kms:Decrypt on the key's ARN
C: Attach an SCP to the organization root that allows kms:Decrypt on the key ARN, so member roles inherit the permission
D: Share the KMS key with the organization by using AWS Resource Access Manager so member accounts see it as their own key
E: Enable trusted access for AWS KMS in AWS Organizations so that every member account automatically gains decrypt permission on all shared keys
K: A,B
G: ## Cross-account KMS needs two permissions
For a principal in another account to use a KMS key, both sides must allow it:
- The **key policy** must allow the principal, or the principal's account. Using `aws:PrincipalOrgID` in a condition lets you allow the whole organization once, so new accounts qualify automatically and outside accounts do not.
- The caller's **identity-based policy** in its own account must also allow the KMS action on the key ARN. A key policy alone is not enough across accounts.
SCPs and RCPs only restrict; they never grant permissions, and KMS keys are not shared through RAM.
W:
A=Key policy with aws:PrincipalOrgID: one statement covers every current and future account in the organization and excludes anyone outside it, which removes per-account edits to the key policy.
B=Identity policy on each workload role: the cross-account caller also needs its own account to allow kms:Decrypt on the key ARN, which the workload team or a baseline template can attach to the roles that need it.
X: C=SCP allowing decrypt: an SCP only sets a ceiling and never grants permissions, so it does not give the roles access to the key.
D=RAM share of the key: KMS keys are not a resource type that RAM shares; cross-account use is granted through key policies, grants and identity policies.
E=Trusted access for KMS: enabling trusted access lets services work with the organization, but there is no setting that grants every member account decrypt on shared keys.
T: Cross-account KMS use needs an allow in the key policy (use aws:PrincipalOrgID for organization-wide access) and an allow in the caller's identity policy; SCPs and RAM do not grant it.
V: AWS KMS, AWS Organizations, AWS IAM

@ SAP-C02 D1 T1.4 advanced use-case
S: A company has standardized on Terraform and GitOps for all infrastructure. It has adopted AWS Control Tower and needs to provision roughly 20 new accounts a month. Each account must be requested through a pull request, enrolled in Control Tower, and receive the same baseline plus per-team customizations (for example VPC settings, IAM roles and budgets) applied by a pipeline, with no console clicking. Which solution best fits?
A: Use AWS Control Tower Account Factory for Terraform (AFT), where account requests are Terraform files in a repository and a pipeline provisions and customizes each account

AWS Control Tower can create and enroll accounts through **Account Factory**. It comes in flavors:
- **Console / Service Catalog Account Factory** is request-driven through a portal and API.
- **Account Factory for Terraform (AFT)** is a Terraform module deployed into a dedicated AFT management account. Account requests are Terraform configuration in a repository; a pipeline calls Control Tower to create and enroll the account, then runs global and per-account customizations.
Accounts created outside Control Tower would need separate enrollment steps to receive the landing zone guardrails.
W: AFT: it matches the GitOps workflow (a pull request becomes an account), enrolls the account in Control Tower so guardrails apply, and runs baseline and per-account customizations from the pipeline.

V: AWS Control Tower, AWS Organizations, AWS Service Catalog

@ SAP-C02 D1 T1.4 advanced use-case
S: A company wants its platform team to deploy baseline CloudFormation stacks (logging roles, security groups, and a GuardDuty configuration) automatically to every account in its Production and Security OUs, including accounts created in the future. Policy forbids day-to-day work in the organization's management account, so the platform team works from a shared services member account. Which solution meets these requirements?

- **Self-managed** permissions need an administration role in the admin account and an execution role in every target account that you create yourself. There is no automatic deployment to new accounts.

A member account can be registered as a **delegated administrator** for StackSets, so the platform team can create and manage service-managed StackSets without working in the management account.

D=Direct stacks via OrganizationAccountAccessRole: this is a per-account manual process with a powerful role, with no OU targeting, no auto deployment and no consistent drift management.

@ SAP-C02 D1 T1.4 advanced troubleshooting
S: A company removed the default FullAWSAccess SCP from its organization root and replaced it with an allow-list SCP at the root that permits EC2, S3, RDS and CloudWatch actions. The Workloads OU has its own SCP that permits EC2 and S3 only. The Payments OU is a child of the Workloads OU. A Payments account administrator has an IAM policy with rds:* and receives AccessDenied when creating an RDS instance. No explicit deny exists in any policy. What explains this, and what is the correct fix?
A: An allow-list SCP at the root is ignored below it, so the IAM policy denies the call by default; add rds:* to the IAM role's permissions boundary
B: SCPs from the root apply only to the management account, so the Workloads OU SCP must be detached for the root allow list to take effect
C: Every level must allow the action; the Workloads OU SCP omits RDS, so add rds actions to it or reattach FullAWSAccess there
D: The account is missing an explicit Allow in its own SCP and any inherited SCP, so create a deny-list SCP that denies non-RDS services
K: C
G: ## How SCPs combine down the tree
An SCP defines which actions are allowed at a level. Effective permissions for an account are the intersection of what every SCP from the root through each parent OU to the account allows:
- With the default **FullAWSAccess** policy attached, each level allows everything, and you add deny statements to restrict.
- With an **allow list**, you remove FullAWSAccess at that level and list what is allowed; every level from the root to the account needs an allow for the action, and any explicit deny still wins.
An IAM policy grant is only effective if the SCP intersection also allows the action, and SCPs never grant permissions themselves.
W: RDS is allowed at the root, but the Workloads OU allow list omits it, so the intersection excludes RDS for accounts under it. Adding RDS to that level (or reattaching FullAWSAccess and using denies) fixes it.
X: A=SCP ignored below the root: SCPs are inherited and enforced all the way down; and a permissions boundary can only restrict, not grant beyond what the SCP allows.
B=Root SCP applies only to management: SCPs affect member accounts, and the management account is the one that is not restricted by SCPs. Detaching the OU policy would leave no allow at that level.
D=Missing explicit allow in the account's own SCP: the failing level is the OU, and a deny-list on non-RDS services does not add an allow and would block other actions the account needs.
T: With allow-list SCPs, each level from the root to the account must allow the action; a missing allow in any intermediate OU is an implicit deny.
V: AWS Organizations

@ SAP-C02 D1 T1.4 advanced use-case
S: A central network team maintains a list of about 40 corporate CIDR ranges used by on-premises offices. Application teams in 70 accounts and two Regions reference these ranges in security group rules that allow inbound access to internal services. The list changes weekly, and the team wants a single change to update every security group in every account without touching the rules themselves, while application teams cannot edit the list. Which solution meets these requirements with the least custom code?
A: Create a customer managed prefix list in the network account in each Region, share it through AWS RAM, and reference it in the security groups
B: Store the CIDR list in a Systems Manager parameter and run a scheduled Lambda function in each account and Region that rewrites the security group rules
C: Copy the CIDR list into a security group in each account and deploy the change by using a StackSet whenever the list changes
D: Put the CIDR list in a network ACL on a shared subnet and share the subnet through RAM so that all accounts inherit the list
K: A
G: ## Managed prefix lists
A **customer managed prefix list** is a named set of CIDR blocks. Security group rules, subnet route tables and other constructs can reference the list by ID instead of listing CIDRs, and a security group rule that references a prefix list counts against the rules-per-security-group quota as many rules as the list's maximum size (not as one rule), so set the maximum size with the quota in mind.
- You **share** a prefix list with other accounts through **AWS RAM**; participants can reference it but only the owner can change its entries.
- When the owner updates the list, every resource that references it uses the new entries without edits.
Prefix lists are Regional, so the list must be created and shared in each Region where it is used.
W: Shared prefix list: one owner-controlled list is referenced by security groups, and each weekly change propagates automatically. No code or redeploy is required, and consumers cannot edit it.
X: B=SSM parameter and Lambda rewriting rules: it works but is custom code in every account that can drift, and it does not use the built-in reference mechanism.
C=StackSet copies: each change requires redeploying rules to every account and Region, and the rules exist in each account where owners might edit them.
D=NACL on a shared subnet: network ACLs are subnet-level, stateless, and not referenced by security groups, and a subnet share does not distribute a CIDR list to other VPCs.
T: To centralize CIDR lists across accounts, share a managed prefix list via RAM and reference it in security groups; updates propagate automatically.
V: Amazon VPC, AWS Resource Access Manager

@ SAP-C02 D1 T1.4 advanced use-case
S: A security team in a delegated administrator account needs a single, continuously updated inventory and compliance view of AWS Config resource data for all 200 accounts and all enabled Regions, including accounts created in the future. The team only needs to read and query the data; remediation is performed by other tooling. Which solution meets these requirements with the least effort?
A: Register the security account as a Config delegated administrator and create an organization aggregator for all accounts and Regions

C: Deploy a Lambda function in each account that copies configuration items into a central S3 bucket, and query the bucket with Athena
D: Create an organization conformance pack in the management account and review the compliance results from each member account console

G: ## Config aggregators
An **AWS Config aggregator** collects configuration and compliance data from multiple accounts and Regions into one account and Region. There are two ways to define its sources:
- **Individual accounts:** each source account must authorize the aggregator account, which does not scale and does not include future accounts.
- **Organization:** with trusted access enabled, the aggregator pulls from every account in the organization automatically, including new ones. It can be created in the management account or a delegated administrator account.
An aggregator gives a read-only view for queries (advanced queries and dashboards); it does not itself change resources in source accounts.
W: Organization aggregator in the delegated administrator: it covers all current and future accounts and Regions without per-account steps, and it provides the read-only aggregated queries the team needs.

D=Conformance pack viewed per member account: a conformance pack deploys rules but does not create a central multi-account view; results have to be viewed account by account.

@ SAP-C02 D1 T1.4 advanced tradeoff
S: A company wants to enforce, across all accounts, that new EC2 instances default to IMDSv2, that EBS snapshots cannot be shared publicly, and that only approved AMI providers can be used. The platform team wants the baseline to hold no matter which API, console flow or SDK version a developer uses, wants a report of the current state of each attribute per account before enforcement, and wants users to see a custom error message. Which approach best meets these requirements?
A: Use declarative policies for EC2 attached to the root or OUs, and review the account status report before enforcing
B: Write SCPs that deny ec2:RunInstances unless ec2:MetadataHttpTokens requires tokens, and deny ec2:ModifySnapshotAttribute for public sharing
C: Deploy AWS Config rules and remediation runbooks in each account that fix noncompliant instances and snapshots after they are created
D: Give developers a Service Catalog portfolio of approved instance products and revoke their direct EC2 launch permissions
K: A
G: ## Declarative policies
**Declarative policies** are an AWS Organizations policy type that lets you state the desired configuration of a service at the organization, OU or account level, and enforce it at the service layer, so it holds even when a new API or feature appears. They support EC2 (and related VPC and EBS) attributes such as IMDS defaults, block public access for snapshots and AMIs, allowed images, serial console access and VPC block public access.
- Before attaching, an **account status report** shows the current state of attributes per account.
- You can define a **custom error message** shown when an action is blocked.
SCPs work at the API-action level, so they must anticipate each API and condition key, and they cannot set a default.
W: Declarative policies for EC2: they enforce the baseline at the service level regardless of the entry point, provide the pre-enforcement status report and custom error text, and are managed centrally.
X: B=SCPs with conditions: they block specific actions and depend on conditions being present for each path; they do not set service defaults and do not provide a state report or a service-level guarantee.
C=Config remediation: it is detective and corrective after creation, leaving noncompliant resources for a period, and needs rules and runbooks in every account.
D=Service Catalog portfolio: this changes the launch process but gives no protection against other paths for accounts with different permissions, and does not cover snapshot sharing or AMI provider rules.
T: For service-level baselines such as IMDSv2 defaults, block public snapshot sharing and allowed images, use declarative policies; SCPs restrict API actions, not defaults.
V: AWS Organizations, Amazon EC2

G: ## Zero trust access to applications
**AWS Verified Access** provides VPN-less access to internal web applications. Each request is evaluated against a policy written in Cedar:
- A **trust provider** for identity (IAM Identity Center or an OIDC provider) supplies user claims such as groups.
- A **device trust provider** (integrations with endpoint management tools such as CrowdStrike, Jamf or JumpCloud) supplies device posture.
- Applications sit behind a Verified Access endpoint pointing at a private load balancer or network interface, and access is logged per request.
W: Verified Access: it checks identity and device posture on every request and needs no VPN client, and the application stays private behind the endpoint.
X: B=Client VPN: it needs a client, and once connected, users get network access based on group membership. It has no per-request device posture check.

T: For VPN-less, per-request access decisions using identity and device posture, use AWS Verified Access.
V: AWS Verified Access, Elastic Load Balancing

@ SAP-C02 D3 T3.2 advanced tradeoff
S: A company stores 2 PB of objects in a set of S3 buckets encrypted with SSE-S3. A new compliance requirement demands SSE-KMS with a customer managed key so that key use is logged in CloudTrail and access can be revoked. The workload issues hundreds of millions of requests a month, and the finance team is concerned about AWS KMS request costs. Which approach meets the requirement with the LOWEST ongoing KMS cost?
A: Set default encryption to SSE-KMS with S3 Bucket Keys, then re-encrypt existing objects with an S3 Batch Operations Copy job that sets SSE-KMS and Bucket Keys
B: Change only the bucket default encryption to SSE-KMS without Bucket Keys, and let existing objects convert automatically the next time they are read
C: Enable client-side encryption in every application with a data key from KMS for each object, and keep SSE-S3 for storage

K: A
G: ## SSE-KMS and request costs
With SSE-KMS, S3 calls AWS KMS for each object to generate data keys or decrypt, and those calls are billed and count toward KMS request quotas.
- **S3 Bucket Keys** let S3 use a bucket-level key derived from your KMS key for a time-limited period, cutting KMS requests by up to about 99 percent. KMS key use is still logged in CloudTrail, but at the bucket level rather than per object.

D=Key per prefix with lifecycle re-encryption: lifecycle transitions do not change encryption, and multiple keys increase KMS management without a request cost benefit.
T: To move existing S3 data to SSE-KMS cheaply, enable Bucket Keys and rewrite old objects with Batch Operations Copy; default encryption changes affect only new objects.
