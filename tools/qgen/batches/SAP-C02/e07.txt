@ Q001173 explain
G: ## The migration strategies ("7 Rs")
AWS groups migration approaches by how much the workload changes on the way to the cloud:
- **Retire**: switch the application off.
- **Retain**: leave it where it is for now.
- **Rehost** (lift and shift): move servers as they are onto EC2.
- **Relocate**: move a platform such as VMware to AWS without changing the VMs.
- **Replatform** (lift, tinker and shift): keep the application's architecture and code, but swap one or more components for a managed or optimized service.
- **Repurchase**: replace it with a different product, often SaaS.
- **Refactor**: re-architect the application, typically to use cloud-native features.
## Where a managed database fits
Moving a self-managed SQL Server to **Amazon RDS for SQL Server** removes patching, backups and failover work, yet the application still talks to SQL Server with the same queries and drivers. The app servers move to EC2 unchanged. That combination, one targeted swap with no redesign, is the textbook replatform.
W: Replatforming: the application architecture and code stay the same while the database is swapped for a managed service; refactoring would instead change the application's design and code, for example breaking it into services or adopting cloud-native databases.
X: A=Retiring: retire means the whole application is decommissioned; here the application keeps running, only its database hosting changes.
B=Rehosting: rehost moves servers as they are; replacing a self-managed database server with RDS is a platform change, even if the engine stays compatible.
C=Refactoring: refactoring means re-architecting the application itself; moving a database to a managed service with no code or architecture change does not qualify.
T: One component swapped for a managed service with the same app design is replatforming; refactoring only applies when the application itself is redesigned.

@ Q001174 explain
G: ## Deciding what not to migrate
Discovery data often shows that part of a portfolio is idle. **AWS Application Discovery Service** collects server inventory, CPU, memory and network utilization and, with agents, connection data, so you can base portfolio decisions on measurements rather than guesses.
## Retire as a strategy
**Retire** means decommissioning an application instead of moving it. Typical signals:
- Utilization near zero for a long observation window, such as 90 days.
- No active users or logins.
- The business owner confirms the output is no longer used.
Availability note: Application Discovery Service stopped accepting new customers on November 7, 2025; AWS recommends AWS Transform for discovery and assessment, while existing customers can keep using ADS.
Every retired application is one less thing to migrate, license, patch, secure and pay for. Portfolio assessments commonly find a meaningful share of applications that can be retired or consolidated.
Example: a reporting server with under 2% CPU, no logins and reports nobody reads is shut down and archived, not moved.
W: Retire the application: usage data and the business owner both show the application is no longer needed, so decommissioning (after archiving any data you must keep) avoids migration effort and ongoing running costs.
X: B=Rehost as-is: this spends migration effort and then pays EC2, storage and licensing costs indefinitely for an application nobody uses.
C=Relocate to VMware Cloud on AWS: moving the VMs to another platform unchanged still carries all the costs of an unused workload; relocate is about speed and tooling continuity, not whether the app is needed.
D=Repurchase with SaaS: buying a replacement makes sense only when the capability is still needed; here the reports themselves are no longer used.
T: When data and the owner both say an application is unused, retire it; every other strategy spends money moving or replacing something nobody needs.

@ Q001175 explain
G: ## Relocate versus rehost
Both strategies move workloads without changing the applications, but they land on different platforms.
- **Relocate** moves VMs to a VMware environment running in AWS, classically **VMware Cloud on AWS**, a VMware software-defined data center (now sold by Broadcom) on dedicated bare-metal hosts in AWS. **Amazon Elastic VMware Service** (Amazon EVS) is a newer AWS option that runs VMware Cloud Foundation on EC2 bare-metal instances in your own VPC. vCenter, vSphere and the operations team's tooling stay the same, and VMs can move with vMotion or VMware HCX without being converted.
- **Rehost** with **AWS Application Migration Service** (MGN) replicates each server at block level and launches it as a native EC2 instance. After cutover the VMs are no longer VMware objects, so vCenter-based tooling and processes no longer apply.
## When relocate wins
Relocate is chosen when speed and continuity matter most: hundreds of VMs, a team that wants to keep VMware operations and licensing during a transition, and a plan to modernize later. Rehost is chosen when the goal is native EC2 and exit from the hypervisor stack.
W: Relocate with VMware Cloud on AWS: VMs move at the hypervisor level with existing vCenter, vMotion and VMware licensing, while MGN would convert each VM into a native EC2 instance and leave the VMware tooling behind.
X: B=Refactor: keeping VMware tooling requires no application change at all; refactoring means re-architecting code, which is slower and contradicts the "minimal changes" goal.
C=Relocate and rehost are identical: they end on different platforms, VMware SDDC hosts versus native EC2, with different tooling, operations and licensing.
D=Relocate supports only Windows: VMware Cloud on AWS runs the guest operating systems vSphere supports, including Linux; there is no Windows-only restriction.
T: Keep the VMware stack and move fast means relocate; convert to native EC2 means rehost with Application Migration Service.

@ Q001176 explain
G: ## Building a migration business case
Before a large migration, leadership usually asks what the company spends today and what it would spend on AWS. The answer must come from real utilization, because on-premises servers are often heavily over-provisioned and a like-for-like price comparison overstates cloud cost.
## AWS Migration Evaluator
**AWS Migration Evaluator** (formerly TSO Logic) collects on-premises inventory and utilization data, for example with its agentless collector or from existing tool exports, then:
- Right-sizes each workload to a matching EC2 instance based on observed use.
- Models licensing options, such as bring-your-own versus license-included.
- Produces a report comparing current on-premises cost with projected AWS cost.
Example: 1,000 servers averaging 15% CPU are modeled on smaller instances, giving a TCO case built on measured usage rather than server nameplate capacity.
W: AWS Migration Evaluator: it is purpose-built for pre-migration business cases, combining actual on-premises utilization with AWS pricing to produce a data-driven TCO comparison.
X: A=Cost Explorer forecasts: Cost Explorer analyzes and forecasts spend already incurred in AWS accounts; it has no data about on-premises servers.
C=Trusted Advisor cost checks: these checks find idle or underused resources already running in AWS; they cannot model a workload that has not migrated yet.
D=Pricing Calculator estimates: the calculator prices configurations you enter or import yourself; it does not collect on-premises utilization, right-size from it, or produce an on-premises versus AWS comparison.
T: For a pre-migration TCO case based on real on-premises utilization, use Migration Evaluator; Cost Explorer and Trusted Advisor only see what already runs in AWS.

@ Q001177 explain
G: ## Why TCO baselines go wrong
A TCO comparison has two sides. The AWS side is fairly easy to price. The on-premises side is where cases fail, because many costs never appear on a server invoice:
- **Facilities**: floor space, power, cooling, physical security.
- **Licensing**: support renewals and true-up fees.
- **Labor**: time spent patching, racking, backing up and troubleshooting.
Leave these out and the on-premises baseline looks cheaper than it is, so projected savings shrink.
## Quick view versus detailed assessment
Migration Evaluator's **Quick Insights** gives a fast, largely automated summary of projected AWS cost from the collected data. A more **detailed assessment and business case**, typically prepared with AWS migration specialists or a partner, lets you add the company's actual facility, licensing and staffing costs so the on-premises side reflects reality.
Example: adding power, space and patching hours to a 500-server estate can change the savings figure substantially.
W: Detailed Migration Evaluator assessment: it lets the team add facilities, licensing true-ups and labor to the on-premises baseline, producing a complete TCO comparison before the budget decision.
X: A=Assume costs already included: the review showed those costs were missing from the baseline, so proceeding would knowingly present understated savings.
B=Cost Explorer after migration: Cost Explorer only reports AWS spend after the fact; it cannot supply the on-premises costs, and the case is needed before approval.
C=Pricing Calculator only: the calculator prices the AWS side from manual inputs; it drops the utilization-based analysis and still has no on-premises cost baseline.
T: A credible TCO needs the hidden on-premises costs (facilities, licensing, labor) in the baseline; enrich the Migration Evaluator assessment rather than switching tools.

G: ## What the Migration Hub home Region is
**AWS Migration Hub** is a single place to track discovery and migration progress across tools such as Application Migration Service and Database Migration Service. Each account chooses a **home Region**, and all discovery and tracking data for that account is stored and shown there.
- The home Region is only where tracking data lives; migrations can still target any Region.
- The console in the home Region shows the consolidated view. Data reported to a different home Region is not merged in.
- Availability note: Migration Hub stopped accepting new customers on November 7, 2025, and AWS recommends AWS Transform for new migration programs; existing customers can continue to use it.
## What happens with two home Regions
If one team reports to `us-east-1` and another to `eu-west-1`, the tracking data ends up in two separate places. Nothing syncs them, so a PMO watching `us-east-1` never sees the European work.
Example: the European team can keep replicating servers into `eu-west-1`, but its Migration Hub status must be reported to the same home Region the PMO uses.
W: One home Region for everyone: Migration Hub stores tracking data only in the configured home Region, so all teams must report to the same one, here `us-east-1`, to get a single consolidated view.
X: A=Automatic cross-Region sync: Migration Hub does not replicate tracking data between home Regions; that is exactly why the PMO cannot see the European status.
B=Delete and recreate migration jobs in us-east-1: the migration target Region is not the problem; replication can continue into `eu-west-1`. Only the tracking home Region needs to be aligned.
C=Unresolvable, separate hubs forever: unified visibility is the purpose of Migration Hub; it is achieved by standardizing on one home Region.
T: Migration Hub consolidates data in one home Region; migrations can go to any Region, but every team must report to the same home Region.

@ Q001179 explain
G: ## Retain (revisit)
Not every application should move in the first wave. **Retain** means keeping an application in its current environment for now, usually for a concrete reason, and scheduling a later review.
Common reasons:
- Tight coupling to local hardware, such as plant-floor controllers needing millisecond response.
- Vendor support only for on-premises installation.
- Recent hardware investment or pending replacement decisions.
## Making retain work in a hybrid estate
A retained system still has to talk to the migrated workloads. Hybrid connectivity such as **AWS Direct Connect** or a Site-to-Site VPN links it to AWS, and the portfolio records a revisit date.
Example: a manufacturing execution system stays next to the production line, exchanges data with analytics in AWS over Direct Connect, and is reassessed in three years.
W: Retain: the system stays on premises because of latency and vendor-support constraints, connected to AWS through Direct Connect, with a planned review in three years.
X: A=Rehost to EC2: moving the system into an AWS Region adds network distance to the controllers and violates the vendor's on-premises-only support terms.
C=Retire: the system still runs the plant floor; retiring it and replacing it with scripts would remove a needed, vendor-supported production system.
D=Relocate to VMware Cloud on AWS: relocate still moves the workload into AWS, so it has the same latency and support problems as rehosting.
T: An application that must stay where it is for now, with hybrid links and a planned review, is retained; every move to AWS breaks the latency and vendor constraints.

@ Q001180 explain
G: ## Online file migration with AWS DataSync
**AWS DataSync** moves file and object data over the network between on-premises storage and AWS storage services.
- An **agent** (a VM deployed on premises) reads from NFS, SMB, HDFS or object storage sources.
- A **task** copies data to Amazon S3, Amazon EFS or Amazon FSx.
- Tasks are incremental: after the first full copy, later runs transfer only new and changed files, and they can run on a schedule.
- DataSync verifies data integrity during and after transfer, and it uses parallel, optimized transfers.
## A typical cutover
Run the initial bulk copy of the 400 TB, schedule incremental runs while users keep working, then do a final incremental run during cutover so only the last changes move.
Example: a nightly task catches up the day's new video files until the NAS is switched off.
W: AWS DataSync: it reads directly from NFS, writes to S3, transfers only changed files on repeat runs and verifies integrity, which matches the multi-week sync requirement.
X: A=S3 Transfer Acceleration: it speeds long-distance uploads to one bucket, but it does not read NFS shares, track changed files or validate a migration.
C=AWS Transfer Family: it provides managed SFTP, FTPS, FTP and AS2 endpoints for clients to push files; it is not a tool to crawl and sync an existing NAS.
D=Snowball Edge: devices move data offline in one shipment; they cannot keep a live NAS in sync with S3 over several weeks.
T: Ongoing NFS-to-S3 migration with incremental syncs and integrity checks is DataSync; Snowball is a one-time offline copy.

@ Q001181 explain
G: ## Do the bandwidth math first
Before choosing a transfer tool, estimate how long the network would take.
- 50 Mbps is about 6.25 MB per second, or roughly 540 GB per day at full, uninterrupted use.
- 2 PB is about 2,000,000 GB, so 2,000,000 / 540 is roughly 3,700 days, around ten years.
No software tool can fix that: DataSync, SFTP or acceleration all send the bytes through the same 50 Mbps uplink.
## Offline transfer with Snowball Edge
**AWS Snowball Edge Storage Optimized** devices are rugged storage appliances shipped to your site. You copy data locally at LAN speed, ship the devices back, and AWS imports the data into Amazon S3.
- Several devices can be filled in parallel to shorten the job.
- Data is encrypted on the device with keys managed in AWS KMS.
- Availability note: since November 7, 2025, Snowball Edge is available only to existing customers; AWS points new customers to AWS Data Transfer Terminal (bring your own storage to an AWS facility), partner solutions, or DataSync where the network allows.
Example: loading a batch of devices in parallel in the data center moves petabytes in weeks rather than years.
W: Multiple Snowball Edge Storage Optimized devices: filling devices in parallel on the local network bypasses the 50 Mbps uplink entirely and fits a 30-day window.
X: B=Transfer Family with parallel SFTP: parallel sessions still share the same 50 Mbps uplink, so the transfer would still take years.
C=S3 Transfer Acceleration: acceleration improves the path after data leaves the site; it cannot raise the capacity of the local 50 Mbps link.
D=DataSync over 50 Mbps: DataSync uses the available bandwidth efficiently but cannot exceed it, and 2 PB at 50 Mbps takes about a decade.
T: When the math shows the network would take years, move the data physically, for example on Snowball Edge devices; no online tool beats the uplink's capacity.

@ Q001182 explain
G: ## Managed file transfer with AWS Transfer Family
**AWS Transfer Family** runs fully managed **SFTP**, **FTPS**, **FTP** and **AS2** endpoints that store files directly in **Amazon S3** or **Amazon EFS**.
- **Identity**: service-managed users with SSH keys, AWS Directory Service, or a custom identity provider through AWS Lambda or API Gateway, so existing credential workflows can be kept.
- **Hostnames**: you can point your existing DNS name at the server endpoint (for example a CNAME in Route 53), and you can import the existing SSH host key so partners do not see a host-key change.
- **Network**: public endpoints, or VPC endpoints with Elastic IPs for partners that allowlist addresses.
- Workflows can trigger post-upload processing.
## Why it fits a partner exchange
Partners keep connecting with the same SFTP client, hostname and credentials. The company stops patching and scaling its own server, and files land in S3.
W: AWS Transfer Family: it replaces the self-managed SFTP server with a managed endpoint writing directly to S3, while keeping hostnames, host keys and credential workflows unchanged for partners.
X: A=Direct Connect: it provides private network connectivity between a data center and AWS; it has no SFTP server and does nothing for external partners.
B=DataSync: it copies data between storage systems you control using an agent; it does not expose an SFTP endpoint for external partners to log in to.
D=S3 Transfer Acceleration: it speeds HTTPS uploads to S3 through edge locations; partners using SFTP clients cannot use it, and there is no SFTP login.
T: External partners that must keep using SFTP need an SFTP endpoint, so use Transfer Family; DataSync and Transfer Acceleration are not partner-facing protocols.

@ Q001183 explain
G: ## S3 Transfer Acceleration
Uploading to a distant Region over the public internet crosses many networks, so latency and packet loss limit throughput. **Amazon S3 Transfer Acceleration** lets clients upload to the nearest AWS edge location, and AWS carries the data over its backbone to the bucket's Region.
- Enable it on the bucket, then use the accelerated endpoint: `bucketname.s3-accelerate.amazonaws.com`.
- The data still lands in the same bucket; only the path changes.
- The bucket name must be DNS-compliant and must not contain periods.
- Acceleration is charged per GB, and AWS does not charge the acceleration fee when it does not make the transfer faster.
## When it helps
Long distances (offices on other continents), larger objects and a requirement to write to one central bucket. Use the Amazon S3 Transfer Acceleration Speed Comparison tool to measure the benefit from each site.
Example: an office in Singapore uploads to a `us-east-1` bucket through a nearby edge location instead of across the public internet.
W: Amazon S3 Transfer Acceleration: it routes uploads from each office through a nearby edge location and over the AWS backbone into the same `us-east-1` bucket, with no Direct Connect required.
X: A=VPC endpoint for S3: gateway endpoints serve traffic from resources inside a VPC; offices uploading over the internet do not use them, and they do not speed up long-distance paths.
B=Cross-Region Replication: it copies objects after they are written to a source bucket; offices would upload to other buckets, which violates the requirement to land in the specific bucket.
D=CloudFront in front of the bucket: CloudFront is designed to cache and deliver content to viewers; accelerated uploads straight into an S3 bucket are the job of Transfer Acceleration.
T: Faster long-distance uploads into one specific bucket means Transfer Acceleration; replication copies data after it lands, and CloudFront is built mainly for content delivery.

@ Q001184 explain
G: ## Two ways to discover servers
**AWS Application Discovery Service** offers two collection methods that can be combined:
- **Agentless Collector**: a collector VM deployed in the VMware environment. Its vCenter module reads VM inventory and utilization through vCenter; an optional network module can also record server-to-server traffic (source IP to destination IP and port) by connecting to the servers remotely. Nothing is installed in the guest operating systems, but it does not report which processes own those connections.
- **Discovery Agent**: software installed in each guest OS. It records system configuration and performance, plus running processes and the TCP connections between servers, which is the data needed for dependency mapping.
## Mixing methods by criticality
Availability note: Application Discovery Service stopped accepting new customers on November 7, 2025 (AWS Transform is the recommended path); existing customers can keep using it.
Deep, process-level dependency data matters most where a wrong wave grouping would break a critical application. For low-risk servers, inventory and utilization are enough for right-sizing and wave planning.
Example: agentless covers all 900 VMs for sizing, and agents on 50 critical servers show which processes talk to which database, so tightly linked servers move in the same wave.
W: Agentless for all VMs, agents on the 50 critical servers: agentless collection covers inventory and utilization without touching restricted guests, and agents supply process and connection data only where dependency mapping is needed.
X: A=Agentless Collector only: it can show traffic between server IPs and ports, but it does not capture running processes or which process owns each TCP connection, which the 50 critical servers require.
B=Discovery Agents on all 900 servers: installing agents on 850 servers violates the guest OS change restriction and adds effort where inventory data is enough.
C=CSV import of server specs: a static import gives no utilization history and no dependency data, so it cannot support right-sizing or dependency-aware wave planning.
T: Use agentless discovery for broad inventory and utilization, and in-guest agents only where you need process-level dependency data.

@ Q001185 explain
G: ## How AWS Application Migration Service works
**AWS Application Migration Service** (MGN) is the main AWS service for rehosting physical, virtual and cloud servers.
- A **replication agent** on each source server continuously copies its disks at the **block level** to a staging area in the target AWS account.
- Replication keeps running while the source stays in production, so the copy stays nearly current.
- **Test launches** start instances from the replicated data in the subnets you choose, so you can validate them in isolation without affecting the source or the replication.
- **Cutover** launches the final instances after a short stop of the source, so downtime is minutes rather than hours.
## Example
Install agents on 150 servers, wait for initial sync, run test launches per wave, fix launch settings, then cut over each wave in a short window.
W: Application Migration Service with block-level replication and test launches: continuous replication keeps cutover downtime minimal, and test launches validate each server before the final cutover.
X: A=DMS full-load-only: DMS migrates database tables, not whole servers, and a full load without change data capture means downtime while data is copied.
B=DataSync nightly copies to EBS snapshots: DataSync copies files between storage services; it does not replicate server disks into bootable instances, and nightly copies lose up to a day of changes.
D=Snowball Edge server images: shipping devices takes days and the data is stale by arrival, which does not meet minimal-downtime cutover or provide test launches.
T: Rehosting many servers with minimal downtime and pre-cutover testing is Application Migration Service; DMS and DataSync move data, not servers.

@ Q001186 explain
G: ## Direct Connect versus VPN
- **AWS Direct Connect** is a private, dedicated network connection from a data center or colocation facility to AWS. It does not cross the public internet, so latency is consistent and bandwidth is predictable (dedicated connections from 1 Gbps upward).
- **AWS Site-to-Site VPN** builds encrypted IPsec tunnels over the internet. It is quick to set up and cheap, but throughput and latency depend on internet conditions.
## Common hybrid pattern
Use Direct Connect as the primary path and a Site-to-Site VPN as a backup. Both advertise the same prefixes over BGP; AWS prefers the Direct Connect path when both are available, and traffic fails over to the VPN if Direct Connect goes down.
For the highest resilience, some designs use two Direct Connect connections at different locations, but DX plus VPN backup is a common cost-effective choice.
Example: market data flows over a 10 Gbps Direct Connect link, while a VPN keeps connectivity if the DX circuit fails.
W: Direct Connect primary with VPN backup: Direct Connect gives the consistent, high-throughput, low-latency link the trading application needs, and the VPN provides an independent failover path.
X: A=VPN as primary: VPN tunnels ride the public internet, so throughput and latency vary; Direct Connect, not VPN, is the consistent option.
B=Two VPNs over different ISPs: diverse providers improve availability, but both paths are still internet-based, so performance remains inconsistent for a latency-sensitive workload.
D=PrivateLink: it exposes specific services to consumers through interface endpoints; it is not a connection between a data center and AWS.
T: Consistent low-latency hybrid connectivity needs Direct Connect; a VPN is the inexpensive backup, not the primary.

@ Q001187 explain
G: ## Route 53 weighted routing
With **weighted routing**, you create several records with the same name and type, and give each a weight. Route 53 answers DNS queries in proportion to each record's weight relative to the total.
- Weights range from 0 to 255; a weight of 0 sends no traffic to that record unless all others are also 0.
- Changing a weight changes the traffic split without touching clients, which keep using the same hostname.
- Health checks can be attached so that unhealthy endpoints stop receiving answers.
- A short TTL makes changes take effect faster, because resolvers cache answers for the TTL.
## Gradual cutover
Example: `app.example.com` has an on-premises record with weight 90 and an AWS record with weight 10. After monitoring, the weights move to 50/50, then 0/100 to finish the migration.
W: Weighted routing: it sends a controllable percentage of traffic to the AWS endpoint and lets the team raise that share step by step, with no client changes.
X: A=Latency-based routing: Route 53 sends each user to the endpoint with the lowest measured network latency; the team cannot choose the percentage split.
B=Multivalue answer routing: it returns several healthy IP addresses and clients pick among them, so there is no control over the proportion of traffic.
C=Geolocation routing: it routes by user location, so whole countries switch at once; it does not provide a gradual, percentage-based shift.
T: A gradual, adjustable traffic shift between old and new endpoints is weighted routing; latency, geolocation and multivalue decide by other criteria.

**AWS IAM Identity Center** is the recommended way to give employees single sign-on access to many AWS accounts in AWS Organizations.

G: ## AWS Directory Service options
- **AD Connector**: a directory gateway (proxy). It forwards authentication and directory requests from AWS services to your **existing on-premises Active Directory**. No directory data is stored or cached in AWS.
- **AWS Managed Microsoft AD**: a real Microsoft Active Directory run by AWS. It is a **new, separate** directory; to use on-premises identities you set up a trust relationship.
- **Simple AD**: a standalone, Samba-based directory with basic AD-compatible features. It does not support trusts and does not replicate from other directories.
## Choosing
If the requirement is "use the directory we already have, and do not create another one", AD Connector is the fit. EC2 Windows instances can join the on-premises domain through it, and supported AWS services authenticate users against on-premises AD. It requires network connectivity to the domain controllers, such as VPN or Direct Connect.
W: AD Connector: it proxies requests to the existing on-premises Active Directory, so AWS-based servers use the same directory with no second directory to create or synchronize.
X: A=AD Connector and Managed Microsoft AD are identical: Managed Microsoft AD creates and runs a new directory in AWS, while AD Connector only forwards requests to an existing one.
B=Simple AD replicates on-premises AD: Simple AD is standalone; it does not replicate objects from or trust an on-premises AD.
D=Managed Microsoft AD because AD Connector cannot serve Windows apps: AD Connector does support domain join and authentication against the existing AD; choosing Managed AD would create the separate directory the company wants to avoid.
T: Use AD Connector to reuse an existing on-premises directory; use AWS Managed Microsoft AD when you need an actual AD running in AWS.

@ Q001190 explain
G: ## Minimal-downtime database migration
A one-time export and import stops writes for the whole copy, which for 5 TB can mean hours or days. **AWS Database Migration Service** (DMS) avoids that with a two-phase task:
- **Full load**: copies the existing data into the target while the source stays online.
- **Change data capture (CDC)**: reads the source's transaction logs (for Oracle, through LogMiner or Binary Reader) and applies ongoing inserts, updates and deletes to the target, keeping it close to real time.
## Cutover
When the target has caught up, stop application writes, let the last changes apply, confirm the target is in sync, and point the application at RDS. Downtime is only this final step.
Example: a 5 TB Oracle database replicates for several days; the actual switch to RDS for Oracle takes minutes.
W: DMS full load plus CDC: the source stays live during the bulk copy, ongoing changes keep RDS in sync, and cutover only needs a brief pause for the final changes.
X: A=Snowball export with multi-day outage: the stem allows only minutes of downtime, and an offline export, ship and restore keeps the database down for days.
B=DataSync into RDS storage: RDS is a managed service with no direct file-system access to its storage, so DataSync cannot write Oracle data files into an RDS instance.
C=SCT single export and import: SCT converts schemas and code between engines, which is not needed for Oracle to RDS for Oracle, and a one-shot copy at cutover means long downtime.
T: For near-zero-downtime database migration, use DMS full load plus CDC; one-shot export and import approaches stop writes for the whole copy.

G: ## Landing zones and AWS Control Tower
A **landing zone** is a well-architected multi-account baseline: an organization structure, shared logging and security accounts, identity, and guardrails. **AWS Control Tower** builds and maintains one for you on top of AWS Organizations.
- **Controls** (guardrails): preventive ones implemented as SCPs, such as denying root user actions or restricting Regions; detective ones implemented with AWS Config rules; and proactive ones checked at resource provisioning.
- **Account Factory** provisions new accounts with a consistent baseline.
- **Centralized logging**: CloudTrail and Config data go to a Log Archive account, with an Audit account for security teams.
## Bringing in existing accounts
Existing standalone accounts are invited into the organization and then **enrolled** into Control Tower in a registered OU, which applies the baseline and the OU's controls.
Example: 40 business-unit accounts are enrolled into a Workloads OU and immediately receive the Region-deny control and centralized logging.
W: Control Tower landing zone with account enrollment: it delivers standardized guardrails, Account Factory for new accounts and central logging as a managed service, and enrollment applies them to the 40 existing accounts.
X: A=One shared account: merging 40 business units removes account-level isolation of security, quotas and billing, and is a major migration of its own.
C=Config rules per account without structure: Config rules detect noncompliance but cannot prevent actions, and they give no account provisioning process or organization-wide governance.
D=Manual SCPs per account: SCPs are managed through AWS Organizations, not configured independently in each account; hand-building everything is exactly the custom governance work the company wants to avoid.
T: To govern many existing accounts without building tooling, set up a Control Tower landing zone and enroll them; manual SCPs and Config rules are pieces, not a managed baseline.

G: ## What Elastic Beanstalk manages
**AWS Elastic Beanstalk** runs web applications on platforms such as Java, .NET, Node.js, Python and Docker. You upload the application, and Beanstalk provisions and manages the load balancer, Auto Scaling group, EC2 instances, health monitoring and platform updates. The instances are regular EC2 instances, so you can still connect to them, for example with an SSH key pair or Session Manager, for troubleshooting.
## Deployment policies
- **All at once**: fastest, but causes downtime.
- **Rolling** and **rolling with additional batch**: update batches of instances; rollback means another deployment.
- **Immutable**: launches a full set of new instances in a temporary Auto Scaling group; only if they pass health checks are they moved into the environment, and the old ones terminated. Rollback is just terminating the new group.
- **Blue/green**: deploy to a second environment and swap CNAMEs.

C=Manually configured EC2: the team would provision the load balancer, Auto Scaling and deployment process itself, the opposite of wanting AWS to handle them.

G: ## Match the instance family to the bottleneck
EC2 instance families differ mainly in their ratio of memory to vCPU:
- **Compute optimized** (C family, such as `c6i`): about 2 GiB per vCPU.
- **General purpose** (M family, such as `m6i`): about 4 GiB per vCPU; `m6i.2xlarge` has 8 vCPUs and 32 GiB.
- **Memory optimized** (R family, such as `r6i`): about 8 GiB per vCPU; `r6i.2xlarge` has 8 vCPUs and 64 GiB.
## Reading the symptoms
Low CPU with high memory use and swapping means the working set does not fit in RAM. In-memory analytics keeps data in memory by design, so swapping to disk slows it dramatically. The fix is more memory per instance, not more CPU.
Example: moving from `m6i.2xlarge` to `r6i.2xlarge` doubles memory with the same vCPU count, so the data set fits and swapping stops. Compute Optimizer can recommend a size once the CloudWatch agent reports memory metrics.
W: Memory-optimized family such as r6i: it provides about twice the memory per vCPU of m6i, removing the swapping while CPU needs stay the same.
X: A=Burstable T family: T instances manage CPU credits for spiky CPU use; they offer no more memory per vCPU and do not address memory pressure.
B=Compute-optimized c6i: C instances have less memory per vCPU than M instances, so this would make the swapping worse, not better.
D=Auto Scaling on CPU: CPU stays low, so a CPU target would never add instances, and adding instances does not increase memory inside the one instance running the in-memory data set.
T: Memory-bound symptoms with low CPU call for a memory-optimized family; compute-optimized and burstable instances solve CPU problems.

G: ## Two AWS container orchestrators
- **Amazon EKS** runs certified, upstream-conformant **Kubernetes**. The Kubernetes API is standard, so manifests, Helm charts, operators and custom resource definitions, `kubectl` and existing CI/CD pipelines keep working.
- **Amazon ECS** is AWS's own orchestrator with its own concepts: task definitions, services and clusters, managed through the AWS API, console, CLI or CloudFormation. It does not accept Kubernetes manifests or Helm charts.
## When to pick which
If a platform team has already invested in Kubernetes tooling and skills, EKS preserves that model and reduces migration effort. ECS is often simpler for teams without Kubernetes experience.
Example: a team with custom operators and Helm-based deployments points its existing `kubectl` pipeline at a new EKS cluster and redeploys the same charts.
W: Amazon EKS: it exposes the standard Kubernetes API, so existing manifests, Helm charts, custom operators and kubectl-based pipelines carry over with minimal change.
X: A=Amazon ECS: ECS uses its own task definition and service model; Kubernetes manifests and Helm charts would have to be rewritten.
B=AWS Lambda: Lambda can run container images as functions, but it is not Kubernetes and cannot deploy from Helm charts or run operators.
D=Elastic Beanstalk: Beanstalk supports Docker-based platforms but not Kubernetes manifests, operators or kubectl workflows.
T: To keep an existing Kubernetes operating model, choose EKS; ECS is a different orchestrator with its own API.

G: ## ECS capacity options
An ECS task needs compute to run on. The main options are:
- **EC2 launch type** (or EC2 capacity providers): tasks run on EC2 instances in your account. You choose instance types and AMIs, patch them and scale the cluster, and you pay for the instances whether or not they are full.
- **AWS Fargate**: serverless compute for containers. You specify CPU and memory per task; AWS provisions, patches and scales the underlying capacity. Billing is for the vCPU and memory each task requests while it runs.
- **ECS Anywhere**: tasks run on your own servers outside AWS, managed from ECS.
## Trade-off
Fargate removes instance management in exchange for less control: no access to the host, no custom AMIs, and fewer hardware choices, such as no GPUs.
Example: a nightly batch job requests 2 vCPU and 4 GB for 20 minutes; with Fargate the team pays for those 20 minutes and never sees a server.
W: AWS Fargate launch type: it runs each task without any EC2 instances for the team to manage, patch or scale, and bills per task based on requested resources.
X: B=EC2 launch type with Spot only: Spot lowers cost, but the team still manages, patches and scales the instances, plus handles interruptions.
C=EC2 launch type with manual Auto Scaling: this adds instance management and manual scaling, the exact work the team wants to avoid.
D=ECS Anywhere: tasks run on the company's own infrastructure, so it keeps all server management on premises.
T: For containers with no servers to manage and per-task billing, use Fargate; any EC2-backed option keeps instance operations with you.

G: ## Amazon ECR governance features
**Amazon Elastic Container Registry** (ECR) is AWS's managed OCI and Docker image registry. It covers each requirement with built-in features:
- **Cross-account access**: repository policies grant `ecr:BatchGetImage` and related pull actions to other accounts or the whole organization.
- **Tag immutability**: once enabled, a tag such as `v1.4.2` cannot be pushed again with different content.
- **Image scanning**: basic scanning, or **enhanced scanning** with Amazon Inspector for continuous CVE detection in OS and language packages.
- **Replication**: registry replication rules copy images to other Regions or accounts, for example for DR.
- **Private access**: interface endpoints for `ecr.api` and `ecr.dkr`, plus an S3 gateway endpoint for image layers, let private subnets pull images with no internet path.
Example: a central account hosts repositories, 12 workload accounts pull through VPC endpoints, and images replicate to a second Region.
W: Amazon ECR with its governance and private access features: repository policies, tag immutability, enhanced scanning, cross-Region replication and VPC endpoints meet every requirement as managed features.
X: A=Self-hosted registry on EC2 with a public IP: the team must run and secure the registry and build scanning and replication itself, and private subnets without internet cannot reach a public IP without extra networking.
C=CodeArtifact generic packages: CodeArtifact hosts software packages such as npm, PyPI and Maven; container runtimes cannot pull images from it, and it has no container image scanning.
D=S3 tarballs with bucket policy and CRR: container runtimes pull from a registry API, not from S3 tarballs, and there is no CVE scanning or tag immutability.
T: Container images belong in ECR; turn on immutability, scanning, replication and VPC endpoints instead of building a registry from S3 or package repositories.
