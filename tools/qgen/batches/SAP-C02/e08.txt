@ Q001198 explain
G: ## Block, file and object storage for a database
A self-managed database engine (MySQL, PostgreSQL, SQL Server and so on) writes its data files and logs to a block device: a disk it formats with a local file system and reads and writes in small random blocks with low latency.
- **Amazon EBS** is network-attached block storage for EC2. A volume lives independently of the instance, so it survives a stop or instance replacement and can be detached and reattached.
- EBS snapshots are point-in-time, incremental copies stored in S3, and Elastic Volumes let you grow the size or change `gp3` IOPS and throughput while the volume stays in use.
- **Instance store** disks are physically on the host and are lost when the instance stops or the host fails.
- **EFS** is a shared NFS file system and **S3** is object storage; neither is a local block device.
Example: a `gp3` volume at 3,000 IOPS can later be raised to 16,000 IOPS and a larger size without downtime, or moved to `io2` for very high, consistent IOPS.
W: Amazon EBS (gp3 or Provisioned IOPS): it is persistent block storage that outlives the instance, supports point-in-time snapshots, and can be resized and retuned online, which matches every requirement for database data files.
X: A=Amazon EFS with "highest IOPS": EFS is a shared NFS network file system with higher per-operation latency than a block volume, and self-managed database engines are normally designed for a dedicated block device; the claim that it is the highest-IOPS database option is not a valid reason to pick it.
B=Instance store: the data is ephemeral and disappears when the instance stops, terminates or its host fails, and instance store has no EBS-style snapshots or resizing.
D=S3 through a file gateway: S3 is object storage, and a file gateway exposes it over NFS/SMB with caching, not as a block device; database engines cannot run their data files on it reliably.
T: Persistent, snapshot-capable, resizable block storage for a database on EC2 is EBS; instance store is ephemeral and EFS/S3 are not block devices.

@ Q001199 explain
G: ## Sharing files across many Linux servers
When several web servers behind a load balancer must all see the same uploaded files, the storage must be mountable by many instances at once with normal file semantics (locking, consistent reads after writes).
- **Amazon EFS** is a managed NFS file system. Any number of Linux EC2 instances, containers or Lambda functions can mount it at the same time, from mount targets in every Availability Zone.
- It grows and shrinks automatically, so there is no volume size to manage.
- **EBS** volumes attach to one instance at a time. Multi-Attach exists only for `io1`/`io2` volumes, only within one AZ, and needs a cluster-aware file system to avoid corruption.
- **Instance store** is local, temporary disk on one host.
Example: four instances in two AZs each mount `fs-12345678:/` at `/var/www/media`; a file uploaded through one instance is immediately readable from the other three.
W: Amazon EFS: it provides one POSIX-compliant NFS file system that all Linux instances in every AZ can mount concurrently for read and write, which is exactly what shared uploaded media needs.
X: A=S3 Glacier: it is an archive storage class with retrieval delays, not a file system that web servers can read and write concurrently.
B=One EBS volume on all instances: a normal EBS volume attaches to a single instance; Multi-Attach is limited to io1/io2 in one AZ and requires a cluster file system, so it cannot serve a multi-AZ web tier.
C=Replicated instance store: instance store data is lost when an instance stops or fails, and building your own replication between hosts gives neither shared access nor consistency.
T: Many Linux instances reading and writing the same files across AZs means EFS; EBS belongs to one instance and instance store is temporary.

@ Q001200 explain
G: ## Windows file shares on AWS
Windows applications usually access files over **SMB** and rely on Active Directory users and groups plus NTFS permissions (ACLs) to decide who can open which folder.
- **Amazon FSx for Windows File Server** runs real Windows file servers managed by AWS. It joins your AD (AWS Managed Microsoft AD or self-managed AD), serves SMB shares, and enforces NTFS ACLs, with features such as shadow copies, DFS namespaces and Multi-AZ deployments.
- **Amazon EFS** is NFS-only and targeted at Linux clients.
- **S3** is object storage accessed through the S3 API, controlled by IAM and bucket policies rather than AD users.
- **Volume Gateway** presents iSCSI block volumes to on-premises servers.
Example: `\\fs.corp.example.com\finance` keeps its existing ACL where only the `Finance-Readers` AD group can read, after a lift-and-shift to FSx.
W: Amazon FSx for Windows File Server: it is a fully managed, native Windows SMB file server that joins Active Directory and enforces NTFS user-level permissions, so the application works unchanged.
X: B=S3 with IAM bucket policies: S3 is an object store reached via API, not an SMB share, and its permissions are IAM-based rather than AD users and NTFS ACLs.
C=Volume Gateway: it exposes iSCSI block volumes backed by AWS to on-premises hosts; it is not a managed SMB file share with AD-integrated permissions.
D=Amazon EFS: EFS serves NFS for Linux clients and has no SMB protocol or Active Directory/NTFS permission model.
T: SMB plus Active Directory plus NTFS ACLs points to FSx for Windows File Server; EFS is NFS for Linux and S3 is object storage.

@ Q001201 explain
G: ## Two different storage patterns
**Moving NetApp workloads** is easiest when the target speaks NetApp's own data management language. **Amazon FSx for NetApp ONTAP** runs the ONTAP file system as a managed service, so teams keep:
- Snapshot copies, FlexClone and storage efficiency features
- SnapMirror replication, including from on-premises ONTAP arrays into AWS for migration
- Multi-protocol access: the same volume served over NFS, SMB and iSCSI
**Hybrid caching** is a different need: on-premises users want local speed while the full dataset lives in AWS. **AWS Storage Gateway (S3 File Gateway)** is a local VM or appliance that presents NFS/SMB shares, keeps recently used data in a local cache, and writes files asynchronously as objects to S3.
Example: a design office mounts `\\gateway\projects`; today's files come from the local cache, while years of older files stay in S3 and are fetched on demand.
Strictly, a Volume Gateway in stored mode is the option that keeps the primary copy on-premises with asynchronous backup to AWS, but no answer choice pairs FSx for ONTAP with it, and a local cache over a full dataset stored in AWS is what File Gateway provides.
W: FSx for NetApp ONTAP plus Storage Gateway File Gateway: ONTAP keeps Snapshots, SnapMirror and NFS/SMB multi-protocol volumes, and File Gateway gives on-premises clients a local cache while storing the full dataset in S3.
X: A=S3 for both: S3 storage classes change cost and retrieval behavior only; S3 has no NetApp Snapshot, SnapMirror or multi-protocol file access, and no on-premises cache.
C=EFS and FSx for Lustre: EFS is NFS-only with no NetApp features, and FSx for Lustre is a high-performance file system for compute clusters, not an on-premises caching gateway.
D=Volume Gateway for NetApp, ONTAP for caching: the roles are reversed; Volume Gateway serves iSCSI block volumes without NetApp features, and FSx for ONTAP in AWS is not a local on-premises cache.
T: Keep NetApp features with FSx for ONTAP; give on-premises users a local cache over AWS-stored data with Storage Gateway.

@ Q001202 explain
G: ## Matching the database to the access pattern
A shopping cart is read and written by one key (`cartId`) with no joins, which is the classic key-value pattern.
- **Amazon DynamoDB** is a serverless key-value and document database. It partitions data automatically by the partition key, so there is no sharding to design, and it returns single-digit-millisecond reads and writes at any scale.
- **On-demand capacity** bills per request and absorbs sudden spikes without capacity planning; **provisioned capacity with auto scaling** adjusts read/write units to utilization and is cheaper for steady traffic.
- Relational databases on RDS scale writes mostly by moving to a bigger instance, and read replicas help only reads.
Example: a flash sale multiplies cart writes many times over; a table with `cartId` as the partition key spreads that load across partitions automatically, and warm throughput can be raised ahead of a known sale so the table is ready for the peak.
W: Amazon DynamoDB (on-demand or auto scaled): simple key-value access by cart ID, 50x spikes and single-digit-millisecond latency with no capacity or sharding management is exactly what DynamoDB is built for.
X: B=Self-managed sharded MySQL on EC2: it can scale, but the team must build and operate sharding, replication, patching and capacity by hand, the opposite of the stated goal.
C=Large Multi-AZ RDS for MySQL: Multi-AZ adds availability, not write capacity, and a single instance must be sized for the peak, so 50x spikes mean overprovisioning or throttling.
D=RDS for PostgreSQL with read replicas: replicas only scale reads, while carts are write-heavy, and relational features are unused for pure key-value access.
T: Key-value access with extreme, spiky scale and no capacity management calls for DynamoDB; relational engines scale writes by instance size.

Elasticsearch clusters need constant care: node sizing, shard allocation, version upgrades, patching and snapshots.
- **Amazon OpenSearch Service** runs OpenSearch (an open-source fork of Elasticsearch 7.10) and legacy Elasticsearch versions as a managed service. AWS handles node provisioning, patching, snapshots, blue/green software updates and Multi-AZ deployment.

@ Q001204 explain
G: ## How much control each database option gives
- **Standard Amazon RDS** gives no OS or file-system access; you can use only the engine versions, extensions and plugins that RDS supports for that engine.
- **Amazon RDS Custom** (for Oracle and SQL Server) is a managed service that does allow OS and database customization, such as installing agents or patches, while AWS still automates backups and some operations.
- **Self-managed on EC2** gives full control of the OS, engine build, extensions and storage engines, but the team owns patching, backups, replication and failover.
- **Aurora** runs AWS's own MySQL- and PostgreSQL-compatible storage layer and supports only its approved extensions; custom storage engines cannot be plugged in.
Example: an application that depends on a third-party MySQL storage engine plugin cannot run on RDS or Aurora, so it moves to MySQL on EC2 with EBS volumes and scripted backups.
W: Self-managed EC2: installing an unsupported engine extension and a custom storage engine plugin requires OS- and engine-level control, which EC2 provides, in exchange for taking on database operations.
X: A=RDS Custom "no customization": this description is false, since RDS Custom exists precisely to allow OS and database customization; it also supports only certain engines, so as worded it cannot be the answer.
C=Aurora Serverless with third-party extensions: Aurora supports only its own list of extensions and cannot load custom storage engines, whether provisioned or serverless.
D=Standard RDS with the extension disabled: removing a feature the application depends on breaks the application, which is exactly the rewrite the team must avoid.
T: When the engine needs unsupported plugins, choose a platform that gives engine and OS control (EC2, or RDS Custom where the engine is supported), not standard RDS or Aurora.

@ Q001205 explain
G: ## Paying only while a job runs
An EC2 instance is billed for every hour it is running, even when idle. A job that runs 10 minutes a night on an always-on instance wastes more than 23 hours of cost per day.
- **AWS Lambda** runs code on demand and bills per request and per millisecond of execution, up to a maximum of 15 minutes per invocation.
- **Amazon EventBridge Scheduler** invokes targets on cron or rate expressions, with time zones and retries, so nothing needs to stay running to wait for the schedule.
Example: a schedule `cron(0 2 * * ? *)` in the company's time zone invokes a report function at 02:00; it runs about 10 minutes and the account pays only for those minutes.
If a job ever grows beyond 15 minutes or needs more than Lambda's 10 GB of memory, a scheduled Fargate task gives the same pay-per-run model.
W: Lambda run by EventBridge Scheduler: a 10-minute nightly job fits within Lambda's 15-minute limit, and serverless billing charges only for execution time, eliminating the idle instance cost.
X: A=Auto Scaling group with minimum one: a minimum of one keeps an instance running all day, so the idle cost remains.
B=Larger instance to finish sooner: a bigger instance costs more per hour and still runs 24 hours a day, so the bill goes up, not down.
C=Reserved Instance for 24/7: a reservation lowers the hourly rate but commits to paying for the instance all day, locking in cost for 23+ idle hours.
T: For a short, scheduled job, remove the always-on server and let EventBridge Scheduler trigger pay-per-use compute such as Lambda.

@ Q001206 explain
G: ## Working around Lambda's 15-minute limit
A Lambda invocation can run at most 15 minutes (`900` seconds). No setting raises that limit, so work that grows past it must be split up.
- **AWS Step Functions** orchestrates a workflow as a state machine of steps. Each step (for example a Lambda task) runs within its own limits, and the workflow itself can run for up to a year (Standard workflows).
- Each state can have its own `Retry` and `Catch` rules, so a failed transform is retried without re-running the extract.
- For large datasets, a **Distributed Map** state can process items (for example S3 objects) in parallel child executions.
Example: `Extract` writes files to S3, `Transform` processes them in parallel batches, and `Load` writes to the warehouse; if `Load` fails, only `Load` is retried.
W: Split into per-step functions orchestrated by Step Functions: each step stays under the 15-minute limit, the steps can be retried independently, and the workflow passes state between them as volume grows.
X: A=Increase memory: more memory also adds CPU and can speed the function up, but it does not change the 15-minute cap, so growing data will hit it again.
B=Rewrite in a compiled language: faster code only delays the problem; as volume keeps growing the single function will again exceed 15 minutes.
C=Reserved concurrency: it reserves or caps the number of concurrent executions and has no effect on how long each execution may run.
T: Lambda's 15-minute cap cannot be raised; decompose the job into steps and orchestrate them with Step Functions.

G: ## Lambda limits versus containers on Fargate
- **AWS Lambda** caps each invocation at 15 minutes and 10,240 MB of memory (up to 6 vCPUs). It is ideal for short, event-driven work.
- **AWS Fargate** runs ECS tasks or EKS pods without managing servers. Tasks have no maximum run time, and task sizes go up to 16 vCPU and 120 GB of memory.

- **Fargate Spot** can cut cost for interruptible batch work; **AWS Batch** can also schedule jobs onto Fargate.
Example: a reconciliation task defined with `cpu: 8192` and `memory: 32768` runs for two hours on Fargate, then stops, and billing ends with the task.
W: ECS or EKS on Fargate: it runs containers for hours with up to 120 GB of memory and no servers to manage, which fits a 2-hour, 30 GB batch job that Lambda cannot run.

C=EC2 Spot only because Fargate cannot run long tasks: the premise is false, since Fargate tasks can run indefinitely; EC2 Spot could work but adds instance management and interruption handling.
D=Provisioned concurrency to remove the timeout: provisioned concurrency keeps environments initialized to reduce cold starts; it does not change the 15-minute maximum.
T: Long-running, memory-heavy jobs without server management go to containers on Fargate; Lambda stops at 15 minutes and about 10 GB.

@ Q001209 explain
G: ## Stateless web servers
Auto Scaling adds and removes identical instances at any time. That only works when an instance holds no data that other requests depend on.
- Files written to local disk exist only on that one server; other servers cannot read them and they are lost when the instance is terminated.
- **Amazon S3** stores objects durably across AZs and is reachable from every instance through the S3 API, so any server can write or read any attachment.
- Session state follows the same rule: move it to a shared store such as ElastiCache or DynamoDB.
- Browsers can even upload and download directly using presigned URLs, taking load off the web tier.
Example: instead of saving to `/var/app/uploads/123.pdf`, the application calls `PutObject` to `s3://app-attachments/users/42/123.pdf` and stores that key in the database.
W: Store attachments in S3 via the S3 API: every instance can reach the same durable objects, so no request depends on a particular server and the tier can scale in and out freely.
X: B=Larger local disks: more space does not make files visible to other servers, and the data is still lost when the instance is terminated by scaling.
C=Nightly disk sync: files uploaded during the day are missing on other servers until the next sync, and a terminated instance loses anything not yet copied.
D=Permanent sticky sessions: they hide the problem by pinning users to one server, causing uneven load and lost data or sessions when that server is scaled in or fails.
T: To scale horizontally, move state off the instance: attachments to S3 and sessions to a shared store.

@ Q001210 explain
G: ## Storage options for Fargate tasks
Fargate tasks run on AWS-managed infrastructure, so you never see the host, its AMI or its disks.
- Each task gets **ephemeral storage** (20 GB by default, configurable up to 200 GB) that disappears when the task stops and is private to that task.
- An **EBS volume** can be attached to a Fargate task at launch, but each volume belongs to one task.
- **Amazon EFS** can be declared in the task definition under `volumes` with `efsVolumeConfiguration`, then mounted into containers with `mountPoints`. Every task that mounts it sees the same NFS file system, across AZs, with optional access points and IAM authorization.
Example: ten tasks of the same service mount `fs-0abc` at `/data`; a file written by one task is immediately readable by the others.
W: Mount EFS in the Fargate task definition: EFS is a shared POSIX file system that many concurrent tasks can read and write, matching the application's original shared-filesystem design.
X: A=Instance store shared via a common AMI: Fargate does not expose hosts, AMIs or instance store, and an AMI copies a disk image at launch rather than sharing live data.
B=EBS volume per task: an EBS volume attached to a Fargate task is used only by that task, so each task would see its own separate files.
D=S3 Glacier as a POSIX mount: Glacier storage classes are archival object storage with retrieval delays and cannot be mounted as a shared read-write file system.
T: Shared files for concurrent Fargate tasks means EFS volumes in the task definition; EBS and ephemeral storage are per task.

@ Q001211 explain
G: ## Aurora capacity models
- A **provisioned Aurora cluster** runs on a fixed DB instance class and is billed per hour whether it is busy or idle.
- **Aurora Serverless v2** measures capacity in Aurora Capacity Units (ACUs, each about 2 GiB of memory with matching CPU). You set a minimum and maximum, and capacity adjusts in fine-grained steps within seconds as load changes.
- On supported engine versions, Serverless v2 can be configured with a minimum of `0` ACUs, which pauses an idle instance automatically so you pay only for storage, and it resumes when a connection arrives.
Example: 30 test databases set to `0`-`8` ACUs cost almost nothing overnight, then scale up while engineers run tests during the day.
Multi-AZ replicas and Global Database add availability and cross-Region reach, which non-production environments rarely need.
W: Aurora Serverless v2: it scales capacity down automatically when the environments are idle, and up when tests run, so intermittently used databases are charged mostly for real usage.
X: B=Multi-AZ with two read replicas each: every environment would pay for three always-on instances, which multiplies cost for test systems that do not need high availability.
C=Aurora Global Database per environment: replicating test data to other Regions adds instance, storage and replication cost for no benefit to intermittent testing.
D=Largest provisioned instance class: a fixed large instance bills every hour, including the long idle periods, which is the most expensive way to run intermittent databases.
T: Intermittent, often-idle Aurora databases fit Serverless v2, which scales down (even to zero) when idle; provisioned instances bill around the clock.

@ Q001212 explain
G: ## Caching hot reads
When many requests read the same rows, the database repeats identical work. An **in-memory cache** stores the results so repeat reads skip the database entirely.
- **Amazon ElastiCache** (Valkey, Redis OSS or Memcached) returns cached items in sub-millisecond time.
- The common **cache-aside** (lazy loading) pattern: the application checks the cache; on a miss it reads the database, then writes the result to the cache with a TTL.
- A TTL or explicit invalidation on update keeps catalog data acceptably fresh.
- The database engine and schema stay the same; only the read path in the application changes.
Example: `GET product:1234` hits the cache 95% of the time, so the database handles only 5% of the catalog reads that it handled before.
W: ElastiCache in front of the database: frequently read catalog data is served from memory, which cuts database load and peak latency without changing the database engine.
X: A=A replica per 10% of traffic: read replicas can add capacity, but adding them in lockstep with traffic is costly and each replica still repeats the same queries at disk-based latency.
B=Replace the database with OpenSearch: that changes the data store the requirement says to keep, and OpenSearch is built for search and analytics, not as the system of record.
C=Global Accelerator: it improves the network path from users to application endpoints and does not reduce the number of queries the database must process.
T: Repeated reads of the same data are solved with a cache such as ElastiCache, not more database copies or network tuning.

@ Q001213 explain
G: ## Synchronous chains versus queues
In a synchronous chain, the front end waits for each downstream service. If payment slows, every web request waits too, threads pile up and requests time out.
- **Amazon SQS** puts a durable buffer between producer and consumer. The front end writes an order message and returns right away; workers pull messages at their own pace.
- If a worker fails, the message becomes visible again after the **visibility timeout** and is retried.
- After a set number of receives (`maxReceiveCount`), a message moves to a **dead-letter queue** for investigation instead of blocking the queue.
- Workers can scale on queue depth, so spikes become a backlog rather than errors.
Example: during a sale, 20,000 orders arrive in a minute; the queue holds them while payment workers process 5,000 per minute, and no order is lost.
W: SQS queue with retries and a DLQ: the front end accepts orders immediately, slow downstream services only build a backlog, and failed messages are retried or set aside, so orders are not lost.
X: A=Scale the front end, keep synchronous calls: more front-end instances still wait on the slow payment service, and they can add even more load to it.
B=Bigger payment instance: extra capacity may help briefly, but the front end remains coupled, so any future slowdown still causes timeouts.
D=Longer payment timeout: users wait longer, connections are held longer and failures still occur, which makes behavior under spikes worse.
T: Break a fragile synchronous chain with a queue so producers and consumers can fail and scale independently.

@ Q001214 explain
G: ## Event buses versus topics and queues
**Amazon EventBridge** is a serverless event bus designed as a central router:
- **Rules** match events by content (source, `detail-type`, any field in `detail`, prefixes, numeric ranges) and send them to one or more targets.
- **Schema registry** stores event schemas; schema discovery can infer them from events on a bus and generate code bindings.
- **Partner event sources** deliver events from SaaS providers directly onto a partner event bus.
**Amazon SNS** is pub/sub fan-out. Subscription filter policies can filter on attributes or payload, but SNS has no schema registry and no SaaS partner sources. **SQS** is a queue for one consumer group, and **Step Functions** orchestrates workflow steps.
Example: a rule with pattern `{"source":["orders"],"detail":{"total":[{"numeric":[">",1000]}]}}` sends only high-value orders to a fraud service.
W: Amazon EventBridge: it combines content-based routing rules, a built-in schema registry with discovery, and native SaaS partner event sources, so consumers need no custom routing logic.
X: A=SNS with schema registry and SaaS sources: SNS supports filter policies but has neither a schema registry nor SaaS partner event sources; those are EventBridge features.
B=Step Functions as an event router: Step Functions coordinates steps within a workflow; it does not receive events from many sources and route them to consumers by content.
C=SQS with granular content filtering: SQS consumers receive whatever is in the queue; SQS itself has no content-based routing to multiple consumers.
T: Content-based routing plus a schema registry plus SaaS partner events is EventBridge; SNS is simpler fan-out and SQS is a buffer.

@ Q001994 explain
G: ## Hybrid DNS with Route 53 Resolver
Every VPC has a built-in Route 53 Resolver at the VPC `+2` address. To connect it with on-premises DNS you use Resolver endpoints:
- An **inbound endpoint** gives on-premises DNS servers IP addresses in a VPC to forward queries to, so they can resolve private hosted zones associated with that VPC.
- An **outbound endpoint** plus **forwarding rules** sends queries for a domain such as `corp.example.com` to on-premises DNS servers.
**Centralized pattern:** put both endpoints in one networking VPC that is reachable over Transit Gateway and Direct Connect, associate all private hosted zones (cross-account association is allowed) with that VPC, and share the forwarding rules through **AWS RAM** so every account can associate them with its VPCs. Queries from those VPCs are then forwarded through the central outbound endpoint.
Example: on-premises servers forward `aws.example.internal` to the two inbound endpoint IPs; all 60 VPCs use one shared rule for `corp.example.com`.
W: Central Resolver endpoints with PHZs associated and rules shared via RAM: one pair of endpoints serves all 60 VPCs in both directions, and RAM sharing means new VPCs only need a rule association, not new endpoints.
X: A=BIND on EC2 in every VPC: it means patching, scaling and making highly available dozens of DNS servers, and Route 53 private hosted zones do not support zone transfers to them.
B=Endpoints in every VPC with manual rules: it works but duplicates endpoint cost (each endpoint needs at least two IPs billed hourly) and rule management across 60 VPCs.
C=Make zones public, restrict with security groups: public zones answer anyone on the internet, and security groups cannot control who queries public DNS, so internal names are exposed.
T: For many accounts, centralize Resolver endpoints in one networking VPC and share forwarding rules with RAM instead of building DNS per VPC.

@ Q001995 explain
G: ## Why stateful firewalls need symmetric paths
A stateful firewall tracks each connection. It must see both the request and the reply; a reply arriving at a firewall that never saw the request is dropped.
By default a Transit Gateway keeps traffic in the Availability Zone it came from where possible. For a flow between workloads in AZ-a and AZ-b, the request can enter the inspection VPC in AZ-a while the reply enters in AZ-b, so each firewall sees only half the connection.
- **Appliance mode** on the inspection VPC attachment makes the Transit Gateway pick one network interface, and so one AZ, per flow using a flow hash, and keep both directions on it for the life of the flow.
- It is enabled per VPC attachment (`ApplianceModeSupport=enable`).
Example: after enabling appliance mode, a flow from `10.1.1.10` in AZ-a to `10.2.2.20` in AZ-b is inspected by the same firewall endpoint in both directions.
W: Enable appliance mode on the inspection VPC attachment: it keeps both directions of each flow on the same AZ and firewall endpoint, removing the asymmetric routing that the stateful firewall drops.
X: A=MTU 9001 on attachments: Transit Gateway supports an MTU of up to 8500 bytes for VPC attachments, and MTU problems affect large packets, not cross-AZ flows specifically.
B=Add a third firewall endpoint: more endpoints add capacity, but without appliance mode traffic can still take different AZs in each direction, so asymmetry and drops continue.
D=Replace TGW with full-mesh peering: peering does not scale to many VPCs, is not transitive, and gives up the centralized inspection the design requires.
T: Stateful inspection behind a Transit Gateway across AZs requires appliance mode to keep flows symmetric.

@ Q001996 explain
G: ## Restricting Regions with an SCP
Service control policies set the maximum permissions for accounts in an organization. Region restriction commonly uses a **Deny** statement with the `aws:RequestedRegion` condition key.
- Global services such as IAM, Organizations, CloudFront, Route 53 and Support send their API calls to a single Region endpoint, usually `us-east-1`. A plain "deny outside the approved Regions" would therefore also block them.
- The fix is `NotAction`: deny everything *except* the listed global actions when the requested Region is not approved.
- Because it is a Deny, it applies alongside `FullAWSAccess`, and applies to every principal in the accounts except the management account.
Example (abbreviated; AWS's published example exempts more global services): `"Effect":"Deny","NotAction":["iam:*","organizations:*","cloudfront:*","route53:*","support:*"],"Resource":"*","Condition":{"StringNotEquals":{"aws:RequestedRegion":["eu-west-1","eu-central-1"]}}`
W: Deny SCP with NotAction for global services and aws:RequestedRegion: it blocks all actions requested in other Regions while exempting global services, so IAM, CloudFront and Route 53 keep working across every account.
X: B=Allow-only SCP replacing FullAWSAccess: allowing actions only in the two Regions would block global services whose calls are made to us-east-1, and allow-list maintenance is fragile.
C=Permissions boundaries on every principal: boundaries are set principal by principal, so any role created without one escapes, and they are not an organization-wide guardrail.
D=Deny ec2:* and s3:* outside the Regions: every other service, such as RDS or Lambda, could still create resources in unapproved Regions.
T: Organization-wide Region restriction is a Deny SCP on aws:RequestedRegion with NotAction exemptions for global services.

G: ## Two tag controls in AWS Organizations
- A **tag policy** standardizes a tag key's capitalization and its **allowed values**. With enforcement (`enforced_for`) on resource types such as `ec2:instance` and `ec2:volume`, requests that set a noncompliant value are rejected. On its own, value enforcement does not reliably stop a resource from being created with no tag at all.
- An **SCP** can deny the create API when the tag is missing from the request, using the `Null` condition on `aws:RequestTag/CostCenter`.
Together: the SCP guarantees the tag is present at creation, and the tag policy guarantees the value is from the approved list.
Example: an SCP denies `ec2:RunInstances` and `ec2:CreateVolume` on `instance/*` and `volume/*` resources when `"Null":{"aws:RequestTag/CostCenter":"true"}`, and the tag policy allows only `CC-100`, `CC-200` and `CC-300`.
Cost allocation tags and Cost Explorer only affect billing reports after resources exist.
W: B=SCP denying creation when CostCenter is missing: the Null condition on aws:RequestTag/CostCenter rejects create calls that omit the tag, so untagged instances and volumes cannot be created.
C=Enforced tag policy with allowed values: it defines the CostCenter key and approved values and, when enforced for EC2 instances and volumes, rejects requests that use a value outside the list.
X: A=Activate as a cost allocation tag: activation only makes the tag appear in billing and cost reports; it does not prevent anything from being created.
D=Cost Explorer reports: it shows spending after the fact and relies on manual follow-up, so untagged resources are still created.
E=Config auto-delete after one day: resources are still created untagged, and deleting instances automatically is destructive and after the fact rather than preventive.
T: Enforce tagging at creation time: an SCP ensures the tag exists and a tag policy ensures the value is approved; billing features only report.

G: ## Direct Connect resiliency models
AWS describes several levels of Direct Connect resiliency:
- **Development and test:** one connection at one location; any failure causes an outage.
- **High resiliency:** one connection at each of two locations; survives a location failure but not a second failure.
- **Maximum resiliency:** separate connections terminating on separate AWS devices at more than one location (for example two connections at each of two locations). It survives a device, connection or entire location failure.
A **LAG** bundles ports on the same AWS device, so it adds bandwidth but shares that device's failure. A Site-to-Site VPN backup runs over the internet with lower, variable throughput and latency.
Example: two connections at location A on different AWS devices, plus two at location B, each with its own customer router, with BGP routing traffic around any failed path.
W: Separate connections on separate devices at two or more DX locations: this is the maximum resiliency model, so losing a single device, connection or a whole location still leaves working Direct Connect paths.
X: A=One connection with VPN backup: the VPN runs over the internet with lower bandwidth and variable latency, which is not equivalent protection for a business-critical trading platform.
B=Two connections at one location: separate devices protect against a device failure, but a power or facility outage at that single location takes both connections down.
C=LAG of two ports on one device: all ports sit on one AWS device at one location, so the device or location is a single point of failure.
T: To survive a location failure, Direct Connect must span at least two locations, with separate devices at each for maximum resiliency.

G: ## Aurora Global Database
An **Aurora Global Database** has one primary cluster that accepts writes and up to several read-only secondary clusters in other Regions.
- Replication happens at the storage layer over dedicated infrastructure, with typical lag under one second, so the RPO is usually about a second.
- Secondary clusters serve local reads, so users in `eu-west-1` read from nearby replicas with low latency.
- If the primary Region fails, a **managed failover** or detach-and-promote makes the secondary writable, typically within minutes or less; a planned **switchover** does the same with no data loss.
- Write forwarding can optionally let applications in a secondary Region send writes to the primary.
Example: the `us-east-1` primary fails; the `eu-west-1` secondary is promoted, and the application's writes go to it (automatically when it connects through the global writer endpoint).
W: Aurora Global Database with a secondary in eu-west-1: storage-level replication gives an RPO of about a second, promotion gives an RTO of minutes, and the secondary serves low-latency reads in Europe.
X: B=Cross-Region binlog replica with manual promotion: binlog replication can lag significantly under load, and manual promotion and reconfiguration make seconds of RPO and minutes of RTO hard to guarantee.
C=AWS Backup copies every 15 minutes: the RPO is up to 15 minutes plus copy time, restoring takes much longer than minutes, and it gives no low-latency reads in Europe.
D=Hourly snapshots restored on failure: the RPO is up to an hour and restoring a cluster from a snapshot takes far longer than a few minutes.
T: Seconds of RPO, minutes of RTO and local reads in another Region for Aurora point to Aurora Global Database, not backups or snapshots.

G: ## AWS Elastic Disaster Recovery
**AWS Elastic Disaster Recovery (DRS)** protects physical, virtual and cloud servers, Windows and Linux, by replicating them to AWS continuously.
- An agent on each source server replicates block-level changes to a **staging area** in your AWS account: small, low-cost EC2 replication servers and inexpensive EBS volumes. No full-size recovery instances run in advance.
- Continuous replication gives an RPO measured in seconds, and point-in-time recovery points let you roll back, for example before a ransomware event.
- On failover (or a non-disruptive drill), DRS launches right-sized recovery instances from the latest data, typically within minutes.
Example: 200 servers replicate to a staging subnet; during a site outage, the team launches recovery instances from launch templates and redirects DNS.
W: Elastic Disaster Recovery with a low-cost staging area: continuous block replication meets an RPO of seconds and quick launch meets an RTO of minutes, while only light staging resources run until a failover.
X: A=Hourly DataSync of file shares: it copies files, not entire servers, and hourly runs mean up to an hour of data loss plus manual server rebuilds.
B=Full warm standby on EC2: it can meet the objectives but keeps a scaled-down running copy of 200 servers, which costs far more than a staging area.
C=Nightly AWS Backup: nightly backups mean up to a day of data loss, and restoring 200 servers takes much longer than minutes.
T: Server-level DR with seconds of RPO, minutes of RTO and minimal standby cost is AWS Elastic Disaster Recovery.

G: ## Blue/green deployments for ECS
In a blue/green deployment the new version (green) runs alongside the current one (blue), and traffic moves only after the new version is validated.
- **CodeDeploy blue/green for ECS** creates a replacement task set behind a second target group of the same Application Load Balancer.
- A **test listener** (for example port `8080`) routes to the green tasks while the production listener still serves blue, so automated tests can run against the new version first.
- **Lifecycle hooks** such as `AfterAllowTestTraffic` and `BeforeAllowTraffic` invoke Lambda functions that run tests and can fail the deployment.
- **CloudWatch alarms** attached to the deployment group trigger an automatic rollback, which simply routes production back to the blue target group.
Amazon ECS also now offers native blue/green deployments with similar test traffic and hook features; a rolling update has neither.
W: CodeDeploy blue/green with a test listener, hooks and alarm rollback: tests run on a separate listener before production shifts, and rollback just switches the listener back to the old task set.
X: A=Rolling update with minimumHealthyPercent 100: tasks are replaced gradually behind the same listener, so there is no separate test listener, and rollback means another deployment rather than an instant switch.
C=Replace and restart all tasks at once: there is no in-environment testing before users receive traffic, it risks downtime, and rollback requires redeploying the old version.
D=Manually edited weighted Route 53 records: DNS caching delays weight changes, nothing automates tests or alarm-based rollback, and it requires running two ALBs.
T: Testing a new ECS version on a separate listener before traffic shifts, with alarm-based instant rollback, is a blue/green deployment.
