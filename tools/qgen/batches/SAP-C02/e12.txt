@ Q003048 explain
G: ## Doing the bandwidth math first
Before choosing a transfer method, work out how long the network would take. 500 TB is 500 x 10^12 bytes, or 4 x 10^15 bits. At a perfect 1 Gbps (10^9 bits per second) that is 4,000,000 seconds, about **46 days**, and real links rarely sustain 100% utilization while also carrying normal business traffic.
## Offline transfer with the Snow family
**AWS Snowball Edge** is a rugged device AWS ships to you. You copy data onto it locally over your LAN at high speed, ship it back, and AWS imports the contents into Amazon S3.
- Several devices can be loaded in parallel, so hundreds of terabytes fit into a two-week window.
- Data is encrypted on the device with keys managed in AWS KMS.
- Rule of thumb: when the online transfer time exceeds about a week, compare it with an offline device.
- Availability note: since November 7, 2025, Snowball Edge is available only to existing customers; AWS points new customers to AWS Data Transfer Terminal or partner solutions for physical transfers. The bandwidth reasoning is unchanged.
W: Snowball Edge devices: loading several devices in parallel over the local network and shipping them bypasses the 1 Gbps link entirely, which is the only way to meet a two-week deadline for 500 TB.
X: A=S3 Transfer Acceleration: it routes uploads through CloudFront edge locations to speed up long-distance transfers, but it cannot push more than 1 Gbps out of the company's own link, so the 46-day floor remains.
B=Site-to-Site VPN copies: a VPN runs over the same internet link, and each tunnel also has its own throughput limit and encryption overhead, so it is no faster than the raw 1 Gbps.
D=DataSync over the internet: DataSync is efficient and verifies data, but it is still bound by the available bandwidth, so it would also need well over a month.
T: When bandwidth math says the network needs longer than the deadline, no online service helps; ship the data offline with Snowball Edge.

@ Q003049 explain
G: ## What AWS DataSync does
**AWS DataSync** is a managed service for moving and synchronizing file and object data between on-premises storage and AWS storage services such as Amazon S3, Amazon EFS and Amazon FSx.
- An **agent** (a VM deployed on premises) reads from the source, for example an NFS or SMB share.
- A **task** defines source, destination, filters and a schedule, for example every hour during the migration.
- Each run copies only changed files and can **verify** data integrity by comparing checksums after transfer.
## Example
A company points a DataSync task at its NFS export `/exports/projects` and at an EFS file system, schedules it hourly, and at cutover runs a final incremental sync before switching the application to EFS.
W: AWS DataSync: it natively supports NFS sources and EFS destinations, runs repeated incremental syncs on a schedule, and performs integrity verification, which matches every requirement.
X: B=Kinesis Firehose: Firehose delivers streaming records to destinations such as S3 or OpenSearch; it does not read files from an NFS share or keep a file system in sync.
C=AWS Snowcone: Snowcone was a small offline device for one-time or edge transfers (discontinued in November 2024); shipping a device cannot provide continuous replication during a migration.
D=AWS Backup Gateway: Backup Gateway lets AWS Backup protect on-premises virtual machines such as VMware VMs; it does not replicate NFS file shares to EFS.
T: Continuous, scheduled, verified file-share sync into EFS is DataSync; streaming, offline and backup services solve different problems.

@ Q003051 explain
G: ## The strangler fig pattern
Named after a vine that gradually grows around a tree, the **strangler fig pattern** replaces a monolith piece by piece instead of all at once.
- A routing layer sits in front of the application, such as an Application Load Balancer, Amazon API Gateway or a proxy.
- One capability at a time is rebuilt as a new service, and the router sends just its paths there, for example `/orders/*` to the new orders service, while everything else still goes to the monolith.
- Users keep one entry point and notice nothing; if the new service misbehaves, the route can be switched back.
- Over time the monolith shrinks until it can be retired.
W: Strangler fig pattern: path-based routing behind one entry point lets the team move one capability at a time with a fast rollback, so the decomposition is gradual and users are not disrupted.
X: A=Two-year feature freeze: stopping all feature work for years hurts the business and still ends in one risky switchover of the rebuilt system.
B=Big-bang rewrite: replacing everything in one weekend concentrates all risk into a single cutover with no incremental validation, the opposite of "gradually without disruption".
C=Duplicate monoliths per feature: copying the monolith multiplies code, data and operating cost and splits users across inconsistent versions instead of decomposing anything.
T: Decompose a live monolith incrementally by routing selected paths to new services behind the same front door, never with a big-bang rewrite.

@ Q003052 explain
G: ## Replatforming a database
After a rehost ("lift and shift"), a common next step is a **replatform** ("lift, tinker and shift"): keep the same engine but let AWS manage it.
- **Amazon RDS for MySQL** runs community MySQL; AWS handles provisioning, patching, automated backups, point-in-time recovery and Multi-AZ failover.
- **Amazon Aurora MySQL-Compatible Edition** is wire-compatible with MySQL, with storage replicated six ways across three Availability Zones and fast read replicas.
- Applications usually only change their connection endpoint, because the SQL dialect, drivers and tools stay the same.
- Migration can use native dump or replication, or AWS DMS for minimal downtime.
W: RDS for MySQL or Aurora MySQL: both keep MySQL compatibility, so code changes are minimal, while backups, patching and high availability move to AWS.
X: A=Amazon Neptune: Neptune is a graph database queried with Gremlin, openCypher or SPARQL; moving relational MySQL data into a graph model means redesigning the schema and queries.
C=Amazon Redshift: Redshift is a columnar data warehouse built for analytics, not for the transactional workload of an application's MySQL database.
D=Amazon DynamoDB: DynamoDB is a key-value and document store with a different API and data model, so the application would need a substantial rewrite.
T: For "managed service with minimal changes", stay on the same engine family (RDS or Aurora MySQL) rather than switching to a different database type.

@ Q003053 explain
G: ## Hybrid connectivity for a long migration
During a multi-year hybrid period, on-premises systems call AWS services all day, so the link must be private, predictable and resilient.
- **AWS Direct Connect** is a dedicated private connection from your network into AWS. It avoids the public internet, so latency and throughput are consistent.
- **Redundancy**: AWS recommends at least two connections, ideally at two Direct Connect locations, so one fiber cut or device failure does not cut off AWS.
- **AWS Transit Gateway** is a regional hub. Attach many VPCs to it, and connect it to Direct Connect through a Direct Connect gateway and a transit virtual interface, so every VPC is reachable over the same links.
## Example
Two 10 Gbps connections at different locations feed a Direct Connect gateway, which is associated with a transit gateway attached to 30 application VPCs.
W: Redundant Direct Connect with a transit gateway: dedicated links give consistent low latency, redundancy removes the single point of failure, and the transit gateway lets the same links reach all VPCs.
X: A=Nightly S3 exports: batch files copied once a day cannot support live application-to-application calls and add up to a day of data staleness.
B=Single VPN to one VPC: a VPN rides the internet, so latency varies, one connection is a single point of failure, and reaching only one VPC does not serve many new services.
C=Public internet with app encryption: encryption protects the data but does nothing for latency consistency, and every service would need to be exposed publicly.
T: Consistent, private hybrid connectivity at scale is redundant Direct Connect into a transit gateway hub; internet-based options cannot guarantee latency.

G: ## Paying only while the job runs
A job that runs 20 minutes each hour on an always-on instance leaves the server idle about two thirds of the time, yet you pay for all 24 hours and must still patch the OS.
## Scheduled serverless containers
- **AWS Batch on AWS Fargate** runs containerized jobs without managing servers; Batch handles queuing, retries and job definitions.
- **Amazon EventBridge Scheduler** (or an EventBridge rule) can start the job, or start an Amazon ECS task on Fargate, on a schedule such as `rate(1 hour)`.
- You pay for the vCPU and memory only while the task runs, and there is no instance to patch.
## Example
Package the job in a container image, store it in Amazon ECR, and have EventBridge Scheduler submit it hourly; about 8 hours of compute per day are billed instead of 24.
W: Scheduled Batch or container task on Fargate: capacity exists only while the job runs, removing idle cost and server management, and the scheduler replaces the always-on host.
X: B=Manual runs from a laptop: depends on a person being available every hour, has no retries or audit trail, and puts production execution on an unmanaged device.
C=Reserved Instance: a reservation lowers the hourly rate but still pays for the roughly 40 idle minutes each hour and keeps all server operations.
D=Larger always-on instance: a bigger instance costs more per hour and is still idle most of the time, so cost rises rather than falls.
T: For periodic jobs, remove the idle server with scheduled serverless compute; discounts on an always-on instance still pay for idle time.

@ Q003055 explain
G: ## Why .NET Framework drives licensing costs
Classic **.NET Framework** runs only on Windows, so every server needs a Windows Server license, often plus SQL Server. Modern **.NET** (formerly .NET Core, now .NET 8 and later) is cross-platform and runs on Linux.
## Porting path
- Assess the code to find incompatible APIs and packages, such as WCF server or Web Forms dependencies.
- Convert projects to modern .NET; **AWS Transform for .NET** uses AI agents to analyze and port .NET Framework applications to cross-platform .NET.
- Package the result in **Linux containers** and run it on Amazon ECS or EKS, often on Fargate.
- Port one application or component at a time, so modernization stays gradual.
W: Port to .NET on Linux containers: removing the Windows dependency eliminates the Windows license cost, and AWS tooling assesses and converts the code incrementally instead of forcing a rewrite.
X: A=Rewrite in a new language first: a full rewrite before any migration is slow and high risk and delays all savings; porting within .NET keeps the existing code and skills.
B=Dedicated Hosts to share licenses: Dedicated Hosts let you bring your own eligible licenses to physical servers dedicated to you; they do not let you share licenses with other customers and still require Windows.
D=Buy more licenses: this increases licensing spend, the opposite of the goal, and does nothing to modernize.
T: The way out of Windows licensing for .NET Framework apps is porting to modern .NET on Linux, not rearranging where Windows licenses run.

G: ## Managed brokers versus AWS-native messaging
**Amazon MQ** is a managed message broker service for **Apache ActiveMQ** and **RabbitMQ**. AWS provisions the broker, patches it and can run an active/standby pair across Availability Zones.
- Because it runs the same broker engines, existing clients keep working using standard APIs and protocols such as JMS, OpenWire, AMQP, STOMP, MQTT and WebSocket.
- Migration usually means changing the broker endpoint and credentials in configuration, not rewriting producers and consumers.
## AWS-native alternatives
Amazon SQS, Amazon SNS and Amazon Kinesis are highly scalable, but each has its own AWS API. Using them means changing application code, which is a refactor rather than a replacement of the broker.
W: Amazon MQ: it runs managed ActiveMQ, so existing clients and protocols work unchanged while AWS takes over broker operations.
X: B=Amazon Kinesis: Kinesis Data Streams is a streaming service with shards and its own SDK calls; ActiveMQ clients cannot talk to it without a rewrite.
C=Amazon SNS: SNS is push-based pub/sub through the AWS API; it does not speak OpenWire or JMS, so clients would have to be changed.
D=Amazon SQS: SQS is a queue service with its own API; moving to it requires client code changes, which the company wants to avoid.
T: To keep existing ActiveMQ or RabbitMQ clients, choose Amazon MQ; SQS, SNS and Kinesis are native services that require code changes.

@ Q003057 explain
G: ## The 7 Rs of migration
Every application in a portfolio is assigned one strategy:
- **Retire**: decommission it, because it is no longer used or needed.
- **Retain**: leave it where it is for now.
- **Rehost**: lift and shift the servers as they are.
- **Relocate**: move a whole platform, such as VMware, without changing it.
- **Replatform**: make small optimizations, such as moving to a managed database.
- **Repurchase**: switch to a SaaS product.
- **Refactor**: re-architect for cloud-native features.
## Why retiring matters
Discovery often finds applications nobody uses. Migrating them still costs effort, licenses and running costs. Retiring them (after archiving any data that must be kept for compliance) shrinks the scope of the migration.
W: Retire: an application with no users and no business value should be decommissioned, not moved, saving migration effort and future running costs.
X: A=Relocate: moves the hosting platform, for example VMware VMs to a VMware environment on AWS, which still carries an unused system forward.
B=Rehost: lifts the servers into AWS unchanged, so the company keeps paying to run something nobody uses.
D=Refactor: is the most expensive strategy, re-architecting code, which is the worst possible investment for an application with no value.
T: Unused, valueless applications are retired; every other R spends money moving or rebuilding something nobody needs.

@ Q003059 explain
G: ## How a DMS migration runs
AWS Database Migration Service (DMS) typically runs a **full load** that copies existing data, followed by **change data capture (CDC)** that reads the source's transaction log and applies ongoing changes to the target.
- While CDC runs, the source stays live and the target keeps catching up, so the lag stays small.
- **DMS data validation** compares rows between source and target after the full load and during CDC and reports mismatches in table statistics.
## A low-risk cutover
- Let full load finish and CDC catch up.
- Check validation results and fix any mismatches.
- Stop writes to the source, let CDC drain the last changes, point the application at the target.
- Keep the source intact until the new system is proven, so a rollback remains possible.
W: D=DMS data validation: it proves that source and target data match before the switch, catching missing or altered rows while there is still time to fix them.
E=Keep CDC running: ongoing replication keeps the target in sync until the application switches over, so the final cutover window is only minutes.
X: A=Stop the source before full load: this turns the migration into a long offline copy, adding downtime instead of reducing risk, and makes CDC pointless.
B=Delete the source after full load: it removes the rollback path and loses any changes written after the full load finished.
C=Skip testing: cutting testing to go faster is how data loss and application errors reach production undetected.
T: Low-risk DMS cutovers combine continuous CDC with data validation and keep the source for rollback, rather than stopping or deleting it early.

@ Q003060 explain
G: ## Picking file storage by protocol
File shares are defined by the protocol clients use to mount them.
- **SMB** is the native Windows file protocol, with NTFS permissions and Active Directory identities.
- **NFS** is the usual protocol for Linux and Unix clients.
## Amazon FSx for Windows File Server
It is a fully managed Windows file system built on Windows Server.
- Serves shares over SMB, supports NTFS ACLs, DFS namespaces and shadow copies.
- Joins your self-managed Active Directory or AWS Managed Microsoft AD, so users authenticate with their existing domain accounts.
- Can be deployed Multi-AZ for high availability.
## Example
An application server maps `\\fs-share.corp.example.com\finance` just as it did on premises, and existing AD groups control who can read and write.
W: FSx for Windows File Server: it provides native SMB shares with Active Directory integration, so Windows applications and permissions work without changes.
X: A=Amazon EFS: EFS is accessed over NFS and uses POSIX permissions, and it is not supported as a file share for Windows clients.
C=Amazon S3: S3 is object storage accessed through an HTTPS API, not an SMB file share joined to Active Directory.
D=EBS io2 Block Express: EBS provides block volumes attached to instances, not a shared network file system with AD-based access control.
T: Windows plus SMB plus Active Directory points to FSx for Windows File Server; EFS is NFS for Linux, S3 is objects and EBS is blocks.

@ Q003061 explain
G: ## Separating transactions from analytics
An **OLTP** database serves many small, fast reads and writes for the application. Heavy **reporting** queries scan and aggregate large amounts of data, holding CPU, memory and I/O and slowing down transactions.
## Change streaming into an analytics store
- Capture changes from the transactional database, for example with AWS DMS CDC or Aurora zero-ETL integration with Amazon Redshift.
- Land them in a store built for analytics, such as Amazon Redshift or an S3 data lake queried with Amazon Athena.
- Point the reporting feature at that store, which also makes reporting a separate component that can evolve independently of the monolith.
## Result
Transactions no longer compete with reports, and reports run on columnar storage designed for large scans.
W: Stream changes to an analytics store: moving reporting onto its own data store removes contention on the production database and splits a capability out of the monolith, improving performance and architecture together.
X: A=Report during business hours: this runs heavy queries exactly when transaction load peaks, which increases contention rather than reducing it.
B=Index every table: extra indexes slow every write and consume storage, and large aggregations still compete with transactions on the same database.
C=Bigger database instance: scaling up buys temporary headroom at higher cost but keeps both workloads on one database and changes nothing about the architecture.
T: Move heavy reporting off the transactional database by streaming changes to a purpose-built analytics store, instead of tuning or scaling the shared database.

G: ## What a migration wave is
Large migrations are split into **waves**: groups of applications and servers that move together in one scheduled window.
## How waves are ordered
- **Dependencies**: applications that call each other frequently or share a database should move together, or be sequenced so hybrid latency is acceptable. Dependency mapping from discovery tools shows these links.
- **Criticality and risk**: early waves usually hold less critical, simpler applications to build skills and prove the process; business-critical systems follow once the team is experienced and has tested rollback plans.
- Other inputs: blackout periods, team availability and licensing or contract dates.
## Example
A reporting tool that reads the ERP database moves in the same wave as the ERP, while an internal wiki with no dependencies goes in an early pilot wave.
W: A=Business criticality and risk tolerance: they decide which applications are safe for early learning waves and which need proven processes and tested rollback first.
E=Dependencies and shared data: they decide which components must move together so that calls and shared data do not break or suffer hybrid latency.
X: B=Project board colors: have no relationship to technical coupling or business risk, so they cannot guide sequencing.
C=Alphabetical order: is arbitrary and would split tightly coupled applications into different waves.
D=Letters in server names: carry no information about dependencies, criticality or readiness.
T: Waves are ordered by what must move together (dependencies) and how much risk the business can take (criticality), never by arbitrary labels.

@ Q003063 explain
G: ## Alarm fatigue
When a team receives hundreds of alarms a day, people start ignoring them and real incidents are missed. The fix is fewer, more meaningful alarms.
## CloudWatch tools that reduce noise
- **Anomaly detection** learns a metric's normal pattern, including daily and weekly cycles, and alarms only when values leave the expected band, instead of on a fixed threshold that brief spikes cross.
- **Composite alarms** combine several alarms with rules such as `ALARM(HighLatency) AND ALARM(HighErrorRate)`, so one notification fires only when the combination indicates real impact. Child alarms can be set to take no action.
- Setting **datapoints to alarm**, for example 3 out of 5, also filters out one-off spikes.
## Routing actionable alarms
Actionable alarms can start an incident in **AWS Systems Manager Incident Manager**, which engages on-call responders, escalates and tracks response plans. Since November 7, 2025, Incident Manager is no longer open to new customers; AWS suggests Systems Manager OpsCenter for managing operational issues, but the principle of routing only actionable alarms is the same.
W: Composite alarms, anomaly detection and Incident Manager: noise from transient spikes is filtered out, and only real, actionable problems page the right responders through a structured incident process.
X: A=Larger distribution list: sends the same noise to more people, which spreads alarm fatigue rather than removing it.
B=Lower thresholds: produces even more alarms for normal variation, making real incidents harder to spot.
D=Delete all alarms: gives up detection completely, so customers find outages first and response time gets worse.
T: Fix alarm fatigue by making alarms smarter (anomaly detection, composite logic) and routing only actionable ones to incident response, not by sending more or fewer emails.

G: ## Configuration drift
When environments are built by hand, small differences creep in: a security group rule, a parameter value, an instance type. Code that works in staging then fails in production. This is **configuration drift**.
## Infrastructure as code
With **infrastructure as code (IaC)** such as AWS CloudFormation, AWS CDK or Terraform, one template describes the environment.
- Staging and production are deployed from the **same template**; intended differences, such as instance size or domain name, are **parameters** like `Env=staging`.
- Changes go through version control and review, and the pipeline deploys them to staging first, then production.
- CloudFormation **drift detection** reports resources that were later changed by hand.
W: Same IaC templates with parameters: both environments are generated from one reviewed definition, so unintended differences disappear and only explicit parameter differences remain.
X: A=More manual testing in production: finds problems only after users are affected and does not stop the environments from diverging.
C=Wiki of differences: documentation relies on people reading and applying it by hand, which is the same manual process that caused the drift.
D=Deploy less often: fewer releases batch more changes together, making each deployment riskier, while the environments still differ.
T: Remove the root cause of environment differences by building every environment from the same parameterized IaC, not by adding manual checks.

G: ## What API keys are for in API Gateway
In Amazon API Gateway, **API keys** identify a client for **usage plans**: throttling and quotas per customer. AWS states that API keys should not be used for authentication or authorization, because a key is a static shared string that is easily copied and does not identify a user.
## Real authentication options
- **Amazon Cognito user pool authorizer**: clients sign in and send a JWT; API Gateway validates the token before calling the backend.
- **Lambda authorizer**: your function validates a token, such as an OAuth token from an external identity provider, and returns an IAM policy that allows or denies the call.
- **IAM authorization**: callers sign requests with SigV4 using AWS credentials.
## Combining them
Keep the API keys attached to usage plans for metering and throttling, and add an authorizer to prove who the caller is.
W: Cognito user pool or Lambda authorizer: they verify caller identity with signed tokens or custom logic, while API keys continue to serve their intended purpose of usage plans.
X: A=Weekly key rotation by email: rotated keys are still shared secrets, not identity proof, and emailing them spreads them further.
B=Keys in the query string: URLs are logged by proxies and servers and kept in browser history, which makes keys easier to leak, not safer.
C=Higher throttling limits: raising limits lets an attacker with a stolen key make more calls, and throttling is not authentication either way.
T: API keys meter and throttle clients; authentication needs an authorizer such as Cognito, Lambda or IAM.

G: ## Removing plaintext passwords
Passwords in configuration files are readable by anyone who can read the disk, backups or images, and changing them means editing files on every instance.
## AWS Secrets Manager
- Stores secrets encrypted with AWS KMS.
- Access is controlled by IAM: the EC2 **instance role** gets `secretsmanager:GetSecretValue` on one secret ARN, so no credentials are stored on the instance.
- **Rotation** can be automatic on a schedule; for Amazon RDS and Aurora, AWS provides rotation functions or managed rotation.
## Minimal code change
At startup the application, or a small wrapper script, calls `GetSecretValue` through the AWS SDK or CLI and passes the value where the config file was used before. Caching clients reduce calls and pick up rotated values.
W: Secrets Manager via the instance role: the password leaves the file system, access is governed by IAM, rotation is built in, and the application only needs a small change to fetch the secret at startup.
X: A=Passwords in source code: exposes them to everyone with repository access and in the history forever, and every rotation would require a new build and deploy.
C=Encrypted file with a nearby password: the decryption password sits next to the file, so anyone who can read one can read both, which gives no real protection.
D=EC2 user data: user data is readable from the instance metadata service and the console by anyone with access, and it offers no rotation.
T: Put secrets in Secrets Manager and read them with the instance role; moving plaintext to code, user data or a co-located key is not protection.

G: ## What a cold start is
When a Lambda function is invoked and no initialized execution environment is available, Lambda must create one: download the code, start the runtime and run your initialization code outside the handler. This **cold start** adds latency, typically from under a second up to several seconds for large packages, and happens most after idle periods when environments were reclaimed.
## Provisioned concurrency
- You configure a number of pre-initialized environments on a function version or alias, for example 20 on alias `live`.
- Requests up to that number are served by warm environments with consistent latency.
- Application Auto Scaling can adjust the number on a schedule or by utilization.
- You pay for the configured concurrency while it is enabled.
Lambda SnapStart is another option for supported runtimes, but provisioned concurrency is the general answer for consistent latency.
W: Provisioned concurrency: environments are initialized ahead of time and kept ready, so the first requests after idle periods no longer pay the cold-start penalty.

G: ## Why small files are slow on shared storage
Amazon EFS is a network file system: each file open, metadata lookup and read is a round trip to the service. Reading many small files is dominated by per-operation latency rather than bandwidth, and under heavy load throughput limits can add queuing.
## EFS throughput modes
- **Bursting**: throughput scales with the amount of data stored and relies on burst credits, which can run out.
- **Provisioned**: you pay for a fixed throughput level.
- **Elastic**: throughput scales automatically with the workload, up to high limits, and you pay for what you use; AWS recommends it for spiky or unpredictable workloads.
## Caching hot files
Keeping frequently read small files close to the application, for example in an in-memory cache such as Amazon ElastiCache, on local instance storage, or behind Amazon CloudFront for static web assets, removes most network round trips.
W: Elastic throughput plus caching: elastic throughput removes throughput ceilings under load, and caching hot small files avoids repeated per-file round trips to EFS, which is the main source of the latency.
X: A=Infrequent Access only: IA is a lower-cost class for rarely read data; its reads have higher latency and per-GB access charges, so hot files get slower and more expensive.
B=Separate EBS volumes: each instance would get its own copy, so the fleet loses the shared file system and must keep copies in sync on every change.
C=Fewer instances: reduces the application's capacity to serve users, trading one performance problem for another instead of fixing file access.
T: For slow small-file reads on EFS, remove throughput ceilings with elastic throughput and cut round trips with caching, rather than moving to slower classes or giving up shared storage.

G: ## Distance is the write latency
A DynamoDB table lives in one Region. A write from Europe to `us-east-1` must cross the Atlantic and back, adding tens of milliseconds or more per request no matter how much capacity the table has.
## DynamoDB global tables
- A **global table** keeps replicas of the same table in several Regions, for example `us-east-1` and `eu-west-1`.
- Every replica accepts reads and writes, so European users write to the nearby Region with local latency.
- By default, changes replicate asynchronously to the other replicas, usually within a second, and conflicts are resolved with last writer wins; a multi-Region strong consistency mode is also available for workloads that need it.
- An existing table can be converted by adding a replica Region.
W: Global table with a European replica: users write to a replica in their own Region, removing the cross-ocean round trip that causes the slow writes.
X: A=DAX in us-east-1: DAX is an in-memory cache that speeds up reads; writes still go through to DynamoDB, and a cluster in us-east-1 is still far from Europe.
B=More write capacity: capacity helps with throttling, not with network distance, so each European write still takes the same round-trip time.
D=DynamoDB Streams: Streams emit a change log after writes happen; they do not accept writes or move the write endpoint closer to users.
T: Cross-Region write latency is solved by writing locally to a global table replica, not by caching, capacity or streams in the distant Region.

G: ## Finding single-AZ dependencies
An Availability Zone can have problems while others stay healthy. An architecture survives this only if **every layer** has capacity in more than one AZ.
## Two common hidden single points of failure
- **Single-AZ RDS**: the database runs in one AZ. With **Multi-AZ**, RDS keeps a synchronous standby in another AZ and fails over automatically, usually within a couple of minutes, and the DNS endpoint follows.
- **One zonal NAT gateway**: a zonal NAT gateway lives in one public subnet in one AZ. If private subnets in all AZs route `0.0.0.0/0` to it, an issue in that AZ breaks outbound internet access for the whole application. The classic fix is one zonal NAT gateway per AZ, with each AZ's private route table pointing to its local NAT gateway. AWS also offers a **regional NAT gateway** that automatically expands into each AZ where you have workloads, achieving the same per-AZ redundancy with one resource.
W: C=Convert the database to Multi-AZ: a synchronous standby in another AZ takes over automatically when the primary's AZ fails, removing the database as a single-AZ dependency.
E=NAT gateway in each AZ: each AZ routes outbound traffic through its own NAT gateway, so losing one AZ does not cut off egress for instances in the others.
X: A=Performance Insights: helps analyze database load and slow queries but adds no redundancy.
B=Larger instance: more CPU and memory in the same AZ still fails when that AZ has problems.
D=More subnets in the same AZ: every new subnet shares the same AZ, so the failure domain does not change.
T: AZ resilience comes from redundancy in another AZ at every layer (Multi-AZ databases, per-AZ NAT gateways), not from monitoring or bigger resources in one AZ.
