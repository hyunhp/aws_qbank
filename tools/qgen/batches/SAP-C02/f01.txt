# SAP-C02 fixes for reported question flaws (full replacement blocks pinned with I:)

@ SAP-C02 D1 T1.2 applied troubleshooting
S: After adding a new NACL rule to explicitly allow inbound traffic on port 443, a web application in a private subnet still cannot receive responses to outbound HTTPS requests it initiates to an external API. The security group only has an outbound allow-all rule and no inbound rules. What is the most likely issue?
A: The private subnet's route table is missing a route to the internet gateway for response traffic
B: KMS encryption on the instance's EBS volume is blocking the HTTPS response
C: Stateless NACL inbound rules do not allow the ephemeral ports that return traffic arrives on
D: The security group needs an explicit rule for response traffic, since security groups are stateless
K: C
G: ## Stateful security groups, stateless NACLs
A **security group** is stateful: when an instance opens a connection, the reply is allowed back automatically, whatever the inbound rules say.
A **network ACL** is stateless: it checks every packet against its rules in each direction separately and remembers nothing about connections.
## Which ports a client connection uses
When the instance calls an external API over HTTPS, it sends from a random **ephemeral port** (for Linux about `32768-60999`, commonly allowed as `1024-65535`) to destination port `443`.
- Request: leaves the subnet **outbound**, destination port `443`.
- Response: comes back **inbound**, source port `443`, destination port = the instance's ephemeral port.
So the NACL needs an outbound rule for `443` and an **inbound** rule for the ephemeral range. An inbound rule for port `443` only helps when the instance is the server, which it is not here.
W: NACL inbound ephemeral ports: the responses arrive inbound on a high ephemeral port, not on 443. Because the NACL is stateless and has no inbound allow rule for `1024-65535`, the default deny drops every reply even though the request left successfully.
X: A=Internet gateway route: a private subnet reaches the internet through a NAT gateway, and a missing route would stop the requests from leaving at all. Adding an internet gateway route would also turn the subnet into a public one.
B=EBS encryption: KMS encryption of the volume protects data at rest on disk and has no effect on network packets entering or leaving the instance.
D=Stateless security groups: security groups are stateful, so replies to connections the instance opened are allowed back automatically without any inbound rule.
T: For connections a subnet initiates, the NACL must allow the ephemeral port range inbound for the replies; allowing the service port inbound does not help.
V: VPC, Network ACL, Security Groups

@ SAP-C02 D1 T1.1 advanced tradeoff
S: A financial services firm needs the highest availability among these options for its hybrid connection between on-premises data centers and AWS, with automatic failover and no dependence on a single Direct Connect location. Which architecture best meets this requirement while balancing cost?
A: One Direct Connect connection at one location with a Site-to-Site VPN over the internet as backup
B: Two Direct Connect connections at the same Direct Connect location, terminating on separate customer routers
C: One DX connection at each of two DX locations, joined through a DX gateway, plus a Site-to-Site VPN backup
D: Site-to-Site VPN only, using both tunnels of two VPN connections that end on separate customer gateways
K: C
G: ## Direct Connect resiliency models
AWS Direct Connect (DX) is a private physical link from your network to AWS at a **DX location** (a colocation facility). Each connection ends on one AWS device at one location, so the connection, the device or the whole location can fail.
The Direct Connect Resiliency Toolkit describes these models:
- **Development and test**: one connection at one location, no redundancy.
- **High resiliency**: one connection at each of two locations, which survives the loss of a whole location.
- **Maximum resiliency**: two connections on separate devices at each of two locations. This is the model AWS ties to its highest availability target (99.99%); high resiliency is associated with 99.9%.
BGP runs over every virtual interface, so when a path fails its routes are withdrawn and traffic moves to a surviving path automatically. A Site-to-Site VPN adds an inexpensive extra path over the internet.
Example: connections at a DX location in one metro area and another in a second metro area keep traffic flowing when a power failure takes down the first facility.
W: Two DX locations plus VPN: this is the only choice whose Direct Connect paths do not share a single location, so it survives a connection, device or location failure with automatic BGP failover, and the VPN is a cheap further path. It follows the high resiliency model; a stricter 99.99% target would call for maximum resiliency with two connections at each location.
X: A=One DX plus VPN: the single connection and single location remain points of failure for the private path, and failing over to an internet VPN gives lower, variable bandwidth and latency.
B=Two connections at one location: separate customer routers help, but a fire, power or fiber problem at that one facility takes both connections down together.
D=VPN only: every path depends on the public internet, whose latency and throughput AWS does not control, so it cannot give the consistent performance or availability of dedicated connections.
T: For resilient Direct Connect, spread connections across at least two DX locations; the highest SLA needs two connections at each of two locations.
V: Direct Connect, Site-to-Site VPN, Direct Connect Gateway

@ SAP-C02 D2 T2.1 advanced comparison
S: An ECS service needs a database password injected at container start. The password must rotate every 30 days without redeploying tasks, each access must be auditable, and only this service's task execution role may read it. Which design meets these requirements?
A: A rotating Secrets Manager secret referenced in the task definition
B: An environment variable in the task definition
C: A Parameter Store Standard parameter referenced in the task definition, rotated by a scheduled Lambda
D: An SSE-S3 encrypted S3 object downloaded by the container at startup with the task role
K: A
G: ## Injecting secrets into ECS tasks
A container definition can list a secret in its `secrets` section by the ARN of an AWS Secrets Manager secret or a Systems Manager Parameter Store parameter. When the task starts, ECS reads the value using the **task execution role** (the role ECS itself uses to pull images and fetch secrets) and exposes it as an environment variable. The **task role** is the role the application code uses to call AWS APIs, so it is not the one that needs `secretsmanager:GetSecretValue` here.
## Why Secrets Manager fits rotation
- **Rotation**: Secrets Manager rotates on a schedule, such as every 30 days, with a rotation Lambda function; for Amazon RDS it supplies ready-made rotation functions or managed rotation that change the password on the database and in the secret together.
- **Access control**: IAM permissions plus a resource policy on the secret can limit reading to one execution role.
- **Audit**: every `GetSecretValue` call is logged in CloudTrail.
New tasks read the current value when they start; running tasks keep the old value, so use alternating-users rotation or have the app re-read the secret.
W: Rotating Secrets Manager secret: the task definition only references the secret ARN, so rotation never requires a new revision; built-in RDS rotation, a policy that lets only this service's execution role read it, and CloudTrail logging of each read cover every requirement.
X: B=Plain environment variable: the password sits in clear text in the task definition, visible to anyone who can describe it, and changing it means registering a new revision and redeploying.
C=Parameter Store with a custom Lambda: Standard parameters have no built-in rotation, so the team must write and maintain code that changes the database password and the parameter in step, which Secrets Manager already provides.
D=SSE-S3 object: S3 manages the SSE-S3 keys, so encryption adds no access control beyond bucket permissions; there is no rotation mechanism and the container needs custom download code.
T: Reference a rotating Secrets Manager secret from the task definition and grant read access only to that service's task execution role.
V: AWS Secrets Manager, Amazon ECS

@ SAP-C02 D3 T3.1 applied comparison
S: A company runs a stateless containerized API on Amazon ECS and requires zero-downtime deployments plus the ability to instantly revert to the previous version if error rates spike after a release, without waiting to redeploy the old task definition. Which ECS deployment approach best satisfies this?
A: ECS rolling update with minimumHealthyPercent 100 and maximumPercent 200
B: Replace task definitions one at a time manually in the ECS console
C: CodeDeploy blue/green for ECS with two target groups
D: ECS rolling update with the deployment circuit breaker and automatic rollback enabled
K: C
G: ## Rolling versus blue/green on ECS
A **rolling update** replaces old tasks with new ones in place. `minimumHealthyPercent` and `maximumPercent` control how many tasks may be stopped or added at a time, so the service stays up, but once old tasks are stopped they are gone. Rolling back means starting a new deployment of the previous task definition and waiting for those tasks to launch and pass health checks.
A **blue/green deployment** starts a complete replacement task set (green) next to the running one (blue). The load balancer uses two target groups: production traffic moves from blue to green, and blue keeps running for a wait period. If alarms fire, traffic is pointed back to blue in seconds, with no tasks to start.
## Ways to run blue/green on ECS
- AWS CodeDeploy with the `CODE_DEPLOY` deployment controller, using two target groups and optional CloudWatch alarms for automatic rollback.
- Since 2025, ECS also offers native blue/green deployments with a bake time, which follow the same idea.
W: CodeDeploy blue/green: the new version runs in a separate task set behind the second target group while the original task set stays up, so a spike in errors is fixed by shifting the listener back to the old tasks immediately.
X: A=Rolling update 100/200: capacity never drops during the rollout, but the old tasks are stopped as new ones become healthy, so reverting requires deploying the old task definition again.
B=Manual console replacement: replacing tasks by hand is slow and error-prone, risks downtime, and gives no quick way back to the previous version.
D=Circuit breaker rollback: the circuit breaker detects failed deployments and rolls back automatically, but it does so by launching tasks from the last completed deployment again, which is the redeploy wait the company wants to avoid.
T: Instant rollback needs the old version still running behind the load balancer, which blue/green provides and rolling updates do not.
V: ECS, CodeDeploy, Elastic Load Balancing

@ SAP-C02 D3 T3.5 advanced troubleshooting
S: A cost optimization review flags a db.t3.medium RDS instance as a top contributor to a recent cost spike. Its CPU credit balance is exhausted every night while batch jobs run near full CPU for hours, and the instance accrues large surplus CPU credit charges despite appearing 'small.' What does this indicate, and what is the appropriate action?
A: Buy a Reserved Instance for the current db.t3.medium size to lower its hourly cost
B: It is undersized; move to a non-burstable or larger class, which may cost less overall
C: The instance is underutilized and should be downsized to db.t3.small
D: Switch the database instance to Spot pricing during the batch window
K: B
G: ## How burstable (T) instances work
T-class instances such as `db.t3.medium` provide a **baseline CPU level** and earn **CPU credits** while running below it. Bursting above the baseline spends credits.
- On EC2, **standard** mode holds the CPU at baseline once credits run out, so work slows down.
- Amazon RDS runs T3 and T4g DB instances in **unlimited** mode: when credits run out the instance keeps bursting, and the extra CPU is billed as **surplus credits** per vCPU-hour.
## What sustained depletion means
If credits are exhausted every night and the CPU stays high for hours, the workload is not spiky; it needs more sustained CPU than the baseline provides. On RDS that shows up as surplus credit charges added to the hourly price, often making the "small" instance more expensive than a fixed-performance one.
- Example: a `db.m6g.large` has no credit mechanism, runs the batch at full speed for a flat hourly rate, and can cost less than a T3 paying surplus credits for hours every night.
W: Undersized, move to a non-burstable or larger class: sustained credit exhaustion shows the workload exceeds the burstable baseline, so a fixed-performance or larger class removes the surplus credit charges and can lower the total bill.
X: A=Reserved Instance for db.t3.medium: a reservation only discounts the hourly rate; surplus CPU credit charges are billed on top and are not covered, so the main cost driver remains for 1 or 3 years.
C=Downsize to db.t3.small: a smaller burstable instance has a lower baseline and earns fewer credits, so credits run out sooner and surplus charges grow.
D=Spot pricing for RDS: Amazon RDS does not offer Spot pricing for DB instances, so this option does not exist.
T: A burstable instance that exhausts its credits every day is undersized; on RDS unlimited mode turns that into surplus credit charges, so move to a larger or non-burstable class.
V: RDS

@ SAP-C02 D4 T4.3 advanced comparison
S: A company wants to migrate its on-premises NetApp-based file storage workloads to AWS while retaining features like NetApp Snapshot technology, SnapMirror replication, and multi-protocol NFS and SMB access from the same volumes. Separately, another workload's on-premises applications need NFS access to files stored as objects in Amazon S3, with frequently accessed data cached locally. Which two services respectively address these needs?
A: Amazon S3 for both cases, using different storage classes
B: Amazon FSx for NetApp ONTAP for the first case, and AWS Storage Gateway File Gateway for the second
C: Amazon EFS for the first case, and Amazon FSx for Lustre for the second
D: AWS Storage Gateway Volume Gateway in cached mode for the first case, and Amazon FSx for NetApp ONTAP for the second
K: B
G: ## Two different storage patterns
**Moving NetApp workloads** is easiest when the target speaks NetApp's own data management language. **Amazon FSx for NetApp ONTAP** runs the ONTAP file system as a managed service, so teams keep:
- Snapshot copies, FlexClone and storage efficiency features
- SnapMirror replication, including from on-premises ONTAP arrays into AWS for migration
- Multi-protocol access: the same volume served over NFS, SMB and iSCSI
**Hybrid file access to S3** is a different need. **Amazon S3 File Gateway** (a type of AWS Storage Gateway) is a local VM or appliance that presents NFS or SMB shares, keeps recently used data in a local cache, and stores every file as an object in an S3 bucket, uploading changes asynchronously.
Example: a design office mounts `gateway:/projects`; today's files come from the local cache, while years of older files live in S3 and are fetched on demand.
Volume Gateway, by contrast, serves iSCSI block volumes whose data AWS stores in a service-managed format, backed up as EBS snapshots, not as S3 objects that applications can read directly.
W: FSx for NetApp ONTAP plus File Gateway: ONTAP keeps Snapshots, SnapMirror and NFS/SMB multi-protocol volumes for the migration, and S3 File Gateway gives on-premises applications NFS access to S3 objects with a local cache of hot data.
X: A=S3 for both: storage classes change only cost and retrieval behavior; S3 has no NetApp Snapshot, SnapMirror or multi-protocol file volumes, and no on-premises cache or NFS mount on its own.
C=EFS and FSx for Lustre: EFS is NFS-only with no NetApp features, and FSx for Lustre is a high-performance file system for compute clusters in AWS, not an on-premises caching gateway.
D=Volume Gateway for NetApp, ONTAP for caching: the roles are reversed; Volume Gateway serves iSCSI block volumes without NetApp features, and FSx for ONTAP in AWS is neither a local cache nor a way to store files as S3 objects.
T: Keep NetApp features with FSx for ONTAP; give on-premises applications cached NFS/SMB access to S3 objects with S3 File Gateway.
V: Amazon FSx, AWS Storage Gateway

@ SAP-C02 D4 T4.2 applied use-case
S: A company wants to migrate a commercial Oracle database with extensive PL/SQL stored procedures to Amazon Aurora PostgreSQL-Compatible Edition to reduce licensing costs. Which AWS tool should be used first to convert the database schema and procedural code, before performing the actual data migration?
A: AWS Schema Conversion Tool or DMS Schema Conversion
B: AWS Glue ETL jobs with crawlers cataloging the tables
C: AWS DataSync tasks copying the database data files
D: AWS DMS replication tasks with full load and CDC
K: A
G: ## Two steps in a heterogeneous migration
Moving from Oracle to PostgreSQL changes the database engine, so two different problems must be solved:
- **Schema and code conversion**: tables, indexes, views, sequences and procedural code such as PL/SQL packages, procedures and triggers must be rewritten for PostgreSQL (PL/pgSQL). The **AWS Schema Conversion Tool (SCT)**, a desktop application, and **DMS Schema Conversion**, the same capability built into the AWS DMS console, analyze the source, convert what they can automatically, and produce an assessment report listing items that need manual changes.
- **Data movement**: once the target schema exists, **DMS replication tasks** copy the rows with a full load and keep the target in sync with change data capture (CDC) until cutover.
## Order matters
Converting the schema comes first because replication tasks need target tables to load into, and the assessment report shows how much manual rework the PL/SQL needs before the project is committed.
W: SCT or DMS Schema Conversion: both convert Oracle schemas and PL/SQL into PostgreSQL-compatible objects and flag code that needs manual rewriting, which is exactly the first step before any data moves.
X: B=Glue ETL jobs and crawlers: Glue catalogs and transforms data for analytics pipelines; it does not convert database schemas, stored procedures or triggers from Oracle to PostgreSQL.
C=DataSync tasks: DataSync copies files and objects between storage systems; copying Oracle data files produces nothing a PostgreSQL engine can use and converts no code.
D=DMS replication tasks: full load and CDC move and synchronize rows into tables that already exist, but replication tasks do not convert PL/SQL procedures or build the target schema.
T: In a heterogeneous migration, convert schema and code with SCT or DMS Schema Conversion first, then move the data with DMS replication tasks.
V: AWS Schema Conversion Tool, AWS Database Migration Service, Amazon Aurora
