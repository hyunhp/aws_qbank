# SCS-C03 batch 05: detailed questions for D2 (incident response), D4 (IAM), D6 (governance)

@ SCS-C03 D2 T2.1 applied use-case
S: A company with a small security team wants AWS to help triage GuardDuty and Security Hub findings around the clock, suppress known benign findings, track each incident in a case with a timeline, and give responders 24/7 access to the AWS Customer Incident Response Team. Which approach fits with the least custom work?
A: Subscribe to AWS Security Incident Response and connect it to the organization so it triages findings, opens cases, and engages the AWS CIRT
B: Enable Amazon Detective in the delegated administrator account and use its finding groups as the case record shared with the AWS CIRT
C: Configure AWS Systems Manager Incident Manager response plans that page the AWS CIRT through an escalation plan for every finding
D: Buy AWS Enterprise Support and ask the technical account manager to review and triage every GuardDuty finding as a support case
K: A
G: ## Build it yourself versus a managed IR service
Most incident response tooling in AWS is do-it-yourself: GuardDuty and Security Hub produce findings, EventBridge routes them, and your own team triages, investigates and responds.
## AWS Security Incident Response
AWS Security Incident Response is a paid service you enable for an organization. It adds people and process on top of the findings:
- **Triage**: it monitors findings from GuardDuty and from third-party tools integrated through Security Hub, and auto-suppresses those that match known benign patterns for your environment.
- **Case management**: each security event becomes a case with a timeline, communications and attachments, which is also where you can open a case yourself.
- **AWS CIRT**: responders can engage the AWS Customer Incident Response Team 24/7 during an active event.
- **Containment support**: responders help you plan containment, and with permissions you grant in your accounts, containment steps can be run for you.
## Example
A small team gets 400 findings per week; the service suppresses the benign ones and escalates only the real events as cases.
W: AWS Security Incident Response: it is the managed service that combines finding triage and suppression, case management with timelines, and 24/7 access to the AWS CIRT, all without building your own pipeline.
X: B=Detective finding groups: Detective helps an analyst investigate related findings and entities, but it has no case workflow, does no triage for you, and is not a channel to the AWS CIRT.
C=Incident Manager paging the CIRT: Incident Manager engages your own contacts and runs your runbooks; the AWS CIRT is not a contact you can add to an escalation plan.
D=Enterprise Support triage: a TAM gives guidance and escalation, not continuous monitoring and triage of every finding; support cases are not an incident triage service.
T: For managed triage, case management and 24/7 AWS CIRT access, enable AWS Security Incident Response; Detective and Incident Manager are tools your own team drives.
V: AWS Security Incident Response, Amazon GuardDuty, AWS Security Hub

@ SCS-C03 D2 T2.1 advanced tradeoff
S: A team built an EventBridge rule for GuardDuty EC2 findings that invokes a Lambda function to tag the instance, swap its security group, and snapshot its volumes. They must prove the whole chain works against a real instance in a test account before production. Which test approach fits?
A: Deploy the amazon-guardduty-tester environment in the test account so real activity from a test instance creates genuine findings for that instance
B: Call the GuardDuty CreateSampleFindings API for the EC2 finding types so the rule fires and the function isolates the instance named in the finding
C: Import a custom finding into Security Hub with BatchImportFindings that names the test instance, so the GuardDuty rule receives it as a finding
D: Run the EventBridge TestEventPattern API with a saved GuardDuty finding, so the rule invokes the function against the test instance end to end
K: A
G: ## Three ways to "test" a detection chain
A response chain has several parts: the finding, the EventBridge rule, the target, and the actions against a resource. Each test method exercises a different part.
- **Sample findings** (`CreateSampleFindings`) publish findings marked as samples. They reach EventBridge, so they prove the rule matches, but their resource details are placeholders, for example an instance ID like `i-99999999`, so any action against the instance fails.
- **TestEventPattern** only evaluates whether a JSON event matches a pattern. It does not deliver the event to any target.
- **amazon-guardduty-tester** is an AWS sample that deploys a small test environment and generates real suspicious activity (for example DNS lookups of known test domains), so GuardDuty produces genuine findings that reference real test resources.
## Choosing
To prove that isolation and snapshots succeed, the finding must name an instance that exists. Only real findings do that.
W: GuardDuty tester in a test account: it produces genuine findings about real test instances, so the rule, the function and every isolation step run against an existing resource.
X: B=Sample findings: they do reach EventBridge, but the resource IDs in them are placeholders, so tagging, security group changes and snapshots have no real instance to act on.
C=Security Hub custom finding: an imported finding arrives with the Security Hub source and format, so a rule matching the GuardDuty source never sees it, and the chain under test is bypassed.
D=TestEventPattern: this API only returns whether the event matches the pattern; it never invokes the target, so nothing downstream is tested.
T: Sample findings prove routing, not actions; to test containment end to end, generate real findings against real test resources with the GuardDuty tester.
V: Amazon GuardDuty, Amazon EventBridge, AWS Lambda

@ SCS-C03 D2 T2.1 applied troubleshooting
S: An incident response runbook for compromised EC2 instances says: isolate the instance, snapshot all EBS volumes, then stop the instance. In a drill, analysts found that the simulated malware ran only in memory and left no trace on the volumes. How should the runbook change?
A: Before stopping, use Systems Manager Run Command to run a pre-staged memory acquisition tool and write the image to the forensics bucket
B: Take multi-volume snapshots with crash-consistent mode enabled, because that mode writes the instance's memory pages into the snapshot
C: Enable VPC Traffic Mirroring on the instance before stopping it, so memory contents are copied to the mirror target for later analysis
D: Enable GuardDuty Runtime Monitoring, because each runtime finding includes a full memory dump of the process that triggered it
K: A
G: ## Volatile versus persistent evidence
Evidence on an instance comes in two kinds:
- **Persistent**: files and logs on EBS volumes. Snapshots preserve these, even after the instance stops.
- **Volatile**: running processes, network connections, loaded kernel modules, decrypted keys and fileless malware. These live only in RAM and are lost the moment the instance stops or reboots.
## Order of collection
Collect the most volatile evidence first: memory, then disks. In AWS a common pattern is:
- keep the SSM Agent and an instance profile on instances so responders can reach them even after isolation,
- pre-stage a memory acquisition tool (for example AVML or LiME) or ship it in an SSM document,
- run it with `AWS-RunShellScript` through Run Command and upload the image to an evidence bucket in the forensics account,
- then snapshot volumes and stop the instance.
W: Memory capture through Run Command first: RAM is the only place fileless malware exists, so it must be acquired with a pre-staged tool before the instance is stopped and the evidence disappears.
X: B=Crash-consistent snapshots: multi-volume snapshots make several volumes consistent to the same point in time, but a snapshot only ever contains block storage, never memory.
C=Traffic Mirroring: mirroring copies network packets from the ENI, which can show what the malware sends, but it cannot read the contents of the instance's memory.
D=Runtime Monitoring dumps: Runtime Monitoring reports suspicious process and file behavior as findings; it does not capture or store memory images for forensics.
T: Snapshots preserve disks only; capture memory first with a pre-staged tool through Systems Manager, then snapshot and stop.
V: AWS Systems Manager, Amazon EC2, Amazon EBS, Amazon S3

@ SCS-C03 D2 T2.1 applied comparison
S: A company stores forensic disk images and memory captures in an S3 bucket in its forensics account. Legal requires that no one, including administrators of that account and its root user, can delete or overwrite any evidence object for one year after upload. Which configuration meets this requirement?
A: Enable versioning with S3 Object Lock and a default retention of one year in compliance mode on the evidence bucket
B: Enable versioning with S3 Object Lock and a default retention of one year in governance mode on the evidence bucket
C: Enable versioning and apply a legal hold to every uploaded object, removing each hold one year after its upload date
D: Enable versioning with MFA Delete so that deleting any object version requires the root user and its MFA device code
K: A
G: ## Why evidence needs WORM storage
Chain of custody depends on proving evidence was not changed after collection. S3 Object Lock stores object versions in a write-once-read-many (WORM) model; it requires versioning on the bucket.
## Object Lock options
- **Compliance mode**: no user, including the root user, can overwrite or delete a protected version or shorten its retention until the retention period ends.
- **Governance mode**: blocks most users, but principals with `s3:BypassGovernanceRetention` can delete or change the retention by sending the bypass header.
- **Legal hold**: no expiry date; it stays until removed, and anyone with `s3:PutObjectLegalHold` can remove it.
## Example
A default bucket retention of `COMPLIANCE`, 365 days, applies to every new version automatically, so responders do not have to set it per upload.
## Related control
MFA Delete protects against version deletion but can be turned off by the root user, so it is not WORM.
W: Compliance mode retention: it is the only option that even the root user cannot bypass or shorten, and a default retention protects every uploaded version for one year automatically.
X: B=Governance mode: principals with s3:BypassGovernanceRetention, which administrators can grant themselves, can still delete or overwrite protected versions.
C=Legal holds: any principal with s3:PutObjectLegalHold can remove a hold at any time, so administrators could remove it and delete the evidence.
D=MFA Delete: the root user can disable MFA Delete or delete versions with its own MFA code, so the root user is not prevented from destroying evidence.
T: When even root must not delete evidence, use Object Lock compliance mode; governance mode and legal holds can be lifted by privileged users.
V: Amazon S3

@ SCS-C03 D2 T2.2 advanced use-case
S: A workforce user in AWS IAM Identity Center is suspected of being compromised. The user has active AWS access portal sessions and has already obtained role credentials in several accounts through permission sets with a 4-hour session duration. Which TWO actions stop this user's access as quickly as possible? (Select TWO)
A: Disable the user in the identity source and delete the user's active sessions in the IAM Identity Center console
B: Add a deny statement to the user's permission sets that matches the user's session name in the aws:userid key
C: Reset the user's password in IAM Identity Center, which also invalidates all role credentials already issued to it
D: Remove the permission set assignments for the user, which immediately revokes the role credentials already issued
E: Delete the AWSReservedSSO roles in each affected account so Identity Center must recreate them for every user
K: A,B
G: ## Two layers of sessions
IAM Identity Center creates two kinds of sessions:
- an **access portal session**, from sign-in until the portal session duration ends (8 hours by default),
- **role sessions** in each account: temporary credentials for the `AWSReservedSSO_<PermissionSet>_...` role, valid for the permission set's session duration (1 hour by default, up to 12).
## Why ordinary fixes are slow
Disabling the user, resetting the password or removing assignments stops new sign-ins and new credentials. Credentials that STS already issued stay valid until they expire, because they are not checked against the directory on each call.
## Cutting existing role sessions
The role session name for Identity Center roles is the user's username, so a deny statement in the permission set can target just that person:
`"Effect": "Deny", "Action": "*", "Resource": "*", "Condition": {"StringLike": {"aws:userid": "*:jane@example.com"}}`
Identity Center provisions the updated permission set to every assigned account, and the deny applies to credentials already in use.
W: A=Disable and delete sessions: disabling the user and deleting the access portal sessions stops the user from obtaining any new role credentials.
B=Deny by session name: a permission set deny keyed on aws:userid immediately blocks the role credentials the user already holds in every assigned account.
X: C=Password reset: a new password blocks future sign-ins only; STS credentials already issued remain valid until their 4-hour duration ends.
D=Remove assignments: removing assignments prevents new role sessions but does not revoke temporary credentials that were already issued.
E=Delete the reserved roles: these roles are managed by Identity Center, deleting them locks out every user of that permission set, and it is not the supported revocation path.
T: Blocking sign-in does not end issued role credentials; pair disabling the user with a permission set deny that matches the user's aws:userid.
V: AWS IAM Identity Center, AWS STS, AWS IAM

@ SCS-C03 D2 T2.2 applied use-case
S: GuardDuty Runtime Monitoring reports a cryptocurrency miner running in one pod of an Amazon EKS deployment that uses the Amazon VPC CNI with network policy enabled. The team must stop the pod's network activity while keeping the pod and node intact for forensic analysis. What should the responder do first?
A: Label the pod, apply a deny-all ingress and egress NetworkPolicy that selects that label, and cordon the worker node
B: Delete the pod so the deployment controller replaces it with a fresh copy, and then snapshot the node's root volume
C: Scale the deployment to zero replicas so the miner stops, and then review the container image for the infection source
D: Attach a security group with no rules to the worker node's primary network interface, and then terminate the affected pod
K: A
G: ## Containing a pod versus a node
Several pods share one worker node, so containment in Kubernetes has two layers:
- **Pod isolation**: a Kubernetes `NetworkPolicy` with empty ingress and egress rules blocks all traffic for the pods it selects. The Amazon VPC CNI can enforce network policies natively.
- **Node isolation**: `kubectl cordon <node>` stops the scheduler from placing new pods on the node, so no new workloads join the suspicious host.
## Preserving evidence
The running container holds the evidence: process list, memory, and files written into its writable layer. Deleting or scaling pods destroys this, and a Deployment immediately starts a clean replacement that hides the trail.
## Example
- `kubectl label pod miner-7c9 quarantine=true`
- a NetworkPolicy with `podSelector: {matchLabels: {quarantine: "true"}}` and `policyTypes: [Ingress, Egress]` with no rules
- `kubectl cordon ip-10-0-3-17.ec2.internal`
Then capture memory and volumes. If service capacity matters, relabel the pod so it no longer matches the Deployment's selector; the controller starts a replacement while the quarantined pod stays for analysis.
W: Label, deny-all NetworkPolicy, cordon: this cuts the compromised pod off the network while leaving it running for forensics, and cordoning keeps new workloads away from the suspect node.
X: B=Delete the pod: deleting it destroys the running process, memory and container filesystem, the very evidence the team must preserve.
C=Scale to zero: this terminates every replica, including the infected one, so the evidence is lost and the service goes down as well.
D=Node security group: it cuts off every pod on the node rather than only the infected one, and terminating the pod still destroys the evidence.
T: In EKS, isolate the pod with a deny-all NetworkPolicy and cordon the node; deleting or scaling pods wipes the evidence.
V: Amazon EKS, Amazon GuardDuty

@ SCS-C03 D2 T2.2 advanced troubleshooting
S: GuardDuty reports UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration.OutsideAWS for the IAM role used by a web server fleet. The team finds a server-side request forgery flaw in the web application that lets attackers fetch URLs from the instance. Which TWO actions contain this incident and block the attack path? (Select TWO)
A: Revoke the role's active sessions, which adds a deny for credentials whose aws:TokenIssueTime is older than the revocation time
B: Require IMDSv2 on the fleet by setting HttpTokens to required, so metadata requests need a session token from a PUT request
C: Rotate the role's access keys in the IAM console, which invalidates the keys the attacker copied from the instance metadata
D: Detach and reattach the instance profile on each instance, which invalidates the temporary credentials already issued to it
E: Enable GuardDuty S3 Protection on the account, which blocks API calls that use EC2 role credentials from outside AWS
K: A,B
G: ## What this finding means
EC2 instances get temporary role credentials from the Instance Metadata Service (IMDS) at `169.254.169.254`. `InstanceCredentialExfiltration.OutsideAWS` means those credentials were used from an IP address outside AWS: someone copied them off the instance.
## How SSRF steals them
With IMDSv1, a simple HTTP GET to `/latest/meta-data/iam/security-credentials/<role>` returns the keys. An SSRF flaw lets an attacker make the server send that GET for them.
IMDSv2 requires a session token obtained with an HTTP `PUT` that carries a special header, which typical SSRF cannot send. Set `HttpTokens=required` on instances and in launch templates.
## Invalidating stolen temporary credentials
Temporary credentials cannot be deleted. Revoking role sessions attaches an inline policy (`AWSRevokeOlderSessions`) that denies everything when `aws:TokenIssueTime` is before the revocation time. Legitimate instances obtain new credentials from IMDS when their credentials are next refreshed, so expect brief errors.
W: A=Revoke active sessions: the TokenIssueTime deny makes the stolen temporary credentials useless immediately, while legitimate instances pick up fresh ones on their next refresh.
B=Require IMDSv2: session tokens obtained with PUT close the SSRF path that let the attacker read credentials from the metadata service.
X: C=Rotate role access keys: roles have no long-term access keys to rotate; instance credentials are temporary STS credentials that stay valid until they expire unless denied.
D=Reattach the instance profile: swapping the profile changes future credentials but does not invalidate credentials already issued and copied by the attacker.
E=S3 Protection: it detects suspicious S3 data access; it does not block the use of instance credentials from outside AWS.
T: Stolen instance credentials are killed with a TokenIssueTime deny (revoke sessions), and the SSRF theft path is closed by requiring IMDSv2.
V: Amazon GuardDuty, AWS IAM, Amazon EC2

@ SCS-C03 D4 T4.1 advanced troubleshooting
S: On-premises servers use IAM Roles Anywhere with a trust anchor that points to the company's own certificate authority. A server's private key was stolen, so the security team revoked its certificate at the CA and published an updated CRL at the CRL distribution point. The stolen certificate can still obtain AWS credentials. What must the team do?
A: Import the updated certificate revocation list into IAM Roles Anywhere with the ImportCrl API and enable it for the trust anchor
B: Turn on OCSP checking for the trust anchor so IAM Roles Anywhere queries the CA's responder before issuing each set of credentials
C: Update the IAM Roles Anywhere profile's session duration to 15 minutes so that the credentials of the revoked certificate expire sooner
D: Replace the CRL distribution point in the certificate with a public HTTPS URL that IAM Roles Anywhere is able to fetch on each request
K: A
G: ## How IAM Roles Anywhere authenticates
IAM Roles Anywhere lets workloads outside AWS exchange an X.509 certificate for temporary credentials. You create:
- a **trust anchor**: the CA (AWS Private CA or your own CA certificate bundle) whose certificates are trusted,
- a **profile**: which roles can be assumed and optional session policies,
- a trust policy on the role that allows `rolesanywhere.amazonaws.com`.
## Revocation
Roles Anywhere does not contact your CA. It does not fetch CRL distribution points in certificates and does not use OCSP. The only revocation check it performs is against CRLs that **you import**:
`aws rolesanywhere import-crl --name corp-crl --crl-data fileb://crl.pem --trust-anchor-arn <arn> --enabled`
Afterwards, a certificate on that list is rejected at `CreateSession`. Update the imported CRL each time the CA revokes more certificates.
## Example
Automate it: when the CA publishes a new CRL, a job calls `UpdateCrl` so AWS sees each revocation promptly.
W: ImportCrl: Roles Anywhere only honors revocation lists imported into the service, so importing the new CRL is what makes the stolen certificate fail at CreateSession.
X: B=OCSP checking: Roles Anywhere has no OCSP option; it never calls the CA's responder, which is why an imported CRL is required.
C=Shorter sessions: a shorter duration limits each set of credentials, but the revoked certificate can still request new ones at any time.
D=Public CRL URL: Roles Anywhere does not fetch CRL distribution points from certificates at all, whatever the URL is.
T: IAM Roles Anywhere checks revocation only against CRLs imported with ImportCrl; revoking at the CA alone does nothing.
V: IAM Roles Anywhere, AWS IAM

@ SCS-C03 D4 T4.1 applied use-case
S: A consumer app uses an Amazon Cognito user pool for email and password sign-in. Credential stuffing attacks are rising. Without writing custom code, the company wants to block sign-ins that use passwords known from public breaches and require MFA only when a sign-in looks risky. Which TWO settings meet this? (Select TWO)
A: Enable threat protection on a Plus plan user pool and turn on compromised credentials detection to block the sign-in
B: Enable threat protection on a Plus plan user pool and configure adaptive authentication to require MFA at higher risk
C: Associate an AWS WAF web ACL with the user pool and add a rate-based rule, which also blocks known breached passwords
D: Configure a password policy with history and 14 characters, which rejects passwords known from breached credential lists
E: Add a pre token generation Lambda trigger that inspects the risk level and requires MFA before the tokens are issued
K: A,B
G: ## Cognito threat protection
Amazon Cognito user pools have a feature called **threat protection** (earlier called advanced security features). It is part of the **Plus** feature plan and can run in audit-only or full-function mode. It has two main parts:
- **Compromised credentials detection**: Cognito checks whether the username and password pair appears in known breach data during sign-in, sign-up or password change, and can block the attempt.
- **Adaptive authentication**: each sign-in gets a risk level (low, medium, high) from signals such as new device, location and IP reputation. For each level you choose an action, for example allow, optional MFA, require MFA, or block.
## Example
Low risk: allow. Medium risk: require MFA. High risk: block. Users signing in from their usual device are not prompted, while a sign-in from an unknown network gets an MFA challenge.
## What it complements
AWS WAF on the user pool limits request rates, and password policies set complexity, but neither knows which passwords have leaked.
W: A=Compromised credentials detection: Cognito compares sign-ins with known breach data and blocks leaked username and password pairs without code.
B=Adaptive authentication: each sign-in gets a risk level, and MFA is required only for the risk levels you choose, so normal sign-ins stay smooth.
X: C=WAF rate rule: a web ACL can throttle request floods, but it has no knowledge of breached username and password pairs.
D=Stronger password policy: length and history rules do not compare passwords with breach data; a long reused password still passes.
E=Pre token generation trigger: it runs after authentication to customize tokens, has no risk score by itself, and would be custom code anyway.
T: Cognito threat protection provides leaked-credential blocking and risk-based MFA; WAF and password policies cannot recognize breached passwords.
V: Amazon Cognito, AWS WAF

@ SCS-C03 D4 T4.1 advanced use-case
S: An organization has 300 member accounts, each with its own root user password and MFA device stored in a safe. The security team wants to remove long-term root credentials from member accounts but still be able to fix an S3 bucket policy that accidentally denies all principals. Which approach fits?
A: Enable centralized root access management, delete member root credentials, and use sts:AssumeRoot with the S3UnlockBucketPolicy task policy
B: Attach an SCP that denies all actions by the root user in member accounts, and use an administrator role to edit the locked bucket policy
C: Keep the root passwords but replace each MFA device with a passkey stored in a shared vault that only the security team members can open
D: Create an IAM Identity Center permission set with AdministratorAccess and assign it in every account to remove locked bucket policies
K: A
G: ## Root users in member accounts
Every AWS account has a root user. In an organization, member root credentials are a large attack surface: hundreds of passwords and MFA devices to protect.
## Centralized root access management
In IAM, the management account (or a delegated administrator) can enable two features once trusted access for IAM is on:
- **Root credentials management**: delete root passwords, access keys, signing certificates and MFA from member accounts; new accounts are created without root credentials.
- **Privileged root actions**: call `sts:AssumeRoot` for a member account with a narrow task policy, getting a short root session that can do only that task.
Task policies include `S3UnlockBucketPolicy`, `SQSUnlockQueuePolicy`, `IAMDeleteRootUserCredentials`, `IAMCreateRootUserPassword` and `IAMAuditRootUserCredentials`.
## Why root is needed for a locked bucket
A bucket policy that denies all principals blocks every IAM role, including administrators. Only the root user can delete that bucket policy.
W: Centralized root access management: it removes member root credentials entirely while keeping a controlled, auditable way to perform root-only tasks such as unlocking a bucket policy through sts:AssumeRoot.
X: B=SCP plus admin role: the SCP limits root but leaves the credentials in place, and an administrator role cannot delete a bucket policy that denies all principals.
C=Passkeys in a vault: the long-term root passwords still exist in every account, which is exactly what the team wants to eliminate.
D=AdministratorAccess permission set: any IAM role is blocked by a deny-all bucket policy, so this cannot unlock the bucket, and it grants broad standing access.
T: Remove member root credentials and use sts:AssumeRoot task policies for root-only fixes; admin roles cannot override a deny-all bucket policy.
V: AWS IAM, AWS Organizations, AWS STS, Amazon S3

@ SCS-C03 D4 T4.1 applied tradeoff
S: A platform team runs 60 Amazon EKS clusters and uses IAM roles for service accounts (IRSA). Each new cluster requires another IAM OIDC provider and edits to trust policies that are nearing their size limit. The team wants pods to keep per-service-account roles with less setup per cluster. Which approach fits?
A: Move to EKS Pod Identity, with role trust policies for pods.eks.amazonaws.com and associations of roles to service accounts
B: Share one IAM OIDC provider across all clusters by adding each cluster's issuer URL as another client ID on that provider
C: Attach one broad role to every node's instance profile, and let pods read credentials from the node's instance metadata
D: Store long-term access keys for each service account in Secrets Manager and mount them into pods with the CSI driver
K: A
G: ## How IRSA works
IAM roles for service accounts (IRSA) federate each cluster's OIDC issuer into IAM:
- one IAM OIDC identity provider per cluster, per account,
- a role trust policy with `sts:AssumeRoleWithWebIdentity` and conditions on the cluster issuer and service account (`...:sub = system:serviceaccount:ns:name`).
Using one role from many clusters means one trust policy statement per cluster, which runs into the trust policy size limit.
## EKS Pod Identity
EKS Pod Identity removes the OIDC federation step:
- the trust policy trusts the service principal `pods.eks.amazonaws.com` with `sts:AssumeRole` and `sts:TagSession`, identical for every cluster,
- you create a **pod identity association** (cluster, namespace, service account, role) through the EKS API,
- the EKS Pod Identity Agent on each node delivers the credentials to pods.
Sessions carry tags such as `eks-cluster-name` and `kubernetes-namespace`, which can be used for ABAC.
W: EKS Pod Identity: roles use one generic trust policy for the EKS service principal, no per-cluster OIDC provider is needed, and associations keep roles scoped per service account.
X: B=Shared OIDC provider: each cluster has its own issuer URL, and an IAM OIDC provider is tied to one issuer; client IDs are audiences, not extra issuers.
C=Node instance profile: every pod on the node would get the same broad permissions, which breaks per-service-account least privilege.
D=Access keys in Secrets Manager: long-term keys must be rotated and can leak; this replaces temporary credentials with a weaker pattern.
T: For many clusters, EKS Pod Identity avoids per-cluster OIDC providers and trust policy growth; IRSA requires both.
V: Amazon EKS, AWS IAM, AWS STS

@ SCS-C03 D4 T4.1 advanced use-case
S: Developers federate from a SAML identity provider into a role, then chain into deployment roles in other accounts and choose their own role session names. Auditors require CloudTrail to show the corporate username for every action, including after role chaining, and developers must not be able to change or remove it. Which approach fits?
A: Pass the SourceIdentity SAML attribute from the IdP and allow sts:SetSourceIdentity in the trust policies of the federated and deployment roles
B: Require developers to set RoleSessionName to their corporate username with a condition on sts:RoleSessionName in every deployment role
C: Use CloudTrail Lake to join AssumeRole events by access key ID, rebuilding the chain from each deployment session back to the federated user
D: Add the username as a non-transitive session tag at federation, so every chained role session carries the tag in its CloudTrail records
K: A
G: ## The problem with role session names
A role session is logged as `assumed-role/RoleName/SessionName`. The caller picks the session name on each `AssumeRole`, so after role chaining the original identity can be replaced by any string.
## Source identity
**Source identity** is a value set once when the first role session is created:
- a SAML IdP sends it in the attribute `https://aws.amazon.com/SAML/Attributes/SourceIdentity` (OIDC and `AssumeRole` callers can pass it too),
- the role trust policy must allow `sts:SetSourceIdentity`,
- once set, it **persists across role chaining** and cannot be changed in later sessions,
- CloudTrail records it as `sourceIdentity` on every event of those sessions.
## Example
Jane signs in; the IdP sends `SourceIdentity=jane`. She chains into `Deployer` in another account and names the session `build-42`. CloudTrail still shows `sourceIdentity: jane` on her deployments, and the `sts:SourceIdentity` condition key can require it.
W: SourceIdentity: it is set by the IdP, carried unchanged through every chained session, and logged by CloudTrail, which is exactly the tamper-resistant user trail auditors want.
X: B=RoleSessionName condition: a condition cannot know the corporate username after chaining unless it is already carried reliably, and the session name is still chosen by the caller.
C=CloudTrail Lake joins: reconstruction is manual and fragile, and it does not stop developers from obscuring identity; nothing in each event proves who acted.
D=Non-transitive session tag: non-transitive tags are dropped when the role is chained, so the deployment sessions would not carry the username.
T: Use SourceIdentity for a user identity that survives role chaining; session names and non-transitive tags can be changed or lost.
V: AWS STS, AWS IAM, AWS CloudTrail

@ SCS-C03 D4 T4.2 applied use-case
S: A data lake bucket holds folders for 400 corporate groups. Users and groups come from Microsoft Entra ID through IAM Identity Center. Each group needs read or read-write access to its own prefixes, the bucket policy is near its size limit, and CloudTrail must show which corporate user accessed the data. Which approach fits?
A: Create an S3 Access Grants instance linked to IAM Identity Center and add grants that map each directory group to its prefix and access level
