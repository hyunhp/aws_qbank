# SCS-C03 batch 06: D6 security foundations and governance (T6.1 x7, T6.2 x7, T6.3 x6)

@ SCS-C03 D6 T6.1 applied use-case
S: A company keeps sensitive data in S3 buckets and KMS keys across 90 accounts in one AWS Organization. Many teams write their own bucket and key policies, and the security team wants a guarantee that no principal from outside the organization can ever use those buckets or keys, even if a team writes a policy that allows it. Which approach fits best?
A: Attach an SCP to the root of the organization that denies s3:* and kms:* when the aws:PrincipalOrgID condition key does not match the organization
B: Enable S3 Block Public Access and IAM Access Analyzer external access findings in every account, then remediate any bucket or key policy flagged
C: Attach a resource control policy to the root of the organization that denies S3 and KMS actions unless aws:PrincipalOrgID matches the organization ID
D: Attach a permissions boundary to every IAM role in the member accounts that denies S3 and KMS actions when the caller is not from the organization
K: C
G: ## SCPs and RCPs guard different sides
- A **service control policy (SCP)** limits what the principals in your accounts can do. It never limits a caller from another organization who is using a resource in one of your accounts.
- A **resource control policy (RCP)** sets the maximum permissions on the resources in your accounts, for the services RCPs support (S3, KMS, STS, SQS and Secrets Manager are among them). Like an SCP it grants nothing on its own, and a deny in it wins over any resource-based policy allow.
## Data perimeter
A common perimeter pattern is an RCP that denies access to a resource when `aws:PrincipalOrgID` is not your organization. Because it is evaluated for the resource's account, an overly generous bucket or key policy written by a team still cannot open the resource to outsiders. AWS service principals that act on your behalf need an exception (for example with `aws:PrincipalIsAWSService`), or the deny breaks them.
W: A resource control policy on the organization root caps who can use the bucket and key resources, so a bucket or key policy that names an outside principal is still denied.
X: A=SCP with PrincipalOrgID: an SCP is evaluated only for principals inside your accounts, so it does not stop an outside principal calling into a bucket.
B=Block Public Access and Access Analyzer: these detect and reduce exposure after the fact. Block Public Access covers public access only, not named outside accounts, and Analyzer findings do not prevent a policy from being written.
D=Permissions boundary on roles: a boundary limits what your own roles can do. It cannot restrict outside callers, and it does nothing for principals that never use those roles.
T: To restrict who can access resources in your accounts regardless of resource-based policies, use an RCP; SCPs restrict only your own principals.
V: AWS Organizations, Amazon S3, AWS KMS

@ SCS-C03 D6 T6.1 advanced troubleshooting
S: A cloud governance team attached a tag policy to an OU that defines the CostCenter key with the allowed values 100, 200 and 300. Weeks later, developers in the OU are still creating supported resources with CostCenter=999 and nothing stops them. The team wants such tagging attempts to fail from now on. What should they do?
A: Add an SCP to the OU that denies every tag-related action unless aws:RequestTag/CostCenter is one of the values 100, 200 or 300
B: Move the tag policy to the management account, because a tag policy attached to an OU is only advisory for member accounts
C: Enable the tag policy in AWS Config in each member account, so that a rule blocks resources created with a noncompliant tag value
D: Edit the tag policy to enforce the CostCenter key for the resource types in use so noncompliant tag values are blocked
K: D
G: ## What a tag policy does by default
A **tag policy** is an Organizations policy type that standardizes tags: the key's capitalization and, optionally, the allowed values.
- By default a tag policy only makes noncompliant tags **visible**: the organization's compliance report shows which resources break the policy.
- To block tagging operations you turn on **enforcement** (`enforced_for`) for the key and list the resource types it applies to. Then a tag request with a noncompliant value fails for those supported types.
## Limits to remember
- Enforcement covers only the resource types that support tag policy enforcement.
- A tag policy does not force a tag to exist. It governs the tags that are used.
- Resources already tagged wrongly are not changed; they show up as noncompliant.
W: Turning on enforcement for the CostCenter key and the resource types in use makes tag requests with a value outside 100, 200 and 300 fail, instead of only appearing in the compliance report.
X: A=Tag-related SCP: this can work for some services but is fragile. Condition keys and tagging actions differ per service, a broad deny can block untagged creates and TagResource calls that are otherwise valid, and it duplicates a control the tag policy already provides.
B=Management account move: tag policies apply wherever they are attached in the hierarchy. Where the policy sits is not the reason nothing is blocked.
C=AWS Config enablement: Config rules such as required-tags evaluate after a resource exists and cannot make a tagging call fail. Tag policies are also not switched on through Config.
T: A tag policy reports by default; add enforcement for specific resource types to block noncompliant tag values, and use a separate control if tags must be required.
V: AWS Organizations, tag policies

@ SCS-C03 D6 T6.1 advanced troubleshooting
S: A security team was delegated administration of AWS Firewall Manager for the organization and created a security group policy scoped to all accounts. Several member accounts never receive the policy, and the policy status for those accounts shows that they are not compliant with prerequisites. The accounts belong to the organization and Firewall Manager can see them. What is the most likely cause?
A: AWS Config is not enabled in those accounts and Regions, and Firewall Manager relies on it to find in-scope resources
B: Amazon GuardDuty is not enabled in those accounts, and Firewall Manager needs GuardDuty findings before it applies any policy
C: Firewall Manager can be administered only from the management account, so a policy created by a delegated account never applies
D: The member accounts have not enabled AWS Security Hub, which Firewall Manager needs as its delivery channel for policy status
K: A
G: ## How Firewall Manager gets to your accounts
AWS Firewall Manager centrally applies WAF, Shield Advanced, security group, network firewall and similar policies across an organization.
- The management account designates a **Firewall Manager administrator account**, which can be a dedicated security account.
- Firewall Manager uses **AWS Config** in each in-scope account and Region to find resources and to track their configuration. Without Config, it cannot evaluate or remediate those resources.
- Other services are needed only for specific policy types. For example, a Shield Advanced policy needs a Shield Advanced subscription.
## Diagnosis
When the organization and administrator are set up correctly but only some accounts are skipped, check the prerequisite that is per account and per Region: AWS Config recording.
W: Firewall Manager depends on AWS Config being enabled in each in-scope account and Region, so accounts without Config fail the prerequisite check and never get the policy.
X: B=GuardDuty requirement: Firewall Manager does not need GuardDuty, and it does not use GuardDuty findings to apply its policies.
C=Management account only: administration can be delegated to a Firewall Manager administrator account. A delegated administrator applying policies is the supported design.
D=Security Hub requirement: Firewall Manager can send findings to Security Hub, but Security Hub is not a prerequisite for policy application.
T: Missing prerequisites in some accounts usually point to AWS Config not recording there; Firewall Manager relies on Config for every policy type.
V: AWS Firewall Manager, AWS Config

@ SCS-C03 D6 T6.1 applied tradeoff
S: A company manages 150 AWS accounts through IAM Identity Center. Each of 120 teams has its own permission set granting access to resources tagged with the team's name, and administrators are hitting permission set limits and spending days on each new team. The identity provider already passes a team attribute for every user. Which approach reduces the administrative work while keeping the same isolation?
A: Merge all team permission sets into one broad permission set and rely on SCPs in each OU to keep every team away from other teams' resources
B: Enable attributes for access control, map the team attribute from the identity source, and use one permission set matching aws:PrincipalTag to the resource tag
C: Replace the permission sets with an IAM role per team in each account and let users assume the roles through SAML federation directly from the IdP tool
D: Attach a permissions boundary that lists every team's resource ARNs to a shared permission set, and update the boundary as teams are added
K: B
G: ## Role-based versus attribute-based access
With **role-based access control (RBAC)** you create one permission set per team or function. It is easy to reason about but multiplies quickly.
With **attribute-based access control (ABAC)** in IAM Identity Center you enable **attributes for access control** and map identity source attributes (such as team or cost center) to session tags. A single permission set can then say "allow actions on resources whose `Team` tag equals `${aws:PrincipalTag/Team}`".
## Effect
- New teams need only the right attribute in the IdP and resources tagged with the same value. No new permission set or per-account role is required.
- Isolation depends on tag hygiene, so the policy should also restrict who may change the tag (for example by denying tag edits by the same principals).
W: One permission set that compares the mapped team attribute in aws:PrincipalTag to the resource's Team tag gives every team the same isolation without a permission set per team.
X: A=Broad permission set with SCPs: SCPs cannot grant permissions, and expressing which team may reach which resources would need a per-team rule in every OU. That is more work and less precise.
C=IAM role per team with direct SAML: this recreates the sprawl in each account, removes central assignment and session management from Identity Center, and adds 120 roles in each of 150 accounts to maintain.
D=Permissions boundary of ARNs: a boundary that lists resource ARNs must be edited for each new team and resource, and it still grants no access by itself.
T: Use ABAC in Identity Center (attributes for access control plus tag conditions) to scale team-based access with one permission set instead of one per team.
V: AWS IAM Identity Center, AWS IAM

@ SCS-C03 D6 T6.1 advanced use-case
S: A company signs in to all AWS accounts through IAM Identity Center federated with an external identity provider. Leadership worries that an identity provider outage or misconfiguration could lock the security team out during an incident. Which TWO measures form a sound break-glass design? (Select TWO)
A: Create one additional Identity Center permission set with a 12-hour session and assign it to the whole security team for everyday use
B: Create a few emergency IAM users in a dedicated account that can assume administrator roles, protected by hardware MFA keys kept in separate secured locations
C: Share the management account root user password with the security team in the password manager so it can be used for routine administration
D: Alert the security team through an EventBridge rule on the emergency users' sign-in and role assumption events recorded by CloudTrail
E: Configure a second external identity provider in Identity Center so that the same emergency users can sign in through it
K: B,D
G: ## What break-glass access is for
Break-glass access exists for the case where your normal access path (here, the identity provider and Identity Center) is unavailable. It must not depend on that path, must be rarely used, and every use must be noticed.
## Design rules
- **Independent of the normal path**: emergency IAM users or roles that authenticate inside AWS, protected by phishing-resistant MFA, ideally held in a dedicated account and reachable by a limited administrator role.
- **Split custody**: hardware keys and credentials stored separately so no single person can use them alone.
- **Detected use**: CloudTrail records the sign-in and AssumeRole events; an EventBridge rule and notification make any use an incident to review.
- **Tested**: exercise the procedure periodically and rotate credentials after each use.
W: B=Emergency IAM users with hardware MFA: they authenticate in AWS without the identity provider, and separately stored keys enforce split custody.
D=Alerting on their use: EventBridge rules on CloudTrail sign-in and AssumeRole events for the emergency users mean any use is seen immediately.
X: A=Everyday 12-hour permission set: it still depends on Identity Center and the identity provider, so it fails in the outage, and routine use of a highly privileged set weakens least privilege.
C=Shared root password for routine work: root should be protected and used only for the few tasks that require it; routine use of a shared secret removes accountability and would not be noticed as a break-glass event.
E=Second external identity provider: Identity Center supports one external identity provider at a time, and a second one would still be an external dependency that can fail.
T: Design break-glass access to work when the identity provider does not: independent AWS-native credentials with hardware MFA in split custody, plus alerts on every use.
V: AWS IAM Identity Center, AWS CloudTrail, Amazon EventBridge

@ SCS-C03 D6 T6.1 advanced use-case
S: A security team wants to remove the root user credentials (password, access keys, MFA devices) from all member accounts in the organization. Occasionally a team locks itself out with a bucket policy that denies everyone, and the security team must then fix it as the root user of that account without keeping any long-term root credentials. Which approach meets the requirement?
A: Keep root credentials in a sealed vault and require two administrators to retrieve them, then sign in as root in that member account
B: Attach an SCP that allows the root user only the s3:PutBucketPolicy action, and let the security team reset root passwords through the account email address
C: Enable centralized root access management, delete member root credentials, and call sts:AssumeRoot with the S3UnlockBucketPolicy task policy
D: Create an administrator role in each member account and add a bucket policy statement that lets the role override any deny statement in the same policy
K: C
G: ## Centralized root access
AWS Organizations can manage root access for member accounts:
- **Root credentials management** lets the management account (or a delegated administrator) remove and audit member account root credentials. New accounts created afterward can be made without root credentials.
- **Root sessions** let those administrators call `sts:AssumeRoot` on a member account to get short-lived credentials that are limited to one privileged task. The AWS-managed root task policies include unlocking an S3 bucket policy (S3UnlockBucketPolicy), unlocking an SQS queue policy, and managing root credentials.
## Why it fits
The team never holds a root password, MFA device or access key in the member accounts. The privileged action needed here is available as a scoped, logged, short session.
W: With centralized root access management, credentials are removed and the security team gets a short, single-task root session through AssumeRoot to remove the locking bucket policy.
X: A=Vault of root credentials: this keeps long-term root credentials in every account, which is exactly what the requirement removes, and each account's root MFA would still need maintenance.
B=SCP for the root user: an SCP cannot grant permissions to root, and recovery through the account email keeps the root password in use, so neither meets the requirement.
D=Role that overrides a deny: an explicit deny in a resource policy cannot be overridden by a role's allow, which is the reason the bucket was locked out in the first place.
T: Use centralized root access management and sts:AssumeRoot for the rare root-only tasks, so member accounts hold no long-term root credentials.
V: AWS Organizations, AWS STS, Amazon S3

@ SCS-C03 D6 T6.2 advanced use-case
S: A company shares golden AMIs with 60 workload accounts. Each AMI needs the operating system baseline, a CIS hardening component and an automated test before use. New base OS versions and patches appear regularly, and the security team wants new golden AMIs built and shared to the organization automatically, without engineers running builds by hand. Which solution fits?
A: Run a Lambda function on a schedule that launches an instance from the last AMI, applies patches with a script and shares the resulting AMI with each account ID
B: Create an EC2 Image Builder pipeline that builds on updated base image versions, runs the hardening and test components, and distributes the AMI to the organization
C: Have each workload account run its own Systems Manager patching against the running instances and take its own AMI from a patched instance each month
D: Publish the AMI as a public AMI with a naming convention and have account owners search for the newest matching name when they launch instances
K: B
G: ## Image Builder in one picture
**EC2 Image Builder** automates the AMI lifecycle:
- an **image recipe** combines a parent image with build and test **components** (for example CIS hardening and validation tests),
- a **pipeline** runs the recipe on a schedule or when a dependency such as the parent image or an AWS-managed component gets a new version,
- **distribution settings** copy the AMI to chosen Regions and share it with accounts, or an organization or OUs, through launch permissions.
## Why it fits
It replaces hand-built scripts with a repeatable, tested build that responds to new base images and shares the result centrally. Workload accounts consume images; they do not build their own.
W: An Image Builder pipeline with hardening and test components, triggered by new parent image versions and distributing to the organization, gives an automated, tested and centrally controlled golden AMI flow.
X: A=Custom Lambda build: this reinvents the pipeline without tests, image versioning or tracked distribution, and building on the previous AMI compounds drift instead of starting from a known base.
C=Per-account patching and AMIs: 60 accounts would each produce a different image, with no central hardening or testing, and running instances are patched but not a controlled image.
D=Public AMI: public sharing exposes the image to everyone and would leak the hardened configuration, and searching by name is not a governed way to select an approved image.
T: Use Image Builder pipelines to build, test and share golden AMIs automatically from updated base images, with distribution to the organization or OUs.
V: Amazon EC2 Image Builder, Amazon EC2

@ SCS-C03 D6 T6.2 advanced use-case
S: A company deploys infrastructure with Terraform from a CodePipeline pipeline. The security team needs any plan that creates public S3 buckets or open security groups to fail before it is applied, and it must not be possible for engineers to skip the check by running terraform apply from their laptops with their own credentials. Which design meets both requirements?
A: Add a CodeBuild stage that runs a policy-as-code scan on the plan output, and let only the pipeline's deploy role change infrastructure while engineers get read-only access
B: Add a CodeBuild scan stage after the apply stage and send a notification to the security channel when the scan finds a noncompliant resource
C: Publish the policy checks as a pre-commit hook in the team repository and ask engineers to install the hook before they push changes
D: Run the scan in the pipeline, and grant engineers the deploy role through a permission set so they can run the same apply commands locally if the pipeline is down
K: A
G: ## Policy as code, in the right place
**Policy-as-code** tools such as Open Policy Agent (conftest) or Checkov evaluate Terraform plans against rules written as code. Where the check runs and who can bypass it matter as much as the rules.
- Run it in the **pipeline before apply**, on the plan output, so that a violation stops the deployment.
- Make the pipeline the only path: the role that can create or change infrastructure is assumed by the pipeline, and people receive read-only or break-glass access.
## Why the second half matters
A scan that a human can skip is advice, not a control. Removing direct write access closes the bypass while keeping the process auditable.
W: A scan stage on the plan output blocks noncompliant changes before apply, and restricting write access to the pipeline deploy role removes the local-apply bypass.
X: B=Scan after apply: by then the public bucket or open group already exists, so the check detects instead of prevents, and engineers could still apply locally.
C=Pre-commit hook: hooks run on developer machines, are optional, and are easily skipped, so they cannot be a control the security team relies on.
D=Deploy role for engineers: this keeps the local apply path open, so the pipeline scan can be bypassed by anyone with the permission set.
T: Enforce policy-as-code on the plan inside the pipeline and make the pipeline's role the only one that can deploy; otherwise the check can be bypassed.
V: AWS CodePipeline, AWS CodeBuild, AWS IAM

@ SCS-C03 D6 T6.2 advanced tradeoff
S: A deployment pipeline builds the configuration of an RDS instance and several other resources as JSON before creating them. The team wants to check that configuration against the organization's AWS Config rules before anything is created, so that violations fail the build, without deploying test resources into an account. Which approach fits?
A: Deploy the resources into a sandbox account and wait for the AWS Config rules to evaluate them, then delete the resources if any rule reports noncompliance
B: Use Config rules that support proactive evaluation and call StartResourceEvaluation from the pipeline with the planned resource configuration, then check the result
C: Enable Config auto-remediation on the same rules so that noncompliant resources are corrected automatically a short time after they are created
D: Query the aggregator with an advanced query to find resources that already match the planned configuration and copy the compliant ones
K: B
G: ## Detective and proactive Config rules
Most AWS Config rules run in **detective** mode: they evaluate a resource after it is created or changed. For some rules you can also turn on **proactive** evaluation mode: you pass a resource's configuration to Config before the resource exists, and Config tells you whether it would be compliant.
- The pipeline calls `StartResourceEvaluation` with the resource type and its configuration, then reads the result with `GetResourceEvaluationSummary`.
- Only rules that support the proactive mode can be used this way, and the rule must have it enabled.
## Where it fits
This gives shift-left compliance checking with the same rules used to monitor running resources, without creating anything. CloudFormation Hooks and Control Tower proactive controls cover the CloudFormation deploy path; the Config API is useful in other pipelines.
W: Proactive evaluation lets the pipeline submit the planned configuration to Config and get a compliance result before anything is created, so violations can fail the build.
X: A=Sandbox deployment: it creates real resources, takes time and cost, and detects rather than prevents, which is the situation the team wants to avoid.
C=Auto-remediation: remediation runs after a noncompliant resource exists, and the resource is still created first, so it does not fail the build.
D=Aggregator advanced query: an aggregator query reports the configuration of existing resources and cannot evaluate a configuration that has not been deployed yet.
T: Use Config proactive evaluation (StartResourceEvaluation) to test planned configurations against Config rules before deployment; detective rules and remediation act only after creation.
V: AWS Config, AWS CodePipeline

@ SCS-C03 D6 T6.2 advanced troubleshooting
S: A team deploys with GitHub Actions to AWS by using an IAM OIDC identity provider and a deploy role, replacing long-lived access keys. A security review finds that workflows from repositories that should have no access to production can assume the production deploy role. The trust policy only checks the aud claim. What is the correct fix?
A: Add a condition on the token's sub claim in the trust policy, limiting it to the specific repository and branch or environment, and keep the aud condition
B: Add an aws:SourceIp condition to the trust policy that lists the published GitHub Actions IP ranges, so only GitHub-hosted runners can assume the role
C: Attach a permissions boundary to the role that denies IAM actions, because the problem is that workflows can create other identities
D: Replace the OIDC provider with an IAM user for the pipeline and rotate its access keys every 30 days from a secrets manager
K: A
G: ## OIDC federation for pipelines
With **OIDC federation**, GitHub Actions requests a signed token per workflow run and calls `sts:AssumeRoleWithWebIdentity`. There are no long-lived AWS keys.
## The claims that matter
- `aud` identifies the audience (normally `sts.amazonaws.com`).
- `sub` identifies who is running: repository, and the branch, tag or environment, in a form like `repo:ORG/REPO:ref:refs/heads/main` or `repo:ORG/REPO:environment:production`.
If the trust policy checks only `aud`, every workflow that GitHub issues a token for can assume the role, in every repository of every organization. Restricting `sub` (with `StringEquals` or `StringLike`) limits assumption to the one repository and environment that should deploy to production.
W: A trust policy condition on the sub claim scopes role assumption to the exact repository and branch or environment, while the aud check keeps the token audience correct.
X: B=Source IP ranges: GitHub-hosted runner ranges are shared by all customers and are large and changing, so the condition does not identify the repository, and self-hosted runners would break.
C=Permissions boundary denying IAM: this limits the role's own permissions but does nothing about who can assume it; unrelated repositories would still be able to deploy.
D=IAM user with rotated keys: this goes back to long-lived credentials, which OIDC was introduced to remove, and does not identify the workflow either.
T: Trust policies for OIDC roles must restrict the sub claim to the specific repository and ref or environment; checking only aud lets any workflow assume the role.
V: AWS IAM, AWS STS

@ SCS-C03 D6 T6.2 advanced use-case

@ SCS-C03 D6 T6.2 advanced troubleshooting
S: A build account produces golden AMIs whose snapshots are encrypted with the AWS managed key aws/ebs. The team shares an AMI with a workload account, but the workload account cannot launch instances from it or copy it. Which change makes the sharing work?
A: Add the workload account to the AMI launch permissions and to the create volume permissions of each backing snapshot, then retry the launch
B: Re-encrypt the AMI's snapshots with a customer managed KMS key whose key policy allows the workload account, then share the AMI and the key
C: Add a statement to the aws/ebs key policy that allows the workload account to use it, since AWS managed key policies can be edited by the account owner
D: Turn on EBS encryption by default in the workload account so that it can decrypt the images encrypted in the build account
K: B
G: ## Why the AWS managed key blocks sharing
An encrypted AMI is backed by encrypted snapshots. To launch from a shared encrypted AMI, the other account needs permission to use the KMS key that encrypted the snapshots.
- The **AWS managed key** `aws/ebs` has a key policy you cannot edit, and it only permits use within your own account. Snapshots encrypted with it cannot be shared with other accounts.
- A **customer managed key** has a key policy you control. Allow the target account (or its roles) to use the key, for example `kms:Decrypt`, `kms:DescribeKey`, `kms:CreateGrant` and `kms:ReEncrypt*`, and share the AMI as usual.
## Fix
Copy the AMI so the snapshots are re-encrypted with a customer managed key that allows the workload account, then share the copy. Image Builder distribution settings can apply this encryption during distribution.
W: Re-encrypting with a customer managed key that trusts the workload account lets that account use the key and launch from the shared AMI.
X: A=Launch and snapshot permissions: these control access to the image and snapshots, but the workload account still cannot use the KMS key that encrypted the snapshots, so the launch and copy fail.
C=Editing the aws/ebs policy: the key policy of AWS managed keys is managed by AWS and cannot be changed by the account owner.
D=Encryption by default in the workload account: this encrypts new volumes there and does not give the account permission to use the build account's key.
T: Encrypted AMIs can only be shared with other accounts when they use a customer managed KMS key that allows those accounts; the AWS managed EBS key cannot be shared.
V: Amazon EC2, AWS KMS, Amazon EC2 Image Builder

@ SCS-C03 D6 T6.2 advanced use-case
S: A company runs microservices on Amazon EKS and wants only container images built by its own CI pipeline to be admitted to production clusters. Images are stored in Amazon ECR. Which approach enforces this?
A: Sign each image in the pipeline with AWS Signer and verify the signature with an admission controller policy that rejects unsigned images

C: Use an ECR lifecycle policy that deletes images not tagged with the pipeline's build number, so only pipeline images remain

K: A
G: ## Provenance versus vulnerabilities
Knowing that an image came from your pipeline is a different question from knowing that it has no known vulnerabilities.
- **Image signing** (for example AWS Signer with the Notation tooling) makes the pipeline attach a signature that ties the image digest to your signing profile.
- **Admission control** in Kubernetes (a policy engine such as Kyverno, or a verification webhook) checks the signature before a pod is admitted. Unsigned or wrongly signed images are rejected at the cluster boundary.
- **Scanning** with Amazon Inspector tells you about vulnerabilities. It complements signing but does not prove origin.
## Why the other layers are not enough
IAM on the repository limits who pushes but not what a cluster is allowed to run; anyone who obtains that role, or an image pulled from elsewhere, is indistinguishable without verification at admission.
W: Signing in the pipeline and verifying the signature at cluster admission ensures that only images produced and signed by the pipeline can run.
X: B=Enhanced scanning: it reports vulnerabilities and does not establish who built an image. A malicious image with no known CVEs would pass.
C=Lifecycle policy: lifecycle rules manage image retention, run periodically, and a tag such as a build number can be applied by anyone who can push.
D=Push permission only: this limits who can push but nothing verifies images at admission, so the cluster would run whatever is referenced, including images from other registries.
T: To run only trusted images, sign them in the pipeline and verify the signature at admission; scanning and repository IAM address different risks.
V: AWS Signer, Amazon ECR, Amazon EKS

@ SCS-C03 D6 T6.3 applied use-case
S: A security team wants to find IAM roles, users and permissions across all accounts in the organization that have not been used in the last 90 days, so they can remove them safely. The analysis should be centrally managed and cover future accounts too. Which approach fits?
A: Create an IAM Access Analyzer unused access analyzer for the organization in the delegated administrator account with a 90-day tracking period
B: Create an external access analyzer with the organization as the zone of trust, since it also reports which roles have not been used for a long time
C: Run an AWS Config rule that lists IAM roles with no attached policies in each account and aggregate the results centrally
D: Enable CloudTrail data events for IAM in every account and query the logs for roles that show no activity in the last 90 days
K: A
G: ## Two Access Analyzer families
IAM Access Analyzer has different analyzer types:
- **External access analyzers** find resources (S3 buckets, KMS keys, roles and others) shared outside the zone of trust, which is an account or the organization.
- **Unused access analyzers** find access that is granted but not used: unused roles, unused IAM user access keys and passwords, and unused permissions (services and actions) in active roles and users.
## Organization scope
An unused access analyzer can be created for the organization from the management account or a delegated administrator. You set a tracking period (unused-access age, for example 90 days), and findings cover existing and new accounts. Findings include suggested policy changes for unused permissions.
W: An organization unused access analyzer set to a 90-day tracking period reports unused roles, keys and permissions across all current and future accounts from one place.
X: B=External access analyzer: it reports resources accessible from outside the zone of trust, not identities that are unused.
C=Config rule for roles without policies: it finds roles that have no policies attached, not roles or permissions that have not been used, and gives no usage history.
D=CloudTrail data events for IAM: IAM actions are management events, and stitching usage together from logs yourself is a large custom effort compared with the built-in analyzer.
T: For unused roles, keys and permissions across an organization, use an unused access analyzer; for outside access to resources, use an external access analyzer.
V: IAM Access Analyzer, AWS IAM

@ SCS-C03 D6 T6.3 applied use-case
S: A healthcare company has 45 accounts in an organization and must sign the AWS Business Associate Addendum (BAA) so that it covers all of them. The compliance team also downloads SOC and ISO reports for auditors. Where should they do this with the least effort?
A: Send an email to the account manager with the list of account IDs, because BAAs are signed on paper outside the console

AWS Artifact is the self-service portal for compliance documents. It has two parts:
- **Artifact Reports**: AWS compliance reports such as SOC and ISO certificates, and other third-party audit reports. Some require accepting confidentiality terms first.

@ SCS-C03 D6 T6.3 advanced use-case
S: AWS Security Hub CSPM in the delegated administrator account receives findings from 70 accounts. The security team wants findings for resources in accounts of the Sandbox OU with a certain low-impact control automatically set to suppressed, and wants findings for resources tagged Environment=prod to be raised to a higher severity, without writing Lambda code. What should they configure?
A: Two EventBridge rules that invoke Lambda functions calling BatchUpdateFindings on each matching finding
B: A Security Hub CSPM central configuration policy that disables the control in the Sandbox OU and lowers severities in the production accounts
C: A Security Hub custom insight for each condition and a manual review of each insight's results every day by the team
D: Two Security Hub automation rules with criteria on account and resource tags whose actions suppress the findings or update their severity
K: D
G: ## Automation rules
**Security Hub automation rules** change findings automatically as they are ingested, without Lambda or EventBridge. A rule has:
- **criteria** on finding attributes (for example account ID, control, severity, resource type, resource tags),
- **actions** such as updating severity, workflow status (for example SUPPRESSED), confidence or criticality, adding a note, or adding user-defined fields.
Rules run in order. In an organization they are created from the delegated administrator account and apply to findings from the member accounts. (Security Hub CSPM is the former AWS Security Hub, which now also has newer automation rules for the unified Security Hub.)
## Automation rules versus other tools
- **Central configuration policies** decide which standards and controls are enabled and their parameters in which accounts. They do not change the severity of individual findings.
- **EventBridge** and Lambda are for external actions such as remediation or ticketing.
W: Automation rules match on account and resource tags and then suppress findings or raise severity as findings arrive, with no code to maintain.
X: A=EventBridge with Lambda: it works, but it is custom code to maintain and the team explicitly wants no Lambda code; automation rules are the built-in feature for editing findings.
B=Central configuration policy: it enables, disables and configures controls for accounts and OUs, and it cannot lower or raise the severity of findings. Disabling the control would also hide it entirely rather than suppress specific findings.
C=Custom insights: an insight is a saved filtered view for analysts and does not modify findings.
T: Use Security Hub automation rules to suppress or re-rate findings by criteria such as account and resource tags; use central configuration for enabling controls and EventBridge for external actions.
V: AWS Security Hub CSPM, Amazon EventBridge

@ SCS-C03 D6 T6.3 advanced troubleshooting
S: A company acquired a subsidiary that runs 12 AWS accounts in a different AWS Organization. The central compliance team wants to see the Config compliance of those accounts in its aggregator. The existing aggregator in the delegated administrator account uses the organization as its source, and the subsidiary accounts do not appear. What should the team do?
A: Create an additional aggregator with the subsidiary accounts as individual sources, and have each subsidiary account authorize the aggregator account
B: Enable trusted access for AWS Config in the subsidiary organization and it will appear automatically in the same aggregator
C: Create a Config conformance pack in the central account with the subsidiary account IDs in the target list
D: Move the subsidiary accounts into the central organization's root by using the aggregator authorization, which does not require an invitation
K: A
G: ## Aggregator sources
An **AWS Config aggregator** collects configuration and compliance data from other accounts and Regions into one account.
- With an **organization source**, it covers all accounts of one organization and needs trusted access and a delegated administrator or the management account.
- With **individual accounts** as sources, each source account must **authorize** the aggregator account and Region by creating an aggregation authorization (`PutAggregationAuthorization`).
## Cross-organization data
Accounts in a different organization are not covered by an organization source. An aggregator uses either an organization source or individual account sources, so create a second aggregator for them, add their account IDs and have each account authorize it, or make the aggregator's organization the owner of those accounts by invitation if that is intended.
W: Accounts outside the organization can be aggregated only as individual account sources, in an aggregator that is separate from the organization-source one, and each account must authorize the aggregator account before data flows.
X: B=Trusted access in the other organization: this affects the other organization's own aggregators and does not connect its accounts to an aggregator in a different organization.
C=Conformance pack target list: a conformance pack deploys rules to accounts and cannot include accounts of another organization, and deploying rules is not the same as aggregating their data.
D=Move without invitation: accounts cannot be moved between organizations without leaving and accepting an invitation, and an aggregator authorization does not do that.
T: Aggregate accounts from another organization through a separate aggregator with individual account sources and an aggregation authorization from every source account.
V: AWS Config

@ SCS-C03 D6 T6.3 applied troubleshooting
S: A Config rule detects S3 buckets without Block Public Access, and the team attached an automatic remediation that uses an AWS Systems Manager Automation document for the action. The buckets stay noncompliant and the remediation execution shows an access denied error from the S3 API. The rule and the remediation configuration are correct. What is the most likely cause?
A: Automatic remediation only runs when a bucket has been noncompliant for 24 hours, so the team has to wait for the next evaluation cycle
B: The remediation is configured as automatic, and Config allows only manual remediation to call Systems Manager Automation documents
C: The role given as the Automation assume role lacks the S3 permission the document calls, or is not trusted by Systems Manager
D: Config cannot remediate S3 Block Public Access settings, because only the bucket owner signed in as the root user can change them
K: C
G: ## How Config remediation runs
An AWS Config **remediation action** runs an SSM Automation document, either manually or automatically when a resource is found noncompliant.
- The document runs with the permissions of the **AutomationAssumeRole** you specify in the remediation configuration.
- That role must trust `ssm.amazonaws.com` and hold the permissions the document needs, for example `s3:PutBucketPublicAccessBlock`.
- Automatic remediation can retry a set number of times and returns the outcome in the remediation execution status.
## Diagnosing failures
Config is only the trigger. An access denied error from the target API means the automation ran but the role it assumed cannot perform the action. Fix the role's permissions or trust, not the rule.
W: The Automation document runs as the assume role, so an S3 access denied error means that role is missing the S3 permission or its trust relationship is wrong.
X: A=24-hour wait: automatic remediation starts when the resource is evaluated as noncompliant, and the execution already ran, as the API error shows.
B=Manual only: Config supports automatic remediation with SSM Automation documents, which is the standard setup.
D=Root-only change: an IAM role with s3:PutBucketPublicAccessBlock can change these settings, so no root sign-in is needed. Remediation of this kind is a documented use of Config with Automation.
T: When a Config remediation fails with access denied, check the AutomationAssumeRole's permissions and trust, because the document runs with that role.
V: AWS Config, AWS Systems Manager Automation

@ SCS-C03 D6 T6.3 advanced use-case
S: Auditors need evidence that CloudTrail logs of the past year were not altered or deleted, including by administrators of the workload accounts. The organization trail already delivers logs to an S3 bucket. Which TWO measures provide this? (Select TWO)
A: Turn on S3 versioning in the workload accounts and ask administrators to sign a statement that they will not delete any objects
B: Enable CloudTrail log file integrity validation and validate the digest files with the CloudTrail validate-logs command
C: Copy the logs each month to an S3 bucket owned by the workload accounts so that each team keeps its own evidence
D: Encrypt the log bucket with a KMS key from the workload accounts so that only their administrators can read the logs
E: Deliver the logs to a bucket in a separate log archive account with S3 Object Lock in compliance mode and a retention period of at least one year
K: B,E
G: ## Evidence has two parts
Auditors ask two questions: were the logs changed, and could they have been deleted?
- **Log file integrity validation** makes CloudTrail write hourly digest files, signed by CloudTrail, containing the SHA-256 hashes of the delivered log files. Validation compares the logs against the digest, so modified, removed or forged log files are detected.
- **Object Lock in compliance mode** with a retention period makes objects immutable: no user, including the account root user, can shorten retention or delete them until it ends.
- A **separate log archive account** keeps the evidence out of the reach of workload administrators.
## Result
Integrity validation proves the content is unchanged, and immutable storage in a dedicated account makes deletion impossible during retention.
W: B=Integrity validation: signed digest files and hashes prove that log files were not modified, deleted or forged after delivery.
E=Object Lock in a log archive account: compliance mode retention makes the objects undeletable for a year, and the separate account keeps them away from workload administrators.
X: A=Versioning and a signed statement: versioning can be disabled or versions deleted by an administrator with permission, and a promise is not technical evidence.
C=Copies owned by workload teams: this puts the evidence in the hands of the people it is meant to be independent from and adds copies that nobody validates.
D=KMS key from workload accounts: encryption controls who can read the logs, not whether they can be changed or deleted, and it gives workload administrators control over access to the evidence.
T: Prove log integrity with CloudTrail log file validation, and prevent deletion with Object Lock in compliance mode in a separate log archive account.
V: AWS CloudTrail, Amazon S3
