@ Q001771 explain
G: ## How GuardDuty findings reach other tools
GuardDuty publishes every new finding (and updates to existing ones) as an event to Amazon EventBridge with source `aws.guardduty`. With a delegated administrator in AWS Organizations, findings from all member accounts also arrive in the administrator account, so one set of rules can cover 30 accounts.
## Severity as a number
Each finding has a numeric `detail.severity`: Low is 1.0-3.9, Medium 4.0-6.9, High 7.0-8.9 and Critical 9.0-10.0. EventBridge event patterns support **numeric matching**, for example:
- `"severity": [{"numeric": [">=", 7]}]` sends High and Critical findings to an SNS topic that pages on-call.
- `"severity": [{"numeric": ["<", 7]}]` in a second rule sends the rest to a ticketing target such as an SQS queue or a Lambda function that opens tickets.
Both rules see the same event stream; only the target changes.
W: EventBridge severity routing: two rules with numeric filters on `detail.severity` split one finding stream into an immediate paging path and a ticket path, centrally and without custom polling.
X: B=Metric filter on a console log: GuardDuty does not write findings to a "console log" in CloudWatch Logs, so there is nothing for a metric filter to match.
C=Generate only severe findings: GuardDuty has no setting to stop producing lower-severity findings, and the requirement still needs those findings to reach a ticket queue, so dropping them would break half the design.
D=Security Hub built-in paging: Security Hub has no native on-call paging feature; it also relies on EventBridge rules (or integrations) to notify people.
T: Route GuardDuty findings by severity with EventBridge numeric filters, not by trying to change what GuardDuty generates.

A trail always delivers log files to an S3 bucket. Sending events to CloudWatch Logs is a **separate, optional** setting on the trail: you name a log group and an IAM role that CloudTrail uses to write to it.
## How a metric filter works
A CloudWatch Logs metric filter watches one log group. For every new log event in that group that matches the pattern (for example `{ $.userIdentity.type = "Root" && $.userIdentity.invokedBy NOT EXISTS }`), it adds to a custom metric; an alarm then watches the metric.
- If no events are ingested into the log group, the filter has nothing to evaluate.
- The CIS root-usage control therefore depends on the trail -> CloudWatch Logs integration, not just on a working trail.
Here the trail is confirmed to deliver to S3 only, which is the classic gap.
W: Trail not delivering to the log group: without CloudTrail's CloudWatch Logs integration pointed at that log group, the root login never appears there, so the filter never matches and the alarm cannot fire.
X: A=Default value 0: the default value only fills periods with no matches; it does not stop a real match from publishing 1 and breaching the alarm.
B=GuardDuty prerequisite: metric filters are a CloudWatch Logs feature that works on any log group; GuardDuty is an independent service and plays no part.
C=Invalid pattern syntax: CloudWatch Logs validates filter patterns when the filter is created, and the stem's clue is that logging was verified only in S3, pointing to missing delivery rather than a pattern error.
T: A metric filter can only see what reaches its log group; confirm the trail sends events to CloudWatch Logs, not only to S3.

@ Q001779 explain
G: ## Sparse metrics and alarm states
A CloudWatch alarm has three states: `OK`, `ALARM` and `INSUFFICIENT_DATA`. The Lambda function here publishes `GuardDutyHighSeverityCount` only when a finding occurs, so most 5-minute periods have **no data points at all**.
## Treat missing data
Each alarm has a `TreatMissingData` setting:
- `missing` (default): no data -> `INSUFFICIENT_DATA`.
- `notBreaching`: no data counts as within the threshold -> `OK`.
- `breaching`: no data counts as breaching -> `ALARM`.
- `ignore`: keep the current state.
For an event-count metric, "no data" really means "zero findings", so `notBreaching` shows the true state. A real finding still publishes 1, which meets the threshold of 1 and moves the alarm to `ALARM`. (Publishing an explicit 0 each period also works, but costs extra calls.)
W: Treat missing data as notBreaching: quiet periods display as `OK`, and any real data point of 1 still triggers the alarm, so detection is unchanged.
X: A=Change the unit to None: the unit is only a label on data points; it does not create data for empty periods, so the alarm stays in `INSUFFICIENT_DATA`.
B=Delete the alarm: removes automated alerting for high-severity findings and makes detection depend on someone looking at a console.
C=Raise the threshold to 2: a single high-severity finding would no longer alarm, weakening detection, and empty periods would still show `INSUFFICIENT_DATA`.
T: For metrics that exist only when something happens, set missing-data handling to notBreaching instead of changing thresholds.

G: ## Composite alarms
A CloudWatch **composite alarm** watches the states of other alarms instead of a metric. Its rule expression combines them with `AND`, `OR` and `NOT`, for example:
`ALARM("UnauthorizedApiCalls") AND ALARM("RootAccountUsage")`
## Reducing alert noise
- Put the paging action (such as an SNS topic) on the composite alarm only.
- Leave the child alarms without paging actions. They keep evaluating, keep their own state history and remain visible on dashboards.
- The composite alarm goes to `ALARM` once when both children are in `ALARM`, so on-call gets one page instead of two for the same incident.
Composite alarms can also suppress actions during a known condition, such as a maintenance window.
W: Composite alarm with AND logic: it pages once when both alarms are firing together, while each child alarm still records its own history for later review.
X: B=Merged Logs Insights query: a saved query is for interactive analysis, and merging the filters would remove the two separate alarms whose history the team wants to keep.
C=Anomaly detection bands: they replace a static threshold with a learned band for one metric; they do not combine two alarms or reduce duplicate pages.
D=One-minute evaluation periods: shorter periods make each alarm react faster and potentially flap more, which increases paging rather than merging it.
T: To page once for correlated alarms while keeping each one, use a composite alarm and put actions only on it.

@ Q001781 explain
G: ## Management events versus data events
CloudTrail splits API activity into two kinds:
- **Management events** (control plane): operations that configure resources, such as `PutBucketPolicy`, `CreateBucket` or `RunInstances`. Trails log them by default, and event history keeps the last 90 days.
- **Data events** (data plane): operations on the data inside a resource, such as S3 `GetObject` and `PutObject` or DynamoDB item reads. They are high volume, are **not** logged by default and are billed separately.
## Enabling S3 data events
Add data events to the trail, preferably with **advanced event selectors** to limit cost, for example `resources.type` = `AWS::S3::Object` and `resources.ARN` starting with `arn:aws:s3:::sensitive-bucket/`.
In this incident, the bucket policy change was a management event (visible) while downloads were data events (never recorded).
W: Object reads are data events: `GetObject` is only recorded when S3 data events are enabled on the trail, ideally scoped with advanced event selectors.
X: A=Management events expiring after 24 hours: downloads are data events, not management events, and management events are kept 90 days in event history and as long as you keep them in a trail's bucket.
B=Logged only with Versioning: S3 Versioning keeps object versions; it has no effect on what CloudTrail records.
C=CloudTrail never logs S3: CloudTrail logs S3 object operations as data events; VPC Flow Logs show IPs and ports, not who called `GetObject`.
T: Configuration changes are management events (logged by default); object reads and writes are data events you must enable.

@ Q001783 explain
G: ## Reading the record
Source `203.0.113.5` port `443` to `10.0.1.20` port `51000` is an HTTPS server answering a connection the instance started: the instance used ephemeral port 51000 for its outbound request. This is **return traffic**.
## Stateful versus stateless filtering
- **Security groups** are stateful: if outbound traffic was allowed, the response is allowed automatically, whatever the inbound rules say.
- **Network ACLs** are stateless: return traffic is evaluated against the subnet's inbound NACL rules like any new packet. If there is no inbound rule allowing TCP `1024-65535` from that source, the response is rejected.
## What flow logs tell you
The `action` field is only `ACCEPT` or `REJECT`; it does not say whether a security group or a NACL made the decision. With the security group clearly allowing this traffic, the next check is the subnet's inbound NACL rules for ephemeral ports.
W: Likely the NACL: return traffic that a stateful security group would allow can still be dropped by a stateless NACL without an inbound ephemeral-port rule, and flow logs do not identify which layer rejected it.
X: A=Stateless security group: security groups are always stateful and cannot be switched to stateless, so they do not block responses to allowed outbound traffic.
B=Logging error: a flow log records `REJECT` whenever either layer drops traffic; a security group allowing it does not stop a NACL from rejecting it.
D=Shield Advanced blocked it: Shield Advanced mitigates DDoS attacks against protected resources; a `REJECT` in a VPC flow log reflects security group or NACL decisions, and a single HTTPS response is not a DDoS event.
T: REJECT on return traffic with a permissive security group points to a stateless NACL missing an inbound ephemeral-port rule.

G: ## What flow logs do not capture
VPC Flow Logs record IP traffic through network interfaces, but some traffic is always excluded. Examples:
- Traffic to and from the **Amazon-provided DNS server** (the VPC base CIDR plus two, such as `10.0.0.2`, or `169.254.169.253`).
- Instance metadata traffic to `169.254.169.254` and Amazon Time Sync traffic.
- DHCP traffic.
If an instance uses your own DNS server instead, that traffic is logged like any other.
## Getting DNS visibility
**Route 53 Resolver query logging** records DNS queries made from resources in a VPC: the query name, type, response code, answers and the source instance. Logs can go to CloudWatch Logs, S3 or Data Firehose. This is the right source for questions such as "which instance looked up this suspicious domain?".
W: Flow logs exclude Amazon DNS traffic: queries to the Amazon-provided resolver never appear in flow logs, so DNS investigations use Route 53 Resolver query logging.
X: A=DNS traffic type: the traffic type setting accepts only `ACCEPT`, `REJECT` or `ALL`; there is no DNS option, and `ALL` already includes everything that flow logs can capture.
C=UDP missed by the interval: flow logs record UDP flows normally, and the aggregation interval only groups packets into records; it does not drop them.
D=S3-only delivery: the destination (CloudWatch Logs, S3 or Firehose) changes where records are stored, not which traffic is captured.
T: Traffic to the Amazon-provided DNS resolver is never in flow logs; use Resolver query logging for DNS visibility.

G: ## What CloudTrail Insights does
CloudTrail Insights analyzes the **management events** a trail or event data store records (and, on trails only, data events if you enable data events Insights) and learns a baseline of normal activity. When activity deviates significantly from it, Insights generates an **Insights event**.

D=Baselines management activity: Insights learns normal API call and error rates for management events (and optionally data events on trails) and flags significant deviations.

G: ## Suppression rules
A GuardDuty **suppression rule** is a saved filter with auto-archive. New findings matching all its criteria are archived automatically: they are not sent to Security Hub, S3 exports, Detective or EventBridge, but they stay viewable as archived findings.
## Scoping narrowly
Good criteria combine the finding type with something that identifies the expected source, for example:
- Finding type = `Recon:EC2/PortProbeUnprotectedPort`
- plus the scanner's IP addresses or instance IDs or a tag such as `Role=vuln-scanner`.
Everything else, including the same finding type from other sources, still alerts.
## Why not IP lists
GuardDuty IP and entity lists apply only to traffic involving publicly routable addresses and domains, and they affect whole groups of finding types, so they are blunt tools for one internal scanner.
W: Narrow suppression rule: matching on finding type plus the scanner's identity archives only the known-benign findings and keeps the finding type active for real probes.
X: A=Disable the finding type: GuardDuty does not let you turn off individual finding types, and even if it did, real port probes from attackers would go undetected.
C=Threat list: a threat list marks IPs as malicious, so it makes GuardDuty generate more findings for the scanner, the opposite of the goal.
D=Trusted IP list: IP lists apply only to publicly routable addresses, while the scanner reaches neighbors in the VPC over private addresses, and a trusted entry would silence many finding types for that IP rather than this one.
T: Quiet known-benign GuardDuty findings with a narrow suppression rule (finding type plus source), not by disabling types or using IP lists.

G: ## Two kinds of GuardDuty IP lists
GuardDuty lets you upload lists from S3 (formats such as plain text or STIX) that change how it evaluates activity involving those entries: legacy IP address lists, or the newer, recommended entity lists that can also hold domains. Lists apply only to publicly routable addresses and domains.
- **Trusted IP list**: addresses you trust, such as your corporate egress IPs. GuardDuty does not generate findings for activity involving these entries. At most one trusted IP list and one trusted entity list per account per Region.
- **Threat list**: known malicious addresses, such as from a threat intelligence feed. GuardDuty generates findings when resources communicate with these IPs. Up to six threat lists can be active per account per Region.
Both are customer-provided, managed in the GuardDuty console or API, and in an organization the administrator account manages them for members.
Example: add your office NAT IPs to the trusted list, and a partner's malicious-IP feed as a threat list.
W: Trusted suppresses, threat detects: trusted IP lists stop certain findings for listed addresses, while threat lists cause findings for activity involving listed addresses.
X: A=Only in Security Hub: IP lists are a GuardDuty feature, configured in GuardDuty; Security Hub has no IP list setting.
B=Threat lists are AWS-generated: GuardDuty already uses its own internal threat intelligence, but threat lists are customer-supplied lists you upload and change.
D=Identical and interchangeable: the lists have opposite effects, one reducing findings and one creating them, so swapping them would reverse the behavior.
T: Trusted IP list = fewer findings for known-good IPs; threat list = findings for known-bad IPs.

G: ## How suppression rules match
A GuardDuty suppression rule archives every new finding that matches **all** of its filter criteria. It does not know your intent: if the only criterion is the subnet ID, then every finding type from that subnet is archived, including high-severity credential exfiltration.
Archived findings are not sent to Security Hub or EventBridge, so no alert fires, but they are **not deleted**: they remain visible under archived findings for the normal retention period.
## A correctly scoped rule
- Finding type, for example `Recon:EC2/PortProbeUnprotectedPort` or other specific Recon types.
- Severity, such as low only.
- A specific source, such as instance IDs, a tag or the scanner IPs, not a whole subnet.
Review suppression rules regularly and periodically review archived findings to catch rules that hide too much.
W: Rule too broad: criteria like "any finding from this subnet" matched the unrelated high-severity finding; adding finding type, severity and specific source criteria limits it to the intended noise.
X: A=Must be a trusted IP list: suppression rules are exactly what auto-archives findings, and trusted IP lists apply only to publicly routable addresses, not to internal instances in a subnet.
B=Permanently deleted: suppressed findings are archived, not deleted, so the team can review them, which is how this was discovered.
D=Only findings older than 7 days: suppression rules have no age condition; they act on new matching findings as they are generated.
T: Suppression rules archive everything that matches, so always include finding type and specific source criteria and review archived findings.
