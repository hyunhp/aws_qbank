@ Q001946 explain
G: ## Zone of trust and external access
IAM Access Analyzer's **external access analyzer** reads resource-based policies and reports every resource that a principal outside a chosen **zone of trust** can reach. The zone of trust is either the current account or the whole AWS Organization.
- It uses automated reasoning over the policy logic, so it finds access granted through wildcards and conditions, not just literal account IDs.
- Supported resources include S3 buckets, IAM role trust policies, KMS keys, Lambda functions and layers, SQS queues, Secrets Manager secrets and several snapshot types.
- Each finding names the resource, the external principal (for example account `444455556666` or `*`) and the actions allowed.
## Example
A role whose trust policy lets account `444455556666` call `sts:AssumeRole` produces a finding when that account is outside the organization. You then either archive it as intended or remove the trust statement, and the finding resolves on the next scan.
W: Access Analyzer with an org or account zone of trust: it is the feature built to list resources shared outside that boundary across S3, IAM roles, KMS keys and Lambda, which is exactly the review the engineer needs.
X: A=Trusted Advisor checks: its security checks cover a small, fixed set of items such as open S3 bucket permissions or exposed access keys; it does not analyze role trust policies, KMS key policies or Lambda resource policies against an organization boundary.
C=Macie: Macie discovers sensitive data inside S3 objects and reports bucket-level exposure for S3 only; it does not evaluate IAM role trust relationships, KMS keys or Lambda permissions.
D=Config aggregators: an aggregator only collects configuration and compliance data from many accounts and Regions into one view; without rules or queries it flags nothing, and it has no reasoning engine for external principals.
T: To find resources reachable from outside the account or organization, use IAM Access Analyzer's external access analyzer, not general best-practice or data-discovery tools.

@ Q001947 explain
G: ## What AWS Audit Manager does
AWS Audit Manager turns day-to-day AWS data into audit evidence. You create an **assessment** from a **framework** (prebuilt ones include SOC 2, PCI DSS and others, or you build a custom one). Each framework contains controls, and each control lists data sources.
- **Compliance checks** come from AWS Config rules and Security Hub CSPM controls.
- **User activity** comes from CloudTrail.
- **Configuration data** comes from snapshots of API calls describing resources.
- **Manual evidence** is uploaded files, such as a signed access-review attestation.
Evidence is collected continuously and attached to the matching control. An auditor-facing **assessment report** can then be generated and saved to S3.
## Example
A SOC 2 control about logical access can hold a Config result that MFA is enabled, CloudTrail sign-in activity and an uploaded quarterly access review, all in one place.
Note: AWS Audit Manager has been closed to new customers since April 30, 2026; existing customers can keep using it, and AWS points new users to AWS Config conformance packs.
W: Audit Manager with a SOC 2 framework: it collects automated and manual evidence, maps it to SOC 2 controls and exports an assessment report, which covers every part of the requirement.
X: A=Config alone: Config evaluates resource configurations, but it cannot hold CloudTrail activity or manual attestations and does not map results to SOC 2 control language or build a report.
C=AWS Artifact: Artifact provides AWS's own compliance reports (such as AWS's SOC reports) and agreements; it does not collect evidence about the customer's own environment.
D=Security Hub standards: Security Hub CSPM produces findings and a security score per standard, but it has no SOC 2 evidence package, cannot store manual attestations and does not produce auditor assessment reports.
T: Audit Manager maps evidence about your own environment to framework controls; Artifact only shares AWS's own reports, and Config or Security Hub only generate raw results.

@ Q001948 explain
G: ## How cross-Region aggregation works
The original Security Hub, now named **AWS Security Hub CSPM**, can gather findings from several Regions into one **aggregation Region** (also called the home Region).
- You choose the aggregation Region and a list of **linked Regions**, or let new Regions link automatically.
- Findings, insights and control status from a linked Region replicate to the aggregation Region.
- A Region only produces findings if Security Hub CSPM is **enabled there** for each account; aggregation copies findings, it does not create them.
GuardDuty and Config send results to Security Hub CSPM in the same Region, so a GuardDuty finding in `eu-west-1` needs Security Hub CSPM enabled in `eu-west-1` first.
## Example
With `us-east-1` as aggregation Region and only `us-west-2` linked, workloads in `eu-west-1` stay invisible centrally even if GuardDuty is active there. Enabling the service in `eu-west-1` for the members (central configuration can do this) and linking the Region fixes it.
W: Not enabled or not linked in eu-west-1: either gap stops findings from that Region reaching `us-east-1`, which matches the symptom that only that Region is missing.
X: B=No cross-Region aggregation: Security Hub CSPM does support aggregating findings from linked Regions into one aggregation Region; that is the feature the team already configured.
C=GuardDuty cannot forward across Regions: GuardDuty sends findings to Security Hub CSPM in its own Region, and aggregation then replicates them to the aggregation Region, so GuardDuty findings do arrive centrally once both steps are in place.
D=Delegated admin covers only itself: a delegated administrator manages and views findings for all member accounts in the organization; that is the purpose of the role.
T: Cross-Region aggregation only copies findings from Regions where Security Hub CSPM is enabled and linked; check both before blaming the sources.

@ Q001949 explain
G: ## Two different Access Analyzer jobs
IAM Access Analyzer has several features that look at policies from different angles.
- **Policy validation** checks a policy document before or while you write it. It returns findings of type `ERROR`, `SECURITY_WARNING`, `WARNING` and `SUGGESTION`, for example an invalid action name, a missing condition or `Principal: "*"` with no condition. It works for identity policies, resource policies, trust policies and SCPs, and is called through `ValidatePolicy` or the console editor.
- **External access findings** come from an analyzer that continuously evaluates policies already attached to resources and reports which ones grant access outside the zone of trust.
## Example
Pasting a new bucket policy into the editor shows validation warnings immediately. After the policy is saved, the analyzer reports a finding if account `444455556666` outside the organization can call `s3:GetObject`. (An access preview can show the external access result for a proposed policy before saving it.)
W: Validation before use versus findings on real access: validation lints the policy text for errors and risky patterns, while external access findings describe what attached policies actually allow outside principals to do.
X: A=Roles swapped: this reverses the features; syntax and best-practice checks are policy validation, and outside principals are found by the external access analyzer.
C=Validation only for identity policies: policy validation also checks resource-based policies such as S3 bucket policies, plus trust policies and SCPs.
D=Same feature: they use different APIs, run at different times and return different finding types, so they are not interchangeable.
T: Policy validation checks the policy text for mistakes; external access findings show which resources are actually reachable from outside the zone of trust.

@ Q001950 explain
G: ## Config rules and conformance packs
An **AWS Config rule** evaluates resources against one requirement. It can be AWS managed (such as `encrypted-volumes`) or custom, written as a Lambda function or in Guard policy language.
A **conformance pack** is a YAML template that bundles many rules, and optionally remediation actions, into one unit.
- A pack can mix managed and custom rules.
- An **organization conformance pack** deploys the same pack to every account in the organization from the management or delegated admin account.
- Packs report compliance as a group, which suits a baseline such as a sample pack for a security framework.
## Example
One custom rule checking that resources tagged `data-class=restricted` use a specific KMS key can be deployed to five accounts on its own. Later, the same rule can be added to a broader baseline pack that rolls out organization-wide.
W: Simple single rule versus reusable pack: one custom rule is the least overhead for a narrow need in a few accounts, while a pack packages rules for repeatable, organization-wide baselines and group reporting.
X: B=Packs require Security Hub: conformance packs are a Config feature and do not depend on Security Hub CSPM being enabled.
C=No tradeoff: a single rule is created per account and Region, while a pack deploys a set of rules as one template, can be deployed across the organization and reports compliance as a group.
D=Only managed rules: conformance packs can include custom Lambda and Guard rules in addition to AWS managed rules.
T: Use a single custom rule for one narrow control; use a conformance pack (which can include that custom rule) when you need a reusable baseline across the organization.

@ Q001951 explain
G: ## Findings as events
Security Hub CSPM sends every new or updated finding to **Amazon EventBridge** automatically, with detail type `Security Hub Findings - Imported`. An EventBridge rule can match on fields inside the finding, such as severity label, resource type and control ID, and send matching events to a target such as a Lambda function.
- The event pattern can require, for example, `Severity.Label` = `HIGH` and a control that detects public S3 buckets.
- The Lambda function receives the finding, reads the bucket name from the resource ARN, and applies S3 Block Public Access or removes the public statement.
- It can then update the finding's workflow status to `RESOLVED` so analysts see what happened.
## Why filter narrowly
Automatic remediation is safe only for well-understood cases. A tight event pattern keeps the Lambda function from touching buckets that are meant to be public, for example ones tagged for a static website.
W: EventBridge rule with filtered findings to Lambda: this reacts within seconds to exactly the chosen finding type and removes public access with no analyst involved.
X: A=Daily CSV plus analyst: a daily export leaves the bucket public for up to a day and still needs a person to run the fix, the opposite of the requirement.
B=Config auto-remediation only: Config remediation acts on Config rule results, not on Security Hub CSPM findings in general, so findings from other sources such as Macie or Access Analyzer would not be handled.
D=CloudTrail Insights: Insights detects unusual rates of API calls or errors; it does not read Security Hub findings and cannot change bucket policies.
T: To auto-remediate a specific Security Hub finding type, match it with an EventBridge rule and invoke a remediation Lambda; Config remediation only covers Config rules.

Config rules and Security Hub CSPM produce continuous **results**: compliant or noncompliant resources and findings. Auditors want **evidence mapped to controls**: for each SOC 2 control, which proof exists and for what period.
AWS Audit Manager bridges the gap:
- It pulls evidence automatically from Config, Security Hub CSPM, CloudTrail and API snapshots.

D=Disable Config and Security Hub: removing them deletes the main automated evidence sources, making audits harder, not easier.

@ Q002053 explain
G: ## Seeing inside the node
Many container attacks happen entirely on the worker node: a pod downloads a miner, or an attacker opens a **reverse shell** (an outbound connection that gives them a command prompt). The Kubernetes API never sees these actions.
**GuardDuty Runtime Monitoring** for EKS installs a GuardDuty security agent (as an EKS add-on, managed automatically if you choose) on the nodes. The agent collects operating-system events:
- process creation and execution,
- file access and modification,
- network connections and DNS queries.
GuardDuty combines these with threat intelligence and produces findings such as `CryptoCurrency:Runtime/BitcoinTool.B` or `Execution:Runtime/ReverseShell`, including the pod, container and process involved.
## Example
A pod runs `xmrig` and connects to a mining pool. The runtime agent reports the process and connection, and GuardDuty raises a finding naming the cluster, namespace and pod.
W: GuardDuty EKS Runtime Monitoring: its node agent sees process execution, file access and network activity inside pods, which is the only way among these options to detect miners and reverse shells.
X: A=Control plane audit logs: audit logs record Kubernetes API calls such as creating a pod or reading a secret; they do not show processes started or files opened inside a running container.
C=Inspector image scanning: Inspector finds known vulnerabilities in images before or while they run; it does not observe runtime behavior such as a miner or a reverse shell started by an attacker.
D=Manual Flow Log search: Flow Logs only record IPs, ports and bytes, with no process or file information, and manual searching for pool IPs is slow and misses new or proxied addresses.
T: Threats that happen inside running containers need a runtime agent, so use GuardDuty Runtime Monitoring rather than audit logs or image scanning.

@ Q002054 explain
G: ## Three separate requirements
- **Central:** an **organization trail** created in the management account (or a delegated administrator account) logs events from every member account to one S3 bucket, and member accounts cannot disable it.
- **Tamper-evident:** **log file validation** makes CloudTrail write an hourly digest file containing SHA-256 hashes of each log file, signed with a private key. The `validate-logs` CLI command then proves whether any file was changed or removed.
- **Undeletable:** **S3 Object Lock in compliance mode** with a 7-year retention prevents any user, including the root user, from deleting or overwriting object versions until retention expires.
## Example
The trail writes to `s3://org-audit-logs/AWSLogs/o-abc123/...` in a log-archive account. The bucket has Object Lock with a default retention of 7 years in compliance mode, and validation digests land alongside the logs.
W: Org trail with validation to a compliance-mode Object Lock bucket: the organization trail centralizes all accounts, validation detects tampering, and compliance-mode retention blocks deletion by everyone for 7 years.
X: A=Event history: event history shows only 90 days of management events per account and Region; it is not central, not immutable and far short of 7 years.
B=MFA Delete: MFA Delete only adds an MFA step to permanently deleting versions; the root user with the MFA device can still delete logs or turn MFA Delete off, so it is not a 7-year guarantee, and it provides no tamper detection.
C=Per-account trails to local buckets: logs stay spread across accounts where local administrators can delete them, so they are neither central nor protected from deletion.
T: Organization trail for coverage, log file validation for integrity, and Object Lock in compliance mode for immutability.

@ Q002055 explain
G: ## What Amazon Security Lake does
Amazon Security Lake builds a security data lake in S3 in your own account. It collects logs, converts them to the **Open Cybersecurity Schema Framework (OCSF)** and stores them as Apache Parquet, managed with Lake Formation.
- Native AWS sources include CloudTrail management and data events, VPC Flow Logs, Route 53 Resolver query logs, Security Hub findings, EKS audit logs and AWS WAF logs.
- **Custom sources**, such as a third-party firewall, can write OCSF data into the lake.
- **Subscribers** get either data access (new objects announced through SQS or HTTPS) or query access (through Lake Formation, for example with Athena).
## Example
One SIEM subscribes with data access and ingests every new Parquet file, while a second analytics tool queries the same tables. Neither needs a separate collection pipeline per source because the schema is identical.
W: Security Lake with OCSF and subscribers: it centralizes AWS and third-party logs in one normalized schema and shares them with several SIEM tools through subscriber access.
X: B=Security Hub insights: insights group findings (for example by resource or severity); Security Hub does not store raw CloudTrail, flow, DNS or firewall logs for SIEMs to consume.
C=Detective behavior graphs: Detective builds its own graph from a few sources to help investigations; it is not a normalized store that external SIEM tools subscribe to, and it does not ingest third-party firewall logs.
D=Logs Insights saved queries: a saved query only searches logs already in CloudWatch Logs; it does not normalize formats or distribute data to several SIEM tools.
T: When the goal is one normalized (OCSF) store of security logs that many tools can consume, use Security Lake, not a findings or investigation service.

@ Q002056 explain
G: ## Contain first, keep the evidence
Incident response on EC2 follows a pattern: **isolate** the instance so it can do no more harm, **preserve** the state for forensics, then investigate and remediate.
- **Isolation security group:** replace all security groups on the instance with one that has no inbound or outbound rules (or allows only a forensics host). New connections to the command-and-control server stop. Connections that security groups already track are not interrupted by the swap and can persist while traffic keeps flowing, so teams often add a deny network ACL as well.
- **Evidence:** take EBS snapshots of all volumes, and capture memory with a tool on the instance before any restart, because running processes and network connections exist only in RAM.
- Tag the instance (for example `status=quarantined`) and remove it from Auto Scaling groups and load balancers so it is not replaced or terminated automatically.
## Example
A GuardDuty `Backdoor:EC2/C&CActivity.B` finding triggers the swap of `sg-isolate` and snapshots of `vol-...` before anyone logs in.
W: B=Isolation security group: replacing the groups cuts the instance off from the command-and-control server while keeping it running for investigation.
D=Snapshots and memory: EBS snapshots and a memory capture preserve disk and in-memory evidence before anything else changes the instance.
X: A=Terminate immediately: termination loses memory contents and, with default settings, deletes the root volume, destroying the evidence the team must keep.
C=Reboot: a reboot wipes memory, including the malicious process and its connections, and may not remove persistence on disk.
E=Delete the finding: GuardDuty findings cannot be deleted by users, only archived, and hiding the record removes context responders and auditors need.
T: Isolate with a restrictive security group and snapshot disks and memory first; terminating or rebooting destroys evidence.

@ Q002057 explain
G: ## How fast leaked keys are used
Automated scanners watch public repositories and try leaked AWS access keys within minutes. An hour of exposure means the key must be treated as **already compromised**.
## Response order
- **Deactivate** the access key (`UpdateAccessKey` with status `Inactive`). This stops all use at once and can be reversed if something legitimate breaks; **delete** it once a replacement key is in place.
- **Review CloudTrail** for calls made with that access key ID (for example `AKIA...EXAMPLE`): new IAM users or keys, launched instances, changed policies or data access.
- Remove anything the attacker created, and check GuardDuty findings.
- Remove the secret from the repository history too, but that alone does not revoke it.
AWS may also attach a quarantine managed policy to the user when it detects a public exposure, but you should not rely on that.
W: Deactivate then delete, then review CloudTrail: disabling the key cuts off the attacker immediately, and CloudTrail shows what was done with it so the team can clean up.
X: A=Rotate the console password: the leaked credential is the access key, which works independently of the password, so the attacker keeps full API access.
B=Delete the repository: the key has likely been copied already, and deleting the repository does nothing to stop API calls that use it.
D=Enable MFA: an MFA device protects console sign-in; access key API calls are not blocked by MFA unless policies explicitly require it, so the key keeps working.
T: A leaked access key must be deactivated first; cleaning up the repository or password does not revoke it.

@ Q002058 explain
G: ## Event-driven, auditable response
GuardDuty sends every finding to **EventBridge**. A rule can match on the numeric `severity` (High is 7.0 to 8.9 and Critical is 9.0 to 10.0, so match 7 and above) and on resource type `Instance`.
The rule target is an **AWS Step Functions** state machine that runs the playbook:
- tag the instance, for example `ir-status=isolated`,
- swap in an isolation security group,
- create EBS snapshots,
- publish to an SNS topic or chat channel for responders.
A Standard workflow records every execution with each step's input, output, timing and errors, so the history can be audited. Built-in retries and error handling make the process repeatable, and each task calls AWS APIs directly or through Lambda.
## Example
A `CryptoCurrency:EC2/BitcoinTool.B!DNS` finding at severity 8 starts an execution within seconds; the execution history shows which steps ran, with what result and when, for the incident record.
W: EventBridge starting Step Functions: findings trigger the workflow immediately and the state machine runs the same ordered, logged steps every time.
X: A=Daily Lambda report: a daily email delays response by up to a day and performs none of the tagging, isolation or snapshots.
B=Manual insights review: someone has to notice and act, so response time and quality vary and there is no automated, step-by-step audit trail.
C=SNS paging for manual steps: notifying people is only one step; the remaining actions stay manual and inconsistent.
T: For repeatable, auditable incident response, trigger a Step Functions playbook from EventBridge rather than relying on reports or people.

@ Q002059 explain
G: ## Amazon Inspector in brief
Amazon Inspector is AWS's vulnerability management service. Once activated (optionally organization-wide through a delegated administrator), it discovers resources automatically and keeps scanning them:
- **EC2 instances** for OS package and application vulnerabilities and network reachability, using the SSM Agent or agentless snapshot scanning.
- **Container images in ECR** on push and continuously afterward.
- **Lambda functions** for vulnerable dependencies, with optional code scanning of the function's own code.
When a new CVE is published, Inspector rescans affected resources automatically, and it closes findings when a fix is applied. Each finding has an Inspector risk score that adjusts the CVSS score for the environment, for example lower if the instance is not reachable from the internet.
## Example
A new OpenSSL CVE is published. Inspector flags the ECR images and EC2 instances that include the affected package version without anyone starting a scan.
W: Inspector: it continuously scans EC2, ECR images and Lambda functions for known vulnerabilities and rescans automatically when new CVEs appear.
X: A=GuardDuty Malware Protection: it scans EBS volumes, S3 objects or backups for malicious files, not for missing patches or vulnerable packages.
B=Macie: Macie discovers sensitive data such as personal information in S3; it does not assess software vulnerabilities.
D=Trusted Advisor: Trusted Advisor runs account-level best-practice checks (cost, limits, some security settings) and does not inventory packages or match them against CVEs.
T: Known software vulnerabilities (CVEs) are Inspector's job; GuardDuty looks for threats and malware, Macie for sensitive data.

@ Q002060 explain
G: ## Filtering egress by domain
Security groups and network ACLs filter on IP addresses, ports and protocols only. Package repositories and SaaS APIs change IPs often, so an allow list must work on **domain names**.
**AWS Network Firewall** has stateful **domain list rule groups**:
- For HTTPS, it reads the **Server Name Indication (SNI)** in the TLS ClientHello, which carries the hostname in clear text; for HTTP it reads the `Host` header.
- An allow list such as `.pypi.org`, `.npmjs.org` and `api.payments.example.com` passes matching traffic; the policy's default action drops everything else.
## Placement
Private subnets route `0.0.0.0/0` through the firewall endpoint (often together with a NAT gateway), so every outbound flow is inspected before it reaches the internet gateway.
W: Network Firewall domain allow list with SNI: it lets through only HTTPS sessions to approved hostnames and drops all other outbound traffic.
X: A=Security groups with domain names: security group rules accept CIDRs, prefix lists or other security groups, not DNS names, so domains cannot be listed.
B=NACL allowing 443 to 0.0.0.0/0: this allows HTTPS to every address on the internet, the opposite of a short allow list.
C=NAT gateway with a port-limited route: route tables choose a next hop by destination CIDR only and have no port or domain matching; a NAT gateway translates addresses but does not filter.
T: Security groups, NACLs and routes see IPs and ports; allowing only specific domains needs Network Firewall's stateful domain (SNI) rules.

@ Q002061 explain
G: ## How SSRF steals role credentials
The instance metadata service (IMDS) at `169.254.169.254` hands out temporary credentials for the instance role at `/latest/meta-data/iam/security-credentials/<role>`. With **IMDSv1**, a single `GET` returns them. An SSRF flaw lets an attacker make the application send that `GET` for them.
## What IMDSv2 changes
IMDSv2 requires a session token:
- The caller first sends a `PUT` to `/latest/api/token` with header `X-aws-ec2-metadata-token-ttl-seconds`.
- Every metadata request must then carry the token in `X-aws-ec2-metadata-token`.
Typical SSRF flaws can only make simple `GET` requests with no custom headers, so they cannot get a token. IMDSv2 also rejects token requests that contain an `X-Forwarded-For` header, and the **hop limit** (`HttpPutResponseHopLimit`, the IP TTL of the token response) set to 1 stops the token from travelling beyond the instance; use 2 if containers on the host need IMDS.
Set `HttpTokens=required` on instances, in launch templates, or as an account default, so IMDSv1 is turned off.
W: Require IMDSv2 with a low hop limit: the token handshake blocks the simple requests an SSRF flaw can make, so the role credentials can no longer be read.
X: A=EBS encryption: it protects data at rest on volumes and has no effect on HTTP calls to the metadata service.
C=Access keys in config: long-term keys in a file are easier to steal (through file-read bugs or source leaks), never expire on their own and replace a safer design with a worse one.
D=Private subnet with NAT: SSRF works from inside the instance, and IMDS is reachable locally regardless of subnet type, so moving the instance changes nothing.
T: SSRF against IMDS is stopped by requiring IMDSv2 session tokens, not by network placement or encryption.

@ Q002062 explain
G: ## Attribute-based access control (ABAC)
With ABAC, permissions depend on **tags** that match between the caller and the resource, so one policy can serve every project.
- The external IdP sends a **session tag** in the SAML assertion (attribute `https://aws.amazon.com/SAML/Attributes/PrincipalTag:project`) or through IAM Identity Center attributes for access control.
- Resources carry the same tag key, for example `project=alpha`.
- The policy compares them with a variable:
  `"StringEquals": {"aws:ResourceTag/project": "${aws:PrincipalTag/project}"}`
- Creation actions use `aws:RequestTag/project` so users can only create resources tagged with their own project.
## Example
Alice signs in with `project=alpha` and can stop instances tagged `project=alpha` but not `project=beta`. Adding a new project needs only new tags, not new policies or roles.
W: ABAC comparing principal and resource tags: a single policy grants access whenever the user's project tag matches the resource tag, which scales to hundreds of projects with no per-project policy.
X: A=Resource policies listing user ARNs: many services do not support resource policies, federated users are not stable IAM users, and every membership change means editing many policies.
B=Account per developer: it multiplies accounts and cross-account plumbing without solving shared project access, and still needs per-project access definitions.
D=Policy and role per project: this is role-based access control, which needs a new policy and role for each of hundreds of projects and runs into IAM quotas and management overhead.
T: When access must follow a project attribute at scale, match principal tags to resource tags (ABAC) instead of writing one policy per project.

@ Q002064 explain
G: ## Application authorization with Verified Permissions
IAM controls access to AWS APIs; it is not designed for rules about your own application's end users and business objects. **Amazon Verified Permissions** is a managed authorization service for applications.
- Rules are written in **Cedar**, an open-source policy language, and stored in a **policy store**, outside the application code.
- A schema describes entities such as `User`, `Expense` and `Department` with their attributes.
- The application calls `IsAuthorized` (or `IsAuthorizedWithToken` with a Cognito or OIDC token) and receives allow or deny, with each decision loggable for audit.
## Example
A Cedar policy of the form
`permit(principal in Role::"manager", action == Action::"approve", resource) when { resource.amount < 10000 && resource.department == principal.department };`
lets managers approve smaller expenses in their own department. Changing the limit means editing the policy, not redeploying code.
W: Verified Permissions with Cedar: it evaluates fine-grained, attribute-based rules about users and resources centrally and keeps them out of the code.
X: A=IAM policy per end user: IAM authorizes AWS API calls, not in-app actions like approving an expense, and per-user IAM identities do not scale to SaaS customers.
C=WAF rules: WAF inspects HTTP requests for patterns such as IPs, headers or SQL injection; it does not understand users, departments or expense amounts.
D=Cognito groups only: groups give coarse role labels in the token; they cannot express conditions such as amount limits or same-department checks.
T: Business-level authorization for application users belongs in Verified Permissions (Cedar); IAM, WAF and Cognito groups do not model those rules.

@ Q002065 explain
G: ## Workforce sign-in across accounts
**AWS IAM Identity Center** is the recommended way to give employees access to many AWS accounts.
- **Authentication:** Identity Center connects to an external IdP (for example Okta or Microsoft Entra ID) using **SAML 2.0**, so users sign in once and see all their accounts and roles in the access portal.
- **Provisioning:** with **SCIM**, the IdP automatically creates, updates and deactivates users and groups in Identity Center when HR changes them.
- **Authorization:** **permission sets** assigned to groups for chosen accounts become IAM roles in those accounts, managed centrally.
## Example
When HR moves Bob into the `Finance-Analysts` group in the IdP, SCIM updates Identity Center within minutes and he gains the read-only permission set in the finance accounts. When he leaves, disabling him in the IdP removes his access everywhere.
W: Identity Center with SAML and SCIM: SAML gives single sign-on to all accounts, and SCIM keeps users and groups in sync with HR changes automatically.
X: A=Cognito user pools: user pools are built for customer sign-in to your applications, not for workforce access to AWS accounts and the console across an organization.
C=SAML provider per account: every account needs its own provider and roles maintained by hand, and there is no automatic user and group provisioning.
D=IAM users synced nightly: it creates long-term credentials in every account, adds up to a day of delay for leavers and depends on a custom script.
T: Workforce SSO to many accounts plus automatic user lifecycle means IAM Identity Center with a SAML IdP and SCIM provisioning.

G: ## KMS keys are Regional
A KMS key normally exists in one Region, and ciphertext can only be decrypted by the same key. Data replicated to `us-west-2` would still need a call back to `us-east-1` to decrypt, or it would have to be re-encrypted under a local key.
## Multi-Region keys
A **multi-Region key** is a set of related keys in different Regions that share the **same key ID and key material**.
- The **primary key** (for example `mrk-1234abcd...` in `us-east-1`) is replicated to a **replica key** in `us-west-2`.
- Ciphertext produced by the primary can be decrypted by the replica locally, with no cross-Region call.
- Each replica has its own key policy, grants and aliases, and key material rotation is shared across the set.
## Example
An application encrypts records with the primary in `us-east-1`. During a DR failover, the `us-west-2` copy of the application calls `Decrypt` on the replica and reads the same records.
W: Multi-Region key with a replica: related keys share key material, so data encrypted in `us-east-1` decrypts in `us-west-2` with a local call and no re-encryption.
X: A=Export key material: KMS never exports key material it generates, and even keys with identical imported material cannot decrypt each other's ciphertext because ciphertext is bound to the specific key.
C=Same alias in each Region: an alias is just a Region-local name; two single-Region keys still have different key material, so neither can decrypt the other's ciphertext.
D=SSE-S3: switching means re-encrypting the existing data, which the team wants to avoid, and it gives up KMS key policies and per-request KMS audit in CloudTrail.
T: To decrypt the same ciphertext in another Region without re-encrypting, use a KMS multi-Region key and its replica.

G: ## S3 Object Lock retention modes
S3 Object Lock stores objects in a **write-once-read-many (WORM)** model. It requires versioning and protects object versions for a **retention period**.
- **Compliance mode:** no user, including the root user, can overwrite or delete a protected version or shorten its retention until it expires. The only way out is to wait.
- **Governance mode:** users with `s3:BypassGovernanceRetention` can delete or change retention by sending the header `x-amz-bypass-governance-retention: true`.
- **Legal hold:** a separate on/off lock with no end date.
A bucket default retention (for example compliance mode, 7 years) applies to every new version automatically.
## Example
An invoice uploaded today with 7-year compliance retention cannot be removed by anyone until that date; a delete request only adds a delete marker and the protected version stays.
W: Object Lock compliance mode, 7 years: it is the only choice that stops everyone, including root, from deleting or overwriting records for the full period.
X: A=Versioning with lifecycle expiry: versioning keeps old versions, but authorized users can still delete versions at any time; the lifecycle rule only deletes more after 7 years and prevents nothing.
B=Bucket policy denying delete: administrators or the root user can edit or remove the policy, and a deny on `s3:DeleteObject` alone does not stop overwrites or version deletion.
D=Governance mode: privileged users with the bypass permission can remove the protection, so it does not meet "anyone, including the root user".
T: Only Object Lock in compliance mode stops deletion by everyone including root; governance mode and policies can be bypassed by privileged users.

G: ## Where KMS keeps key material
By default, KMS keys live in the **AWS KMS key store**: HSMs that AWS operates and that are shared by many customers (validated under FIPS 140-3), with logical isolation per key.
A **custom key store** backed by **AWS CloudHSM** changes where key material lives:
- You own a CloudHSM cluster of single-tenant HSMs in your VPC, with at least two active HSMs in different Availability Zones.
- KMS keys created in the custom key store have their key material generated and used only inside your cluster; KMS signs in as a dedicated crypto user `kmsuser`.
- Services such as S3 (SSE-KMS) and EBS still just reference the KMS key ARN, so integrations work unchanged.
## Tradeoffs
You manage the cluster's availability and pay for the HSMs, and if the cluster is unavailable, encryption and decryption with those keys fail.
W: CloudHSM-backed custom key store: key material stays in single-tenant HSMs the company controls, while S3 and EBS keep using normal KMS key integrations.
X: A=Default key store: keys are protected by HSMs that AWS runs as a shared, multi-tenant fleet, which does not meet a single-tenant, customer-controlled requirement.
B=SSE-S3: keys are fully owned and managed by S3, and SSE-S3 does not apply to EBS at all, since EBS encryption uses KMS keys.
D=Secrets Manager: it stores secret values encrypted with KMS; it is not an HSM and cannot act as the key for S3 or EBS encryption.
T: Single-tenant, customer-controlled HSMs with KMS integration means a KMS custom key store backed by CloudHSM.

G: ## Enforcing HTTPS on S3
S3 endpoints accept both HTTP and HTTPS. To require encryption in transit, a bucket policy uses the global condition key **`aws:SecureTransport`**, which is `true` only when the request arrived over TLS.
The standard statement denies everything that is not TLS:
- `"Effect": "Deny"`, `"Principal": "*"`, `"Action": "s3:*"`
- `"Resource"`: both `arn:aws:s3:::sensitive-bucket` and `arn:aws:s3:::sensitive-bucket/*`
- `"Condition": {"Bool": {"aws:SecureTransport": "false"}}`
Because an explicit deny overrides any allow, no principal can use plain HTTP. The optional `s3:TlsVersion` condition key can also require a minimum TLS version such as 1.2.
## In transit versus at rest
Encryption in transit protects data on the wire (TLS). Server-side encryption (SSE-S3, SSE-KMS) protects stored objects. Settings for one do not enforce the other.
W: Deny when `aws:SecureTransport` is false: the explicit deny rejects every request not made over TLS, which directly enforces encryption in transit.
X: A=Transfer Acceleration: it routes uploads and downloads through edge locations for speed; it does not require clients to use HTTPS.
B=SSE header condition on GetObject: `s3:x-amz-server-side-encryption` concerns encryption at rest on uploads; it says nothing about whether the connection uses TLS.
C=Default SSE-KMS: default encryption encrypts objects when stored, which is at rest, and still accepts requests over plain HTTP.
T: Encryption in transit to S3 is enforced with a bucket policy deny on `aws:SecureTransport` = false; SSE settings only cover data at rest.

G: ## Three kinds of Control Tower controls
AWS Control Tower groups controls by when they act:
- **Preventive** controls block API actions, implemented with service control policies (and resource control policies or declarative policies). They can only use condition keys the service exposes in the request, so many resource properties cannot be checked this way.
- **Detective** controls use AWS Config rules to report noncompliant resources after they exist.
- **Proactive** controls use **CloudFormation hooks** to inspect resource properties in a template before CloudFormation provisions them. If a resource fails, for example an `AWS::RDS::DBInstance` without `StorageEncrypted: true`, the stack operation fails and the resource is never created.
## Example
Enabling the proactive control that requires RDS storage encryption on an OU makes any CloudFormation stack in its accounts fail when it tries to create an unencrypted instance, instead of raising a finding hours later.
W: Proactive controls (CloudFormation hooks): they check resource properties at deployment time and stop noncompliant resources before they are created, exactly the requested behavior.
X: A=Preventive SCPs only: SCPs act on API calls and can inspect only the condition keys a service exposes; a few settings have one (RDS offers a key for storage encryption), but most resource properties do not, so SCPs alone cannot enforce general property rules at deployment time.
B=Security Hub after deployment: these standards evaluate resources that already exist, which is detection, not blocking at deployment time.
D=Detective Config controls: Config rules evaluate resources after creation and report noncompliance; they do not stop the deployment.
T: To block noncompliant resources during CloudFormation deployment, use Control Tower proactive controls; detective controls only report afterward.
