@ Q002071 explain
G: ## What a conformance pack is
An AWS Config **conformance pack** is a collection of Config rules and optional remediation actions, defined in one YAML template and deployed as a single unit. Config reports compliance for the pack as a whole (including a compliance score), not just rule by rule.
## Deploying it to an organization
An **organization conformance pack** is created once from the management account or a Config delegated administrator (API `PutOrganizationConformancePack`). Config then deploys the same pack into every member account, and accounts that join the organization later receive it automatically.
- Example: a "PCI baseline" pack with 40 rules such as `s3-bucket-public-read-prohibited` and `encrypted-volumes`, plus SSM Automation remediations, pushed to all 200 accounts.
- Member accounts cannot edit or delete the organization pack, so the baseline stays identical everywhere.
- Aggregated results can be viewed centrally with a Config aggregator.
W: Organization conformance packs: one template deploys the same rules and remediations to every account, new accounts included, and compliance is reported per pack so the 40 rules are tracked as one unit.
X: B=Manual rules per account: creating 40 rules in each account by hand is slow, drifts over time, misses new accounts and gives no single pack-level compliance view.
C=Trusted Advisor checks: Trusted Advisor runs a fixed set of AWS-defined best-practice checks. You cannot load your own Config rules or remediations into it.
D=Access Analyzer policy validation: this checks IAM policy grammar and best practices when policies are written. It does not deploy Config rules or report resource compliance.
T: To enforce and report the same set of Config rules and remediations across every account, deploy an organization conformance pack from the delegated administrator.

@ Q002072 explain
G: ## Two ways Macie finds sensitive data
Amazon Macie inspects S3 objects with managed data identifiers (for example credit card numbers, AWS secret keys, passport numbers) and custom identifiers.
- **Sensitive data discovery jobs** scan the objects you select, once or on a schedule. They are thorough but you pay for every byte inspected, so scanning every bucket every day across a large estate is costly.
- **Automated sensitive data discovery** runs continuously: each day Macie selects a representative sample of objects across buckets, inspects them and builds a **sensitivity score** per bucket. It is designed to give broad visibility at controlled cost.
## Organization scale
With a Macie **delegated administrator** in AWS Organizations, automated discovery can be enabled for all member accounts, and the administrator sees a single data map showing which buckets in which accounts are likely to hold sensitive data. Targeted full jobs can then be run only on the buckets that matter.
W: Macie automated discovery with an org delegated admin: sampling-based, continuous analysis across all accounts gives an estate-wide estimate of where credit card numbers live without paying to scan every object.
X: B=Daily one-time jobs on every bucket: full classification of every object every day across thousands of buckets is exactly the "pay to scan everything" approach the company wants to avoid, and it is operationally heavy to manage.
C=GuardDuty S3 Protection: it analyzes S3 data-plane API activity (CloudTrail data events) for threats such as suspicious access or exfiltration. It never inspects object contents for credit card numbers.
D=S3 Inventory review: inventory lists object keys, sizes and encryption status. A file name says nothing reliable about what the object contains.
T: For an ongoing, low-cost estimate of where sensitive data sits across many accounts, use Macie automated discovery; save full discovery jobs for targeted deep scans.

@ Q003929 explain
G: ## How GuardDuty detects threats without agents
Amazon GuardDuty is a managed threat detection service. When enabled, it reads its **foundational data sources** directly from AWS through independent streams, so you do not need to turn on the logs yourself or install anything:
- **CloudTrail management events**: for example API calls from an unusual location or a known malicious IP.
- **VPC Flow Logs**: for example an EC2 instance talking to a crypto-mining pool or port-scanning other hosts.
- **Route 53 Resolver DNS query logs**: for example lookups of a command-and-control domain.
GuardDuty combines these with threat intelligence and machine learning and produces findings such as `CryptoCurrency:EC2/BitcoinTool.B!DNS`.
## Multi-account
With a GuardDuty **delegated administrator** in AWS Organizations, detection can be auto-enabled for every member account, and all findings are visible in one account (per Region).
W: GuardDuty with a delegated administrator: it continuously analyzes CloudTrail, VPC Flow Logs and DNS logs agentlessly for threats, and the delegated admin enables and views it across all accounts.
X: B=Inspector EC2 scanning: Inspector looks for software vulnerabilities (CVEs) and network exposure on workloads. It does not analyze CloudTrail, flow or DNS logs for active attacks.
C=Macie automated discovery: Macie classifies S3 object contents to find sensitive data such as PII. It does not watch account activity for threats.
D=Config conformance packs: Config evaluates resource configurations against rules (for example "is this bucket encrypted"). It does not detect malicious behavior in logs.
T: Agentless, log-based threat detection across accounts is GuardDuty; Inspector finds vulnerabilities, Macie finds sensitive data and Config checks configuration.

@ Q003930 explain
G: ## GuardDuty protection plans
Beyond its foundational log analysis, GuardDuty has optional protection plans that add new data sources.
- **EKS Protection (EKS Audit Log Monitoring)**: GuardDuty reads the Kubernetes audit logs of your EKS clusters (no configuration on the cluster needed) and detects control-plane activity such as anonymous access, a pod created with a privileged container, or a service account used from a malicious IP.
- **Runtime Monitoring**: a lightweight **GuardDuty security agent** runs on EKS nodes (as an EKS add-on), on EC2 instances, or alongside ECS on Fargate tasks. It reports OS-level events such as process execution, file access and network connections, so GuardDuty can detect, for example, a reverse shell or a crypto miner started inside a container.
Audit logs show what was requested of the cluster; runtime events show what actually ran on the host. Together they cover both layers.
W: D=EKS protection with audit log monitoring: analyzes Kubernetes audit logs to find suspicious API activity inside EKS clusters.
E=Runtime Monitoring with the security agent: collects process, file and network events from EKS nodes and EC2 hosts, giving process-level threat detection.
X: A=Access Analyzer findings for the node role: Access Analyzer reports external or unused access in policies. It says nothing about what processes run in the cluster.
B=Config rules for EKS version checks: a version rule flags outdated clusters (a configuration issue). It does not detect malicious behavior.
C=S3 Storage Lens dashboards: Storage Lens reports storage usage and activity metrics for buckets. It has no view into containers or hosts.
T: For threats inside EKS and on hosts, add GuardDuty EKS audit log monitoring (control-plane activity) and Runtime Monitoring (process-level events).

G: ## One place for security findings
Each detective service produces its own findings: GuardDuty (threats), Inspector (vulnerabilities), Macie (sensitive data) and AWS Config (rule compliance). Checking each console separately does not scale.
**AWS Security Hub** collects findings from these services into one view. The original service is now named **AWS Security Hub CSPM**; it also runs security standards such as the AWS Foundational Security Best Practices and CIS AWS Foundations Benchmark, using Config to evaluate controls, and shows a **security score** per standard.
- Example: the dashboard shows 72% for CIS, a list of failed controls, and GuardDuty and Inspector findings for the same account, filterable by severity.
- Findings from many accounts and Regions can be aggregated in a delegated administrator account.
The newer, unified AWS Security Hub builds on this, correlating findings from these services in OCSF format.
W: Security Hub: it aggregates findings from GuardDuty, Inspector, Macie and Config into a single dashboard and (in Security Hub CSPM) scores compliance against security standards.
X: B=Amazon Detective: Detective builds a behavior graph to investigate a finding after it appears (who did what, from where). It is not the aggregation and compliance-scoring dashboard.
C=Trusted Advisor: it runs AWS-defined best-practice checks across cost, security and performance, but it does not ingest GuardDuty, Inspector or Macie findings.
D=Firewall Manager: it centrally deploys WAF, Shield Advanced, security group and Network Firewall policies. It enforces protections, it does not consolidate findings.

@ Q003932 explain
G: ## Where root sign-ins show up
Every console sign-in is recorded by CloudTrail as a `ConsoleLogin` event. For the root user, `userIdentity.type` is `Root`. CloudTrail sends these events to **Amazon EventBridge** as the detail type `AWS Console Sign In via CloudTrail`, usually within minutes.
## Building the alert
An EventBridge rule matches the pattern and sends it to a target such as an SNS topic that emails or pages the security team:
- Pattern fields: `detail-type` = `AWS Console Sign In via CloudTrail` and `detail.userIdentity.type` = `Root`.
- Create the rule in the Region where the sign-in events are recorded (root sign-ins are typically recorded in `us-east-1`), and in each account, or forward events to a central event bus.
GuardDuty also raises `Policy:IAMUser/RootCredentialUsage` when root credentials are used, which is another useful signal.
W: EventBridge rule on root ConsoleLogin, targeting SNS: the CloudTrail event reaches EventBridge in near real time, and SNS notifies the team within minutes.
X: A=Monthly credential report review: the report only shows when the root password was last used, and a monthly check means an intrusion can go unnoticed for weeks.
B=Config recorder: Config records resource configuration changes, not sign-in activity, so it never sees a root login.
D=CloudWatch dashboard of sign-ins: a dashboard displays data but does not notify anyone. Someone would have to be watching it at the right moment.
T: Near-real-time root sign-in alerts come from CloudTrail events matched by an EventBridge rule and sent to SNS; periodic reviews and dashboards do not alert.

@ Q003933 explain
G: ## What deserves an immediate alert
Alerting on everything creates noise that hides real attacks. Immediate alerts should cover events that remove visibility or create direct exposure.
- **Tampering with logging**: `StopLogging`, `DeleteTrail` or `UpdateTrail` on CloudTrail is a classic attacker step to hide further actions. GuardDuty reports it as `Stealth:IAMUser/CloudTrailLoggingDisabled`, and an EventBridge rule on these API calls can alert directly.
- **Opening administrative ports to the internet**: a security group rule allowing TCP 22 from `0.0.0.0/0` exposes the instance to worldwide brute-force and exploitation. The Config managed rule `restricted-ssh` or an EventBridge rule on `AuthorizeSecurityGroupIngress` can flag it, and automatic remediation can revoke the rule.
Routine operational events (backups, tags, new deployments) belong in logs and reports, not in paging alerts.
W: C=SSH open to 0.0.0.0/0: it creates immediate internet exposure of an administrative port and is a common precursor to compromise.
E=CloudTrail stopped or deleted: it removes the audit trail, often right before an attacker acts, so it needs an immediate response.
X: A=Successful scheduled EBS snapshot: this is expected backup activity. A failed backup might deserve a ticket, but success is not a security signal.
B=Tag added to a dev bucket: tagging does not change access or exposure, so it is routine change that should not page anyone.
D=New Lambda layer version: publishing layer versions is normal development activity. Code risk is better handled by scanning (for example Inspector) than by alerting on every publish.
T: Page on events that blind you or expose you, such as disabling CloudTrail or opening SSH to the world, not on routine operations.

@ Q003934 explain
G: ## Organization trail
An **organization trail** is created in the management account (or a CloudTrail delegated administrator account) and automatically logs events for every account in AWS Organizations, including new ones.
- Member accounts can see the trail but **cannot modify or delete it**.
- Log files for all accounts go to one S3 bucket, in the prefix `AWSLogs/<org-id>/<account-id>/`.
## Where to store the logs
Best practice (used by AWS Control Tower) is a dedicated **log archive account** that only a few security staff can access. The bucket policy lets CloudTrail write, and nobody in the member accounts has permissions in that account at all.
- Add S3 Object Lock, versioning, SSE-KMS and CloudTrail log file integrity validation for further tamper resistance.
- Example: management account creates `org-trail`, which writes to `s3://org-cloudtrail-logs-111122223333` in the log archive account.
W: Organization trail to a log archive account bucket: one trail covers every account, member admins cannot change the trail, and the logs sit in an account those admins cannot access.
X: A=Management-account trail for its own events: a normal trail logs only the account it is in, so all member account activity would be missing.
B=Event history only: event history keeps 90 days of management events per account and Region, is not centralized, and cannot be protected or retained long term.
D=Per-account trails to local buckets: the account administrators being audited control both the trails and the buckets, so they could stop logging or delete the files.
T: For tamper-resistant org-wide audit logs, use an organization trail delivering to a bucket in a separate log archive account.

@ Q003935 explain
G: ## Management events vs data events
CloudTrail records two main kinds of events:
- **Management events** (control plane): operations on resources, such as `CreateBucket`, `PutBucketPolicy` or `DeleteBucket`. Trails log them by default.
- **Data events** (data plane): operations on the data inside a resource, such as S3 `GetObject`, `PutObject` and `DeleteObject`. They are high volume, so they are **off by default** and billed separately.
## Scoping data events
Use advanced event selectors to log only what you need. Example: `eventCategory` = `Data`, `resources.type` = `AWS::S3::Object`, `resources.ARN` starts with `arn:aws:s3:::payroll-bucket/`, and optionally `readOnly` = `true` for reads only. Each `GetObject` event then shows who read which object, when and from which IP.
W: CloudTrail data events for the bucket: they record object-level API calls such as `GetObject`, which is exactly the read activity to audit.
X: B=Config history for the bucket policy: Config tracks changes to the bucket's configuration, such as its policy. It never sees individual object reads.
C=VPC Flow Logs: flow logs record IP-level traffic metadata (addresses, ports, bytes), not S3 API calls or object keys, and traffic from outside the VPC is not captured at all.
D=Management events only: management events cover bucket-level operations like changing policies, but object reads are data events and are not included.
T: Object reads in S3 are CloudTrail data events, which must be enabled explicitly; management events only cover bucket-level changes.

@ Q003936 explain
G: ## What Amazon Security Lake does
Amazon Security Lake builds a security data lake in S3 buckets in your own account and normalizes the data into the **Open Cybersecurity Schema Framework (OCSF)**, stored in Apache Parquet format.
- **AWS sources** can be enabled with a few clicks across an organization: CloudTrail management and data events, VPC Flow Logs, Route 53 Resolver query logs, Security Hub findings, EKS audit logs and AWS WAF logs.
- **Custom sources** (third-party firewalls, identity providers, on-premises tools) write OCSF data into the same lake.
- **Subscribers** such as Amazon Athena, OpenSearch or an external SIEM query or receive the data.
Example: an analyst writes one Athena query over OCSF fields like `src_endpoint.ip` to find the same IP in VPC flow logs and firewall logs, without writing separate parsers for each format.
W: Amazon Security Lake: it centralizes AWS and third-party security logs, normalizes them to OCSF and stores them in S3 for analytics tools to query.
X: A=ElastiCache: an in-memory cache (Redis OSS, Valkey, Memcached) for application speed. It does not collect or normalize logs.
B=Storage Gateway: it gives on-premises applications access to cloud storage (file, volume, tape). It has no log ingestion or OCSF normalization.
D=Lightsail: a simplified service for virtual servers and small websites, unrelated to security data analytics.
T: Centralized, OCSF-normalized security logs from AWS and third-party sources point to Amazon Security Lake.

@ Q003937 explain
G: ## CloudTrail Lake
CloudTrail Lake is a managed store for CloudTrail events that you can query with SQL directly in the CloudTrail console or API, with no pipeline to build.
- You create an **event data store**, which can collect events from all accounts in the organization and keep them for a configurable period (up to years).
- Queries use SQL, for example `SELECT eventName, userIdentity.arn FROM <event-data-store-id> WHERE eventTime > '2025-10-01' AND eventName = 'DeleteBucket'`.
- It can also ingest events from outside AWS.
## Availability note
Since May 31, 2026, CloudTrail Lake is closed to new customers; existing customers can keep using it, and AWS points new customers to Amazon CloudWatch for similar capabilities. Athena over organization trail logs in S3 also remains open to everyone. The feature set described here is what the question tests, and it is still the only option that fits.
W: CloudTrail Lake event data stores: they hold a year or more of organization-wide CloudTrail events and answer SQL queries without any ETL.
X: B=Config aggregators: aggregators combine resource configuration and compliance data across accounts. They do not hold CloudTrail API events.
C=S3 Inventory reports: inventory lists the log files in the bucket (names, sizes), not the events inside them, so it cannot answer questions about API activity.
D=CloudWatch dashboards on API counts: dashboards show metric graphs; they cannot run event-level SQL such as "who called `DeleteBucket` last March".
T: SQL over organization-wide CloudTrail events without ETL is the CloudTrail Lake use case (closed to new customers since May 31, 2026, but still the feature this requirement describes).

@ Q003938 explain
G: ## CloudWatch Logs data protection
A **data protection policy** on a log group (or for the whole account) tells CloudWatch Logs to scan incoming log events for sensitive data using managed data identifiers such as `CreditCardNumber`, `EmailAddress` or `AwsSecretKey`, or custom regular expressions.
- Matches are **masked** when the logs are viewed or queried, for example `4111-1111-1111-1111` appears as `****`.
- Only principals with the `logs:Unmask` permission can see the original values, so analysts get useful logs without card numbers.
- The policy can also send audit findings (what was found and where) to another log group, S3 or Firehose.
Example: a data protection policy on `/app/payments` with the `CreditCardNumber` identifier, and analysts' IAM roles without `logs:Unmask`.
W: CloudWatch Logs data protection policies: they detect credit card numbers in log events and mask them for anyone without `logs:Unmask`.
X: B=Retention settings: retention controls how long log events are kept before deletion. The card numbers stay fully visible during that time.
C=Metric filter patterns: metric filters count matching log events to create CloudWatch metrics. They do not change or hide the log content.
D=Subscription filters: subscriptions stream log events to Lambda, Kinesis or Firehose. They forward the data as is, which would spread the card numbers further.
T: Mask sensitive values in CloudWatch Logs with a data protection policy; retention, metric filters and subscriptions do not hide content.

@ Q003939 explain
G: ## Two layers of log integrity
- **Detect changes: log file integrity validation.** When enabled on a trail, CloudTrail writes an hourly **digest file** that contains a SHA-256 hash of every log file delivered in that hour and is signed with a private key held by CloudTrail. Running `aws cloudtrail validate-logs` later proves whether any log file was modified or deleted after delivery.
- **Prevent changes: S3 Object Lock.** With Object Lock in **compliance mode** and a retention period (for example 365 days), no user, including the root user, can delete or overwrite the log object versions until retention ends. Object Lock works together with bucket versioning.
Storing logs in a separate log archive account with a tight bucket policy adds a third layer.
W: C=Log file integrity validation: signed digest files let you prove cryptographically that log files were not altered or removed.
E=S3 Object Lock: WORM retention blocks deletion or overwriting of log files for the retention period.
X: A=Developer write access: giving many people write access to the log bucket is the opposite of integrity; any of them could replace or delete logs.
B=Disabling encryption: validation works fine with SSE-S3 or SSE-KMS encrypted logs. Removing encryption only weakens confidentiality.
D=Same-account storage only: administrators of the account being audited could then delete the logs. Integrity improves by storing logs in a separate account.
T: Protect CloudTrail logs by detecting tampering (integrity validation) and preventing it (Object Lock), ideally in a separate log archive account.

@ Q003940 explain
G: ## How CloudTrail writes to S3
CloudTrail delivers log files by calling S3 as the service principal `cloudtrail.amazonaws.com`. The destination bucket's policy must allow it:
- `s3:GetBucketAcl` on the bucket.
- `s3:PutObject` on `arn:aws:s3:::my-trail-bucket/AWSLogs/111122223333/*`, with condition `s3:x-amz-acl` = `bucket-owner-full-control`.
- A condition such as `aws:SourceArn` = the trail ARN is recommended to prevent confused-deputy use.
When the console creates a new bucket it adds this policy automatically; with an existing bucket, a pre-created bucket, or a wrong prefix or account ID, delivery fails and the trail status shows the last delivery error. If the trail uses SSE-KMS, the KMS key policy must also let CloudTrail use the key.
W: Bucket policy does not allow CloudTrail: without `s3:PutObject` and `s3:GetBucketAcl` for `cloudtrail.amazonaws.com`, every delivery attempt is denied, so no log files appear.
X: A=Versioning enabled: versioning keeps older object versions and is recommended for log buckets. It does not block writes.
C=No EC2 instances in the Region: CloudTrail logs API activity for the account regardless of what resources run in a Region.
D=Lowercase letters and hyphens: those are exactly the characters S3 bucket names are allowed to use, so the name is valid.
T: When a trail delivers nothing, first check that the bucket policy (and KMS key policy, if used) lets `cloudtrail.amazonaws.com` write.

G: ## How GuardDuty findings reach Security Hub
The GuardDuty integration sends findings to Security Hub (here meaning **Security Hub CSPM**, the name the original service now carries) in the **same account and Region** where GuardDuty produced them. That requires:

E=Security Hub enabled in those accounts and Regions: findings are imported locally, so any account or Region without Security Hub cannot contribute findings.
X: A=Root user MFA: MFA protects root sign-in and has no effect on how findings flow between services.
B=S3 storage class for logs: GuardDuty findings are sent directly to Security Hub, not read from S3 log files, so the storage class is irrelevant.
D=More than 100 IAM roles: the number of roles in an account does not limit or block finding imports.
T: Missing findings in Security Hub usually mean Security Hub is not enabled in that account or Region, or the product integration is not accepting findings.

@ Q003942 explain
G: ## What the CloudWatch agent needs
The CloudWatch agent reads log files on the instance and sends them with API calls such as `PutLogEvents` to the CloudWatch Logs endpoint `logs.<region>.amazonaws.com`. Two things must be in place:
- **IAM permissions**: the instance profile role needs permissions such as `logs:CreateLogStream`, `logs:PutLogEvents` and `logs:DescribeLogStreams`; the managed policy `CloudWatchAgentServerPolicy` covers them. Without it the calls fail with AccessDenied in the agent log.
- **A network path** to the endpoint: an internet gateway with a public IP, a NAT gateway, or an interface VPC endpoint for CloudWatch Logs (`com.amazonaws.<region>.logs`). In a private subnet with none of these, the agent cannot connect.
Troubleshooting tip: check the agent's own log file (`amazon-cloudwatch-agent.log`) for AccessDenied or connection timeout errors.
W: A=No network path to the endpoint: without internet, NAT or a Logs VPC endpoint, the agent's API calls time out and no logs arrive.
E=Missing CloudWatch Logs permissions: the agent authenticates with the instance role, so without `logs:PutLogEvents` and related actions every upload is denied.
X: B=Burstable instance with low CPU credits: a throttled T instance runs slower but still runs the agent and sends logs.
C=Detailed monitoring disabled: detailed monitoring only changes EC2 hypervisor metrics from 5-minute to 1-minute intervals. It has nothing to do with agent log delivery.
D=gp3 instead of gp2: the EBS volume type affects disk performance, not the agent's ability to reach CloudWatch.
T: When the CloudWatch agent sends nothing, check the instance role's CloudWatch Logs permissions and the network path to the Logs endpoint.

@ Q003943 explain
G: ## CloudTrail Insights
CloudTrail Insights learns a baseline of normal API activity for an account and raises **Insights events** when activity deviates from it, with no rules or thresholds to write.
- **API call rate insights**: an unusual volume of calls to one API, for example a sudden burst of `CreateAccessKey` or `AttachUserPolicy` calls.
- **API error rate insights**: an unusual number of failed calls, for example many `AccessDenied` errors as an attacker probes permissions.
Insights events show the baseline, the anomaly period and the users and sources involved. They can be delivered to the trail's S3 bucket and to EventBridge for alerting. Insights is enabled per trail (or event data store) and is billed per events analyzed.
W: CloudTrail Insights: it automatically detects abnormal API call and error rates, such as a spike in IAM actions, without any rules to maintain.
X: B=CloudTrail Lake: it stores events for SQL queries. You could search for a spike, but only by writing and running queries yourself; it does not detect anomalies automatically.
C=S3 Storage Lens: it reports storage usage and activity metrics for S3. It does not analyze API calls across services such as IAM.
D=Config rules: rules evaluate whether resource configurations are compliant. They are written for specific conditions and do not detect unusual call volumes.
T: For automatic detection of unusual API volumes or error rates, enable CloudTrail Insights; Lake and Config need explicit queries or rules.

@ Q003945 explain
G: ## Route 53 Resolver query logging
Every VPC uses the **Route 53 Resolver** (at the VPC base address +2, for example `10.0.0.2`) to resolve DNS names. **Resolver query logging** records the queries it handles: the source instance IP, the VPC, the queried name (for example `bad-c2.example.net`), the record type and the response.
- A query logging configuration is associated with one or more VPCs and delivers logs to CloudWatch Logs, S3 or Amazon Data Firehose.
- It can be shared across accounts with AWS RAM.
Threat hunters use these logs to find instances resolving known malicious domains or showing DNS-tunneling patterns. They complement Route 53 Resolver DNS Firewall, which can block such domains.
W: Route 53 Resolver query logging: it records the DNS queries that VPC workloads send to the Resolver, which is exactly the data needed for threat hunting.
X: A=Health check logging: health checks probe endpoints to decide availability. They do not see DNS queries from workloads.
C=Traffic flow: traffic flow is a visual editor for routing policies in public hosted zones (latency, geolocation, failover). It does not log queries.
D=DNSSEC signing: DNSSEC signs hosted zone records so resolvers can verify responses are authentic. It provides integrity, not query logs.
T: DNS activity from VPC workloads is logged with Route 53 Resolver query logging; health checks, traffic flow and DNSSEC do not record queries.

G: ## GuardDuty is Regional
Amazon GuardDuty works Region by Region. A detector exists only in the Regions where GuardDuty was enabled, and it analyzes only the CloudTrail, VPC Flow Logs and DNS activity of that Region.

@ Q003947 explain
G: ## What Amazon Inspector scans
Amazon Inspector is AWS's automated vulnerability management service. Once enabled, it discovers workloads automatically and rescans them continuously when new CVEs are published or the workload changes.
- **EC2 instances**: package vulnerabilities and network reachability (for example a port open to the internet), using the SSM Agent or agentless snapshot-based scanning.
- **Amazon ECR images**: container images are scanned on push and continuously afterward.
- **AWS Lambda functions**: dependencies in function code and layers, and optionally code-level issues such as injection flaws or hardcoded secrets.

G: ## Preparing before an incident
Under the shared responsibility model, the customer is responsible for responding to incidents in its own workloads. The AWS Security Incident Response Guide (an AWS whitepaper) puts **preparation** first:
- **Runbooks (playbooks)**: written, step-by-step procedures for a scenario such as "compromised EC2 instance": who is paged, how to isolate the instance, which snapshots to take, how to preserve evidence and who communicates. Keep them in a shared, access-controlled place; they can be automated with Systems Manager Automation documents.
- **Exercises**: tabletop exercises walk the team through a scenario on paper; game days simulate the incident in a test environment. Both expose gaps such as missing permissions or outdated contact lists before a real attack.
Example: a quarterly game day where a test instance generates GuardDuty sample findings and the team follows the runbook end to end.
W: Runbooks plus regular game days or tabletop exercises: they document the procedure and prove it works, so responders act quickly and consistently during a real compromise.
X: B=Decide during the incident: improvising under pressure causes delays, missed evidence and mistakes, which is what preparation is meant to prevent.
C=Personal notes of the security lead: procedures that only one person can see are not documented for the team and fail when that person is unavailable.
D=Rely on AWS Support: AWS secures the underlying infrastructure, but the customer owns incident response for its resources. A paid AWS Support plan or the AWS Security Incident Response service can assist, but the customer's own team and procedures are still required.
T: Incident readiness means written runbooks that are regularly tested through game days or tabletop exercises, not improvisation or reliance on AWS.

G: ## What a forensics account is for
A **forensics account** is a dedicated AWS account, set up before any incident, where responders copy and analyze evidence from compromised workloads without risking contamination or spreading the compromise.
- **Isolated network**: a VPC with no internet gateway or NAT, and only the VPC endpoints needed (for example S3, EC2, KMS, SSM). Malware on a mounted disk cannot call home, and analysis tools cannot leak evidence.
- **Prepared cross-account access**: IAM roles that responders assume, permissions to copy EBS snapshots shared from other accounts, and KMS key policies that allow using or re-encrypting encrypted snapshots.
- **Ready tooling**: pre-built forensic AMIs or SSM documents to attach volumes read-only and capture hashes.
Example: the production account shares a snapshot; a responder in the forensics account copies it, creates a volume and attaches it to an analysis instance in the isolated VPC.
W: C=Isolated network with no internet: analysis instances cannot be reached by or talk to attacker infrastructure, so evidence stays contained.
E=Preconfigured roles and snapshot-copy tools: responders can collect evidence from other accounts immediately instead of arranging access during the incident.
X: A=Public S3 buckets for evidence: public access could expose sensitive evidence to anyone. Share with vendors through scoped, time-limited access instead.
B=Peering with every production VPC: peering creates a network path between the forensics environment and possibly compromised systems, which is exactly what isolation should prevent.
D=Shared credentials in a wiki: shared long-lived credentials leak easily and remove individual accountability; use individual federated access to assumed roles.
T: A forensics account should be isolated from the internet and production, with cross-account roles and tooling prepared in advance.

G: ## AWS Systems Manager Incident Manager
Incident Manager, a capability of AWS Systems Manager, helps teams respond to operational incidents:
- **Contacts and on-call schedules**: engagement plans escalate from the primary on-call engineer to backups by SMS, voice or email until someone acknowledges.
- **Response plans**: define what happens when an incident starts, such as which contacts to engage, which chat channel to use (through Amazon Q Developer in chat applications) and which Systems Manager Automation runbook to run.
- **Incident timeline**: records events, actions and notes automatically, which feeds the **post-incident analysis**.
Incidents can be started automatically, for example from a CloudWatch alarm or an EventBridge rule on a GuardDuty finding.

G: ## Contain first, keep the evidence
When an instance talks to a command-and-control (C2) server, the goals are to stop the damage and keep evidence for investigation. Destroying the instance too soon removes the evidence.
- **Contain**: replace its security groups with an isolation security group that allows no traffic, or only access from a forensics host. Connections that are already tracked are not necessarily cut when security group rules change, so AWS guidance first makes them untracked (or adds a network ACL deny) before applying the isolation group. Also remove it from Auto Scaling and load balancers and enable termination protection.
- **Preserve**: take EBS snapshots of all volumes and, if possible, capture memory (running processes, network connections, injected code) with a tool run through Systems Manager, since memory is lost on reboot or stop. Tag the instance and record the actions.
Example: apply the isolation group `sg-quarantine`, snapshot `vol-0abc...`, capture memory, then analyze in a forensics account.
W: A=Snapshot EBS volumes and capture memory: this preserves disk and volatile evidence before anything is changed.
E=Isolate with a restrictive security group: this cuts the instance off from the C2 server and other systems while keeping it running for investigation.
X: B=Reboot the instance: a reboot wipes memory evidence (running malware, connections) and may not remove persistent malware anyway.
C=Terminate immediately: termination destroys memory and, by default, the root volume, losing the evidence needed to understand the attack.
D=Delete CloudTrail logs: logs are key evidence of what the attacker did. Deleting them helps the attacker, not the investigation.
T: For a compromised instance, isolate it and capture snapshots and memory first; do not reboot, terminate or delete logs.
