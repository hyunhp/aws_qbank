@ SCS-C03 D3 T3.1 advanced troubleshooting
S: A login endpoint is being targeted by a credential stuffing campaign that keeps retrying the same few thousand user accounts from a large, rotating pool of residential IP addresses, making a standard per-source-IP rate-based rule ineffective. The application includes a custom header 'X-Account-Attempted' identifying the target username on each login POST. How should the security team configure AWS WAF to throttle this attack more effectively?
A: Custom aggregate key on the attempted-account header alone, counting per account
B: Extend the rate-based rule's window to 24 hours, keeping IP-only aggregation
C: Replace it with a geo match rule blocking traffic outside the home country
D: Switch the rule to CAPTCHA action only, without changing aggregation
K: A
G: ## How rate-based rules count
An AWS WAF rate-based rule keeps a separate counter for every value of its **aggregation key** and acts when one counter exceeds the limit within the evaluation window. By default the key is the source IP, so each IP address gets its own counter.
With custom keys you can aggregate on request components instead: a header, cookie, query argument, label namespace, HTTP method, and so on, alone or combined (up to five keys). The counter is kept per unique combination of all the chosen values.
## Why the key choice decides the outcome
- Rotating residential IPs spread the attempts so thinly that no single IP reaches the limit.
- Adding the IP to the key does not help: the combination IP plus account is still new for every rotated IP, so each counter stays low.
- Aggregating on the `X-Account-Attempted` header **alone** gives one counter per targeted account, however many IPs the attempts come from.
Example: 3,000 attempts against user `alice` from 3,000 different IPs are 3,000 counters of 1 when keyed on IP plus account, but one counter of 3,000 when keyed on the account header, which the rule throttles.
W: Account header alone: counting per attempted account makes the rotating IP pool irrelevant, because every attempt against the same account lands in the same counter and is throttled once it passes the limit. AWS WAF Fraud Control account takeover prevention (ATP) is a complementary managed option for login pages.
X: B=Longer window, IP-only key: a longer window still counts per source IP, and each rotated IP sends only a few requests, so none of them reaches the limit; it also delays reaction.
C=Geo match rule: residential proxy pools usually include IPs in the home country, so the attack continues, and legitimate customers who travel or use foreign networks get blocked.
D=CAPTCHA action on an IP key: the action only runs when the rule matches, and with IP aggregation the rule still never matches because no single IP exceeds the limit.
T: A rate-based rule is only as good as its key: to throttle attacks from rotating IPs, aggregate on the thing being attacked (the account), not on the source.
V: AWS WAF

@ SCS-C03 D3 T3.2 advanced use-case
S: Amazon ECS tasks run on EC2 instances (EC2 launch type) using bridge network mode. A penetration test reveals that a compromised container can query the EC2 instance's IMDS directly and obtain the broader EC2 instance profile's IAM credentials rather than being limited to its intended, narrowly-scoped ECS task IAM role. Which combination best resolves this while keeping the workload on EC2?
A: Give the instance profile and every task role the same broad role
B: A security group rule denying outbound access to 169.254.169.254/32
C: awsvpc mode with ECS_AWSVPC_BLOCK_IMDS (or iptables) blocking IMDS
D: IMDSv2 optional with hop limit 2 so each task must request a token
K: C
G: ## Where task credentials come from
An ECS task role is delivered by the ECS agent through a separate credentials endpoint (`169.254.170.2`), not through the EC2 instance metadata service (IMDS, `169.254.169.254`). IMDS hands out the **instance profile** credentials, which the ECS agent and the host need but the tasks should never see.
If a container can reach IMDS, a compromised task can escalate from its narrow task role to the instance role.
## Ways to block tasks from IMDS
- **awsvpc network mode** gives each task its own ENI. Setting `ECS_AWSVPC_BLOCK_IMDS=true` in `/etc/ecs/ecs.config` makes the agent block IMDS for those tasks.
- For **bridge mode**, the ECS documentation gives an `iptables` rule on the host that drops traffic from the `docker+` interfaces to `169.254.169.254`. Requiring IMDSv2 with a hop limit of 1 also helps, because the token response cannot reach containers one hop away.
The important detail for the last approach is that tokens must be **required**: with IMDSv2 optional, IMDSv1 requests need no token and are not affected by the hop limit.
W: awsvpc plus ECS_AWSVPC_BLOCK_IMDS: each task gets its own network interface and the agent blocks IMDS for it, so a compromised container can use only its own task role credentials while the instances keep their instance profile for the agent.
X: A=Same broad role everywhere: this removes the escalation only by giving every task the broad permissions, which is the opposite of least privilege and enlarges the blast radius of any compromise.
B=Security group deny rule: security groups have only allow rules and do not filter traffic to the link-local metadata address, so this rule cannot be written and would not block IMDS.
D=Optional IMDSv2, hop limit 2: with tokens optional, containers can still call IMDSv1 without any token, and a hop limit of 2 even lets IMDSv2 token responses reach bridge-mode containers.
T: Keep ECS tasks away from IMDS: block it for awsvpc tasks with ECS_AWSVPC_BLOCK_IMDS, or for bridge mode with iptables or required IMDSv2 and hop limit 1.
V: Amazon ECS, Amazon EC2

@ SCS-C03 D2 T2.2 applied use-case
S: An organization suspects the AWS account root user credentials may have been compromised, evidenced by a GuardDuty Policy:IAMUser/RootCredentialUsage finding combined with unexpected root sign-in events in CloudTrail. Which combination of actions represents the most appropriate immediate response?
A: Delete the root user, since best practice is to never use it
B: Reset password, remove root keys, confirm MFA, review CloudTrail
C: Apply an SCP denying all root actions as the only containment step
D: Rely on IAM Identity Center to lock the root user after suspicious activity
K: B
G: ## What the root user is
Every AWS account has one root user: the email address and password used to create it. It has full access to the account and a few tasks only it can perform (such as changing the account's support plan or closing the account). The root user cannot be deleted while the account exists.
GuardDuty reports API calls made with root credentials as `Policy:IAMUser/RootCredentialUsage`. Together with unexpected root sign-ins in CloudTrail, it is a strong signal that someone other than the owners is using root.
## Responding to suspected root compromise
- **Reset the root password** and make sure the account email mailbox is under your control.
- **Delete any root access keys**; root should never have long-term keys.
- **Confirm or re-register MFA** on root, removing any device you do not recognize.
- **Review CloudTrail** for root activity (`userIdentity.type` = `Root`): new IAM users or keys, changed billing or contact details, new Regions in use, and disabled logging.
- Then remove whatever the attacker created, such as IAM users, access keys and roles.
In AWS Organizations, centralized root access management can also remove root credentials from member accounts.
W: Reset, remove keys, MFA, investigate: these steps cut off every way the attacker could still sign in or call APIs as root, and the CloudTrail review finds persistence (new users, keys, roles) that must be removed next.
X: A=Delete the root user: the root user cannot be deleted while the account exists; you can only secure it or remove its credentials.
C=SCP as the only step: SCPs do not restrict the management account at all, and even in a member account an SCP alone leaves the stolen password, any root keys and any persistence the attacker created in place.
D=Identity Center locks root: IAM Identity Center manages workforce users and permission sets; it has no mechanism to detect or lock the root user.
T: For suspected root compromise, rotate the password, remove keys, enforce MFA and investigate in CloudTrail; root cannot be deleted and an SCP is not enough.
V: AWS IAM, Amazon GuardDuty, AWS CloudTrail, AWS Organizations

@ SCS-C03 D2 T2.2 applied troubleshooting
S: A responder applies an account-level S3 Block Public Access configuration to remediate an exposed bucket, but external access continues briefly: CloudTrail data events show successful GetObject calls from unfamiliar external IP addresses after the change. What is the most likely explanation?
A: CloudTrail was caching stale entries from before the change was made
B: Unexpired pre-signed URLs from permitted principals still work
C: Block Public Access settings take up to 24 hours to propagate globally
D: Account-level Block Public Access skips buckets created before it was set
K: B
G: ## What BPA blocks and what it does not
S3 Block Public Access decides whether a bucket's ACLs or policy count as **public** (granting access to everyone or anonymous users). It removes that public access. It does not revoke access that an authorized identity already has.
## How pre-signed URLs work
A pre-signed URL is a normal `GetObject` request signed in advance with the credentials of an IAM user or role that is allowed to read the object. Anyone holding the URL can use it until:
- the expiry time in the URL (`X-Amz-Expires`) passes, or
- the signing credentials stop being valid, for example because the access key is deactivated or the role session expires or is revoked.
S3 evaluates the request as the **signer**, not as an anonymous caller, so BPA treats it as authorized access. In CloudTrail data events the `userIdentity` is the signer, the `sourceIPAddress` is the external party's address, and `additionalEventData.AuthenticationMethod` is `QueryString`.
Example: a URL signed an hour ago with a 7-day expiry keeps working after BPA is enabled until the signer's key is disabled.
W: Pre-signed URLs keep working: the external party is presenting URLs signed by a permitted principal, which BPA does not block. Deactivate the signer's access keys or revoke its role sessions, and deny the requests in the bucket policy if needed.
X: A=Stale CloudTrail cache: CloudTrail does not replay old events as new ones; each data event has the real event time, so entries timestamped after the change are real requests.
C=24-hour propagation: BPA changes take effect quickly (at most a short eventual-consistency delay), not over 24 hours, and a delay would not explain requests that carry a valid signature.
D=Only newer buckets: account-level BPA applies to every bucket in the account, including ones created long before the setting was turned on, so the age of the bucket does not explain the requests.
T: BPA removes public access, not authorized access; pre-signed URLs keep working until they expire or the signer's credentials are revoked.
V: Amazon S3, AWS CloudTrail

@ SCS-C03 D1 T1.1 advanced tradeoff
S: A security team in a central security-tooling account wants to receive GuardDuty and Security Hub findings from 40 member accounts in near real time for automated triage. The tooling account is not the delegated administrator for either service (a separate audit account holds that role), and it must not get broad cross-account IAM read access into member accounts. Which architecture best satisfies this while minimizing per-account maintenance?
A: Each account writes findings to a local bucket, polled hourly with Athena from the tooling account
B: A central event bus with an org PutEvents policy and forwarding rules via StackSets
C: Each account assumes a role in the tooling account and pushes findings via GetFindings on a schedule
D: Security Hub cross-Region aggregation enabled in each member account, pointed at the tooling account
K: B
G: ## Getting findings out of many accounts
GuardDuty and Security Hub publish every new or updated finding as an event to Amazon EventBridge in the account and Region where the finding lives (and in the delegated administrator account for member findings). EventBridge can forward events to an event bus in another account.
## The central bus pattern
- Create a custom event bus in the tooling account with a resource policy that allows `events:PutEvents` for the organization (`aws:PrincipalOrgID`).
- Deploy one EventBridge rule per member account and Region with CloudFormation StackSets (service-managed, auto-deployment to new accounts). The rule matches GuardDuty and Security Hub finding events and targets the central bus.
- In the tooling account, rules on the central bus invoke triage (Lambda, Step Functions, a ticketing integration).
Events arrive within seconds, the tooling account never reads member accounts, and new accounts are covered automatically by StackSets.
W: Central event bus with StackSets rules: findings are pushed as events the moment they are created, the org-wide PutEvents policy avoids per-account trust changes, and StackSets deploys and maintains the forwarding rules in every current and future account.
X: A=Local buckets polled by Athena: hourly polling is not near real time, and reading 40 accounts' buckets from the tooling account needs exactly the cross-account read access the team wants to avoid.
C=Scheduled GetFindings pushes: scheduled jobs add delay and require code, credentials and a role path per account; it is more maintenance and still not event-driven.
D=Cross-Region aggregation per member: cross-Region aggregation only gathers findings from linked Regions into one Region of the same Security Hub administrator; it cannot send findings to another account, least of all one that is not the administrator.
T: For near-real-time cross-account findings without read access, forward finding events with EventBridge to a central bus and deploy the rules with StackSets.
V: EventBridge, Security Hub, GuardDuty, CloudFormation

@ SCS-C03 D3 T3.3 advanced troubleshooting
S: An application team created an interface VPC endpoint for Amazon DynamoDB (the PrivateLink-based interface endpoint, not the gateway endpoint) but confirms that traffic from the application instances still exits through the NAT gateway to the public DynamoDB service endpoint instead of using the interface endpoint's private IP addresses. What is the most likely cause?
A: The NAT gateway must be deleted before interface endpoint traffic is used
B: Private DNS is disabled on the endpoint, so default names still resolve publicly
C: The SDK clients still use the default Regional endpoint, not the vpce DNS name
D: Interface endpoints work only for resources launched after they are created
K: C
G: ## How clients find a DynamoDB interface endpoint
For most AWS services, enabling **private DNS** on an interface endpoint makes the default name (for example `sqs.us-east-1.amazonaws.com`) resolve to the endpoint's private IPs inside the VPC. **AWS PrivateLink for DynamoDB does not support private DNS.** The default name `dynamodb.us-east-1.amazonaws.com` keeps resolving to public DynamoDB addresses, so traffic follows the route table: through the NAT gateway, or through a gateway endpoint if one exists.
## What clients must do instead
Each DynamoDB interface endpoint gets endpoint-specific names:
- Regional: `vpce-1a2b3c4d-5e6f.dynamodb.us-east-1.vpce.amazonaws.com`
- Zonal: the same name with the Availability Zone added.
Clients must be configured with that name as the endpoint URL, for example `--endpoint-url` in the CLI or `endpoint_url` in Boto3. AWS also warns against private hosted zones that override `dynamodb.<region>.amazonaws.com`, because DynamoDB's DNS layout can change and such overrides can silently send traffic to public IPs.
W: Default endpoint still in use: without private DNS support, only clients that explicitly use the endpoint-specific vpce DNS name reach the interface endpoint; the unchanged SDK configuration keeps resolving the public name and uses the NAT gateway.
X: A=Delete the NAT gateway first: an interface endpoint works alongside a NAT gateway; deleting it would only make the public-endpoint calls fail instead of redirecting them.
B=Private DNS disabled: DynamoDB interface endpoints do not offer private DNS at all, so there is no setting to turn on; the default name always resolves to public addresses.
D=Only newer resources: an interface endpoint is reachable by any client in the VPC that can resolve and route to its ENIs, regardless of when that client was launched.
T: DynamoDB interface endpoints have no private DNS: point clients at the vpce endpoint-specific DNS name, or keep using a gateway endpoint for in-VPC traffic.
V: Amazon VPC, Amazon DynamoDB, AWS PrivateLink

@ SCS-C03 D6 T6.1 advanced troubleshooting
S: An administrator relies on the AWS Control Tower mandatory control that disallows changes to the encryption configuration of the S3 buckets Control Tower created in the Log Archive account. An engineer with an administrator role in that account nevertheless changes the default encryption of the Control Tower log bucket, even though the console shows the control as enabled on the Security OU. What is the most likely explanation?
A: Controls apply only to accounts created after the control was enabled
B: Mandatory controls affect only new resources, never pre-existing ones
C: The account has drifted from its baseline; repair the OU or account
D: S3 encryption changes are only detected, never prevented, by any control
K: C
G: ## Control Tower drift
AWS Control Tower deploys its controls and baseline resources (SCPs, Config rules, roles, log buckets) and expects them to stay as it set them. When someone changes these resources outside Control Tower, the landing zone is in **drift**. Examples:
- an SCP created by Control Tower is edited or detached in the Organizations console,
- an enrolled account is moved to another OU directly in Organizations,
- a control-managed role or bucket policy is changed by hand.
The console can still show a control as enabled on the OU while the account no longer receives the policy. Drift is reported in the Control Tower console and through notifications to the Audit account.
## Scope of this control
The mandatory control is an SCP that denies `s3:PutEncryptionConfiguration` on the Control Tower-created log buckets only, for every principal except the Control Tower roles. It does not cover other buckets in other accounts; those need your own controls. Since January 2023 S3 always encrypts new objects (SSE-S3 at minimum), so such a change can switch the encryption type (for example from SSE-KMS to SSE-S3) but cannot turn encryption off.
## Fixing it
Re-register the OU, update or re-enroll the account, or reset the landing zone, depending on what drifted.
W: Account drift: the control is a preventive SCP, so if an administrator's change went through, the SCP is most likely not in effect for that account because something was changed outside Control Tower; repairing the OU or account restores it.
X: A=Only newer accounts: controls enabled on an OU apply to all enrolled accounts in it, existing and new.
B=Only new resources: a preventive SCP evaluates each API call when it happens, so it blocks changes to existing buckets as much as to new ones.
D=Detection only: this mandatory control is preventive and denies encryption changes on the log buckets, so prevention is available and should have stopped the call.
T: When a preventive control seems ignored while the console says it is enabled, suspect drift: the SCP or the account placement was changed outside Control Tower.
V: AWS Control Tower, Amazon S3, AWS Organizations

@ SCS-C03 D4 T4.2 advanced troubleshooting
S: An ABAC policy grants access when aws:PrincipalTag/Department equals aws:ResourceTag/Department. An engineer whose IAM role is tagged Department=finance reports AccessDenied when accessing a resource that is tagged Department=Finance. What is a likely cause worth investigating first?
A: IAM supports ABAC only for EC2 instances, not this resource type
B: ABAC ignores case, so the policy syntax itself must be invalid
C: The resource must be recreated with the tag for ABAC to take effect
D: Tag values compare case-sensitively, so finance and Finance don't match
K: D
G: ## How ABAC compares tags
In attribute-based access control, a policy compares a tag on the caller with a tag on the resource, for example:
`"StringEquals": {"aws:ResourceTag/Department": "${aws:PrincipalTag/Department}"}`
- The **tag key** inside a condition key name is matched case-insensitively: `aws:ResourceTag/department` and `aws:ResourceTag/Department` refer to the same tag.
- The **tag value** is compared by the operator. `StringEquals` is case-sensitive, so `finance` does not equal `Finance`, and a trailing space also breaks the match.
## Troubleshooting pattern
When ABAC denies access that "should" work, compare the exact values on both sides first: the principal's role or session tags and the resource's tags. Standardizing values (for example with tag policies in AWS Organizations) prevents the problem. `StringEqualsIgnoreCase` exists, but consistent values are the cleaner fix.
W: Value case mismatch: the StringEquals comparison between the principal's value finance and the resource's value Finance fails because string values are compared case-sensitively, so the Allow never applies and the request is implicitly denied.
X: A=Only EC2 supports ABAC: many services support aws:ResourceTag conditions (S3, Secrets Manager, Lambda, DynamoDB and more), so the resource type is not limited to EC2.
B=ABAC ignores case: only the tag key in the condition key name is case-insensitive; the values are compared exactly, and the policy syntax itself is valid.
C=Recreate the resource: tags added or changed on an existing resource are evaluated on the next request; nothing has to be recreated.
T: In ABAC, tag keys in condition keys are case-insensitive but tag values are compared exactly, so standardize values across principals and resources.
V: IAM

@ SCS-C03 D5 T5.2 applied definition
S: A company stores regulatory archives as objects in the S3 Glacier Deep Archive storage class and must guarantee for 10 years that no IAM principal, including administrators and the root user, can delete or overwrite them or shorten the retention period. Which feature should they use?
A: S3 Object Lock in compliance mode with a 10-year retention period
B: S3 Object Lock in governance mode with a 10-year retention period
C: A bucket policy with an explicit Deny on s3:DeleteObject for everyone
D: A permissions boundary on every IAM role that omits s3:DeleteObject
K: A
G: ## S3 Object Lock
Object Lock stores objects in a write-once-read-many (WORM) model. It requires versioning and protects individual object versions, whatever their storage class, including S3 Glacier Deep Archive.
- **Compliance mode:** no user, not even the root user, can delete or overwrite a locked version or shorten its retention until the retention date passes. The mode itself cannot be changed.
- **Governance mode:** users with `s3:BypassGovernanceRetention` can delete versions or shorten retention by sending the bypass header, so administrators can still remove data.
- **Legal hold:** an indefinite lock without a date, removable by anyone with `s3:PutObjectLegalHold`.
Example: a default retention of 10 years in compliance mode on the bucket applies to every new object version automatically.
## Legacy Glacier vaults
The original vault-based Amazon Glacier service offered Vault Lock policies for the same purpose. That service has been closed to new customers since December 15, 2025; AWS recommends S3 Glacier storage classes with S3 Object Lock instead.
W: Compliance mode: once an object version is locked in compliance mode, nobody, including administrators and the root user, can delete it, overwrite it or shorten its retention for 10 years, which is exactly the immutability requirement.
X: B=Governance mode: principals granted s3:BypassGovernanceRetention can still delete locked versions or shorten retention, so administrators remain able to remove the archives.
C=Bucket policy Deny: an administrator or the root user can edit or delete the bucket policy at any time, so the protection can later be altered.
D=Permissions boundary: administrators can remove or change boundaries, and boundaries never apply to the root user, so this is not an unalterable control.
T: Retention that nobody, including root, can override → S3 Object Lock compliance mode; governance mode and policies can be bypassed by administrators.
V: Amazon S3

@ SCS-C03 D5 T5.3 advanced use-case
S: A payments platform needs an existing migration role in Account A to use a KMS customer managed key owned by Account B to encrypt objects during a one-time data migration. The role must call AWS KMS with its own credentials (no role assumption into Account B), and Account B must be able to revoke the access right after the migration without modifying the key's resource-based policy. What mechanism should Account B use?
A: A permanent key policy statement for Account A, removed manually after the migration
B: A role in Account B that Account A assumes, deleted after the migration finishes
C: Share the key through AWS RAM with a resource share scoped to the migration window
D: A KMS grant to Account A's migration role, retired or revoked after the migration
K: D
G: ## KMS grants
A grant is a permission record attached to one KMS key that lets a grantee principal use specific operations, such as `Encrypt` and `GenerateDataKey`. Grants are created by principals allowed to call `kms:CreateGrant` and can name a principal in another account as the grantee.
- Grants do not change the key policy, so they suit temporary, programmatic access.
- **Grants have no expiry time.** They stay active until the grant is **retired** (for example by its retiring principal) or **revoked** (by the key owner's account). Temporary access therefore means creating the grant at the start and revoking it at the end, for example from the migration runbook.
- New grants can take a short time to propagate; a grant token lets the grantee use them immediately.
## Cross-account use
The grantee in Account A calls KMS with the key ARN (aliases do not work across accounts) using its own credentials, so no role assumption is needed.
W: KMS grant: a grant gives Account A's own role exactly the operations it needs on the key without editing the key policy, and Account B can revoke it (or the grantee retire it) as soon as the migration ends.
X: A=Permanent key policy statement: this edits the key's resource-based policy, which the requirement forbids, and relies on someone remembering to remove it later.
B=Role in Account B: it could work technically, but the migration role would have to assume a role in Account B, which the requirement explicitly rules out.
C=AWS RAM share: AWS RAM does not support sharing KMS keys; cross-account key access is granted through key policies or grants.
T: Temporary cross-account KMS use without key policy edits → a grant, revoked or retired when done; grants never expire on their own.

@ SCS-C03 D5 T5.3 applied use-case
S: A team needs to rotate an API key for a third-party SaaS service that is stored in AWS Secrets Manager. AWS provides no rotation function template, managed rotation or managed external secret type for this vendor. How should the team implement automatic rotation for this third-party API key?
A: Move the key to Parameter Store, which rotates any secret type out of the box
B: Rotation isn't possible for non-database secrets; rotate the key manually
C: A custom rotation Lambda (create/set/test/finish) calling the vendor API
D: Enable AWS Config remediation to regenerate the key periodically
K: C
G: ## How Secrets Manager rotation works
Rotation in AWS Secrets Manager is driven by a Lambda function. On each rotation, Secrets Manager invokes the function four times, once per step:
- `createSecret`: generate a new credential and store it as a new version labelled `AWSPENDING`.
- `setSecret`: register that new credential with the system that uses it (the database, or here the vendor's API).
- `testSecret`: prove the pending credential actually works.
- `finishSecret`: move the `AWSCURRENT` label to the new version; the old one becomes `AWSPREVIOUS`.
## Built-in versus custom
AWS provides rotation function templates mainly for database credentials, managed rotation for secrets that certain AWS services own, and managed external secrets for a short list of partner SaaS providers. For any other vendor you write the function yourself. Example: for a SaaS API key, `setSecret` calls the vendor's "create key" endpoint, `testSecret` makes a harmless authenticated call with the new key, and `finishSecret` can revoke the old key. You then turn on rotation with a schedule such as `rate(30 days)`.
W: Custom rotation Lambda: Secrets Manager rotation is not limited to databases; any secret can rotate if you supply a function that implements the four steps against the vendor API, and Secrets Manager handles scheduling, versioning and staging labels.
X: A=Parameter Store rotation: Systems Manager Parameter Store has no built-in rotation feature at all; you would have to build your own scheduler, so moving the key there loses capability rather than gaining it.
B=Manual rotation only: the four-step Lambda contract is generic. The ready-made options cover only certain secret types, but API keys can still be rotated automatically with your own function.
D=AWS Config remediation: Config evaluates resource configuration and can run SSM Automation remediations, but it has no notion of rotating a secret value or talking to a vendor API, and it would bypass Secrets Manager versioning.
T: Any secret type can rotate automatically in Secrets Manager; when no AWS-provided template or managed option covers it, you write the create/set/test/finish Lambda yourself.
V: Secrets Manager, Lambda

@ SCS-C03 D4 T4.2 advanced troubleshooting
S: A role in a member account has the AdministratorAccess policy attached, yet s3:DeleteBucket calls fail with AccessDenied. The bucket policy does not mention the role. Which TWO are the MOST likely causes? (Select TWO)
A: A permissions boundary without s3:DeleteBucket.
B: The role's trust policy is missing the sts:AssumeRole action.
C: The bucket is in a different Region from the caller.
D: An SCP denying s3:DeleteBucket.
E: S3 Block Public Access is enabled at the account level.
K: A,D
G: ## Everything that must allow a request
For a call from a role in a member account, IAM evaluates several policy types. The request succeeds only if:
- no applicable policy has an explicit `Deny`,
- the SCPs (and RCPs) of every OU on the path allow the action,
- the role's identity policy allows it (AdministratorAccess does),
- the permissions boundary, if one is attached, also allows it,
- and, where relevant, the resource policy does not deny it.
## Explicit versus implicit deny
An SCP with `"Effect": "Deny"` for `s3:DeleteBucket` is an **explicit deny**. A permissions boundary that simply does not list the action causes an **implicit deny**: the boundary is a maximum, and anything outside it is not allowed. Both end in AccessDenied; the error message often says which policy type blocked the call ("with an explicit deny in a service control policy" or "because no permissions boundary allows").
W: A=Permissions boundary: the boundary caps the role's effective permissions, so if it does not include s3:DeleteBucket the call is implicitly denied even though AdministratorAccess allows everything.
D=SCP deny: an SCP applies to every principal in the member account, including administrators, and an explicit Deny there overrides any Allow in the role's policies.
X: B=Trust policy: the trust policy controls who may assume the role; once the role is assumed and making calls, it has no effect on which S3 actions succeed.
C=Different Region: S3 answers a request sent to the wrong Region with a redirect or a Region error, not an AccessDenied caused by permissions.
E=Block Public Access: BPA restricts public ACLs and public bucket policies; it does not block authorized principals from deleting buckets.
T: AdministratorAccess is not the final word: permissions boundaries (implicit deny) and SCPs (explicit deny) can still block an action.

G: ## Continuous compliance evidence
Auditors want proof that controls operated throughout a period, not a one-time screenshot. Two services produce that evidence automatically:
- **AWS Config conformance packs** deploy a set of Config rules (and optional remediations) as one unit, often from AWS sample templates aligned to frameworks such as PCI DSS, HIPAA or NIST. Config records configuration changes and compliance results over time, so you can show a resource's compliance history for the whole audit period.
- **AWS CloudTrail** records who did what, when and from where. A trail delivering to a protected S3 bucket with **log file integrity validation** adds signed digest files, so you can prove that the log files were not modified or deleted after delivery.
## Example
A team deploys a PCI DSS conformance pack to its payment accounts through an organization-wide deployment and keeps an organization trail with validation enabled. At year end it shows the auditor the compliance timeline of each resource and validated CloudTrail logs of all administrative changes.
Availability note: AWS Audit Manager, which used to package such evidence per framework, has been closed to new customers since April 30, 2026; AWS points new users to Config conformance packs.
W: B=Config conformance packs: they continuously evaluate resources against a packaged set of rules and keep compliance history, which is evidence that controls held over time.
E=CloudTrail with log file validation: it records all API activity continuously, and the digest files prove the activity record is complete and untampered, which auditors accept as evidence.
X: A=Lightsail snapshots: they are backups of Lightsail instances and disks; they show nothing about whether controls operated.
C=Amazon Polly: it converts text to speech and has no role in compliance evidence.

G: ## Automating audit evidence
Preparing for audits by taking screenshots is slow and error-prone. **AWS Config** records resource configurations and evaluates them against rules continuously. A **conformance pack** bundles many Config rules (and optional remediation actions) into one deployable unit.
- AWS publishes sample conformance pack templates aligned to frameworks such as PCI DSS, HIPAA, NIST 800-53 and the CIS AWS Foundations Benchmark, and you can write your own.

- Config keeps the compliance timeline of each resource, so you can show when it was compliant during the audit period.
Example: a PCI DSS conformance pack flags an unencrypted EBS volume the day it is created and shows the auditor when it was fixed.
