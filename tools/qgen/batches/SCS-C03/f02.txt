@ SCS-C03 D6 T6.3 advanced definition
S: A conformance pack contains 4 AWS Config rules, and every rule evaluates the same 10 resources. Rule 1 reports three of the resources as noncompliant, and rule 2 reports one of those same three as noncompliant; all other results are compliant. The console shows a compliance score of 90%. Which definition of the conformance pack compliance score explains this value?
A: Compliant rule-resource pairs divided by all rule-resource pairs in the pack's scope
B: Resources compliant with every rule in the pack divided by all resources the pack evaluates
C: Rules that report no noncompliant resource divided by the total number of rules in the pack
D: Passed security checks as a share of all checks, weighted by each rule's severity label
K: A
G: ## What a conformance pack compliance score is
A conformance pack deploys a set of AWS Config rules (and optional remediations) as one unit, so a team can report compliance against the whole set, for example an internal baseline or a framework-aligned sample pack.
AWS Config gives each conformance pack a **compliance score**: the percentage of compliant **rule-resource combinations** out of all possible rule-resource combinations in the pack. Every rule multiplied by every resource it evaluates is one combination.
- The score is shown in the Config console and returned by the `ListConformancePackComplianceScores` API.
- Config also publishes it to Amazon CloudWatch as a metric, so the team can graph it over time and alarm when it drops.
## Working through the numbers
- 4 rules x 10 resources = 40 combinations.
- Rule 1 fails 3 resources and rule 2 fails 1 resource: 4 noncompliant combinations.
- 36 / 40 = **90%**.
Other ways of counting give different numbers: only 7 of 10 resources pass every rule (70%), and only 2 of 4 rules have no failures (50%). So a score of 90% does not mean "90% of resources are compliant", which is a common mistake when the number is reported to auditors.
## Why it matters for audits
A pair-based score moves in small steps as individual problems are fixed, which makes it good for tracking remediation progress. For an auditor, it should be paired with the list of noncompliant resources and the rule history, not presented as a share of compliant resources.
W: Compliant rule-resource pairs: AWS Config defines the score as compliant rule-resource combinations divided by all possible combinations in the pack. Here that is 36 of 40, exactly the 90% shown in the console.
X: B=Share of fully compliant resources: counting a resource as compliant only if it passes every rule gives 7 of 10, which is 70%, not the 90% shown; that is not how the score is calculated.
C=Share of rules with no failures: counting rules that report no noncompliant resource gives 2 of 4, which is 50%; the score counts every rule and resource pair, not whole rules.
D=Severity-weighted checks: AWS Config rules have no severity label that feeds the score, and every rule-resource pair counts equally; severity-based scoring is not part of conformance packs.
T: A conformance pack compliance score counts rule-resource pairs (compliant pairs / all pairs), so 90% is not the share of compliant resources or the share of passing rules.

@ SCS-C03 D6 T6.3 advanced tradeoff
S: Auditors use AWS Config configuration history as evidence that security groups and S3 buckets were never left open, even for a few minutes. They also require at least a daily record of each EC2 instance's configuration. Config costs have grown because an Auto Scaling fleet changes thousands of EC2 instances and network interfaces every day. The team wants to lower cost without weakening the security group and bucket evidence. Which recording setup should the team choose, and what does it give up?
A: Continuous by default plus a daily override for EC2 instances and network interfaces, losing their intra-day history
B: Daily recording as the default for all resource types, losing only a few hours of delay before changes appear in history
C: Continuous for all types except EC2 instances and network interfaces, which are excluded, losing nothing auditors need
D: Continuous for all types with every Config rule switched to a 24-hour periodic trigger, losing only faster rule results
K: A
G: ## How AWS Config records changes
AWS Config records a **configuration item (CI)** for a resource and is billed per CI recorded. The configuration recorder has a recording mode with two frequencies:
- **Continuous recording**: a CI is recorded every time the resource changes. Each short-lived change, such as a security group opened and closed again within minutes, stays visible in the configuration history.
- **Daily recording**: at most one CI per 24 hours, showing the most recent state of the resource, and only if it differs from the previous CI. Changes made and reverted within the day never appear.
A recorder has a default frequency and can have a **recording mode override** that sets a different frequency for listed resource types. A few Config-internal types, such as `AWS::Config::ResourceCompliance`, always stay continuous.
## Applying it here
The cost comes from high-churn fleet resources, while the evidence the auditors care most about comes from security groups and S3 buckets. Keeping the default continuous protects that evidence, and a daily override for `AWS::EC2::Instance` and `AWS::EC2::NetworkInterface` cuts the number of CIs from the fleet while still recording each instance's latest configuration every day.
## The price of the choice
For the overridden types, the team loses the intra-day timeline: brief changes to an instance or network interface are not recorded, and rules triggered by configuration changes see those resources only when their daily CI arrives. That fits the stated requirement of a daily instance record.
W: Continuous default with a daily override for the fleet types: security groups and S3 buckets keep a CI for every change, so brief exposures stay provable, and the fleet's thousands of daily changes shrink to at most one CI per resource per day. The accepted cost is that intra-day history and change-triggered evaluations for those fleet resources are lost.
X: B=Daily recording for everything: a security group or bucket policy that is opened and closed within one day is never recorded, so the auditors' main evidence is weakened; the loss is missing changes, not just a few hours of delay.
C=Exclude the fleet types: excluded types are no longer recorded (Config tracks only their creation and deletion), so the auditors' required daily record of each instance's configuration disappears.
D=Periodic rule triggers only: rule trigger type does not change how many CIs the recorder writes, so the per-CI recording charges from the fleet, which drive the growth, stay the same.
T: Lower Config cost by giving high-churn, low-evidence resource types a daily recording override, and keep continuous recording where auditors need every change.
