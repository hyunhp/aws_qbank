# SOA-C03 batch 02: Domain 2 (reliability and business continuity)
@ SOA-C03 D2 T2.1 applied use-case
S: A web tier's load rises gradually each morning and falls each evening. The team wants capacity to track average CPU at 50% automatically. Which scaling policy fits?
A: Target tracking scaling on average CPU utilization
B: Scheduled scaling at a fixed time every night only
C: Simple scaling with a single fixed step adjustment
D: Manual scaling performed by the on-call engineer
K: A
W: Target tracking adjusts capacity to keep a metric near a target value, like a thermostat.
X: B=Scheduled scaling alone cannot follow variable load. | C=Simple scaling is less responsive and needs manual tuning. | D=Manual scaling is not automatic.
T: Keep a metric at a target → target tracking.
V: Amazon EC2 Auto Scaling

@ SOA-C03 D2 T2.1 advanced use-case
S: Traffic spikes every weekday at 9:00, and new instances take eight minutes to be ready. Users see slow responses for the first minutes. Which combination helps most?
A: Scheduled or predictive scaling before 9:00 plus a warm pool
B: Target tracking alone with a longer cooldown period set
C: Reduce the maximum group size to limit instance launches
D: Replace the load balancer with a round-robin DNS record
K: A
W: Scaling ahead of a known spike and keeping pre-initialized instances in a warm pool avoids lag from slow instance startup.
X: B=Reactive scaling still lags behind startup time. | C=Lower maximums reduce capacity. | D=DNS round robin does not add capacity.
T: For predictable spikes with slow startup, scale ahead and use warm pools.
V: Amazon EC2 Auto Scaling

@ SOA-C03 D2 T2.1 applied use-case
S: A DynamoDB table has unpredictable traffic with sudden spikes, and the team does not want to manage capacity. Which option fits?
A: On-demand capacity mode
B: Provisioned mode without scaling
C: A global secondary index per spike
D: DynamoDB Accelerator only
K: A
W: On-demand mode scales automatically with traffic and charges per request, with no capacity planning.
X: B=Fixed provisioned capacity cannot absorb spikes. | C=Indexes do not add capacity to the table. | D=DAX caches reads but does not handle write spikes or capacity planning.
T: Unpredictable DynamoDB traffic → on-demand mode.
V: Amazon DynamoDB

@ SOA-C03 D2 T2.2 applied use-case
S: An application uses a single RDS instance. The team needs automatic failover if the Availability Zone fails. Which option fits?
A: Enable a Multi-AZ deployment for the database
B: Create a read replica in the same Availability Zone
C: Take manual snapshots every hour during the day
D: Increase the instance size to the largest available
K: A
W: Multi-AZ maintains a synchronous standby in another AZ with automatic failover.
X: B=A same-AZ replica does not survive an AZ failure and does not fail over automatically. | C=Snapshots need manual restore. | D=Size does not provide availability.
T: Automatic database failover across AZs → Multi-AZ.
V: Amazon RDS

@ SOA-C03 D2 T2.2 advanced use-case
S: An Auto Scaling group spans three AZs behind an ALB. One AZ fails. What happens with correct configuration?
A: The ALB stops routing to that AZ and the group launches instances elsewhere
B: All traffic stops until the failed AZ recovers and instances restart there
C: The ALB moves to a different Region automatically with the instances
D: The Auto Scaling group deletes itself and must be recreated manually
K: A
W: Health checks remove failed targets, and Auto Scaling replaces capacity in healthy AZs.
X: B=Multi-AZ design avoids a total outage. | C=ALBs are Regional; they do not move Regions. | D=Groups are not deleted by AZ failures.
T: Multi-AZ ASG plus ALB rides through an AZ failure.
V: Elastic Load Balancing, Amazon EC2 Auto Scaling

@ SOA-C03 D2 T2.2 applied use-case

@ SOA-C03 D2 T2.2 applied use-case

@ SOA-C03 D2 T2.3 advanced use-case
S: An RDS database must be restorable to any second within the last seven days after accidental data deletion. Which feature supports this?
A: Automated backups with point-in-time recovery
B: A single manual snapshot taken each month
C: A Multi-AZ standby in another Availability Zone
D: A read replica in a second AWS Region
K: A
W: Automated backups with transaction logs allow restoring to any point within the retention period.
X: B=Monthly snapshots cannot restore to arbitrary times. | C=The standby replicates deletions too. | D=Replicas also replicate deletions.
T: Restore to a specific time → PITR with automated backups.
V: Amazon RDS

@ SOA-C03 D2 T2.1 applied use-case
S: Which TWO actions improve an application's ability to absorb sudden traffic spikes? (Select TWO)
A: Put an SQS queue between the web tier and workers
B: Use Auto Scaling with a policy based on queue depth
C: Run all components on a single large EC2 instance
D: Disable health checks to avoid replacing instances
E: Set the Auto Scaling maximum equal to the minimum
K: A,B
W: Queues buffer bursts, and scaling on queue depth adds workers as backlog grows.
X: C=A single instance is a bottleneck and single point of failure. | D=Health checks are needed for reliability. | E=Equal min and max prevents scaling.

V: Amazon SQS

@ SOA-C03 D2 T2.2 applied use-case
S: A company wants its web application to fail over to a static maintenance page in S3 if the primary site becomes unhealthy. Which Route 53 feature fits?
A: Failover routing with a health check on the primary
B: Simple routing with a single A record and long TTL
C: Weighted routing with 50% sent to each destination
D: Geolocation routing based on the user's country
K: A
W: Failover routing sends traffic to the secondary record when the primary's health check fails.
X: B=Simple routing has no failover. | C=Weighted routing splits traffic regardless of health unless configured with health checks, and does not express primary/secondary. | D=Geolocation routes by location, not health.
T: Primary/secondary with health checks → failover routing.
V: Amazon Route 53

@ SOA-C03 D2 T2.1 advanced tradeoff
S: An Auto Scaling group scales out and in repeatedly within minutes, causing instability. Which change reduces this flapping?
A: Increase the cooldown or instance warm-up period
B: Lower the scale-out threshold to react sooner
C: Remove the scale-in policy and keep scale-out only
D: Switch the group to use a single Availability Zone
K: A
W: Cooldowns and warm-up periods prevent new actions before previous changes take effect, reducing oscillation.
X: B=A lower threshold can increase oscillation. | C=Removing scale-in wastes capacity. | D=Single-AZ reduces availability and does not fix flapping.
T: Stabilize scaling with cooldowns and warm-up.
V: Amazon EC2 Auto Scaling
