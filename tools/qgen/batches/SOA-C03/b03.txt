# SOA-C03 batch 03: Domain 3 (deployment, provisioning, automation)
@ SOA-C03 D3 T3.1 applied use-case
S: A team wants to preview exactly which resources a CloudFormation stack update will add, modify, or replace before applying it. What should they use?
A: A change set for the stack
B: A stack policy on the stack
C: Drift detection on the stack
D: A nested stack for the update
K: A
W: Change sets show the proposed changes, including replacements, before execution.
X: B=Stack policies protect resources from updates. | C=Drift detection compares actual resources to the template. | D=Nested stacks organize templates.
T: Preview stack updates with change sets.
V: AWS CloudFormation

@ SOA-C03 D3 T3.1 advanced use-case
S: A team must deploy the same CloudFormation template to 40 accounts across three Regions in an organization. Which feature fits?
A: CloudFormation StackSets with service-managed permissions
B: A separate stack deployed manually from each account's console
C: A single stack with 120 duplicated resources for each target
D: A Lambda function that copies the template to each account's S3
K: A
W: StackSets deploy stacks across accounts and Regions from one place, with service-managed permissions using Organizations.
X: B=Manual deployment does not scale. | C=One stack cannot deploy into other accounts. | D=Copying templates does not deploy them.
T: Multi-account, multi-Region deployments → StackSets.
V: AWS CloudFormation

@ SOA-C03 D3 T3.1 applied troubleshooting
S: A CloudFormation stack update failed and the stack is now in UPDATE_ROLLBACK_FAILED. What is the recommended way to recover?
A: Continue update rollback, skipping resources that cannot roll back if needed
B: Delete the AWS account and recreate all resources in a new account
C: Edit the resources directly in the console so they match the new template
D: Wait for the stack to recover on its own without any further action
K: A
W: ContinueUpdateRollback resumes the rollback and can skip resources that cannot be rolled back, returning the stack to a stable state.
X: B=Deleting the account is drastic and unnecessary. | C=Manual edits cause drift. | D=The stack will not recover by itself.
T: Recover UPDATE_ROLLBACK_FAILED with ContinueUpdateRollback.
V: AWS CloudFormation

@ SOA-C03 D3 T3.2 advanced use-case
S: Engineers need shell access to private EC2 instances without opening inbound ports or managing SSH keys, with sessions logged. Which approach fits?
A: Systems Manager Session Manager
B: A bastion host with port 22 open
C: EC2 Instance Connect over the internet
D: A VPN to each instance's public IP
K: A
W: Session Manager provides audited shell access through the SSM agent without inbound ports or SSH keys.
X: B=Bastions require open ports and key management. | C=Instance Connect over the internet needs reachable SSH. | D=VPNs to public IPs add complexity and exposure.
T: Keyless, portless, audited access → Session Manager.

@ SOA-C03 D3 T3.2 applied use-case

A: Systems Manager Parameter Store
B: AWS Secrets Manager
C: Amazon S3 Glacier Deep Archive
D: Amazon CloudFront Functions
E: AWS Direct Connect gateway
K: A,B
W: Parameter Store holds configuration (including SecureString values), and Secrets Manager stores secrets with rotation.

@ SOA-C03 D3 T3.1 applied use-case
S: A team uses Terraform for AWS infrastructure. Several engineers run it, and the state file occasionally becomes corrupted from concurrent runs. What should they configure?
A: A remote backend with state locking
B: A local state file on each laptop
C: A shorter Terraform plan output
D: A separate AWS account per engineer
K: A
W: A remote backend (such as S3 with locking) stores shared state and prevents concurrent modifications.
X: B=Local state causes conflicts and loss. | C=Plan output length is irrelevant. | D=Separate accounts do not fix shared-state conflicts.
T: Shared Terraform state needs a remote backend with locking.
