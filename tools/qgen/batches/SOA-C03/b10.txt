@ SOA-C03 D1 T1.1 applied use-case
S: A Lambda function behind API Gateway must publish per-endpoint latency and order-value metrics to CloudWatch with an Endpoint dimension. Each log line must also keep the customer ID and request ID for later investigation. The team does not want extra synchronous API calls inside the request path. Which approach fits best?
A: Write each record in CloudWatch embedded metric format to standard output so CloudWatch extracts the metrics from the log events
B: Call PutMetricData from the handler for every request and write the customer ID to the log as a separate plain-text log line
C: Create one metric filter per customer ID on the function's log group so that every customer gets an individual latency metric
D: Add the customer ID and latency as AWS X-Ray annotations and build CloudWatch alarms directly on the resulting trace segments
K: A
W: Embedded metric format: the function prints a structured JSON log event with an `_aws` metadata block, and CloudWatch Logs extracts the declared metrics asynchronously. There is no extra API call in the request path, and high-cardinality fields such as the customer ID stay in the same log event for Logs Insights queries.
X: B=PutMetricData per request: it adds a synchronous network call and API cost to every invocation, can be throttled at high request rates, and splits metrics and context into separate records.
C=Metric filter per customer: a log group supports only a limited number of metric filters (100), so one per customer does not scale, and it would create a separate high-cardinality metric for every customer.
D=X-Ray annotations: annotations index traces for filtering in X-Ray, but CloudWatch alarms are built on metrics, not on individual trace segments, so this does not produce the required alarmable metrics.
T: Metrics plus rich context from Lambda without extra API calls → embedded metric format in the logs, not PutMetricData or per-value metric filters.
G: ## Two ways to publish custom metrics
- **PutMetricData**: the code calls the CloudWatch API. Simple, but every call is a network round trip, costs money per request and can be throttled.
- **Embedded metric format (EMF)**: the code writes a JSON log event. A special `_aws` block lists which fields are metrics (with units) and which are dimensions. CloudWatch Logs extracts those metrics in the background.
## Why EMF suits Lambda
Lambda already ships standard output to CloudWatch Logs, so EMF adds no network call to the handler. The same log event can carry extra fields that are *not* dimensions, such as `customerId` or `requestId`. They do not become metrics (no cardinality explosion) but remain searchable with Logs Insights.
Example event: `{"_aws":{"CloudWatchMetrics":[{"Namespace":"Shop","Dimensions":[["Endpoint"]],"Metrics":[{"Name":"Latency","Unit":"Milliseconds"}]}]},"Endpoint":"/order","Latency":87,"customerId":"c-123"}`
Libraries such as Powertools for AWS Lambda generate this format for you.
V: Amazon CloudWatch, AWS Lambda

@ SOA-C03 D1 T1.1 advanced tradeoff
S: A CloudWatch alarm on an EC2 fleet's CPUUtilization uses a 1-minute period and 1 evaluation period, and it pages on single short spikes. The team wants a page only when CPU is high for most of a 5-minute window, even if one or two samples inside that window dip below the threshold. Which alarm configuration fits?
A: Set evaluation periods to 5 and datapoints to alarm to 3, keeping the 1-minute period and the current CPU threshold
B: Set evaluation periods to 5 and datapoints to alarm to 5, keeping the 1-minute period and the current CPU threshold
C: Change the statistic to Maximum with a single 5-minute period and one datapoint to alarm at the current CPU threshold
D: Keep one evaluation period and set the alarm to treat missing data as notBreaching to suppress the brief spike alerts
K: A
W: 3 out of 5 datapoints: the alarm looks at the last five 1-minute points and fires when any three breach. A single spike is ignored, while sustained high CPU still alarms even if one or two samples dip.
X: B=5 out of 5 datapoints: every one of the five points must breach, so a single dip below the threshold resets the condition and a real sustained problem can go unreported.
C=Maximum over 5 minutes: the Maximum statistic reports the highest sample in the period, so one short spike still makes the whole 5-minute datapoint breach. This makes the noise worse, not better.
D=Treat missing data as notBreaching: this only changes how gaps in the data are evaluated. The spikes are real datapoints, not missing ones, so the alarm keeps firing on them.
T: To tolerate spikes and dips at the same time use "M out of N" datapoints to alarm; "N out of N" is too strict and Maximum amplifies spikes.
G: ## How an alarm evaluates
A metric alarm has three settings that work together:
- **Period**: the length of one datapoint, for example 60 seconds.
- **Evaluation periods (N)**: how many of the most recent datapoints are examined.
- **Datapoints to alarm (M)**: how many of those N must breach the threshold.
## M out of N
With `Period=60`, `N=5`, `M=3` the alarm checks the last five minutes and goes to ALARM when any three minutes breach. The breaching points do not have to be consecutive.
- 1 out of 1: every spike pages.
- 5 out of 5: a single healthy minute cancels the alarm.
- 3 out of 5: short spikes are ignored and short dips do not hide a sustained problem.
The statistic also matters: `Average` smooths a period, `Maximum` reports its worst sample.
V: Amazon CloudWatch, Amazon EC2

@ SOA-C03 D1 T1.1 applied use-case
S: Application logs in a CloudWatch Logs log group sometimes contain customer email addresses and credit card numbers. Developers must keep reading these logs for troubleshooting without seeing those values, while a small security group must still be able to view the original values. What should the CloudOps engineer configure?
A: A data protection policy on the log group with managed data identifiers, granting logs:Unmask only to the security group
B: A customer managed KMS key on the log group, granting kms:Decrypt on that key only to the members of the security group
C: An IAM policy that denies logs:GetLogEvents and logs:FilterLogEvents on the log group for every developer role
D: A Logs Insights saved query that filters out lines matching card and email patterns, shared with the developer roles
K: A
W: Data protection policy: CloudWatch Logs scans events at ingestion with managed data identifiers such as `EmailAddress` and `CreditCardNumber` and masks matches for all readers. Only principals with the `logs:Unmask` permission can view the original values.
X: B=KMS key on the log group: encryption protects data at rest, but it never hides parts of a log event. Anyone who can read the log group sees the full values, so developers cannot be given readable logs with the sensitive fields masked.
C=Deny read APIs: this blocks developers from reading the logs entirely, which breaks the requirement that they keep troubleshooting with them.
D=Saved query with filters: a saved query is only a convenience. Developers can still open the log stream or write their own query and see every sensitive value in clear text.
T: Hide sensitive values while keeping logs readable → data protection policy with masking and `logs:Unmask`, not encryption or access denial.
G: ## Masking sensitive data in CloudWatch Logs
A **data protection policy** is attached to a log group (or set account-wide). It uses **managed data identifiers**, predefined patterns for things like email addresses, credit card numbers, AWS secret keys or national ID numbers.
- Matching text in new log events is masked, for example `card=****************`.
- The original data is kept; a principal with `logs:Unmask` can see it in the console or through `GetLogEvents` with `unmask=true`.
- The policy can also send audit findings (which identifier matched, how often) to another log group, S3 or Firehose.
## Why not just encrypt?
KMS encryption answers "who can read stored data at all". Masking answers "which parts of a record can a reader see". Here both groups need access to the logs, so only masking separates them.
V: Amazon CloudWatch, AWS IAM

@ SOA-C03 D1 T1.1 applied troubleshooting
S: An internal reverse proxy process named haproxy on several EC2 instances is occasionally killed by the OS, but the instances keep passing status checks. Traffic is sporadic, so long periods without requests are normal. The team wants an alarm within minutes when the process is not running. What should they do?
A: Configure the CloudWatch agent procstat plugin to track haproxy and alarm when the process PID count drops below 1
B: Enable detailed monitoring on the instances and alarm when CPUUtilization falls below 1 percent for five minutes
C: Create alarms on StatusCheckFailed_Instance for each instance and add an EC2 reboot action when the check fails
D: Stream the haproxy access log to CloudWatch Logs and alarm when the IncomingLogEvents metric drops to zero
K: A
W: procstat plugin: the CloudWatch agent looks up processes by name or pattern and publishes metrics such as `procstat_lookup_pid_count`. An alarm on that metric below 1 fires as soon as the process disappears, independent of traffic.
X: B=Low CPU alarm: idle periods are normal here, so low CPU also occurs while haproxy runs fine, and CPU from other processes can hide a dead proxy. The metric does not represent the process.
C=Instance status check: this check tests OS reachability and networking. A single killed process leaves the OS healthy, which is exactly why the checks keep passing.
D=IncomingLogEvents at zero: with sporadic traffic the access log is often quiet while the proxy is healthy, so the alarm would fire constantly or have to be too slow to be useful.
T: Watch a specific process with the CloudWatch agent's procstat plugin; hypervisor metrics and status checks cannot see individual processes.
G: ## What EC2 metrics can and cannot see
Default EC2 metrics come from the hypervisor: CPU, network, disk I/O and status checks. The hypervisor sees the VM, not the processes inside it.
## The procstat plugin
The unified CloudWatch agent runs inside the OS and can collect process-level data. In its config you name a process by `exe`, `pattern` or `pid_file`:
`"procstat": [{"exe": "haproxy", "measurement": ["pid_count", "cpu_usage", "memory_rss"]}]`
- `procstat_lookup_pid_count` reports how many matching processes exist.
- When the process dies the count becomes 0, and an alarm with threshold `< 1` fires on the next evaluation.
- With the instance ID appended as a dimension, create one alarm per instance to cover the fleet.
Treat missing data as breaching so the alarm also fires if the agent itself stops reporting.
V: Amazon CloudWatch, Amazon EC2

@ SOA-C03 D1 T1.2 advanced troubleshooting
S: An AWS Config rule uses automatic remediation with an AWS Systems Manager Automation runbook to fix noncompliant resources. Evaluations work, but every remediation execution fails with an authorization error on the API call the runbook makes. What should the CloudOps engineer do?
A: Create an IAM role that trusts ssm.amazonaws.com with the needed permissions and pass its ARN as the AutomationAssumeRole parameter
B: Attach the permissions the runbook needs to the AWS Config service-linked role that evaluates the rule and triggers remediation
C: Add the permissions the runbook needs to the instance profile role of every EC2 instance that is managed by Systems Manager
D: Increase the remediation retry attempts and retry interval so the runbook is re-executed until the API call eventually succeeds
K: A
W: AutomationAssumeRole: Automation runbooks make their AWS API calls with the role passed in `AutomationAssumeRole`. That role must trust `ssm.amazonaws.com` and hold the permissions the runbook's steps need, and the remediation configuration maps its ARN into the parameter.
X: B=Config service-linked role: service-linked roles are managed by AWS and cannot be edited, and the runbook does not run with Config's credentials anyway, so its API calls would still be denied.
C=Instance profile role: the instance profile is used by the SSM Agent on the instance. Automation steps such as `aws:executeAwsApi` run in the Automation service, not on the instances, so they never use that role.
D=More retries: an authorization error is deterministic. Retrying the same call with the same missing permission fails every time and only delays the fix.
T: Config remediation runs as the Automation assume role you supply; fix permissions there, not in Config's own role or the instance profile.
G: ## How Config remediation runs
An AWS Config rule only evaluates. When a resource is noncompliant, the remediation configuration starts an **SSM Automation** runbook such as `AWS-EnableS3BucketEncryption` or a custom one.
## Whose permissions?
Automation executes each step itself (for example `aws:executeAwsApi` calls an AWS API). It needs credentials, and remediation supplies them through the `AutomationAssumeRole` parameter:
- The role's trust policy allows `ssm.amazonaws.com` to assume it.
- Its permissions policy allows exactly what the runbook does, for example `s3:PutEncryptionConfiguration`.
- The remediation's parameter mapping sets `AutomationAssumeRole` to a static value, the role's ARN.
If the role is missing or too narrow, the rule keeps flagging the resource and the execution history shows `AccessDenied` on the step's API call.
V: AWS Config, AWS Systems Manager, AWS IAM

@ SOA-C03 D1 T1.2 advanced troubleshooting
S: After the security team enabled server-side encryption on an SNS topic using the AWS managed key aws/sns, CloudWatch alarms that publish to the topic still enter ALARM, but no notifications arrive. The alarm history shows the action failed. Subscriptions are confirmed. What is the fix?
A: Re-encrypt the topic with a customer managed KMS key whose key policy allows cloudwatch.amazonaws.com to use the key
B: Add cloudwatch.amazonaws.com to the aws/sns key policy so the CloudWatch service principal can call kms:GenerateDataKey
C: Delete and re-create the email subscriptions so each subscriber confirms the new encrypted delivery path of the topic
D: Recreate the alarms so their actions use the SNS topic's delivery policy instead of publishing to the topic ARN directly
K: A
W: Customer managed key: CloudWatch must be allowed to call `kms:GenerateDataKey*` and `kms:Decrypt` to publish to an encrypted topic. The key policy of an AWS managed key cannot be changed, so the topic needs a customer managed key whose policy grants these actions to `cloudwatch.amazonaws.com`.
X: B=Edit the aws/sns key policy: AWS managed key policies are owned by AWS and cannot be modified, so this grant cannot be made.
C=Re-create subscriptions: the failure happens when CloudWatch publishes to the topic, before any delivery to subscribers. Confirmed subscriptions are not the problem and re-confirming changes nothing.
D=Use the delivery policy: a delivery policy controls retries for HTTP/S endpoints. Alarms always publish to a topic ARN, and the KMS permission problem remains.
T: Services that publish to encrypted SNS topics (such as CloudWatch alarms) need a customer managed key they are allowed to use; aws/sns cannot be shared with them.
G: ## Encrypted SNS topics
With server-side encryption, SNS encrypts each message with a data key from AWS KMS. The **publisher** therefore needs KMS permissions on the topic's key, not only `sns:Publish`.
## AWS managed vs customer managed keys
- **AWS managed key** (`alias/aws/sns`): free and automatic, but its key policy is fixed. It only allows principals in your account that use SNS on their own behalf.
- **Customer managed key**: you write the key policy, so you can allow AWS service principals.
Key policy statement for CloudWatch alarms:
`{"Effect":"Allow","Principal":{"Service":"cloudwatch.amazonaws.com"},"Action":["kms:Decrypt","kms:GenerateDataKey*"],"Resource":"*"}`
The same pattern applies to EventBridge, S3 event notifications and other services that publish to encrypted topics.
V: Amazon SNS, AWS KMS, Amazon CloudWatch

@ SOA-C03 D1 T1.2 applied troubleshooting
S: New EC2 instances in a private subnet do not appear as managed nodes in Systems Manager, so Run Command and Session Manager cannot reach them. The AMI includes a current SSM Agent, and the account does not use Default Host Management Configuration. Which TWO causes should the engineer check? (Select TWO)
A: The instance profile does not include the AmazonSSMManagedInstanceCore managed policy
B: The subnet has no NAT gateway route and no interface endpoints for ssm, ssmmessages, and ec2messages
C: The security group does not allow inbound TCP 22 from the Systems Manager service IP ranges
D: The instances were launched without an EC2 key pair, so the agent cannot sign its registration
E: The security group does not allow inbound TCP 443 from the Systems Manager service endpoints
K: A,B
W: A=Instance profile permissions: the SSM Agent registers with Systems Manager using the instance profile credentials, which need `AmazonSSMManagedInstanceCore` when Default Host Management Configuration is not used.
B=Outbound path from the private subnet: the agent must reach the service endpoints over outbound HTTPS, through a NAT gateway or through interface VPC endpoints for `ssm`, `ssmmessages` and `ec2messages`.
X: C=Inbound SSH rule: Systems Manager does not use SSH. The agent opens outbound connections, so no inbound port is needed at all.
D=Missing key pair: key pairs are only for SSH or RDP logins. The agent authenticates with the instance profile's IAM credentials, not a key pair.
E=Inbound HTTPS rule: the connection is initiated outbound by the agent; security groups are stateful, so return traffic is allowed without any inbound rule.
T: A node becomes managed when the agent has IAM permissions and an outbound path to the SSM endpoints; inbound ports and key pairs play no role.
G: ## How a node becomes "managed"
The SSM Agent on the instance calls the Systems Manager service outbound over HTTPS (port 443). Three things must be true:
- **Agent** installed and running (true here).
- **Credentials**: normally an instance profile role with the managed policy `AmazonSSMManagedInstanceCore`. (Default Host Management Configuration can supply them instead, but it is not enabled here.)
- **Network path** to the endpoints `ssm.<region>.amazonaws.com`, `ssmmessages...` and `ec2messages...`.
## Private subnets
A private subnet has no internet gateway route. The path must come from:
- a NAT gateway route `0.0.0.0/0 → nat-...`, or
- interface VPC endpoints for the three services, with private DNS enabled and a security group on the endpoints allowing 443 from the instances.
Nothing needs to reach the instance inbound, which is why Session Manager works without open ports.
V: AWS Systems Manager, Amazon VPC, AWS IAM

@ SOA-C03 D1 T1.3 advanced troubleshooting
S: During a disaster recovery drill, EBS volumes for a database are created from snapshots. For the first hour the database shows extremely high read latency, then performance becomes normal. The runbook requires full volume performance as soon as the restored instances start. What should the team do?
A: Enable EBS fast snapshot restore on the snapshots in the Availability Zones where the recovery volumes will be created
B: Restore the volumes as io2 with much higher provisioned IOPS than production so reads have enough headroom right away
C: Register the snapshots as an AMI and launch the database instances from it so the volumes are created during instance launch
D: Choose a larger instance type with more dedicated EBS bandwidth so reads from the new volumes are not limited by the instance
K: A
W: Fast snapshot restore: volumes created from a snapshot normally load blocks lazily from Amazon S3 on first access. With fast snapshot restore enabled for a snapshot in an AZ, volumes created there are fully initialized at creation and deliver full performance immediately.
X: B=Higher provisioned IOPS: the delay comes from fetching each block from S3 on first read, not from the IOPS limit. Extra IOPS do not remove the first-read penalty.
C=Launch from an AMI: an AMI is backed by the same EBS snapshots, so its volumes are also initialized lazily and show the same first-read latency.
D=Larger instance type: the instance was not the bottleneck; performance becomes normal later on the same instance once blocks are loaded, which points to volume initialization.
T: Slow first reads on restored volumes come from lazy loading; fast snapshot restore (or pre-reading every block) removes it, more IOPS or bigger instances do not.
G: ## How a volume is restored from a snapshot
Snapshots live in Amazon S3. When you create an EBS volume from one, the volume is usable at once, but its blocks are pulled from S3 **the first time they are read**. That first access can be much slower than normal, which is called volume initialization.
## Ways to avoid the penalty
- **Fast snapshot restore (FSR)**: enabled per snapshot and per Availability Zone. Volumes created from it in those AZs are fully initialized at creation. Billed per snapshot-AZ hour, so enable it before drills or for critical DR snapshots.
- **Pre-warm by reading everything**: run `fio` or `dd` over the whole device after restore. It works without extra cost but takes time proportional to the volume size.
Example: a 2 TiB database volume restored normally might take hours to warm under load; with FSR on `snap-0abc` in `us-east-1a`, the volume created in `us-east-1a` performs fully from its first read.
V: Amazon EBS, Amazon EC2

@ SOA-C03 D1 T1.3 applied tradeoff
S: A CPU-bound image-processing Lambda function is configured with 512 MB of memory and takes about 8 seconds per invocation. CloudWatch shows it uses only 180 MB of memory, so a teammate proposes reducing memory to save cost. What should the CloudOps engineer recommend?
A: Test higher memory settings, because Lambda assigns CPU in proportion to memory and shorter runs can cost less
B: Reduce the memory to 256 MB, because billed cost scales with configured memory and the extra memory is unused
C: Configure provisioned concurrency for the function, because it gives each execution environment dedicated CPU
D: Increase the function timeout, because the 8-second duration shows the function is close to hitting its limit
K: A
W: Raise memory to get CPU: Lambda allocates CPU power proportionally to the memory setting (about one full vCPU at 1,769 MB, up to 6 vCPUs at 10,240 MB). A CPU-bound function often finishes several times faster with more memory, and because cost is memory x duration, the total can stay the same or drop.
X: B=Reduce to 256 MB: it halves the CPU share too, so a CPU-bound function runs roughly twice as long. Cost per invocation barely changes while latency gets worse.
C=Provisioned concurrency: it keeps environments initialized to avoid cold starts. It does not give an invocation more CPU than its memory setting allows.
D=Longer timeout: nothing indicates timeouts are occurring, and a longer limit does not make the code run faster.
T: For CPU-bound Lambda functions memory is the CPU dial; tune it by measuring duration and cost, not by memory used.
G: ## Memory is the only compute knob in Lambda
You set memory from 128 MB to 10,240 MB. CPU and network bandwidth are assigned in proportion:
- About 1,769 MB equals one vCPU.
- 10,240 MB gives up to 6 vCPUs (useful only if the code is multithreaded).
## Cost is memory x time
Lambda bills GB-seconds. Example for this function:
- 512 MB x 8 s = 4 GB-s
- 1,536 MB x 2.5 s = 3.75 GB-s: faster **and** slightly cheaper.
- 256 MB x 16 s = 4 GB-s: same cost, twice as slow.
## How to choose
Run the function at several memory sizes and compare duration and cost. AWS Lambda Power Tuning automates this, and AWS Compute Optimizer gives memory recommendations from real invocations. The "Max Memory Used" value in the logs only tells you the floor, not the best setting.
V: AWS Lambda, Amazon CloudWatch

@ SOA-C03 D1 T1.3 advanced troubleshooting
S: A database on an m5.large instance uses an io2 volume provisioned for 40,000 IOPS, but under load it never gets close. CloudWatch shows the instance's EBSIOBalance% draining to zero and volume IOPS then settling far below the provisioned value. What should the CloudOps engineer do?
A: Move to an instance type whose EBS-optimized IOPS and bandwidth limits meet or exceed the volume's provisioned performance
B: Modify the io2 volume to raise its provisioned IOPS further so that it can push more operations through the same instance
C: Stripe two io2 volumes in RAID 0 on the same instance so that the operating system can spread its I/O across both volumes
D: Turn on the EBS-optimized attribute for the instance so that storage traffic gets its own dedicated network bandwidth
K: A
W: Bigger EBS limit on the instance: every instance type has its own maximum EBS IOPS and throughput. Smaller sizes can burst above a low baseline only while their EBS I/O credits (`EBSIOBalance%`) last. Once the balance is empty the instance, not the volume, caps performance, so the fix is an instance type with higher sustained EBS limits.
X: B=Raise volume IOPS: the volume is already provisioned above what the instance can deliver. More volume IOPS cannot pass through an instance-level cap.
C=RAID 0 across two volumes: striping helps when a single volume is the limit. Both volumes share the same instance EBS limit, so the total stays capped.
D=Enable EBS-optimized: current-generation types like m5 are EBS-optimized by default. The attribute is already in effect, and the limit being hit is the size of that dedicated bandwidth.
T: EBS performance is the lower of the volume's and the instance's limits; a draining EBSIOBalance% means resize the instance, not the volume.
G: ## Two limits on every EBS I/O
Each I/O must fit within both:
- the **volume** limit (for example provisioned io2 IOPS), and
- the **instance** EBS limit, which depends on instance type and size.
## Burst EBS performance on smaller instances
Many smaller sizes list EBS performance as "up to" a value. They have a lower **baseline** and can burst above it for a limited time (around 30 minutes per day) using credits. CloudWatch exposes the credits as `EBSIOBalance%` (IOPS) and `EBSByteBalance%` (throughput).
Example: the volume allows 40,000 IOPS, but a small instance's baseline is a few thousand IOPS. When `EBSIOBalance%` reaches 0 the volume metrics flatten at the instance baseline.
## What to do
Compare the instance type's documented EBS baseline IOPS and throughput with the volume's needs and pick a size or family that meets them in sustained operation.
V: Amazon EBS, Amazon EC2, Amazon CloudWatch

@ SOA-C03 D1 T1.3 advanced troubleshooting
S: A provisioned-capacity DynamoDB table uses event_date as its partition key. Writes for the current day are throttled even though the table's consumed WCU is far below provisioned WCU. The team wants to confirm the cause and fix it for the long term. Which TWO actions should they take? (Select TWO)
A: Enable CloudWatch Contributor Insights for DynamoDB on the table to identify the most throttled partition keys
B: Redesign the key with a higher-cardinality partition key or add a calculated suffix to spread writes across partitions
C: Double the table's provisioned WCU so that each partition receives a larger share of the total write capacity
D: Put DynamoDB Accelerator (DAX) in front of the table so that the write traffic for the current day is absorbed
E: Add a global secondary index keyed on event_date so the writes for the current day are divided between table and index
K: A,B
W: A=Contributor Insights for DynamoDB: it ranks the most accessed and most throttled partition keys, confirming that one date value receives nearly all of the day's writes.
B=Higher-cardinality key or write sharding: a key with more distinct values, or a suffix such as `2026-09-29#7`, spreads the writes across many partitions and removes the hot key.
X: C=Double provisioned WCU: a single partition still cannot exceed about 1,000 WCU. When all writes target one key, raising the table total leaves that partition's limit unchanged.
D=Add DAX: DAX caches reads. Writes go through DAX to the table (write-through), so the hot-partition writes still hit the same partition.
E=GSI on event_date: the index has the same hot key, and writes to the table must also be written to the index. A throttled GSI adds back-pressure instead of relieving it.
T: Throttling with spare table capacity means a hot partition key; find it with Contributor Insights and fix the key design, not the capacity.
G: ## Partitions and their limits
DynamoDB stores items in partitions chosen by hashing the partition key. Each partition supports up to **3,000 RCU and 1,000 WCU**. Adaptive capacity shifts unused capacity toward busy partitions, but it cannot fully absorb traffic that is concentrated on one partition key value.
## The hot-key pattern
With `event_date` as the key, every write of the day has the same key, so all writes land on one partition. The table total looks fine, yet requests are throttled.
## Diagnose and fix
- **Contributor Insights for DynamoDB**: ranks keys by traffic and by throttled requests.
- **Write sharding**: append a random or calculated suffix, `event_date#0` ... `event_date#9`, and query all suffixes when reading a day.
- **Better key**: use a high-cardinality attribute such as `device_id` and keep the date as the sort key.
V: Amazon DynamoDB, Amazon CloudWatch

@ SOA-C03 D2 T2.1 applied tradeoff
S: Instances in an Auto Scaling group need about 12 minutes after launch to load application data before they can serve traffic. Traffic spikes are unpredictable. The team wants new capacity in service within about a minute of a scale-out, while paying as little as possible for pre-initialized capacity that is waiting. Which solution fits best?
A: Add a warm pool to the Auto Scaling group with the pool state set to Stopped and use a lifecycle hook to initialize instances
B: Add a warm pool to the Auto Scaling group with the pool state set to Running so initialized instances can join immediately
C: Raise the group's minimum capacity to cover the largest expected spike so that initialized instances are always in service
D: Enable predictive scaling on the group in forecast-and-scale mode so that instances are launched ahead of each spike
K: A
W: Warm pool in Stopped state: instances are launched, fully initialized once by a lifecycle hook, then stopped. While stopped you pay only for EBS volumes and attached Elastic IPs; on scale-out they start in seconds with the application data already loaded.
X: B=Warm pool in Running state: it gives the fastest join, but you pay full instance-hours for every waiting instance, which is not the lowest cost for idle capacity.
C=Higher minimum capacity: the extra instances run and serve traffic all the time, costing full price around the clock just to cover rare spikes.
D=Predictive scaling: it forecasts from recurring daily or weekly patterns. Unpredictable spikes have no pattern to learn, so instances would still launch late.
T: Long boot plus unpredictable spikes → warm pool; Stopped state keeps pre-initialized capacity cheap, Running state is faster but pays for compute.
G: ## What a warm pool is
A **warm pool** is a set of pre-initialized EC2 instances kept next to an Auto Scaling group. On scale-out, the group takes instances from the warm pool instead of launching fresh ones, skipping the slow boot and application setup.
## Pool states and cost
- **Running**: instances run but receive no traffic. Fastest, full compute cost.
- **Stopped**: instances are stopped after initialization. You pay only for storage (EBS) and Elastic IPs. Starting takes seconds to a minute.
- **Hibernated**: memory is saved to EBS, useful when in-memory state is expensive to rebuild.
## How initialization works
A lifecycle hook on the warm pool launch runs your setup (download data, warm caches), then completes the hook and the instance moves to its pool state. Example: `MinSize=4`, warm pool `MinSize=6`, state `Stopped`; a spike moves up to six ready instances into service within about a minute.
V: Amazon EC2 Auto Scaling, Amazon EC2

@ SOA-C03 D2 T2.1 applied comparison
S: An API fleet behind an ALB is limited by calls to a downstream service, not by CPU. Load tests show each instance handles about 500 requests per minute before latency rises, while CPU stays under 30%. A CPU-based target tracking policy therefore never scales out. Which policy fits best?
A: Target tracking on ALBRequestCountPerTarget with a target value somewhat below 500 requests per target
B: Target tracking on average CPUUtilization with the target value lowered from 50 percent to 20 percent

@ SOA-C03 D2 T2.2 advanced comparison
