@ SOA-C03 D4 T4.1 applied troubleshooting
S: An AWS Config rule evaluates security groups for unrestricted SSH access. The team attached automatic remediation that runs an AWS Systems Manager Automation runbook, but non-compliant security groups stay non-compliant and the remediation execution status shows Failed with an access denied error. What is the most likely cause?
A: The remediation action has no AutomationAssumeRole, or the role it uses does not trust Systems Manager and lacks the EC2 permissions to change security group rules
B: The Config rule is a custom rule backed by Lambda, and automatic remediation is only supported for rules that use an AWS managed rule identifier
C: The configuration recorder is set to daily recording, so Config waits up to 24 hours before it is allowed to start any remediation for a changed resource
D: The runbook was chosen from the Systems Manager public documents, and Config can only run remediation with runbooks that the account has copied into its own Region
K: A
W: Missing or under-privileged role: a Config remediation action runs an Automation runbook, and that runbook makes the EC2 calls under the role given as its AutomationAssumeRole parameter. If the role is missing, does not trust `ssm.amazonaws.com`, or lacks permissions such as `ec2:RevokeSecurityGroupIngress`, the execution fails with access denied while the resource stays non-compliant.
X: B=Managed rules only: remediation actions can be attached to any Config rule, managed or custom, because they act on the evaluation result and not on how the rule was built.
C=Daily recording: recording frequency affects how quickly configuration changes are captured and evaluated, but it does not produce an access denied error in an execution that has already started.
D=Copied documents: Config remediation can use AWS owned runbooks such as `AWS-DisablePublicAccessForSecurityGroup` directly from the public documents. Nothing has to be copied first.
T: A Config remediation is only as powerful as the AutomationAssumeRole behind its runbook: check trust to Systems Manager and the permissions for the exact change.
G: ## How Config remediation works
AWS Config rules mark resources COMPLIANT or NON_COMPLIANT. A remediation action links a rule to a Systems Manager Automation runbook, and can run automatically (with a retry count and interval) or manually.
## Who does the work
The runbook does not run as Config. It runs with the permissions of the IAM role passed as `AutomationAssumeRole`. That role must trust Systems Manager and allow exactly the API calls the runbook makes, for example changing security group rules. When an execution fails immediately with access denied, check this role first.
V: AWS Config, AWS Systems Manager

@ SOA-C03 D4 T4.1 applied use-case
S: A company uses AWS Organizations and wants every new EC2 instance and EBS volume in member accounts to carry a CostCenter tag, and a request that omits the tag must be rejected at creation time. The team already attached a tag policy that defines the CostCenter key, but untagged resources are still being created. What should the team add?
A: A service control policy that denies ec2:RunInstances and ec2:CreateVolume when the aws:RequestTag/CostCenter condition key is absent, checked with a Null condition
B: A second tag policy on the same organizational unit that lists CostCenter as a required key, because tag policies can force a tag to be present on every new resource
C: An AWS Config rule in each member account that stops any untagged instance or volume the moment it is created, before the launch API call finishes
D: A resource-based policy on every EBS volume and instance that refuses launch requests without the tag, attached by the account administrators after each launch
K: A
W: SCP with a Null condition: a tag policy standardizes tag keys and values (for example capitalization and allowed values) but does not require a tag to exist. An SCP that denies `ec2:RunInstances` and `ec2:CreateVolume` when `aws:RequestTag/CostCenter` is null blocks the creation request itself, in every member account.
X: B=Second tag policy: tag policies cannot make a tag mandatory. They only check the tags that are present, so untagged resources are not reported by them and are not blocked.
C=Config rule: Config evaluates resources after they exist, so it can flag or remediate an untagged resource but cannot reject the API call before creation.
D=Resource-based policies: EC2 instances and EBS volumes do not have resource-based policies that gate the launch request, and doing something by hand after each launch would not prevent the creation anyway.
T: Tag policies standardize tags; to require a tag at creation, use an SCP (or IAM policy) that checks aws:RequestTag with a Null condition.
G: ## Two tools that sound alike
- **Tag policies** define the allowed tag keys, capitalization and values, and report non-compliant tags. They can optionally block non-compliant tagging operations for supported resource types, but they never demand that a tag be there.
- **Service control policies** set the maximum permissions of member accounts and can deny an API call based on condition keys such as `aws:RequestTag/<key>` and `aws:TagKeys`.
## Requiring a tag
Deny the create action when `aws:RequestTag/CostCenter` has `"Null": "true"`. Combine it with a tag policy so that the tag that is present also has an allowed value.
V: AWS Organizations, Amazon EC2

@ SOA-C03 D4 T4.1 applied comparison
S: A company is building a multi-account landing zone with AWS Control Tower. One requirement is to block member accounts from disabling AWS CloudTrail. Another is to be alerted when an S3 bucket in any account allows public read access, while still allowing the change to happen. How do Control Tower controls meet the two requirements?
A: Use a preventive control, which is enforced with a service control policy, for the CloudTrail requirement, and a detective control, which uses an AWS Config rule, for the bucket requirement
B: Use a detective control, which is enforced with a service control policy, for the CloudTrail requirement, and a preventive control, which uses an AWS Config rule, for the bucket requirement
C: Use proactive controls for both, because proactive controls are implemented through CloudFormation hooks that stop every noncompliant API call across all accounts and services
D: Use an IAM permissions boundary on every account administrator for the CloudTrail requirement, and a Control Tower preventive control for the alerting requirement on public buckets
K: A
W: Preventive plus detective: preventive controls are implemented with SCPs from AWS Organizations, so an account cannot perform the denied action (such as stopping the trail). Detective controls are implemented with AWS Config rules and report non-compliance after the change, which fits alerting without blocking.
X: B=Reversed types: SCPs are the mechanism of preventive controls, and Config rules are the mechanism of detective controls. Swapping them describes behavior Control Tower does not have.
C=Proactive for both: proactive controls use CloudFormation hooks and only evaluate resources being provisioned through CloudFormation, so they do not stop API calls made directly against an account and they do not alert on existing buckets.
D=Permissions boundary: boundaries have to be attached identity by identity and can be removed by anyone who can change the identity, while an SCP applies to the whole account. A preventive control also blocks a change rather than alerting on it.
T: Control Tower preventive controls are SCPs (block), detective controls are Config rules (detect and report), proactive controls are CloudFormation hooks (check before provisioning).
G: ## The three behaviors of controls
- **Preventive**: implemented as SCPs, block the action.
- **Detective**: implemented as AWS Config rules, flag non-compliant resources.
- **Proactive**: implemented as CloudFormation hooks, check a template before resources are created.
## Picking the behavior
"Must never happen" points to preventive, "tell me if it happened" points to detective, and "stop a bad template from deploying" points to proactive.
V: AWS Control Tower, AWS Organizations, AWS Config

@ SOA-C03 D4 T4.1 applied troubleshooting
S: A patch policy in AWS Systems Manager Patch Manager is applied to a fleet. Compliance reports show many instances as NON_COMPLIANT because critical operating system patches are missing, but the instances have never installed any patches even though they are all in the target. What is the most likely cause?
A: The patching operation in the patch policy or maintenance window task is set to Scan, which only reports missing patches, so it must be changed to Scan and install
B: The patch baseline has an auto-approval delay of zero days, and Patch Manager does not install any patch that is approved on the same day it was released
C: The instances are running an older SSM Agent version, and Patch Manager marks all of them non-compliant until the agent is replaced by the new agent
D: The instances are members of two patch groups, and Patch Manager refuses to install patches until an administrator selects one patch group for each of them
K: A
W: Scan operation: Patch Manager can run in Scan mode, which evaluates each instance against its patch baseline and reports missing patches as compliance data without installing anything. Changing the operation to Scan and install makes it apply the missing patches during the maintenance window.
X: B=Zero-day delay: an auto-approval delay of zero approves patches immediately, which makes them eligible for installation, not blocked.
C=Old SSM Agent: an outdated agent can cause other problems, but compliance is calculated from the baseline scan. Non-compliance for missing patches is the expected result of a scan-only run.
D=Two patch groups: an instance can belong to only one patch group for a patching operation, and it is not a state that blocks installs. It also does not explain why the instances only show as non-compliant.
T: Non-compliant plus nothing installed usually means the patching operation is Scan; use Scan and install to remediate.
G: ## Scan versus install
Patch Manager has two operations: Scan reports which approved patches are missing (compliance data in Patch Manager and Explorer), and Install (Scan and install) applies them. A patch policy or a maintenance window task selects which one runs.
## Reading compliance
An instance is compliant when no approved patch in its baseline is missing, so a scan-only setup will show non-compliance until an install run succeeds.
V: AWS Systems Manager

@ SOA-C03 D4 T4.1 advanced comparison
S: A team reviews how service control policies apply in an organization. Which TWO statements about SCPs are correct? (Select TWO)
A: An SCP does not grant permissions by itself; a principal needs an identity-based or resource-based policy allowing the action, and the SCP must also allow it
B: SCPs attached to the root of the organization apply to every account, including the management account, so an administrator there can be restricted
C: A deny in an SCP attached to an OU applies to member accounts in it, including the account root user, but not to service-linked roles
D: An SCP with an Allow statement for s3:* on an OU gives all IAM users in those accounts access to S3 without a separate IAM policy
E: SCPs can be attached only to individual accounts, and a policy attached to an OU has to be copied to each account before it is evaluated
K: A,C
W: A=No grants: SCPs define the maximum available permissions. A request succeeds only when an SCP allows it and an IAM policy (or resource policy) also grants it.
C=Root user and service-linked roles: SCPs affect all principals in member accounts, including the account root user, but do not affect service-linked roles.
X: B=Management account: SCPs do not restrict the management account, whichever level they are attached to.
D=Allow gives access: an SCP Allow only permits actions to be granted by other policies, and does not grant any access itself.
E=Accounts only: SCPs can be attached to the root, OUs, or accounts, and OU policies are inherited by the accounts below.
T: SCPs limit but never grant; they apply to member accounts (including root users) but not to the management account or service-linked roles.
G: ## How SCPs are evaluated
SCPs form a filter above IAM: the effective permissions of a principal are the intersection of what the SCPs allow and what IAM policies grant. An explicit Deny in an SCP always wins.
## Exceptions
The management account is not affected by SCPs, and service-linked roles are not restricted by them. Everything else in member accounts, including the root user of each account, is.

@ SOA-C03 D4 T4.2 applied troubleshooting
S: A security policy requires annual rotation of a customer managed KMS key. The team created the key with imported key material so that it could bring its own key, and when they try to enable automatic key rotation, the operation is rejected. What is the correct way to meet the policy?
A: Rotate the key manually by creating a new key with new imported material and pointing the alias at it, keeping the old key to decrypt existing data

Keys with imported key material, asymmetric keys, HMAC keys and keys in custom key stores do not support automatic rotation. For those, create a new key and move the alias, and keep the old key for old ciphertext.

X: B=Governance mode: governance mode lets users with the right permissions change or remove the lock, so it does not meet a rule that nobody can.
C=Lifecycle rule: a lifecycle defines when backups expire, but an administrator can still delete the recovery points or edit the plan.
D=Access policy: a vault access policy can be edited by whoever has permission to change it, so it does not offer an immutability guarantee.
T: For immutable backups, use AWS Backup Vault Lock in compliance mode; the lock becomes permanent after the grace period.
G: ## Vault Lock modes
- **Governance mode**: enforces the retention rules, but authorized users can still remove the lock.
- **Compliance mode**: after a grace period (cooling-off time), nobody can change or delete the lock or the protected recovery points before they expire.
## Why the grace period matters
It lets you test the settings, because after it ends the configuration is permanent.
V: AWS Backup

@ SOA-C03 D4 T4.2 applied use-case
S: Workloads in private subnets read from the company's S3 buckets through a gateway VPC endpoint. Security wants to make sure that resources in the VPC can be used to reach only three named company buckets, so that a compromised instance cannot copy data to a bucket owned by an outside account. Which control should be added?
A: An endpoint policy on the gateway endpoint that allows S3 actions only on the ARNs of the three buckets and their objects
B: A network ACL on the private subnets that lists the IP addresses of the three buckets and denies all other S3 addresses
C: A bucket policy on each of the three buckets that denies access unless the request comes from the endpoint, and nothing else in the VPC
D: A security group rule on the instances that allows outbound HTTPS only to the S3 prefix list, which limits traffic to specific buckets
K: A
W: Endpoint policy: a VPC endpoint policy is evaluated on every request that goes through the endpoint. Limiting the Resource element to the three bucket ARNs blocks requests to any other bucket, including buckets in accounts outside the company.
X: B=Network ACL: S3 addresses are shared and change, and NACLs work with IP ranges, so they cannot name individual buckets.
C=Bucket policies: these protect the company's buckets from access that does not use the endpoint, but they do not stop the VPC from writing to an outside bucket.
D=Security group prefix list: the S3 prefix list covers all S3 addresses in the Region, so it allows all buckets.
T: To restrict which buckets a VPC can reach through an endpoint, use the endpoint policy with bucket ARNs; bucket policies control who can reach the bucket, not where the VPC can go.
G: ## Two directions of control
- **Bucket policy** (with `aws:SourceVpce` or `aws:SourceVpc`): limits which networks can access a bucket you own.
- **VPC endpoint policy**: limits which resources and actions can be reached through the endpoint.
## Data exfiltration
To stop a compromised instance from copying data to an outside bucket, restrict the endpoint policy to named buckets.
V: Amazon VPC, Amazon S3

@ SOA-C03 D4 T4.2 applied troubleshooting
S: An ALB serves HTTPS with an ACM public certificate validated by DNS. The certificate is close to expiry and the status shows it was not renewed. A cleanup script deleted several CNAME records in the public hosted zone last month. What should the engineer do?
A: Recreate the CNAME record that ACM provided for validation in the hosted zone, so that ACM can validate the domain and renew the certificate
B: Import the certificate again from a private key that was generated with OpenSSL, because ACM public certificates cannot be renewed automatically
C: Add a TXT record with the ACM certificate ARN to the hosted zone, because renewal checks use TXT records and not CNAME records
D: Delete the certificate on the ALB listener and request a new one over email validation, because DNS validation supports a single issuance only
K: A
W: Restore the validation CNAME: ACM renews public certificates automatically, but DNS-validated certificates need the validation CNAME record to remain in DNS. When it was deleted, ACM cannot prove control of the domain, so renewal fails until the record is added again.
X: B=Import: imported certificates are not renewed by ACM, so the automatic renewal would be lost.
C=TXT record: DNS validation uses a specific CNAME record for the certificate.
D=Switch to email: DNS validation is not single-use. It supports renewals as long as the CNAME is present, and email validation is the more manual method.
T: ACM renews DNS-validated certificates automatically only while the validation CNAME remains in DNS.
G: ## Managed renewal
For public certificates issued by ACM and in use, ACM starts renewing about 60 days before expiry. For DNS-validated certificates it re-checks the same CNAME record it gave you at request time.
## Why cleanup scripts break it
If the record is removed, ACM cannot validate, and the status shows a validation problem. Imported certificates are not renewed by ACM at all.
V: AWS Certificate Manager, Elastic Load Balancing, Amazon Route 53

@ SOA-C03 D4 T4.2 applied use-case
S: A company must share an encrypted EBS snapshot with a partner account so the partner can create volumes from it. The volume was encrypted with the AWS managed key aws/ebs. The share fails. What must the operations team do?
A: Copy the snapshot and encrypt the copy with a customer managed KMS key, then share the snapshot and grant the partner account permission to use the key
B: Add the partner account to the key policy of aws/ebs, then share the snapshot with the partner, who can then decrypt it with the shared AWS managed key
C: Turn off encryption on the snapshot and share the plaintext snapshot, because encrypted snapshots cannot be shared with other accounts
D: Share the snapshot with all AWS accounts by making it public, and rely on the encryption to prevent any unauthorized account from using it
K: A
W: Customer managed key: snapshots encrypted with the AWS managed key cannot be shared, because that key's policy cannot be changed. Copy the snapshot with a customer managed key, share it, and allow the partner account to use the key through its key policy.
X: B=Edit aws/ebs: the key policy of an AWS managed key cannot be edited.
C=Decrypt: encrypted snapshots can be shared as long as the key is a customer managed key, and there is no need to expose plaintext data.
D=Public: encrypted snapshots cannot be made public, and public sharing would be a poor choice.
T: To share an encrypted EBS snapshot, use a customer managed KMS key and grant the target account access to the key.
G: ## Why AWS managed keys block sharing
The key policy of an AWS managed key is controlled by AWS and cannot be changed to allow other accounts.
## The sharing procedure
1. Copy the snapshot, choosing a customer managed key.
2. Share the copy with the target account IDs.
3. Allow those accounts to use the key (key policy or grant).
The partner then copies the snapshot with its own key and creates volumes.
V: Amazon EBS, AWS KMS

@ SOA-C03 D4 T4.2 advanced use-case
S: An existing Amazon EFS file system was created without encryption at rest, and an audit finding requires it to be encrypted. What is the correct approach?
A: Create a new encrypted file system and copy the data to it, for example with AWS DataSync, then switch the mounts and retire the old file system
B: Enable encryption on the existing file system from the EFS console, which re-encrypts stored files in the background without any downtime
C: Attach a KMS key to the existing file system's mount targets, so that data is encrypted in transit and at rest as it moves through them
D: Enable encryption by default on the account for EFS, which converts every existing unencrypted file system to encrypted in the next maintenance window
K: A
W: New file system and copy: encryption at rest for EFS is set when the file system is created and cannot be changed later. To meet the requirement, create an encrypted file system, copy the data (DataSync or another copy tool), and cut over.
X: B=Console toggle: there is no in-place option to encrypt an existing file system.
C=Mount target key: KMS keys are not attached to mount targets. In-transit encryption is a mount option that uses TLS, separate from at-rest encryption.
D=Account default: no account-level setting converts existing file systems.
T: EFS encryption at rest can only be chosen at creation; migrate an unencrypted file system to a new encrypted one.
G: ## Encryption at rest for EFS
A file system is encrypted at rest only if you choose it when creating it. It uses a KMS key, and the choice cannot be changed later.
## Migration
Create the encrypted file system, copy data with AWS DataSync (or AWS Backup restore into a new encrypted file system), test, and switch the applications to the new file system.
V: Amazon EFS, AWS DataSync, AWS KMS

@ SOA-C03 D4 T4.2 advanced use-case
S: A company wants to protect its customer managed KMS keys against accidental or malicious deletion, because deleting a key would make the encrypted data unrecoverable. Which TWO controls help? (Select TWO)
A: Use an SCP or IAM policy that denies kms:ScheduleKeyDeletion for everyone except a break-glass role that requires MFA
B: Set the waiting period for key deletion to zero days so that the deletion completes as quickly as possible and can be audited afterwards
C: Create an EventBridge rule that matches the CloudTrail ScheduleKeyDeletion API call and notifies a security topic as soon as anyone schedules a key for deletion
D: Enable automatic key rotation, because a key with rotation enabled cannot be scheduled for deletion by any principal
E: Convert each key into a multi-Region primary key, since replica keys in other Regions block deletion of the primary key
K: A,C
W: A=Restrict the action: denying `kms:ScheduleKeyDeletion` except for a controlled role limits who can start a deletion.
C=Alert on scheduling: the ScheduleKeyDeletion call is recorded by CloudTrail as a management event that EventBridge can match, and the waiting period gives time to cancel the deletion.
X: B=Zero-day waiting: KMS requires a waiting period of 7 to 30 days for scheduled deletion, which gives time to react.
D=Rotation: rotation changes key material and does not prevent scheduling deletion.
E=Multi-Region: a primary key with replicas can still be scheduled for deletion, but the deletion only completes after the replicas are deleted, so this is not a protection control.
T: Guard KMS keys by limiting who can schedule deletion and alerting on the ScheduleKeyDeletion call within the 7-30 day waiting period.
G: ## Deleting a key is a scheduled event
KMS keys are not deleted right away: you schedule deletion with a waiting period of 7 to 30 days. During that time the key cannot be used and the deletion can be canceled.
## Layers of protection
- Prevent: restrict `kms:ScheduleKeyDeletion` by policy or SCP.
- Detect: alert on the ScheduleKeyDeletion API call through CloudTrail and EventBridge.
- Recover: cancel the deletion during the waiting period.
V: AWS KMS, Amazon EventBridge
