@ Q002748 explain
G: ## Paying for steady compute
EC2 has several purchase models, and the right one depends on how predictable the usage is.
- **On-Demand**: pay per second or hour with no commitment. Most flexible, highest unit price.
- **Savings Plans**: commit to a dollar amount of compute per hour (for example `$10/hour`) for 1 or 3 years. **Compute Savings Plans** apply automatically across instance families, sizes, Regions, operating systems, and also to Fargate and Lambda. **EC2 Instance Savings Plans** give a deeper discount but are tied to one instance family in one Region.
- **Reserved Instances**: a 1- or 3-year commitment to a specific instance configuration (Standard or Convertible).
- **Spot**: spare capacity at a large discount that AWS can reclaim with a two-minute notice.
## Example
A fleet that runs 24/7 for three years uses the same baseline every hour. A 3-year Compute Savings Plan sized to that baseline turns most of the On-Demand spend into discounted committed spend, and any burst above the commitment is simply billed On-Demand.
W: Savings Plans or Reserved Instances: long-running, predictable usage is exactly what commitment discounts are for. The company pays much less per hour than On-Demand, and a Compute Savings Plan still lets it change instance types later without losing the discount.
X: A=On-Demand only: the claim is false. On-Demand has the highest unit price, and a 1- or 3-year commitment on a steady 24/7 baseline is the standard way to lower long-term cost.
B=Spot without interruption handling: Spot capacity can be reclaimed at any time with two minutes of notice, so running production on it with no handling risks outages. It suits fault-tolerant work, not a steady fleet that must stay up.
D=Dedicated Hosts: a Dedicated Host is a whole physical server reserved for you, used for per-socket or per-core licensing or compliance isolation. It can be shared with other accounts through AWS RAM, but the owner still pays for the whole host, and putting every instance on hosts generally costs more than shared tenancy.
T: Steady, predictable 24/7 usage belongs on Savings Plans or Reserved Instances; Spot is for interruptible work, and On-Demand only for unpredictable or short-lived usage.

G: ## Finding what drives a bill
**AWS Cost Explorer** is the built-in tool for analyzing past and forecast spending. It shows cost and usage over time at daily or monthly granularity and lets you:
- **Group by** service, linked account, Region, usage type or cost allocation tag.
- **Filter** to a date range, a service or a tag value to narrow the cause.
- Save reports and view a forecast of future spend.
## Example
The bill jumps in the middle of the month. In Cost Explorer, set daily granularity, group by **Service**, and look for the bar that grows. If it is EC2, group by **Usage type** next to see whether it is instance hours, data transfer or EBS. For automatic detection of unusual spend, **AWS Cost Anomaly Detection** (part of Cost Management) can alert on spikes.
W: AWS Cost Explorer: it breaks down cost by service and by day, which is exactly the question "what service increased, and when".
X: B=AWS Config history: Config records configuration changes of resources, such as a security group rule edit. It can explain what changed, but it does not show spend or cost by service and date.
C=VPC Reachability Analyzer: it tests whether a network path exists between two resources in a VPC. It has no billing data.
D=CloudWatch Logs Insights: it queries log events in CloudWatch log groups. Cost and usage data is not stored as application logs there, so it cannot break down the bill.
T: Questions about which service costs more and since when are answered in Cost Explorer; Config, Reachability Analyzer and Logs Insights answer configuration, network and log questions.

@ Q002750 explain
G: ## Alerts on spending
**AWS Budgets** lets you set a cost or usage amount (for example `$5,000` per month) and attach alerts to it. Each alert has a threshold and a type:
- **Actual**: fires when the money already spent this period crosses the threshold.
- **Forecasted**: fires when AWS projects that spend by the end of the period will cross the threshold, giving warning before the money is spent.
Alerts are sent by email or to an Amazon SNS topic, and budget actions can also apply an IAM or SCP policy or stop certain instances when a threshold is reached.
## Example
A monthly budget of `$5,000` with a forecasted alert at 100% notifies the team on day 12 if the current pace would reach `$5,600` by month-end, while there is still time to act.
W: AWS Budgets with a forecast alert: a forecasted-spend threshold is designed to warn before the monthly budget is actually exceeded.
X: A=Config compliance timeline: it shows how a resource's compliance with Config rules changed over time. It has no budget amounts or spend forecasts.
B=AWS Artifact: Artifact is a portal for downloading AWS compliance reports (such as SOC reports) and agreements. It does not track or forecast spend.
D=Amazon Inspector: Inspector scans EC2 instances, container images and Lambda functions for software vulnerabilities and network exposure. Its coverage alerts are about scanning, not cost.
T: Warnings that spending is on track to exceed a limit come from AWS Budgets forecasted alerts, not from compliance or security services.

@ Q002751 explain
G: ## Scaling a queue worker fleet
Workers that pull from an Amazon SQS queue should scale on how much work is waiting per worker, not on CPU alone. The common metric is **backlog per instance**:
- Backlog = `ApproximateNumberOfMessagesVisible` from the queue.
- Backlog per instance = backlog / number of `InService` instances in the Auto Scaling group.
- Acceptable backlog per instance = how long a message may wait / average processing time per message.
## Example
Each message takes 2 seconds and messages may wait at most 100 seconds, so one worker can hold a backlog of 50. With 1,500 messages visible and 10 workers, the backlog per instance is 150, so a **target tracking** policy on a custom metric (published by a script or built with CloudWatch metric math) with target 50 scales toward 30 workers.
W: Backlog per instance: it measures pending work relative to current capacity, so the fleet grows when messages pile up and shrinks when the queue drains.
X: A=Disk space per worker: disk usage depends on logs and local files, not on how many messages are waiting, so it would not rise as the queue grows.
C=CloudTrail events per minute: CloudTrail records AWS API calls for auditing. The rate of API events does not reflect how many messages the workers still need to process.
D=Total instances in the account: that counts capacity, not demand, and includes unrelated instances. Scaling on it would not react to the queue at all.
T: Scale queue consumers on backlog per instance (queue depth divided by in-service workers) with target tracking, not on unrelated host or account metrics.

@ Q002752 explain
G: ## Spot Instances for batch work
**Spot Instances** use spare EC2 capacity at a large discount compared with On-Demand. The trade-off: when EC2 needs the capacity back, it sends a **two-minute interruption notice** and reclaims the instance.
Each combination of instance type and Availability Zone is a separate **Spot capacity pool**. Interruptions usually hit one pool at a time, so spreading requests across many pools lowers the chance that the whole job stops.
- In an Auto Scaling group or EC2 Fleet, list several similar types (for example `c5.xlarge`, `c6i.xlarge`, `m5.xlarge`) or use attribute-based instance type selection.
- Use the `price-capacity-optimized` allocation strategy so instances come from pools with the most spare capacity at a low price.
- Make jobs checkpoint or be retried, which a fault-tolerant batch workload already does.
W: Spot with diversified instance types: the workload tolerates interruptions, so it can use the cheapest capacity, and diversification across pools keeps enough instances running when one pool is reclaimed.
X: A=Reserved Instances: they need a 1- or 3-year commitment and pay off for steady usage. A batch job that runs intermittently would pay for idle reservations, and a single size limits flexibility.
B=On-Demand single type: On-Demand has no interruptions but a much higher price than Spot. It gives up the savings the workload's fault tolerance makes possible.
C=Dedicated Instances: they run on hardware dedicated to one account for isolation or compliance and cost more than shared tenancy. Nothing in the requirement needs isolation.
T: Interruption-tolerant batch work belongs on Spot spread across many instance types and AZs; commitments and dedicated tenancy only raise the cost here.

@ Q002753 explain
G: ## Aurora readers and Auto Scaling
An Aurora cluster has one writer and up to 15 **Aurora Replicas** (readers) that share the same cluster storage volume. Applications send reads to the **reader endpoint**, which spreads connections across the replicas.
**Aurora Auto Scaling** uses Application Auto Scaling to add or remove replicas automatically:
- You set a target on a metric such as average CPU utilization of the replicas or average number of connections.
- You set a minimum and maximum replica count, for example 1 to 8.
- When load rises above the target, replicas are added; when it drops, extra replicas are removed after a cooldown.
## Example
Morning traffic pushes average reader CPU to 80% against a target of 50%, so Aurora adds replicas; at night the count falls back to the minimum and the company stops paying for idle readers.
W: Aurora Auto Scaling for Aurora Replicas: it changes the number of readers to follow demand, which is exactly the requirement.
X: A=Global Database secondary Regions: Global Database replicates a cluster to other Regions for disaster recovery and low-latency local reads. It does not add or remove readers in the primary cluster as load changes.
C=Backtrack: Backtrack rewinds an Aurora MySQL cluster's data to an earlier point in time after a mistake. It has nothing to do with read capacity.
D=Aurora cloning: a clone is a separate copy-on-write copy of the cluster, typically for testing or analytics. It does not serve the production reader endpoint or follow demand.
T: A reader count that follows demand is Aurora Auto Scaling; Global Database, Backtrack and cloning address DR, data rewind and copies.

@ Q002754 explain
G: ## How Aurora survives an AZ failure
Amazon Aurora separates compute from storage:
- The **cluster volume** keeps six copies of the data across three Availability Zones, and a write is committed once a quorum of copies has it. Losing an entire AZ does not lose committed data.
- **Aurora Replicas** in other AZs read from the same volume. If the writer fails, Aurora promotes a replica to writer, typically within about a minute or less, and the cluster endpoint points to the new writer.
Compare with RDS Multi-AZ with one standby instance: the standby is not readable and failover generally takes longer, while Aurora replicas serve reads all the time and are ready to be promoted.
## Example
A cluster has a writer in `us-east-1a` and replicas in `us-east-1b` and `us-east-1c`. If `us-east-1a` fails, a replica becomes the writer and the app reconnects through the same cluster endpoint.
W: Aurora with replicas in multiple AZs: storage replicated across three AZs gives minimal data loss, and promoting an existing replica gives fast failover while staying relational.
X: A=DynamoDB single-partition design: DynamoDB is a key-value and document database, not a relational one, and a single-partition design would also concentrate load on one partition.
B=Self-managed database on one EC2 instance: one instance in one AZ is a single point of failure. If the AZ fails, the database is down until someone rebuilds it.
D=RDS single-AZ with daily snapshots: there is no standby to fail over to, and restoring a daily snapshot can lose up to a day of data and takes time.
T: For a relational database with minimal data loss and fast failover across AZs, Aurora with replicas in other AZs beats single instances and snapshot-based recovery.

@ Q002755 explain
G: ## Surviving a full Region outage with DynamoDB
A normal DynamoDB table already stores data across multiple AZs in one Region, so it survives an AZ failure but not the loss of the Region.
**DynamoDB global tables** keep replica tables in two or more Regions:
- Each replica accepts reads and writes, and changes are replicated between Regions, usually within about a second with the default multi-Region eventual consistency.
- If one Region fails, the application switches to the replica in another Region (for example with Route 53 failover) and keeps working with the replicated data.
## Example
A global table with replicas in `us-east-1` and `us-west-2` lets the app write in `us-east-1` normally; during a `us-east-1` outage, traffic is sent to `us-west-2`, which already has the data.
W: DynamoDB global tables: they keep a live, writable copy of the table in another Region, so failover takes minutes instead of a restore.
X: B=TTL: Time to Live deletes items automatically after a timestamp passes. It reduces storage but adds no copy of the data anywhere.
C=On-demand backups in one Region: backups stored in the failed Region cannot be restored while it is down, and a restore creates a new table, which takes time.
D=DynamoDB Accelerator (DAX): DAX is an in-memory cache cluster in one Region that speeds up reads. It is not a durable copy and fails with its Region.
T: Region-level resilience with minimal downtime for DynamoDB means global tables; backups, TTL and DAX stay in one Region.

@ Q002756 explain
G: ## Load balancer nodes and cross-zone load balancing
When a Network Load Balancer is enabled in two AZs, it has a **node** in each AZ, and DNS returns the node IPs.
- With **cross-zone load balancing off** (the default for NLB), each node sends traffic only to targets in its own AZ.
- With **cross-zone load balancing on**, each node can send traffic to healthy registered targets in all enabled AZs.
## Example
AZ-a has 3 targets and AZ-b has 3 targets. All targets in AZ-b fail health checks. Without cross-zone, the AZ-b node has no local targets, so the service depends on DNS steering clients away from that node. With cross-zone, the AZ-b node forwards its requests to the healthy targets in AZ-a, and all traffic is spread across them.
For NLB, cross-zone traffic can incur inter-AZ data transfer charges, which is the trade-off to consider.
W: Cross-zone load balancing: every load balancer node can reach healthy targets in every enabled AZ, so traffic keeps flowing to the remaining healthy targets when one AZ has none.
X: A=TLS termination: a TLS listener decrypts traffic at the load balancer. It changes where encryption ends, not which AZs' targets a node may use.
B=Sticky sessions: stickiness keeps a client on the same target. It does not let a node route to targets in another AZ, and pinned clients still fail when their target does.
C=Longer deregistration delay: this only controls how long in-flight connections are drained when a target is deregistered. It adds no capacity and no cross-AZ routing.
T: To use healthy targets in other AZs when one AZ has none, turn on cross-zone load balancing; listener, stickiness and draining settings do not change routing between AZs.

@ Q002757 explain
G: ## Stateless instances
When a web app keeps user sessions (login state, shopping cart) in instance memory or on local disk, the session disappears whenever that instance is terminated, replaced by Auto Scaling or fails a health check.
The fix is to make the instances **stateless** by moving session data to a shared store:
- **Amazon ElastiCache** (Valkey, Redis OSS or Memcached): very fast in-memory key-value storage, often with a TTL on each session key.
- **Amazon DynamoDB**: durable key-value storage with TTL to expire old sessions.
## Example
The app stores `session:8f3a...` in ElastiCache. A user's next request lands on a brand-new instance, which reads the same key and continues the session as if nothing happened.
W: Store session state externally: any instance can serve any user, so replacing, scaling in or losing an instance no longer loses sessions.
X: A=Larger minimum size: more instances reduce load per instance but each still keeps its own sessions in memory, so replacing any one of them still logs its users out.
C=Permanent sticky sessions: stickiness sends a user back to the same instance, but when that instance is replaced the session is gone anyway, and it can also unbalance load.
D=Larger instances: fewer replacements only make the problem rarer. Instances still fail and get replaced, and session data on them is still lost.
T: Session resilience comes from keeping state outside the instance, not from more, bigger or sticky instances.

@ Q002758 explain
G: ## Amazon Data Lifecycle Manager
**Amazon Data Lifecycle Manager (DLM)** automates the creation, retention and deletion of EBS snapshots and EBS-backed AMIs.
A policy defines:
- **Target resources**: volumes or instances selected by tag, for example `Backup=true`.
- **Schedule**: how often to create snapshots, such as every 6 hours or daily at a fixed time.
- **Retention**: keep a count of snapshots or keep them for an age, such as 14 days, after which DLM deletes them.
- Optional cross-Region copy and cross-account sharing.
## Example
A policy targeting `Backup=true` with a 6-hour interval and 14-day age retention keeps about 56 snapshots per volume, and new volumes get covered as soon as they are tagged.
AWS Backup can also schedule EBS backups centrally; the key point is that a managed policy, not a manual process, handles it.
W: Data Lifecycle Manager policy: it snapshots tagged volumes on the required schedule and deletes them after 14 days with no scripts or manual steps.
X: B=S3 Lifecycle rules: EBS snapshots are stored by AWS but are not objects in your S3 buckets, so S3 Lifecycle rules cannot create or expire them.
C=CloudTrail Lake queries: CloudTrail Lake runs SQL over recorded API activity. A query reads history; it never creates a snapshot.
D=Manual snapshot runbook: people must remember to run it every six hours and delete old snapshots, which is error-prone and the opposite of minimal management.
T: Scheduled, tag-based EBS snapshots with automatic retention are a DLM (or AWS Backup) policy, not S3 Lifecycle or manual work.

@ Q002759 explain
G: ## Backups that survive a Region failure
A backup stored only in the Region that fails cannot be used to recover there or elsewhere while the Region is down. Disaster recovery needs a copy in a **second Region**.
**AWS Backup** plans contain rules with a schedule and retention, and each rule can add a **copy action** to a backup vault in another Region (and optionally another account).
- For EC2, the recovery point is an AMI with its EBS snapshots; the copy creates the same in the destination Region.
- The copy can have its own retention period.
## Example
A plan backs up instances tagged `Tier=prod` daily into a vault in `eu-west-1` and copies each recovery point to a vault in `eu-central-1`. If `eu-west-1` fails, the team launches instances from the copies in `eu-central-1`.
W: AWS Backup plan with a cross-Region copy rule: every recovery point is automatically copied to another Region, so the EC2 instances can be restored there when the primary Region is lost.
X: A=Snapshots shared with another account in the same Region: sharing changes who can use the snapshot, not where it is stored. It is still in the failed Region.
B=AMIs only in the primary Region: an AMI is a Regional resource. If the Region is down, its AMIs cannot be used, and nothing exists in the second Region.
D=Same-Region copies only: extra copies in the same Region protect against accidental deletion, not against the whole Region being unavailable.
T: Region-level recovery requires recovery points copied to another Region, such as an AWS Backup cross-Region copy rule.

@ Q002760 explain
G: ## Proving backups can be restored
A backup that has never been restored is an assumption, not a guarantee. **AWS Backup restore testing** automates the check:
- A **restore testing plan** runs on a schedule and picks recovery points (for example the latest one) from selected vaults and resource types.
- AWS Backup restores them into temporary resources, records whether the restore succeeded and how long it took, then deletes the test resources.
- You can add your own validation, for example an EventBridge rule that triggers a Lambda function to check the restored data before cleanup.
## Example
A weekly restore testing plan restores the newest RDS and EBS recovery points; the job history shows restore duration, which helps confirm the team can meet its RTO.
W: Restore testing plans: they regularly perform real restores from recovery points, which is the only way to verify the backups are recoverable.
X: A=Vault access policies: these resource-based policies control who can access or delete recovery points in a vault. They protect backups but never restore one.
B=Legal hold: a legal hold stops selected recovery points from being deleted, for example during litigation. It keeps backups but does not test them.
C=Audit logs only: logs and AWS Backup Audit Manager reports show that backup jobs ran and met policies. A successful backup job does not prove the data restores correctly.
T: To verify recoverability, restore on a schedule with AWS Backup restore testing; access policies, legal holds and logs protect or report on backups but never restore them.

@ Q002761 explain
G: ## The four DR strategies
AWS describes four disaster recovery strategies, from cheapest and slowest to most expensive and fastest:
- **Backup and restore**: back up data to another Region and rebuild everything after a disaster. RPO and RTO in hours.
- **Pilot light**: core data is replicated live (for example a database replica) and other infrastructure is defined but switched off or scaled to zero. RTO in tens of minutes.
- **Warm standby**: a scaled-down but running copy of the full stack that is scaled up on failover. RTO in minutes.
- **Multi-site active/active**: full capacity running in two or more Regions. Near-zero RTO and highest cost.
## Example
An internal reporting app can be down for four hours. Backup and restore or pilot light meets that target without paying for a running second environment.
W: Backup and restore or pilot light: both meet recovery objectives measured in hours while keeping little or no infrastructure running in the recovery Region, so they are the low-cost choices.
X: B=Multi-site active/active: it gives near-zero downtime by running full production in two Regions, which costs the most and far exceeds a recovery time of hours.
C=No DR plan: AWS services are designed for high availability, but the customer is responsible for planning recovery of its own workloads. Without a plan, recovery time is unknown.
D=Warm standby at full production size: warm standby normally runs scaled down; at full size it costs almost as much as active/active, which is more than a recovery-within-hours target needs.
T: Choose the cheapest DR strategy that meets RTO and RPO: hours means backup and restore or pilot light, minutes or less means warm standby or active/active.

@ Q002762 explain
G: ## S3 replication
S3 replication copies objects from a source bucket to a destination bucket automatically and asynchronously.
- **Cross-Region Replication (CRR)**: the destination bucket is in a different Region, which is the choice for disaster recovery, compliance copies in another Region and lower-latency access elsewhere.
- **Same-Region Replication (SRR)**: the destination is in the same Region, used for log aggregation or copies between accounts.
Requirements and behavior:
- Versioning must be enabled on both buckets, and S3 needs an IAM role with permission to replicate.
- New objects are replicated after the rule is created; existing objects need **S3 Batch Replication**.
- **S3 Replication Time Control** adds an SLA that most objects replicate within 15 minutes.
W: S3 Cross-Region Replication: it keeps a copy of the critical objects in a bucket in another Region, which is available if the source Region fails.
X: A=Storage Lens: Storage Lens gives usage and activity metrics and recommendations across buckets. It does not copy any data.
B=Same-Region Replication: the copy stays in the same Region, so a Region-wide failure affects both buckets.
C=Transfer Acceleration: it speeds up long-distance uploads and downloads through CloudFront edge locations to one bucket. It creates no second copy.
T: A copy of S3 data in another Region for DR is Cross-Region Replication; Same-Region Replication stays in the failure domain.

@ Q002763 explain
G: ## What makes Auto Scaling recover quickly
An Auto Scaling group replaces an instance that fails its EC2 or ELB health checks by launching a new one from its **launch template**. Two things decide how well that works:
- **What it launches**: the launch template must reference an AMI that still exists, boots correctly and contains the current application, plus valid security groups, instance profile and user data. A broken or deleted AMI means every replacement fails.
- **Where it launches**: with subnets in several AZs, the group spreads instances and, if an AZ has problems, launches replacements in the healthy AZs and later rebalances.
## Example
An ASG across `us-east-1a`, `1b` and `1c` with a launch template on a tested AMI loses an AZ; it replaces the lost instances in the other two AZs within minutes.
W: B=Multiple Availability Zones: spreading instances means one AZ failure removes only part of the capacity, and the group can launch replacements in the AZs that are still healthy.
E=Launch template with a working, current AMI: replacements come up quickly and correctly only if the template launches a valid, up-to-date image.
X: A=Desired capacity zero: it terminates every instance, so there is nothing running to recover and the application is simply off.
C=Hard-coded IP addresses: replacement instances get new private IPs, so code that points to old addresses breaks after every replacement. Use a load balancer or DNS instead.
D=Disable health checks: health checks are how the group detects failed instances. Without them, failed instances stay in service and are never replaced.
T: Fast self-healing needs a healthy launch template and multi-AZ placement; turning off health checks or capacity, or hard-coding IPs, defeats replacement.

@ Q002764 explain
G: ## Finding single points of failure
A **single point of failure (SPOF)** is any one component whose failure takes the whole system down. Review each tier:
- **Entry**: DNS and load balancing. Route 53 and an Application Load Balancer enabled in several AZs have no single node to lose.
- **Compute**: several instances in an Auto Scaling group across AZs.
- **Data**: a Multi-AZ database keeps a synchronous standby (or Aurora replicas) in another AZ and fails over automatically.
- **Network egress**: one NAT gateway per AZ, not one shared device.
## Example
An ALB in two AZs in front of an ASG, with RDS Multi-AZ behind it, keeps running when any single instance, node or AZ fails.
W: C=Multi-AZ database: a standby in another AZ with automatic failover removes the database as a single point of failure.
E=ALB across multiple AZs: the load balancer has nodes in each enabled AZ and routes only to healthy targets, so losing one instance or one AZ does not stop the web tier.
X: A=Single on-premises DNS server: if that one server fails, names stop resolving and the whole application appears down. It is itself a SPOF.
B=Single NAT instance: one EC2 instance handles all outbound traffic from every private subnet, so its failure cuts off internet access for all of them.
D=One EC2 instance for everything: any instance failure, patch reboot or AZ problem takes the entire application offline.
T: Remove SPOFs by making each tier redundant across AZs, such as a multi-AZ load balancer and a Multi-AZ database, rather than relying on any single server.

@ Q002765 explain
G: ## NAT gateways and Availability Zones
A standard (zonal) **NAT gateway** is created in one subnet and therefore lives in one Availability Zone. It is highly available inside that AZ, but if the AZ has an outage, the NAT gateway is unavailable too.
- If private subnets in `a`, `b` and `c` all have `0.0.0.0/0` pointing to a NAT gateway in `a`, an outage of AZ `a` cuts internet access for instances in `b` and `c` even though those AZs are healthy.
- Cross-AZ traffic to the shared gateway also incurs data transfer charges.
## Designs that remove the dependency
- Create one zonal NAT gateway per AZ, and give each AZ's private subnets their own route table pointing to the local gateway.
- Or use a NAT gateway in **regional availability mode**, which AWS operates across the AZs of the VPC.
W: AZ failure cuts outbound access for all AZs: all three AZs depend on one zonal gateway, so a failure of that one AZ breaks internet egress for workloads in the healthy AZs too.
X: A=Only one subnet at a time: a NAT gateway can serve any number of subnets that route to it. Sharing is allowed; the problem is the single AZ.
B=No routing to NAT gateways in other AZs: routing to a NAT gateway in another AZ does work, which is exactly how this setup functions today. It is allowed but creates a cross-AZ dependency.
D=Daily recreation: NAT gateways are managed and do not need to be recreated to keep working.
T: Every AZ's private subnets should use a NAT gateway in their own AZ (or a regional NAT gateway), so one AZ failure cannot remove egress for the others.

@ Q002766 explain
G: ## RPO and RTO
Two objectives define disaster recovery targets:
- **Recovery point objective (RPO)**: the maximum acceptable **data loss**, measured as time before the failure. RPO of 15 minutes means that after recovery, at most the last 15 minutes of changes may be missing, so backups or replication must capture data at least that often.
- **Recovery time objective (RTO)**: the maximum acceptable **downtime**, from the failure until service is restored.
## Example
With RPO 15 minutes and RTO 1 hour, a failure at 10:00 may lose data written after 09:45, and the application must be running again by 11:00. Continuous backups or replication meet the RPO; the recovery procedure must meet the RTO.
W: Recovery point objective: "maximum acceptable data loss, expressed in time" is the definition of RPO.
X: A=Mean time between failures: MTBF is the average time a system runs between failures. It describes reliability, not how much data may be lost.
C=Service level indicator: an SLI is a measured value such as availability percentage or request latency. It is a measurement, not a data loss target.
D=Recovery time objective: RTO limits how long the service can be down, not how much data can be lost.
T: RPO is the data loss you can tolerate; RTO is the downtime you can tolerate.

@ Q002767 explain
G: ## Scaling policy types
EC2 Auto Scaling offers several ways to change capacity:
- **Target tracking** and **step scaling**: react to CloudWatch metrics after load has already changed.
- **Scheduled actions**: change capacity at times you set by hand.
- **Predictive scaling**: analyzes the history of a load metric (such as CPU or request count), detects daily and weekly patterns, forecasts the next 48 hours, and schedules capacity so instances are running before the load arrives.
Predictive scaling needs at least a day of history and forecasts better with more; it can run in forecast-only mode first so you can review its predictions. It is often combined with target tracking to handle unexpected changes.
## Example
Traffic rises every weekday at 08:00. Predictive scaling learns this and launches instances shortly before 08:00, so they are warmed up when users arrive.
W: Predictive scaling: it learns the recurring weekly pattern from history and provisions capacity ahead of time, which is exactly what the team wants.
X: B=Manual scaling: someone changes desired capacity by hand. Nothing is learned or automated.
C=Lifecycle hooks: they pause instances during launch or termination to run custom actions. They do not decide when or how much to scale.
D=Step scaling: it adds or removes capacity when a CloudWatch alarm fires, after the load has already risen, and does not learn patterns.
T: Recurring, predictable load is handled ahead of time by predictive scaling; step and target tracking policies only react after the metric changes.

G: ## Auto Scaling lifecycle hooks
When an Auto Scaling group terminates an instance during scale-in, it normally shuts it down right away. A **lifecycle hook** on the `autoscaling:EC2_INSTANCE_TERMINATING` transition changes that:
- The instance moves to the `Terminating:Wait` state and keeps running.
- An event goes to EventBridge (or an SNS topic or SQS queue), which can start a Lambda function or a Systems Manager Run Command to upload logs to S3.
- When the work is done, the script calls `CompleteLifecycleAction`; if nobody calls it, the hook continues after its heartbeat timeout (default one hour).
## Example
On scale-in, the hook pauses the instance, an EventBridge rule runs an SSM document that copies `/var/log/app/*` to S3, then completes the action, and the instance is terminated.
W: Lifecycle hook on termination: it pauses the instance before it is terminated so the log upload can finish reliably.
X: A=Scheduled action every five minutes: scheduled actions change group capacity at fixed times. They know nothing about which instance is about to be terminated, so logs written just before termination can be lost.
B=Termination protection: EC2 termination protection only blocks termination through the EC2 API and does not stop Auto Scaling from terminating the instance. Even instance scale-in protection would simply keep the instance, not run the upload.
C=Longer cooldown: a cooldown delays the next scaling activity. It does not pause the terminating instance or run any action on it.
T: To run work on an instance before Auto Scaling terminates it, use a termination lifecycle hook; schedules, cooldowns and protection settings do not give that hook point.

G: ## Aurora Backtrack
**Backtrack** is an Aurora MySQL feature that rewinds the existing cluster to an earlier point in time, in place, without restoring from a backup.
- It must be enabled beforehand, when the cluster is created or restored (it cannot be turned on later for a cluster created without it), with a target backtrack window of up to 72 hours.
- Aurora keeps change records for that window; a backtrack to a time usually finishes within minutes because no new cluster is created.
- The cluster is briefly unavailable during the rewind, and all changes after the chosen time are undone.
## Compared with point-in-time restore
Point-in-time restore from automated backups also reaches any second within the retention period, but it always creates a **new** cluster, so endpoints change and the restore takes longer.
## Example
A bad `UPDATE` ran at 14:20. The team backtracks the cluster to 14:19; the same endpoints now serve the data as it was before the update.
W: Aurora Backtrack: it rewinds the same Aurora MySQL cluster to 20 minutes ago quickly and in place, which is exactly the requirement.
X: A=Week-old manual snapshot: restoring it loses a week of legitimate changes and creates a new cluster instead of fixing the existing one in place.
B=Aurora cloning: a clone is a new copy-on-write cluster of the current data, which already includes the bad update. It does not rewind anything.
C=Cross-Region read replica: replication copies the bad update to the replica within seconds, so it holds the same wrong data.
T: To undo a recent mistake in place on Aurora MySQL, use Backtrack; clones and replicas copy the bad data, and snapshots restore to a new cluster.

G: ## Multi-Region static sites with CloudFront
An S3 bucket lives in one Region. To keep a static site up during a Regional S3 problem, keep a second copy and let the CDN switch to it:
- **S3 Cross-Region Replication** copies objects from the primary bucket to a bucket in another Region.
- A **CloudFront origin group** lists a primary and a secondary origin. When the primary returns selected error codes (such as 500, 502, 503, 504) or cannot be reached, CloudFront retries the request against the secondary origin.
Origin failover applies to `GET`, `HEAD` and `OPTIONS` requests, which fits a static website. Cached content keeps being served from edge locations as well.
## Example
Primary bucket in `us-east-1`, replica in `us-west-2`, both in one origin group. When `us-east-1` S3 errors, CloudFront serves the site from `us-west-2` without any DNS change.
W: Replicate to a second Region and use CloudFront origin failover: a copy of the files exists outside the affected Region, and CloudFront switches to it automatically when the primary origin fails.
X: A=Versioning in one bucket: versioning keeps previous versions of objects to recover from overwrites and deletes. All versions stay in the same bucket and Region.
B=S3 One Zone-IA: it stores data in a single Availability Zone, which is less resilient than S3 Standard, the opposite of the goal.
D=Single EC2 instance: one instance in one AZ is a single point of failure and is less available than S3.
T: Regional resilience for a static S3 site comes from a replicated bucket in another Region plus CloudFront origin failover, not from features inside one bucket or one server.

G: ## What a DR runbook needs
A **disaster recovery runbook** is the document the team follows during a real incident, often under stress. It should contain:
- **Step-by-step procedures**: exact actions to fail over and fail back, for example promote the replica, update the Route 53 record, scale the standby.
- **Owners and contacts**: who performs each step and who decides to declare a disaster.
- **Objectives and dependencies**: the RTO and RPO for each application and what must be recovered first.
- **Testing**: regular DR drills or game days that run the procedure and measure whether recovery meets RTO and RPO, with the runbook updated after each test.
A runbook that is never tested usually fails when needed, for example because an AMI or credential it relies on has changed.
W: A=Step-by-step recovery procedures with owners: clear actions and accountable people are what lets the team recover correctly and quickly.
E=Regular tests that validate RTO and RPO: only tested procedures prove the plan meets its recovery objectives and reveal outdated steps.
X: B=Marketing copy: website marketing text has no role in restoring systems during a disaster.
C=Favorite programming languages: personal preferences do not help anyone recover a workload.
D=Office seating chart: where people sit does not describe how to recover systems, and teams often recover remotely anyway.
T: A DR runbook needs owned, step-by-step procedures and regular tests against RTO and RPO; everything else is noise.

G: ## Lambda concurrency
**Concurrency** is the number of requests a Lambda function is handling at the same time. All functions in an account and Region share a concurrency quota (1,000 by default, which can be raised). When the pool is used up, new invocations are **throttled**.
- **Reserved concurrency** sets aside a fixed number of concurrent executions for one function. No other function can use that capacity, so a burst elsewhere cannot starve it.
- It is also a **maximum** for that function: it cannot scale beyond the reserved value.
- It costs nothing extra; **provisioned concurrency** is a separate, billed feature that keeps environments initialized to avoid cold starts.
## Example
With account concurrency 1,000, reserving 200 for `order-processor` guarantees it 200 concurrent executions, while other functions share the remaining 800.
W: Reserved concurrency: it guarantees the function a dedicated share of the account's concurrency, so it always has capacity even when other functions are busy.
X: A=Longer timeout: a longer timeout lets each invocation run longer, which can actually keep concurrency occupied longer. It reserves nothing.
C=Larger memory: more memory also gives more CPU and can make each invocation faster, but it does not guarantee any concurrent executions.
D=Dead-letter queue: a DLQ captures asynchronous events that failed after retries. It records failures rather than preventing throttling.
T: Guaranteed capacity for one Lambda function is reserved concurrency; timeout, memory and DLQs change runtime, speed or failure handling, not capacity.
