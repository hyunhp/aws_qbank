# SOA-C03 fixes of published questions (full blocks pinned with I:)

@ SOA-C03 D1 T1.1 applied troubleshooting
S: To turn on Container Insights for an existing Amazon EKS cluster, an administrator attached CloudWatchAgentServerPolicy to the worker node role. Afterward, only the standard EC2 instance metrics for the worker nodes and the EKS control plane metrics appear in CloudWatch. No Container Insights node, pod, or container metrics are visible. What is the MOST likely missing component?
A: The EKS cluster must first be upgraded to the latest supported Kubernetes version
B: The Amazon VPC CNI plugin needs to be reinstalled on every worker node in the cluster
C: IAM Identity Center has not been configured as the identity source for the cluster
D: The CloudWatch agent DaemonSet (Observability add-on) is not deployed on the nodes
K: D
G: ## Where Container Insights metrics come from on EKS
Container Insights does not read metrics out of the EKS control plane by itself. On Amazon EKS it depends on a collector running on every worker node:
- The **Amazon CloudWatch Observability EKS add-on** (or a manual install) deploys the **CloudWatch agent as a DaemonSet** plus Fluent Bit for logs.
- Each agent pod reads kubelet/cAdvisor data on its node and publishes Container Insights metrics such as `node_cpu_utilization`, `pod_cpu_utilization` and `container_memory_utilization`, and the cluster-level rollups built from them, to the `ContainerInsights` namespace.
- The node role or an IAM role for service accounts needs the `CloudWatchAgentServerPolicy` permissions to publish.
## What still shows up without the agent
The basic `AWS/EC2` metrics for the worker instances come from the EC2 hypervisor, and control plane metrics come from EKS itself. Both keep appearing even when nothing is collecting inside the cluster, which is exactly the symptom here.
W: CloudWatch agent DaemonSet missing: without the agent pods on the nodes, nothing collects node, pod or container data, so the `ContainerInsights` namespace stays empty while EC2 and control plane metrics still arrive. Installing the CloudWatch Observability add-on (with publish permissions) fixes it.
X: A=Upgrade Kubernetes first: Container Insights supports all currently supported EKS versions, and a version gap would not produce this pattern of EC2 metrics present but every Container Insights metric missing.
B=Reinstall the VPC CNI: the VPC CNI assigns pod IP addresses. If it were broken, pods would fail to get networking, but it has no role in collecting or publishing CloudWatch metrics.
C=IAM Identity Center: Identity Center manages human sign-in to AWS accounts and applications. The agent publishes with the node role or a service-account IAM role, not with Identity Center.
T: On EKS, Container Insights needs the CloudWatch agent DaemonSet (Observability add-on) on the nodes; EC2 and control plane metrics alone mean the collector is missing.
V: Amazon CloudWatch, Amazon EKS

@ SOA-C03 D5 T5.1 advanced troubleshooting
S: A subnet's network ACL has outbound rule 100 that allows all traffic. To stop instances from initiating connections to high ports on the internet, an administrator adds outbound rule 90 that denies TCP ports 1024-65535 to 0.0.0.0/0. Immediately afterward, clients on the internet can no longer complete HTTPS connections to a web server in the subnet. Security groups were not changed. What is the most likely cause?
A: Network ACL rules are evaluated in random order, so the new deny sometimes wins over the allow
B: A network ACL cannot contain both allow and deny rules, so the new rule broke the rule set
C: The stateless deny, numbered before the allow, drops responses sent to client ephemeral ports
D: The instance security group now blocks the traffic because it inherits the new network ACL rule
K: C
G: ## How network ACLs evaluate traffic
A network ACL is a **stateless** filter at the subnet boundary. It has separate inbound and outbound rule lists, and each list is evaluated in ascending rule-number order: the first rule that matches a packet decides allow or deny, and later rules are ignored.
## Why return traffic matters
A client opening HTTPS uses destination port `443` and a random ephemeral source port; AWS recommends allowing 1024-65535 to cover every client operating system. The server's reply goes back to that client port. Because a network ACL keeps no connection state, the reply is checked against the **outbound** rules like any new packet.
- Outbound rule 90 denies TCP 1024-65535 to `0.0.0.0/0` and is evaluated before rule 100.
- Every response from the web server to a client's ephemeral port matches rule 90 and is dropped, so the TCP handshake never completes.
A safer approach is to scope the deny to specific destinations, or block instance-initiated traffic with security groups, which are stateful and always allow replies.
W: Stateless deny before the allow: rule 90 is evaluated before rule 100, and because network ACLs do not track connections, the server's replies to client ephemeral ports hit the deny and are dropped, breaking every inbound HTTPS session.
X: A=Random evaluation order: network ACL rules are always evaluated in ascending rule-number order, and the first match wins. The outage is consistent, not intermittent.
B=No mixing allow and deny: network ACLs are designed to hold both allow and deny rules in the same list; that is how you block specific ranges while allowing the rest.
D=Security group inherits the rule: security groups are evaluated independently of network ACLs and are stateful, so they automatically allow responses; nothing was changed in them.
T: Network ACLs are stateless and first-match by rule number: an outbound deny on ephemeral ports placed before the allow breaks return traffic for inbound connections.
V: Amazon VPC

@ SOA-C03 D1 T1.2 advanced use-case
S: When a critical CloudWatch alarm fires, a team wants AWS to automatically create a tracked operational work item for the on-call engineers and immediately start a Systems Manager Automation runbook that collects diagnostics. Which approach meets this requirement?
A: Have the alarm trigger an Amazon Inspector coverage report and attach it to a new finding
B: Configure the alarm to create an OpsCenter OpsItem and an EventBridge rule to run the runbook
C: Send the alarm to AWS Cost Anomaly Detection so that it opens a monitor alert with a runbook
D: Enable AWS Trusted Advisor priority checks so that the alarm opens a tracked recommendation
K: B
G: ## Turning an alarm into tracked work plus automated response
AWS Systems Manager gives operators two pieces that fit together:
- **OpsCenter** stores **OpsItems**: operational work items with status, severity, related resources, runbook suggestions and history. A CloudWatch alarm can create an OpsItem directly through its **Systems Manager action**, so every critical alarm becomes a tracked item.
- **Automation** runs **runbooks** (for example `AWS-RestartEC2Instance` or a custom diagnostics runbook). An Amazon EventBridge rule that matches the `CloudWatch Alarm State Change` event for the alarm can start the runbook immediately as its target.
Example: the alarm `web-5xx-critical` enters ALARM, OpsCenter opens an OpsItem for the on-call team, and EventBridge starts a runbook that captures logs and instance diagnostics that responders can review from the OpsItem.
W: OpsItem plus EventBridge-triggered runbook: the alarm's Systems Manager action creates a tracked OpsItem in OpsCenter, and an EventBridge rule on the alarm state change starts the Automation runbook right away, meeting both requirements.
X: A=Inspector coverage report: Inspector reports which resources it scans for vulnerabilities. It cannot be triggered by an operational alarm, and it neither creates work items for operators nor runs runbooks.
C=Cost Anomaly Detection: it watches spending patterns and alerts on unusual cost. It does not accept CloudWatch alarms as input and has no work-item tracking or runbook execution.
D=Trusted Advisor priority checks: they surface best-practice recommendations curated for the account. They do not react to alarms, open operational work items, or run Automation runbooks.
T: Alarm to tracked work: CloudWatch alarm action creates an OpsCenter OpsItem; alarm to automated response: EventBridge rule starts a Systems Manager Automation runbook.
V: AWS Systems Manager

@ SOA-C03 D3 T3.1 advanced use-case
S: An Elastic Beanstalk update must not reduce capacity and should roll back quickly if new instances fail. Which deployment policy fits?
A: Rolling deployment policy
B: Immutable deployment policy
C: Rolling with additional batch
D: All at once deployment policy
K: B
G: ## Elastic Beanstalk deployment policies
Beanstalk offers several ways to roll out a new application version:
- **All at once**: every instance is updated together; fastest, but causes downtime and a failed deploy affects all instances.
- **Rolling**: updates batches of existing instances, so capacity drops by one batch at a time.
- **Rolling with additional batch**: launches an extra batch first to keep full capacity, then updates in batches; rolling back means running another rolling update with the old version.
- **Immutable**: launches a full set of new instances with the new version in a temporary Auto Scaling group. Only when they pass health checks are they moved into the original group and the old instances terminated.
- **Traffic splitting**: like immutable, but sends a percentage of traffic to the new instances for a canary period.
With immutable, a failure is handled by simply terminating the temporary Auto Scaling group; the original instances were never touched and keep serving.
W: Immutable: the old instances keep serving at full capacity while new ones launch in a temporary Auto Scaling group, and rolling back is just discarding those new instances, which is much faster than redeploying.
X: A=Rolling: it takes one batch of existing instances out of service at a time, so capacity drops during the deploy, and a failure leaves a mix of versions that needs another deployment to undo.
C=Rolling with additional batch: the extra batch keeps full capacity, but the existing instances are still updated in place, so rolling back means another full rolling deployment of the old version.
D=All at once: all instances are updated together, causing a brief outage, and a bad version breaks every instance until the previous version is redeployed.
T: Immutable keeps full capacity and rolls back by discarding the new instances; in-place policies either reduce capacity or need a redeploy to roll back.
V: AWS Elastic Beanstalk
